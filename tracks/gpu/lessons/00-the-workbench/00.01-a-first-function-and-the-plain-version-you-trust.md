# 00.01 A first function, and the plain version you trust

Every function this track makes fast is written twice: a plain version that
nobody could get wrong, and the version being made fast, which is held to
it. This lesson writes the first pair, two ways of adding two arrays, and
the numbers they work on, which come from a seed so that every machine sees
the same ones.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

The whole track, read from the bottom up. A **kernel** is one function that
a GPU runs as thousands of threads at once. An inference server such as
vLLM is mostly Python; the arithmetic of its model runs in a few kernels
underneath, and this track writes them.

Follow one prompt down the map. Module 09 runs a small language model on
your kernels and sets its answers and speed against PyTorch's. Each
operation of that model is a kernel from a module below: element-wise ones
(02), matrix multiply (03), sums across a block of threads for RMS norm and
softmax (04), rotary positions and the KV cache kept in blocks (05),
attention for one new token (06) and for a whole prompt (07), then the same
on 16-bit numbers (08). Each kernel's answer comes down to the workbench,
which says whether it is right and how long it took.

The track builds upward. The workbench comes first: nothing above it can
be believed without it. Module 01 makes matrix multiply fast on the CPU,
where the ideas that make a kernel fast (the order memory is read in,
several numbers per instruction, tiles that fit a cache, many workers) can
be stepped through in a debugger. Both run on any laptop with a C compiler.
From module 02 on you need an NVIDIA GPU: your own, a cloud machine or a
hosted notebook.

Two rules hold in every lesson. A function is checked against a slow, plain
version before it is timed. And a speed on a page is one you measure: the
page names the machine its numbers came from, and yours will differ.

## The idea

![The same eleven sums, one at a time and four at a time](figures/00.01-two-versions.svg)

The smallest kernel there is adds two arrays, `out[i] = a[i] + b[i]`.
`add_ref` does it one element at a time, in a loop short enough to trust by
reading. `add` does the same sums four elements a pass, then the rest
singly. For n = 11 its passes start at 0 and at 4; a third would need
element 11, which does not exist, so 8, 9 and 10 are the **tail**. So
`add` has a place to be wrong that `add_ref` has not. Every fast version
later in the track is like `add`, and answers to a plain one like
`add_ref`.

<!-- verify: mention names="rand()" outside reason="the C library's generator, not this project's" -->
The numbers come from a **seed**, which decides every number a generator
gives after it: the same seed gives the same arrays on every machine, so a
page can show values and your run prints the same ones. The C library's
`rand()` cannot promise that, since every C library has its own: seeded
with 1, macOS's gives 16807 first, glibc's 1804289383.

![From a seed to a float](figures/00.01-seed.svg)

### `add_ref` and `add`

`add_ref` is the definition written as a loop. `add`'s first loop runs
while a whole pass of four still fits; its second goes on from where the
first stopped to n.

### xorshift64*: the next 32 bits

The generator is **xorshift64***. For each number its 64-bit state is
stirred by three shifts, right 12, left 25 and right 27, each XORed back
in; then it is multiplied by a 64-bit constant, and the product's top 32
bits are the number given out. It is the generator llama2.c samples with, bit for bit: the
same shifts, constant and bits as `random_u32` in its run.c.

### a float in [0, 1)

Of those 32 bits the top 24 are kept and divided by 2^24. A float holds 24
bits exactly, so every value this gives, from 0 up to 1 - 2^-24, is a float
with nothing rounded. llama2.c's `random_f32` does the same.

### an array from a seed

`rng_fill` starts the generator at the seed itself, as llama2.c does, and
turns each number f into 2f - 1: values in [-1, 1), on both sides of 0.

### wb show

`wb`, the workbench, is the program this module grows. `wb show` fills a
from the seed and b from the seed plus one, adds them with `add`, and
prints n, the seed and the first four values of each array.

## How it works

### Four more, counted without going below 0

`add`'s first loop asks whether four more elements remain like this:

```
    for (; i + 4 <= n; i += 4) {
```

The obvious `i < n - 3` is wrong: n is a `size_t`, which has no negative
values, so for n below 3, n - 3 wraps around to a huge number and the loop
writes past the end of out. With an addition the test is right for every
n, 0 included. That keeps the **invariant** both versions share: every
element below n written once, nothing from n on.

### The seed is the first state

Because the seed is the generator's first state, 0 cannot be one: each of
xorshift's steps turns 0 into 0, so every number would be 0 and every value
of a -1. Nothing in rng.c stops it; `wb` refuses it and says why:

<!-- verify: session -->
```
$ ./wb show -s 0; echo $?
wb: -s 0: xorshift's state 0 never changes, so every number would be the same; a seed is 1 to 4294967295
2
```

llama2.c never meets this: it replaces a seed of 0 or less with the time.
The seeds stop at 4294967295 so that b's, one more, can never wrap around
to 0.

## Decide the boundary

Here the plain version sits in the same language and file as the version it
checks: `add_ref` can be read in ten seconds and needs nothing installed.
The other kind comes from another system, numpy or PyTorch, which module 09
sets the whole model against: its bugs found by far more people than will
ever read `add_ref`, at the cost of an install, a second language, and a
difference in arithmetic to explain whenever the two disagree. Who checks
the reference?

## Break it

Make the tail stop one element early: in `build/at/gpu/00.01/add.c`, change
the tail's test so that the line reads `for (; i < n - 1; i++)`. Build it
and look again:

Exactly what it printed before. Yet element 1002, the last, is never

first four. Put the line back.
