# 00.02 Right before fast: checking against a reference

A checker compares an answer with the plain version's, every element of
it, and says in one line whether they agree and, if not, where they differ
most. This lesson writes it, with the rule for when two floats are close
enough, which every later lesson leans on.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

The checker is the middle piece of the workbench. It is given two arrays,
the answer of the version under test and the plain version's, and a
tolerance; it gives back one line, ok or not, naming the element furthest
off. Everything above it on the map comes through it before it is timed:
`add` here, the matrix multiplies of module 01, every GPU kernel after
them. Before this lesson a wrong answer was seen only if it happened to be
printed. After it, every element is looked at.

## The idea

![What counts as close: the allowance around want](figures/00.02-allowance.svg)

Lesson 00.01 ended with `add` wrong in its last element and `wb show`
printing what it printed before. A checker looks at every element instead:
it runs the plain version and the version under test on the same inputs and
compares the answers one element at a time.

For `add` the comparison is `==`. Both versions do one addition for each
element, of the same two floats, rounded the same way whatever loop is
around it, so they must agree to the last bit. From module 01 on they will
not: the versions add many terms in different orders, a float is rounded
after every step, and two right answers differ in their last bits. Then
close needs a rule: `|got - want| <= atol + rtol * |want|`, with want the
plain version's answer and got the other.

**atol**, the absolute tolerance, is an error allowed whatever the value;
**rtol**, the relative tolerance, one allowed in proportion to it. Neither
works alone. With rtol alone nothing is allowed around a want of 0. With
atol alone one number must serve every size: an error of 0.002 is noise on
20 and twice the answer on 0.001.

Take rtol = 1e-4 and atol = 1e-3, the values lesson 01.01 uses. Want 20,
got 20.002: the error is 0.002, the allowance 0.001 + 0.0001 x 20 = 0.003,
so it is good. Want 0, got 0.002: the same error, but the allowance is atol
alone, 0.001, so it is bad. This is numpy.isclose's rule, and like numpy's
it is not symmetric: the allowance comes from want, the side that is
trusted, so swapping the two can change the verdict.

### `check_close`

`check_close` walks both arrays once. For each element it works out the
allowance from want and the error, counts the element if it is bad, and
keeps the **worst** one, the element furthest past its own limit. The
`check_result` it returns holds the count and that element, for the report
to name.

### how far past the limit

`over` gives an element's distance from its limit as the error over the
allowance: 1 is exactly at the limit, more than 1 is outside it. With
nothing allowed, any error at all is infinitely far.

### which of two elements is worse

`further` says whether an element beats the worst so far: a NaN beats
everything, then the larger distance from the limit, then, at the same
distance, the larger error. A tie keeps the earlier element.

### `check_report`

`check_report` prints the one line: ok, with the worst error, its index and
its allowance; or the failure, with how many elements were wrong and the
worst one's got and want to nine significant digits, enough that two
different floats never print alike. It returns 0 when all were good.

### wb check

`wb check` fills a and b as `wb show` does, runs `add_ref` into want and
`add` into got, and compares them with rtol and atol both 0. Its exit
status is the report's, so a script can stop on a failure.

## How it works

### A NaN is never close

The test for a bad element is written the long way round, on purpose:

```
        if (!(err <= allowed))  /* written so that a NaN error is bad */
            r.bad++;
```

A NaN compares false with everything, itself included. If got is NaN, the
error is NaN, and `err > allowed` would be false: the NaN would count as
good. `!(err <= allowed)` is true for it, so it is bad. That is the
**invariant** of the checker: an element is good only when a comparison has
said so.

### Infinities

Two infinities of the same sign are equal, and `g == w` gives them an error
of 0: good. Around an infinite want nothing is allowed, since rtol times
infinity would allow anything:

```
        double allowed = isfinite(w) ? atol + rtol * fabs(w) : 0;
```

### The worst is not the largest error

The element to name is the one furthest past its own limit. A large error
on a large number can be well inside its allowance while a smaller one near
0 is outside it: with the numbers above, want 20 and got 20.0025 is 0.0025
off and good; want 0 and got 0.0015 is 0.0015 off and bad. The report has
to name the second.

### got starts as NaN

`wb check` fills got with NaN before it calls `add`, so an element `add`
never writes keeps its NaN and is bad, instead of holding whatever the
memory held, which could be right by luck. The special cases:

| got | want | the element is |
|---|---|---|
| NaN | anything | bad |
| anything | NaN | bad |
| +inf | +inf | good |
| -inf | +inf | bad |
| finite | +inf | bad |
| +inf | finite | bad |

## Decide the boundary

One tolerance for the whole array, as here and in numpy: two numbers chosen
once, and every element held to them. The other way is a bound worked out
for each element from its inputs, which is what an error analysis of the
arithmetic gives: much tighter, so smaller mistakes are caught, at the cost
of a page of algebra for every function, done again whenever the function
changes. How small is the smallest bug you need to catch?
