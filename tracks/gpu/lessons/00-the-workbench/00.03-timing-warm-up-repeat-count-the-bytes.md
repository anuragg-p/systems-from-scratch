# 00.03 Timing: warm up, repeat, count the bytes

One run of a function is not a measurement. This lesson writes the timer
the track measures everything with: a call thrown away, then the function
run again and again, the fastest run reported with the median beside it,
and the time turned into bytes moved a second, so that numbers can be
compared.

## Where this fits

![Where 00.03 fits](figures/00.03-map.svg)

The timer is the last piece of the workbench. It is given a function and
what to call it with, and gives back how many times it ran, the fastest run
and the median. Every function above it on the map is timed with it, once
the checker has passed it. With it the workbench can say of a function both
that it is right and how long it takes.

## The idea

![One measurement: a run thrown away, then the fastest of the rest](figures/00.03-runs.svg)

Time `add` once and the number includes things that are not `add`. Memory
a program has just been given is handed over by the system a page at a
time, on first use, and the call that first writes it pays for that. The
caches hold whatever ran before. And whatever else the machine is doing
takes its share.

So the timer calls the function once and throws the time away: the
**warm-up**, which pays for what happens only the first time. Then it times
run after run until there are enough, and reports the fastest. Noise only
ever adds time, so the fastest run is the closest to the function alone.
The **median**, the middle run, is printed beside it: when the two are far
apart, the machine was busy.

Then the unit. 4 ms is quick for sixteen million elements and slow for a
thousand. `add` reads two floats and writes one for every element, 12
bytes, so n elements in a fastest time of t seconds is 12n / t bytes a
second, printed in GB/s (10^9 bytes). It describes this loop, one float at
a time (`add.c` is built with the compiler's vectorizer off, as the
Makefile says), not the memory.

### `bench_now`

`bench_now` reads a clock that only goes forward and that nothing sets or
adjusts, in seconds. Which clock, and why, is below.

### `bench`

`bench` takes the function to time as a pointer, with one pointer to pass
it, so it can time anything. It makes the warm-up call, times calls until
the stopping rule below says enough, and sorts the times for the fastest
and the median.

### the order of two times

`earlier` is the comparison `qsort` needs: negative, zero or positive as
the first time is less than, equal to or greater than the second.

### one call of add, as bench calls it

`bench` calls a function with one pointer, and `add` takes four arguments.
`struct add_args` holds them, and `run_add` takes them out and calls `add`.

### wb time

`wb time` fills a and b from seeds 1 and 2, with 2^24 elements unless `-n`
says otherwise, times `add` with `bench`'s defaults, and prints the runs,
the fastest and the median in milliseconds, and the GB/s at the fastest.

## Run it

`./learn run gpu --at 00.03` runs `wb time`. On an Apple M4 Pro, with
Apple clang 21, it printed this; yours will differ:

That is 2^24 elements, 192 MiB for the three arrays, timed until the runs

4096 elements are 48 KiB in all, small enough to stay in the cache nearest
the core; 2^24 are 192 MiB, far more than this machine's caches hold. Here
the GB/s came out nearly the same at all three sizes: where the data lived
did not decide `add`'s speed. Yours may differ. Lesson 01.02 is about when
it does.

## How it works

### Paid for once, before the clock starts

The warm-up is the one call before the loop, `fn(arg);`. In `wb time` it
is the call that first writes out's 64 MiB: a and b were written by
`rng_fill`, but out was only allocated.

### When to stop

```
    while (r.runs < o.max_runs && (r.runs < o.min_runs || r.total < o.min_time)) {
```

At least min_runs runs and min_time seconds of them, never more than
max_runs. Each rule alone fails at one end: a count alone gives a 4 ms
function five runs, too few to see what the noise does; a time alone gives
a 300 ms function two. Together they give a fast function half a second of
runs and a slow one at least five, and max_runs stops a very quick one at a
thousand. A field of 0 asks for the default: 0.5 s, 5 runs, 1000 runs.

### The clock

`bench_now` reads `CLOCK_MONOTONIC_RAW`. **Monotonic** means it never goes
back, as the time of day can when the system corrects it. RAW, because on
macOS the plain `CLOCK_MONOTONIC` moves in whole microseconds, and a
4096-element `add` takes less than one: on that clock it read 0 or 1
microsecond. On this Mac the RAW clock moves in steps of about 41
nanoseconds. A run can still be shorter than one step:

<!-- verify: session
line 2 ~ add: n = 64, 1000 runs, min 0 ms, median [\d.e+-]+ ms, too fast for the clock: try a larger -n
-->
```
$ ./wb time -n 64
add: n = 64, 1000 runs, min 0 ms, median 0 ms, too fast for the clock: try a larger -n
```

Here 64 elements took less than one step, so the fastest run read 0, and
`wb time` says so instead of dividing by it. Yours may print a GB/s.

### A clock you can choose

The clock is a field of `bench_opts`, not a call written into `bench`.
Given a clock that returns chosen times, every number `bench` works out,
the runs, the fastest and the median, can be checked exactly, with no real
time in it. `wb` passes none, and gets `bench_now`.

## Decide the boundary

Which number to report. This timer leads with the fastest run, as Julia's
BenchmarkTools does: its `@btime` prints the minimum, and its manual argues
that machine noise is "inherently positive", so the minimum is "a robust
estimator". hyperfine, which times whole commands, prints the mean with its
standard deviation, the min and the max, and counts its first run unless
told `--warmup`. Google Benchmark reports the mean over its iterations, and
by default throws nothing away. The mean is what a user waits on a busy
machine; the minimum is what the function costs. Are you measuring the
function, or the machine it will run on with everything else going?

## Break it

Take the warm-up away, and time one run instead of many. In
`build/at/gpu/00.03/bench.c`, delete the warm-up call:

<!-- verify: patch file=bench.c
-    fn(arg);
     bench_result r = {0, 0, 0, 0};
-->
```
    fn(arg);                        <- delete this line
    bench_result r = {0, 0, 0, 0};
```

and in `wb.c`, in `time_add`, ask for at most one run, so that the line
reads `bench_opts o = {0, 0, 1, NULL};`. Build, and time it three times:

Each time is now one call, the first, the one that writes out's 64 MiB for
the first time. Here that was 2.4 to 3.5 times the fastest run of Run it,
and different on every try; with one run the median is the same run, so
nothing on the line says how unsteady it was. Put both lines back.
