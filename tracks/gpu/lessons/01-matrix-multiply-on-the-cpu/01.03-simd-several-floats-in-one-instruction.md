# 01.03 SIMD: several floats in one instruction

One instruction can multiply or add several floats at once. This lesson
writes matrix multiply that way, in C that the compiler turns into those
instructions on whatever machine builds it, and shows that until now the
compiler had been kept from doing it by itself.

## Where this fits

![Where 01.03 fits](figures/01.03-map.svg)

This is the third rung of matrix multiply on the CPU. It keeps lesson
01.02's order, along the rows, and does each step of the inner loop on
several floats at once. The kernel it writes does any rectangle of the
product; the two rungs above it, tiles and threads, are made of calls to
it. After this lesson the CPU does several multiply-adds an instruction.

## The idea

![Eight columns of c and four values of p: two steps of the inner loop with 4-float vectors, one with AVX2](figures/01.03-lanes.svg)

A **vector register** holds several floats side by side, and one
instruction adds or multiplies all of them at once, each in its own
**lane**. How many depends on the machine; the file's own comment gives the
width it uses: 8 floats (256 bits) on x86-64 with AVX2, and 4 floats (128
bits) otherwise, which on arm64 is a NEON register and on x86-64 without
AVX2 an SSE one. On this Mac, an arm64 machine, it is 4.

ikj's inner loop does c[i][j] += a[i][p] x b[p][j] for j = 0, 1, 2 and on:
the same operation on neighbouring floats, which is exactly what a vector
does. Put a[i][p] in every lane, load the next four floats of b's row and
of c's row, multiply, add, and store: four columns of c in one go.

The second change is to take four values of p together. ikj loads
c[i][j], adds one product and stores it, once for every p. Here each vector
of c is loaded once, gets the products for p, p + 1, p + 2 and p + 3 added
to it, and is stored once: a quarter of the loads and stores of c.

### the vector type

`vec` is one of the compiler's vector types: LANES floats that `+` and `*`
work on lane by lane, the compiler picking the machine's instructions.
LANES is set once, at the top of the file, from whether the compiler was
told the machine has AVX2.

### a vector of floats in

`load` reads LANES floats, starting anywhere, into a `vec`.

### a vector of floats out

`store` writes one back. Why both go through `memcpy` is below.

### one float in every lane

`splat` makes a `vec` with the same float in every lane: a[i][p], to
multiply a whole vector of b's row by.

### `mul_add_tile`

The kernel. It adds to c the products for one rectangle of the work: rows
i0 to i1 of c, values of p from p0 to p1, columns j0 to j1. Here it is
called once, on the whole product; lessons 01.04 and 01.05 call it on
pieces.

### `matmul_simd`

`matmul_simd` sets c to 0, then calls the kernel once with ranges that
cover all of it.

## How it works

### Loading through memcpy

```
    vec v;
    memcpy(&v, p, sizeof v);
    return v;
```

The address is somewhere inside a row of b or c, `b0 + j`, and need not be
a multiple of anything. Read as `*(const vec *)p`, it would promise the
compiler that p is aligned like a `vec`, and the compiler may then use an
instruction that needs that: built for x86-64 without AVX, clang has been
seen to make an SSE add read its operand straight from memory, which works
only at a multiple of 16 bytes. `memcpy` promises nothing about the address, and the
compiler still makes it one load instruction, one that takes any address.

### Columns and values of p left over

```
        for (; p + 4 <= p1; p += 4) {
```

The same test as `add`'s in lesson 00.01, written with an addition for the
same reason. After the groups of four, the values of p left over (fewer
than four) go one at a time; inside each group, after the whole vectors,
so do the columns left over. At n = 1000 there are none of either. Of the
shapes `mm check` runs, 33 x 31 x 65 has both: 31 values of p are seven
fours and three more, and 65 columns are sixteen vectors of 4 and one more.

### Fused multiply-add

A **fused multiply-add** works out a x b + c and rounds once, at the end,
where a multiply then an add round twice. Every other file is built with
`-ffp-contract=off`, which keeps the two apart. This one is built with:

```
SIMD = -ffp-contract=fast
```

so each `cv += a0 * load(b0 + j)` may become one fused instruction, where
the machine has them, as arm64 does. The sums round differently, and the
check shows it:

<!-- verify: session -->
```
$ cd build/at/gpu/01.03
$ ./mm check ijk simd
ijk     256x256x256: ok, worst error 9.3e-06 at [52480] of 65536 (allowed 0.00136)
simd    256x256x256: ok, worst error 1.91e-05 at [37521] of 65536 (allowed 0.00279)
```

ikj gave ijk's answers to the last bit; simd is the first variant that
does not. From here on the tolerance is what tells a right answer from a
wrong one. Measured while this track was built, at n = 2000: with this file
built without fusing, simd's worst error was ijk's to the digit; fused, it
moved by 5 to 7 percent, and stayed under 0.07 of the allowance.

### Four lanes here, eight with AVX2

On x86-64 the Makefile adds `-march=native` to this file, so that AVX2 is
used where the machine has it. A vector wider than the machine's still
compiles, as two narrower operations; an earlier version of this file used
8 floats everywhere, and on arm64 gcc built its splat through memory, which
made lesson 01.04's tiled version slower than this one. At the machine's
width neither compiler does.

## Decide the boundary

<!-- verify: mention names="_mm256_fmadd_ps vfmaq_f32" outside reason="intrinsics from the compilers' headers, not this project's" -->
There are three ways to get vector instructions out of C. The compiler's
vector types (ours): one source for every machine, and the compiler picks
the instructions, but only for what `+`, `*` and friends can say.
**Intrinsics**: a C function for each instruction, such as
`_mm256_fmadd_ps` for AVX2 with fused multiply-add and `vfmaq_f32` for NEON,
which give exact control over the instructions, with one source for each
kind of machine. Assembly: OpenBLAS's source tree calls its kernel
directory "Optimized assembly kernels for CPU architectures"; its Haswell
sgemm kernel is GCC inline assembly on 256-bit registers, and its arm64
one for Neoverse N1, which its Apple configurations reuse, is an assembly
file. How many machines must your code be fast on, and how fast on each?

## Break it

Turn the compiler loose on ikj. In `build/at/gpu/01.03/Makefile`, take
`$(SCALAR)` out of the rule for `matmul.o`, so that its second line reads
`$(CC) $(CFLAGS) -c -o $@ matmul.c`. Rebuild everything, and time three
variants:

<!-- verify: patch file=Makefile old="$(CFLAGS) $(SCALAR) -c -o $@ matmul.c" new="$(CFLAGS) -c -o $@ matmul.c" -->
<!-- verify: session timeout=120
line 5 ~ ijk +[\d.]+ +[\d.]+ +1\.0x
line 6 ~ ikj +[\d.]+ +[\d.]+ +[\d.]+x
line 7 ~ simd +[\d.]+ +[\d.]+ +[\d.]+x
-->
```
$ make -s clean && make -s
$ ./mm time ijk ikj simd
n = 1000
variant      min ms    GFLOP/s  vs ijk
ijk         622.010       3.22    1.0x
ikj          68.135      29.35    9.1x
simd         44.839      44.60   13.9x
```

Here ikj ran about 4 times as fast as in Run it, with no change to its
source: clang at `-O2` made its inner loop vector code by itself. gcc 14
at `-O2` leaves that loop scalar even so, and vectorizes it at `-O3`; the
two flags keep both from doing it. ikj's order is what made the loop
something a compiler can vectorize.

ijk's time hardly moved. Its inner loop's floats are a row of b apart, and
clang left that loop one float at a time; even told it may reorder the
terms of a sum, which changes their rounding, it vectorized ijk only when b
has a single column, whose floats are neighbours. Put the line back, and
rebuild with `make -s clean && make -s`.
