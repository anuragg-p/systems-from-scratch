# 01.04 Blocking

Once the arithmetic is fast, the time goes on bringing the data to it.
This lesson does the multiply a tile at a time, so that the piece of b in
use is read many times while it is still in the cache, instead of being
read again for every row of c.

## Where this fits

![Where 01.04 fits](figures/01.04-map.svg)

This is the fourth rung of matrix multiply on the CPU. It changes nothing
in the arithmetic: it calls lesson 01.03's kernel on pieces of the product
instead of on the whole of it, in an order that keeps those pieces near
the core. The rung above it, threads, gives each core a band of rows done
exactly this way. After this lesson the multiply keeps its speed far better
as the matrices grow.

## The idea

![Without tiles every row of c reads all of b; with them a tile of b serves a whole band of rows](figures/01.04-tiles.svg)

GFLOP/s, not the milliseconds. On an Apple M4 Pro, with Apple clang 21:

(The last column is `-` because ijk was not timed.) Here ikj did 7.5 to 7.8

not change with the size of the matrices; simd's fell as they grew.

Look at what simd reads. For each row of c, the kernel runs p over all of
b's rows and j over all of its columns: it reads the whole of b. At n =
2000 b is 16 MB, read again for every one of 2000 rows. This Mac's
performance core has 128 KiB in its nearest cache, the L1d.

A **tile** is a square piece of a matrix. Cut the product into tiles of
MM_BLOCK rows of c, MM_BLOCK values of p and MM_BLOCK columns. A tile of b
is MM_BLOCK x MM_BLOCK floats, 64 KiB at 128, which fits in that L1d. Use
it for a whole band of MM_BLOCK rows of c before moving on to the next, and
each piece of b is read from further away once per band instead of once
per row.

Does it change the answers? Each c[i][j] gets the same products. Whether it
gets them in the same order and the same groups of four is the question,
and `mm check` answers it below.

### MM_BLOCK

The side of a tile, 128, defined at the top of `matmul_blocked.c`.

### `blocked_rows`

Rows i0 to i1 of c, a tile at a time: those rows set to 0, then the
kernel, `mul_add_tile`, on each tile. It is a function of its own because
lesson 01.05 gives each thread a band of rows to do with it.

### `matmul_blocked`

`matmul_blocked` is `blocked_rows` over every row of c.

## How it works

### Three loops of tiles

```
    for (int r0 = i0; r0 < i1; r0 += MM_BLOCK) {
        int r1 = r0 + MM_BLOCK < i1 ? r0 + MM_BLOCK : i1;
        for (int p0 = 0; p0 < k; p0 += MM_BLOCK) {
            int p1 = p0 + MM_BLOCK < k ? p0 + MM_BLOCK : k;
            for (int j0 = 0; j0 < n; j0 += MM_BLOCK) {
```

The tiles go in the same order as ikj's loops: a band of rows outermost,
then values of p, then columns. Inside the kernel each row of the band
runs over the same tile of b, so that tile is read MM_BLOCK times in a row
while it is near. c's rows are set to 0 once, before any tile, because
every tile of p adds only part of each sum: the sum for c[i][j] is built up
across all of them, in c itself, as in ikj.

### The last tile is smaller

`r1`, `p1` and `j1` stop at the end of the matrix, not at the tile's edge.
At n = 1000 a side is seven tiles of 128 and one of 104; in `mm check`'s
33 x 31 x 65 every side is a single short tile.

### Why 128

128 was picked by measuring. While this track was built, `blocked` at n =
1000 on this Mac took 47.0 ms with tiles of 32, 29.8 with 96, 28.7 with
128, 52.6 with 192, and 42.8 with no tiles at all; n = 2000 gave the same
order. (That was with an earlier, 8-float vector, which ran blocked at the
same speed here.) So on this machine anything from about 96 to 128 is good, and past
that tiles are worse than none. A 128 x 128 tile of floats is 64 KiB, half
of a performance core's L1d. On another machine the best size may differ:
change `MM_BLOCK` and time it, as Break it does.

### Tiles around ikj

The first design of this track put tiles around ikj's scalar loop. It
never beat plain ikj. That is what the measurement above shows: ikj's
speed was the same at every size, so keeping its data near gave it
nothing.

## Decide the boundary

One tile size for every cache, as here, against a block for each level. Goto
and van de Geijn choose kc so that a kc x nr sliver of b takes less than
half the L1 cache, and mc so that the block of a takes about half of the
L2 or of what the TLB can reach, and copy those blocks into contiguous
buffers before the inner kernel runs. BLIS writes the same design as five
loops around a micro-kernel, named JC (over n), PC (over k), IC (over m),
JR and IR, each with its own block size per machine: for float on Haswell,
an MC of 168, a KC of 256 and an NC of 4080. Ours is one number and three
loops, and has to suit every cache at once. When is one number enough?

## Break it

Make the tiles tiny: in `build/at/gpu/01.04/matmul_blocked.c` change the
line to `#define MM_BLOCK 8`, rebuild, check and time:

<!-- verify: patch file=matmul_blocked.c old="#define MM_BLOCK 128" new="#define MM_BLOCK 8" -->
<!-- verify: session timeout=120

-->
```
$ make -s
$ ./mm check simd blocked
simd    256x256x256: ok, worst error 1.91e-05 at [37521] of 65536 (allowed 0.00279)
blocked 256x256x256: ok, worst error 1.91e-05 at [37521] of 65536 (allowed 0.00279)
$ ./mm time simd blocked
n = 1000
variant      min ms    GFLOP/s  vs ijk
simd         42.977      46.54       -
blocked      67.938      29.44       -
```

Still right, and the same bits, since 8 is a multiple of four too; but
here blocked is now slower than simd. Tiles can cost more than they save.
Now make one tile hold everything:
`#define MM_BLOCK 100000`.

The same time as simd: with one tile the whole matrix, blocked makes one
call to the kernel over everything, which is exactly what simd does. Put
128 back.
