# 01.05 Threads, and the distance left to BLAS

The rows of c do not depend on each other, so every core can take a share
of them. This lesson splits the multiply between threads, then puts the
system's own matrix multiply in the same table, to measure what a real
library does beyond everything in this module.

## Where this fits

![Where 01.05 fits](figures/01.05-map.svg)

This is the top rung of matrix multiply on the CPU. Each thread runs
lesson 01.04's tiled multiply on its own band of rows, so nothing in the
arithmetic changes; the workbench checks the result as before. Beside it
stands the library every rung has been heading towards. After this lesson
the multiply uses every core of the machine, and the module ends with the
question the GPU modules ask again: when to write the kernel, and when to
call the library.

## The idea

![Each thread owns a band of c's rows; all of them read a and b](figures/01.05-rows-to-threads.svg)

Rows i0 to i1 of c need rows i0 to i1 of a and all of b, and nothing else:
they are a matrix multiply of their own. So thread t of T takes a band of
rows and runs `blocked_rows` on it. Each thread reads its own rows of a
and all of b, which no thread writes; each writes only its own rows of c,
which no other thread touches. No two threads ever write the same element,
so they need no **lock**, nothing that makes one thread wait for another,
until the end, when the caller waits for all of them to finish.

Then the comparison this module has been heading towards. **BLAS** is the
standard interface to linear algebra libraries, and `sgemm` is its single
precision matrix multiply. On macOS the library is Apple's Accelerate; on
Linux, OpenBLAS when it is installed.

### `matmul_threads`

It asks how many threads to run, never more than there are rows, gives
thread t rows m x t / T up to m x (t + 1) / T, starts them, and waits for
all of them. A thread that cannot be started has its share done by the
caller instead.

### one thread's share

`struct share` holds what one thread needs: the matrices, the row lengths
and its rows. `run_share` is what the thread runs: `blocked_rows` on them.

### `thread_count`

The number of threads: what `mm`'s `-t` asked for, or else one for each
core online, and never more than 256.

### `matmul_blas`

One call to `cblas_sgemm`: row by row, neither matrix transposed, c = 1 x a
x b + 0 x c. Each leading dimension, the distance from one row to the next,
is the row's length, but at least 1: Accelerate refuses 0 even for a
matrix with no columns, and stops the program.

## How it works

### Shares that differ by one row

```
        shares[t] = (struct share){a, b, c, k, n, m * t / count, m * (t + 1) / count};
```

Thread t's rows start where thread t - 1's stop, so every row belongs to
exactly one thread, whatever m and T are. When m is not a multiple of T the
shares differ by one row: 10 rows on 4 threads are 2, 3, 2 and 3; 1000 on
14 are 71 or 72. With more threads than rows, T is cut to m and each
thread gets one row.

### Starting threads costs time

The threads are created and joined on every call. On a small multiply
that is most of the time:

<!-- verify: session
line 5 ~ simd +[\d.]+ +[\d.]+ +-
line 6 ~ threads +[\d.]+ +[\d.]+ +-
-->
```
$ ./mm time -n 64 simd threads
n = 64
threads = 14
variant      min ms    GFLOP/s  vs ijk
simd          0.009      57.72       -
threads       0.071       7.43       -
```

Here 14 threads took eight times as long as one core doing all of a 64 x
64 multiply. At n = 1000 the same cost is a small part of 4 ms. A program
that multiplies many small matrices would keep its threads alive between
calls instead.

### What would need a lock

Two threads adding into the same element of c: each reads the element,
adds, and writes it back, and one thread's write can land between the
other's read and write and wipe it out. Splitting the rows never does that.
Splitting the values of p would: every thread would add part of every sum.
BLIS's documentation says the same of its loop over k, which it does not
split between threads, "because each iteration of the loop updates the
same part of the output matrix C".

## Decide the boundary

The distance left. Here threads took 4.333 ms and blas 0.550: the library
was about 8 times as fast as everything in this module together, and 54
times as fast as blocked on one core. What a library does that this module
does not, from the sources read for this track: it packs pieces of a and
b into buffers in the order its innermost loop reads them (Goto and van de
Geijn's design, which OpenBLAS implements); its innermost kernel is
written for each kind of CPU, in OpenBLAS in assembly or inline assembly;
its block sizes are chosen for each cache level and each machine, in
OpenBLAS and BLIS alike; and OpenBLAS's threads share one packed copy of b
instead of each packing its own. How Accelerate gets its speed Apple does not document: its pages say
that Accelerate uses the CPU's "vector-processing capability" and decides
how many threads to use, and nothing about how `cblas_sgemm` is built.
So: when do you write the kernel, and when do you call the library? Module
03 asks again on the GPU, against cuBLAS.

## Break it

More threads than cores: in `build/at/gpu/01.05/matmul_threads.c`, in
`thread_count`, double the count of cores, so that the line reads
`t = 2 * (int)sysconf(_SC_NPROCESSORS_ONLN);`. Rebuild, and time it
against the old count:

<!-- verify: patch file=matmul_threads.c old="t = (int)sysconf(_SC_NPROCESSORS_ONLN);" new="t = 2 * (int)sysconf(_SC_NPROCESSORS_ONLN);" -->
<!-- verify: session timeout=120
line 4 ~ threads = \d+
line 6 ~ threads +[\d.]+ +[\d.]+ +-
line 11 ~ threads +[\d.]+ +[\d.]+ +-
-->
```
$ make -s
$ ./mm time threads
n = 1000
threads = 28
variant      min ms    GFLOP/s  vs ijk
threads       4.752     420.91       -
$ ./mm time -t 14 threads
n = 1000
threads = 14
variant      min ms    GFLOP/s  vs ijk
threads       5.048     396.17       -
```

Here 28 threads were faster than 14, not slower. Timed against each other
six more times on this Mac while it was fairly quiet, 28 won every time;
while it was busy, the two came out within the noise of each other. The shares
do not take the same time: in a scratch build that timed each share at 14
threads, the slowest took nearly twice as long as the fastest, and the call
waits for the slowest. With 28 every share is half the size, so the
slowest cost less. An even split suits cores that are equal and idle, and
this machine's are neither. Put the line back.
