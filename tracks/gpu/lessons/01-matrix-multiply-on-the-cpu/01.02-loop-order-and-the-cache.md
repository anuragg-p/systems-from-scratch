# 01.02 Loop order and the cache

Swap two of the three loops, and the same sums, in the same order for
each element, run faster. Nothing about the arithmetic changes; what
changes is the order memory is read in. This lesson makes the
swap and shows where the time went.

## Where this fits

![Where 01.02 fits](figures/01.02-map.svg)

This is the second rung of matrix multiply on the CPU. It takes the plain
loops of lesson 01.01 and changes only the order they visit the matrices,
checked against the same reference and timed by the same timer. Every rung
above it keeps this order: the vectors of lesson 01.03, the tiles of 01.04
and the threads of 01.05 all walk the matrices the way this lesson does.
After it the multiply reads memory the way memory is fastest to read.

## The idea

![A row is neighbours in memory; a column is a stride](figures/01.02-row-and-column.svg)

Memory does not reach the processor one float at a time. It comes in
**cache lines**, blocks of neighbouring bytes, 64 bytes on an Intel Golden
Cove core and 128 on this Mac's cores, and a line once fetched is kept in
the **cache**, a small fast memory beside the core, until something else
needs its place. So the float right after one just read is nearly free: it
came in the same line. A float far away is a new fetch.

Look at ijk's inner loop with that in mind. For one element of c it walks p
down a column of b, `b[p * n + j]`, and each step is a whole row of b
further on: n floats, 4000 bytes at n = 1000, a different line every
step.

Swap the two inner loops, so that p is the middle loop and j the inner one.
Now the inner loop takes one a[i][p] and walks j along row p of b and row i
of c, adding a[i][p] x b[p][j] to each c[i][j]: neighbours in both, so one
128-byte line serves 32 steps. The products are the same, there are as
many, and each c[i][j] still gets its terms in the order p = 0, 1, 2 and
on. So the answers should be ijk's to
the last bit, and `mm check` below says whether they are.

### `matmul_ikj`

The loops in the order i, p, j, hence the name. For each row i of c, the
row is set to 0; then for each p, a[i][p] times row p of b is added to it,
one float at a time.

`hw.l1dcachesize` says 64 KiB: Apple's documentation says the plain keys
give the slowest kind of core's values, here an efficiency core's. On
Linux, `lscpu --caches` lists the caches; in a virtual machine it may print
the levels without their sizes, as it did in a Linux container on this Mac.

## How it works

### Zero first, then add

```
        for (int j = 0; j < n; j++)
            c[i * n + j] = 0;
```

In ijk each sum lived in a local variable, `sum`, and was written to c
once. In ikj the sum for c[i][j] is spread over the whole p loop, a term
each time round, so it has to live in c itself, and start at 0. c may hold
anything when a variant is called, so the variant sets it to 0 itself.

### One read of a[i][p] per row of b

```
            float aip = a[i * k + p];
```

a[i][p] is the same for every j of the inner loop, so it is read once into
a local. The compiler is not allowed to make that move by itself: for all
it knows, c and a overlap, and a store to c could change a[i][p]. A local
cannot be changed by a store to c.

### The vectorizer is off

```
SCALAR = -fno-tree-vectorize -fno-tree-slp-vectorize
```

The Makefile builds `matmul.c` with these two flags. ikj's inner loop is
the same operation on neighbouring floats, exactly what the compiler's
vectorizer looks for, and left on it can rewrite the loop to work on
several floats at once. Then this lesson's speed-up would be two things,
the order and the vectors, and each step up the ladder would measure
something else. Lesson 01.03 writes the vectors itself, and turns the
vectorizer back on to see what it does.

## Decide the boundary

Fixing the order of the loops is free, but it depends on how the matrices
are stored: with b stored column by column, ijk would be the fast one. The
other way is to store b **transposed**, each column of b written as a row,
so that even ijk's inner loop reads neighbours: a copy of b, made once,
and the loops left in the order the formula reads. Algorithmica's
matrix-multiply page takes that road as its second step. The libraries take
neither. OpenBLAS and BLIS copy pieces of a and b into buffers laid out in
exactly the order their innermost loop reads them; Goto and van de Geijn's
paper, whose design both follow, calls this **packing**. Which is cheaper
for you: changing how a loop walks the data, or changing how the data lies
for the loop?

## Break it

The track's default size is 1000, not 1024. See why: in
`build/at/gpu/01.02/mm.c`, change the default so that the line reads
`#define DEFAULT_N 1024`. First the two variants at 1000, for comparison,
then rebuilt at 1024:

<!-- verify: session timeout=120
line 5 ~ ijk +[\d.]+ +[\d.]+ +1\.0x
line 6 ~ ikj +[\d.]+ +[\d.]+ +[\d.]+x
-->
```
$ cd build/at/gpu/01.02
$ ./mm time ijk ikj
n = 1000
variant      min ms    GFLOP/s  vs ijk
ijk         669.452       2.99    1.0x
ikj         281.804       7.10    2.4x
```

<!-- verify: patch file=mm.c old="#define DEFAULT_N 1000" new="#define DEFAULT_N 1024" -->
<!-- verify: session timeout=120
line 5 ~ ijk +[\d.]+ +[\d.]+ +1\.0x
line 6 ~ ikj +[\d.]+ +[\d.]+ +[\d.]+x
-->
```
$ make -s
$ ./mm time ijk ikj
n = 1024
variant      min ms    GFLOP/s  vs ijk
ijk        1135.537       1.89    1.0x
ikj         278.532       7.71    4.1x
```

1024 is 7% more work than 1000 (1024 cubed over 1000 cubed). Here ijk took
1.7 times as long, and ikj about the same time. At 1024 one step down a
column of b is exactly 4096 bytes, a power of two and a whole number of
cache lines, so the floats of a column compete for the same few places in
the cache; at 1000 they spread out. ikj reads along
rows and never notices. This is the known hazard of sizes that are
multiples of large powers of two: Algorithmica's page reports n = 1536
running roughly 3 times slower than 1535. The track's default avoids it.
With gcc the cliff is steeper still: built with gcc 14 on Linux arm64, ijk
took 5.9 times as long at 1024 as at 1000; why gcc's suffers so much more
was not looked into. Put the line back.
