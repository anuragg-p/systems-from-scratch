# 01.01 A stream of tokens

The compiler gets its first phase, a scanner: it reads the characters of the
source once and cuts them into tokens, numbers and operators, and from here on
no other part of the compiler looks at a character. With it the compiler takes
sums and differences, written with spaces or without.

## Where this fits

![Where 01.01 fits](figures/01.01-map.svg)

This lesson builds the scanner, the first box inside the compiler on the map,
and its first cell, numbers and operators. It is given the source text that the
driver of lesson 00.01 reads from the file, and it hands a list of tokens to the
right. The parser that will take them is module 02's; until then the driver
reads the tokens itself and writes the assembly, which goes down to the
assembler, the linker and the machine of lesson 00.02 as before. After this
lesson the compiler takes any number of numbers joined by plus and minus, with
or without spaces, over as many lines as you like, and can print the tokens it
found.

## The idea

![The scanner walking 5 + 20 - 4: at each step it stands at one character, takes one token, and moves past it.](figures/01.01-scan.svg)

Module 00's compiler read one number and nothing else. A sum needs more: the
numbers, the operators between them, and the spaces that may or may not be
there. `5+20-4`, `5 + 20 - 4` and the same written over three lines are one
program. If every part of the compiler read characters, every part would have
to skip spaces and newlines, in every place it reads.

So the first phase of a compiler reads the characters once and cuts them into
**tokens**: the smallest pieces of the text that mean something on their own.
Here a token is a number or an operator; later lessons add names, keywords and
strings. The code that does it is the **scanner** (it is also called a lexer, or
a tokenizer). It drops the spaces and newlines between tokens, and after it no
other part of the compiler looks at a character: the scanner is where spaces
stop mattering.

The figure walks it over `5 + 20 - 4`. At each step the scanner looks at the
character it stands on. A digit starts a number, which runs as far as the
digits do, so `20` is one token and not two. A `+` or a `-` is a token of one
character. A space makes no token: the scanner steps over it. After the last
character it adds one more token, the end of the file. Each token knows its
kind, where its text is in the source, and, for a number, its value.

![What the compiler does with the tokens at this lesson: one total kept in a0, each new number through t0.](figures/01.01-walker.svg)

There is no parser yet, so the driver's `main` does the compiling itself: it
walks the tokens from left to right. The first number becomes `li a0, 5`, the
total in a0, the register main's result has to be in when it returns (00.01).
Each `+ 20` or `- 4` after it becomes two instructions: `li t0, 20` loads the
number into t0, a **temporary** register, free for any short-lived value, and
`add a0, a0, t0` adds it to the total (`sub` takes it away). This walker is the
whole compiler until lesson 02.03 replaces it with a tree and a code generator,
and it knows only sums and differences: anything else is an error.

### `tokenize`

The scanner's loop. It goes along the text with one pointer, `p`, and at each
place takes the first of these that fits: a space, a tab or a newline is
skipped; a digit starts a number; a `+` or a `-` is a token of one character;
anything else stops the compiler with `invalid token`. Each token goes on the
end of a list. After the last character come the end-of-file token and the line
numbers.

### `new_token`

A token of a kind, for the characters from one pointer up to another. It is
made with `calloc`, so every field it does not set starts at zero.

### `read_int_literal`

A number. `strtoul` in base 10 reads the digits and says where they stop. A
letter or a `_` right there, as in `1x`, is `invalid numeric constant`: no
token starts with a digit and goes on with a letter.

### `add_line_numbers`

Gives every token its line and its column, in one walk over the text once the
list is made. How it works says why it is a walk of its own.

### `equal` and `skip`

The two questions the walker asks of a token. `equal()` says whether the
token's text is exactly the text given, all of it. `skip()` is for a token that
must be there: it gives back the token after it, or stops with `expected '-'`
(or whatever was wanted). The walker takes a `+` with `equal()`, and anything
else must be a `-`.

### `error`

Prints a message and stops with exit status 1. `error_at()` and `error_tok()`
take a place in the source too, a character or a token, and for now they also
print only the message; lesson 01.05 makes them point at the place.

### printing the tokens

`--tokens` prints the list and stops: one line a token, `LINE:COLUMN KIND
TEXT`, and for a number its value. The next three lessons show what the scanner
does through it.

Outside these, the lesson adds `cc.h`, the header the compiler's files share,
with the token, its kinds and the functions' prototypes; and in `main.c` the
`--tokens` option, the call of the scanner, `get_number()` and the walker. The
sample, `try.c`, is now `5 + 20 - 4`.

## How it works

### A token points into the source

A token copies nothing. `new_token()` keeps where its text starts and how long
it is:

```
  tok->loc = start;
  tok->len = end - start;
```

The text of `20` stays where it is, in the one buffer that reading the file
filled (00.01), and the token points at it. Nothing is allocated for text, and
every token knows where in the file it came from: that is what `--tokens`
prints, and what lets an error point at the source in lesson 01.05. A number's
value is read once, by the scanner, into `val`; nothing later reads its digits
again. The price is that the buffer must stay where it is, unchanged, for as
long as any token is in use. It does: the compiler frees nothing, as chibicc
frees nothing, and exits when the file is done.

### The list ends in a token

The tokens are a linked list in the order of the text, and the list does not
end in a null pointer. Its last token is a real one, of kind end-of-file:

```
  cur = cur->next = new_token(TK_EOF, end, end);
```

That is the **invariant** the rest of the compiler counts on: every token
except the end of the file has a next one. So the walker can look at the token
after a `+` without first asking whether there is one. At the end of the file
it finds a token that is not a number, and says so:

<!-- verify: session -->
```
$ printf '5 +\n' > end.c
$ ./cc end.c >/dev/null; echo $?
expected a number
1
```

(`>/dev/null` hides the start of the assembly, which the walker has already
written when it finds the mistake.) The list starts from `head`, a token on the
stack that is not part of it, so adding a token is the same one line whether
the list is empty or not: `cur = cur->next = ...`.

### Line and column, afterwards

The loop that cuts tokens does not count lines. A second walk over the text
does, once the list is made, stopping at each token's `loc` in turn, since the
tokens are in the order of the text. chibicc does the same. Its column is
counted from the start of the line, from 1:

```
      tok->col = p - line + 1;
```

So a column is a count of bytes, and a tab is one column however wide a
terminal shows it; lesson 01.05 has to deal with that when it puts a mark under
a place. The end-of-file token sits on the newline that ends the last line, not
after it, which is why it is `1:11 eof` above, just after the `4`:

```
  char *end = (p > current_input && p[-1] == '\n') ? p - 1 : p;
```

Reading the file makes sure it ends in a newline (00.01), so this is the last
line's own. An error at the end of the file will then show the last line, not
an empty one after it.

## Decide the boundary

This scanner is written by hand, as chibicc's is: a loop with a branch for each
kind of token, in plain C. The other way is to generate one. Each kind of token
is described by a **regular expression**, a number as one or more digits, and a
tool builds a scanner from the list, a finite automaton that reads the text a
character at a time. Section 2.2 of the book under Go deeper describes the
generated kind, and says that production compilers often use scanners written
by hand. A generated scanner keeps its whole description in one short list,
and the tool, not the author, gets the matching right. A hand-written one is a
longer program, but it is only C: it can check what a pattern does not say
easily, such as a letter straight after a number, stop with exactly the error
it wants at exactly the place, and it needs no tool to build. For a language
whose tokens hardly ever change, which do you want to maintain: a description
and a tool, or the code itself?

## Break it

Stop the line numbers. In `build/at/cc/01.01/tokenize.c`, at the end of
`tokenize()`, delete the line

<!-- verify: patch file=tokenize.c
-  add_line_numbers(head.next);
-->
```
  add_line_numbers(head.next);
```

then build the compiler again and print the tokens:

<!-- verify: session -->
```
$ make -s
tokenize.c:86:13: warning: unused function 'add_line_numbers' [-Wunused-function]
   86 | static void add_line_numbers(Token *tok) {
      |             ^~~~~~~~~~~~~~~~
1 warning generated.
$ ./cc --tokens try.c
0:0 num 5 5
0:0 punct +
0:0 num 20 20
0:0 punct -
0:0 num 4 4
0:0 eof
$ ./ccrun try.c; echo $?
21
```

The C compiler that builds `./cc` notices first: the function is still there,
and nothing calls it (those are clang's words; gcc says the same in its own).
The tokens are all still right, their kinds, their text and their values. Only
the places are gone: every line and column is the zero that `calloc` left in
it. The program still gives 21, because the scanner's loop and the walker never
needed a line number. What needs one is what reports a place: `--tokens` now,
and from lesson 01.05 every error. Put the line back.
