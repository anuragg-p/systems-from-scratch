# 01.05 Errors that point at the source

Until now an error was a message alone, `expected a number`, and the place was
for you to find. This lesson makes every error about the program show the
file, the line, and a caret under the place, because a message without a place
is a search.

## Where this fits

![Where 01.05 fits](figures/01.05-map.svg)

This lesson builds the wide box under the scanner and the parser on the map,
errors that point at the source. Whatever finds a mistake in the program, the
scanner now, the walker in the driver until module 02's parser takes over,
reports it here, with the place it found it: a character, or a token. It reads
back from the source text the driver keeps, and from the line numbers the
scanner gave its tokens. After this lesson every error the compiler gives
about a program names the file and the line, shows the line, and points at
the place.

## The idea

![The two lines of an error: where the caret's column comes from, and why a tab above it is answered with a tab.](figures/01.05-caret.svg)

In a file of a few hundred lines, `invalid token` says what is wrong and
nothing about where. The compiler knows where: every token points into the
source (01.01), and every error is raised at a token or at a character. All it
has to do is say so, in a form a person can use at a glance:

<!-- verify: skip reason="the two lines of an error, as the figure shows them; Run it below replays the same case" -->
```
d.c:1: 1 + $
           ^ invalid token
```

The first line is the file's name, the line's number, and the whole line as it
is in the file. The second puts a **caret**, `^`, under the place, then the
message. To get the caret under the `$`, the second line starts with as many
spaces as the first line's prefix, `d.c:1: `, took, then one more for every
character of the line before the place. The figure's main case is harder: a
line that starts with a tab. A tab is one byte, but a terminal shows it as a
jump to the next tab stop, so a space under it would be too narrow. The caret's
line answers a tab with a tab, and both jump to the same stop.

### pointing at the source

`verror_at()` writes those two lines, given the line's number, the place, and
the message. It finds where the place's line starts, walking back to the
newline before it, and where it ends, walking on to the next. It prints the
prefix and the line; then, under it, the prefix's width in spaces, a tab for
each tab of the line before the place and a space for anything else, and `^ `
and the message.

Outside it, the two error functions that know a place now call it.
`error_tok()` passes the token's line, which the scanner worked out.
`error_at()`, which has only a character, counts the newlines from the start of
the file to it.

## Run it

Build the project as it stands, which runs the sample, `5 + 20 - 4`, as before;
then, in its directory, an invalid token:

<!-- verify: session wait=10 -->
```
$ ./learn run cc --at 01.05
Running cc as it stands at 01.05 (Errors that point at the source). Its files are in build/at/cc/01.05/
$ cd build/at/cc/01.05
$ printf '1 + $\n' > d.c
$ ./cc d.c; echo $?
d.c:1: 1 + $
           ^ invalid token
1
```

A sum that stops half way, on a second line that starts with a tab, and a
character constant with two characters in it, two lines further down:

<!-- verify: session -->
```
$ printf '1 +\n\t2 +\n' > end.c
$ ./cc end.c >/dev/null; echo $?
end.c:2: 	2 +
         	   ^ expected a number
1
$ printf "1 +\n\n   'ab'\n" > q.c
$ ./cc q.c; echo $?
q.c:3:    'ab'
          ^ a character constant holds one character
1
```

In the first, the caret comes after `2 +`, where the number is missing. In the
second it is under the opening quote, where the constant starts. An error with
no place in the program, such as a file that cannot be opened, is still one
line, from `error()`.

## How it works

### The line is still there

The place is a pointer into the buffer that holds the whole file, which is why
the tokens point into it and copy nothing (01.01): around any token, its line
is still in memory. Finding the line's start is a walk back to the newline
before the place, or to the start of the file:

```
  char *line = loc;
  while (current_input < line && line[-1] != '\n')
    line--;
```

and its end, a walk on to the next newline. Nothing is stored for this but the
pointer itself.

### The caret's column

`fprintf` returns the number of characters it wrote, and that is the width
of the prefix, whatever the file's name and the line's number:

```
  int indent = fprintf(stderr, "%s:%d: ", current_filename, line_no);
```

Then come that many spaces, and one character for each byte of the line before
the place:

```
  for (char *p = line; p < loc; p++)
    fputc(*p == '\t' ? '\t' : ' ', stderr);
```

The **invariant** is that, up to the caret, the second line is exactly as wide
on the screen as the first is up to the place. Both lines have the same prefix
width, so a tab in the source and the tab under it start at the same column,
and jump to the same tab stop, at whatever width the terminal sets its stops.
chibicc prints spaces only, as many as the place's column: under a tab its
caret falls short. Columns count bytes (01.01), so the caret lines up as long
as every other character before the place is one byte and one column wide, as
in plain ASCII text.

### The end of the file is on the last line

In the second case of Run it, the walker reached the end of the file and
wanted a number there. The end-of-file token sits on the newline that ends the
last line (01.01), not after it, so the error shows line 2 with the caret just
past `2 +`: the line where the program stops, which is where the missing
number belongs. chibicc puts that token after the newline, so for a file
holding `1+` it reports line 2, an empty line with nothing to point at.

### The first error is the only one

An error stops the compiler, with exit status 1: the error functions never
return. So one run shows one mistake, the first one found, and found means in
the order of the phases, not of the file. The scanner reads the whole file
before the walker looks at a token, so a bad token anywhere comes before a
mistake in the sum, even one on an earlier line:

<!-- verify: session -->
```
$ printf '1 * 2\n$\n' > two.c
$ ./cc two.c
two.c:2: $
         ^ invalid token
```

## Decide the boundary

This compiler stops at the first error, as chibicc does. The other way is
**recovery**: after an error, carry on and find more, so that one run reports
every mistake it can. Section 2.2.4 of the book, under Go deeper, describes it
in a scanner: throw the bad token away, and go on.
Stopping is simple, and every message it prints is about a real mistake. A
compiler that recovers has to guess how to carry on, and when it guesses wrong,
later messages are about mistakes that are not in the program, only in the
guess; in return, a run tells you more. When one run of the compiler takes a
fraction of a second, and the program is one expression long, is a second
error worth a guess?

## Break it

Leave out the prefix's width. In `build/at/cc/01.05/tokenize.c`, in
`verror_at()`, delete the line

<!-- verify: patch file=tokenize.c
-  fprintf(stderr, "%*s", indent, "");
-->
```
  fprintf(stderr, "%*s", indent, "");
```

then build the compiler again, and give it the invalid token of Run it once
more:

<!-- verify: session -->
```
$ make -s
tokenize.c:44:7: warning: unused variable 'indent' [-Wunused-variable]
   44 |   int indent = fprintf(stderr, "%s:%d: ", current_filename, line_no);
      |       ^~~~~~
1 warning generated.
$ ./cc d.c
d.c:1: 1 + $
    ^ invalid token
```

The C compiler that builds `./cc` notices first: `indent` is set and never used
(clang's words; gcc has its own). The caret is four columns in, one for each
character of `1 + ` before the `$`, and so it stands under the line number,
not under anything in the program. The count of the line was right; it was
counted from the wrong place. A caret's column is only meaningful together
with where the line above it starts, and that is the prefix. Put the line back.
