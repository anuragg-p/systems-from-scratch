# 01.03 Identifiers and keywords

The scanner learns names, the words a program makes up for its variables and
functions, and the fixed list of words the language keeps for itself, its
keywords. The names are only read here: nothing uses them until module 03.

## Where this fits

![Where 01.03 fits](figures/01.03-map.svg)

This lesson builds the third cell of the scanner on the map, names and
keywords. The scanner still takes the source text from the driver and hands a
list of tokens on; now a token can be a name, and a name on the language's list
of keywords is marked as a keyword. What gives a name a meaning, as a variable,
comes with the statements of module 03, further along the parser. Until then
the driver, which compiles only sums, turns a name away as not a number. After
this lesson the compiler reads every word of a C program, and tells the
language's own words from the program's.

## The idea

![A name is a letter or underscore, then letters, digits and underscores; only when it is complete is it looked up in the keyword list.](figures/01.03-names.svg)

Most of the text of a C program is words. Some are the program's own: `main`,
`count`, `x1`. Some belong to the language: `int`, `return`, `while`. The
scanner needs to read both, and to tell them apart, since the parser will treat
`return` as the start of a statement and `x1` as whatever the program declared
it to be.

A name, an **identifier** in C's word, is a letter or an underscore, then any
number of letters, digits and underscores. The scanner reads one in two states,
the left half of the figure: the first character must be a letter or `_`; every
character after it may be a digit too, and the name ends at the first character
that is none of these. So `x1` and `_y` are names, and `1x` is not.

A **keyword** is a name the language keeps for itself; a program cannot use one
as a name of its own. The scanner does not look for keywords while it reads.
It reads `int2` as a name, the whole of it, and only then asks whether that
name is on the list. It is not, so `int2` is a name, like `x1`. `return` is on
the list, and becomes a keyword. `float` is a keyword of C, but not of this
compiler, which has no floating point: here it is an ordinary name.

### `is_ident1`

Whether a character can start a name: `a` to `z`, `A` to `Z`, or `_`.

### `is_ident2`

Whether a character can go on a name: what `is_ident1()` takes, and the digits.
`tokenize()` has a new branch for names, after the one for numbers: a character
that `is_ident1()` takes starts a name, and it goes on for as long as
`is_ident2()` takes the next.

### `is_keyword`

Whether a name is a keyword: it compares the token with each entry of a table,
with `equal()`.

### `convert_keywords`

Walks the list once the scanning is done, and gives every name that
`is_keyword()` says yes to the kind keyword. `tokenize()` calls it last, after
the line numbers.

Outside these, the token has two new kinds, an identifier and a keyword, and
`--tokens` prints them as `ident` and `keyword`.

## Run it

`./learn run cc --at 01.03` builds the compiler and runs the sample, `5 + 20 -
4`, as before. Then, in the project's directory, five names:

<!-- verify: session -->
```
$ ./learn run cc --at 01.03
Running cc as it stands at 01.03 (Identifiers and keywords). Its files are in build/at/cc/01.03/
$ cd build/at/cc/01.03
$ printf 'return x1 _y int2 float\n' > i.c
$ ./cc --tokens i.c
1:1 keyword return
1:8 ident x1
1:11 ident _y
1:14 ident int2
1:19 ident float
1:24 eof
```

A name in a sum is a token now, but the walker wants numbers:

<!-- verify: session -->
```
$ printf '1 + x\n' > x.c
$ ./cc x.c >/dev/null; echo $?
expected a number
1
```

Names stay this way, read and refused, until module 03 gives a function
variables; a C program's whole `int main() { ... }` comes there too.

## How it works

### Keywords are picked out afterwards

The branch that reads a name makes every name an identifier, whatever it
spells. The keywords are found in a walk of their own, the last thing
`tokenize()` does:

```
  convert_keywords(head.next);
```

That is chibicc's structure. The scanning loop has a single branch for every
word, with no case for any keyword, and the keywords are known in exactly one
place, the table. What any design has to respect is that a keyword is a whole
name: while the scanner is still reading `int2`, it cannot know at the `t`
whether the name goes on. Matching keywords the way the last lesson matches
operators, by the entries the text starts with, would read `int2` as `int` and
`2`; Break it shows that split from the other side.

### A name never starts with a digit

That one rule is what makes a token that starts with a digit always a number.
And the number reader, since 01.01, takes nothing name-like straight after its
digits:

<!-- verify: session -->
```
$ printf '1x\n' > d.c
$ ./cc d.c; echo $?
invalid numeric constant
1
```

So `1x` is not the number 1 followed by the name `x`: it is one mistake, and
the error says so. chibicc's scanner, at the commit this one is taken from,
read `12a` as a number and then a name; it makes it an error two commits later.
A programmer who writes `1x` almost certainly meant something else, and two
tokens would only push the error further along, to wherever the parser gave
up.

### This compiler's keywords, not all of C's

<!-- verify: fact cmd="awk '/is_keyword/,/};/' tokenize.c | grep -o '\"[^\"]*\"' | wc -l | tr -d ' '" expect=37 -->
The table holds 37 keywords:

```
    "return", "if", "else", "for", "while", "int", "sizeof", "char",
```

and so on. It is the list of the language this compiler takes, which is not
quite C. `float` and `double` are not on it: the compiler will never have
floating point, so those are names like any other, and a program that uses
them is not one it takes. Words chibicc's list lacks are on it: `inline`,
which is C's, and GNU C's `__attribute__`, which the xv6 track's programs use
(module 09 compiles them), with two other spellings of `restrict`. A word
that comes onto the list makes a name illegal that was legal before, so the
list is part of the language's definition, here the definition of what this
compiler accepts.

## Break it

Let a name hold no digits. In `build/at/cc/01.03/tokenize.c`, in
`is_ident2()`, change the line

<!-- verify: patch file=tokenize.c
-  return is_ident1(c) || ('0' <= c && c <= '9');
+  return is_ident1(c);
-->
```
  return is_ident1(c) || ('0' <= c && c <= '9');
```

to

<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
  return is_ident1(c);
```

then build the compiler again and read the five names:

<!-- verify: session -->
```
$ make -s
$ ./cc --tokens i.c
1:1 keyword return
1:8 ident x
1:9 num 1 1
1:11 ident _y
1:14 keyword int
1:17 num 2 2
1:19 ident float
1:24 eof
```

No error, and two more tokens. A name now ends at its first digit, and the
digit starts a number, so `x1` is the name `x` and the number 1. `int2` is
worse: its letters are a whole name, `int`, which is on the list, so it comes
out as the keyword `int` and the number 2, a type followed by a constant, where
the program wrote one name. That is the split a keyword lookup made during the
reading would have made too. The rule for the characters after the first is
what makes a name one token, and the keyword lookup is only as right as the
names it is given. Put the line back.
