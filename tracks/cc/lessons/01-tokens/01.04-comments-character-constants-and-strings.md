# 01.04 Comments, character constants and strings

Some of the source is not what it looks like. A comment is text the compiler
never sees, and an escape like `\n` is two characters that stand for one. The
scanner learns to drop the first and decode the second, and to read numbers in
hexadecimal, octal and binary.

## Where this fits

![Where 01.04 fits](figures/01.04-map.svg)

This lesson builds the last cell of the scanner on the map, comments and
literals. Some of the source text now never becomes a token, and some becomes
a token that holds more than its text: a string carries the bytes it stands
for, a character its number. So the parser to its right never sees a comment,
an escape, or the base a number was written in. After this lesson the compiler
reads a line of C as a person writes it, comments and all, and its sums may use
characters and numbers in four bases.

## The idea

![One line of source, and what each token on it stands for once the scanner has read it.](figures/01.04-literals.svg)

On this line, what the text says and what it is are different things.
`/* a comment */` and `// the end` are for whoever reads the source: a
**comment** makes no token, and the scanner skips it as it skips a space.

A **string literal**, `"a\tb"`, is written with six characters and stands for
three bytes: `a`, a tab, `b`. The `\t` is an **escape sequence**, a backslash
and what follows it, standing for one byte that would be awkward or impossible
to type between quotes. The token keeps its text, as every token does, and the
bytes it stands for as well.

A **character constant**, `'\n'`, is one character between single quotes, here
an escape, and stands for the character's code, 10 for a newline: a number.

Numbers can be written in other bases than ten. `0x1F` is hexadecimal, 31;
`0b101` is binary, 5. And `017` is octal, 15: in C a leading zero means base 8,
a rule old enough to be a trap.

![The escapes the scanner knows, and the byte each one becomes.](figures/01.04-escapes.svg)

### `from_hex`

The value of one hexadecimal digit, 0 to 15, for the `\x` escapes.

### `read_escaped_char`

Given the text just after a backslash, the byte the escape stands for, and
where the escape ends. One to three octal digits are their value; `x` and hex
digits, as many as there are, theirs. The letters C names, `a b t n v f r`,
are the control characters, and `\\ \' \" \?` stand for the character itself.
Anything else is `unknown escape sequence`, and a value over 255 is `escape
sequence out of range`. The values themselves come from the C compiler that
builds `./cc`: `return '\n';` returns whatever that compiler takes `\n` to be,
as the comment above the function points out.

### `string_literal_end`

Finds the closing quote of a string, stepping over the character after each
backslash. A newline or the end of the file first is `unclosed string literal`.

### `read_string_literal`

A string token: the end first, then a buffer, and the bytes copied into it,
each escape decoded. `str` holds the bytes, with a `'\0'` after them, and
`str_len` how many there are.

### `read_char_literal`

A character constant: one character or one escape, then the closing quote,
made into a number token. Anything else between the quotes is an error.

Outside these, the scanner's loop gets the two kinds of comment at its top and
branches for strings and characters; `read_int_literal()` gets its prefixes,
`0x`, `0b` and a leading `0`; the token a kind for strings, with `str` and
`str_len`; and `--tokens` a string's decoded length after its text.

```
/* a comment */ "a\tb" '\n' 0x1F 017 0b101 // the end
```

<!-- verify: session -->
```
$ ./cc --tokens lit.c
1:17 str "a\tb" 3
1:24 num '\n' 10
1:29 num 0x1F 31
1:34 num 017 15
1:38 num 0b101 5
1:54 eof
```

The two comments made no tokens; the first token starts at column 17, after
the first comment and its space. A string's line ends in its length in bytes,
decoded: 3. The character constant is a `num`, as the three numbers are, each
with its value in decimal. An escape the scanner does not know is an error. The
other bases are numbers like any other: the walker adds them, and `./same`
(00.03) checks that gcc reads them the same way:

<!-- verify: session -->
```
$ printf '%s\n' "'\e'" > e.c
$ ./cc e.c; echo $?
unknown escape sequence
1
$ printf '0x10 + 010 + 0b10 - 1\n' > b.c
$ ./ccrun b.c; echo $?
25
$ ./same b.c
same: status 25
```

## How it works

### A character constant is a number

`read_char_literal()` ends by making a number token:

```
  Token *tok = new_token(TK_NUM, start, p + 1);
  tok->val = c;
```

From there on, nothing in the compiler knows `'\n'` was written as a character:
it is 10, as if the program had said 10. That is C's own view, where a
character constant is an `int`, and it means the walker adds characters with
no new code:

<!-- verify: session -->
```
$ printf "'a' + 1\n" > ch.c
$ ./ccrun ch.c; echo $?
98
$ ./same ch.c
same: status 98
```

### A string is read twice

A string ends at a double quote, but not at every one: `\"` puts a quote inside
it. So `string_literal_end()` walks to the end first, stepping over whatever
follows a backslash, and only then does `read_string_literal()` copy:

```
  char *end = string_literal_end(start + 1);
  char *buf = calloc(1, end - start);
```

Knowing the end first gives the size of the buffer before anything is copied.
No string decodes to more bytes than it has characters between its quotes, so
`end - start`, which counts the opening quote as well, is room for all of them
and the `'\0'` after. Here the escaped quote is one byte of three:

<!-- verify: session -->
```
$ printf '%s\n' '"a\"b"' > q.c
$ ./cc --tokens q.c
1:1 str "a\"b" 3
1:7 eof
```

A string is a token now, and nothing takes one: strings get their use in
module 07.

### A comment ends at the first `*/`

A `/*` comment ends at the first `*/` after it, and holds anything until then:
a `*`, a `/`, even another `/*`. C's comments do not nest, so in `/* a /* b */
c */` the comment ends after `b`, and what follows is code. An unclosed one is
an error:

<!-- verify: session -->
```
$ printf '1 /* 2 * 3 */ + 4\n' > c.c
$ ./cc --tokens c.c
1:1 num 1 1
1:15 punct +
1:17 num 4 4
1:18 eof
$ ./ccrun c.c; echo $?
5
$ printf '/* a /* b */ c */\n' > n.c
$ ./cc --tokens n.c
1:14 ident c
1:16 punct *
1:17 punct /
1:18 eof
$ printf '1 /* no end\n' > u.c
$ ./cc u.c; echo $?
unclosed block comment
1
```

The error is raised at the `/*`, not at the end of the file where the scanner
found out: the place to fix is where the comment opens. At this lesson only
the message shows; lesson 01.05 shows the place. An unclosed string is
reported at its opening quote for the same reason.

### What is refused, and why

The scanner turns away some things other compilers take. An escape it does not
know, such as `\e`, is an error: gcc for this machine compiles `'\q'` with only
a warning, and chibicc takes any unknown escape as the letter itself, but a
mistyped escape is a mistake, and an error says so where it is. A character
constant holds exactly one character, where chibicc takes the first and skips
the rest. And a value over 127 is refused for now:

<!-- verify: session -->
```
$ printf '%s\n' "'ab'" > ab.c
$ ./cc ab.c
a character constant holds one character
$ printf '%s\n' "'\xff'" > ff.c
$ ./cc ff.c
a character constant above 127 is not supported yet
```

Is `'\xff'` 255 or -1? C says it depends on whether a plain `char` is signed,
and leaves that to each machine. On RISC-V it is unsigned, but this compiler
has no types yet; they arrive in module 06, and the constant with them.

## Break it

Let a block comment end at any star. In `build/at/cc/01.04/tokenize.c`, in
`tokenize()`, change the loop that looks for the end of a comment,
`while (*q && !startswith(q, "*/"))`, to

<!-- verify: patch file=tokenize.c
-      while (*q && !startswith(q, "*/"))
+      while (*q && *q != '*')
-->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
      while (*q && *q != '*')
```

then build the compiler again, and read the same file as above:

<!-- verify: session -->
```
$ make -s
$ ./cc --tokens c.c
1:1 num 1 1
1:10 num 3 3
1:12 punct *
1:13 punct /
1:15 punct +
1:17 num 4 4
1:18 eof
$ ./ccrun c.c; echo $?
expected '-'
1
```

The comment now ends at the `*` after `2`, and the line after the loop,
`p = q + 2`, steps over it and the space that follows, as if they were the `*/`.
The rest of the comment, `3 */`, is code: a number and two operators that no
one wrote as code. Any comment with a star inside it, a product in a line that
was commented out or a row of stars drawn around a heading, now leaks into the
program. Here the walker happens to stop at the 3; in a program with
statements, a leaked fragment could just as well compile. Put the line back.
