# 00.02 What the assembler, the linker and the machine do with it

<!-- verify: fact cmd="wc -l < rt/start.S | tr -d ' '" expect=31 -->
The compiler's four lines are text, and a machine cannot run text. This
lesson runs the three programs that stand between them and a result, the
assembler, the linker and an emulated RISC-V machine, each by hand once,
and adds the 31 lines of start-up code that stand in for an operating
system.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

This lesson builds the bottom row of the map, the road from the compiler's
assembly to a number coming back: the assembler, the linker with the
runtime joining from below, and the bare machine. Above it is the
compiler, which from now on only has to write assembly; below it, only
QEMU. After this lesson one command turns a file that holds a number into
a program that runs and returns it.

## The idea

![The linked program in the machine's memory: where the linker put each piece, and the one device the program talks to.](figures/00.02-memory.svg)

The four lines of 00.01 define `main` and nothing else. But a machine does
not start at `main`, and `ret` must return to something that called it.
Under an operating system, the system loads the program, calls `main` and
takes its status. On a bare machine nothing does, so the program brings
its own **runtime**: a few instructions that run first, give `main` a
stack, call it, and hand its result to the outside world.

Three programs make a running program of the compiler's text:

- **Assemble.** The assembler, `riscv64-elf-as`, turns one file of
  assembly into an **object file**: the instructions as numbers, and a
  table of the names the file defines and those it uses without defining.
  Its code starts at address 0: where it will sit is not known yet.
- **Link.** The linker, `riscv64-elf-ld`, joins object files into one
  program. A **linker script** says where each piece goes in memory; then
  the linker fills in each use of a name with the address it stands for.
- **Run.** QEMU, `qemu-system-riscv64`, imitates `virt`, a RISC-V board
  that exists only in QEMU. With no firmware (`-bios none`), it puts the
  program's bytes in memory and jumps to 0x80000000, the first byte of the
  machine's memory, where the linker put the runtime's first instruction.

![From the first instruction to QEMU's exit, one step at a time.](figures/00.02-run.svg)

### assemble, link and run

`ccrun` does the three steps for one file: `./cc` into `build/prog.s`,
the assembler on that and on `rt/start.S`, the linker with `rt/link.ld`,
then QEMU, started with `exec` so that its exit status is `ccrun`'s. First
it finds the tools, named `riscv64-elf-...` (Homebrew's),
`riscv64-unknown-elf-...` (Debian's) or `riscv64-linux-gnu-...`, and QEMU.

### rt/start.S

The start-up code. `_start` sets `sp`, the **stack pointer**, to
`stack_top`, calls `main`, and turns what `main` returned into one 32-bit
word, which it stores at 0x100000. `.section .text.start` puts it in a
section of its own, which the linker script places first.

### rt/link.ld

The linker script. `. = 0x80000000;` is where the program starts, because
the `virt` machine's memory starts there. Then the code, `_start`'s section
first; the constants, the data and the zeroed data, all empty for now; and
64 KiB for the stack, whose top, since a stack grows down, is `stack_top`.

## Run it

`./learn run cc --at 00.02` compiles `try.c` and runs it. The program has
no way to print yet (lesson 04.01 gives it one): its whole result is its
status. Then the same by hand in the project's folder, with `nm` to list
the names in each object file. On Linux the tools may be named
`riscv64-unknown-elf-as` and so on: type that in place of `riscv64-elf-`.

<!-- verify: session wait=10 -->
```
$ ./learn run cc --at 00.02
Running cc as it stands at 00.02 (What the assembler, the linker and the machine do with it). Its files are in build/at/cc/00.02/
$ echo $?
42
$ cd build/at/cc/00.02
$ ./cc -o prog.s try.c
$ riscv64-elf-as -march=rv64im -mabi=lp64 -o start.o rt/start.S
$ riscv64-elf-as -march=rv64im -mabi=lp64 -o prog.o prog.s
$ riscv64-elf-nm start.o prog.o

start.o:
0000000000000000 T _start
                 U main
                 U stack_top

prog.o:
0000000000000000 T main
```

`-march=rv64im` allows 64-bit RISC-V with multiply and divide;
`-mabi=lp64` is the calling convention, with 64-bit `long` and pointers.
In `nm`'s list `T` is a name the file defines, at the address beside it,
and `U` one it uses without defining: `start.o` calls `main` without
knowing where it is. The linker settles that. QEMU then runs the result
with no window, no console of its own, and the machine's serial port on
this terminal:

<!-- verify: session -->
```
$ riscv64-elf-ld -T rt/link.ld -o prog.elf start.o prog.o
$ riscv64-elf-nm prog.elf
0000000080000000 T _start
0000000080000038 T main
0000000080010040 T stack_top
$ qemu-system-riscv64 -machine virt -bios none -display none -monitor none -serial stdio -kernel prog.elf
$ echo $?
42
```

Here is the program taken apart by `objdump` (the `sed` skips its
header): each line an address, the instruction stored there as a number,

## How it works

### The stack, before the first call

```
  la sp, stack_top              # the stack grows down from the top of its room
  call main
```

The **stack** is memory a function uses for what does not fit in
registers: the address to return to when it calls another function, its
local variables. `sp` points at its top, and it grows down. When the
machine starts, nothing has set `sp`. `main` for 42 never touches the
stack, but most functions do, at once: gcc's `main` for `return 1 + 2 * 3;`
at `-O0` starts with `addi sp,sp,-16` and `sd ra,8(sp)`. So `sp` is set
first, to the top of the 64 KiB `rt/link.ld` set aside. `call` itself needs
no stack: it leaves the return address in `ra`, and `ret` jumps back to it.

### Stopping a machine with no operating system

```
  li t1, 0x100000               # the test device
  sw t0, 0(t1)
```

A program under an operating system ends by asking the system to end it.
Here there is no system, but QEMU's `virt` machine has a device for it,
the **test device**, at 0x100000. QEMU's source (version 10.2.1) reads a
32-bit store there as a command in the low 16 bits and a code in the high
16: 0x5555 means "passed" and 0x3333 "failed", and for either QEMU exits
with the code; 0x7777 resets the machine; anything else is ignored.
`rt/start.S` writes 0x5555 when `main` returned 0, and otherwise the
status shifted left 16 bits with 0x3333. That is its own choice: 0x75555
makes QEMU exit with 7 too, so 0x5555 would serve for every status. The
two differ only in the reason QEMU records for stopping, which the exit
status does not show.

### A status is eight bits

```
  andi a0, a0, 0xff             # the status: main's low 8 bits
```

`main` returns a 64-bit register, but an exit status is 8 bits by the time
a shell sees it. 300 is 0x12C; its low 8 bits are 0x2C, 44. The `andi`
keeps those bits, so 256 becomes 0 and takes the 0x5555 path. Without it
nothing you can see would change, since the operating system under QEMU
keeps only 8 bits of QEMU's exit code; it says in the code what a status is.

### What the disassembly says that the source did not

Where the source of `_start` has `la sp, stack_top`, the disassembly has
`auipc` and `addi`: `la` is a **pseudo-instruction**, a line the assembler
writes as one or more real instructions. `auipc sp,0x10` puts its own
address plus 0x10000 in `sp`, and `addi` adds 64: 0x80010040, `stack_top`.
`li t0, 0x5555` became `lui` and `addiw` the same way, and the `andi` is
printed as `zext.b`, another name for the same instruction.

And `call main` became one `jal`. In `start.o`, before linking, it was two:

<!-- verify: session -->
```
$ riscv64-elf-objdump -d start.o | grep -A4 '<_start>:'
0000000000000000 <_start>:
   0:	00000117          	auipc	sp,0x0
   4:	00010113          	mv	sp,sp
   8:	00000097          	auipc	ra,0x0
   c:	000080e7          	jalr	ra # 8 <_start+0x8>
```

In the object file every address is still 0, for the linker to fill in,
and `call` is the pair `auipc` and `jalr`, which can reach far: the
assembler cannot know how far away `main` will be. The linker knows, 0x30
bytes, so it put one `jal` in place of the pair and moved everything after
it 4 bytes down. This is **relaxation**, and why `main` is at 0x38.

## Decide the boundary

These programs run on a bare machine, with nothing between them and the
processor but `rt/start.S`. A program could instead run as a process under
an operating system, as the programs of [the xv6 track](/t/xv6) do: the
kernel loads it, gives it a stack and its arguments, lets it read files
and print, and ends it when it asks. The bare machine starts in a few
hundredths of a second, and nothing runs that the compiler and the runtime
did not write, so whatever the program does is their doing. It also gives
a program nothing: no files, no printing until lesson 04.01 drives the
serial port by hand. An operating system gives all that, and in return
the programs must follow its rules for how a program starts, asks for
things and ends. This track runs its programs on xv6 only near the end,
in lesson 09.04. How much does a program need from the world around it to
show that its compiler is right?

## Break it

Move the program away from where the machine starts. In
`build/at/cc/00.02/rt/link.ld`, change the line `. = 0x80000000;` to
`. = 0x80001000;`, and run `try.c` again:

<!-- verify: patch file=rt/link.ld old="= 0x80000000;" new="= 0x80001000;" -->
<!-- verify: session hangs=3 timeout=5 -->
```
$ ./ccrun try.c
```

Nothing comes back. Press Ctrl-C, which stops QEMU, and look at where the
linker put things:

<!-- verify: session send=ctrl-c
vary 12345 int
-->
```
qemu-system-riscv64: terminating on signal 2 from pid 12345 (<unknown process>)
$ riscv64-elf-nm build/prog.elf
0000000080001000 T _start
0000000080001038 T main
0000000080011040 T stack_top
```

The program is all there, 0x1000 bytes higher. But QEMU still jumps to
0x80000000, where there is nothing now: memory the program did not fill,
which QEMU starts as zeros. The machine never reaches `_start`, never
stores to the test device, and QEMU never stops. The linker script and the
machine must agree on that address, and nothing but the hang tells you
when they do not. Put the line back.
