# 00.01 From a number to assembly

A compiler is an ordinary program: it reads a file of text and writes
another file of text. This lesson builds the smallest one there is, for a
language whose only program is a single number, and follows that number
along the whole road its output travels, to a status coming back from a
RISC-V machine.

The compiler is built on chibicc, Rui Ueyama's small C compiler. From
module 01 on, its scanner and its parser keep chibicc's function names and
structure, so you can hold [its source](https://github.com/rui314/chibicc)
beside these lessons. The part that writes RISC-V, and everything after the
compiler, are this course's own.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

This is the whole system in one picture. Source text goes into the compiler
at the top, assembly comes out, and along the bottom three more programs
turn it into a running program and bring back a number. Each box is given
something and gives something back:

- **The compiler**, `cc`, is given a C source file and gives back
  **assembly**: the machine's instructions written as text, one a line.
  Inside it, in order:
  - **the scanner** is given the characters and gives back **tokens**, the
    words of the program: numbers, names, operators;
  - **the preprocessor** is given tokens and gives back tokens, with
    `#include` and macros carried out;
  - **the parser** is given tokens and gives back a **syntax tree**, the
    structure of the program, each operator with its operands under it;
  - **types** go over the tree and give every value in it a type;
  - **the code generator** is given the tree and writes the assembly.
- **The assembler** is given assembly and gives back an **object file**:
  the instructions as the numbers the machine runs, with names it could
  not settle left for later.
- **The linker** is given object files, the program's and the
  **runtime**'s, the few instructions that start a program on a machine
  with nothing else on it, and gives back one program with every piece at
  a fixed address.
- **The bare machine** is a RISC-V computer that QEMU, an emulator,
  imitates on yours. It is given the program, runs it, and hands back the
  number `main` returned, as QEMU's exit status.
- **gcc, for the same machine**, takes the same source along a lane of its
  own, so that the two numbers can be compared.

![One program, from the file that holds 42 to the status 42 coming back: every stage it passes through, and what each hands to the next.](figures/00.01-journey.svg)

Follow one program. A file holds the text `42`. The compiler reads it and
writes four lines of assembly. The assembler turns them into two
instructions, as numbers. The linker joins those with the runtime's
start-up code into one program that begins at address 0x80000000. QEMU
runs it, and the shell sees 42.

This lesson builds the frame of the compiler: a program that reads a file
and writes assembly. Nothing inside the frame exists yet; one function does
the work of all of it, for a language with one kind of program. Lesson
00.02 runs the assembler, the linker and the machine by hand and adds the
runtime. Lesson 00.03 adds gcc's lane, to check every answer against. Then
the compiler grows from the front, a phase at a time, and is a whole
compiler at every lesson: tokens (module 01), expressions with their tree
and the first real code generator (02), statements (03), functions (04),
names and scopes (05), types (06), arrays, strings and structs (07), the
preprocessor (08), and real programs, ending with the compiler compiling
itself (09). The road to the machine and the check come first so that,
from the first lesson on, everything the compiler writes is run and
compared.

## The idea

![The four lines the compiler writes, and what each one is for.](figures/00.01-four-lines.svg)

A RISC-V processor runs **instructions**: small commands, each one number,
that do one thing, such as put a value in a register or jump to another
address. It knows nothing of C. Someone has to turn a program into
instructions, and that is the compiler's job.

The smallest program with a result you can see is one that returns a
number. What `main` returns becomes the program's **exit status**, the
number a shell prints for `echo $?`. So the language of this lesson is a
file holding one number, and the file `42` means the C program
`int main(void) { return 42; }`. The compiler writes four lines for it:

- `.globl main` is a **directive**, an order to the assembler rather than
  an instruction. It makes the name `main` visible outside this file, so
  that the linker can join it to the start-up code that calls it.
- `main:` is a **label**. It names the address of whatever comes next.
- `li a0, 42` loads 42 into **register** `a0`. Registers are the
  processor's few fast places to hold a value while it works on it. The
  RISC-V **calling convention**, the rules every compiler for the machine
  follows so that their code can call each other's, says a function leaves
  its result in `a0`.
- `ret` returns to whoever called `main`.

### the command line

`parse_args` goes through the arguments: one file to compile, `-o` to name
the file the assembly goes to (without it, standard output), `--help`, and
nothing else. A second file, or anything else that starts with `-`, is an
error. Module 01 adds `--tokens` here, and module 02 `--tree`, to print
what the scanner and the parser make.

### reading the file

`read_file` reads the whole file into one buffer in memory, made bigger
with `realloc` as it fills, and returns it as one string. The name `-`
means standard input, so `printf 42 | ./cc -` works too.

### `main`

At this lesson `main` is the whole compiler. After the command line and the
file, it skips spaces and newlines, insists on a digit, reads the number,
insists that nothing but spaces and newlines follows, and prints the four
lines. Anything else stops it in `error`, with a message on standard error
and exit status 1. `usage` and `open_file`, which opens the `-o` file, come
whole with it. Lesson 01.01 changes this: a scanner reads the file, and
`main` walks its tokens.

## Run it

`./learn run cc --at 00.01` builds the compiler and gives it the lesson's
sample, `try.c`, which holds `42`:

```
$ ./learn run cc --at 00.01

  .globl main
main:
  li a0, 42
  ret
```

That is as far as it goes: nothing yet turns the text into a program and
runs it. Lesson 00.02 does. The compiler is `cc` in the project's folder,
built from `main.c` by `make` with your own computer's C compiler. Go there
and give it a file that is not one number, and one that is not there:

<!-- verify: session -->
```
$ cd build/at/cc/00.01
$ cat try.c
42
$ ./cc try.c
  .globl main
main:
  li a0, 42
  ret
$ printf '4 2\n' > two.c
$ ./cc two.c; echo $?
expected the end of the file after the number
1
$ ./cc nosuch.c; echo $?
cannot open nosuch.c
1
```

Each error is one line and status 1, and nothing goes to standard output:
the checks all come before the first line of assembly is printed, so a file
the compiler does not understand never gets half a program.

## How it works

### Text, not machine code

The compiler writes assembly with `fprintf`, as text, and not the numbers
the machine runs:

```
  fprintf(out, "  li a0, %lu\n", val);
```

That buys two things. You can read what it wrote, as above, and compare it
line by line with what another compiler writes. And the assembler, which
already knows how every instruction is encoded and how an object file is
laid out, does that work. The cost is one more program between the
compiler and a result, and the same instructions read twice: the compiler
prints `li a0, 42` and the assembler parses it back.

### Base 10, on purpose

```
  unsigned long val = strtoul(p, &p, 10);
```

`strtoul` reads digits from `p`, returns their value and moves `p` past
them. The `10` says the digits are decimal, and decimal is the whole
language here: in `0x2A` it reads the `0` and stops at the `x`, and `main`
says "expected the end of the file after the number". Base 0 would have
`strtoul` guess the base the way
C writes numbers, so `0x2A` would be 42; but then what a number means would
be up to the C library of the computer that runs the compiler, not up to
the compiler. C's other ways of writing a number come in lesson 01.04, read
by the scanner, with its own rules and its own messages. The decision has a
price: C reads `042` as octal, 34, and this compiler reads it as 42. Lesson
00.03 builds the tool that catches that kind of difference.

### One buffer, ending in a newline

The file is read whole, once, into one buffer. Every later phase works in
that buffer and copies nothing out of it: from 01.01 a token is a pointer
into it and a length, and from 01.05 an error finds its line by walking
from such a pointer to the newlines on either side. The buffer always ends
in a newline and a `'\0'`, whatever the file ends in:

```
  if (len == 0 || buf[len - 1] != '\n')
    buf[len++] = '\n';
  buf[len] = '\0';
```

There is always room for those two bytes, because of the one **invariant**
the reading loop keeps: it never lets `fread` fill the last two bytes of
the buffer.

```
    int n = fread(buf + len, 1, cap - len - 2, fp);
```

The newline is chibicc's, and nothing in modules 00 to 02 depends on it:
the scanner and the error messages stop at the `'\0'` as well. It stays
because with it the last line of every file ends the way the others do.

## Decide the boundary

This compiler writes assembly and stops. Another could write the object
file itself: encode each instruction as its number, lay out the file with
its names and the notes the linker needs, and leave the assembler out. It
would be one program fewer to run. It would also be a second assembler
inside the compiler, to be kept right for every instruction the compiler
ever writes, and its output could not be read without taking it apart
again. chibicc writes assembly too; its first commit, for x86-64, writes
the number with `printf("  mov $%d, %%rax\n", atoi(argv[1]));` and then
`printf("  ret\n");`. This track builds an assembler and a linker of its
own only in an optional module at the end (module 11), once the compiler
is finished and the instructions it writes are known. Do you need a
compiler that stands alone, or one that leans on tools that already exist
and are already right?

## Break it

Let the C library decide what a number means. In
`build/at/cc/00.01/main.c`, in `main`, change the base of the `strtoul`
call from 10 to 0, so that it reads `strtoul(p, &p, 0)`:

<!-- verify: patch file=main.c old="strtoul(p, &p, 10)" new="strtoul(p, &p, 0)" -->

Then build it again and give it a number with a leading zero, and one that
is not octal:

<!-- verify: session -->
```
$ make -s
$ printf '042\n' > o.c
$ ./cc o.c
  .globl main
main:
  li a0, 34
  ret
$ printf '09\n' > n.c
$ ./cc n.c
expected the end of the file after the number
```

`042` is now 34, octal, which is what C says. But nothing in this compiler
decided that: `strtoul` did. And `09`, which was 9 a moment ago, is now an
error that describes the wrong thing: `strtoul` read `0` as an octal number
and stopped at the `9`, so `main` saw a number followed by something else.
A compiler that borrows its rules gets the borrowed errors too. Put the
line back.
