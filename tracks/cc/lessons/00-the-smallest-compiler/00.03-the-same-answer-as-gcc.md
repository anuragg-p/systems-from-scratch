# 00.03 The same answer as gcc

A compiler is right when the programs it writes do what the language says.
This lesson builds the practical form of that check, the one the whole
track uses: build the same source with gcc for the same machine, run both
programs, and compare what they do.

## Where this fits

![Where 00.03 fits](figures/00.03-map.svg)

This lesson builds the lane beside the bottom row of the map: gcc, for the
same machine, taking the same source text to the same bare machine, and
the comparison where the two lanes meet. Under it is everything lesson
00.02 built, the runtime and QEMU included, used unchanged by both lanes.
Above it is the compiler, whose every program can now be held against
gcc's. After this lesson one command says whether this compiler and gcc
agree on a program.

## The idea

![The same source through two compilers to the same machine: the statuses must match.](figures/00.03-two-compilers.svg)

Lesson 00.02 ended with 42 coming back from the machine, and for a file
that holds `42` anyone can see that is right. That stops working soon. By
module 02 the input is an expression with dozens of operators, and someone
would have to work out each answer by hand, and be right every time. gcc
already knows what every C program means. So ask it: build the same source
with gcc, run its program on the same machine, and compare the two
results.

It has to be gcc **for the same machine**, `riscv64-elf-gcc`, and not the C
compiler your computer uses for its own programs. C leaves some things to
each platform to decide, and both answers must come from the same
decisions. Plain `char` is one: it is unsigned on RISC-V, and signed on
x86-64 and on macOS. And everything else must be the same as well: both
programs link with the same start-up code, sit at the same addresses and
run on the same QEMU. Then the only thing left that differs is the
compiler. When the two statuses differ, `same` shows both and says so;
below, for a compiler made wrong on purpose, the one this lesson ends with.

![A compiler that is wrong on purpose: the two statuses differ, and same says so.](figures/00.03-differ.svg)

### the same program from gcc

The body of `same`. It builds the file with the compiler under test into
`build/same/ours.elf`, the same steps `ccrun` takes. Then it builds the
file with gcc. The input is not C yet, only an expression, so for gcc it is
wrapped in a `main` that returns it: `int main(void) { return ` before the
file, and a newline and `; }` after it. The wrapping is temporary: lesson
03.01 makes the input a whole C program, and it goes. gcc gets `-O0`, no
optimisation; `-march=rv64im -mabi=lp64`, the instructions and the calling
convention ours uses; `-ffreestanding -nostdlib -fno-builtin`, because
there is no C library on this machine; `-mcmodel=medany -fno-pie`, because
the program sits at 0x80000000, which matters from lesson 05.02, when there
are global variables to reach; and `-mno-relax`, no relaxation. Then it
runs both programs with no input, keeping what each prints and its status.
If both agree it prints `same: status N` and exits 0; otherwise it prints
each one's status and output, then `differ`, and exits 1. Given whole with
it: the usage line, the search for gcc and for QEMU, and `CC_UNDER_TEST`,
which names a compiler to test in place of `./cc`.

## Run it

`./learn run cc --at 00.03` still runs `try.c` with `ccrun`. In the
project's folder, `same` builds it both ways:

<!-- verify: session wait=10 -->
```
$ ./learn run cc --at 00.03
Running cc as it stands at 00.03 (The same answer as gcc). Its files are in build/at/cc/00.03/
$ echo $?
42
$ cd build/at/cc/00.03
$ ./same try.c; echo $?
same: status 42
0
$ cat build/same/gcc.c
int main(void) { return 42

; }
```

The file gcc compiled is the wrapped one: `try.c` ends in a newline, and
the wrapping adds another before the `; }`. Now a number with a leading
zero:

<!-- verify: session -->
```
$ printf '042\n' > o.c
$ ./same o.c; echo $?
ours: status 42
gcc: status 34
differ
1
```

A real difference, and the one lesson 00.01 chose: C reads `042` as octal,
34, and this compiler reads every number in base 10. The language of these
first lessons is a decimal number, which is not quite C. Lesson 01.04
changes this, when the scanner learns C's ways of writing numbers.

## How it works

### Only the compiler differs

The two programs are linked by two lines that differ only in the compiler's
object file:

```
"${prefix}ld" -T "$here/rt/link.ld" -o "$build/ours.elf" "$build/start.o" "$build/ours.o" || exit 2
...
"${prefix}ld" -T "$here/rt/link.ld" -o "$build/gcc.elf" "$build/start.o" "$build/gcc.o" || exit 2
```

The same `start.o`, assembled once, the same linker script, then the same
QEMU command for both. That is the **invariant** the script keeps:
everything between the source and the status is shared, except the
compiler. So a difference can only be the compiler's doing. The two
programs are not the same code, and `same` does not ask them to be. Build
`try.c` again and take gcc's object file apart: its `main` for 42 is ten
instructions where ours is two.

<!-- verify: session -->
```
$ ./same try.c
same: status 42
$ riscv64-elf-objdump -d build/same/gcc.o | tail -11
0000000000000000 <main>:
   0:	ff010113          	addi	sp,sp,-16
   4:	00113423          	sd	ra,8(sp)
   8:	00813023          	sd	s0,0(sp)
   c:	01010413          	addi	s0,sp,16
  10:	02a00793          	li	a5,42
  14:	00078513          	mv	a0,a5
  18:	00813083          	ld	ra,8(sp)
  1c:	00013403          	ld	s0,0(sp)
  20:	01010113          	addi	sp,sp,16
  24:	00008067          	ret
```

At `-O0` gcc gives every function a **frame**, its own piece of the stack,
and keeps values in it, even when there is nothing to keep. What `same`
compares is what the programs do, never how.

### One sample proves little

`try.c` agreed and `042` did not, and the compiler was the same both times.
A compiler can agree on one program by luck, or because the program is too
small to show its mistake; 42 has no leading zero to get wrong. What `same`
is worth depends on how many programs go through it, and how different
they are. It costs one command, so an expression with forty operators is
checked as easily as 42, and a thousand of them as easily as one.

### What it compares, now and later

```
if [ "$ours_status" -eq "$gcc_status" ] && cmp -s "$build/ours.out" "$build/gcc.out"; then
```

The status, and everything the program printed. Nothing can print yet, so
both outputs are empty; from lesson 04.01, when programs can print, the
output counts as much as the status. And a status is only 8 bits:

<!-- verify: session -->
```
$ printf '300\n' > n.c
$ ./same n.c
same: status 44
```

Both programs return 300, and both statuses are 44. A compiler that wrote
44 for 300 would agree just as well: the bits of a result above the lowest
8 never reach `same`.

## Decide the boundary

`same` checks this compiler against another compiler. The other way is to
write each program together with the answer it should give, worked out by
hand, and check the status against that. Each catches what the other
misses. A mistake both compilers make passes `same`, since they agree; an
answer worked out by hand catches it, if the answer is right.
But answers worked out by hand are sometimes wrong, and each one costs a
person's time, which keeps the programs few; gcc answers any program, so a
thousand cost no more than one. And on some programs neither works. C
leaves them **undefined**: an `int` that overflows, a division by zero. A
correct compiler may do anything with them, so two correct compilers can
disagree, and `same` reports a difference that is no bug, while no answer
written by hand is the right one either. Programs given to `same` must stay
inside what C defines. When the two disagree, whom do you believe: a second
compiler, or your own reading of the language?

## Break it

Make a compiler that is wrong on purpose. `wrongcc` is a shell script
that ignores its input and always writes the program for 7. `same` calls a
compiler as `-o FILE SOURCE`, so the script's `$2` is where the assembly
goes. Type it in the project's folder, then hand it to `same` through
`CC_UNDER_TEST`:

<!-- verify: session -->
```
$ cat > wrongcc <<'EOF'
#!/bin/sh
printf "  .globl main\nmain:\n  li a0, 7\n  ret\n" > "$2"
EOF
$ chmod +x wrongcc
$ CC_UNDER_TEST=./wrongcc ./same try.c; echo $?
ours: status 7
gcc: status 42
differ
1
$ printf '7\n' > seven.c
$ CC_UNDER_TEST=./wrongcc ./same seven.c; echo $?
same: status 7
0
```

On `try.c` the two lanes disagree, and `same` says so and exits 1, so a
script can stop on it. On a file that holds 7, the same wrong compiler
agrees: one sample proved nothing about it. The variable is not called
`CC`, the usual name, because `CC` already names the C compiler `make` and
many shells use for your own computer's programs; with `CC=gcc` set, `same`
would have tested gcc against gcc.
