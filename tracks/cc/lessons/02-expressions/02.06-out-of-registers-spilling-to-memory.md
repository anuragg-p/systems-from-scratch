# 02.06 Out of registers: spilling to memory

Six registers hold six waiting values. When a seventh value has to wait, it
waits somewhere else, and the somewhere else is the stack in memory: stored
there, and loaded back just before the one instruction that needs it.

## Where this fits

![Where 02.06 fits](figures/02.06-map.svg)

This lesson is the last cell of the code generator in this module,
"spilling", beside the registers-as-a-stack of lesson 02.03. Nothing above it

the code now uses the memory the runtime of lesson 00.02 set aside as the

too deep. Every expression of the module compiles, however its tree leans.

## The idea

![9 - (8 - (7 - (6 - (5 - (4 - (3 - 2)))))): six registers fill, then the stack in memory takes the rest and gives it back.](figures/02.06-spill.svg)

At lesson 02.03, `1 - (2 - (3 - (4 - (5 - (6 - 7)))))` stopped with "out of
registers". Every subtraction in it has a whole subtraction as its right
operand, so every left operand has to wait, and six of them fill `t0` to `t5`.
More registers would only move the limit: an expression can always be one
level deeper. What is needed is a place that holds as many values as an
expression can have waiting.

Memory is that place, and the program already has some set aside: the 64 KiB
stack that `rt/link.ld` lays out and `rt/start.S` points `sp` at, the **stack
pointer**. The stack grows down. To keep a value there, the code moves `sp`
down to make room and stores the register at the new `sp`; to get it back, it
loads from `sp` and moves `sp` up again. Putting a register's value in memory
because the register is needed for something else is called **spilling**.

This lesson's sample is the deepest yet, `9 - (8 - (7 - (6 - (5 - (4 - (3 -
2))))))`. The numbers 9 to 4 fill `t0` to `t5`. At `4 - (3 - 2)` the 4 is in `t5`, the last
register, and the right operand has nowhere to go. So the 4 goes to the stack,
and `t5` is free for `3 - 2`. Inside that, the 3 is in `t5` again, the last
register again, so the 3 goes to the stack too, and the 2 takes `t5`. Then the
values come back in the opposite order: 3 into `t6`, `3 - 2` is 1; 4 into `t6`,
`4 - 1` is 3. From there the waiting registers finish as at lesson 02.03, down
to 4 in `t0`.

### `spill`

What `gen_expr` does for an operator whose left operand landed in the last
register, instead of writing the right operand's code one register up. It
moves `sp` down by 16 and stores that register there with `sd`; writes the
right operand's code at the same depth, into the register it just freed, which
may spill again, deeper; loads the left operand back into `t6` with `ld` and
moves `sp` back up; and writes the operator's instruction with `t6` as the left
operand. In `gen_expr`, the call takes the place of the "out of registers"
error.

## How it works

### Six, not seven

The stack of registers is `t0` to `t5`, though the machine has a `t6` too:

```
static char *reg[] = {"t0", "t1", "t2", "t3", "t4", "t5"};
```

`t6` is kept out of it on purpose. When the left operand comes back from
memory, the right operand's value is in the last register, and every register
below it holds a value still waiting. The left operand needs a register of its
own for the one instruction that combines the two, and the only one that is
sure to be free is one the stack never uses:

```
  println("  ld t6, 0(sp)");
```

With `t6` in the stack as well, the scheme would need some other register
kept spare for the same moment. One register is given up so that every spill
can come back the same way.

### The left operand is in `t6` now

After the reload, the left operand is in `t6` and the right one in the
register at `d`, the other way round from every other operator. The
instruction must follow the tree, not the registers:

```
  gen_binary(node, reg[d], "t6", reg[d]);
```

so a spilled subtraction is `sub t5, t6, t5`, left minus right. For `+`, `*`,
`&`, `|`, `^`, `==` and `!=` the order of the operands makes no difference,
and a mistake here would never show. Subtraction is why this lesson's sample
is all subtractions. The Break it below swaps the two.

### 16 bytes for 8

A register is 8 bytes, but `sp` moves by 16. The RISC-V calling convention
keeps the stack pointer a multiple of 16, as the comment above `spill` says,
and a spill keeps to it like any other code. Half of each slot is unused.

### Simple, not good

The second spill above stores the 3 only so that the number 2 can be loaded
into `t5`, and then loads the 3 back into `t6`. The 2 needed no register at
all; `li t6, 2` would have done. The scheme spills whenever the right operand
needs the register at `d + 1` and there is none, without looking at what the
right operand is. That keeps it to one rule and six lines, and it makes some
deep expressions cost more instructions and memory accesses than they need.

## Decide the boundary

The same seven subtractions can be written to lean the other way:

<!-- verify: session -->
```
$ printf '((((((1 - 2) - 3) - 4) - 5) - 6) - 7) - 8\n' > left.c; ./cc left.c
  .globl main
main:
  li t0, 1
  li t1, 2
  sub t0, t0, t1
  li t1, 3
  sub t0, t0, t1
  li t1, 4
  sub t0, t0, t1
  li t1, 5
  sub t0, t0, t1
  li t1, 6
  sub t0, t0, t1
  li t1, 7
  sub t0, t0, t1
  li t1, 8
  sub t0, t0, t1
  mv a0, t0
  ret
```

![The same seven subtractions written two ways: leaning right the tree needs every register and two spills, leaning left it needs two registers.](figures/02.06-leaning.svg)

Leaning left, nothing ever waits but one value, in `t0`. How many registers
an expression needs depends on which side its depth is on, because the left
operand is always computed first and has to wait. C lets a compiler compute
either operand of a `-` first. A code generator that looked at both operands
and computed the deeper one first would need only two registers for the
right-leaning chain too: a third only where both sides of a node need as many.
Counting each node's need this way is known as Sethi-Ullman numbering. It
costs a pass over the tree before the code is written, and code whose order
no longer follows the source.

Other compilers make other choices. tcc keeps a stack of values too, but when its registers run out it spills the oldest value, the
one at the bottom, not the newest. gcc at `-O0`, as lesson 02.03 showed, does
not try to keep values in registers at all: every variable lives in memory.
Real register allocation, where each value gets a register for exactly the
stretch of code that needs it, is a back end of its own, this track's module
10. This one is six lines that anyone can check by reading. How deep do the
expressions you compile really go, and what is a handful of memory accesses on
the rare deep one worth against a code generator you can hold in your head?

## Break it

Swap the operands back to the order every other operator uses. In
`build/at/cc/02.06/codegen.c`, at the end of `spill`, change

<!-- verify: patch file=codegen.c
-  gen_binary(node, reg[d], "t6", reg[d]);
+  gen_binary(node, reg[d], reg[d], "t6");
-->
```
  gen_binary(node, reg[d], "t6", reg[d]);
```

to

<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
  gen_binary(node, reg[d], reg[d], "t6");
```

and build again:

<!-- verify: session -->
```
$ make -s
$ ./ccrun try.c; echo $?
12
$ ./same try.c
ours: status 12
gcc: status 4
differ
```

Both spilled subtractions are now right minus left: `2 - 3` is -1 instead of
1, and `-1 - 4` is -5 instead of 3. The five subtractions after them are
correct, and they carry the wrong value up: 5 - (-5) is 10, and so on, to 12
instead of 4. On a sum the same change gives the right answer, which is why it
needs a subtraction, and a spill, to be seen at all. Put the line back.
