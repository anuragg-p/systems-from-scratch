# 02.03 Code from a tree: registers as a stack

The code generator walks the tree once and writes an instruction for every
node. The one question it has to answer is where each value waits while the
rest of the expression is computed, and the answer here is a stack kept in
registers.

## Where this fits

![Where 02.03 fits](figures/02.03-map.svg)

This lesson is the code generator, the last box of the compiler on the map.
The parser to its left hands it the tree; it writes the assembly that leaves
the compiler on the right and goes on to the assembler, the linker and the
machine of module 00. With it the compiler is three phases in a row: tokens,
then a tree, then code. The walk over the tokens that made the code since
module 01 is gone. After this lesson every expression of numbers, `+`, `-`,
`*`, `/` and parentheses compiles to a program that gives gcc's answer, as
long as it is not nested too deep.

## The idea

![The code for 1 + 2 * 3, one instruction a step: the registers are a stack, and each operator replaces its two operands with one value.](figures/02.03-registers.svg)

The machine does arithmetic in **registers**, the few small stores inside the
processor that its instructions work on. RISC-V's `add`, `sub`, `mul` and
`div` each take two registers and write a third. So to compute `1 + 2 * 3`,
the 1 must sit in a register while `2 * 3` is worked out, and `2 * 3` needs
two registers of its own. Something has to decide which register holds what,
and when one can be used again.

This compiler uses the temporary registers `t0` to `t5` as a **stack**. A
value is pushed by putting it in the next register up, and an operator pops
its two operands and pushes its result, which here means: it combines the two
top registers into the lower one. The position in the stack is a **depth**, `d`:
depth 0 is `t0`, depth 1 is `t1`. The whole code generator is one rule:

![The one rule of the code generator: a node's value goes in the register at its depth, the left operand at the same depth, the right one a register higher.](figures/02.03-depth.svg)

For `1 + 2 * 3`, the `+` is at depth 0. Its left operand, 1, goes in `t0`.
Its right operand, the `*`, is at depth 1: its left operand, 2, goes in `t1`,
its right one, 3, in `t2`, and `mul t1, t1, t2` leaves 6 in `t1`. Then
`add t0, t0, t1` leaves 7 in `t0`. Five instructions, one for each node of the
tree, in the order of a walk that visits a node's children before the node
itself.

`li` (load a number into a register) and `mv` (copy one register to another)
are **pseudo-instructions**: names the assembler accepts for one or two real
instructions, so that the compiler does not have to spell those out.

### `gen_binary`

One operator's instruction: `add`, `sub`, `mul` or `div`, from the two source
registers into the destination. `div` is the signed division, which rounds
toward zero, as C's `/` does on integers. Any other kind of node is an
"invalid expression"; at this lesson there is none, and lessons 02.04 and
02.05 add the other operators here.

### `gen_expr`

The walk. A number is one `li` into the register at depth `d`. An operator
puts its left operand at `d`, its right operand at `d + 1`, and calls
`gen_binary` to combine them into the register at `d`. When `d + 1` would be
past `t5`, there is no register left for the right operand, and the compiler
stops with "out of registers", pointing at the operator. Lesson 02.06 changes
this.

### `codegen`

The whole program: `main` made global and its label, as since lesson 00.01;
the expression at depth 0; its value moved from `t0` into `a0`; and `ret`. The
driver now calls this after the parser, where the walk over the tokens used to
be.

```
$ cd build/at/cc/02.03
$ ./cc try.c
  .globl main
main:
  li t0, 1
  li t1, 2
  li t2, 3
  mul t1, t1, t2
  add t0, t0, t1
  li t1, 4
  li t2, 2
  div t1, t1, t2
  sub t0, t0, t1
  mv a0, t0
  ret
$ ./same try.c
same: status 5
```

The first five instructions are the figure's. Then `4 / 2` is worked out in
`t1` and `t2` while 7 waits in `t0`, and the `sub` at the root makes 5. Now an
expression in which each subtraction is inside the right operand of the one
before:

<!-- verify: session -->
```
$ printf '1 - (2 - (3 - (4 - (5 - (6 - 7)))))\n' > deep.c; ./cc deep.c >/dev/null; echo $?
deep.c:1: 1 - (2 - (3 - (4 - (5 - (6 - 7)))))
                                     ^ out of registers: the expression is too deep
1
```

The numbers 1 to 6 are left operands still waiting, in `t0` to `t5`, when the
last `-` needs a register for the 7.

## How it works

### Nothing below is touched

The **invariant** is in the comment above `gen_expr`: the code for a node at
depth `d` leaves its value in the register at `d`, may use the registers above
it, and never changes the ones below, which hold values still waiting for
their operator. One line keeps it:

```
  gen_expr(node->rhs, d + 1);
```

The right operand's code starts one register higher, so whatever it does, it
does at `d + 1` and above, and the left operand's value in the register at `d`
is still there when `gen_binary` needs it. Each operand's code is correct by
itself, wherever in a bigger expression it ends up, because it only ever
looks up the stack.

### The left operand waits

<!-- verify: mention names="deep.c" outside reason="the file the reader made in Run it, not part of the project" -->
The left operand's code comes first, as the expression reads, and its value
waits while the right operand's code runs. How long it waits, and how many
registers are in use at once, depends on the tree's shape. In `try.c` it is
never more than three: the right operands, `2 * 3` and `4 / 2`, are each one
operator over two numbers. In `deep.c` every right operand is a whole
subtraction, and each one adds a waiting value. A tree that leans left needs
only two registers however long it is; a tree that leans right needs one more
for every level.

### `a0` at the end

`gen_expr` leaves the value in `t0`, but nobody looks there. A function hands
its result back in `a0`, which is why the compiler of lesson 00.01 wrote
`li a0, 42`, and the `call main` in `rt/start.S` takes what it finds in `a0`
as the status. Hence the last instruction before `ret`:

```
  println("  mv a0, %s", reg[0]);
```

## Decide the boundary

This compiler keeps waiting values in registers and touches memory never,
for now. chibicc, whose parser this one shares, does the opposite. Its first
code generator (its commit 5, 84cfcaf) keeps one value in `%rax` and puts
every other on the machine's stack in memory:

<!-- verify: skip reason="chibicc's code at its commit 84cfcaf (x86-64), not this project's" -->
```
        gen_expr(node->rhs);
        push();
        gen_expr(node->lhs);
        pop("%rdi");
```

That costs a store and a load in memory for every operator, at any depth, and
it never runs out. Registers cost nothing to reach, but there are few of them:
this lesson stops at six waiting values, and lesson 02.06 has to find another
place for the seventh.

Two more compilers sit between. tcc (its mob branch, at commit e9e9e7f6)
keeps a stack too, but of descriptions of values: each entry
says whether the value is a constant, in a register, or in memory in the
function's frame. A constant can stay a constant, so `1 + 2 * 3` is worked out
by tcc itself and no instruction is written for it. When no register is free,
tcc saves the value at the bottom of its stack to memory, "free the first one
on the stack", as its source puts it, so the oldest value waits in memory and
the newest stay in registers. gcc at `-O0` keeps every variable in memory in
the frame and loads it each time it is used. This program has three:

<!-- verify: session -->
```
$ printf 'int main(void) { int a = 1, b = 2, c = 3; return a + b * c; }\n' > vars.c
$ riscv64-elf-gcc -O0 -march=rv64im -mabi=lp64 -S -o - vars.c | sed -n '/^main:/,/jr/p'
main:
	addi	sp,sp,-32
	sd	ra,24(sp)
	sd	s0,16(sp)
	addi	s0,sp,32
	li	a5,1
	sw	a5,-20(s0)
	li	a5,2
	sw	a5,-24(s0)
	li	a5,3
	sw	a5,-28(s0)
	lw	a5,-24(s0)
	mv	a4,a5
	lw	a5,-28(s0)
	mulw	a5,a4,a5
	sext.w	a5,a5
	lw	a4,-20(s0)
	addw	a5,a4,a5
	sext.w	a5,a5
	mv	a0,a5
	ld	ra,24(sp)
	ld	s0,16(sp)
	addi	sp,sp,32
	jr	ra
```

Every value goes to the frame (`sw`) and comes back (`lw`) through `a5` and
`a4`. Written as `return 1 + 2 * 3;`, the same function gets `li a5,7`: gcc
works out constants even at `-O0`. (On Linux the tools may be called
`riscv64-unknown-elf-gcc` and the like.)

Registers as a stack is the cheapest scheme that keeps values out of memory.
It pays with a limit to watch and, from module 04, with saving the waiting
registers around every call, since a call does not keep them. How deep do the
expressions you compile really go, and is one memory access per operator a
fair price for never having to count?

## Break it

Leave the result where `gen_expr` put it. In `build/at/cc/02.03/codegen.c`, in
`codegen`, delete the line

<!-- verify: patch file=codegen.c
-  println("  mv a0, %s", reg[0]);
-->
```
  println("  mv a0, %s", reg[0]);
```

and build again:

<!-- verify: session -->
```
$ make -s
$ ./ccrun try.c; echo $?
0
$ ./same try.c
ours: status 0
gcc: status 5
differ
```

The program still computes 5, in `t0`, and returns. What comes back is
whatever `a0` held when `main` began, which on this machine is 0. Every
instruction of the expression is right; only the agreement about where a
result goes is broken, and `same` is what notices. Put the line back.
