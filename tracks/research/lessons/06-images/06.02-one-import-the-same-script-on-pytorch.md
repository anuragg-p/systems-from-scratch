# 06.02 One import: the same script on PyTorch

Every script so far names its engine in one line. This lesson changes
that line to `import torch`, runs the same experiment on PyTorch, and
measures that the two libraries take the same training step to the last
digits a float64 can hold. Then it sets the rules every later script
keeps: where a run computes, how it is timed, how it is seeded, and
where its networks live.

## Where this fits

![Where 06.02 fits](figures/06.02-map.svg)

This lesson's piece is in the lab: devices, the setting that says where
a PyTorch run computes, the CPU or a GPU, and a clock that times the run
there. Under the experiments, PyTorch takes the engine's place from here
on, with the same names; the engine stays as it is, complete, the thing
the track checked PyTorch against and that the scripts of modules 00 to
06.01 still run on. The models row gets its first piece, a small
convolutional network built by one function on either library. After
this lesson every new script of the track that trains a network runs on
PyTorch, on the CPU unless it is asked to use a GPU.

It is one missing layer of many. Module 07 needs embeddings, module 08
attention, module 09 the published weights of GPT-2 in a model that
computes what the reference does, module 11 arithmetic in half
precision. Each would be another engine lesson, spent on writing a layer
again instead of on what the layer is for. And the engine is numpy, which
computes on the CPU only, where PyTorch can also use a GPU, an NVIDIA
one (cuda) or the one in an Apple laptop (mps).

The reason is not speed on this laptop's CPU. Run it below times a
training step of this lesson's network on both, and PyTorch is about
twice as fast. The engine's convolution is one numpy matrix product,
which numpy hands to the laptop's own linear algebra library (Apple's
Accelerate), and PyTorch's build for this laptop lacks oneDNN, the
library it uses elsewhere for fast convolutions on the CPU
(`torch.backends.mkldnn.is_available()` is False here). A Linux machine
with an Intel or AMD processor may tell another story, not measured
here. On this laptop's GPU a step of the same network took 7.1 ms,
against 75.7 ms on its CPU in the same run.

The same table as 06.01's on the engine, within the spread of its seeds:
0.945 against 0.949 for the convolutional network on digits as they are,
0.412 against 0.427 at 4 pixels, 0.829 against 0.821 shuffled; the moved

Within the spread of seeds is a loose test. The experiment of this lesson
is the tight one: build the same network with each library, give
PyTorch's the engine's starting weights, feed both the same batch, and
compare everything one training step computes.

### `convnet`

The network both libraries build, for CIFAR-10's colour images of 32 by
32: three 3 by 3 convolutions of width, twice and four times width
filters, each with a relu and 2 by 2 max pooling, then a Linear layer to
10 scores. It takes the library as its first argument, as module 04's
shared code took the engine, so one function builds it from the engine's
`nn` or from PyTorch's, with the same parameter names and shapes.

### `copy_weights`

PyTorch's network made to compute what the engine's computes: the
engine's `state_dict()` gives every weight by name, each one's numbers
become a PyTorch tensor, and `load_state_dict()` puts them in place. The
names match because one function built both.

### `step`

One training step with either library: the cross-entropy of the
network's scores, `zero_grad()`, `backward()` and the optimiser's step.
The same five lines run on both, since they use only names the two
share.

### `device`

The `torch.device` a run's `device` setting names: "cpu", "cuda" or "mps"
as they are, and "auto" as an NVIDIA GPU when PyTorch sees one, else an
Apple one, else the CPU.

### `clock`

The time in seconds once the device has finished what it was asked, for
timing a run where it computes.

**In float64, the same step.** The loss differs by 1.3e-16 and every
gradient and every weight after the step by at most 4.7e-17, relative
to its size. A float64 holds about 16 significant digits: the gap
between 1 and the next float64 is 2.2e-16, and every difference here is
smaller than that. The two libraries did the same arithmetic, and the
only difference left is the order in which each added up its sums,
which moves the last binary digit.

**In float32, the same at first, and then not quite.** Training runs in
float32, which holds about 7 digits. The losses agree to every digit
printed for four steps, then part in the seventh decimal place, and by step 10
they differ by 1.8e-05. Rounding in another order, once, makes each
weight a little different, and every later step starts from those
weights, so the difference grows with the steps. (The loss does not fall:
the labels are random, which is all a check of the arithmetic needs.)

**Twice as fast, here.** The timing lines differ from run to run and
from machine to machine. On this laptop they say about twice, which is
not why the track switches; a GPU is, and what the next modules need.

## How it works

### Where a run computes, and why the default is the CPU

```
    dev = lab.device(torch, cfg.device)
```

Every script from here on that runs on PyTorch has a `device` setting
and starts with this line. Its default is "cpu", so the numbers and
times on these pages are CPU numbers, which any laptop can check, and
replaying a page gives the same digits. `device=auto` asks for a GPU
when there is one; a script then moves its model there with `.to(dev)` and its data with one copy,
06.03 shows how. A GPU adds its sums up in yet another order, so its
last digits differ from the CPU's: on this laptop `switch device=auto`
adds a column for the Apple GPU, whose losses part from the engine's at
step 8, in the seventh decimal place, and its step took 7.1 ms. Never compare a
GPU's digits with a page's. PyTorch's own notes say the same: "results
may not be reproducible between CPU and GPU executions, even when using
identical seeds."

### Timing a GPU

![A GPU works through a queue while Python goes on: a clock read without waiting times the asking, lab.clock waits for the device first](figures/06.02-clock.svg)

```
    if dev.type == "cuda":
        torch.cuda.synchronize()
    elif dev.type == "mps":
        torch.mps.synchronize()
    return time.perf_counter()
```

On a GPU, an operation's line in Python returns as soon as the work is
queued, and the GPU works through the queue on its own while Python goes
on to the next line. A clock read straight after a training step would
measure how long it took to ask, not how long the work took. `clock()`
waits for the device to finish everything it was given, then reads the
time; on the CPU there is nothing to wait for. Times are printed, never
written into a run's log or summary, so two runs with the same seed
still write the same bytes.

### Seeds, library by library

The same seed gives the same starting weights in one library, and other
ones in the other, since each library has its own generator. In the
project's folder:

<!-- verify: session needs="torch" -->
```
$ cd build/at/research/06.02
$ python3 -c "
import engine, torch
from models.convnet import convnet
for lib in (torch, torch, engine):
    lib.manual_seed(0)
    print(lib.__name__, [round(v, 4) for v in convnet(lib, 8)[0].weight[0, 0, 0].tolist()])
"
torch [-0.0014, 0.1032, -0.1584]
torch [-0.0014, 0.1032, -0.1584]
engine [0.0527, -0.0886, -0.1767]
$ cd ../../../..
```

That is why `switch` seeds both and then copies the engine's weights into
PyTorch's network, and why 06.01's table on PyTorch matched within the
spread of seeds and not digit for digit. The rule from here on is the one modules 00 to 05 kept,
with PyTorch's generator for the weights: everything about the data, its
order and its augmentation comes from the run's numpy generator;
`torch.manual_seed(run.seed)` comes just before the model is built and
decides its starting weights. Then the same seed on the same machine and
device gives the same digits, byte for byte in the run's log and
summary.

### One file per network

The networks experiments share live in `models/`, one file per family.
`convnet()` is the only one that takes the library as an argument,
because it is the one network built on both; 06.04's residual network,
and every later model, imports torch and is an `nn.Module` of PyTorch. A
model file holds the network only: training stays in the experiments.

## Decide the boundary

The track stops growing its engine at convolution and moves to PyTorch,
keeping the engine as the thing PyTorch was checked against. Another
course keeps going: a batch norm for maps, embeddings, attention, a GPU
back end, until its engine runs a GPT, and every layer is one its reader
wrote. That costs a lesson per layer and gains understanding of each
one; this track spends those lessons on the papers instead, and leans on
02.02's checks having taught what a layer's backward is. Which layers
are worth writing yourself once, and which only need to be understood?

## Go deeper

- [Making Deep Learning Go Brrrr From First Principles](https://horace.io/brrr_intro.html) by Horace He - where the time of a training step goes: compute, moving memory, and "overhead", everything else, Python included; and why PyTorch can "run ahead" of a GPU, queueing work while the GPU computes, which is what `clock()` waits out.
- [CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html) in PyTorch's documentation - "Asynchronous execution": "By default, GPU operations are asynchronous", and "time measurements without synchronizations are not accurate".
- [Reproducibility](https://docs.pytorch.org/docs/stable/notes/randomness.html) in PyTorch's documentation - what a seed does and does not promise: `torch.manual_seed()` seeds every device's generator, and results may differ across releases, platforms, and between the CPU and a GPU.
