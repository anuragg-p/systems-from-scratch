# 00.02 The same run twice: seeds, configs and logs

A result is worth something only if someone can get it again: the same
settings and the same seed, the same digits. This lesson gives the
experiment a runner, the first piece of the lab. It takes the settings from
the command line, makes every random number of a run follow from one seed,
and keeps a folder for each run with its settings, its log and its result.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

This is the first box of the lab, at the bottom of the map: runs. Every
experiment of the track starts its runs through it, and the later pieces
of the lab are made from what it records, the spread over seeds and the
curves of the next lesson first. Below it there is only numpy's random number
generator. After this lesson an experiment can be changed from the command
line without editing its file, and each run leaves a folder behind that
says exactly what was run and what came out, byte for byte the same when
it is run again.

## The idea

![One run: CONFIG and the command line make the settings, the run gets a folder and a generator seeded with 0, and writes config.json, log.jsonl and summary.json (their real contents for curve lr=0.1 steps=300)](figures/00.02-run.svg)

The experiment of 00.01 keeps its settings in a dictionary at the top of
its file, and that is the only place they can be changed. Ask it for a
smaller learning rate on the command line and it answers without a word,
with the result of the old one:

<!-- verify: session -->
```
$ ./learn run research --at 00.01 -- curve lr=0.1 | tail -1
train loss 0.0104  test loss 0.0496
```

Those are the numbers of lr 0.5: the script never reads its command line.
So every new setting means editing the file, and every result is a few
lines on a screen that scroll away. A week later there is no telling which
settings gave 0.0496.

Three ideas fix that.

The **settings** of an experiment, its **config**, are every number it can
be run with, each with a name. The defaults stay in `CONFIG` at the top of
the file, and `key=value` on the command line changes one for a run. A
name the experiment does not have is an error, never ignored.

The **seed** decides the randomness. A computer's random numbers are not
random: a **random number generator** works out each number from its state,
which starts from one number, the seed. The same seed gives the same
numbers in the same order, every time. If every random number in a run,
here all 520 points, comes from one generator made from the run's seed,
then the settings and the seed together decide the whole run.

A **run** is one execution with one seed, and it gets a folder of its own,
`runs/curve/seed0/` for the curve with seed 0. Three files go in it:
`config.json`, every setting the run used, the defaults too, and its seed;
`log.jsonl`, one line for each logged step, written as the run goes; and
`summary.json`, the numbers it ended with. The first says what was run,
the second how it went, the third what came out. The figure shows them for
`curve lr=0.1 steps=300`.

### `config()`

Starts from the experiment's defaults and reads `key=value` pairs from the
command line. A value is read as a Python literal, so `lr=0.1` is a number
and `lrs=[0.1, 0.5]` a list; anything else is text. A key the defaults do
not have stops the script with exit status 2 and a line that lists the
settings there are. It adds two settings of its own: `out`, the folder runs
go under (`runs` unless given), and `name`, the experiment's name, from its
file name.

### `Run`

One run. Making one makes its folder, writes `config.json` there, opens
`log.jsonl`, and makes the run's generator, `run.rng`, from its seed.
`log()` writes one line of the log and keeps it in `run.rows`; `finish()`
writes `summary.json`.

### `one_run()` and `main()`

The curve fit of 00.01, moved onto the runner: `one_run()` draws its points
from `run.rng`, logs the training loss every 100 steps, and finishes with
both losses. `main()` reads the settings, runs it with the seed they give,
and prints what 00.01 printed and where the run's files are.

## How it works

### One generator, one order

The run's generator is made once, from the seed, when the run starts:

```
        self.rng = np.random.default_rng(seed)
```

and `one_run()` draws every point from it, the training points first and
then the test points:

```
    x, y = make_data(cfg.n_train, cfg.noise, run.rng)
    xt, yt = make_data(cfg.n_test, cfg.noise, run.rng)
```

That is the **invariant** the runner depends on: every random number a run
uses comes from `run.rng`, and the run draws them in the same order every
time. Nothing else in the run is random, so nothing else can make two runs
differ. A random number taken from anywhere else, such as numpy's global
generator or the clock, would break it without a sign, and two runs would
no longer write the same bytes.

### Every digit, written at once

`log()` turns each value into a plain Python float and writes the line
straight away:

```
        self._log.write(json.dumps(values) + "\n")
        self._log.flush()
```

Python writes a float as the shortest text that reads back as exactly the
same float, so nothing is rounded on the way to the file: the log reads
back as the very numbers the run had, and two logs can be compared byte for
byte, as `cmp` did. The flush sends each line to the file as soon as it is
written, so a run that crashes or is stopped half way keeps its log up to
that step, which is often the part worth reading.

### A setting that is not there is an error

00.01 ignored `lr=0.1` because nothing read it. A runner that read only
the settings it knew and skipped the rest would ignore `lrr=0.1` the same
way, and report the default run as the one asked for. `config()` refuses
instead, before anything has run:

```
        if not eq or key not in cfg:
```

It also turns a whole number given for a setting whose default is a float
into a float, so `lr=1` and `lr=1.0` are the same run and write the same
`config.json`.

## Decide the boundary

This runner gives a run one generator and draws everything from it in one
order. That keeps the story short: the seed is the whole of the
randomness. But it ties the draws together. The test points are drawn
after the training points, so a run with `n_train=40` is scored on other
test points than one with `n_train=20`, and comparing the two mixes the
change you made with a change of test set; 00.01's Break it met exactly
that. Another runner could give each use its own generator, one for the
training points and one for the test points, each made from the run's
seed, so that changing one leaves the other's numbers alone. It would pay
with more generators to keep apart, and one more way to get the record
wrong. Later lessons take that step once: a network's starting weights come
from a second generator, the engine's own. Which numbers in your experiment
should stay fixed when you change another setting?

## Break it

Take the seed away. In `lab/run.py`, where `Run` makes its generator,
change `default_rng(seed)` to `default_rng()`. With no seed, numpy seeds
the generator from the operating system's own source of randomness,
different every time. Run the default experiment twice:

<!-- verify: patch file=lab/run.py old="default_rng(seed)" new="default_rng()" -->
<!-- verify: session
vary 0.0339 num
vary 0.0481 num
vary 0.0313 num
vary 0.0532 num
-->
```
$ python3 -m experiments.curve | tail -2
train loss 0.0339  test loss 0.0481
run in runs/curve/seed0
$ python3 -m experiments.curve | tail -2
train loss 0.0313  test loss 0.0532
run in runs/curve/seed0
$ grep '"seed"' runs/curve/seed0/config.json
 "seed": 0,
```

Two runs of the same code with the same settings, two results, and on your
machine two others again. The run's folder still says seed 0, and seed 0
gave 0.0496: the record now describes a run that never happened, and
neither number can be got back by anyone. Nothing crashed and nothing
warned. How far a number like these moves by chance alone is the next
lesson. Put `default_rng(seed)` back.

## Go deeper

- [NumPy, Random sampling](https://numpy.org/doc/stable/reference/random/index.html) -
  "Quick start" makes a generator with `default_rng`. The page says these
  generators "are deterministic sequences and can be reproduced by
  specifying a seed integer", and that with no seed `default_rng` seeds
  itself from the operating system, as in Break it.
- [A Recipe for Training Neural Networks](https://karpathy.github.io/2019/04/25/recipe/)
  by Andrej Karpathy - "fix random seed", the first item of its step 2, for
  the reason this lesson gives: run the code twice, get the same outcome.
- [An Opinionated Guide to ML Research](http://joschu.net/blog/opinionated-guide-ml-research.html)
  by John Schulman - "Keep a Notebook, and Review It": a record of every
  day's experiments and results, kept by hand; the runner's folders are the
  part of that record a program can keep for you.
- [Python tutorial, 15. Floating-Point Arithmetic: Issues and Limitations](https://docs.python.org/3/tutorial/floatingpoint.html) -
  why `eval(repr(x)) == x`, and why Python can print the shortest text that
  keeps it true: what lets the log hold every digit.
