# 11.06 One more optimisation, measured

The last change of the module is one chosen the way every change here
should be: from a profile. Training has had four; this one is for
writing text. 08.05's `generate()` runs the whole window through the
model for every token it writes and keeps one position's scores: with
SmolLM2-135M, 94% to 99.9% of the positions it computes are thrown away.
Every earlier position's keys and values are the same as at the step
before, so they can be kept, a **cache of keys and values**, and each
step can read the new token alone. This lesson builds the cache into the
GPT and checks that it writes the same tokens with it and without, on
the small GPT, GPT-2 small and SmolLM2. On this CPU it writes 2.8 times
as fast at 32 tokens and 6.3 times at 256, the gain growing with the
length; and with 10.04's grouped heads it holds a third as much as
SmolLM2 would with a key and value head for every query head. Then the
module's recorded benchmark, every row of the module on one table, and
two more changes for the reader to measure.

## Where this fits

![Where 11.06 fits](figures/11.06-map.svg)

This lesson's piece is fast, in the models row: the GPT reading new
symbols after the keys and values it kept, chosen by an argument of
08.05's `generate()` whose default writes as before. It changes module
08's attention and positions, which must place a new symbol after the
kept ones, and module 10's rotary turning and grouped heads, whose
fewer key and value heads are what the cache keeps. It is checked
against 08.05's writing token for token, on 09.03's GPT-2 and 10.04's
SmolLM2 too. After this lesson the GPT writes in time that grows with
the length written, not with its square, and module 11 is done: its
table says what each change bought on this laptop.

## The idea

### The profile of writing

A step of 08.05's writing is `model(ids[:, -model.context:])[:, -1]`:
the whole window through every block, and the last position's scores
kept. Timed with SmolLM2-135M, one row, greedy, the smallest of 3 at
load 7.3 in the track's notes: 23.9 ms a step for a window of 16
tokens, 61.1 for 64, 103.0 for 256, 353.0 for 1024. Of the positions
each step computes, all but the last are thrown away: 93.8% at 16,
99.9% at 1024. The profile of writing is the whole forward pass, again
and again, for one new token.

### What a step can keep

The key and the value of a position depend only on the symbols up to
it: the causal mask (08.01) never lets a later one in. So when one
symbol is added, every earlier position's keys and values, in every
block, are what they were. Keep them, a cache for each block, and the
next step runs the model on the new symbol alone: its query, key and
value are made, its key and value join the cache, and its query reads
every key kept. A step then costs one position's work through the
blocks, and reading the cache.

![Writing without a cache and with one: every step without reads the whole window again and keeps one position's scores; with a cache each step reads the new symbol only, after the keys and values kept; and what SmolLM2 keeps](figures/11.06-waste.svg)

Three things in the GPT have to know where the new symbol is. Rotary
positions (10.02) turn its query and key for its own place, after the
kept ones, not for place 0. Learned positions (08.03) add the vector of
its place. And the mask is no longer square: one new query at place n
sees n + 1 keys. PyTorch's `is_causal` puts its triangle at the top
left, which is right only when there are as many queries as keys
(11.03), so a cached step gets the triangle moved to the right.

### Grouped heads keep less

The cache holds the keys and values as they are made, turned for their
places and before 10.04 repeats them for the query heads of each group:
`kv_heads` heads of them, not `heads`. 10.04's promise, kept: the page's
small GPT, 2 key and value heads for 4 query heads, keeps half as much;
SmolLM2, 3 for 9, keeps 11,520 numbers a token, 2 x 3 heads x 64 x 30
blocks, 45 KiB in float32, where 9 heads would keep 34,560. A full
window of 8,192 tokens is 360 MiB, against 1,080 MiB.

### Past the window

The cache holds the model's window. Past it the window moves on, the
first symbol leaves, and every kept key of the deeper blocks would
change, since each depends on symbols that have left. So the cache
starts again from the last window's symbols once the window is full:
the same tokens as without a cache, and no gain past the window.

### What the run does

1. The profile of writing: a step of SmolLM2-135M without a cache,
   against the window's length.
2. The same symbols: `generate()` with the cache against without, the
   same seed, greedy, plain sampling, top-k and the nucleus, on a small
   GPT trained here (rotary positions, 2 key and value heads for 4) for
   100 characters, past its window of 64, and on SmolLM2-135M; the small
   GPT's scores in float64, cached against the whole window, at every
   length.
3. Greedy writing with SmolLM2-135M, 32 to 256 tokens, without and with
   the cache: seconds, tokens a second and the last step's time.
4. What the cache holds, a token and a full window.

### `Cache`

One block's keys and values, kept while text is written: room for the
model's window, filled from the front, the new positions' keys and
values added after the kept ones.

### `cached_scores`

The scores of the symbol after the ones given, reading only what the
caches have not seen; on the first call, or past the window, the caches
start again from the window's symbols.

### `written`

Greedy writing with each step timed, with the cache or without: the
symbols and the seconds after each step.

### Two more to try

This module's rule is the same numbers, sooner, measured before and
after with the load beside every time. Two more changes passed through
its measurements without being taken, and either is a lesson the reader
can make:

- **`torch.compile(model)`**, which turns the forward and backward
  passes into fused kernels, what 11.02's profile points at after
  attention: the element-wise passes over memory. In a trial outside
  the page (one training step, the smallest of 9 timings, at load 3.5 to
  7), 1.12 to 1.40 times faster alone and 1.30 to 1.71 with the rest,
  at three sizes of the GPT. Not taken: on the CPU it compiles C++ and
  needs a C++ compiler on the machine (Xcode's clang was there); its
  first step took 10 to 20 seconds; its numbers differ from the model's
  in the last bits, so the check that the numbers are the same needs a
  tolerance where this module's checks have none; and with rotary's
  angles kept it compiled again for every new place and gave up at its
  limit of 8 (set `Rotary.keep = False` first).
- **AdamW's `fused=True`**, PyTorch's one kernel for the optimiser's
  step: 1.10 to 1.55 times a training step on this CPU in the same
  trial, 1.05 to 1.22 on the Apple GPU; `foreach=True` gave nothing.
  More than 11.02's 6% for the optimiser suggests, so the first thing to
  measure is why; and whether it gives the same weights to the last bit
  was not checked.

The same trial found PyTorch's own 10 threads never the fastest with
other work on the machine: 4 threads were 1.43 and 1.27 times faster
at the two smaller sizes at load 5 to 7. That is the machine's state,
not the model's, and nothing in the track sets a thread count; to try
it, set `OMP_NUM_THREADS` before a run and print the load beside it.

## How it works

### Placed after the kept ones

```
            start = len(cache) if cache is not None else 0
            q, k = self.rotary(q, start), self.rotary(k, start)
```

In `SelfAttention.qkv()`, the new positions' place is the number of
positions the cache holds, and rotary turns their queries and keys for
it. `GPT.embed()` does the same for learned positions, adding the rows
from that place on. Without a cache both start at 0, as before.

### The mask, moved to the right

```
    return torch.ones(T, keys, dtype=torch.bool, device=device).tril(keys - T)
```

T new queries after `keys - T` kept positions: query i is at place
`keys - T + i` and may look at every key up to its own place, so the
lower triangle is moved right by `keys - T`. With as many queries as
keys it is 08.01's square mask. `fused_attend` passes this mask to
PyTorch when the queries are fewer than the keys, and none when there
is one query, which may look at every key.

### Kept before the repeat

```
        if cache is not None:
            k, v = cache.add(k, v)
```

The keys and values join the cache after rotary has turned them and
before 10.04's `repeat_interleave` copies each to the query heads of its
group: the cache holds `kv_heads` heads, and the repeat is made again,
cheaply, at every step.

## Decide the boundary

The cache trades memory for time: SmolLM2's full window is 360 MiB of
keys and values for one row, and a batch of rows multiplies it. Here it
starts again at the window's end, which keeps the tokens the same as
without it and gives up the gain past the window; a model trained with
rotary positions could instead keep writing past its window, as 10.02
showed it can read past it, and get worse, as 10.02 also showed. Grouped
heads cut the memory at a cost in quality 10.04 could not see at its
size. If you were serving many readers at once from this laptop, which
would you spend first: rows, window, or heads?

## Break it

Turn every new token as if it were at place 0. In
`build/at/research/11.06/models/gpt.py`, in `SelfAttention.qkv()`:

same, which is why every way of choosing is checked, not one. The step
is still as fast: a cache that writes the wrong text is still faster
than one that writes the right one. Put the place back.
