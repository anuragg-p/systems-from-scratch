# 10.04 Grouped-query attention, and loading a current open model

Every head of 08.02's attention has its own keys and values. When a model
writes, each new token's queries read the keys and values of every token
before it, and a model that keeps them so as not to make them again keeps
one set for every head. Ainslie et al. (2023) let a group of query heads
share one key head and one value head: fewer numbers to keep and to read.
This lesson adds that to the GPT and measures it: half the key and value
heads cost nothing the seeds can see. Then it loads a model released in
2025 that has every change of this module, SmolLM2-135M, into the
learner's own GPT. Its 134.5 million weights give the reference's logits
to the last bit, its tokenizer, GPT-2's kind with every digit cut out
alone, gives the reference's ids, and on Shakespeare's test text it scores
1.405 bits per character, against GPT-2's 1.851: on a text it may have
seen.

## The idea

### What every head's own keys cost

08.05's `generate()` writes one token at a time by running the whole
window through the model again for each new token. Most of that work was
done the step before: the keys and values of every earlier token are the
same as they were. A model that keeps them, a **cache of keys and
values**, does not make them again, and module 11 builds one. What it
keeps is 2 numbers (a key and a value) for each head's each number, for
every block, for every token so far: 2 x 4 heads x 16 x 4 blocks = 512 a
token for 08.04's GPT, and for a model of 9 heads of 64 in 30 blocks,
34,560 a token. Writing the next token means reading all of it.

### Groups of query heads

Ainslie, Lee-Thorp, de Jong, Zemlyanskiy, Lebron and Sanghai, "GQA:
Training Generalized Multi-Query Transformer Models from Multi-Head
Checkpoints" (2023), section 2.2: "Grouped-query attention divides query
heads into G groups, each of which shares a single key head and value
head." With one group, every query head shares one key head and one value
head, **multi-query attention**, an earlier proposal; with as many groups
as heads, it is 08.02's attention again. In between, the cache shrinks by
the number of query heads in a group. Their reason, from section 1:
"Autoregressive decoder inference is a severe bottleneck for Transformer
models due to the memory bandwidth overhead from loading decoder weights
and all attention keys and values at every decoding step."

Their claim, from the abstract: "uptrained GQA achieves quality close to
multi-head attention with comparable speed to MQA". **Uptrained**: they
took T5 models trained with every head its own, averaged the key and
value heads of each group into one, and trained on for 5% of the original
compute. Their table 1: the largest T5 with every head its own averages
47.2 over their tasks, at 1.51 seconds a sample; with 8 groups, 47.1, at
0.28 seconds. Here the heads are grouped from the first step: the
paper's uptraining is not run.

![Query heads sharing key and value heads: 08.02's attention, every head its own; the page's run, 2 key and value heads for 4 query heads; SmolLM2-135M, 3 for 9; and the numbers a cache of keys and values would keep for each token](figures/10.04-groups.svg)

In the GPT it is one argument, `kv_heads`. The key and value layers
make `kv_heads` heads' worth of numbers instead of `heads`, so they have
fewer weights, and once the queries, keys and values are cut into heads,
each key and value head is repeated for the query heads of its group.
Everything after that, 08.01's scores and sums, is unchanged.

### The download

`data/fetch.py` gains SmolLM2-135M, from the HuggingFaceTB/SmolLM2-135M
repository on Hugging Face at one fixed commit, under the Apache-2.0
licence its model card gives: four files, 271,169,470 bytes in all, each
kept only if its size and SHA-256 are the pinned ones. `config.json`,
`tokenizer.json` (its tokenizer, whole), `tokenizer_config.json` (read only
by the reference, below) and `model.safetensors`, 269 MB of weights. About
half a minute here: `python3 -m data.fetch smollm2`.

### Its file, and bfloat16

The file is the safetensors format 02.05 reads, with 272 tensors, every
one of type BF16. **bfloat16** is a 16-bit number made by keeping the top
half of a float32: its sign, all 8 bits of its exponent, and the first 7
of its 23 bits of fraction. So it covers the same range as a float32 with
two or three significant digits, half the memory, and numpy has no such
type. Widening one is
exact: put its 16 bits in the top half of 32 and read them as a float32.

Its names are Hugging Face's Llama's, `model.layers.0.self_attn.q_proj.weight`
and so on, and every weight is kept as `nn.Linear` keeps it, (outputs,
inputs). Loading is renaming: nothing is cut in three and nothing is
transposed, where GPT-2's file needed both (09.03). There is no output
layer in the file: it is the embedding, tied.

![SmolLM2-135M's file beside the GPT that holds it, for block i of 30: every tensor goes in as it is, only renamed; in the accent the shapes 08's GPT never had (keys and values of 3 heads, the gate)](figures/10.04-names.svg)

### Its tokenizer

SmolLM2 keeps its tokenizer in one file, `tokenizer.json`: the symbols,
the merges in order, the special symbols, and the steps that cut a text
into pieces. Read there, it is 09.02's kind of tokenizer: bytes written
as GPT-2's printable characters, GPT-2's pattern, merges applied in the
order learned. Three things differ.

- **Digits.** Before GPT-2's pattern, every character Unicode counts as a
  number is cut out as a piece of its own: " 2019" is " ", "2", "0", "1",
  "9" where GPT-2 has one piece. A year, a sum, a line of code's numbers:
  always one token a digit.
- **Special symbols first.** 49,152 symbols, of which the first 17 are
  special: `<|endoftext|>` is 0, then `<|im_start|>` and `<|im_end|>`,
  which mark the turns of a chat, and 14 for code. Then the bytes, and
  then 48,900 merges, the k-th making symbol 252 + k.
- **Missing bytes.** 235 of the 256 bytes have a symbol; 21 never occurred
  in the text it was learned on: control characters, bytes that never
  occur in UTF-8 at all, and the first bytes of the characters from
  U+40000 to U+BFFFF.
  A character that needs one of them loses that byte, as the reference
  does too, and no longer decodes to itself.

![SmolLM2's tokenizer beside GPT-2's on two pieces of text: the same pattern cuts both, but SmolLM2 cuts every digit out first; each piece in a box, its ids under it](figures/10.04-tokens.svg)

## How it works

### Each key and value head, repeated for its group

```
            k, v = (t.repeat_interleave(self.heads // self.kv_heads, dim=1) for t in (k, v))
```

After the heads are cut, `k` and `v` are (batch, kv_heads, T, d) and `q`
is (batch, heads, T, d). `repeat_interleave` on the head dimension makes
key heads [k0, k1, k2] into [k0, k0, k0, k1, k1, k1, k2, k2, k2] for 9
query heads: query head h reads key head h // 3. That is the order
SmolLM2's weights were trained with; transformers' Llama code says of its
`repeat_kv` that it is "the equivalent of torch.repeat_interleave". The
repeat makes copies, so in this GPT the saving is in the weights of the
key and value layers, not yet in the work.

### Fewer key and value numbers, the same view

```
        q, k, v = (t.view(B, T, -1, width // self.heads).transpose(1, 2) for t in (q, k, v))
```

08.02 cut each of q, k and v into `self.heads` heads. Now the key and
value layers make `kv_heads` heads' worth, so the view takes the number
of heads from each tensor's own size (`-1`) and the size of a head from
the queries' (`width // self.heads`): 64 numbers a head for SmolLM2, 9
query heads, 3 key and value heads.

### Widening, exactly

```
    return (bits.astype(np.uint32) << 16).view(np.float32)
```

A float32 is a sign bit, 8 bits of exponent and 23 of fraction; a
bfloat16 is the first 16 of those 32. Moved up by 16 places with zeros
below, its bits are a float32's bits, the same number exactly. `view`
reads them as float32 without converting anything.

### Digits first

```
    for part in re.split(f"([{gpt2.classes()['N']}])", text):
```

`gpt2.classes()['N']` is 09.02's list of every Unicode number character,
in a form `re` reads. Splitting on one of them in brackets keeps it as a
piece of its own, and each run of text between is cut by GPT-2's pattern
as before. "Number" here is Unicode's, not 0 to 9: the reference's
pre-tokenizer cuts every character whose category is a number, and so
does this.

## Decide the boundary

Grouping trades the size of the cache against how many different keys
each query can look for: 9 query heads on 3 key heads is three questions
asked of each set of keys. The paper's tables, and this page's, say the
quality hardly moves at the sizes tried; the cache shrinks by the size
of a group. One group for all, multi-query attention, shrinks it most;
`kv=[4,2,1]` runs it, and this page does not measure it. Where would you
stop, and what would you measure to decide: the bits, or the time to
write a thousand tokens with a cache?

## Break it

Repeat the key and value heads in the other order: tiled, [k0, k1, k2,
k0, k1, k2, ...], instead of each one three times in a row. In
`build/at/research/10.04/models/gpt.py`, in `SelfAttention.qkv()`:

and 2 did, and it learned to use whichever it was given. SmolLM2 is
ruined: 5.975 bits per character, about as bad as guessing among 65
characters with equal chances (6.022, the bottom of module 07's ladder),
and its likeliest next tokens after "To be, or not to be," are pieces of
accented letters and broken bytes. Every shape fits, every name is right, the
file loads; 6 of its 9 query heads in every block read the keys and
values that were trained for another group. The order of a repeat, like
09.03's transposed square weight, is a fact about how the weights were
trained, to be read from the reference's code and checked against its
logits. Put `repeat_interleave` back.
