# 04.06 Five bugs that do not crash: a debugging checklist

The worst bugs in a training script raise no error: the script runs to
the end, prints a loss and an accuracy, and the numbers are wrong. This
lesson plants five such bugs in a working MNIST script and builds a
checklist of five measurements, each with a right answer known in
advance, so that every bug is caught by one of them.

## Where this fits

![Where 04.06 fits](figures/04.06-map.svg)

The checklist is a new part of the lab, under every run, next to the
settings, seeds and plots: it judges numbers a script measures (a loss,
gradients, an accuracy, predictions), so it works for any network and
either engine. Above it, this lesson's experiment is a script with
batch norm and Adam, the pieces of modules 03 and 04, in six versions:
right, and wrong five ways. After this lesson a run can be checked
before its result is believed.

## The idea

![Each version of the script against each of the five checks, three seeds: the correct script fires none, each bug fires exactly one, and no two bugs fire the same one](figures/04.06-checks.svg)

04.01 found a network that learned nothing by looking inside it. The
bugs here are subtler: the network learns something in all of them, the
loss goes down, the script reports a number. Each check is a measurement
whose right answer can be worked out before running anything:

| the bug | what goes wrong | the check that catches it | its right answer |
|---|---|---|---|
| pixels 0-255 | the inputs are 255 times bigger than the weights were sized for (04.02) | 1. starting loss | log(10) = 2.303: a network that knows nothing gives each of 10 classes 1/10 |
| softmax twice | `cross_entropy()` takes a softmax of its own, so the scores go through two | 2. one batch | below 0.05: a network can learn 64 digits by heart |
| no zero_grad | every step adds its gradient to the last step's, which nothing cleared | 3. fresh gradients | the same: two backward passes on one batch with the same weights |
| labels shuffled | the images were put in a new order and their labels were not | 4. beats chance | at least 0.5 on held-out digits, where guessing gives 0.1 |
| eval in train mode | held-out digits are scored with batch norm still using each batch's own statistics | 5. same answers | 0 changes: scored in another order, every prediction the same |

How each right answer comes about is the point of the check.

**Check 1.** Before training, the scores for the ten classes are small
and near each other, so the softmax gives each about 1/10, and the
cross-entropy is -log(1/10) = log(10). A starting loss far from it means
the scores are not small: the inputs, or the start, are the wrong size.

<!-- verify: fact cmd='python3 -B -c "from experiments.bugs import network; print(sum(p.data.size for p in network(128).parameters()))"' expect=118794 -->

**Check 2.** The network has 118794 weights, and 64 examples are few
enough to learn exactly, so 300 steps on one small batch alone must
drive its loss to nearly 0. If they cannot, something between the scores
and the loss is broken. Under the second bug, the scores reach
`cross_entropy()` as softmax probabilities, between 0 and 1, and the best
of those, 1 for the right class and 0 for the rest, still gives the right
class only e / (e + 9) after the second softmax.

<!-- verify: fact cmd='python3 -B -c "import engine as torch; F = torch.nn.functional; s = torch.tensor([[100.0] + [0.0] * 9]); print(round(F.cross_entropy(F.softmax(s, 1), torch.tensor([0])).item(), 3))"' expect=1.461 -->

So the loss cannot go below log(e + 9) - 1 = 1.461, which is what the
engine gives for a softmax of the scores 100, 0, ..., 0 taken twice.

**Check 3.** `backward()` adds to whatever `.grad` already holds (it
must: a weight used in two places gets the sum of both gradients), so a
script has to clear it before every step. With the same weights and the
same batch, two passes must give the same gradient; if the second is
twice the first, nothing cleared it.

**Check 4.** A network that learned from images with the wrong labels
learned nothing that holds on new digits: its accuracy there is chance.
Held-out digits, kept apart from training, are what shows it.

**Check 5.** In eval mode batch norm uses its running averages, so a
digit's answer cannot depend on its batchmates. Score the held-out digits
shuffled, then sorted by label, and compare.

### `starting_loss`

Check 1: is the loss within a quarter of log(classes)?

### `learns_one_batch`

Check 2: did the loss of the last step on one batch end below 0.05?

### `gradients_fresh`

Check 3: are two lists of gradients equal, to rounding? It reports the
ratio of their sizes, which says what went wrong when they are not.

### `beats_chance`

Check 4: held-out accuracy of at least 0.5.

### `same_answers`

Check 5: how many predictions differ between two orders of scoring.

### `gradients`

The training step's gradient, with one of two bugs or neither: it skips
`zero_grad()` under one, and puts the scores through a softmax under the
other.

### `predict`

The predicted class of every digit, in chunks of 1000 in the order
given, in eval mode and without a graph; under the last bug, without
`model.eval()`.

The correct script passes all five checks on all three seeds. Each bug
fires exactly its own check, on every seed, and no other: the table
above, measured. What each check saw, from the lines under the table:

- pixels 0-255: a starting loss of 12.826 where 2.303 was due.
- softmax twice: one batch, 300 steps, and the loss stops at 1.462, on
  the floor of 1.461 worked out above.
- no zero_grad: the second backward's gradient is 2.00 times the first's.
- labels shuffled: held-out accuracy 0.108, against 0.100 by guessing.
- eval in train mode: 2376 of 5000 predictions change with the order.

None of the five buggy scripts crashes, and each prints numbers that
look like a result. The checklist is what tells them apart.

## How it works

**Each check judges a measurement, not the script.** The functions in
`lab/checks.py` take plain numbers and arrays (a loss, a list of losses,
gradients, an accuracy, two arrays of predictions) and return whether it
passed and a sentence saying what they saw. The experiment does the
measuring, so the same checks work on any network, on this engine or on
PyTorch.

**Why each check catches one bug and not the others.** The checks look at
different stages of a run. Only the scale of the inputs moves the loss
before any training. Only the loss function stops a single batch from
being learned: the other bugs learn it, the shuffled labels included,
since 64 wrong labels can be memorised as well as 64 right ones. Only a
missing `zero_grad()` makes the gradient depend on the step before.
Only wrong labels leave nothing that holds on new digits. Only scoring
in train mode makes an answer depend on its batchmates. A bug of another
kind can slip through all five; the checklist is a floor, not a proof.

**The order in check 5 is chosen to be unkind.** Shuffled batches have
digits of every kind, close to the training batches; chunks of 1000
sorted by label hold two or three kinds of digit, whose mean is far from
the running average. If train mode is going to change an answer, sorting
makes it show: 2376 of 5000.

of `predict()`. In `build/at/research/04.06/experiments/bugs.py`, delete
them:
