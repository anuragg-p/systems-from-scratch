# 09.01 Bytes, UTF-8 and byte pair encoding

Every model so far read Shakespeare a character at a time, from an
alphabet of 65. GPT-2 does not, and this lesson shows why. Characters
make a window short: 08.04's 256 characters hold about 48 words. Whole
words leave out every word the training text never had, 15.9% of the
test text's different words. Sennrich, Haddow and Birch (2016) took a
middle way from data compression, byte pair encoding: start from the 256
values of a byte, and make the pair of neighbours that comes up most often
a new symbol, again and again. Any text in any script is bytes, so nothing
is unknown, and a frequent word ends as one symbol. The lesson writes the
trainer twice, the obvious way and a way fast enough for a real
vocabulary, and trains 08.04's GPT on its tokens: in the same steps, 2.691
bits per character against 3.332 on characters.

## Where this fits

![Where 09.01 fits](figures/09.01-map.svg)

This lesson's piece is new, in the data row: tokens, the numbers a
language model reads, made from text. Until now a text and its numbers
were one table of 65 characters (07.01). From here they are two steps:
text to bytes, which UTF-8 fixes for every character there is, and bytes
to tokens, which a trainer learns from a text. Above the tokens, module
08's GPT reads them, and 07.03's way of scoring a whole text gives its
bits per character, so a model on tokens and one on characters can be
put side by side. After this lesson the track turns any text into tokens
and back, and the next lesson reads GPT-2's own vocabulary into the same
code.

## The idea

### Two obvious vocabularies

A language model gives a chance to every symbol of its vocabulary, at
every position. The track's models so far used characters: 65 symbols
for Tiny Shakespeare. Nothing is ever unknown, but a symbol says little,
and a window of a fixed number of symbols holds little text. 08.04's
GPT reads windows of 256 characters, and the run counts what one holds:
47.7 words on average, over 2000 windows of the test text.

The other obvious choice is a symbol for each word. The run counts that
too, a word being a run of letters: the training text has 187,779 words,
12,558 different ones. A model with one symbol for each of them cannot
write a word that is not among them, and the test text, the end of The
Taming of the Shrew and then The Tempest, is full of them.

381 of its 2,396 different words never occur in the training text: 15.9%

### Bytes, and UTF-8

A computer keeps text as bytes, numbers from 0 to 255. Unicode gives
every character there is a number, its **code point**, written U+ and
four or more hex digits: the letter e is U+0065, an e with an acute
accent U+00E9, the Chinese character for "you" U+4F60, a waving hand
U+1F44B. **UTF-8** is the usual way to write code points as bytes, one
to four of them (RFC 3629): a code point up to U+007F is one byte, itself,
so plain English text is the same in UTF-8 as in ASCII; a larger one is
cut into groups of bits, and the first byte says how many bytes follow.

![Four characters as UTF-8: each code point's bits cut into the pattern for its size; the first byte says how many bytes the character takes, and every byte after it starts 10](figures/09.01-utf8.svg)

U+00E9 is the bytes c3 a9; U+4F60 is e4 bd a0. In Python,
`"\xe9".encode("utf-8")` is `b'\xc3\xa9'`. So any text, in any script,
is a sequence of the 256 values of a byte. A model whose symbols include
all 256 can be given any text and can write any text; on its own, though,
a byte says even less than a character, and a Chinese character is three
of them.

### Byte pair encoding

Sennrich, Haddow and Birch (2016) wanted a translation model "capable of
open-vocabulary translation by encoding rare and unknown words as
sequences of subword units". They took byte pair encoding, in their
section 3.2 "a simple data compression technique" (Gage, 1994), and ran it
on words. It starts from single symbols, counts every pair of neighbours
in the training text, makes the commonest pair a new symbol, replaces
it everywhere, and counts again. Each **merge** adds one symbol: "The
final symbol vocabulary size is equal to the size of the initial
vocabulary, plus the number of merge operations." A common word is merged
all the way to one symbol; a rare word stays a few pieces that are
common; and only a symbol of the first vocabulary could be unknown. Their
first symbols are characters, with a mark at the end of each word; here
they are the 256 bytes, as GPT-2's are, and no byte can be unknown.

![One word the training text has and one it never had, as the trainer's merges come: each frame is a merge that changes one of them, numbered in the order learned, 1,792 in all](figures/09.01-merge.svg)

Step through it. The trainer learns its merges from the whole training
text, in the order of how often each pair occurs at that point: h + e is
merge 2, and " heavens", which the training plays have 35 times, becomes
one symbol at merge 1,790. " Prospero" never occurs in them; the same
merges, as far as they apply, leave it 5 pieces the training text does
have.

Two rules of this trainer's own. A pair is never counted across
**pieces**: the text is first cut into words, each with the space before
it, runs of other marks, and runs of spaces, and a symbol never holds the
end of one word and the start of the next. The paper does the same, "For
efficiency, we do not consider pairs that cross word boundaries". And
when two pairs are counted equally often, the merge is the smaller pair,
first symbol then second. The paper's own code, its Algorithm 1, takes the
first pair in the order counted, which depends on the order the text was
read in; with this rule the merges do not.

### The obvious trainer, and the paper's

The obvious trainer does exactly what the description says: for every
merge, count every pair of every piece of the text, then merge the winner
in every piece. The training text is a million bytes in 264,485 pieces,
and every merge counts them all again. The paper's section 3.2 says what
to do instead: "The algorithm can thus be run on the dictionary extracted
from a text, with each word being weighted by its frequency", and "In
practice, we increase efficiency by indexing all pairs, and updating data
structures incrementally". The training text has only 14,134 different
pieces; the fast trainer counts each once, times how often it occurs, and
keeps, for every pair, the pieces that hold it, so that a merge touches
only those. The run times the obvious one for 3 merges and checks that the
fast one's first 3 are the same.

### Encoding new text

Training gives a list of merges in the order learned. To **encode** a new
text, cut it into pieces, write each piece as its bytes, and then, of the
pairs of neighbours that are merges, merge the one learned first,
wherever it occurs; again, until no pair left is a merge. To **decode**,
put each symbol's bytes one after another and read them as UTF-8.

### What the run does

1. Counts the two obvious vocabularies on Tiny Shakespeare, as above.
2. Trains byte pair encoding on the training text, both ways, to a
   vocabulary of 2,048 symbols: 256 bytes and 1,792 merges.
3. Bytes per token, a text's bytes over its tokens, at vocabularies of
   256, 512, 1,024 and 2,048, on the training text and on the test text.
4. Round trips: the test text, and eight strings the training text never
   had (accents, Greek, Russian, Chinese, Hindi, an emoji with a skin tone
   and a flag, a combining accent, a tab, a NUL and a DEL), encoded and
   decoded back.
5. 08.04's GPT, 4 blocks of 4 heads, width 64, windows of 64 symbols, 300
   steps of 32 windows, two seeds, on characters and on tokens of the
   vocabulary of 2,048; both scored in bits per character of the test text.

### `pieces`

The text cut into its pieces, by one regular expression: a word with the
space before it, a run of other marks with the space before it, or a run
of spaces and line breaks. Every character is in exactly one.

### `pairs`

How often each pair of neighbours occurs in a list of symbols.

### `merge`

A list of symbols with every occurrence of one pair, read left to right,
replaced by a new symbol.

### `train_simple`

The obvious trainer: every piece as its bytes, then for each merge every
pair of every piece counted again.

### `train`

The same merges, each different piece counted once with how often it
occurs, the counts kept up to date: a merge takes the old pairs of the
pieces it changes out of the counts and puts their new ones in.

### `encode`

Each piece's bytes, then the merge learned first, again and again.

### `vocab`

The bytes each symbol stands for: a byte for each of the first 256, and
for each merge the bytes of its two symbols one after the other.

### `decode`

The symbols' bytes, read as UTF-8.

### `unseen`

Of the words of one text, the share of different words and of running
words that never occur in another.

### `per_character`

A model's bits per token made bits per character, so that models with
different symbols are scored on one scale.

## How it works

### A symbol never spans two words

```
SPLIT = re.compile(r" ?\w+| ?[^\w\s]+|\s+")
```

`\w` is a letter or digit of any script, or `_`; `\s` any kind of space.
The three alternatives are a word with one space before it, a run of
other marks with one space before it, and a run of spaces and line
breaks, and every character is one of the three, so the pieces of a text,
put back together, are the text. A space joins the word after it, so "
the" is one piece and becomes one symbol, while "the" at the start of a
line is another. Merging only inside pieces is what lets the fast trainer
count each different piece once: a pair that crossed from one word into
the next would belong to no piece.

### Ties, settled the same way every time

```
        best = max(counts, key=lambda p: (counts[p], -p[0], -p[1]))
```

The most frequent pair; of pairs counted equally often, the one with the
smaller first symbol, then the smaller second. The obvious trainer counts
the pieces as the text has them, the fast one in the order of its
dictionary of different pieces, and Python's plain `max` would return
whichever tied pair it met first. With the rule, both make the same list,
whatever order they read in. In the project's folder, the two trainers
on the first 20,000 characters, and a text where every pair ties:

### Learned first, merged first

```
            pair = min(zip(ids, ids[1:]), key=lambda p: merges.get(p, float("inf")))
```

Training applied its merges one after another to every piece, so in a
piece it trained on, merge 2 happened before merge 38. Encoding a piece
does the same: of the pairs present that are merges, the earliest
learned, then the earliest of what is left, and so on. That replays what
training did to every training piece, and gives a new piece the merges
it can take, in the same order. In the project's folder, with the merges
of the run's vocabulary of 2,048:

" heavens" is one symbol, 2045, the merge learned 1,790th. " Prospero"

### A cut character

```
    return b"".join(table[i] for i in ids).decode("utf-8", errors="replace")
```

A list of symbols that `encode()` made always holds whole characters. A
list made any other way, by a model writing one token at a time, can stop
in the middle of one: the last line above decodes "caf" and the byte c3
alone, half of U+00E9. `errors="replace"` writes U+FFFD, the replacement
character, for a byte that is no character's, instead of stopping the
program; the line after it, with a9 too, decodes whole.

### Bits per character, from bits per token

```
    return bits_per_token * len(scored) / sum(len(table[int(i)]) for i in scored)
```

07.03's `window_bits()` gives the mean bits of every token scored. Times
the number of tokens, that is the bits of the whole stretch of text; over
the characters those tokens stand for, it is bits per character. Tiny
Shakespeare is plain ASCII, where a character is a byte, so the bytes of
`table` count characters. With characters for tokens, each one byte, it
changes nothing, and the two models of part 5 are scored by the same
measure.

## Decide the boundary

This lesson stops at 2,048 symbols; GPT-2 has 50,257. A bigger
vocabulary makes texts fewer tokens, so a window holds more text and a
step reads more of it. It costs a row of the embedding table and of the
output layer for every symbol, and each symbol is seen less often in
training, so a model learns less about each; and the figure above shows
the later merges fitting the training text more than the test text. How
many symbols does a given amount of training text pay for?

The test text still comes back whole: it is ASCII, where a character's
code point is its byte, so nothing changed for it. That is how a
tokenizer of code points passes every check written in English. The
accented words do not come back: U+00EF is 239, and 239 alone is a byte
UTF-8 never uses for a whole character, so it decodes to U+FFFD. The
Greek kappa is U+03BA, 954, and 954 here is not a letter at all but the
symbol of merge 699, some other bytes of Shakespeare; the word decodes to
the wrong text without a complaint. The Chinese character U+4F60, 20320,
is no symbol of a vocabulary of 2,048, and decoding it stops the run. A
code point can be as large as 1,114,111, and above 255 its number is
already some merge's. Bytes are the only symbols every text can be
written in that leave the numbers from 256 free. Put the line back.
