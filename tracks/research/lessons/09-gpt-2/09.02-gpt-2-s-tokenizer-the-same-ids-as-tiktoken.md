# 09.02 GPT-2's tokenizer: the same ids as tiktoken

09.01's byte pair encoding learned its own merges from Shakespeare. To
run GPT-2 the project must turn text into exactly the numbers GPT-2 was
trained on: OpenAI's 50,000 merges, read from OpenAI's own files, and
the text cut into pieces the way GPT-2 cuts it. The merges need no new
code at all: the files are 09.01's form. The cutting does: GPT-2's
pattern names every letter and every number of Unicode, which Python's
`re` cannot say, so the lesson builds those classes from the standard
library's own tables. Checked against tiktoken, OpenAI's tokenizer, the
ids are the same on everything tried, with one exception that depends on
your Python: a character newer than its Unicode tables, followed by a
contraction.

## Where this fits

![Where 09.02 fits](figures/09.02-map.svg)

This lesson's piece is the tokens again, now GPT-2's: the same merge
loop as 09.01, with OpenAI's vocabulary and merges in place of ones
learned here, and GPT-2's way of cutting text into pieces. Below it is
the fetch of 03.01 and 06.03, which gains GPT-2's three files; above it,
the next lesson gives these ids to GPT-2's own weights, which must see
the numbers they were trained on or they mean nothing. After this lesson
the project encodes any text as GPT-2 does and decodes GPT-2's output
back to text.

## The idea

### OpenAI's two files

GPT-2's tokenizer is two files of text. `vocab.json` maps each of 50,257
symbols to its id. `merges.txt` lists 50,000 merges, one pair a line, in
the order they were learned on OpenAI's WebText. They are 09.01's form
exactly: 256 symbols for the bytes, then the k-th merge makes the
symbol 256 + k, and one more symbol, 50256, `<|endoftext|>`, which GPT-2
saw between one document and the next. So 09.01's `encode()` loop runs
on them unchanged: a piece's bytes, then the merge learned first, again
and again.

Two things are new. The files are text, and a byte that is not a
printable character, a space, a line break, a control byte, cannot be
written in them as itself: OpenAI's code writes every byte as a
printable character, the 188 printable ones as themselves and the other
68 as the characters from U+0100 on. A space is U+0120 in the files, a
line break U+010A. And the 256 byte symbols are not numbered by their
bytes: "!" is id 0. The tokenizer keeps a table, `first`, from a byte to
its symbol's id.

![GPT-2's 256 byte symbols: the 188 bytes that are printable characters stand for themselves; the other 68, in the accent, are written as the characters U+0100 to U+0143, in byte order](figures/09.02-bytes.svg)

### The pieces

Radford et al. (2019), section 2.2, say why GPT-2 does not run byte pair
encoding on raw text: "We observed BPE including many versions of common
words like dog since they occur in many variations such as dog. dog!
dog? ... To avoid this, we prevent BPE from merging across character
categories for any byte sequence. We add an exception for spaces which
significantly improves the compression efficiency". Their code does it
with one regular expression, in OpenAI's `src/encoder.py`:

<!-- verify: skip reason="OpenAI's pattern as their encoder.py has it, written for the regex module; the project's version follows" -->
```
's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
```

Tried in order, at each place in the text: a contraction ('s 't 're 've
'm 'll 'd); a run of letters with one space before it or none; a run of
numbers, the same; a run of anything else that is not a space, the
same; a run of spaces that stops before the last one when a word
follows, so the word keeps its space; any run of spaces. Merges then
happen only inside a piece, so " dog", "." and "!" are separate pieces,
and " dog" needs one symbol, not one for each mark after it.

![GPT-2's pattern cutting the run's sentence into pieces, by kind, and each piece into its ids; below, 09.01's pattern on the same sentence, its pieces that GPT-2 does not make in the accent](figures/09.02-pieces.svg)

### Letters and numbers, from the standard library

`\p{L}` is every letter of every script Unicode has, `\p{N}` every
number. That is the `regex` module's syntax, which OpenAI's code
imports; Python's own `re` has no such class, and the project imports
nothing beyond numpy and PyTorch. But Python's `unicodedata` knows the
**general category** of every code point, two letters whose first says
what it is: L for a letter (Lu upper case, Ll lower case, Lo other
letters, ...), N for a number, Z for a space, C for a control or a code
point no character has yet (Cn, unassigned). So the classes can be built:
every code point whose category starts with L, written as runs of
neighbours, `\U00000041-\U0000005a` and on. This Python's tables are
Unicode 15.0.0: 136,104 letters in 1,181 runs, 1,831 numbers in 268. The
pattern is then GPT-2's, character for character, in `re`.

One more class needs care. GPT-2's `\s` is the regex module's, Unicode's
25 White_Space characters; `re`'s `\s` is `str.isspace()`, which has four
more, the separators 0x1c to 0x1f. The project writes the 25 out.

Radford et al. give the reason for bytes in the same section: Unicode
code points "would result in a base vocabulary of over 130,000 before
any multi-symbol tokens are added", where "a byte-level version of BPE
only requires a base vocabulary of size 256". The letters alone are
136,104.

### The download

`data/fetch.py` gains GPT-2: its vocabulary, its merges and, for the
next lesson, its weights, 549,603,790 bytes in all, from the
openai-community/gpt2 repository on Hugging Face at one fixed commit.
`vocab.json` and `merges.txt` are byte for byte OpenAI's own files
(their SHA-256s are the ones tiktoken pins for OpenAI's encoder.json and
vocab.bpe). The model card gives the licence as MIT; OpenAI's own
repository has a "Modified MIT License", which asks that GPT-2 be used
responsibly and that what it writes be marked as GPT-2's. The project
does not ship them: one command fetches the three files into the cache
outside it, each checked against the size and SHA-256 written in
`data/fetch.py`. A dropped connection carries on from where it stopped
with an HTTP Range request, file by file (`fetch_each()`).

### What the run does

1. What the files hold, and the printable characters bytes are written as.
2. GPT-2's pieces of one sentence, against 09.01's pattern.
3. A few texts encoded: their ids and each id's bytes; then all of Tiny
   Shakespeare, decoded back.
4. Bytes per token on Tiny Shakespeare: GPT-2's 50,257 symbols, learned
   on web pages, against 09.01's 4,096, learned on its training text.
5. The speed of encoding, with and without a cache of pieces seen.

### `byte_symbols`

The character each of the 256 bytes is written as in GPT-2's files.

### `classes`

Unicode's letters and numbers, as the inside of an `re` character class,
from `unicodedata`; made once.

### `pattern`

GPT-2's pattern for `re`: the classes for `\p{L}` and `\p{N}`, the 25
spaces for `\s`.

### `split`

The pieces of a text, as GPT-2 cuts it.

### `Tokenizer`

GPT-2's tokenizer from the two files: each symbol's bytes, each byte's
symbol, and the merges as 09.01 keeps them, `{(id, id): new id}`, checked
to be in the files' order. `encode()` is 09.01's loop with a cache of
pieces already merged; `decode()` is 09.01's.

### `load`

The tokenizer from the files the fetch keeps, or the script stopped with
the fetch command.

**The files are 09.01's form.** 50,257 symbols and 50,000 merges, the
k-th making 256 + k, which `Tokenizer` checks as it reads them. The first
merges are a space and t, a space and a, h and e; the seventh joins ' t'
and 'he' into ' the'. Web text, not Shakespeare, but the same start as
09.01's. The longest symbol is 128 bytes: c3 83 c3 82 over and over, the
UTF-8 of U+00C3 and U+00C2, the trace of web pages decoded with the wrong
table again and again, often enough on WebText to be merged into one
symbol.

**GPT-2's pieces.** The two patterns agree on most of the sentence. They
differ where Radford et al. meant them to: "It's" is ' It' and "'s",
where 09.01's `\w` stops at the apostrophe and leaves "'" and 's'; before
' Yes', two spaces become ' ' and ' Yes', the second space left to the
word; '\n\n   NAME' becomes '\n\n  ' and ' NAME'. A word that starts
after spaces looks like a word that starts after one space, and gets
the same symbols.

**Encoding.** "Hello world" is 15496 and 995. " SolidGoldMagikarp" is
one symbol, 43453, though it is no word: it was common in OpenAI's text.
Digits are merged as any symbols are, so "1234567890" is '123' '45' '678'
'90', learned groups, not one digit at a time. The contractions are lower
case only, so "IT'S" is 'IT' "'" 'S'. The two Chinese characters, U+4F60
and U+597D, are six bytes and four tokens, two of which cut a character
between its bytes: tokens are bytes, not characters, and only the whole
list decodes to text. All of Tiny Shakespeare is 338,025 tokens and
decodes back to itself.

**Twelve times the symbols, a little shorter.** On the training text, a
token of GPT-2's is 3.324 bytes, against 3.291 for 09.01's 4,096 learned
on that very text: 1% more. On the test text, 3.099 against 2.916: 6%
more. GPT-2's merges were learned on 40 GB of web pages, 09.01's on a
million bytes of these plays; the plays' own words are 09.01's last
merges, and they help on the text they came from.

![Bytes per token on Tiny Shakespeare: GPT-2's 50,257 symbols, learned on web pages, against 09.01's 4,096, learned on the training text](figures/09.02-compress.svg)

**The cache.** Encoding all of Tiny Shakespeare merges 297,833 pieces,
but only 15,057 different ones; keeping each one's ids the first time
makes encoding three to four times faster.

### The same ids as tiktoken

tiktoken is OpenAI's tokenizer, written in Rust: "a fast BPE tokeniser
for use with OpenAI's models", in its README's words. It is not part of
the project, and nothing here needs it. Built from the same two fetched
files with GPT-2's pattern, it gives this project's ids on all of Tiny
Shakespeare, on runs of spaces and line breaks, contractions in every
case and in odd places, digits of several scripts, runs of marks,
combining accents, 18 scripts, emoji with skin tones, families and
flags, and every assigned character of every general category in eight
places of a string, and so do transformers' two GPT-2 tokenizers. With
tiktoken installed (`python3 -m pip install tiktoken`), in the project's
folder:

The last line is where the two part. U+1C89 is a Cyrillic capital
letter that Unicode added in version 16.0. This Python's `unicodedata` is
Unicode 15.0.0, where U+1C89 is not assigned: category Cn, not a letter.
So the pattern takes it as "anything else", and the apostrophe after it
too, and "'s" is no longer a contraction: the pieces are U+1C89 with
"'", then "s". tiktoken's tables are newer; to it U+1C89 is a letter, a
piece of its own, and "'s" is the contraction, one symbol, 338.

![Where the ids part from tiktoken's: U+1C89, a letter Unicode added in version 16.0, before 's. This Python's unicodedata does not know it, so the pattern cuts it with the apostrophe; tiktoken cuts it as a letter](figures/09.02-unicode.svg)

It is not only U+1C89. Of the 104,782 code points this Python leaves
unassigned in planes 0 to 3, 5,004 give other ids than tiktoken's when
"'s" follows them: exactly the letters and numbers Unicode 15.1 and 16.0
added. In every one, tiktoken's ids are this project's for the character
alone and then for "'s". In the seven other places tried (after an x, a
space or a digit, before an x or a digit, after an apostrophe, between a
space and "!") the pieces differ but the ids do not: no merge joins those
new bytes to their neighbours, so cutting them apart or not changes
nothing. So the
answer to the title is: the same ids as tiktoken, on everything tried,
except a character newer than your Python's Unicode tables followed by a
contraction. Which characters those are depends on your Python; to see
its Unicode version:

```

```

Unicode 16.0, as Python 3.14's are, should give tiktoken's ids on U+1C89
too; that was not run here, since the project runs on 3.12.

## How it works

### Printable stand-ins for every byte

```
    printable = [*range(ord("!"), ord("~") + 1), *range(0xA1, 0xAD), *range(0xAE, 0x100)]
```

These 188 bytes are printable characters read as Latin-1, ! to ~ and
0xa1 to 0xff without 0xad, the soft hyphen, which is invisible. Every
other byte is given a character from U+0100 on, in byte order, so the
table is fixed and the same on every machine. OpenAI's `bytes_to_unicode`
does the same and says why: it "avoids mapping to whitespace/control
characters the bpe code barfs on". `Tokenizer` reads the files through
this table, back to bytes, and from then on works in bytes and ids only,
as 09.01 does: the stand-ins never reach a model or a page.

### Leaving the last space for the word

```
    return re.compile(rf"'s|'t|'re|'ve|'m|'ll|'d| ?[{L}]+| ?[{N}]+| ?[^{S}{L}{N}]+|[{S}]+(?![^{S}])|[{S}]+")
```

`[{S}]+(?![^{S}])` is GPT-2's `\s+(?!\S)`: a run of spaces not followed
by anything that is not a space. Before "Yes", the run of two spaces is
followed by Y, so `re` gives back one space and tries again: one space,
followed by a space, matches. The second space is left, and ` ?[{L}]+`
takes " Yes". The last alternative, any run of spaces, catches the run
at the very end of a text, where nothing follows.

### A cache of pieces

```
            ids = self.cache.get(piece) if cache else None
```

A text repeats its pieces: " the" thousands of times. Merging a piece
is the slow part, a loop over its pairs for every merge, so the
tokenizer keeps every piece it has merged with its ids. OpenAI's encoder
keeps the same cache. It is exact: a piece always merges to the same
ids, wherever it occurs, because merges never cross pieces.

## Decide the boundary

This project takes its letters from the `unicodedata` of whatever Python
runs it, so the tables change when Python does, and with them the pieces
of the newest characters. tiktoken and the regex module carry tables of
their own, each its own version, and give the same pieces on every
machine until they are updated. Neither is GPT-2's: OpenAI's tokenizer of
2019 used the regex module of 2019, and to it every letter added since
was unassigned too. When a model was trained on one tokenizer's pieces,
which version of Unicode should the tokenizer that serves it use?

"Hello world" starts as its bytes, 72, 101, 108, ..., read as GPT-2's
ids. In GPT-2's vocabulary 72 is not H but the symbol of another byte,
so the merges, which are pairs of GPT-2's ids, almost never apply: Tiny
Shakespeare becomes 1,088,538 tokens, nearly one a byte. A few pairs of
wrong ids happen to be merges, and "1234567890" comes out as R, ST, U,
VW: every token is another symbol's, and the text decodes to other
letters. The merge loop and the decoder are right; only the first
lookup, from a byte to its symbol, is wrong, and nothing is ever
refused. This is the bug a round trip catches, since decoding uses the
same file's table and returns other text. A subtler error, one that
gave a real symbol the wrong id but kept the table consistent, would
round-trip and still feed GPT-2 numbers it never saw: that one only a
comparison with the reference catches. Put the line back.
