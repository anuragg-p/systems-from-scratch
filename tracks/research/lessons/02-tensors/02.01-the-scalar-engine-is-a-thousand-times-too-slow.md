# 02.01 The scalar engine is a thousand times too slow

The scalar engine of module 01 makes a Python object for every number at
every step, and spends its time on those objects, not on the arithmetic.
This lesson writes the engine again over numpy arrays: one object for a
whole array, numpy doing the arithmetic on all its numbers at once, and the
same backward rules as before. It uses PyTorch's names and gives PyTorch's
gradients.

## Where this fits

![Where 02.01 fits](figures/02.01-map.svg)

This lesson's piece is the tensors box of the engine row, next to the nudge
and the scalar values of module 01. A **tensor** is an array of numbers
that remembers how it was computed, so that the engine can give the
gradient of a result with respect to every number in it. From here on,
everything above the engine is arithmetic on tensors: the two groups again
in 02.03, the digits of module 03, the deep networks of module 04. Below
it is numpy, which does the arithmetic, and the nudge of 01.01, which
checks the gradients. After this lesson the engine can push a whole array
through arithmetic and back in one step per operation, under the names
PyTorch uses.

Sixteen seconds here, for a network of 105 weights, 3 seeds of 80 steps on
50 points: about 70 milliseconds a step. MNIST, in module 03, has 60,000
training images, 1200 times these 50 points, for a network several hundred
times this one. At this speed one pass over it would take most of a day.

The arithmetic is not what takes the time. Every number in the computation
is a Value: a Python object holding the number, its gradient, the Values it
came from and a function for backward. Each multiply makes a new one, with
its own function, and backward visits each one again. A multiply of two
floats takes the machine about a nanosecond; making and later visiting the
object around it takes about a thousand times longer.

So hold the numbers together. A tensor is one object over a whole numpy
array. One operation on tensors is one call into numpy, which runs a
compiled loop over every number, and one node in the graph. The figure
shows the difference on three pairs of numbers, through `(x * y + x).tanh()`:
the scalar engine makes 15 Values, five for each pair; the tensor engine
makes 5 tensors, and would make 5 for twenty thousand pairs.

The backward rules do not change. Take out = a * b, number by number, so
out[i] = a[i] * b[i]. By the chain rule of 01.02, the gradient of the result
with respect to a[j] adds up, over every output number out[i], the gradient
of out[i] times how much out[i] moves when a[j] does. But out[i] depends on
a[j] only when i is j, so every other term is zero, and what is left is
a.grad[j] = out.grad[j] * b[j]. For every j at once that is
`a.grad = out.grad * b`: the scalar rule, applied to whole arrays with one
numpy multiply.
The same holds for every **elementwise** operation, one whose output number
i depends only on number i of each input: `+`, `*`, `**`, `exp`, `log`,
`tanh` and `relu`. Each backward is the scalar engine's, written once for
the whole array.

Backward also needs a gradient to start from. For a single number it is 1,
as before. Here `out` holds many numbers, so the code passes a tensor of
ones, `out.backward(torch.ones_like(out))`: that is the gradient of the sum
of `out`, since moving any one out[i] moves the sum by the same amount. (A
tensor that sums itself comes in 02.03.)

### `Tensor`

The class holds the array in `.data`, whether it needs a gradient in
`.requires_grad`, and after backward the gradient in `.grad`, itself a
`Tensor`, as in PyTorch. `_prev` and `_backward` are the scalar engine's:
the inputs, and the function that passes the gradient back to them.
`_result` makes the tensor an operation returns, and records its inputs
only when one of them needs a gradient. `tensor()`, `zeros()`, `ones()`
and the rest make tensors the way PyTorch's functions of the same names do:
a list of Python floats becomes float32, PyTorch's default.

### `_accumulate`

Where every gradient arrives. It adds a share of gradient to `.grad`: the
first share makes it, each later one is added in place, since a tensor
used twice gets a share from each use.

### `backward`

The scalar engine's backward over tensors: the same depth-first walk to put
every tensor after the ones it was made from, then each one's `_backward`,
last first, starting from the gradient it is given.

### The operations: `__add__` to `relu`

Each computes its result with numpy and sets a `_backward` that applies its
rule to the whole array: add passes the gradient unchanged to both inputs,
multiply passes it times the other input, `tanh` times 1 - tanh squared,
`relu` only where the input was positive. Subtraction, negation and
division are made of these, as in the scalar engine.

### `with_tensors`

The speed test's tensor half. It is written with `torch.` names only, after
the script's one line `import engine as torch`, so the same function runs on
PyTorch when that line says `import torch`.

## How it works

### One number of gradient for each number of data

The engine keeps one rule everywhere, its **invariant**: a tensor's `.grad`
has exactly the tensor's shape. This lesson's engine keeps it the blunt
way. In `_accumulate`:

```
if g.shape != self.data.shape:
    raise ValueError(f"a gradient of shape {g.shape} for a tensor of shape {self.data.shape}: "
```

Every operation here is elementwise, and its gradient comes back in the
output's shape. That is the input's shape only when the two inputs had the
same shape. numpy will add a row of 4 to a table of 5 rows of 4 without
complaint, and the forward pass works, but the gradient for the row comes
back as a table: this engine refuses it. 02.02 is about what it should be.

### Used twice, a share from each use

In `(x * y + x).tanh()`, `x` is used twice, once in the multiply and once
in the add, and its gradient is the sum of the two shares. So
`_accumulate` adds:

```
self.grad.data += g
```

The first share makes `.grad` as a copy of `g`, and later shares are added
to it. The scalar engine's `self.grad += out.grad` did the same, one number
at a time.

### Only the leaves keep their gradients

At the end of `backward()`, every tensor in between (one an operation
made) has its `.grad` set back to `None`. A **leaf** is a tensor nobody
computed, made by `tensor()` or `zeros()`: the weights and the data. Only
the leaves' gradients are wanted, and the ones in between can be as big as
the activations of a whole network for a whole batch. PyTorch does the
same.

### Four bytes a number, eight to check

`torch.tensor([0.5])` holds float32, four bytes a number, as PyTorch's
does: enough for training, and half the memory and time of float64. To
check a gradient, use float64: the scalar engine's Python floats are
float64, so in float64 the two engines agree to 1.3e-15, where float32
would agree only to about seven digits. A numpy array keeps its own type,
which is why `with_tensors` says `dtype=torch.float64`.

## Decide the boundary

![The time of forward and backward through tanh(x * y + x), against how many numbers: the Values grow with every number, the tensor stays flat until numpy's loop starts to show](figures/02.01-overhead.svg)

This engine runs each operation as soon as Python reaches it, and pays a
fixed cost for every operation, whatever the size of the tensor: the
Python call, the new object, the numpy call. With ten numbers that cost is
most of the time, and the tensor is barely ahead:

The networks of modules 02 to 05 are a few hundred numbers wide and are

computation first and compile it into one loop, as PyTorch's
`torch.compile` and JAX do, and pay for the compile step and for code that
is harder to step through. Is your model made of a few big operations, or
of many small ones?

## Break it

Make the second share replace the first instead of adding to it. In
`engine/tensors.py`, in `_accumulate`, change `+=` to `=`:

<!-- verify: patch file=engine/tensors.py
-            self.grad.data += g
@block
-->
```
self.grad.data = g
```

<!-- verify: session
line 3 ~   scalar Values +\d+\.\d\d ms  \( +\d+ ns a number\)
line 4 ~   one tensor +\d+\.\d\d ms  \( +\d+ ns a number\)
vary 1432 int
-->
```
$ python3 -m experiments.speed
20000 numbers, forward and backward:
  scalar Values     167.30 ms  (   8365 ns a number)
  one tensor          0.12 ms  (      6 ns a number)
  the tensor is 1432 times faster
  largest difference between their gradients: 1.0e+00
```

Nothing crashes, and the tensor's gradients are now wrong by up to 1. `y`
is used once and is still right. `x` gets two shares, and only the last
one survives: the one from the multiply, the gradient times `y`. The one
from `+ x`, the gradient times 1, is lost, which is 1 - tanh squared, up to
1 where the tanh is near 0. The check against the scalar engine is what
caught it: the program ran and printed numbers either way. Put the `+=`
back.
