# 02.04 Cursors and range scans

A cursor is a position in a tree that can move to the next entry. With it the
engine reads a whole table, or every rowid between two numbers, in key
order, across as many leaves as it takes.

## Where this fits

![Where 02.04 fits](figures/02.04-map.svg)

The B-tree can now find one row. Most queries want many: every row of a
table, or every row whose rowid lies in a range, in order. The executor
(module 04's table scan, module 05's range scans) drives a cursor: put it on
the first entry, or on the first entry at or after a key, then ask for the
next one until it has enough. Below, the cursor only reads pages through the
pager. After this lesson the B-tree can walk a table of any size in key
order, from its first row or from any key, and an index too.

## The idea

Inside one leaf, the next row is simply the next cell pointer. The question
is what happens at the end of a leaf. The rows go on in another leaf, but
SQLite's pages have no "next leaf" link; a leaf knows nothing about its
neighbours.

The path that the descent of 02.03 leaves behind already holds the answer. It
lists, for every level, the page and the child taken. To get to the next
leaf, climb the path until a level where the child taken was not the last
one, step to the next child there, and go down its left edge to the leftmost
leaf. Here is a range that starts at the last row of one leaf and goes on into
the next:

![WHERE id BETWEEN 1499 AND 1502 in deep.db: the cursor reads 1499 at the end of leaf 283, climbs to page 518, steps from child 230 to 231, and goes down to leaf 563](figures/02.04-walk.svg)

The climb is cheap. Page 518 was read on the way down and is still in the
page cache, so moving on to the next leaf reads exactly one new page, the
leaf itself.

A cursor, then, is that path plus "which entry am I at". It has three
moves: the first entry (down the left edge from the root), the first entry at
or after a key (the descent of 02.03), and the next entry. After the first
two, and after every step, the same fix-up runs: if the position is past the
end of a leaf, climb until there is something to the right.

**Indexes are different.** In a table, an interior cell is only a signpost:
every row is in a leaf, so the cursor climbs straight past it. In an index,
an interior cell is a real entry, stored nowhere else. The reason is size.
A table's signpost is one rowid, a few bytes, so repeating it above the
leaves costs nothing; an index's key is a whole record, and copying it into
the page above would store every divider twice. SQLite stores each index
entry once, wherever the split left it. So on its way up, an index cursor
stops on the interior cell it climbs to, returns it, and only then goes down
into the next child.

![Index t_a of ix.db: the root holds 7 entries, the leaves the rest, and a cursor visits a leaf, then a root entry, then the next leaf](figures/02.04-index-order.svg)

## How it works

Both pieces of this lesson work on the path that `seek_raw` builds in 02.03:
`c->pgno[]` and `c->idx[]`, one entry per level from the root down. On every
level above the last, `idx` is the child that was taken; on the last level it
is the cell the cursor is at. Both pieces keep that true.

### Writing `settle`, step by step

`settle` turns any position into either "at an entry" or "no more entries".
A seek can land one past the end of a leaf (the key is larger than
everything in that leaf), and so does every step past a leaf's last cell, so
every cursor move ends here: `cursor_first`, `cursor_next`,
`cursor_seek_rowid` and `cursor_seek_key`. Built up in the order the cases
turn up:

1. **The easy case: a real cell.** If the leaf's `idx` is below its cell
   count, load the entry and return 1. Inside one leaf, that is all a scan
   needs:
   ```
   for (;;) {
       Node n = node_get(c->pager, c->pgno[c->depth - 1]);
       if (c->idx[c->depth - 1] < n_ncells(&n)) {
           cursor_load(c);
           return 1;
       }
       ...
   }
   ```
   The loop is for step 4, which goes round again to this test.
2. **Past the end of a leaf: climb.** Drop a level from the path and look at
   the parent's `idx`. If it is still below the parent's cell count there is
   a child further right at this level, so stop climbing; if not, climb
   again.
   ```
   c->depth--;
   Node up = node_get(c->pager, c->pgno[c->depth - 1]);
   if (c->idx[c->depth - 1] < n_ncells(&up))
       break;
   ```
3. **The end of the tree.** When the climb reaches the root with nothing to
   its right, the scan is over: mark the cursor not valid and return 0.
   Without this stop, the climb would go on to read level -1 of the path.
4. **A table: step to the next child and go down.** Move `idx` on by one, go
   down that child's left edge with `descend_leftmost`, and go round the loop
   again: the first cell of the new leaf is the next row, and step 1 finds
   it.
   ```
   c->idx[c->depth - 1]++;
   descend_leftmost(c);
   ```
5. **An index: the interior cell is the entry.** Before step 4, an index
   cursor stops: the cell it has climbed to is the next entry in key order, as
   the index-order figure shows, so load it and return.
   ```
   if (!c->intkey) {
       cursor_load(c);
       return 1;
   }
   ```
6. **Let `cursor_next` step off an interior cell.** When the cursor stands on
   an index's interior cell, the next entry is the first one in the child to
   its right. So `cursor_next` moves `idx` on and, if the page is not a leaf,
   goes down that child's left edge before calling `settle`; on a leaf it only
   moves `idx` on.

### Down to the leftmost leaf

`descend_leftmost` finds the first entry of a subtree, which is always at the
bottom of its left edge. `cursor_first` uses it from the root to start a full
scan, and the table case of `settle` and `cursor_next` use it to enter the
next child. It is short, and its
one decision is to extend the path the cursor already has rather than start a
new one: it takes the child at the last level's `idx` and pushes each page
below with index 0, until a leaf. That is what lets one function serve both
the start of a scan and the middle of one.

### One fix-up for every move

Handling "past the end of a leaf" once, in `settle`, rather than in each move
is the decision that keeps the cursor small. A seek that lands past the end
and a step that runs off a leaf are the same situation, and so is the start
of a scan on an empty table, whose only page is a leaf with no cells. The
single condition `if (!c->intkey)` is then the whole difference between
walking a B+tree and walking a B-tree.

## Break it

In `settle`, treat an index like a table: delete the `if (!c->intkey) { ... }`
block, so the cursor climbs past interior cells in both kinds of tree. Index
walks first run in 05.03's build, so make the change in

interior cells are data.

## Decide the boundary

This cursor finds the next leaf by climbing its path, because SQLite's leaves
carry no link to their neighbours. The climb reads nothing new: the range
above read five pages, and a link would not have saved any of them.

Many B+trees instead give every leaf a pointer to the next one, so a scan
moves sideways without climbing. The price is upkeep: every split and every
merge must keep the chain of links right, and here, where a split puts the
new page on the left, that would mean rewriting the left neighbour too. The links earn their keep when many threads share the tree: Lehman and
Yao's B-link tree uses them so that a reader that arrives at a page just
after it split can still follow the link to the keys that moved. Will your
tree be read by one connection with a warm cache, or scanned by many while
others split it?
