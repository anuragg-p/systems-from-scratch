# 02.05 Delete and free pages

Deleting a row removes its cell from a leaf. When that empties the leaf, the
page has to leave the tree, and it goes on the freelist, where the next
insert finds it before the file grows.

## Where this fits

![Where 02.05 fits](figures/02.05-map.svg)

So far the tree only grows. DELETE, and UPDATE when it changes a row's
rowid, run by the executor in module 04, put a cursor on an entry and ask the
B-tree to remove it. Taking out a cell is easy; the work is what happens when a page
ends up with nothing in it, and where that page goes. Free pages are recorded
in the file itself, through page 1's header, so that the pager reuses them
before it makes the file longer. After this lesson the B-tree can delete
rows and drop whole trees, reuse the space they held, and still leave a file
sqlite3 accepts.

## The idea

A tree that loses rows has two problems a growing tree never had. Pages run
empty, and the space they held should go to the next rows rather than sit
unused while the file grows at its end. Delete the last 2000 of 3000 rows from
a table as sqlite3 stores it, and 23 pages are left with no rows at all.

**Removing a cell.** A cell comes out of its leaf, its pointer leaves the
array, and the page is packed again. If the row had overflow pages, they are
freed first: nothing else points at them, so forgetting them would lose them
for good.

**An empty page must go.** A leaf with no cells cannot stay in the tree.
sqlite3 refuses such a file outright, and an empty page is wasted space
anyway. So when a delete empties a leaf, the leaf is merged into a sibling:
the sibling takes its place under the parent, the divider between the two
disappears, and the empty page is set free. If that leaves the parent empty,
the same happens one level up; a root left with a single child takes in that
child's cells, and the tree gets one level shorter.

![Deleting rowid 1147, the only row left in page 16: the parent loses the divider (15 | 1061), page 15 takes over up to 1147, and page 16 goes on the freelist](figures/02.05-merge.svg)

**Remembering free pages.** A freed page is still part of the file; it just
belongs to no tree. The file keeps a list of them, the **freelist**, made of
**trunk** pages: each holds the number of the next trunk, a count, and the
numbers of free pages. Two fields of page 1's header point at it: the first
trunk at offset 32, the number of free pages at offset 36. When a tree needs
a page, it takes one from the list, and only when the list is empty does the
file grow.

![The freelist of del.db: page 1's header points at trunk page 16, which lists the other 22 free pages; pages are taken back from the end of the list](figures/02.05-freelist.svg)

**An index entry in an interior page.** In an index, interior cells are
entries (02.04), and deleting one cannot just remove it: its left child hangs
off it. The fix is to take the entry just before it in key order, which is
always the last entry of the right-most leaf under its left child, copy it up
into the interior cell's place, and delete it from that leaf instead. The
interior page keeps a cell, and the actual removal happens in a leaf like
any other.

![Deleting the index entry (389, 91) from the root of t_a: its predecessor (388, 2004) moves up, then is deleted from leaf 16](figures/02.05-predecessor.svg)

## How it works

### Writing btree_delete, step by step

`src/btree.c:btree_delete` is called with a cursor standing on the entry to
remove; module 04's DELETE and UPDATE put it there. Removing one cell is
easy; the steps below are the cases that force more code.

1. **A leaf entry first, and leave the cursor unpositioned.** The cell at the
   end of the path goes, through `leaf_delete`:
   ```
   int L = c->depth - 1;
   Node n = node_get(p, c->pgno[L]);
   if (n_leaf(&n)) {
       leaf_delete(c);
   } else {
       ...
   }
   c->valid = 0;
   c->depth = 0;
   ```
   A delete may merge pages and change the tree's shape under the path, so
   the cursor is left not valid, with an empty path. Whoever deletes and
   wants to go on must seek again; module 04's DELETE does, collecting the
   rowids first and seeking each one.
2. **Free the overflow chain before the cell.** `leaf_delete` frees the
   chain, then removes the cell (`node_remove` packs the page again). Nothing
   else points at those pages: forget them and they are in no tree and not on
   the freelist, lost to the file for good.
   ```
   if (ci.ovfl)
       overflow_free(p, ci.ovfl, ci.npayload - ci.nlocal);
   node_remove(p, &n, c->idx[L]);
   ```
3. **An emptied leaf leaves the tree.** If the leaf now has no cells and is
   not the root, `fix_empty` merges it into a sibling, as in the merge
   figure. A root leaf may stay empty: that is simply an empty table.
   ```
   if (n_ncells(&n) == 0 && L > 0)
       fix_empty(c, L);
   ```
4. **An entry in an interior page**, which happens only in an index, cannot
   be removed the same way; it gets the predecessor swap of the next
   subsection, in the `else` branch.

### Writing the predecessor swap in `btree_delete`, step by step

This is the other branch of `btree_delete`, for an index entry that sits in
an interior cell. Its left child hangs off it, so the cell must stay and only
its key may change. In the order to write it:

1. **Find the predecessor.** From the entry's left child, follow right-most
   children down to a leaf. The last cell there is the largest entry smaller
   than the one being deleted, so it can take that entry's place without
   breaking the order on either side.
   ```
   u32 pg = ci.child;
   for (;;) {
       Node m = node_get(p, pg);
       if (n_leaf(&m)) {
           ...
           break;
       }
       pg = n_right(&m);
   }
   ```
2. **Copy its key out, and build the replacement cell** with `cell_build`:
   the old cell's left child and the predecessor's key. The key gets a
   buffer of its own because the pages it sits on are rewritten by the next
   steps. The child stays: it is the same subtree, now bounded by a slightly
   smaller key.
3. **Swap the cells.** Remove the old one, freeing its overflow chain first
   as in a leaf, and insert the replacement at the same index with
   `insert_cell`, after cutting the path back to this page's level. The
   predecessor's key can be longer than the key it replaces, so the page may
   have to split, and `insert_cell` knows how; it finds the parents on the
   path, which must end at this page.
   ```
   node_remove(p, &w, i);
   c->depth = L + 1;
   insert_cell(c, L, i, cell, size);
   ```
4. **Delete the copy in the leaf.** Seek the key over all its fields with bias
   -1. The two copies are equal, and that bias lands on the first of them in
   key order, which is the one in the leaf; `leaf_delete` removes it and
   merges the leaf if it empties.

### Writing fix_empty, step by step

`fix_empty` is the merge in the figure. `leaf_delete` calls it when a page
other than the root is left with no cells, at level L of the path; it hands
the page's place under the parent to a sibling and sets the page free.

1. **Merge into the left sibling.** Left first, because then the divider to
   remove sits just before the empty page's slot and that slot can simply
   be pointed at the sibling; only a first child has no left sibling. The
   parent's cell i - 1 is the divider between the sibling and the empty
   page. Take the sibling's cells, remove
   that divider, point the slot it leaves at the sibling, free the empty
   page and lay the sibling out again:
   ```
   if (i > 0) {
       target = n_child(&g, i - 1);
       Node s = node_get(p, target);
       cells_from_node(p, &cl, &s);
       ...
       node_remove(p, &g, i - 1);
       n_set_child(&g, i - 1, target);
       ...
   }
   page_free(p, n.pgno);
   ...
   node_fill(p, &t, type, &cl, 0, cl.n, cl.right);
   ```
   Removing cell i - 1 moves the empty page's pointer into slot i - 1, so
   once it points at the sibling, the sibling covers both ranges: in the
   figure, page 15 takes over up to 1147.
2. **Index and interior pages: pull the divider down.** In a table leaf the
   divider only repeated a rowid that is still in the sibling, so it can
   simply go. In an index it is an entry, and in an interior page it
   separates two children, so `add_divider` adds it to the sibling's cells
   (in an interior page, with the sibling's old right-most child as its
   child; into an index leaf, without the 4-byte child number, which leaf
   cells do not have, and padded to the 4-byte minimum of 02.01), and the
   merged page takes the empty page's right-most child.
   ```
   add_divider(p, &cl, type, n_cell(&g, i - 1), gtype, cl.right);
   cl.right = n_leaf(&n) ? 0 : n_right(&n);
   ```
3. **No left sibling: merge into the right one.** When the empty page is the
   parent's first child, its right sibling takes it over: the divider, cell
   0, then the sibling's own cells, and the parent loses cell 0.
4. **The sibling may overflow.** A divider pulled down can make it too big
   for one page. Then it splits again, which spreads the cells over two
   pages: a redistribution, with no code of its own.
   ```
   if (fits)
       node_fill(p, &t, type, &cl, 0, cl.n, cl.right);
   else
       split(c, L, &cl, -1);
   ```
5. **An emptied parent: the same, one level up.** Losing a divider can leave
   the parent with no cells. Then `fix_empty` runs again at L - 1, or, when
   the parent is the root, the root takes in its single child's cells
   (`collapse_root`), so the tree shrinks from the top just as it grew.
   ```
   if (L - 1 == 0)
       collapse_root(c);
   else
       fix_empty(c, L - 1);
   ```

### Writing page_free and freelist_pop, step by step

`page_free` is where every page goes when a tree lets go of it: a merged
leaf, an overflow page, every page of a table at DROP TABLE (`btree_drop`
walks the whole tree and frees each page, with `drop_page`). `freelist_pop`
is how `page_alloc` gets one back, whenever page 1 says the list is not
empty. They are mirror images; write them together.

1. **The simplest correct `page_free`: every freed page becomes a trunk.**
   Write the old first trunk's number and a count of 0 into the freed page,
   point offset 32 at it, and add one to offset 36:
   ```
   u8 *h = pager_write(p, 1);
   u32 trunk = get4(h + 32);
   ...
   u8 *d = pager_write(p, pgno);
   memset(d, 0, p->page_size);
   put4(d, trunk);
   put4(d + 4, 0);
   put4(h + 32, pgno);
   put4(h + 36, get4(h + 36) + 1);
   ```
   That alone is a valid freelist, a chain of empty trunks; it just spends a
   whole page on every entry.
2. **Fill the first trunk instead.** If it has room, append the freed page's
   number to its array. Room is `p->usable / 4 - 8` numbers, six fewer than
   fit: sqlite3 leaves a trunk's last six entries unused so that old versions
   can read the file, and this engine does the same. A full trunk falls back
   to step 1, and the freed page becomes the new first trunk.

   ![With 512-byte pages a trunk holds 120 numbers: trunk 29 is full, so page 152, freed next, became the first trunk and points at 29](figures/02.05-trunks.svg)
3. **`freelist_pop`, the mirror: take the last number** from the first trunk
   and lower its count. The most recently freed page goes out first, and
   nothing in the array moves.
   ```
   if (nleaf > 0) {
       pgno = get4(t + 8 + 4 * (nleaf - 1));
       put4(t + 4, nleaf - 1);
   }
   ```
4. **An empty trunk gives itself.** When the first trunk lists no pages, hand
   out the trunk page itself and make its next trunk the first.
5. **Keep offset 36 in step, and change pages only through `pager_write`.**
   `page_alloc` trusts the count: if it is above 0, it pops. Both functions
   change the count along with the list. Page 1 and the trunks are fetched with `pager_write`, so they
   are written at commit like any other changed page; a change made to a
   page fetched for reading would never reach the file.

### Only empty pages are merged

`btree_insert`, listed again with this lesson, gains two lines: a row that
replaces another frees the old row's overflow chain first, for the same
reason `leaf_delete` does.


`fix_empty` merges a page into a sibling only when it is empty, never because
it is nearly empty. That is enough for the file format and keeps the code
short; the price, pages that stay mostly empty after big deletes, is the
subject of the last section.

time.

## Decide the boundary

This engine merges a page only when it is empty and never shrinks the file.
Both are choices, and both cost space. Take a fresh copy of sqlite3's
3000-row table above and delete three rows of every four
(`DELETE FROM t WHERE id % 4 <> 0`) with 04.04's build: this engine frees
nothing. All 35 leaves stay, each about a quarter full, around 3090 of their
4088 bytes unused. sqlite3, given the same file and the same DELETE, ends
with 11 leaves and 24 free pages, because it rebalances an underfull page
with its siblings.

The file is another matter: in both engines the freed pages stay in the file
for later rows. Only VACUUM, which rebuilds the whole file, or sqlite3's
auto_vacuum mode, which moves pages around at commit, gives the bytes back to
the operating system. If your tables shrink as often as they grow, is it the
pages inside the file you want back, or the bytes on disk, and how much work
per delete will you spend on it?
