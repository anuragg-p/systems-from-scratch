# 02.03 Interior pages and the root

Leaves that split need pages above them that say which leaf holds which
rowids. This lesson adds those interior pages, a root that grows taller
without ever changing its page number, and the walk from the root down to a
leaf.

## Where this fits

![Where 02.03 fits](figures/02.03-map.svg)

After a split there are two leaves, and then dozens; a lookup has to know
which one to read. Interior pages are the B-tree's map of its own leaves:
they hold no rows, only signposts to the pages below. Every lookup and every
insert the executor asks for now starts at the table's root, reads one page
per level through the pager, and ends at one leaf. The catalog keeps each
table's root page number, so the root must stay where it is. After this
lesson the B-tree is complete enough for a table to grow to any size with a
row still found in a handful of page reads.

## The idea

**Signposts.** After the first split of a table there are two leaves, page 4
with rowids up to 180 and page 3 with the rest. Something must say so. An
**interior page** holds cells of the form (child page, rowid): "everything in
this child is at most this rowid". After its cells comes one more pointer,
the **right-most child**, for everything larger than all of them. A page with
n cells has n + 1 children.

**The root stays put.** The catalog stores the number of each table's root
page, written once by CREATE TABLE. If a full root split like any other page
and a new root were made somewhere else, the catalog would have to be
rewritten each time the tree got taller. So the root does something
different when it fills up: it copies everything it holds into a new page and
becomes an interior page with no cells and that new page as its only child.
The tree is one level taller, the new page is an ordinary full page, and it
splits as in 02.02, sending its divider up into the root.

![The root grows, as in g.db below: page 2 hands its 37 rows to a new page 3, becomes an interior page pointing at it, and page 3 splits into pages 4 and 3](figures/02.03-grow.svg)

This is why a B-tree grows at the top: every leaf stays at the same depth, and
a lookup reads the same number of pages whichever row it wants.

**Going down.** A lookup starts at the root. In each interior page it runs
the binary search of 02.01, which returns the first cell whose rowid is not
smaller than the one wanted; that cell's child is the only one that can hold
the row. If every cell is smaller, the search returns one past the last cell,
and that means the right-most child. One page per level, down to a leaf.

![Looking for rowid 1500 in a three-level tree: the search in each page picks the child, and the page and index at every level are kept as a path](figures/02.03-seek.svg)

On the way down the descent writes down where it went: at each level, the
page and the index it chose. That **path** is what later steps need. An insert
uses it to find the parent that must take a divider, and the cursor of the
next lesson uses it to move on to the next row.

## How it works

`src/btree.c:insert_cell` calls the first piece when the page that is full is
the root; every lookup and every insert starts with the second.

Two small functions come with them. `btree_insert` puts a row in by rowid:
it seeks the rowid's place and inserts the cell there, or replaces the row
if that rowid is already present, which is what UPDATE will rely on (INSERT
checks for a taken rowid before it gets here). `btree_max_rowid` follows the
right-most child down to the last leaf and returns its largest rowid: an
INSERT that gives no id takes the next one, which is how 00.01's eight names
got 1 to 8. And `insert_dividers` gains the re-seek that 02.02 described for
the rare three-way split: it searches the tree for an earlier divider's own
key (with 02.01's "compare every field" and "before equal entries" in its
`SeekKey`), which leaves the path ending at a leaf, at level `depth - 1`. The
page that split is `h` levels above the leaves, so its parent, where the
divider goes, is one level higher still: `level = c->depth - 2 - h`.

### Writing grow_root, step by step

`grow_root` runs at the moment the root has no room for a cell. It must make
the tree one level taller without moving the root, and leave the insert in
progress able to carry on as if nothing special had happened.

1. **Copy the root into a new page, and make the root point at the copy.**
   The copy keeps the root's own type and its right-most child, if it has
   one (`cl.right`); the root becomes an interior page with no cells and the
   copy as its right-most child:
   ```
   u32 child = page_alloc(p);
   Node ch = node_new(p, child);
   ...
   cells_from_node(p, &cl, &root);
   node_fill(p, &ch, n_type(&root), &cl, 0, cl.n, cl.right);
   CellList none = {0};
   node_fill(p, &root, c->intkey ? PAGE_TABLE_INTERIOR : PAGE_INDEX_INTERIOR, &none, 0, 0, child);
   ```
   A full leaf root becomes a full leaf one level down; its content does
   not change.
2. **The interior type of the same kind of tree.** An index root must
   become an index interior page (type 2), a table root a table interior
   page (type 5); sqlite3 reads the type to know how to take the cells
   apart.
3. **Shift the path down a level.** The insert in progress holds a path that
   ends at the full page, and that page is now one level deeper. Move every
   level down by one, put the root back at level 0 with index 0, and the new
   page at level 1 with the index the root had. The insert then carries on at
   level 1, and the split there sends its divider to level 0, the root.
   Without the shift the path no longer describes the tree.
   ```
   memmove(&c->pgno[1], &c->pgno[0], (size_t)c->depth * sizeof c->pgno[0]);
   memmove(&c->idx[1], &c->idx[0], (size_t)c->depth * sizeof c->idx[0]);
   c->pgno[1] = child;
   c->idx[0] = 0;
   c->depth++;
   ```

   ![The path of the insert of rowid 15, before grow_root, after it, and without the shift: level 1 is then page 0](figures/02.03-path.svg)
4. **Refuse to grow past `MAX_DEPTH`.** The path arrays have 20 slots, and a
   tree that needed a 21st would write past them.

### Writing seek_raw, step by step

`seek_raw` takes a key and builds the path to it, from the root down to the
key's place in a leaf. Lookups, inserts and the cursor of the next lesson all
start here.

1. **Search a page; if it is not a leaf, go down and search again.** For a
   table that fits in one leaf the loop runs once, and that already is a
   lookup:
   ```
   u32 pgno = c->root;
   for (;;) {
       Node n = node_get(c->pager, pgno);
       int i = node_search(c->pager, &n, k);
       ...
       if (n_leaf(&n))
           return;
       pgno = n_child(&n, i);
   }
   ```
2. **The search result is the child.** `n_child` turns i into a page number:
   the left child of cell i, or, when i is the cell count, the right-most
   child (the next subsection says why that is right).
3. **Write the path down.** Push each page and the index found into
   `c->pgno[]` and `c->idx[]`. A lookup alone would not need them, but an
   insert has to find the parent of a page that splits, and the cursor of
   02.04 has to find the next leaf; both read the path.
4. **Bound the depth.** Stop with an error past `MAX_DEPTH`. No real tree is
   that deep, but in a corrupt file a child pointer that leads back up would
   loop for ever and run past the path arrays.

### Why the search result is also the child number

On an interior page the index `node_search` returns is directly the child to
take. A divider is the largest key in its left child, so the first divider
not smaller than the key marks the only child that can hold it; when every
divider is smaller, the key can only be in the right-most child, and the
search returns one past the last cell, which is exactly that child's number.
The walk stops at a leaf position that may be one past the leaf's last cell,
when the key is larger than everything in that leaf; turning that into "the
next row" is the next lesson's job.

### Page 1, and a root with no cells

The same code serves page 1, the root of the catalog, whose B-tree header
starts at byte 100, after the file header: the page helpers carry that offset
with them, so `grow_root` never needs to know. A hundred CREATE TABLEs are
enough to turn page 1 into an interior page.

Right after `grow_root` the root has no cells at all; the split that follows
puts the first divider into it. Page 1 can stay that way: the new page has
the 100 bytes page 1 spends on the file header, so the cell may fit without a
split.

of 02.02:

## Break it

In `grow_root`, leave the path alone: delete the two `memmove` calls and the
three lines after them (`c->pgno[1] = child`, `c->idx[0] = 0`,
`c->depth++`). A table's root first grows in 04.01's build, so make the
change in `build/at/db/04.01/src/btree.c`. Rebuild, then insert 400-byte rows in order;
nine fit in the root:

<!-- verify: session -->
```
$ make -s
$ Z=$(printf '%0400d' 0)
$ (echo "CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT);"; for i in $(seq 1 40); do echo "INSERT INTO t VALUES ($i, '$Z');"; done) | ./db grow-broken.db
db: fatal: page 0 is out of range (the database has 3 pages)
$ ./db grow-broken.db 'SELECT id FROM t;' | wc -l
       9
$ sqlite3 -list grow-broken.db 'PRAGMA integrity_check'
ok
```

The tenth insert grows the root, so page 3 now holds the nine rows and the
root points at it. But the path still has one level, so `insert_cell` goes
on to look for the full page at level 1 of the path, finds page number 0
there, and stops. The file is unharmed, still nine rows and two pages,
because nothing is written until a statement commits; "3 pages" counts the
page the root had just allocated in memory. A path is part of the tree's
state while an insert runs, and every change of shape has to keep it true.

## Decide the boundary

This tree keeps its root at a fixed page and, when the root fills, copies a
whole page down to make room. That costs one page copy each time the tree
gets a level taller, which happens a handful of times in a table's life.

The textbook alternative splits the root like any other page and makes a new
root above it, at a new page number. No copy, but now the root's number
changes: the catalog row must be rewritten in the same transaction, and
anything that cached the old number is wrong. sqlite3 keeps the root fixed,
as here, because the catalog is itself a B-tree. Where else is your root's
address written down, and can every copy of it change atomically?
