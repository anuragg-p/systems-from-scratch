# 02.02 Insert and split

Inserting a row means putting its cell into the right leaf. When the leaf is
full, it splits in two and the page above it learns about the new page.

## Where this fits

![Where 02.02 fits](figures/02.02-map.svg)

The leaf of 02.01 can be read and searched, but nothing can put a row into it
yet. This lesson adds the write side of the B-tree. INSERT, which the
executor runs in module 04, hands the B-tree one row; the B-tree finds the
leaf it belongs in (the descent that finds it is 02.03's), writes the cell
there, and asks the pager for a fresh page when a leaf runs out of room.
After this lesson the B-tree has what it needs for a table to grow past one
page to thousands of rows spread over many leaves, in a file sqlite3 checks
and reads.

## The idea

A page has 4096 bytes and no more. Fill one with 100-byte rows and the 38th
does not fit. The page cannot grow, and the row cannot go just anywhere: it
has to sit in rowid order, or the search of 02.01 stops finding things.

**Putting a cell into a page.** While there is room, an insert is cheap. The
free space is the gap between the pointer array and the cells. The new cell
goes at the bottom of the cell area, just below the cells already there; its
pointer goes into the array at the position the search returned, and the
pointers after it move along by 2 bytes. Here is rowid 5 going into the
three-row page of 02.01 (a fresh copy, before rowid 12 was added):

![Rowid 5 goes into demo.db's leaf: its 9-byte cell lands just below the others, and its pointer is slotted in second](figures/02.02-insert.svg)

**Splitting a full page.** When the gap is too small, take every cell of the
page plus the new one, in key order, and cut the list in two halves of about
the same number of bytes. A new page takes the left half, the old page keeps
the right half, and the parent page gets one new cell, a **divider**: the
new page's number and the largest rowid in it.

![Page 4 of s.db is full when rowid 22 arrives: page 5 takes rowids 1-19, page 4 keeps 20-180, and the divider (5 | 19) goes into page 2](figures/02.02-split.svg)

Why the old page keeps the *right* half: the parent already holds a pointer
to page 4, saying "rowids up to 180 are here". After the split page 4 still
holds the largest rowids of the pair, up to 180, so that pointer is still
true. Only the new page needs a new cell, and it goes just before the old
one. A split changes the parent by one cell.

What travels up depends on the kind of page. In a table leaf, the divider
is a copy: rowid 19 stays in page 5, and the parent repeats it as a
signpost. In an index, and in any interior page, the cell in the middle of
the cut moves up whole and leaves the child, because those cells are entries
or signposts in their own right.

![What a split sends up: a copy of a rowid from a table leaf, the entry itself from an index leaf, the middle cell from an interior page](figures/02.02-dividers.svg)

The parent may be full too. Then the divider's insert splits the parent in
the same way, one level up, and the next lesson takes over when the full page
is the root.

Scrambled, every split cuts in the middle and each half is then filled by
the rows that happen to land in it: the leaves end up about 70% full, 1189 of
their 4088 bytes unused. In order it is worse. Every new row lands in the
right-most leaf, so after each split the left half never gets another row:
the leaves stay half empty, 2026 bytes unused, and the table takes 47 pages
instead of 34. Module 07 measures a split made for rows that arrive in
order.

## How it works

`src/btree.c:insert_cell` ties this lesson's two pieces together. It tries to
put the cell into its page; if that fails (and the page is not the root,
which is 02.03's case), it gathers the page's cells and the new one, in key
order, and splits them.

Both work on the **cursor path**: `c->pgno[L]` is the page at level L on the
way from the root (level 0) down to the leaf, and `c->idx[L]` the cell
position taken in it. The descent of 02.03 fills it in; here it is how a
split knows its page (`c->pgno[L]`) and its parent (`c->pgno[L - 1]`). The
helpers listed with the lesson are plumbing: `cell_build` makes a cell's
bytes (and `overflow_write` its overflow chain when the payload is too big),
the `CellList` functions keep copies of cells in key order, `node_height`
says how far a page is above the leaves, `btree_create` makes an empty root
for a new table, and `page_alloc` hands out a new page at the end of the
file.

### Writing node_insert, step by step

`node_insert` is called for every cell that goes into any page: rows into
leaves, and dividers into the pages above them. It either places the cell or
answers "full", and that answer is what makes `insert_cell` split. Write it
in this order.

1. **The easy case: the page has room.** Copy the cell in just below the
   cell area, open a slot in the pointer array at position i, and update
   the header:
   ```
   int nc = n_ncells(n), hs = n_hdrsize(n);
   u32 content = n_content(n);
   content -= size;
   memcpy(n->d + content, cell, size);
   u8 *ptr = n->d + n->h + hs + 2 * i;
   memmove(ptr + 2, ptr, (size_t)(2 * (nc - i)));
   put2(ptr, content);
   put2(n->d + n->h + 3, (u32)(nc + 1));
   put2(n->d + n->h + 5, content);
   return 1;
   ```
   Without the `memmove`, the new pointer overwrites cell i's pointer: that
   row is still in the page, but nothing points at it any more. Forget the
   cell area's new start at byte 5 and the next insert writes its cell on
   top of this one.
2. **Check the gap.** Work out where the pointer array would end with one
   more pointer; the cell must fit between there and the start of the cell
   area.
   ```
   u32 ptrs_end = (u32)(n->h + hs + 2 * (nc + 1));
   ...
   if (ptrs_end + size > content) {
   ```
3. **Say "full" honestly.** When the gap is too small, add up what the cells
   really occupy (`node_used`) plus 2 bytes per pointer, and compare that
   with the page's room: its usable size less the header, and less the 100
   bytes of file header on page 1 (`n->h`). Only when even that does not fit,
   return 0.
4. **Room, but not in one piece.** Pages sqlite3 wrote keep the space of a
   deleted cell as a freeblock between other cells. Then `node_rebuild`
   packs every cell against the end of the page, which gathers the free bytes
   into the gap, and the easy case runs. Without it, a page could split while
   a quarter of it was free.

### Writing `split`, step by step

`insert_cell` calls `split` when `node_insert` says the page is full. It is
handed the page's cells plus the new one, already in key order, as copies in
a `CellList`. Its job is to spread them over pages and send a divider up for
every new page. The parts in the order a person would add them:

1. **Cut, fill each part, send the dividers up.** For a table leaf the cut
   gives two halves: `split_point` picks it where the halves are closest in
   bytes while both fit, and `partition` turns it into two ranges of cells,
   `[0, m)` and `[m, n)`. Each part is then laid out on its page:
   ```
   m = split_point(p, type, cl);
   int gs[MAX_PARTS], ge[MAX_PARTS];
   int k = partition(p, type, cl, m, gs, ge);
   ...
   for (int g = 0; g < k; g++) {
       ...
       node_fill(p, &pn, type, cl, gs[g], ge[g], right);
       ...
   }
   insert_dividers(c, L, h, div, dsize, k - 1);
   ```
   Bytes, not cells: one 4000-byte row weighs as much as forty small ones.
   `node_fill` writes a page from scratch, and that is safe because the
   `CellList` holds copies; rewriting the old page in place would overwrite
   cells not yet copied. `insert_dividers` puts each divider into the parent
   through `insert_cell`, so the parent can split in turn, up to the root.
2. **New pages take the left parts; the old page keeps the last.** The last
   part stays on the page being split, so the parent's pointer to it stays
   true, as the split figure shows.
   ```
   if (g < k - 1) {
       pgno = page_alloc(p);
       pn = node_new(p, pgno);
   } else {
       pgno = c->pgno[L];
       pn = node_write(p, pgno);
   }
   ```
3. **The divider of a table leaf** is the new page's number and the rowid of
   the part's last cell, `ge[g] - 1`. The largest rowid on the left keeps the
   format's rule: keys left of a divider are at most the divider, keys right
   of it are larger. The Break it below takes the first rowid on the right
   instead.
   ```
   cell_parse_type(p, type, cells_at(cl, ge[g] - 1), &ci);
   put4(div[g], pgno);
   dsize[g] = 4 + (u32)varint_put(div[g] + 4, (u64)ci.key);
   ```
4. **Index leaves and interior pages: the middle cell moves up.** For them,
   `partition` leaves one cell out between the parts (the `up` in
   `gs[1] = m + up`), and that cell, with the new page's number in front,
   becomes the divider: an index entry has to live somewhere. In an
   interior page that cell's left child becomes the new page's right-most
   child; without it, the first lookup that goes there asks for page 0.
5. **Sometimes two pages are not enough.** Cells of 2007, 4007 and 2007
   bytes have no cut that leaves both halves within a page's 4088 bytes, so
   `split_point` returns -1 and `partition` fills pages one after another,
   three of them. This is why the loop is over k parts rather than two.

   ![Rows of 2000, 4000 and 2000 bytes: no cut into two fits, so page 3 splits into pages 4, 5 and 3, and the root gets two dividers](figures/02.02-three-way.svg)

### Dividers that have to find their place again

A three-way split sends two dividers up, and the order matters.
`insert_dividers` puts the last one in first, where the parent points at the
split page. That insert can itself split the parent, and then the parent page
the earlier divider belongs in may no longer be the page on the path. So each
earlier divider finds its place afresh, by searching the tree for its own key
and inserting just before the divider that followed it. It costs a descent
per divider, only in a rare case, and keeps the code from tracking how the
parent level was rearranged. That search is the descent from the root that
02.03 builds, so this part of `insert_dividers` arrives with it.

## Break it

Make a table leaf's divider the *first* rowid of the page to its right
instead of the last of its own. A table's leaves first split in 04.01's
build, so make the change there: in `build/at/db/04.01/src/btree.c`, function `split`, in
the `PAGE_TABLE_LEAF` branch, change `cells_at(cl, ge[g] - 1)` to
`cells_at(cl, ge[g])`. Rebuild, load the scrambled 2000 rows again into a
new file, and ask sqlite3:

```
$ make -s
$ (echo "CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT); BEGIN;"; for i in $(seq 1 2000); do k=$(( i * 1237 % 2003 )); echo "INSERT INTO t VALUES ($k, 'row $k $Z');"; done; echo "COMMIT;") | ./db mixed-broken.db
$ sqlite3 mixed-broken.db 'PRAGMA integrity_check' | head -4
*** in database main ***
Tree 2 page 2 cell 30: Rowid 1941 out of order
Tree 2 page 2 cell 29: Rowid 1881 out of order
Tree 2 page 2 cell 28: Rowid 1819 out of order
$ sqlite3 -list mixed-broken.db 'SELECT id FROM t WHERE id = 71; SELECT id FROM t WHERE id = 72;'
72
```

All 31 dividers are wrong, and sqlite3 can no longer find the rows they
name. Rowid 71 is the first row of the second leaf; the root now says
"rowids up to 71 are in the first leaf", so sqlite3 goes there, does not find
71, and returns nothing. The row is still in the file: this build's
`SELECT id FROM t` reads every leaf in turn without searching, and lists it
between 70 and 72. A bug that only a search notices, and only another
program's search at that: the rule for dividers is part of the file format,
not a private convention.

## Decide the boundary

This engine splits a full page 50/50 and never looks at its neighbours. It
is simple, and each split writes three pages. The price is space: after
random inserts the leaves sit about 70% full. sqlite3 loaded the same 2000
scrambled rows into 27 pages, 25 leaves averaging 80 cells and 377 unused
bytes; this engine used 34 pages.

sqlite3 instead rebalances a full page with up to two siblings, spreading
the cells of three pages over as few pages as hold them. Pages stay fuller,
files smaller and scans shorter, at the cost of more code and more pages
written per split. Which matters more to you, the size of the file and the
speed of a scan, or the cost and simplicity of each insert?
