# 02.01 A leaf page: cells and search

A table keeps its rows in pages of the file, sorted by rowid. This lesson
reads the bottom kind of page, a leaf: how rows of any size are packed into
4096 bytes, and how a binary search finds one of them.

## Where this fits

![Where 02.01 fits](figures/02.01-map.svg)

Module 01 left two tools: the pager, which hands out any page of the file by
its number, and the record format, which turns a row into bytes and back.
Nothing yet decides which page a row lives in, or how to find it again. That
is the B-tree, the layer this module builds. Above it, the executor will ask
for "the row with rowid 7" or "every row, in order"; below it, the B-tree only
asks the pager for pages. After this lesson the B-tree can take apart any
cell of a page, its own or sqlite3's, and find where a rowid sits among a
leaf's cells: the search that every lookup and every insert will start
from.

## The idea

**A table is a tree of pages.** Every row of a table has a **rowid**, a
64-bit integer that is its key; a column declared `INTEGER PRIMARY KEY` is
the rowid under another name, which is why 01.03's records keep a NULL in
its place. A table of a million rows fills thousands of
pages. Reading them all to find rowid 7 is out of the question, and so is
keeping the rows in one long sorted run that has to shift whenever a row
arrives in the middle. A B-tree avoids both. The rows sit in leaf pages,
sorted by rowid from the first leaf to the last. Above the leaves, interior
pages hold only signposts: "rowids up to 19 are in page 5, up to 180 in page
4, the rest in page 3". Above those, more signposts, up to a single root
page. A lookup reads one page per level, and with 4096-byte pages three or
four levels hold millions of rows. The catalog stores the number of each
table's root page, and that number is all the B-tree needs to start.

![A table is a tree of pages: rows in the leaves, signposts above them, and what each lesson of this module adds](figures/02.01-tree.svg)

The module builds that tree bottom up, one piece per lesson, starting with a
single leaf.

**A leaf page.** A leaf holds as many rows as fit in its 4096 bytes. Rows come
in every size: a row of three small numbers takes a dozen bytes, a row with a
long text takes hundreds. They must stay in rowid order, or no search can
work, and a new row may belong anywhere in that order.

Moving rows around on every insert would be slow. SQLite's file format, which
this engine follows byte for byte, solves it with one level of indirection.
Each row is stored as a **cell**, and cells are packed against the end of the
page in whatever order they arrived. At the front, after an 8-byte header, is
the **cell pointer array**: one 2-byte offset per cell, kept in rowid order.
The free space is the gap in the middle; pointers grow into it from the
front, cells from the back.

Here is the page sqlite3 wrote for three rows inserted in the order 7, 3, 9:

![Page 2 of demo.db: the cells lie in the order they arrived, the 2-byte pointers in front of them are in rowid order](figures/02.01-leaf-page.svg)

The cells sit where they landed: rowid 7 at the very end, then 3, then 9.
The pointers are sorted: 4076 (rowid 3), 4086 (rowid 7), 4067 (rowid 9).
Reading the rows in order means following the pointers. Putting a new row in
the middle means writing its cell anywhere in the gap and sliding a few
2-byte pointers along, never a cell.

**Finding a rowid.** Because the pointers are sorted, the search can halve:
read the middle cell, compare its rowid, throw away the half that cannot hold
the key, repeat. A leaf of 93 cells takes six or seven reads.

![Binary search for rowid 50 among 93 cells: six probes, each halving the range](figures/02.01-search.svg)

The search answers "where does this key go?", not "is it here?": it returns
the first cell whose key is not smaller than the one asked for. If that cell
holds the key, the row is found. If not, it is the spot where the row would
be inserted, which is what an insert needs, and the spot where a range of
rowids starts.

**Rows bigger than a page.** A 5000-byte text cannot fit in a 4096-byte page.
Then the cell keeps the start of the row plus the number of an **overflow
page** that holds the rest, with more pages chained on if needed.

**What comes with it.** Two pieces arrive now for the index trees of module
05, where a search compares whole records instead of rowids. `record.c`
gains `record_compare`, which compares two records value by value, and a new
file, `expr.c`, brings `value_compare`, which puts any two values in
SQLite's order: NULL first, then numbers, then text, then blobs. It compares
an integer with a float exactly, without turning the integer into a double,
because a double cannot hold every 64-bit integer and two different numbers
would compare equal. `db.h` also declares the `Cursor`, a position in a
tree, which 02.03 and 02.04 build.

Make a table with sqlite3, inserting the rows out of order. The table's root

pointers, then its cells:

```
$ sqlite3 demo.db "CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT); INSERT INTO t VALUES (7, 'seven'); INSERT INTO t VALUES (3, 'three'); INSERT INTO t VALUES (9, 'nine');"
$ xxd -s 4096 -l 16 demo.db
00001000: 0d00 0000 030f e300 0fec 0ff6 0fe3 0000  ................
$ xxd -s 8163 demo.db
00001fe3: 0709 0300 156e 696e 6508 0303 0017 7468  .....nine.....th
00001ff3: 7265 6508 0703 0017 7365 7665 6e         ree.....seven
```

`0d` says table leaf, `0003` three cells, `0fe3` (4067) where the cells
begin; then come the three pointers. Each cell starts with the length of its
record and its rowid: `07 09` for rowid 9, `08 03`, `08 07`. A search for
rowid 8 would land on the third pointer, rowid 9: the place 8 would go.

Now a row that does not fit, 5000 x's, which with its 4-byte record header
make a payload of 5004 bytes:

<!-- verify: session -->
```
$ sqlite3 demo.db "INSERT INTO t VALUES (12, printf('%.*c', 5000, 'x'));"
$ xxd -s 4096 -l 16 demo.db
00001000: 0d00 0000 040c 4c00 0fec 0ff6 0fe3 0c4c  ......L........L
$ xxd -s 7244 -l 16 demo.db
00001c4c: a70c 0c04 00ce 1d78 7878 7878 7878 7878  .......xxxxxxxxx
$ xxd -s 8156 -l 8 demo.db
00001fdc: 7878 7800 0000 0307                      xxx.....
$ xxd -s 8192 -l 16 demo.db
00002000: 0000 0000 7878 7878 7878 7878 7878 7878  ....xxxxxxxxxxxx
```

Four cells now, the new one at 0x0c4c (3148): the payload size `a7 0c`
(5004), the rowid `0c`, then the record, `04 00 ce 1d` and the first x's. Its
last four bytes, `00 00 00 03`, name the overflow page, just before rowid 9's
cell begins with `07`. Page 3, at byte 8192, starts with 4 bytes of "next
page in the chain" (0: there is none) and then the rest of the x's.

## How it works

### Writing cell_parse_type, step by step

Everything in the B-tree reads cells: the search compares their keys, a
lookup hands their record to the executor, and the next lessons copy cells
between pages. `src/btree.c:cell_parse_type` turns the bytes of any cell into
one `CellInfo`, so that nothing else has to know the four layouts. This is
the order to write it in.

1. **The table leaf first**, the only kind of cell a one-page table has.
   Read the payload's size, then the rowid, both varints; the record starts
   right after them. Then remember where the cell ends:
   ```
   const u8 *q = cell;
   u64 v;
   q += varint_get(q, &v);
   ci->npayload = (u32)v;
   q += varint_get(q, &v);
   ci->key = (i64)v;
   ci->payload = q;
   ...
   ci->len = (u32)(q - cell);
   ```
   The fields are read in order because varints have no fixed width: there
   is no other way to know where the next one begins. And cells sit back to
   back with nothing between them, so `len` is the only record of a cell's
   size; the split in 02.02 copies cells by it.
2. **Only part of a big payload is on the page.** Ask `local_size` how much,
   and when that is less than the whole payload, read the 4-byte overflow
   page number after it. Without this step the 5004-byte payload of the Run
   it would be read as 5004 bytes of a 4096-byte page. The formula is the file
   format's, word for word, so that sqlite3 cuts every payload at the same
   byte.
   ```
   ci->nlocal = local_size(p, type, ci->npayload);
   q += ci->nlocal;
   if (ci->nlocal < ci->npayload) {
       ci->ovfl = get4(q);
       q += 4;
   }
   ```
3. **Index leaves** are the same without the rowid: in an index the key is
   the record itself. So the rowid of step 1 moves inside
   `if (type == PAGE_TABLE_LEAF)`.
4. **Interior pages** start every cell with the 4-byte page number of its
   left child, for both kinds of tree, so read it before anything else. The
   table interior cell has no payload at all, only a rowid after the child,
   so it gets its own branch around steps 1 to 3.
   ```
   if (!is_leaf_type(type)) {
       ci->child = get4(q);
       q += 4;
   }
   ```
5. **At least 4 bytes.** `ci->size` is `len`, or 4 when `len` is smaller.
   When sqlite3 deletes a cell it reuses the space as a **freeblock** with a
   4-byte header, so no cell may be smaller than that. This engine never makes
   freeblocks, but its pages must be ones sqlite3 can edit.

### Writing node_search, step by step

`src/btree.c:node_search` answers the one question every caller has for a
page: where does this key go? A lookup asks it of a leaf. The descent from
the root (02.03) asks it of every page on the way down, and an insert (02.02)
asks it where the new cell goes.

1. **Fix what it returns first: a position, not "found or not".** The index
   of the first cell that does not sort before the key, or the cell count
   when there is none. A walk from cell 0 would already give it; the search
   narrows a range `[lo, hi)` down to that one place instead:
   ```
   int lo = 0, hi = n_ncells(n);
   while (lo < hi) {
       ...
   }
   return lo;
   ```
   The **invariant**: every cell before `lo` sorts before the key, no cell
   from `hi` on does. When the two meet, `lo` is the answer.
2. **Halve.** Look at the middle cell and move one end: six or seven reads
   instead of 93 on a leaf like the one in the figure. Comparing through `cell_compare` makes the
   search the same for both kinds of tree, rowids for a table and records
   for an index.
   ```
   int mid = lo + (hi - lo) / 2;
   if (cell_compare(p, n, mid, k) < 0)
       lo = mid + 1;
   else
       hi = mid;
   ```
3. **Only a strictly smaller cell moves `lo`.** It is tempting to stop as
   soon as the middle cell equals the key. Do not: in an index many entries
   can compare equal, and the caller wants the first of them.

### Why 912 bytes stay on the page

How much of a payload stays on the page is not the engine's choice, and the
formula picks an odd-looking number on purpose. `local_size` works between
two limits: `X`, the most a cell may keep on its page (for a table leaf, the
usable size less 35), and `M`, the least it keeps once it spills (489 bytes
on a 4096-byte page). Within them it keeps just enough that the overflow
pages come out full. The 5004-byte payload of rowid 12 keeps 912 bytes on
page 2, and the other 4092 fill page 3 exactly (4096 bytes, less the 4-byte
link to the next page). When filling the last overflow page would leave more
than `X` on the page, the cell keeps only `M`, and the last overflow page has
room to spare.

### Ties in an index

`cell_compare` is where tables and indexes part. For a table it compares
rowids. For an index (module 05) it compares whole records, and a tie is
broken by the probe's `bias`: -1 puts the probe before every equal entry, +1
after them all. That is how the same search will find both the first and the
last entry of `a = 5`. The two kinds of tree also differ in where entries
live: a table keeps its rows only in leaves (a B+tree, in the textbooks'
terms), while an index keeps entries in its interior pages too (a plain
B-tree), which 02.04 comes back to. Either way the caller decides whether the cell the
search returns is a match, so one answer serves a lookup, an insert and the
start of a range.

## Break it

In `node_search`, let `lo` move past equal cells too: change
`cell_compare(p, n, mid, k) < 0` to `<= 0`. Nothing at this lesson calls
`node_search`. The first build where it visibly matters is 04.01's: INSERT
there asks the B-tree whether a rowid is already taken, through this
lesson's `node_search`, unchanged. From the repository root, write that
project out, build it, and try a rowid that is taken:

<!-- verify: session -->
```
$ ./learn files db --at 04.01

$ cd build/at/db/04.01
$ make -s
$ sqlite3 demo.db "CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT); INSERT INTO t VALUES (7, 'seven'); INSERT INTO t VALUES (3, 'three'); INSERT INTO t VALUES (9, 'nine');"
$ ./db demo.db "INSERT INTO t VALUES (7, 'again');"
Error: UNIQUE constraint failed: t.id
```

Now make the change in `src/btree.c` there, and try again:

<!-- verify: patch file=src/btree.c at=04.01 old="cell_compare(p, n, mid, k) < 0" new="cell_compare(p, n, mid, k) <= 0" -->
<!-- verify: session -->
```
$ make -s
$ ./db demo.db "INSERT INTO t VALUES (7, 'again'); SELECT * FROM t;"
3|three
7|seven
7|again
9|nine
$ sqlite3 -list demo.db "PRAGMA integrity_check"
*** in database main ***
Tree 2 page 2 cell 1: Rowid 7 out of order
```

INSERT asks the search where rowid 7 goes and looks at the cell it lands on:
if that cell holds 7, the rowid is taken. The search now returns the first
cell *after* the key, 9, so the check never sees the 7 that is there, and
the new cell goes in beside it. The table holds two rows with one rowid,
which the format forbids, and sqlite3 says so. Every lookup by rowid would
land one cell late in the same way. One character, `<` against `<=`, is the
difference between finding a row and stepping over it.

## Decide the boundary

This page keeps its cells unsorted behind a sorted array of 2-byte pointers,
and searches by halving. Each probe jumps to a different spot in the page and
decodes a varint there.

Another design could keep the keys themselves in a sorted, fixed-width array
at the front of the page: a probe would be one memory read, but an insert in
the middle would move 8 bytes per later key instead of 2, and index keys of
varying length would not fit the scheme at all. Or it could skip sorting and
scan every cell, which makes inserts trivial and every search read the whole
page. Here the file format chose, because sqlite3 must read these pages. If
it had not: how many cells does a page hold, and does your workload search
more often than it inserts?
