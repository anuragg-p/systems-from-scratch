# 07.01 Reading the benchmark

The benchmark puts this engine and sqlite3 through the same seven workloads
and prints one ratio per line. A ratio is easy to read and easy to misread:
this lab takes one run line by line and finds out what each line is really
measuring, including the lines where this engine loses.

## Where this fits

![Where 07.01 fits](figures/07.01-map.svg)

Every layer is now built: SQL text goes in, through the tokenizer, parser,
planner and executor, down through B-trees and the pager to a file that
sqlite3 can open, with journals or a log keeping commits whole. This last
module stops adding parts and asks how good they are. This lab reads the
benchmark of 00.02 against sqlite3, the next one finds where the time goes
inside the engine, and the last one changes one thing because of what the
first two found. The lab adds no code; it runs the engine as it stands now.

## The idea

![One run of the benchmark as ratios; update and delete are the rows where ./db is slower.](figures/07.01-ratios.svg)

The benchmark builds the same table in both engines,
`t(id INTEGER PRIMARY KEY, a INTEGER, b TEXT)`, with 100000 rows and an
index on `a`, and times seven workloads on it. Both engines get the same SQL
text on their shell's standard input and the same durability settings: a
rollback journal and an `fsync` at every commit. Each workload runs once to
warm up and then three times, and the table shows the median. The times are
for the whole process, start-up included.

A line that says `4.29x` says only that one program finished a script four
times sooner than another. It does not say which part of the work was
faster. To read a line, find what dominates its script: the disk, the cost
of starting each statement, the B-tree, or the way pages change. Then try
that guess with a second, smaller experiment that removes one of them.

## How it works

Line by line, what each one measures.

**Insert, autocommit: the disk.** Every INSERT is its own transaction, so
every row pays a full commit: four `fsync`s with the journal (06.02), in both
engines. The CPU work of one insert is a few microseconds; the commit is a
few hundred. Both engines spend this line waiting for the same disk.

**Insert, one transaction: a draw.** 100000 inserts and one commit, so this
is the CPU cost of an insert, and the two engines are within each other's
noise: 0.91x in this run, 1.05x in the next, with spreads of 1.21 and 1.12.
Rows arriving in rowid order make this an easy case for both: every row
goes at the end of the last leaf.

**Lookups: sqlite3 shares the file, this engine does not.** Outside a
transaction, sqlite3 begins every statement by taking a shared lock on the
file, checking that no hot journal is waiting, and checking that no other
process changed the file since its last statement. Those are system calls,
and they are where most of its 0.30 s of system time goes. A sampling
profiler (`sample`, the tool of the next lab) on sqlite3 working through six
copies of `lookups.sql` finds 794 of its 1711 samples in `btreeBeginTrans`,
the start of each statement's read transaction: `fcntl` locks, two `stat`
calls looking for a journal, an `fstat`. Inside one BEGIN it does that once,
and its lookups go from 0.550 s to 0.227 s. This engine assumes it is the
only process using the file and does none of it, which is a choice with a
cost: two `./db` processes writing one file at once can corrupt it. Take
away what a statement costs when it does nothing at all (0.030 s and
0.097 s for 100000 `SELECT 1`), and a lookup itself costs about 1.4
microseconds here and 1.3 in sqlite3 inside a transaction. The B-trees are
about even; the 4.29x is mostly locking that this engine does not do, and
partly a cheaper statement (sqlite3 compiles each one into a bytecode
program first).

**Range scan: less of a gap.** Each statement reads 100 rows, so the cost of
starting a statement is spread over 100 rows of walking leaves, and the
ratio falls to 1.36x.

**Lookup by secondary index: the same story, twice the descents.** An index
lookup is two descents, the index and then the table (05.02), in both
engines; the fixed cost per statement is the same as for the point lookup,
so the ratio is a little lower.

**Update and delete by key: slower, for reasons in this engine.** 10000
statements inside one transaction, so sqlite3 takes its lock once and there
is little to skip. What is left is changing pages, and this engine changes
them more expensively than sqlite3 does. The next lab measures where that
time goes.

**File size: both trees are half empty.** sqlite3's `dbstat` table counts
the pages of each B-tree, and how full they are:

The table is 2292 pages here at half full, against 1155 nearly full in
sqlite3's file. Its rows arrive in rowid order, and every split cuts a full
leaf in the middle (02.02): the new rows go on to the right half, and the
left half is never written to again. The index is 516 pages at 55% against
288 at 99% for a different reason: sqlite3 builds an index by sorting all
its entries first and then appending them in order, so its pages come out
full, while this engine inserts entries one at a time in table order and
splits full pages into half-full ones that later inserts only partly
refill. sqlite3, when it does have to insert entries out of order (an index
created before the rows, so every INSERT adds to it), moves cells between
neighbouring pages when one fills: that index ends at 311 pages, 92% full.
The table's half is what 07.03 takes on.

## Break it

The lookup reading says the gap is per-statement locking. Test it by making
this engine pay for a lock too: a shared lock on the file before every
statement outside a transaction, dropped after it. In `src/exec.c`, add
`#include <sys/file.h>` under the other includes, and in `db_exec` replace
the two lines `if (rc > 0)` and `rc = run_stmt(db, s);` with

<!-- verify: patch file=src/exec.c
 #include <strings.h>
+#include <sys/file.h>
-->
<!-- verify: patch file=src/exec.c
-        if (rc > 0)
-            rc = run_stmt(db, s);
@block
-->
```
        if (rc > 0) {
            if (!db->in_txn)
                flock(db->pager.fd, LOCK_SH);
            rc = run_stmt(db, s);
            if (!db->in_txn)
                flock(db->pager.fd, LOCK_UN);
        }
```

then `make` and time the two lookup scripts again:

<!-- verify: session cwd=project timeout=120
line 2 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
line 4 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
-->
```
$ time (./db base.db < lookups.sql > /dev/null)
  0.15s user 0.07s system 99% cpu 0.222 total
$ time (./db base.db < lookups-txn.sql > /dev/null)
  0.13s user 0.04s system 99% cpu 0.167 total
```

Separate statements slow down from 0.173 s to 0.222 s, most of it in system
time; inside one BEGIN nothing changes, because the lock is only taken
outside a transaction. No other process holds the lock, so it never waits:
this is the cost of the two system calls alone, half a microsecond a
statement. sqlite3 makes more of them per statement (its locks, the checks
for a journal, the look at the file's size) and pays about three
microseconds. The point lookup line measures who locks, not whose B-tree is
faster.

## Decide the boundary

This benchmark feeds SQL text to each engine's shell and times the whole
process, so it measures what a user of the shell gets: parsing, planning,
running, printing, start-up. Another benchmark would call each engine
through its C interface with prepared statements, which would remove
parsing and most of the per-statement cost, and show the B-trees more
nearly alone. And the lookup line would look very different if this engine
had to take the locks that let several processes share a file safely, which
sqlite3 pays for on every statement. Which of these costs would your
program pay?
