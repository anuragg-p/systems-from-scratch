# 07.02 Where the time goes

The benchmark says how long a workload took, not what the engine was doing
all that time. Two tools answer that: the engine's own counters, which count
what it did (pages read, fsyncs, splits), and a sampling profiler, which
shows where the CPU was. This lab uses both, and finds the reason this
engine is slower than sqlite3 at updates and deletes.

## Where this fits

![Where 07.02 fits](figures/07.02-map.svg)

The previous lab read the benchmark from outside and made guesses: lookups
cost a few page reads, commits cost fsyncs, and updates and deletes spend
their time changing pages. This lab looks inside the B-tree, the pager and
the journal to put numbers on those guesses. It adds no code; it runs the
engine as it stands at this lesson with its counters on, and once under a
profiler. What it
finds decides what the last lesson changes, and what it leaves alone.

## The idea

**Counters** are exact and cheap. Every time the pager reads a page or calls
`fsync`, or the B-tree splits a page, a counter goes up, and `DB_STATS=1`
prints them all when the process exits. They answer "how many", which is
often the whole answer: a lookup that reads four pages, a commit that waits
for the disk four times.

A **sampling profiler** answers "where". It stops the program about a
thousand times a second, records which functions were on the call stack,
and lets it go on. A function that shows up in half the samples was running,
or was being waited on by its callers, for half the time. On macOS the tool
is `sample`, which comes with the system; on Linux, `perf` does the same job.

## How it works

What the numbers say.

**A lookup costs one page per level, plus the schema.** The four reads are
the depth of the tree plus page 1. The pager's cache keeps those pages for
the rest of the process, so in the benchmark, where 100000 lookups share one
process, most lookups find the upper levels already cached and read only a
leaf, if that.

**A journal commit waits four times, a log commit once.** Twenty fsyncs for
five commits with the journal: the journal, its directory, its header, the
database (06.02). Each commit journals three pages, the table leaf, the
index leaf and page 1, whose change counter every commit bumps, and the 22
page reads are 7 for the inserts and 15 to read those originals back. In
WAL mode the eight fsyncs are one per commit, one for the new log's
directory, and two for the checkpoint when the file was closed (06.04). This
is the autocommit line of the benchmark, counted.

![One autocommit INSERT: four fsyncs with the rollback journal, one with the log.](figures/07.02-fsyncs.svg)

**Half of a delete is rewriting the page.** This is how a cell leaves a
page today: `node_remove` calls `node_rebuild`, which copies every other
cell of the page out into a list (`cells_from_node`) and lays them all out
again, packed against the end of the page. A leaf of this table holds about
44 rows (it is half full, 07.01) and a leaf of its index about 194 entries,
so removing one cell moves all the others. A delete does this twice, once
in the index and once in the table, and an update does it once, because it
replaces a row by removing the old cell and inserting the new one, which is
why the rebuild is a smaller share of an update.

**Nothing else comes close.** Walking down the trees from the root, three or
four times per row, takes about a fifth of the samples; parsing, planning
and the copies a statement keeps of the pages it changes, so that it alone
can be undone if it fails, take a few percent each. The rebuild is the one
thing worth changing first.

![Removing one cell: this engine rebuilds the page; sqlite3 drops the pointer and records a freeblock.](figures/07.02-remove-cell.svg)

Why rebuild at all? The page format has room for holes. Its header starts a
list of **freeblocks**, holes of four bytes or more left by removed cells,
to be reused or cleaned up later, and counts the **fragmented bytes**, holes
too small to list. This engine never makes either. Every page it writes is
packed, with all free space in one gap in the middle, which keeps its
insert code simple: a cell fits if the gap is big enough, or after one more rebuild if
the page's total free space is. The price is paid at every removal.

## Break it

Remove a cell the cheap way: drop its pointer and nothing else. In
`src/btree.c`, replace the body of `node_remove`, `node_rebuild(p, n, i);`,
with

<!-- verify: patch file=src/btree.c
-    node_rebuild(p, n, i);
@block
-->
```
    u8 *ptr = n->d + n->h + n_hdrsize(n) + 2 * i;
    memmove(ptr, ptr + 2, (size_t)(2 * (n_ncells(n) - i - 1)));
    put2(n->d + n->h + 3, (u32)(n_ncells(n) - 1));
```

then `./learn bench db --at 07.02`, which builds the changed engine and
runs the benchmark on it. The two lines that change:

<!-- verify: session run="./learn bench db --at 07.02" more wait=300 timeout=900

line 3 ~ delete by key, one transaction +10000 +[\d,]+ +[\d,]+ +\d+\.\d\dx +\d+\.\d\d +\d+\.\d\d
-->
```
...
update by key, one transaction      10000      204,096        233,181       0.88x          1.08   1.29
delete by key, one transaction      10000      199,889        176,682       1.13x          1.12   1.00
```

From 0.82x and 0.76x in 07.01's table to 0.88x and 1.13x (another run gave
0.97x and 1.01x): the rebuild was most of the gap. The engine itself does
not mind the leftover bytes: its free-space arithmetic counts the cells
that are there, and rebuilds when it needs the room. sqlite3 minds:

<!-- verify: session cwd=project -->
```
$ cp base.db del.db
$ (head -10001 deletes.sql; echo 'COMMIT;') | ./db del.db
$ sqlite3 del.db 'PRAGMA integrity_check' | head -3
*** in database main ***
Fragmentation of 450 bytes reported as 0 on page 3
Fragmentation of 270 bytes reported as 0 on page 2293
$ ./db del.db 'SELECT id FROM t WHERE id <= 20' | wc -l
      19
```

The file format says every free byte of a page must be accounted for, in
the gap, a freeblock or the fragmented count, and these holes are in none
of them. The rows are right (19 of the first 20 survive, as with the
unchanged engine), but the file is no longer a valid SQLite file. The fast and correct version is the one sqlite3 has: write the
hole into the page's freeblock list, and teach insert to reuse freeblocks
before it rebuilds.

## Decide the boundary

This engine keeps every page packed, so free space is always one gap and
inserting is simple; it pays on every removal, in proportion to the size of
the page. sqlite3 leaves holes and tracks them, so a removal costs a few
bytes of bookkeeping; it pays in the code that finds, merges and reuses
holes, and in an occasional defragmentation of a page when the holes are
too small to use. Which costs more depends on the mix: a table that is only
appended to never removes a cell, and a queue that deletes as fast as it
inserts removes all the time. What does your workload do to its pages?
