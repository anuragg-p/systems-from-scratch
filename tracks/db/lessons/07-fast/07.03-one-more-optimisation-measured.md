# 07.03 One more optimisation, measured

Most tables grow at the end: each new row gets the next rowid. Split a full
page down the middle when that happens, and every page but the last stays
half empty for good. This lesson changes where a table leaf splits when a
row is appended, and measures what that is worth.

## Where this fits

![Where 07.03 fits](figures/07.03-map.svg)

When an insert finds its leaf full, the B-tree splits the page in two and
sends a divider up to the parent (02.02); so far the cut has always gone
where the two halves come out the same size. This lesson adds one case in
front of that rule, for a table leaf whose new row goes after every row in
the tree. Nothing above the B-tree changes. Afterwards a table filled in
rowid order is as small as sqlite3 makes it, where before it was twice the
size: in 07.01 the benchmark's table took 2292 pages, half full, against
sqlite3's 1155.

## The idea

![A full leaf and an appended row: split in the middle, or keep the old cells together and start a page with the new row.](figures/07.03-splits.svg)

Insert rows with rowids 1, 2, 3, and so on. The last leaf fills up, and the
next row, bigger than every rowid in the tree, does not fit. A split in the
middle puts the older half of the cells on one page and the newer half, with
the new row, on another. The next rows go to the newer page, because their
rowids are bigger still; nothing will ever again be inserted into the older
page, which stays half full. Repeat that 250 times and the table takes twice
the pages it needs.

The fix is to recognise the append and cut at the end instead: all the old
cells stay together on one page, full, and the new row starts the next page
alone. The next rows fill that page, and the same thing happens again when
it is full. Every leaf but the last ends up as full as a page can be.

It only works because the case is so narrow. When the new row is the last
cell of the right-most leaf, the full page on the left holds exactly the
cells that were already on the page, so they fit, and no later row in rowid
order can ever belong there. Anywhere else neither is promised, so anywhere
else the split stays in the middle.

### append_split: where to cut a table leaf

Called by the split of 02.02 for a table leaf, before it computes the
middle cut. It gets the leaf's cells with the new one already in place, and
the path from the root down to the leaf. It returns where to cut for an
append, or -1 to let the split cut in the middle as before.

## How it works

### Writing append_split, step by step

The function is short, but each of its lines is a condition that took
thought, so here they are in the order one would arrive at them.

1. **Cut just before a new last cell.** The split hands over the page's
   cells with the new one already in place, at `newidx`. If it is the last,
   cutting just before it puts every old cell in the left part, exactly
   what the page held before, and the new one alone in the right; if not,
   the row went into the middle of the page, and -1 leaves it to the
   middle split.

   ```
   static int append_split(Cursor *c, int L, CellList *cl, int newidx)
   {
       if (newidx != cl->n - 1)
           return -1;
       ...
       return cl->n - 1;
   }
   ```

2. **Only on the right-most leaf of the whole tree.** On a leaf in the
   middle of the tree, rows can still arrive between its last row and the
   next leaf. The insert's path tells: at every level above the leaf it
   must have gone down the right-most child, so the index it took equals
   that page's cell count.

   ```
   for (int l = 0; l < L; l++) {
       Node n = node_get(c->pager, c->pgno[l]);
       if (c->idx[l] != n_ncells(&n))
           return -1;
   }
   ```

3. **Asked first, by the split of a table leaf.** The split keeps the last
   part on the page being split, where the parent already points for
   everything after its last divider, and puts the left parts on new pages.
   So the old cells move together to a new, full page, and the original
   page keeps the one new row and is where the next rows go.

   ```
   if (type == PAGE_TABLE_LEAF)
       m = append_split(c, L, cl, newidx);
   ```

The idea is not new: sqlite3 has the same special case, `balance_quick`,
linked below.

### Why it is built this way

<!-- verify: fact cmd="sqlite3 base.db \"SELECT count(*) || ' interior pages' FROM dbstat WHERE name = 't' AND pagetype = 'internal'\"" expect="5 interior pages" -->
<!-- verify: fact cmd="sqlite3 sq.db \"SELECT 'has ' || count(*) FROM dbstat WHERE name = 't' AND pagetype = 'internal'\"" expect="has 4" -->
**Only table leaves.** Index entries arrive in whatever order the indexed
values come, so for an index the append case is rare, and the split stays in
the middle; that is why the benchmark's index is still half empty (07.01).
Interior pages split in the middle too. They are one page in two hundred
here, and sqlite3's own append case is for table leaves only as well; its
interior pages come out fuller because it moves cells between neighbouring
pages instead. The benchmark's table has 5 interior pages where sqlite3's
has 4, and that is the one page of difference between the two tables.

**Two parts, always.** `split` can cut a page into more than two parts
(up to `MAX_PARTS`) when a few big cells leave no way to make two that
fit; an append split always makes two, since the left part fitted before.

## Break it

<!-- verify: patch file=src/btree.c
-    if (newidx != cl->n - 1)
-        return -1;
-->
Drop the first condition: delete the two lines
`if (newidx != cl->n - 1)` and `return -1;` at the top of `append_split`, so
that every split of the right-most leaf cuts before its last cell, then
`make`. Rows in rowid order come out as before. Now rows almost in order:
every tenth row arrives five rows late, with a value twice as long
(`late.py`):

A late row went into the middle of a full right-most leaf, and the cut
before the last cell put the old cells, minus the last, plus the new and
longer row on the left page: more than the page held before, and more than
it can hold. The engine as written takes all 20000 rows. When a late row is
the one that fills the leaf, it splits in the middle; 232 of its 411 splits
are append splits, and the leaves end up 64% full.

## Decide the boundary

This engine handles one pattern specially, rows appended in order, and
leaves every other insert order to the middle split, so pages filled in
random order end up around half to two thirds full. sqlite3 does the same
special case for appends, and on top of it rebalances: when a page
overflows it redistributes cells across the page and its neighbours, which
keeps pages close to full in any order, at the cost of a far more complex
split. And for an index created on existing rows, it avoids the question by
sorting the entries first and loading them in order. How much does your
file's size matter, and in what order do your keys arrive?
