# 01.03 Records: varints and serial types

A row is a handful of values of any type and any length; a page holds bytes.
This lesson packs a row into a short run of bytes, a **record**, in exactly
the format sqlite3 uses, and unpacks it again.

## Where this fits

![Where 01.03 fits](figures/01.03-map.svg)

Records sit between the rows the engine works with and the pages the pager
hands out. The B-tree of the next module will store each record inside a page
and find it again by its key; the executor of module 04 will build a record
for every row it inserts and take one apart for every row it reads. Below, a
record is just bytes in a page. After this lesson a row can be turned into
exactly the bytes sqlite3 stores for it, and those bytes back into the row.

## The idea

![The row (1, 'pear', 300, 0.75, NULL) on page 2, from xxd: a header of six small numbers, then the values back to back.](figures/01.03-record.svg)

How should the row `(1, 'pear', 300, 0.75, NULL)` be stored? Giving every
column a fixed width wastes space: 300 would take 8 bytes, and a text column
would need room for its longest value. Worse, in SQLite any column can hold
any type of value: a column declared `INTEGER` can still hold `'pear'`. So the
type has to be stored with each value, not just once for the table.

SQLite's answer is a record in two parts. The **header** lists one small
number per column, the **serial type**, which says both what the value is and
how many bytes it takes. The **body** holds the values themselves, back to
back, each in as few bytes as it needs. A NULL takes no body bytes at all, and
neither do the integers 0 and 1; 300 takes two; 'pear' takes four. The row
above is 20 bytes, and its 1 is not even among them. That column is declared
`INTEGER PRIMARY KEY`, which makes it the row's **rowid**, the number the
B-tree of module 02 files the row under and stores beside the record, so the
record holds a NULL in its place.

The numbers in a record's header are almost always small, but they must be
allowed to be large (a text of a million bytes has a serial type of two
million and some). So they are written as **varints**: seven bits of the
number per byte, most significant first, and the top bit of each byte says
whether another byte follows. Any number below 128 takes one byte. 300 takes
two, `82 2c`:

![Three varints from real cells: 5 takes one byte, 300 two, and -1, as a 64-bit pattern, all nine.](figures/01.03-varint.svg)

### Varints: `varint_get` and `varint_put`

These two read and write one varint. They are used wherever the file stores a
number that is usually small: in a record's header here, and in the next
module for the length and the rowid at the start of every cell.

### Serial types: `serial_type` and `serial_get`

`serial_type` chooses how a value will be stored, when a record is built.
`serial_get` turns a value's body bytes back into a value, when a record is
read. The two loops that walk a whole record, `record_build` and
`record_decode`, sit in the same file and call these for each column.

## How it works

### Writing `varint_get`, step by step

1. **Take seven bits from each byte, most significant first,** shifting what
   you have left by seven each time:

   ```
       u64 x = 0;
       for (int i = 0; i < 8; i++) {
           x = (x << 7) | (p[i] & 0x7f);
           ...
       }
   ```

2. **Stop at the first byte whose top bit is clear,** and return how many
   bytes that took. Callers need the length as much as the value: it is how
   they find the next field.

3. **If eight bytes all said "more", take the ninth whole.** That is how a
   full 64-bit number fits in nine bytes (the first decision below).

### Writing `varint_put`, step by step

1. **Cut the value into seven-bit groups, low end first, and copy them out
   in reverse,** so the most significant group lands first, as `varint_get`
   expects:

   ```
       u8 tmp[9];
       int n = 0;
       do {
           tmp[n++] = (u8)((v & 0x7f) | 0x80);
           v >>= 7;
       } while (v);
       ...
       for (int i = 0; i < n; i++)
           p[i] = tmp[n - 1 - i];
       return n;
   ```

   A `do ... while` loop rather than a `while` makes sure the value 0 still
   produces one byte, `00`.

2. **Clear the top bit of the group that will come last.** It was made first,
   so it is `tmp[0]` (the second decision below; Break it removes this line).

3. **Put the nine-byte case in front of the loop.** A value with any of its
   top eight bits set takes the odd path: the last byte gets the low eight
   bits, and the eight before it get seven bits each, every one with its top
   bit set.

### Writing `serial_type`, step by step

1. **The types with one answer.** NULL is 0 and a float is 7, whatever the
   value:

   ```
       switch (v->type) {
       case V_NULL:
           return 0;
       case V_REAL:
           return 7;
       ...
       }
   ```

   (sqlite3 makes one exception: in a column declared REAL it stores
   a float with nothing after the point, such as 2.0, as an integer, to save
   space. This engine reads that back as a float, in module 04, and writes
   floats as type 7 always.)
2. **Text and blobs carry their length.** Text of n bytes is 13 + 2n, a blob
   12 + 2n: odd for text, even for blobs, so the one number says both what
   the value is and how long it is.
3. **Integers: 0 and 1 first, then the narrowest width.** 8 and 9 need no
   body bytes; after them, try 1, 2, 3, 4 and 6 bytes in order and take the
   first range the value fits, with 8 bytes for the rest (the last decision
   below).

### Writing `serial_get`, step by step

1. **Start from an empty value, then the types with no body bytes:** 0 is
   NULL, 8 and 9 are the integers 0 and 1. The empty value means no field is
   left over from the last call.

   ```
       memset(v, 0, sizeof *v);
       if (type == 0) {
           v->type = V_NULL;
       } else if (type == 8 || type == 9) {
           v->type = V_INT;
           v->i = type - 8;
       ...
       }
   ```

2. **Integers in 1 to 8 bytes:** sign-extend the first byte, then shift in the
   rest (the third decision below).
3. **A float:** assemble the eight big-endian bytes into a 64-bit integer and
   `memcpy` it into a `double`. The bytes are big-endian in the file whatever
   the CPU is, and `memcpy` is the portable way to reinterpret bits.

   ```
           for (int k = 0; k < 8; k++)
               bits = (bits << 8) | p[k];
           v->type = V_REAL;
           memcpy(&v->r, &bits, sizeof v->r);
   ```

4. **Text and blobs: point, do not copy.** The value points into the record,
   which is inside a page, and gets the length from `serial_size`; odd types
   are text. Copying every string out of every row would cost more than
   reading it.

### Writing `record_build` and `record_decode`, step by step

These two, beside the four above in `src/record.c`, turn a whole row into a
record and back. They are what the B-tree and the executor will call.

1. **Building: one pass to choose and measure, one to write.** For each
   value, its serial type, the bytes that type takes as a varint in the
   header, and its size in the body; then the header length, every serial
   type and every body, written in one go:

   ```
       for (int i = 0; i < n; i++) {
           t[i] = serial_type(&vals[i]);
           hdr += (u64)varint_len(t[i]);
           body += serial_size(t[i]);
       }
       ...
       p += varint_put(p, hlen);
       for (int i = 0; i < n; i++)
           p += varint_put(p, t[i]);
       ...
   ```

   The first pass means the record's size is known, and its space reserved
   once, before a byte is written.
2. **Building: the header's length counts itself.** The first varint of the
   header is the header's own length, including that varint; it is there so
   a reader knows where the body starts before decoding a single serial
   type. Its size depends on its value. Start by assuming one byte and grow it while the
   total needs a longer varint:

   ```
       int lenlen = 1;
       while (varint_len(hdr + (u64)lenlen) > lenlen)
           lenlen++;
   ```

   With 127 bytes of serial types, a one-byte length would make the header
   128 bytes, and 128 needs two bytes; with a two-byte length it is 129,
   which fits in two.
3. **Decoding: walk the header with a second position in the body.** The
   body of value k starts where the sizes of values 0 to k - 1 end, so the
   decoder keeps two positions, one in the header and one in the body, and
   moves both together.

   ```
       while (h < hlen) {
           u64 type;
           h += (u32)varint_get(rec + h, &type);
           u32 size = serial_size((u32)type);
   ```

4. **Decoding: refuse what cannot be.** A header longer than the record or
   shorter than its own length varint, the reserved types 10 and 11, and a
   value that would run past the end of the record can only come from a
   damaged page, so the record is refused instead of read past its end.
5. **Decoding: fill as many values as asked, count them all.** The caller
   passes room for `max` values and gets back the number the record really
   has; with `max` 0 it only counts. A row written before a column was added
   simply has fewer values, and the executor of module 04 fills in each
   missing one with its column's DEFAULT, or NULL if it has none.

### Four decisions in this code

**The ninth byte is different.** Seven bits a byte would need ten bytes for a
64-bit number. Instead, a varint stops at nine: the first eight bytes carry
seven bits each and the ninth carries all eight of its bits, 56 + 8 = 64.
`varint_get` reads at most eight bytes the ordinary way and treats the ninth
as a whole byte:

```
    *v = (x << 8) | p[8];
    return 9;
```

and `varint_put` takes the nine-byte path for any value with one of its top
eight bits set. A negative number, read as unsigned, always has them set, so
`-1` costs nine bytes: the format is built for numbers that are small and not
negative, which rowids and lengths almost always are.

**One line ends every varint.** `varint_put` cuts the value into seven-bit
groups from the low end, sets the top bit on every group, and then clears it
on the group that will come last:

```
    tmp[0] &= 0x7f;              /* the last byte, written first here, ends it */
```

The groups are produced least significant first, so the last byte of the
varint is the first one made; the loop after this line copies them out in
the other order. A reader stops at the first byte whose top bit is clear, so
this line is all that tells it where the number ends.

**Decoding an integer means restoring its sign.** Integers in the body are
big-endian two's complement in 1, 2, 3, 4, 6 or 8 bytes. `serial_get` starts
from the first byte as a signed value and shifts in the rest:

```
        u64 x = (u64)(i64)(signed char)p[0];    /* sign-extend the first byte */
        for (u32 k = 1; k < n; k++)
            x = (x << 8) | p[k];
```

Without the sign extension, `-2` stored in one byte as `fe` would come back as
254. Floats are assembled the same way into 64 bits and then copied into a
`double` with `memcpy`, because the file is big-endian whatever the CPU is.
Text and blobs are not copied at all: the value points into the page, which
is one more reason the cache of 01.02 never evicts a page in the middle of a
row.

**`serial_type` picks the smallest type that holds the value.** The integers
0 and 1 get types 8 and 9, which need no body bytes; any other integer gets
the narrowest of 1 to 6 that holds it. These are all the serial types:

| serial type | meaning | body bytes |
|---|---|---|
| 0 | NULL | 0 |
| 1, 2, 3, 4, 5, 6 | integer | 1, 2, 3, 4, 6, 8 |
| 7 | float, IEEE 754 | 8 |
| 8, 9 | the integer 0, the integer 1 | 0 |
| 10, 11 | reserved | - |
| even, 12 and up | blob of (N - 12) / 2 bytes | (N - 12) / 2 |
| odd, 13 and up | text of (N - 13) / 2 bytes | (N - 13) / 2 |

## Decide the boundary

SQLite stores the type with every value, so any column can hold anything and
no value takes more room than it needs. The price is that column k has no
fixed position: to read the fifth column, the engine walks four serial types
in the header and adds up their sizes. Most other databases do the opposite:
the catalog fixes each column's type, a fixed-width value sits at the same
offset in every row, and one bit per column in a small bitmap marks the
NULLs. Their rows are bigger, but such a column is one addition away. Which costs
more in your workload, bytes on disk or the walk through the header?

## Break it

Delete the line that ends every varint, `tmp[0] &= 0x7f;`, in `varint_put`
(`build/at/db/01.03/src/record.c`), rebuild, and build the pear row again:

<!-- verify: patch file=src/record.c
-    tmp[0] &= 0x7f;              /* the last byte, written first here, ends it */
-->
<!-- verify: session -->
```
$ make -s
$ ./db row.db .exit
86 80 95 82 87 80 70 65 61 72 01 2c 3f e8 00 00 00 00 00 00
record_decode: -1
```

![The pear row's record, written correctly and with the broken varint_put. Every header byte gains a top bit, and the first varint runs on into the body.](figures/01.03-run-on.svg)

The body is untouched: its values are written whole, not as varints. Every
byte of the header gained its top bit, so each one now says "more follows".
A reader starts on the header's length, `86`, and keeps going through the
whole header and into the body, until `70`, the "p" of "pear", is the first
byte with its top bit clear. The length it reads that way is far longer than
the 20-byte record, so `record_decode` refuses the record. sqlite3 reads
varints the same way: put those six header bytes over the good ones in its
own file, at byte 8172, and ask it for the row:

<!-- verify: session -->
```
$ printf '\x86\x80\x95\x82\x87\x80' | dd of=row.db bs=1 seek=8172 conv=notrunc 2>/dev/null
$ sqlite3 row.db "SELECT * FROM p"
Error in 2nd command line argument: database disk image is malformed
```
