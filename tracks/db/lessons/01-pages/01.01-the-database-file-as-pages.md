# 01.01 The database file as pages

The bottom layer of the engine is one ordinary file. This lesson cuts it into
numbered pages of 4096 bytes, moves it between disk and memory a whole page at
a time, and gives a new file the 100 bytes that make it a SQLite database.

## Where this fits

![Where 01.01 fits](figures/01.01-map.svg)

The file is the bottom of the picture, and the pager is the part of the
engine that reads and writes it. Everything above will ask for "page 2" or "page 812"
and get back that page's bytes; nothing above ever deals in byte offsets.
Below the pager is the operating system's file, which can read or write any
number of bytes anywhere. After this lesson the engine has what it needs to
turn an empty file into a database that sqlite3 recognises and to read any
page of one that sqlite3 wrote, and opening a file already checks that it is
a database.

## The idea

![demo.db after one CREATE TABLE and one INSERT: two pages. Page 1 begins with the 100-byte database header; in each page, rows fill from the end.](figures/01.01-pages.svg)

A table can hold more rows than fit in memory, and changing one row must not
mean rewriting the whole file. So the engine reads and writes the file in
pieces, and the question is what kind of pieces.

The answer here, and in SQLite, is pages: the file is a row of equal-sized
blocks, numbered from 1. Fixed size buys three things at once. A page is found
by arithmetic, with no table of contents: page n starts at byte
(n - 1) x 4096. A page number is a stable address, so a structure inside the
file can point from one page to another, which is exactly how the B-tree in
module 02 will hold itself together. And a page that is no longer needed can
be reused for anything, because every page fits every hole. Numbering from 1
leaves 0 free to mean "no page" wherever the file stores a page number.

4096 bytes is not a magic number. It matches the 4 KB block that most drives
and file systems work in, so one page is one read. sqlite3 has used it as its
default since 2016, and a file can choose any power of two from 512 to 65536
when it is created.

Page 1 is the one page with a job of its own. Its first 100 bytes are the
**database header**: the string "SQLite format 3", the page size, the format's
version numbers, and two counts kept current at every commit, how many times
the file has been changed and how many pages it has. Any program can read
those 100 bytes and know what it is looking at. The rest of page 1 is an
ordinary page, the first page of the catalog, the table of all tables.

### Reading and writing a page: `read_page` and `write_page`

`read_page` and `write_page` in `src/pager.c` are the engine's door to the
file: every ordinary read or write of a page goes through them. Everything
else will ask the pager for a page by number; the next lesson puts a cache in
front of these two, so most requests never reach them. They take a page
number and a buffer of exactly one page, and they always move the whole page.

### The header: `header_init`

An empty file is a valid empty database: zero pages. The first statement that
writes anything will call `header_init`, which makes page 1 in memory: the
header, and after it, in the same page, an empty catalog. It reaches the file
at the next commit, with everything else that changed.

### What comes with it

The rest of `pager.c` arrives already written, and later lessons explain it.
`pager_get` and `pager_write` are the door everything above uses: the first
returns a page's bytes, the second marks the page changed ("dirty") and keeps
it in memory until a commit. `pager_commit` writes the dirty pages, sorted by
page number so the file is written front to back, and stamps the commit
fields of the header; with no journal yet (module 06) a crash halfway through
leaves half a commit in the file, and the crash points are there to show
that. The statement savepoint lets one failed statement be undone without
the rest of its transaction. `util.c` holds the plumbing every file
shares: error messages, the counters `DB_STATS=1` prints, memory helpers and
growable byte buffers. `db.h` declares every module's types and the
big-endian `get2`/`put2`/`get4`/`put4` the file format is written in. And
`main.c` is the shell, cut down: it opens the file and refuses every
statement, and until the tokenizer arrives in 03.01 it takes the first `;` as
the end of a statement.

## How it works

### Writing `read_page`, step by step

1. **Find the page and read it until the whole page is in.** Page n begins
   (n - 1) page sizes into the file, because the format counts pages from 1:

   ```
       off_t off = (off_t)(pgno - 1) * p->page_size;
       ssize_t got = 0;
       while (got < (ssize_t)p->page_size) {
           ssize_t n = pread(p->fd, buf + got, p->page_size - (size_t)got, off + got);
           ...
           got += n;
       }
   ```

   `pread` takes the offset as an argument, so nothing depends on where an
   earlier call left the file position. It may return fewer bytes than asked
   for, when a signal arrives partway through, so the loop goes on from where
   it stopped. The cast to `off_t` is the first decision below.

2. **Retry an interruption; stop on anything else.** `EINTR` only means a
   signal came in, so the loop goes round again. Any other error is a disk or
   file the engine cannot trust any more, and `fatal` stops the process
   rather than carry on with a buffer of garbage.

3. **Stop at the end of the file and zero the rest.** `pread` returning 0
   means the file has no more bytes; the rest of the page becomes zeroes (the
   second decision below).

`write_page` is the same steps in the mirror image: the same offset, `pwrite`
in a loop until every byte is written, the same `EINTR` retry, its own
counter. It needs no end-of-file case, because writing past the end is how
the file grows: that is how a database gets its page 2.

### Writing `header_init`, step by step

1. **Make page 1 exist and say what the file is.** The page count goes from
   0 to 1 and the pager hands back page 1's bytes for writing: all zeroes,
   and marked as changed, so the next commit will write it. Then the 16
   bytes "SQLite format 3" with its closing 0, and the page size:

   ```
       p->npages = 1;
       u8 *d = pager_write(p, 1);
       ...
       memcpy(d, "SQLite format 3", 16);
       put2(d + 16, p->page_size == 65536 ? 1 : p->page_size);
   ```

   The page size field has two bytes, so 65536 does not fit and is written
   as 1, as the format says.

2. **Write the values the format fixes.** The format versions, the payload
   fractions, the schema format, the text encoding (1, UTF-8) and the version
   stamp: the comment in the code lists them by offset. None of these is a
   choice; copy them. sqlite3 refuses a file whose fractions differ, and so
   does this engine when it opens one.

3. **Leave the three commit fields.** The change counter, page count and
   version-valid-for are written by every commit, together (the third decision
   below), so there is nothing to put there yet.

4. **Make the rest of page 1 an empty table.** Page 1 is also the first page
   of the catalog, the table that lists every table, so after the 100 bytes
   comes an empty table page: type 13, no cells, and the area where rows will
   go starting at the very end of the page. Module 02 explains each of these
   fields; here they only have to describe "a table with no rows".

   ```
       u8 *h = d + 100;
       h[0] = PAGE_TABLE_LEAF;
       put2(h + 1, 0);
       put2(h + 3, 0);
       put2(h + 5, p->page_size == 65536 ? 0 : p->page_size);
   ```

### Writing the open: `pager_open` and `read_header`, step by step

These two come with the lesson already written, and they are the other half
of the header: they turn a file name into a pager that knows the page size
and the number of pages. They are also the only part of the pager the shell
runs at this lesson.

1. **Open the file, creating it if it is missing, and read its header.**

   ```
       p->fd = open(path, O_RDWR | O_CREAT, 0644);
       if (p->fd < 0)
           return err("cannot open %s: %s", path, strerror(errno));
       if (read_header(p) < 0)
           return -1;
   ```

   `O_CREAT` makes a name that does not exist into an empty file, and an
   empty file is an empty database. That is why `./db learn.db` works on a
   new name.

2. **An empty file needs no header.** With zero bytes there is nothing to
   check: the page size comes from `DB_PAGE_SIZE` or defaults to 4096, the
   page count is 0, and `header_init` will make page 1 at the first write.

3. **Otherwise refuse anything that is not a database.** Read the first 100
   bytes, with a `pread` of their own rather than `read_page`, because the
   page size is one of the things in them; then check them in order: the
   magic string, a page size that is a power of two from 512 to 65536, a
   format version this engine knows, the fixed payload fractions, and UTF-8
   text. Each failure is a clear message,
   like the `file is not a database: Makefile` of 00.01, instead of a crash
   later on a page that was never a page.

   ```
       if (memcmp(h, "SQLite format 3", 16) != 0)
           return err("file is not a database: %s", p->path);
   ```

4. **Work out the page count.** Use the header's count when it can be
   trusted, else divide the file size by the page size (the third decision
   below).

5. **Later lessons add to it.** The next lesson builds its empty cache
   here, and module 06 makes it run crash recovery before the header is
   read, because a file left mid-commit by a crash must be repaired before
   anyone believes its header.

### Three decisions worth slowing down for

**The offset is computed in 64 bits.** The heart of `read_page` is one line:

```
    off_t off = (off_t)(pgno - 1) * p->page_size;
```

Page numbers and the page size are 32-bit numbers, and so is their product
unless one of them is widened first. Without the cast, page 1,048,577 of a
4096-byte-page file, the first page past 4 GiB, would wrap around and be read
from the start of the file. With it, the file can grow as far as the format
allows.

**A read always fills the whole page, with zeroes if it must.** `pread` may
return fewer bytes than asked for, so `read_page` loops until it has the
whole page. If the file ends first, the rest of the buffer is zeroed rather
than left holding whatever was there before:

```
        if (n == 0)
            break;
        got += n;
    }
    memset(buf + got, 0, p->page_size - (size_t)got);
```

A missing page then looks like an empty one, and an empty page is not a valid
B-tree page (its type byte, the first byte of its own header, is 0), so once
the B-tree of module 02 reads pages, a file cut short is reported as damaged
instead of read as data.

**`header_init` leaves three fields alone.** The change counter (byte 24), the
page count (28) and the "version-valid-for" number (92) are written at every
commit, all three together. The pairing matters when a file is opened:
`read_header` trusts the page count only if version-valid-for equals the
change counter. An old SQLite that did not know about the page count field
could change the file without updating it; it would not update the copy of
the counter at 92 either, and the mismatch tells the engine to count pages
from the file's size instead. The **invariant** both sides keep is that the
file is a whole number of pages and the header's count says how many.

The other bytes `header_init` writes are either fixed by the format or
describe the file: its page size, its text encoding, and the SQLite version
whose format it follows (3046000, 3.46.0). Here are the first 112 bytes of
`demo.db` as this engine writes them once `CREATE TABLE` and `INSERT` can
run, one box per byte; they differ from sqlite3's above only in that version,
at byte 96:

![The database header of demo.db as xxd showed it: the bytes header_init sets, the three a commit rewrites, and page 1's own header starting at byte 100.](figures/01.01-header.svg)

## Decide the boundary

This engine, like SQLite, uses one page size for the whole file, chosen once
when the file is made. Bigger pages mean fewer pages to read for a scan and
shallower B-trees; smaller pages mean less to write, and to journal, when one
row changes. Another design could use variable-sized blocks and pack every
row tightly, and pay with free space that comes in odd sizes; the CMU notes
below give that as the reason most databases use fixed pages. The question that decides the size: will this file
mostly be read in long runs, or changed a row at a time?

## Break it

Forget that pages count from 1. Nothing at this lesson reads a page, so this
experiment uses the first build that does: 03.03's, where opening a database
reads the catalog on page 1. Its `read_page` is this lesson's, unchanged.
From the repository root, write that project out and work in it:

<!-- verify: session -->
```
$ ./learn files db --at 03.03
Wrote db as it stands at 03.03 (The schema: CREATE TABLE and the catalog) to build/at/db/03.03/
$ cd build/at/db/03.03
```

In `src/pager.c`, function `read_page`, change the offset to

<!-- verify: patch file=src/pager.c at=03.03
 void read_page(Pager *p, u32 pgno, u8 *buf)
 {
-    off_t off = (off_t)(pgno - 1) * p->page_size;

-->
```
    off_t off = (off_t)pgno * p->page_size;
```

then build, and open a file sqlite3 made:

<!-- verify: session -->
```
$ make -s
$ sqlite3 theirs.db "CREATE TABLE t(a); INSERT INTO t VALUES ('hello');"
$ ./db theirs.db .tables
db: fatal: database is corrupt: page 1 is not a b-tree page (type 0)
```

Page 1 is now read from where page 2 is. The engine looks for page 1's own
header at byte 100 of what it read, and in page 2 that byte is a zero.

![The right formula reads page 1 from byte 0; the broken one reads page 2's bytes and finds a 0 where the page type should be.](figures/01.01-off-by-one.svg)

The engine's own file is stranger:

<!-- verify: session -->
```
$ printf "CREATE TABLE t(a);\n.tables\n" | ./db ours.db
t
$ ./db ours.db .tables
db: fatal: database is corrupt: page 1 is not a b-tree page (type 0)
$ sqlite3 -list ours.db "PRAGMA integrity_check; SELECT name FROM sqlite_schema"
ok
t
```

The first run works because it never reads the file: it made page 1 itself,
and the cache of 01.02 still holds it after the commit. `write_page` is
unchanged, so the file is perfect, as sqlite3 confirms; only reading it back
is wrong, and that shows only in the next process. A bug in the bottom layer
can hide for as long as nothing goes back to the disk.
