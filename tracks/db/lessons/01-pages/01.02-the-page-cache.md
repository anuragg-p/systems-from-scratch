# 01.02 The page cache

Reading a page from the file costs a trip to the operating system, and a
database asks for the same few pages again and again. This lesson keeps
recently used pages in memory, finds them by number, and decides which ones
to let go when memory runs short.

## Where this fits

![Where 01.02 fits](figures/01.02-map.svg)

The cache lives inside the pager, between everything that asks for pages and
the file reads and writes of the last lesson. Above it, the B-tree will ask
for the same pages over and over: the top page of a table is needed by every
single lookup in it. Below it, the file is reached only when a page is not
already in memory. After this lesson a page read once is served from memory
until room runs out, and a page that has been changed waits in memory until
its transaction commits.

## The idea

![The cache: a hash table finds a page by number, a list orders the clean pages by last use, and changed pages are kept apart.](figures/01.02-cache.svg)

Take a table of 30,000 rows as sqlite3 stores it. With the catalog's page 1
the file has 380 pages: one at the top of the table that points to the
others, and 378 at the bottom that hold the rows. Looking up one row reads two of them, the top page
and one bottom page. Two thousand lookups ask for four thousand pages, and
without a cache every request is a read from the file. With one, each of the
380 pages is read once, and every request after that is answered from
memory.

A cache like this needs three things. It must find a page by its number
quickly, so it keeps a **hash table** of the pages it holds. It must know
which page to give up when it is full, so it keeps the pages on a list in the
order they were last used and gives up the one at the far end, the **least
recently used**: the page nobody has needed for longest is the best guess for
the one nobody will need next. And it must never give up a page that holds a
change the file does not have yet. Such a page is **dirty**; it comes off the
list as soon as it is changed and goes back on, clean, once the commit has
written it.

![A page's life: read into the cache on a miss, moved to the front on every hit, taken off the list while it is dirty, and dropped from the cold end when the cache is over its size.](figures/01.02-life.svg)

### Finding a page: `page_get`

Every page request in the engine ends in `page_get`. On a hit it moves the
page to the front of the list and returns it. On a miss it reads the page
from the file, puts it at the front, and returns it. It never evicts anything,
for a reason that comes in How it works.

### Letting pages go: `pager_shrink`

`pager_shrink` is where pages leave. It drops clean pages from the cold end
of the list until no more than `cache_max` of them remain: 500 pages by
default, 2 MB, the same as sqlite3's default cache, or whatever
`DB_CACHE_PAGES` says.

The rest of what this lesson adds is small: `pager_open` now sets up the
empty table and list, `pager_close` frees them, a page that becomes dirty
leaves the list (and returns to it at commit), and `pager_drop`, for 02.05,
forgets a page that has been freed.

## How it works

### Writing `page_get`, step by step

1. **A lookup, and a read on a miss.** Walk the chain of pages in the page's
   bucket; on a hit, return it. On a miss, make a page, fill it from the file
   and put it in its bucket:

   ```
       for (pg = p->hash[hash_of(p, pgno)]; pg; pg = pg->hnext) {
           if (pg->pgno == pgno) {
               ...
               return pg;
           }
       }
       pg = xmalloc(sizeof *pg + p->page_size);
       ...
       fetch_page(p, pgno, pg->data);
       ...
       return pg;
   ```

   Pages are numbered in a row, so a chain usually holds one page or two.
   The bookkeeping and the page's bytes sit in one allocation, the bytes
   right after the struct: one `malloc` per page, one `free` when it goes.

2. **Refuse a page that cannot exist.** Page 0 means "no page" (01.01) and a
   number past the end of the database means some layer above followed a
   pointer it should not have. Stopping here, with the number in the message,
   catches that bug where it shows instead of reading garbage.

   ```
       if (pgno == 0 || pgno > p->npages)
           fatal("page %u is out of range (the database has %u pages)", pgno, p->npages);
   ```

3. **On a hit, move the page to the front, if it is on the list.** That is
   what keeps the list in order of last use. The `if` matters: a dirty page
   is not on the list, its links are null, and unlinking it would crash.

   ```
           if (pg->prev) {
               lru_unlink(pg);
               lru_push_front(p, pg);
           }
   ```

4. **On a miss, link the page in, and make room in the table, not in the
   cache.** The new page goes at the front of the list. If the table holds
   twice as many pages as it has buckets, it doubles first. Nothing is
   evicted here; the first decision below says why.

5. **Fill it without a read when the file has nothing.** `fetch_page` usually
   calls `read_page`, but a page that this transaction added at the end of
   the database has nothing committed in the file, so it starts as zeroes;
   and once module 06 adds a write-ahead log, a newer copy of a page may
   live there instead.

### Writing `pager_shrink`, step by step

1. **Drop the coldest page while there are too many.** The list is a ring
   around the sentinel `p->lru`, a dummy page that is never removed, so
   adding and unlinking need no checks for an empty list, and the least
   recently used page is `p->lru.prev`: no searching.

   ```
       while (p->ncached - p->ndirty > p->cache_max && p->lru.prev != &p->lru) {
           Page *pg = p->lru.prev;
           lru_unlink(pg);
           ...
           free(pg);
           p->ncached--;
   ```

2. **Count only clean pages, and stop when the list is empty.** With every
   page dirty there is nothing it may evict. Both halves of the condition
   are the second decision below.

3. **Take it out of its bucket too.** Forgetting the bucket would leave the
   hash table pointing at freed memory, and the next lookup of that page
   would "hit" it: one line, `hash_remove(p, pg)`, before the `free`.

### Three decisions that protect something

**Eviction waits for a safe moment.** Code that asks for a page gets a
pointer to the page's bytes and keeps using it: splitting a B-tree page works on
several pages at once, and a row's text is read straight out of the page it
lives in. If `page_get` freed some other page to make room, any of those
pointers could suddenly point at freed memory. So `page_get` only ever adds
pages, and `pager_shrink` runs where nobody holds a pointer: from module 04
on, before every statement and every 256 rows of a long SELECT. The price is
that the cache can briefly hold more than `cache_max`. In the 10-page run
above, each lookup took the cache to 11 pages and the shrink after it back to
10: 2,001 pages read, 1,991 evicted, 10 left at the end.

**Dirty pages do not count, and cannot be evicted.** The loop in
`pager_shrink` compares clean pages, not all pages, with the limit:

```
    while (p->ncached - p->ndirty > p->cache_max && p->lru.prev != &p->lru) {
```

and it only ever looks at the list, which dirty pages are not on. In this
engine the database file is written only at COMMIT, so a dirty page is the
only copy of its change; evicting it would lose the change. The **invariant**
is that every page on the list is clean, its bytes the same as the file's, so
dropping one costs a re-read at worst. A big transaction therefore stays in
memory however small the cache, every page it changes waiting for COMMIT.

**The hash table grows, and its hash is simpler than it looks.** Because dirty
pages are not limited by `cache_max`, the number of cached pages has no fixed
bound, so `page_get` doubles the table (`hash_grow`) once it holds twice as
many pages as buckets. The bucket is `(pgno * 2654435761) & (nhash - 1)`.
Knuth's multiplicative hash takes the high bits of that product; keeping the
low bits instead, as here, leaves the multiply with no say in which pages
share a bucket: two pages share one exactly when their numbers differ by a
multiple of the table size, as they would without it. It does no harm,
because page numbers, which run 1, 2, 3 and so on, already spread as evenly
as numbers can: the 380 pages of `look.db` land in 380 of the 1,024 buckets
the table starts with.

## Decide the boundary

This engine keeps every dirty page in memory until COMMIT. That makes
ROLLBACK free, because the file never saw the change, and it means the file
only ever holds committed data, which module 06 builds on. The cost is that
a transaction must fit in memory. sqlite3 chooses the other way: when its cache
fills up in the middle of a transaction, it **spills** dirty pages into the
database file, after saving the originals in its journal, and pays with more
writes and a lock on the file held from that moment on. Should a transaction
be limited by memory, or by disk?

## Break it

Make the list first-in, first-out: on a hit, leave the page where it is. In
`build/at/db/01.02/src/pager.c`, function `page_get`, delete the four lines
that move a hit to the front:

rebuild, and run the 2,000 lookups with 10 pages again:

<!-- verify: session

-->
```
$ make -s
$ DB_STATS=1 DB_CACHE_PAGES=10 ./db look.db .exit
stats: pages read 2200, cache hits 1800, cache misses 2200, evictions 2190, ...
```

199 more reads than before, one for every ten lookups. Every lookup uses the
top page, but first-in, first-out does not care how often a page is used,
only when it arrived. Page 2 sits where it was first read while ten newer
pages pile in in front of it, so every ten lookups the most-used page in the
table drops off the end and has to be read again.
