# 08.07 UNIQUE: a constraint is an index lookup

A UNIQUE column promises that no two rows hold the same value in it. The
engine keeps that promise the way SQLite does: with an index it makes for
itself, and one lookup in that index before every write.

## Where this fits

![Where 08.07 fits](figures/08.07-map.svg)

A constraint sits where the statements of module 04 meet the indexes of
module 05. CREATE TABLE now makes indexes as well as a table, and records
them in the catalog; INSERT and UPDATE ask each of them one question before
they change anything. Below that nothing changes: the B-trees, the pages
and the journal work as they did. After this lesson a table can declare
UNIQUE columns and a PRIMARY KEY that is not the rowid, and the tables
sqlite3 made with them, which the engine could only read until now, can be
written.

## The idea

<!-- verify: mention names="users(id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT)" outside reason="the example table as SQL, not a function of the project" -->
Take a table of users,
`users(id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT)`. A login
finds the account by its email, so two rows holding `ada@example.com` are
two accounts answering to one address, and nothing says which is meant.

An application can try to prevent that itself: SELECT the email, and
INSERT only if nothing came back. That costs a scan, because without an
index on email the SELECT reads every row (05.01 counted 496 pages to find
one). And it is still not safe: the SELECT and the INSERT are two
statements, and between them another program can insert the same email.
Both looked, both found nothing, both inserted. The check has to be part of
the write, so it belongs in the database.

The structure that answers "is this value here?" in a few page reads
already exists: an index on email, whose entries are `(email, rowid)`
sorted by email (05.01). A UNIQUE constraint is that index plus one rule.
Before a row is written, look its email up. If an entry with that email
belongs to another row, refuse the write and write nothing; otherwise
write the row and its entries exactly as before.

![Two inserts into users. A new email: the lookup finds nothing, then the table and the index are written. An email already there: the lookup finds its entry, nothing is written, and the statement fails.](figures/08.07-check.svg)

With Ada in row 1, inserting `(2, 'brook@example.com', 'Brook')` seeks
`brook@example.com`, finds no entry with it, and writes the row and the
entry `('brook@example.com', 2)`. Inserting `(3, 'ada@example.com', 'Chen')`
lands on `('ada@example.com', 1)`: the same email, another row. The
statement fails with sqlite3's words,
`UNIQUE constraint failed: users.email`, and neither tree changes.

Nothing in the index says it is unique. Its entries are the bytes of any
index, the key and then the rowid:

![An entry of the unique index on email beside an entry of an ordinary index: the same bytes, the key and then the rowid.](figures/08.07-entry.svg)

Uniqueness is a rule kept on every write, not a format. sqlite3 learns it
from the SQL alone: the word UNIQUE in a CREATE TABLE, or a CREATE UNIQUE
INDEX, which makes the same kind of index by hand.

### The index nobody created

Nobody types CREATE INDEX for the index on email: the table's definition
implies it. When a CREATE TABLE runs, sqlite3 makes a unique index for each
UNIQUE constraint, and one for a PRIMARY KEY that is not the rowid. Each
gets a row in sqlite_schema with its root page like any index, but its SQL
is NULL and its name follows a fixed rule, `sqlite_autoindex_<table>_<n>`,
n counting the indexes made for that table so far. That is an **automatic
index**. `id INTEGER PRIMARY KEY` gets none: it is the rowid, the table's
own B-tree is sorted by it, and `insert_row` has checked it with a seek
since 04.01. So the index on email is number 1.

![The rows of sqlite_schema for users: the table on page 2, and sqlite_autoindex_users_1 on page 3 with no SQL.](figures/08.07-schema.svg)

### auto_indexes: an index for each constraint

Each time the catalog builds a table from its CREATE TABLE text, when the
statement runs and whenever the file is opened, `auto_indexes` walks the
table's UNIQUE and PRIMARY KEY constraints in the order written and makes
an index, under sqlite3's name, for each one that needs it. CREATE TABLE
then writes a row with a fresh root page for each; loading the catalog
finds that root page in the row of the same name.

### unique_taken: is this value taken?

The lookup itself. Given an index, a row about to be written and that row's
rowid (its old one, for an UPDATE), it answers whether another row already
holds the same values in the index's columns. `check_unique` asks it about
every unique index of the table before INSERT or UPDATE writes anything.

## Run it

`./learn run db --at 08.07` builds the engine as it stands at this lesson in
build/at/db/08.07/ and opens its shell there (`.quit` leaves it). Run what
follows in that directory. Make the table and read the catalog back, with
our engine and with sqlite3:

<!-- verify: session cwd=project -->
```
$ ./db users.db "CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT)"
$ ./db users.db "SELECT type, name, rootpage, typeof(sql) FROM sqlite_schema"
table|users|2|text
index|sqlite_autoindex_users_1|3|null
$ sqlite3 -list users.db "SELECT name, rootpage, quote(sql) FROM sqlite_schema; PRAGMA index_list(users);"
users|2|'CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT)'
sqlite_autoindex_users_1|3|NULL
0|sqlite_autoindex_users_1|1|u|0
```

One CREATE TABLE, two rows: the table on page 2, its automatic index on
page 3 with NULL for SQL. sqlite3 works out from the CREATE TABLE text which
index the constraint needs and what it is called, finds the row of that
name, and reports the index unique (the `1`) and made for a UNIQUE
constraint (the `u`). Now two users, then the first one's email again:

<!-- verify: session cwd=project -->
```
$ ./db users.db "INSERT INTO users VALUES (1, 'ada@example.com', 'Ada'), (2, 'brook@example.com', 'Brook')"
$ ./db users.db "INSERT INTO users VALUES (3, 'ada@example.com', 'Chen')"
Error: UNIQUE constraint failed: users.email
$ sqlite3 users.db "INSERT INTO users VALUES (3, 'ada@example.com', 'Chen')"
Error in 2nd command line argument: UNIQUE constraint failed: users.email
```

sqlite3 reads the constraint from the file our engine wrote and refuses
the same row in the same words. Now the same two rows in a table with no
constraint and an ordinary index on email:

<!-- verify: session cwd=project -->
```
$ ./db plain.db "CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT, name TEXT); CREATE INDEX users_email ON users(email)"
$ ./db plain.db "INSERT INTO users VALUES (1, 'ada@example.com', 'Ada'), (2, 'brook@example.com', 'Brook')"
$ cmp users.db plain.db 4096 4096 && echo same from page 2 on
same from page 2 on
```

Given two offsets, `cmp` compares the files from there to the end. The
table on page 2 and the index on page 3 are the same bytes in both, and the
refused inserts left no trace. Only page 1 differs: one CREATE TABLE says
UNIQUE, and the other file has a CREATE INDEX.

Two users with no email yet, then two UPDATEs:

<!-- verify: session cwd=project -->
```
$ ./db users.db "INSERT INTO users VALUES (3, NULL, 'Chen'), (4, NULL, 'Dee')"
$ ./db users.db "UPDATE users SET email = 'ada@example.com' WHERE id = 2"
Error: UNIQUE constraint failed: users.email
$ ./db users.db "UPDATE users SET id = 10 WHERE id = 1"
$ ./db users.db "SELECT * FROM users"
2|brook@example.com|Brook
3||Chen
4||Dee
10|ada@example.com|Ada
```

Both NULLs go in. NULL means "no value here", and one missing value is not
equal to another, so a NULL never conflicts, however many there are; in a
constraint over several columns, one NULL among them is enough. (sqlite3
applies the rule to a PRIMARY KEY that is not the rowid too, so such a key
accepts NULLs, a quirk its documentation owns up to.)

Giving Brook Ada's email is refused like an INSERT. Moving Ada to rowid 10
is not, though it is checked: her entry changes from
`('ada@example.com', 1)` to `('ada@example.com', 10)`, and the lookup for
her email does find an entry, her own, the one this UPDATE replaces.

A statement that writes several rows can fail on its last one. Here Gus
repeats Brook's email:

<!-- verify: session cwd=project -->
```
$ ./db users.db "INSERT INTO users VALUES (5, 'eve@example.com', 'Eve'), (6, 'fay@example.com', 'Fay'), (7, 'brook@example.com', 'Gus')"
Error: UNIQUE constraint failed: users.email
$ ./db users.db "SELECT id, name FROM users"
2|Brook
3|Chen
4|Dee
10|Ada
```

Eve and Fay were written before Gus was checked, and they are gone: the
statement is undone whole. Inside BEGIN the same failure undoes that
statement only, and the transaction goes on. Open the shell on the file,
`./db users.db`:

<!-- verify: session run="./db users.db" cwd=project -->
```
db> BEGIN;
db> INSERT INTO users VALUES (5, 'eve@example.com', 'Eve');
db> INSERT INTO users VALUES (6, 'fay@example.com', 'Fay'), (7, 'brook@example.com', 'Gus');
Error: UNIQUE constraint failed: users.email
db> COMMIT;
db> SELECT id, name FROM users;
2|Brook
3|Chen
4|Dee
5|Eve
10|Ada
db> .quit
```

Eve, inserted by a statement of her own, survives the COMMIT; Fay does not.
That is sqlite3's default for a broken constraint too: undo the statement,
keep the transaction. Its integrity check, which also checks that no unique
index holds a value twice, agrees with every entry written:

<!-- verify: session cwd=project -->
```
$ sqlite3 -list users.db "PRAGMA integrity_check"
ok
```

Last, a table sqlite3 made. In 03.03 the engine could open one with UNIQUE
but marked it read-only, because it could not keep the index up to date.
Now it can:

<!-- verify: session cwd=project -->
```
$ sqlite3 theirs.db "CREATE TABLE users(id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT); INSERT INTO users VALUES (1, 'ada@example.com', 'Ada');"
$ ./db theirs.db "INSERT INTO users VALUES (2, 'ada@example.com', 'Brook')"
Error: UNIQUE constraint failed: users.email
$ ./db theirs.db "INSERT INTO users VALUES (2, 'brook@example.com', 'Brook')"
$ sqlite3 -list theirs.db "SELECT * FROM users; PRAGMA integrity_check;"
1|ada@example.com|Ada
2|brook@example.com|Brook
ok
```

## How it works

### Compare the key, then read the rowid

The lookup searches for the row's values alone, with no rowid after them:

```
record_build(&k, vals, ix->ncols);
```

The rowid is left out because it is the one thing nobody knows: the
question is whether any row holds this email, not whether row 3 does. The
seek compares only the first `ncols` fields of each entry and, with a bias
of -1, lands on the first one whose email is equal (05.02's lookup). Then
the rowid, the entry's last field, decides:

```
taken = e[ix->ncols].i != self;
```

`self` is the rowid of the row being written. For an INSERT no entry can
have it yet, so any equal entry is taken. For an UPDATE it is the row's old
rowid, and the entry found may be the row's own, about to be replaced: that
is how Ada moved to rowid 10. sqlite3 makes the same exception, comparing
the rowid in the entry it found with the row's old one.

Two rules come before the seek. A NULL in any of the index's columns means
"not taken" at once: in the index NULLs sort together and compare equal,
so a seek would find the others, but in SQL a NULL equals nothing
(sqlite3's probe, `OP_NoConflict`, jumps straight to "no conflict" on one).
And `check_unique` skips an index whose entry an UPDATE leaves as it is:
setting only `name` gives the email nothing new to meet but itself.

### Check everything, then write

`insert_row` asks about every index before its first write:

```
Row cand = {vals, t->ncols, rowid};
if (check_unique(db, t->indexes, &cand, NULL) < 0) {
    rc = -1;
    goto done;
}
```

It could check each index as it adds that index's entry. It must not.
04.01's rule is that `insert_row` checks everything before it writes
anything, and `run_stmt` (03.02) relies on it: inside BEGIN it keeps no
copies of the pages a one-row INSERT changes, because such an INSERT that
fails has changed nothing. A row that passed one unique index, got its
entry there, and failed a second would leave its table row and that entry
behind, with nothing to undo them. The rows a longer statement wrote before
it failed are another matter: `run_stmt` undoes them by rolling back the
statement's transaction outside BEGIN, or its savepoint inside.

### Newest first, as sqlite3 does

A row can break two constraints, and the error names one. Give a copy of
users a second constraint by hand, and repeat both an email and a name:

<!-- verify: session cwd=project -->
```
$ cp users.db two.db
$ ./db two.db "CREATE UNIQUE INDEX users_name ON users(name)"
$ ./db two.db "INSERT INTO users VALUES (6, 'ada@example.com', 'Brook')"
Error: UNIQUE constraint failed: users.name
$ sqlite3 two.db "INSERT INTO users VALUES (6, 'ada@example.com', 'Brook')"
Error in 2nd command line argument: UNIQUE constraint failed: users.name
```

sqlite3 keeps a table's indexes in a list, newest first, and checks them in
that order: it reports the constraint declared last, and an index created
after the table before any declared in it. This engine's list is oldest
first, because 05.03's planner prefers the oldest index, so `check_unique`
goes to the end of the list first and checks on the way back:

```
if (check_unique(db, ix->next, row, old) < 0)
    return -1;
```

Either order refuses every row it should. It has to be sqlite3's anyway,
because the message is part of the answer: a program that turns
`users.email` into "that address is taken" must get the same words from
both engines.

The names of the automatic indexes are bound tighter still. sqlite3 does
not store which constraint an index belongs to: at every open it parses the
CREATE TABLE again, works out the names, and pairs each row that has no SQL
with the index of that name. A name it would not have made is
`malformed database schema ... - orphan index`, and it refuses the whole
file. So `auto_indexes` gives no number to the INTEGER PRIMARY KEY, nor to
a constraint that repeats an earlier one's columns in the same order:
sqlite3 makes no index for either.

## Decide the boundary

<!-- verify: mention names="insert.c wal.c nbtinsert.c" outside reason="SQLite's and PostgreSQL's source files, not this engine's" -->
This engine checks with a separate lookup before the write, and so does
SQLite: `sqlite3GenerateConstraintChecks` in its insert.c lays down every
check for a row, a probe of each unique index among them, and only after it
`sqlite3CompleteInsertion` writes the row and its entries. A refused row
writes nothing. But the look and the write are two steps, safe only while
nobody else can write between them: this engine assumes it is the only
process using the file (07.01), and SQLite lets one connection write at a
time ("There can only be a single writer active at a time", its wal.c).

PostgreSQL lets many transactions write one table at once, and checks
inside the index insert instead, with the row already in the table.
`_bt_doinsert` (nbtinsert.c) goes down to the first leaf page the key could
be on, write-locks it, calls `_bt_check_unique`, and keeps the lock until
the new entry is in; anyone inserting the same key needs that page, so only
one of them can be checking at a time. The check does more than ours, too.
That index keeps entries for old versions of rows, so for each equal entry
it asks the table whether the row is still live, and when that row's
transaction has not finished, it lets go of the page, waits for it to end,
and searches again. The price is a check woven into the B-tree's own
insert, a lock held across it, and a row written to the table before anyone
knows whether it may stay. How many writers can be in the table at once?

## Break it

Make the row's own entry count: in `unique_taken`, change
`taken = e[ix->ncols].i != self;` to `taken = 1;`, then run `make` (in
build/at/db/08.07/) and go on with the users.db of Run it:

<!-- verify: patch file=src/exec.c
-        taken = e[ix->ncols].i != self;
+        taken = 1;
-->
<!-- verify: session cwd=project -->
```
$ ./db users.db "UPDATE users SET name = 'Ada L' WHERE id = 10"
$ ./db users.db "INSERT INTO users VALUES (8, 'hal@example.com', 'Hal')"
$ ./db users.db "UPDATE users SET id = 1 WHERE id = 10"
Error: UNIQUE constraint failed: users.email
```

Changing Ada's name still works: her entry in the email index does not
change, so that index is never looked at. A new email still works: the
lookup finds no equal entry, and the changed line is never reached. But
moving Ada back to rowid 1 changes her entry, the lookup for her email
finds the only entry with it, her own, and now that counts. Every UPDATE
that changes the rowid of a row with an email would fail the same way.
Put the line back and `make` again.

## Go deeper

- [SQLite: CREATE TABLE, UNIQUE constraints](https://www.sqlite.org/lang_createtable.html#unique_constraints) -
  a unique index per UNIQUE or PRIMARY KEY constraint, NULLs distinct from
  each other; section 3.5 has the PRIMARY KEY that accepts NULLs, section 5
  the rule that only a column declared exactly INTEGER is the rowid.
- [SQLite: Database File Format, section 2.6, Storage Of The SQL Database Schema](https://www.sqlite.org/fileformat2.html#storage_of_the_sql_database_schema) -
  the `sqlite_autoindex_TABLE_N` names and their NULL sql. Its N counts
  "each constraint seen", but one that makes no index takes no number: in
  users the email's index is 1, not 2.
- [SQLite: PRAGMA index_list](https://www.sqlite.org/pragma.html#pragma_index_list) -
  the five columns printed above, and what `c`, `u` and `pk` say about who
  made an index.
- [SQLite source, insert.c at version-3.54.1](https://github.com/sqlite/sqlite/blob/version-3.54.1/src/insert.c) -
  the comment above `sqlite3GenerateConstraintChecks` lists the conflict
  actions; ABORT, the default, backs out the current statement only.
- [PostgreSQL source, nbtinsert.c at REL_18_7](https://github.com/postgres/postgres/blob/REL_18_7/src/backend/access/nbtree/nbtinsert.c) -
  the comment in `_bt_doinsert` on the write lock held on the first page
  the value could be on, and `_bt_check_unique` waiting for another
  transaction.
- [PostgreSQL: Unique Indexes](https://www.postgresql.org/docs/18/indexes-unique.html) -
  the index made for every unique constraint and primary key, and NULLS
  NOT DISTINCT, the option that makes NULLs conflict.
