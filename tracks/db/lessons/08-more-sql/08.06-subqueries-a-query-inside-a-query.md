# 08.06 Subqueries: a query inside a query

Some questions need another answer first: which orders are bigger than
the average order, which customers have no orders at all. This lesson lets
a SELECT stand inside an expression and run from there as a query of its
own, once for the whole statement or once for every row around it.

## Where this fits

![Where 08.06 fits](figures/08.06-map.svg)

A subquery is a whole query, parsed, planned and run by everything modules
04 and 05 and this module built. What is new is where it runs from: the
middle of an expression, while the query around it holds a row, so that a
filter, a result column or an UPDATE can ask it for one value, a set of
values, or whether it has a row at all. Afterwards the engine answers
questions that need another answer first, NULLs and all as sqlite3 does.

## The idea

![Three kinds of subquery on the shop: one value (2, so Brook), a set (1, 1, 2, 3, 3 and a NULL: Ada, Brook and Chen are in it), and yes or no (an order exists for Ada, Brook and Chen, none for Dee).](figures/08.06-kinds.svg)

"Which orders are bigger than the average order?" The average is one value
made from all six orders (08.04), about 26.7, and only once it is known can
each order be compared with it. A **subquery** asks for it on the way: a
SELECT in parentheses, written where a value goes,
`total > (SELECT avg(total) FROM orders)`. Orders 10, 12 and 15 pass.
"Which customers have no orders?" 08.02 answered with a LEFT JOIN and its
NULL row; a subquery asks it as it is said: those for whom no order exists.

There are three forms, and each hands back something different:

- `(SELECT ...)`, a **scalar subquery**: one value, the only column of its
  first row, or NULL if there is no row.
  `id = (SELECT customer_id FROM orders WHERE id = 13)` is `id = 2`, Brook.
  With several rows the first is taken, as in sqlite3; PostgreSQL calls
  that an error.
- `x IN (SELECT ...)`: a **set**, the values of its one column, and whether
  x is one of them. `(SELECT customer_id FROM orders)` is 1, 3, 1, 2, 3 and
  order 15's NULL: Ada, Brook and Chen are in it.
- `EXISTS (SELECT ...)`: yes or no, does it have a row? Its columns are
  never computed, so `SELECT 1` is the usual way to write it.
  `NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)` is true
  for Dee alone.

Each is an expression like any other, so it goes wherever one goes, UPDATE
and DELETE included, and a subquery can hold subqueries.

![The outer query stopped on Ada's row while the inner query runs under it, its c.id reading 1 from that row; beside it, muted, a subquery that names nothing outside, run once and its answer kept.](figures/08.06-outer.svg)

The average is the same for every order. That subquery names nothing
outside itself, so it runs the first time it is needed and its answer is
kept for the rest of the statement. Dee's is different: `o.customer_id =
c.id` names c, the customer the query outside is on, so it must run again
for every customer. A subquery that names a table of a query around it is
**correlated**, and the row it reads there is its **outer row**. While it
runs, the query outside waits on that row, Ada's say, and `c.id` inside
reads 1 from it; for Brook it runs again and reads 2.

A name inside a subquery is looked for first among its own tables, as 08.01
binds any name; only when none has it does the search go out to the query
around it, and on out. So a name inside hides the same name outside: in
`EXISTS (SELECT 1 FROM orders WHERE customer_id = id)` the bare `id` is the
order's own. And a name the inner tables lack goes out silently: orders has
no city, so `city` in a subquery on orders is the customer's. A name found
one query out is bound to its slot there, with a **depth** of 1: how many
queries out the row it reads is.

![id NOT IN (SELECT customer_id FROM orders) for each customer against the set 1, 1, 2, 3, 3 and a NULL: Ada, Brook and Chen are found, so NOT IN is false; Dee's 4 is not found, but the set holds a NULL, so the answer is NULL; no row survives.](figures/08.06-notin.svg)

"Customers with no orders" sounds like
`id NOT IN (SELECT customer_id FROM orders)`, which returns nothing at all,
not even Dee. Ada's 1 is in the set: IN is true, NOT IN false. Dee's 4
equals none of the numbers, but the set also holds order 15's NULL, a value
nobody knows, which might be 4. So `4 IN` the set is NULL, NOT of NULL is
NULL (04.02), and WHERE keeps only what is true. The rule, sqlite3's and
PostgreSQL's: found is true; not found is false, or NULL if the set holds a
NULL; a NULL x is NULL against any set but an empty one. To ask what was
meant, use NOT EXISTS, which asks about rows and compares with nothing, or
keep the NULL out of the set with a WHERE inside.

### parse_subquery: a SELECT in parentheses

Called at `(SELECT`, `EXISTS (` and `IN (SELECT`: reads the SELECT as a
statement of its own, hung on the expression, its text kept for EXPLAIN.

### resolve_outer: a name from the query outside

Called for a name none of a subquery's tables has: binds it in the query
around, one more step out in its depth, and marks the subquery correlated.

### run_subquery: run the query inside

One run: the outer row pushed, the subquery planned and its rows pulled,
and the answer copied out before the run's arenas go.

### set_lookup: IN a set that may hold NULL

Bisects the sorted set an IN kept: yes, no, or NULL when x is not there
and a NULL is.

## How it works

### The outer row holds still

A correlated subquery's outer row stays where the query outside has it, in
a scan's row, a join's, an Aggregate's; nothing copies it.
`run_subquery()` pushes a pointer to it on a stack in the Db, and `eval()`
reads a name of depth d from the dth row down from the top, the top one
for depth 1:

```
        if (e->depth)        /* a name from a query outside: that query's row */
            row = e->depth <= db->nouter ? db->outer[db->nouter - e->depth] : NULL;
```

That row's values point into pages of the cache, and what the outer query
has computed for it so far (`name || '!'` in an earlier result column)
sits in its row arena. A run must disturb neither. Its loop never calls
`pager_shrink()`; only the statement loop does, between output rows
(08.01). And it gets arenas of its own: its operators empty db->rowa as
they go (a Filter, for every row it drops), and its plans would pile up in
db->stmt, the statement's arena, one per run, until the statement ends:

```
    Arena rowa = db->rowa, stmt = db->stmt;     /* the caller's */
    Arena *keepa = e->correlated ? &rowa : &db->once;
    ...
    memset(&db->rowa, 0, sizeof db->rowa);
    memset(&db->stmt, 0, sizeof db->stmt);
    db->outer[db->nouter++] = row;
```

The run's arenas are freed at its end, so the answer is copied out first
with `keep()` (04.03): a correlated one into the caller's row arena, a kept
one into db->once, which `db_exec()` empties with the statement. The
**invariant**: nothing a run leaves behind points into the run or into a
page. Without the copy, a kept 3000-byte text printed beside 3000 rows,
under AddressSanitizer with a two-page cache, stopped at row 256 on a read
of the page the statement loop had just let go.

### A plan for every run

Each run builds the subquery's plan anew (`plan_select()`), where it could
build one and restart it, as the Join restarts its inner side. Rebuilding
is what lets 05.03's planner use an index: within one run the outer row
does not change, so a name from outside is a constant (`is_constant()`):

```
    if (e->op == E_COLUMN || e->op == E_ROWID)
        return e->depth > 0;
```

`o.customer_id = c.id` is then column = constant, like `customer_id = 3`,
and becomes an index lookup whose key is evaluated as the scan is made,
from the row on the stack. The price is a planner pass per outer row.

### The set, sorted once

An IN that runs once takes every value with the affinity the comparison
would give it, copies each into db->once, notes a NULL instead of storing
it, and sorts them once with `value_compare()`, ORDER BY's order. Then
`set_lookup()` bisects, about 15 comparisons for 20000 values, and its last
line is where NOT IN gets its NULL: `return e->has_null ? -1 : 0;`. A
correlated IN has a different set for every row: it scans and stops at the
first match.

### Where the condition goes in a join

08.01 checks a WHERE term at the first Filter whose row holds every table
it names. For a subquery, `last_table()` walks inside and counts the names
of depth 1, which read this query's row. Back in the engine on the small
shop (`./db shop.db`, in build/at/db/08.06/; big.db's index would change
the plan):

<!-- verify: session run="./learn run db --at 08.06 -- shop.db" -->
```
db> EXPLAIN SELECT c.name, o.total FROM customers c JOIN orders o ON o.customer_id = c.id WHERE (SELECT count(*) FROM orders p WHERE p.customer_id = c.id) > 1;

  Join
    Filter ((SELECT count(*) FROM orders p WHERE p.customer_id = c.id) > 1)
      Scan customers AS c

```

It reads only c, so it runs on customers' own rows, four times, and Brook
and Dee never meet orders.

## Decide the boundary

This engine runs every subquery as it is written: a plan of its own, run
from inside the expression, once and kept or once per outer row. SQLite
3.54.1 does the same for many: expr.c's `sqlite3CodeSubselect` codes one as
a subroutine with `OP_Once` in front unless it is correlated, and
`sqlite3CodeRhsOfIN` builds an uncorrelated IN's set once, into a
temporary index. But
first it rewrites what it can. `WHERE EXISTS (...)` becomes a join
(select.c, `existsToJoin`): the inner table joins the outer FROM, its WHERE
the outer WHERE, and its loop is left at the first match. A query in FROM
is flattened into the one around it (`flattenSubquery`) or run as a
co-routine. Leave the engine, and on shop.db, in build/at/db/08.06/:

<!-- verify: session host cwd=project -->
```
$ sqlite3 shop.db 'EXPLAIN QUERY PLAN SELECT name FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)'
QUERY PLAN
|--SCAN c
|--BLOOM FILTER ON o (customer_id=?)
`--SEARCH o EXISTS USING AUTOMATIC PARTIAL COVERING INDEX (customer_id=?)
```

As a join, EXISTS got the automatic index of 08.01's boundary. That is
3.54.1's plan (`sqlite3 --version`); an older sqlite3, macOS's own among
them, keeps EXISTS a subquery and prints the plan NOT EXISTS gets below.

<!-- verify: fact cmd="sqlite3 shop.db 'EXPLAIN QUERY PLAN SELECT name FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)' | grep -o 'CORRELATED SCALAR SUBQUERY 1'" expect="CORRELATED SCALAR SUBQUERY 1" -->
NOT EXISTS is not rewritten: its plan says CORRELATED SCALAR SUBQUERY 1, a
scan of orders per customer, as here.

PostgreSQL 18.7 rewrites more. Before it plans, prepjointree.c's
`pull_up_sublinks` turns IN and EXISTS into semi-joins, joins that hand up
an outer row once, at its first match, and NOT EXISTS into an anti-join,
which hands up the outer rows that match nothing (subselect.c), for the
join planner of 08.03's boundary to order and run by hash, merge or nested
loop. Each only at the top level of WHERE or ON, for IN "because we cannot
distinguish whether the ANY ought to return FALSE or NULL in cases
involving NULL inputs"; NOT IN never. What is left
is a SubPlan: run once, or per outer row, or, for an uncorrelated IN
estimated to fit in memory, hashed (nodeSubplan.c, `ExecHashSubPlan`),
with the rows holding a NULL in a table of their own, this engine's
has_null. A rewrite lets the planner choose order and algorithm, and needs
a proof, rewrite by rewrite, that the answer stays the same, NULLs and all;
running as written costs a run per outer row and is easy to predict. So:
is a subquery an instruction, to be run where it is written, or a
description of an answer, to be computed any way that provably gives the
same rows?

in build/at/db/08.06/src/exec.c, change `if (!e->correlated) {` to
`if (1) {`, then run the engine on the same file:

was asked once too, for Ada, who has orders: false, kept, and Dee is lost.

whether it may be kept; only the names inside the subquery can, which is
why `resolve_outer()` marks the subquery correlated as it binds one.
