# 08.03 An index for the inner loop

The nested loop of 08.01 reads the whole inner table again for every
outer row. When the join's condition says which inner rows can match, the
inner loop can go straight to them instead, by rowid or through an index.
This lesson teaches the planner to do that, and measures what it is worth.

## Where this fits

![Where 08.03 fits](figures/08.03-map.svg)

The planner of 05.03 chose how a query's one table is read; now it also
chooses how each later table of a join is read, once for every row of the
tables before it, with the rowid and index lookups of 05.02. The Join and
the Filters above are those of 08.01 and 08.02. Afterwards a join on a
rowid or an indexed column costs one lookup per outer row instead of a
scan, and the order the tables are written in decides which table is
looked up.

## The idea

![For an order whose customer_id is 3, one descent of customers' B-tree to the leaf that holds row 3, beside the sweep across every leaf that the nested loop makes.](figures/08.03-lookup.svg)

Give the shop 1000 customers and 20000 orders. The join of 08.01,
`customers c JOIN orders o ON o.customer_id = c.id`, reads all 20000
orders for each customer: twenty million pairs looked at, for 20000 rows
of answer. Run it measures it: most of a second, and sixty million times
the B-tree asks the pager for a page.

Yet the condition says which rows can match. Write the tables the other
way round, `orders o JOIN customers c ON c.id = o.customer_id`, and take
an order whose customer_id is 3. Only customer 3 can match it, and id is
customers' INTEGER PRIMARY KEY, its rowid: one descent of customers'
B-tree finds her, the rowid lookup of 05.02, with the 3 taken from the
outer row instead of the query. That is an **index nested loop join**:
the inner loop is a lookup, made again for every outer row, with a
**key** computed from that row. Written customers first, the key is
`c.id`, to be found in orders' customer_id; index that column, and for
Ada the inner loop looks up customer_id 1 as `WHERE customer_id = 1`
would.

A key may use only tables written before the inner one, the tables whose
values are in the joined row when the inner loop starts again. So the
order the tables are written in decides which one is looked up.

![The inner table's ladder: the rowid equal to a key, an index's first column equal to one, or a scan; each with a join that takes it and its EXPLAIN QUERY PLAN line.](figures/08.03-ladder.svg)

For each table after the first the planner climbs a ladder like 05.03's,
and the first rule that applies wins: the rowid (or the INTEGER PRIMARY
KEY) equal to a key gives a rowid lookup; the first column of an index
equal to a key gives an index lookup, when the two types allow it (How it
works); otherwise a scan. Keys come from
WHERE and from the ON of every inner join, all of which must hold. The
condition that gave the key is still checked on every row the lookup
finds, in the Filter above the join: the lookup only narrows what is read.

### choose_join_access: choose how to read the inner table

Called for each table after the first while the plan is built: it looks
for `column = key` with the column the inner table's and the key made of
earlier tables, and fills in 05.03's access path with that key where a
constant used to be.

### scan_rebind: start the inner side for this outer row

Called by the Join where it used to start its inner scan again. A scan
still starts from its first row; a lookup evaluates its key on the new
outer row and seeks to it.

The ON decides what a match is (08.02), so a lookup by it reads every row
that could match. WHERE is checked on what the join hands up, and the
join must hand up the same rows however its table is read. In the second
query every order matches Dee (`ON 1`), so the join hands up six pairs
for her, which the WHERE drops. A lookup by customer_id 4 would find no
order, and the join would hand up a row of NULLs in their place. The WHERE
happens to drop that row too; sqlite3 proves as much and plans such a
LEFT JOIN as a plain join (select.c, "OUTER JOIN strength reduction").
This engine makes no such proof, and scans.

A NULL key finds nothing: `= NULL` is never true (04.02), so the lookup
reads no row, and order 15 gets its row of NULLs. With three tables, each
can look up the next. Pairs of orders by one customer: each order, its

## How it works

### The lookup only narrows

The **invariant**: every condition is checked in full on every row it
applies to, whatever lookup found that row; a lookup may narrow which
rows are read, never lose one. So `choose_join_access()` only reads the
list of conditions, and 08.01's code that puts each one in the Filter
where its tables meet runs after it as before:

```
        choose_join_access(q, k, terms, n, &plan->jacc[k]);
        ...
        if ((here = terms_at(db, terms, n, k)))
            op = op_filter(db, op, here);
```

That check lets a lookup read loosely: a rowid key of 1.5 reads rowids 1
and 2 (`rowid_bound()`), and the Filter drops both.

### The affinity test

The danger is the other way: reading too little. SQL converts values
before it compares them (04.02), and a TEXT column compared with an
INTEGER column is compared as numbers, so the text '03' equals 3. An
index on the TEXT column keeps '03' as text; a lookup for 3, made the
text '3' for that column, finds '3' and never '03'. Notes typed in by
hand, with the customer's number as text:

<!-- verify: session -->
```
db> CREATE TABLE notes(customer TEXT, note TEXT);
db> CREATE INDEX notes_customer ON notes(customer);
db> INSERT INTO notes VALUES ('1', 'gift wrap'), ('3', 'call first'), ('03', 'paid late');
db> SELECT c.name, n.note FROM customers c JOIN notes n ON n.customer = c.id;
Ada|gift wrap
Chen|call first
Chen|paid late
db> EXPLAIN QUERY PLAN SELECT c.name, n.note FROM customers c JOIN notes n ON n.customer = c.id;
QUERY PLAN
|--SCAN c
`--SCAN n
```

The index is there, and the planner scans, because `index_affinity_ok()`
refuses it:

```
    if (aff == AFF_INTEGER || aff == AFF_REAL || aff == AFF_NUMERIC)
        return 1;
    return key->aff != AFF_INTEGER && key->aff != AFF_REAL && key->aff != AFF_NUMERIC;
```

A numeric column is always safe, for there the key is what gets
converted (`notes n JOIN customers c ON c.id = n.customer` turns '03'
into 3 and finds Chen by rowid); a TEXT column, or one with no type, only
when the key is not a column of numeric affinity. This is sqlite3's own
test (`sqlite3IndexAffinityOk`, in its expr.c), and sqlite3 kept to this
order (CROSS JOIN, automatic indexes off) scans notes too.

### Why the key is read back from its own record

A key computed by an expression, or a number made text for a TEXT index,
lives in the row arena, which is emptied after every row the statement
prints and by a Filter for every row it drops, while the lookup still has
entries to go. The lookup needs its key as a record to seek to and as a
value to stop at. So `scan_rebind()` builds the record in the scan's own
buffer and decodes the value back out of it, into a buffer only the next
outer row's key overwrites:

```
    scan->key.n = 0;
    record_build(&scan->key, &v, 1);
    record_decode(scan->key.p, (u32)scan->key.n, &scan->hi, 1);
```

A constant's key is copied into the statement's arena instead
(`bound_value()`): per outer row, that would keep a copy for every
customer until the statement ends.

### What a page request counts

Pages read is what came from the file: with a 500-page cache, every page
once whatever the plan, so by that count the index made the join worse
(69, then 134). A **page request** is each time the B-tree asks the pager
for a page, hit or miss: the work a plan does, and what turns into reads
once the file outgrows the cache. The three counts add up from parts
measured alone (leave the engine first, and run them in
build/at/db/08.03/):

<!-- verify: session host cwd=project

-->
```
$ DB_STATS=1 ./db big.db 'SELECT 1' > /dev/null
stats: pages read 1, cache hits 10, cache misses 1, ...
$ DB_STATS=1 ./db big.db 'SELECT id FROM orders' > /dev/null
stats: pages read 61, cache hits 60186, cache misses 61, ...
$ DB_STATS=1 ./db big.db 'SELECT * FROM orders WHERE customer_id = 3' > /dev/null
stats: pages read 24, cache hits 131, cache misses 24, ...
$ DB_STATS=1 ./db big.db 'SELECT * FROM customers WHERE id = 3' > /dev/null
stats: pages read 3, cache hits 15, cache misses 3, ...
```

Less the 11 every statement starts with, a scan of orders is 60,236
requests: three per row, for the cursor asks for its leaf to step, to see
whether a row is there, and to read it. A customer's 20 orders through
the index are 144, a customer by rowid 7. So the nested loop is a
thousand scans of orders, sixty million; the index join a thousand
searches of about 144 and a scan of customers, 147 thousand; the other
order a scan of orders and 20000 rowid lookups of about 7, 200 thousand.

## Decide the boundary

This engine nests the loops in the order written, and Run it showed the
price: with no index, 0.86 s one way, 0.010 s the other. SQLite works it
out: where.c's `wherePathSolver` "attempts to find the lowest cost path
that visits each WhereLoop once", which on big.db put orders outside
however the query was written. When no index fits it builds one for the
statement (`constructAutomaticIndex`, 08.01's CROSS JOIN), and goes no
further: it has no hash join. Its documentation calls an automatic index
"almost the same thing as a hash join", a B-tree in place of a hash table.

PostgreSQL 18.7 has hash and merge joins beside the nested loop.
nodeHashjoin.c "is based on the 'hybrid hash join' algorithm": it builds
a hash table on the join key from the inner side and probes it with each
outer row, and "if the inner side tuples of a hash join do not fit in
memory, the hash join can be executed in multiple batches".
nodeMergejoin.c walks two inputs sorted on the join
key forward together, marking the first inner row of a run of equal keys
and going back to it for the next outer row with that key. Its planner
weighs "all possible paths that use the two component rels as outer and
inner rel" (joinpath.c), the nested loop over an index among them. An
index is work kept in the file, paid for by every INSERT and paid back by
every query; a hash table redoes the work, a pass over the inner table,
each time the join runs. How often does the join run, against how often
its tables change?

## Break it

Take the affinity test away: in `index_affinity_ok()` in
build/at/db/08.03/src/plan.c, replace the last line,
`return key->aff != AFF_INTEGER && key->aff != AFF_REAL && key->aff != AFF_NUMERIC;`,
with `return 1;`, then `make` (in build/at/db/08.03/) and run the notes
join again there, on shop.db (`./db shop.db`):

<!-- verify: patch file=src/plan.c
-    return key->aff != AFF_INTEGER && key->aff != AFF_REAL && key->aff != AFF_NUMERIC;
+    return 1;
-->
<!-- verify: session run="./db shop.db" cwd=project -->
```
db> SELECT c.name, n.note FROM customers c JOIN notes n ON n.customer = c.id;
Ada|gift wrap
Chen|call first
db> EXPLAIN QUERY PLAN SELECT c.name, n.note FROM customers c JOIN notes n ON n.customer = c.id;
QUERY PLAN
|--SCAN c
`--SEARCH n USING INDEX notes_customer (customer=?)
```

Chen's '03' note is gone. Her lookup searched the index for the text '3';
'03' sits elsewhere in it, and only a scan would have compared it with 3
as a number. The Filter cannot bring it back: it never sees a row that
was not read. Nothing fails and the answer looks complete; a lookup that
reads too little is wrong in silence. Put the line back and `make` again.
