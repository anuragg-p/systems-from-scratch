# 08.02 LEFT JOIN: the row with no match

The join of 08.01 builds rows only from pairs that match, so a customer
who never ordered is in none of them. A LEFT JOIN keeps every row of the
tables written before it, the ones that match nothing too, with NULL
where the other table's values would be. With it comes the difference
between a condition in ON and the same condition in WHERE.

## Where this fits

![Where 08.02 fits](figures/08.02-map.svg)

A LEFT JOIN is 08.01's nested loop with one more rule, in the same
operator: one outer row held, the inner table read in full for it. The
new part is what happens when the inner table runs out and nothing
matched. The scans below and the Filter, Sort and Limit above work as
before, on the row the join made up too. Afterwards the engine can answer
questions about what is missing: customers who never ordered, orders
whose customer is not there.

## The idea

![customers c LEFT JOIN orders o: the five rows of 08.01, then Dee's row, whose three values from orders are NULL: made by the join, not read from orders.](figures/08.02-nomatch.svg)

Ask 08.01's join for every customer with their orders and it answers with
Ada, Brook and Chen. Dee has no orders, so she is in no pair that
matches and in no row. "Which customers have never ordered?" cannot be
asked at all: WHERE picks among the rows a join builds, and the answer is
a row nobody built.

So build it. The join already tries every order for each customer; it
only has to remember whether any matched. When the inner side runs out
and nothing did, it hands the outer row up anyway, once, with every slot
of the inner table NULL. For Dee six orders are tried, none matches, and
`Dee, NULL, NULL, NULL` goes up: six rows where 08.01 had five. In SQL:
`customers c LEFT JOIN orders o ON o.customer_id = c.id` (LEFT OUTER JOIN
is the same). The table before the words is the one whose rows are all
kept.

That gives ON a meaning WHERE does not have. "Nothing matched" needs a
rule for what a match is, and a LEFT JOIN's ON is that rule: checked
inside the join, on each pair, it decides only whether the pair is a
match. WHERE is checked on the rows the join hands up, the NULL row
among them, and decides which survive. Put `o.total > 25` in ON and a
match is an order of this customer over 25: Ada has two, the others none,
so Brook, Chen and Dee each come up once with NULLs. Put it in WHERE and
any order is a match: the six rows go up, and the filter keeps Ada's two
(on Dee's row `NULL > 25` is NULL, not true: 04.02).

![The same LEFT JOIN with o.total > 25 in ON and in WHERE. In ON: all four customers, with NULLs where no order passed. In WHERE: only Ada's two orders over 25.](figures/08.02-on-where.svg)

A condition on the outer table alone splits the same way: `c.city =
'London'` in ON lets only London customers have matches, and Brook and
Dee still come up with NULLs; in WHERE it drops them. And the NULL row
is how to find what matched nothing: ask for the rows where a column no
stored order has NULL in, orders' INTEGER PRIMARY KEY, is NULL.
`WHERE o.id IS NULL` keeps Dee and nobody else.

### left_join: the row with no match

The LEFT JOIN's part of the loop. Given an inner row, it checks the
join's own ON on the pair and remembers a match; when the inner side has
run out, it makes the NULL row if nothing matched.

A NULL prints as nothing between the bars. The Left join carries its ON,
and no Filter holds it. WHERE's terms go where 08.01 put them:
`o.total > 25` above the join, where it meets the NULL rows, and
`c.city = 'London'` below it, on customers' own rows.

A LEFT JOIN with no ON counts every pair as a match, so Dee is paired
with all six orders and gets no NULL row, as in sqlite3. And the order
of the tables decides what is kept: orders first, and the join keeps
every order, order 15 too, whose customer_id is NULL. With inner joins
the order only changed how fast (08.01); here it changes the answer.

In a chain the outer side of a LEFT JOIN is everything written before
it. LEFT, then an inner join: each order, its customer, and everyone in
that customer's city (m). Order 15 is kept by the LEFT JOIN and lost at
the next join, whose ON, `m.city = c.city`, is NULL on its row; make
that join LEFT too and it stays. (Writing the inner join first does not
help: an inner ON waits for every table it names, 08.01, so it still
meets the NULL row.) An inner join, then LEFT: the outer row is a pair,
and each order with no later order of its customer gets a NULL row: 12,
13 and 14, each customer's last.

## How it works

### Why ON stays inside the join

08.01 put every inner ON into one list with WHERE's terms, each checked
in a Filter as soon as its tables are in the row. A LEFT JOIN's ON stays
out of that list:

```
    for (int k = 0; k < sc->nfrom; k++)
        if (!sc->from[k].left)          /* a LEFT JOIN checks its own ON (left_join()) */
            n = conjuncts(sc->from[k].on, terms, n, nterms);
```

A Filter can only drop a row. For an inner join that is all a failed ON
means; for a LEFT JOIN it means "not a match", and whether any pair
matched only the join knows, at the end of its inner loop. Were the ON
in the list too, it would be checked again above the join on the NULL
row, where it is NULL: every NULL row dropped, an inner join again, as
Break it shows. WHERE terms keep 08.01's rule: a term naming orders
waits above the Left join and meets the NULL rows; a term on customers
alone is checked below it, and the answer is the same, since a
customer's values are the same on every row made from it.

The ON is checked inside its join, where the tables to its right are not
in the row yet, and cannot wait for them as an inner ON can: hence the
error, raised in `plan_select()` when `last_table()` of a LEFT JOIN's ON
is past its own table.

### Two calls from one loop

`join_next()` calls `left_join()` at the two moments its two questions
can be answered. "Is this pair a match?" needs the pair in the row, so
it is asked for each inner row, and a pair that fails is skipped as a
Filter skips a row. "Did anything match?" can only be asked when the
inner side is done:

```
        if (rc == 0) {
            op->have_outer = 0;
            if (op->leftjoin && left_join(op, 0)) {
```

The flag, `op->matched`, is cleared where a new outer row is taken.
`have_outer` is cleared before the NULL row goes up, so the next call
starts the next outer row; until then the outer values stay good in the
join's own arena (08.01).

### The rowid slot of the missing row

Each table's rowid has the slot after its columns (08.01), and this
join's row ends there. The loop that makes the NULL row runs to the end
of the row, so it clears the rowid too (all zero bytes is a NULL Value):

```
    for (int i = op->lwidth; i < op->row.ncols; i++)
        memset(&op->row.cols[i], 0, sizeof(Value));     /* V_NULL */
```

So `o.rowid` is NULL on Dee's row, as in sqlite3. Stop the loop one slot
short and the slot keeps the rowid of the last order the scan read:
`SELECT c.name, o.id, o.rowid` prints `Dee||15`, and
`WHERE o.rowid IS NULL` finds nobody. The **invariant**: on a NULL row
every slot of the inner table reads NULL, and nothing of the last inner
row read is left in it.

## Decide the boundary

This engine decides "nothing matched" inside the loop, with a flag. So
does SQLite 3.54.1, in bytecode. wherecode.c's
`sqlite3WhereCodeOneLoopStart` gives a LEFT JOIN's table a register,
`pLevel->iLeftJoin`, set to 0 before its inner loop ("init LEFT JOIN
match flag") and to 1 once the ON terms pass ("record LEFT JOIN hit"),
with WHERE's terms after it: "WHERE clause constraints apply to the
results of the OUTER JOIN". When the inner loop ends with the register
still 0, where.c's `sqlite3WhereEnd` moves the cursor to a row of NULLs
(OP_NullRow) and jumps back to the hit, so WHERE and the output run once
more. Same flag, same place, same row.

The choice is what SQLite does first. When WHERE can only be true if
some column of the LEFT JOIN's table is not NULL, no NULL row can
survive it, and the LEFT JOIN is made a plain JOIN: "OUTER JOIN strength
reduction", in select.c's `sqlite3Select`, with expr.c's
`sqlite3ExprImpliesNonNullRow` as the proof. A plain join may be
reordered (only outer joins and CROSS JOIN are pinned, in
`whereLoopAddAll`), so the WHERE half of Run it's pair runs orders
outside, where sqlite3 kept the plain LEFT JOIN's order:

<!-- verify: session host cwd=project -->
```
$ sqlite3 shop.db 'EXPLAIN QUERY PLAN SELECT c.name, o.id FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.total > 25'
QUERY PLAN
|--SCAN o
`--SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
```

The proof must never say yes wrongly: its comment calls a false positive
"deadly" and a false negative "a harmless missed optimization". So it is
careful, and gives up at any function call: with
`WHERE coalesce(o.total, 0) > 25`, which drops the NULL row as surely,
sqlite3 keeps the LEFT JOIN. This engine would gain nothing yet: it runs
the order written, so a LEFT JOIN made plain would run the same loops.
The rewrite pays only in an engine that chooses its order. Who should
notice a LEFT that a WHERE undoes: the engine, with a proof that may
never be wrong, or the person who wrote both?

## Break it

Put the LEFT JOIN's ON into the filters as well, as an inner join's: in
`plan_select()` in build/at/db/08.02/src/plan.c, delete the line
`if (!sc->from[k].left)`, so the line after it runs for every table,
then run the engine on the same file:

<!-- verify: patch file=src/plan.c
-        if (!sc->from[k].left)          /* a LEFT JOIN checks its own ON (left_join()) */
-->
<!-- verify: session run="./learn run db --at 08.02 -- shop.db" -->
```
db> SELECT c.name, o.id, o.total FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;
Ada|10|30
Ada|12|50
Brook|13|20
Chen|11|15
Chen|14|5
db> EXPLAIN SELECT c.name, o.id, o.total FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;
Filter (o.customer_id = c.id)
  Left join on (o.customer_id = c.id)
    Scan customers AS c
    Scan orders AS o
```

Dee is gone. The Left join still made her NULL row, and the Filter above
checked the ON again, as a WHERE, on that row: `NULL = 4` is NULL, and
the row was dropped. A row with a real match passes the same test twice,
so nothing else changes. Whether a condition says "what is a match" or
"what survives" is decided by where it is checked, not by what it says.
