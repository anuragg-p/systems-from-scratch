# 08.01 Two tables in one query: the nested loop join

Until now every query has read one table. A question as plain as "who
placed each order?" needs two: an order holds its customer's number, and
the customer's name is in another table. This lesson joins tables the
simplest way there is, one loop inside another, and teaches every name in
a query which table it means.

## Where this fits

![Where 08.01 fits](figures/08.01-map.svg)

This lesson opens an optional module that stands on the finished core.
Everything modules 00 to 07 built is still here and works as it did: a
query on one table is planned and run exactly as before. A join is one
more operator in the tree of module 04. It sits above two inputs where a
Filter sits above one and hands up rows like any other, so the Filter,
Sort and Limit above it take joined rows as they are. Below it each table
is read by the scans of modules 04 and 05, and the planner of 05.03 still
decides how the first table is read. Afterwards the engine answers
questions whose answer lives in several tables, with sqlite3's answers.

## The idea

![Two loops: for each customer, every order is tried against c.id = o.customer_id, and each pair that matches becomes a row of the output.](figures/08.01-loops.svg)

The shop of this module has four customers, each with an id, a name and a
city, and six orders, each with an id, a customer_id and a total. Order 11
says customer_id 3. Who is that, and where does she live? The order cannot
say; the answer is in customers, in the row whose id is 3.

So read both. For each customer, go through every order, and when the
order's customer_id equals the customer's id, put out one row made of the
two. That is a **nested loop join**: the **outer** table is read once, in
the outer loop, and the **inner** table is read in full, from its first
row, once for every outer row. Four customers and six orders make 24 pairs
to look at, and five match. Dee, who has no orders, and order 15, whose
customer_id is NULL, are in no pair that matches: NULL is never equal to
anything (04.02). In SQL: `SELECT c.name, o.id, o.total FROM customers c
JOIN orders o ON o.customer_id = c.id`, where `c` and `o` are
**aliases**, short names this query gives its tables, and `o.total` is a
**qualified name**, the column total of the table called o here.

![The joined row of customers c JOIN orders o: c's three columns and its rowid in slots 0 to 3, o's in slots 4 to 7. o.total is bound to slot 6.](figures/08.01-row.svg)

Each pair becomes one row with both tables' values side by side:
customers' three columns and its rowid in slots 0 to 3, then orders' in
slots 4 to 7. Before the first row is read, every name in the query is
**bound** to one slot of that row, once: `o.total` to slot 6, `c.name` to
slot 1. From then on, reading `o.total` is reading slot 6, as reading a
column has been reading one slot since module 04.

Binding is where a name can go wrong. A bare name is looked for in every
table: if one has it, it binds there; if two do, the name is
**ambiguous** and the query is refused (`id` could be the customer's or
the order's). A qualified name looks only in the table that answers to
it: the table's alias if it has one, else its name. That is what lets a
table be joined with itself, a **self-join**: the same table twice under
two aliases, each with its own slots. `*` stands for every table's
columns, left to right, and `o.*` for o's alone.

With three tables the join of the first two is the outer side of a join
with the third. A condition is checked as soon as the row holds every
table it names: a pair dropped early never meets the third table. For
orders over 10 placed by anyone in Ada's city (customers as a for Ada and
as c for anyone who lives there, then orders), `a.name = 'Ada'` is
checked on a's rows alone, `c.city = a.city` on each pair of customers,
the conditions on o once orders has joined. For an inner join, ON means
what WHERE means: all are conditions joined by AND, each checked at the
first place it can be, wherever it was written.

![A three-table join, each condition drawn at the level where it is checked: as soon as the row holds every table it names.](figures/08.01-levels.svg)

### parse_from: the FROM clause

Reads the tables after FROM, with their aliases and ONs, joined by
commas, JOIN, INNER JOIN or CROSS JOIN, all one inner join here. LEFT,
RIGHT, FULL and NATURAL are names to the tokenizer (a column may be
called left), so this is where they are told from an alias and refused.

### resolve_names: bind a name to its table

Finds the one table a name belongs to, or says in sqlite3's words that it
is ambiguous or missing, and binds it to that table's **base**, the slot
where its values start, plus the column.

### join_next: the nested loop

The operator: one outer row held, a joined row handed up for each inner
row, and the inner side started again for the next outer row.

### plan_select: where each condition is checked

One table: the plan of 05.03, unchanged. Several: a scan of the first
table, read as its own conditions allow; for each later table a Join with
a scan of it; above every operator a Filter with the conditions that have
just become checkable. Then a Sort for ORDER BY, and Limit.

    Scan orders AS o

only the pairs of customers in her city reach the second. The top Filter
holds `o.total > 10`, written in WHERE, and `o.customer_id = c.id`,
written in ON: one list of conditions, each placed by the tables it names.

## How it works

### Why the outer row is copied

The join holds its outer row for the whole inner loop, across many calls
to the inner side and many rows handed up. Its values point into a page
of the cache (04.01). The outer cursor does not move meanwhile, so they
would stay good if the page stayed, but the statement loop lets the cache
shrink every 256 rows it prints (`pager_shrink()`, 01.02), and the outer
row's page can be one that goes:

```
        if ((++count & 255) == 0)
            pager_shrink(&db->pager);    /* no page pointer is held between rows */
```

So `join_next()` copies the outer row into an arena of its own, emptied
when the next outer row comes, with the `keep()` the sort uses (04.03):

```
            arena_reset(&op->hold);
            int n = op->table ? op->table->ncols : op->lwidth;
            for (int i = 0; i < n; i++)
                op->row.cols[i] = keep(&op->hold, l->cols[i]);
```

The inner row is not kept: its values go into the joined row as they
are, still pointing into their page, and the row is handed up at once,
good until the join is asked again, like a scan's row. The **invariant**: a value
read from a page is good until the operator that read it is asked for
another row, or the cache shrinks between output rows; an operator that
holds a row longer copies it. Until now the sort was the only one.

Without the copy (`op->row.cols[i] = l->cols[i];`) the join is right
nearly always, which is the trouble. It was tried on a 3000-row table
with long text joined to a 300-row one, 900 rows out. Built with
AddressSanitizer and run with `DB_CACHE_PAGES=2`, it printed 256 rows and
stopped on a heap-use-after-free: a read from a page the cache had freed
after row 256. A plain build of the same change printed all 900 rows
correctly, with either cache size, because nothing had reused the freed
memory yet.

### Table 0's rowid waits for the first join

With one table, a scan's row carries its rowid beside its columns, not in
a slot. A joined row has one such field and several tables, so in a join
each table's rowid has the slot after its columns, and the join fills
table 0's when it copies the outer row from table 0's own scan (the
`op->table` above). Below the first join that slot does not exist yet, so
`last_table()` sends a condition on table 0's rowid up a level:

```
    if (e->op == E_COLUMN)
        return e->tab == 0 && e->tcol == TCOL_ROWID ? 1 : e->tab;
```

`c.id`, customers' INTEGER PRIMARY KEY, is the rowid under another name
but a column with a slot, so `c.id = 3` is checked at the bottom, where
05.03's rules make it a rowid lookup. `c.rowid = 3` waits above the join,
and every customer is read and joined first. Same answers, more work:

<!-- verify: session run="./learn run db --at 08.01 -- shop.db" -->
```
db> EXPLAIN SELECT c.name, o.id FROM customers c JOIN orders o ON o.customer_id = c.id WHERE c.id = 3;
Filter (o.customer_id = c.id)
  Join
    Filter (c.id = 3)
      Rowid lookup customers rowid = ?
    Scan orders AS o
db> EXPLAIN SELECT c.name, o.id FROM customers c JOIN orders o ON o.customer_id = c.id WHERE c.rowid = 3;
Filter ((c.rowid = 3) AND (o.customer_id = c.id))
  Join
    Scan customers AS c
    Scan orders AS o
```

### Why evaluating a name did not change

Telling tables apart is done once per statement: `resolve_names()` binds
a column of a table to that table's base plus the column
(`e->col = it->base + c_hit;`), and `eval()` reads a column as it always
has:

```
    case E_COLUMN:
        if (!row || e->col < 0 || e->col >= row->ncols)
            return err("no such column: %s", e->name);
        *out = row->cols[e->col];
        return 0;
```

So the Filter, the Sort and the result columns run their old code on
joined rows. With one table the base is 0, the slot is the column, and a
rowid name still reads the row's rowid: a one-table query binds as before,
and `plan_select()` hands it to 05.03's planner untouched.

## Decide the boundary

This engine nests the loops in the order the FROM clause names the
tables, always. sqlite3 chooses. In SQLite 3.54.1, where.c's
`wherePathSolver` "attempts to find the lowest cost path that visits each
WhereLoop once", a WhereLoop being one way to read one table, and only
CROSS JOIN and the outer joins keep a table behind the ones written
before it (`whereLoopAddAll`). Run it showed the result on this lesson's
first join. Pin the order with CROSS JOIN, and sqlite3 still will not
scan orders once per customer: it builds an index on orders' customer_id
for the length of the statement, with a Bloom filter in front
(`constructAutomaticIndex`), for six rows, because without ANALYZE it
takes every table to hold about a million (build.c):

<!-- verify: session host cwd=project -->
```
$ sqlite3 shop.db 'EXPLAIN QUERY PLAN SELECT c.name, o.id, o.total FROM customers c CROSS JOIN orders o ON o.customer_id = c.id'
QUERY PLAN
|--SCAN c
|--BLOOM FILTER ON o (customer_id=?)
`--SEARCH o USING AUTOMATIC COVERING INDEX (customer_id=?)
$ sqlite3 -list shop.db 'SELECT c.name, o.id, o.total FROM customers c CROSS JOIN orders o ON o.customer_id = c.id'
Ada|10|30
Ada|12|50
Brook|13|20
Chen|14|5
Chen|11|15
```

The index's key is customer_id, then the other columns the query reads,
then the rowid, so Chen's orders come out by total. A fixed order asks
whoever writes the query to know which table is small and which
condition narrows; get it wrong, and every row of one table meets every
row of the next before a condition can drop a pair.

The joined row is a choice too. SQLite builds none: each table in the
loop has a cursor, and a column is read from its table's cursor when an
expression needs it (`sqlite3ExprCodeGetColumnOfTable` emits `OP_Column`
on that cursor). PostgreSQL 18.7 keeps the two rows apart as well:
`ExecNestLoop` in nodeNestloop.c sets `ecxt_outertuple`, rescans the inner
plan, sets `ecxt_innertuple` for each inner row and tests the join's
conditions on the two, the planner having rewritten every name into
"outer" or "inner" and a position (setrefs.c, `set_join_references`).
Only a pair that passes is projected into one new row (`ExecProject`),
holding only the values the plan above needs. This engine's row holds
every value of both tables for every pair it looks at, kept or not, at
the cost of copying the inner row into it each time, and gets in return
an `eval()` that never learned about joins. The order is the larger choice,
and one question decides it: who knows more about the data, the person
who writes the query, or an engine that knows only what it has measured?

## Break it

Stop the inner side from starting again: in `join_next()` in
build/at/db/08.01/src/exec.c, delete the line
`op->inner->started = 0;`, then run the engine on the same file:

<!-- verify: patch file=src/exec.c
-            op->inner->started = 0;
-->
<!-- verify: session run="./learn run db --at 08.01 -- shop.db" -->
```
db> SELECT c.name, o.id, o.total FROM customers c JOIN orders o ON o.customer_id = c.id;
Ada|10|30
Ada|12|50
```

The inner scan runs once, for Ada. When Brook comes it is already past
its last row and says so at once, and the same for Chen and Dee: they are
read, and each is paired with nothing. Nothing fails; the answer is just
short, and looks like an honest one. A nested loop is one only if the
inner loop runs in full for every outer row.
