# 08.05 GROUP BY, HAVING and DISTINCT

The aggregates of 08.04 fold a whole table into one row, but most
questions want a row per something: orders per customer, money per
city. This lesson finds the groups by sorting the rows and watching the
key change, filters them with HAVING, and drops repeated rows with
DISTINCT by remembering the ones already handed up.

## Where this fits

![Where 08.05 fits](figures/08.05-map.svg)

The Aggregate of 08.04 gets a Sort under it, which puts each group's
rows next to each other, and learns to finish one group and start the
next in a single pass. Above it a Filter checks HAVING on each group's
row; a new operator, below ORDER BY, lets a row through only if its
result is new. The scans, joins and filters below are unchanged.
Afterwards the engine answers "per customer" and "per city" questions,
keeps the groups that pass a test, and lists or counts the different
values of a column, with sqlite3's answers.

## The idea

![The orders sorted by customer_id, NULL first, walked from the top: each time the key changes, the group behind is finished and its row comes out: NULL 1 40, 1 2 80, 2 1 20, 3 2 20.](figures/08.05-groups.svg)

"How many orders has each customer placed, and for how much?"
`SELECT count(*), sum(total) FROM orders` answers 6 and 160, one row for
the whole table. The question wants a row per customer: the orders split
into **groups**, one per value of customer_id, and the aggregates run
once per group. In SQL that is `GROUP BY customer_id`, and the value a
group's rows share is its **key**.

An Aggregate holds the state of one group at a time (08.04), so each
group's rows must come one after another. Sort the rows by the key
first, with the Sort of 04.03, then walk them: step each row as before,
and when a row's key differs from the group's, the group is over. Finish
it, hand up its row, clear the state, and let this row start the next
group; when the input ends, finish the last one. Sorted by customer_id,
order 15 comes first, since NULL sorts before every number (04.03), then
10 and 12 for customer 1, 13 for customer 2, 11 and 14 for customer 3:
the key changes three times and the input ends once, four groups, four
rows. Two NULL keys would make one group: for grouping, as for sorting,
NULL equals NULL. The groups come out in key order, the order the walk
meets them in.

**HAVING** is WHERE after the groups. WHERE is checked on the rows
before they reach the Aggregate, where there is no count(*) yet. HAVING
is checked on each group's row, above it, where an aggregate is a slot
like a column (08.04). A condition on the key alone, such as
`customer_id > 1`, means the same in either place, since every row of a
group has the group's key; so the engine moves it to WHERE, as sqlite3
does, and the rows of a group it rules out are never sorted or added up.
ORDER BY's Sort and LIMIT come above HAVING, as for any rows.

![The operator tree of a grouped join, bottom to top, with the rows on every edge: 4 customers, 24 pairs, 5 that match, sorted by city, 2 groups, 1 past HAVING, sorted for ORDER BY.](figures/08.05-pipeline.svg)

**DISTINCT** wants each different result once. `SELECT DISTINCT city
FROM customers` reads four rows and must print London once. No sort is
needed: keep a **set** of the results handed up so far, and pass a row
on only if its result is not in it yet, adding it. The rows come out in
the order first seen: London, Paris, Oslo. Two NULLs are the same
result, and so are 1 and 1.0. The same set gives `count(DISTINCT city)`:
an aggregate written with DISTINCT has a set of its own, emptied when a
group starts, and a value steps it only the first time the group has it.

![SELECT DISTINCT city FROM customers: London, Paris and Oslo go into the set and through; Chen's London is found there and stopped.](figures/08.05-distinct.svg)

### new_group: a new group starts

Asked by the Aggregate for each row once a group has begun: does this
row's key differ from the group's? Term by term, as the sort compared.

### set_add: a row not seen before

The set: finds a list of values by its hash, compares it with the lists
there, and keeps a copy if it is new.

### distinct_new: DISTINCT inside an aggregate

Makes an aggregate's set when its first value comes, and asks the set
whether this value is new to the group.

sqlite3 sorts the groups and keeps DISTINCT's rows seen in temporary
B-trees; this engine prints the same lines, though its set is a hash
table. Order is where the two can part. With no index both give groups
in key order and DISTINCT's rows in first-seen order; an index on the
column lets sqlite3 read the rows in the index's order instead, with no
sort and no set. The same rows, in another order: `GROUP BY city` on
desc.db is Paris, Oslo, London in sqlite3 too, and London, Oslo, Paris
here, which always sorts. Only ORDER BY promises an order.

## How it works

### Equal is what the sort calls equal

The Sort orders rows with `value_compare()`, and `new_group()` ends a
group where the same function finds a difference:

```
        if (value_compare(&a, &b) != 0)
            return 1;
```

They must agree. A walk stricter than the sort, one that also compared
types, would split a key the sort put together into several groups; a
looser one would print a key twice. With order 15's NULL key replaced by
1.0, then by '1':

<!-- verify: session run="./learn run db --at 08.05 -- shop.db" -->
```
db> SELECT coalesce(customer_id, 1.0) AS k, count(*) FROM orders GROUP BY k;
1|3
2|1
3|2
db> SELECT coalesce(customer_id, '1') AS k, count(*) FROM orders GROUP BY k;
1|2
2|1
3|2
1|1
```

Numbers compare by value, so 1.0 joins customer 1's group, which shows
its first row's key, 1. A text never equals a number and sorts after
them all (04.03), so '1' is a group of its own, last. sqlite3 prints the
same, and DISTINCT treats the three the same way.

### A number hashes by its value

The set compares a list, with `same_list()`, only with the lists in the
slots its hash leads to. Lists it calls equal must therefore hash alike,
or the second is never compared with the first and comes out again. 1
and 1.0 are equal but stored as an integer and a double, so `set_hash()`
hashes a real that is a whole number in range as that integer:

```
            if (v->type == V_INT || (r == floor(r) && r >= -9223372036854775808.0 && r < 9223372036854775808.0)) {
                i64 x = v->type == V_INT ? v->i : (i64)r;
                tag = V_INT;
```

Cut the test to `if (v->type == V_INT)` and
`SELECT DISTINCT coalesce(customer_id, 1.0) FROM orders` prints 1, 3, 2
and then 1.0. The **invariant**: lists the comparison calls equal hash
alike. Text and blobs are equal only byte for byte, and hash their bytes.

### What each operator copies, and when

The Aggregate learns that a group is over from the row that starts the
next, and in the same call steps that row into the cleared state and
takes it as the new group's row. So `group_done()` first copies the
finished row and each answer into its own arena, emptied only when the
Aggregate is asked again:

```
        op->row.cols[w + k] = keep(&op->outa, v);
        agg_clear(&q->aggs[k]);
```

A max() of text points into its aggregate's arena (08.04), which
`agg_clear()` empties, and the group's row into one `take_row()` empties
for the new row: uncopied, the row handed up would show the next group.
The Distinct's values are computed by `eval()` into db->rowa, which is
emptied for each row it drops, or point into a page the statement loop
may let go (08.01). So `set_add()` copies each new list into the set:

```
        copy[k] = keep(&s->arena, vals[k]);
```

It is 08.01's **invariant**: an operator that keeps a value past the
next call to its child keeps its own copy. The set holds one of every
different result until the statement ends.

## Decide the boundary

This engine groups by sorting, as SQLite always does. SQLite 3.54.1's
select.c (`sqlite3Select`) begins "a loop that will extract all source
rows in GROUP BY order", with "an OP_Sort in between" or "an index",
compares each row's GROUP BY terms with the previous row's, and outputs
a row "whenever the GROUP BY changes"; no hash table groups rows
anywhere in it. For DISTINCT this engine hashes, where SQLite keeps a
temporary B-tree index (`codeDistinct`: "Build an ephemeral table that
contains all entries seen before").

PostgreSQL 18.7 chooses per query. Its planner (planner.c,
`add_paths_to_grouping_rel`) makes one plan that groups sorted input,
AGG_SORTED, and one that groups into a hash table, AGG_HASHED, "since
input order won't matter", and keeps the one its estimates call cheaper;
DISTINCT gets the same choice. The hash table holds an entry per group,
and since PostgreSQL 13 one that outgrows work_mem times
hash_mem_multiplier (2.0 by default) spills: rows of groups not in it
yet go to disk in partitions, to be grouped later (nodeAgg.c, "Spilling
To Disk"). Before 13 it stayed in memory "no matter how large it got",
the release notes say.

What decides is what each costs in memory and the order its rows come
out in. A sort holds every row (in memory here, 04.03) and hands the
groups up in key order, which an ORDER BY on the key can use; this
engine sorts again anyway, where sqlite3 drops the second sort. A hash
table holds one entry per group however many rows feed it, needs no
sort, and gives the groups in no order worth having. So: are there many
more rows than groups, and does anyone want the groups in key order?

## Break it

Take away the Sort under the Aggregate: in `plan_top()` in
build/at/db/08.05/src/plan.c, delete the line
`op = op_sort(db, op, by, s->ngroup);`, then run the engine on the same
file:

-            op = op_sort(db, op, by, s->ngroup);
-->

```
db> SELECT customer_id, count(*), sum(total) FROM orders GROUP BY customer_id;
1|1|30
3|1|15
1|1|50
2|1|20
3|1|5
|1|40
```

The Aggregate still does its job exactly, ending a group wherever the
key changes. The scan hands up the orders in rowid order, customers 1,
3, 1, 2, 3 and NULL, so the key changes at every row: six groups of one,
each the right answer for a run of rows that is not a group. The walk
finds groups only because the sort put each group's rows together.
