# 05.02 Index lookups and range scans

An index is only useful if a query can read a piece of it: jump to the
first entry that might match, walk forward while entries still match, and
fetch each matching row from the table. This lesson adds the two
operators that do that, one for a range of rowids and one for a range of an
index.

## Where this fits

![Where 05.02 fits](figures/05.02-map.svg)

The previous lesson gave the table a second B-tree, sorted by a column. Queries
still read rows through the executor's bottom operator, the one that until
now could only scan a whole table from its first row. This lesson gives that
operator two more ways to read: a stretch of the table between two rowids,
and a stretch of an index between two values, going back to the table for
each row. Which way a query uses is the planner's choice, made in the next
lesson; here the choice is taken as given. Once the planner makes it, a
lookup by an indexed value reads a handful of pages instead of the whole
table.

## The idea

`WHERE a = 7919` is a range with both ends at 7919.
`WHERE a BETWEEN 100 AND 105` is a range with two ends, and `WHERE a > 5`
a range with one. So one operator can answer all of them: put a cursor on
the first index entry that is not below the lower bound, hand out entries in
order, and stop at the first one past the upper bound.

Each entry is `(a, rowid)`, and the query wants the row, so for every entry
the operator descends the table's tree to that rowid. The whole cost of
`WHERE a = 7919` is then five page reads: page 1 to find the index, the
index's root and one of its leaves, the table's root and one of its leaves.
A scan reads all 496 pages of 05.01's file.

![WHERE a = 7919 on demo.db: page 1, two pages of the index, two pages of the table.](figures/05.02-lookup.svg)

A range of rowids is the same idea without the second tree: the table is
already sorted by rowid, so `WHERE id > 19997` seeks to rowid 19997 and
walks forward, and the rows it wants sit next to each other on one leaf.

How the bottom operator should read is written down as an **access path**:
a kind (a scan, a rowid lookup or range, an index lookup or range), the
index to use, and the constant expressions of the lower and upper bound.
`op_scan`, the function that builds the bottom operator, now looks at the
access path and builds the scan or one of the two operators below. Filling
in the access path is the planner's job, in 05.03; until then every query
gets a scan.

### rowid_range_next: a range of the table itself

The bottom operator of a query whose WHERE pins or bounds the rowid. It
needs only the table: one seek to where the range starts, and from there
the table's own order does the rest.

### index_range_next: a range of an index

The bottom operator of a query whose WHERE pins or bounds an indexed
column. It runs two cursors: one on the index, walking entries, and one on
the table, jumping to each entry's rowid to fetch the row.

Both hand back rows like the plain scan does, so the Filter, Sort and Limit
operators above them (module 04) do not know or care how the rows were
found.

## How it works

### Writing index_range_next, step by step

Built up from the simplest operator that works, one chunk at a time.

1. **Every row, in index order.** The first version walks the whole index
   and turns each entry into its row: decode the entry, take its last
   field as the rowid, and seek the table to it. This already answers
   every query correctly, with the Filter above it doing all the choosing;
   it is just slow. An entry whose row is not there means the index and
   the table disagree, and the engine stops (below).

   ```
   int n = record_decode(op->icur.payload, op->icur.npayload, key, ix->ncols + 1);
   ...
   i64 rowid = key[ix->ncols].i;
   if (!cursor_seek_rowid(&op->cur, rowid) || op->cur.rowid != rowid)
       fatal("database is corrupt: index %s points at row %lld, which is not there", ix->name, (long long)rowid);
   decode_row(op->table, &op->cur, &op->row);
   *out = &op->row;
   return 1;
   ```

   `key` has nine slots, as in 05.01: up to eight indexed columns and the
   rowid.

2. **Start at the lower bound.** A `next` function is called once per row,
   so it has to remember whether it has started: the first call positions
   the cursor, later calls step. When the range has a lower bound, that
   first call seeks there instead of going to the first entry: one field
   compared, bias -1, both explained below. Now `a = 7919` skips every
   entry below 7919.

   ```
   if (!op->started) {
       op->started = 1;
       more = op->has_lo ? cursor_seek_key(&op->icur, op->key.p, (u32)op->key.n, 1, -1) : cursor_first(&op->icur);
   } else {
       more = cursor_next(&op->icur);
   }
   ```

3. **Stop at the upper bound, and stay stopped.** The first entry past the
   bound ends the range, and the operator records that in `done`, checked
   first on every call. Without `done`, a second call after the end would
   step the cursor on into entries that do not match. Now `a = 7919` reads
   its one match, looks at the entry after it, and stops.

   ```
   if (op->has_hi && value_compare(&key[0], &op->hi) > 0) {
       op->done = 1;
       return 0;
   }
   ```

`rowid_range_next` is the same build without the second tree: it seeks the
table itself with `cursor_seek_rowid`, compares the cursor's rowid with the
upper bound, and decodes the row it is already on.

### Why it is built this way

**The seek compares one field and lands before the ties.** The lower bound
is built into a one-field record, and the index cursor seeks it comparing
only the first field of each entry, so the rowid in the entry is ignored.
That leaves a question for the entries equal to the bound: does the probe
land before them or after them? The **bias** answers it: -1 lands before
every equal entry, which is what the start of a range needs. Equal entries
are in rowid order, so `WHERE a = 7` reads `(7, 1)`, `(7, 8)`, `(7, 9)` and
stops at `(9, 2)`.

![Among equal keys, bias -1 lands before the first and bias +1 after the last.](figures/05.02-bias.svg)

**The two bounds are kept in two forms.** The lower bound is used once, by
the seek, which compares records with records, so it is stored already
encoded as one (`op->key`). The upper bound is checked against every entry
after decoding it, so it stays a plain value (`op->hi`). Only the entry's
first field is compared with it, because the planner of 05.03 only ever
bounds an index's first column.

**Bounds are always inclusive, and WHERE checks the rest.** `a > 5` seeks to
the first entry with `a >= 5`, and the scan stops after the last entry equal
to the upper bound, even for `<`. Rowid bounds are even rougher:
`id > 19997.5` is widened to start at 19997, a whole number. Every row the
operator produces still goes through the Filter above it, which evaluates
the full WHERE clause, so the extra rows at the edges are dropped there. The
operator never has to get strictness, mixed types or rounding exactly
right; it only has to never read *less* than WHERE accepts.

**A range stops; a filter would not.** Without step 3 the operator would
still be correct, because the Filter above it re-checks every row, but it
would read to the end of the index. The upper bound is what makes the work
stop where the matches stop.

**One table seek per entry.** For each entry the table cursor seeks the
rowid from the root. Neighbouring entries rarely mean neighbouring rows, so
a range of k matches costs about k descents of the table. An entry whose
row is not there is not a missing match; it means the index and the table
disagree, so the engine stops with `database is corrupt` rather than
quietly returning less.

**Impossible ranges are caught before any read.** `op_scan` evaluates the
bounds once, when it builds the operator, with the column's affinity
applied, and copies any text into the statement's arena, which lasts until
the statement ends (unlike the row arena, emptied after every row). A bound
of NULL matches nothing, and a text bound on the rowid is either no bound
(every integer sorts below text) or no rows; those cases set the operator to
done from the start. The operator's struct gains a second cursor and the
bounds for all this, and `op_close` frees them.

The lookup finds nothing, and the range loses its first row. With +1 the
seek lands after every entry equal to the bound, so the entries equal to the
lower bound are skipped, and for an equality those are all the matches.
The query does not fail; it returns a wrong answer that looks like an
honest empty result.

## Decide the boundary

This operator fetches each row the moment it reads its entry, in index
order, so the table is read in a scattered order: a range of 1000 entries
can touch 1000 different leaves, some of them more than once. Another design
reads the whole range of the index first, sorts the rowids, and only then
fetches the rows in table order, touching each leaf once (PostgreSQL's
bitmap heap scan does this). It pays with memory for the rowids, a sort,
and losing the index's order, which an `ORDER BY a` would then have to
redo. How many rows does a typical range return, and how many of them share
a leaf?
