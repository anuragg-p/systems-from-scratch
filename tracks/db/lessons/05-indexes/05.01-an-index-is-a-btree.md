# 05.01 An index is a B-tree

Finding a row by its rowid takes a few page reads; finding it by any other
column means reading the whole table. An index fixes that by keeping a
second B-tree, sorted by the column you search on, that points back at the
rows.

## Where this fits

![Where 05.01 fits](figures/05.01-map.svg)

The engine can already store rows, find them by rowid, and run SELECT,
INSERT, UPDATE and DELETE over them, but every question about any other
column is answered by a full scan. This module adds the missing half of a
real database: indexes, and a planner that decides when to use them. This
first lesson builds the index itself: one more B-tree in the same file, made
of the B-tree pages from module 02, filled from the table when it is created
and kept in step with it ever after. Once it exists, sqlite3 can already use
it; our engine learns to in the next two lessons.

## The idea

Take the 20000-row table of this module,
`t(id INTEGER PRIMARY KEY, a INTEGER, b TEXT)`. Its B-tree is sorted by
rowid, which is useless for `WHERE a = 2`: the row with `a = 2` could be on
any of its 494 leaves, so the engine reads all 496 pages of the file to
find one row.

If the same rows were also kept sorted by `a`, the search would be the same
walk down a tree that a rowid lookup is. That is all an index is: a second
B-tree whose keys are the indexed column. Each entry is small, because it
holds only the indexed value and a way back to the row, and the way back is
the rowid. Row 2062 has `a = 2`, so the index holds the entry `(2, 2062)`.

![Row 2062 in its table leaf, and its entry in the index: the key is the value of a, then the rowid.](figures/05.01-entry.svg)

The rowid is in the key for a second reason. Two rows may have the same `a`;
with the rowid as the last field, their entries still differ and still sort,
by rowid. So every entry in an index is unique, and a B-tree never has to
cope with equal keys.

The index lives in the same file as the table, as its own tree of pages,
named in `sqlite_schema` by its root page like a table is. The file format
fixes one difference between the two trees. A table is a B+tree: its
interior pages hold only rowids as signposts, and every row sits in a leaf.
An index is a plain B-tree: its interior pages hold whole entries too, each
between the two children it separates. The cursor of 02.04 already walks
both kinds.

![The table and its index in demo.db: two trees, one entry per row, and the entry's rowid leading back to its row.](figures/05.01-trees.svg)

Two pieces of code make an index, and the page shows them next.

### index_key: what an entry is

Everything that touches an index needs the entry for a given row: creating
the index, and every INSERT, UPDATE and DELETE afterwards. `index_key`
builds it: the values of the indexed columns, then the rowid, encoded as one
record with the same record format the table uses (01.03).

### index_build: filling a new index

`CREATE INDEX` makes an empty index tree and records it in `sqlite_schema`;
then the index has to catch up with the rows that are already there.
`index_build` walks the table from its first row to its last and adds an
entry for each.

```

```

Three pages through the index (page 1, the index's root and one of its
leaves; the entry `(2, 2062)` already holds everything this query asks
for), against all 496 without it. The integrity check looks up every row in
every index and every entry in its table, so `ok` means all 20000 entries
are right.

## How it works

### Writing index_key and index_build, step by step

1. **An entry is the indexed values, as a record.** An index knows its
   columns by their position in the table (`ix->cols[i]`), so the key
   starts as those values, in the order the index lists them; with one
   column, as here, that is just `a`. The file format says an index cell's
   payload is a record, in the same format as a row (01.03), so the
   encoder that already exists does the rest. The output buffer is emptied
   first because its callers reuse one buffer for many keys.

   ```
   void index_key(Index *ix, Row *row, Buf *out)
   {
       Value vals[9];
       for (int i = 0; i < ix->ncols; i++)
           vals[i] = row->cols[ix->cols[i]];
       ...
       out->n = 0;
       record_build(out, vals, ix->ncols + 1);
   }
   ```

   Nine slots are enough because an index keeps at most eight column
   numbers (`cols[8]` in its struct), and one more value follows them.

2. **Append the rowid as one more value:** the way back to the row, and
   what keeps two equal values apart.

   ```
   vals[ix->ncols].type = V_INT;
   vals[ix->ncols].i = row->rowid;
   ```

3. **Fill a new index by walking the table.** `index_build` uses the cursor
   of 02.04 to visit every row and adds each one's entry with `index_add`,
   which opens a cursor on the index's root and inserts the key. The last
   argument of `cursor_open` says which kind of tree it walks: 1 for a
   table, keyed by rowid, 0 for an index, keyed by whole records. The full
   row is decoded rather than the record read directly, because
   `decode_row` (04.01) already puts the rowid into an INTEGER PRIMARY KEY
   column and fills in the columns an old row lacks.

   ```
   for (int more = cursor_first(&c); more; more = cursor_next(&c)) {
       decode_row(t, &c, &row);
       index_add(db, ix, &row);
   }
   ```

### Why it is built this way

**The rowid is a field, not the key.** In a table cell the rowid stands
outside the record, as the cell's integer key. In an index there is no
integer key at all: the whole cell is the record, and the rowid is just its
last field. That is why `index_key` appends the rowid to the values instead
of passing it separately, and why the lookup that comes in 05.02 can find it
by decoding the entry like any record.

**Entries compare field by field.** A table's tree compares integer keys;
an index's tree compares whole records, one value at a time, in SQLite's
order: NULL, then numbers, then text, then blobs. Because the rowid is the
last field, two entries with the same value are told apart by their rowids,
which is what makes every entry unique.

**Building walks the table in rowid order, not index order.** `index_build`
inserts entries in whatever order the table hands them out, which for this
table is a scattered order of `a`. Each insert is a full B-tree insert, with
a split wherever a page fills. It is the simplest way to build an index and
it is correct. sqlite3 does it differently: it sorts all the entries first
and then writes them in order, which fills every page. 07.01 measures what
the difference costs in file size.

**The table's cursor survives the inserts.** `index_build` holds a cursor on
the table while it inserts into another tree. That is safe because the
inserts only change the index's pages; the table's pages, and so the
cursor's position in them, are untouched.

### Keeping the index in step

An index is only useful if it never disagrees with its table. For every row
there must be exactly one entry in each index, made from that row's current
values and its rowid, and no other entry. `index_build` makes that true when
the index is created; three changes to module 04's statements keep it true,
and they make up most of the other code this lesson adds:

- **INSERT** stores the row, then adds its entry to every index of the
  table (`insert_row`).
- **DELETE** removes a row's entries before the row itself, since the
  row's values are what find them. `exec_delete` decodes the row and copies
  its values out of the page first (`keep_row`), so they stay valid while
  other pages change, and it seeks the row again, a cheap check that it is
  still there, before deleting it.
- **UPDATE** touches an index only when the entry would change: when an
  indexed column or the rowid changes (`index_changes`). Most updates leave
  the indexes alone. The check compares the type as well as the value,
  because 1 and 1.0 compare equal but are stored differently, and the entry
  must hold the row's value exactly.

The rest is plumbing. `create_index` refuses what the engine could not keep
in step: a name starting with `sqlite_`, the table `sqlite_schema` itself
(root page 1), a table the engine may only read, a name already taken, a
column the table does not have. When a file is opened, `schema_load` builds
each index from its `CREATE INDEX` text once every table is known, and an
index it cannot understand makes its table read-only rather than let it
fall out of date. DROP INDEX needs nothing new: the DROP of 03.03 already
frees an index's pages.

## Break it

Leave the rowid out of the key: in `index_key`, change
`record_build(out, vals, ix->ncols + 1);` to
`record_build(out, vals, ix->ncols);`, run `make`, then build the index on
a fresh table and ask sqlite3 about it:

`CREATE INDEX` succeeds: entries of one field sort and insert as well as
entries of two. But nothing in them leads back to a row. sqlite3 looks for
`(a, rowid)` and finds only `(a)`, so its check reports every row missing
(it stops at 100 errors), and a lookup through the index finds no rowid to
follow and calls the file malformed. Our own engine still answers, because
it still scans the table and never reads the index.

index can say that a value exists, but not where.

## Decide the boundary

This index stores the indexed column and the rowid, and nothing more, so a
lookup that wants any other column pays a second descent, into the table.
Another design stores more: a covering index includes the columns a query
needs, so the table is never read (sqlite3 does this for you whenever an
index already holds every column a query uses, as in the three-page lookup
above), and a clustered index goes all the way and stores the rows
themselves in the index's order, as sqlite3's WITHOUT ROWID tables and
MySQL's InnoDB do. Each extra column makes every entry bigger and every
write to that column one more B-tree change. How often do your queries read
columns the index does not have, against how often they write the ones it
does?
