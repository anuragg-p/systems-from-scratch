# 05.03 Choosing a plan, and EXPLAIN

A query says which rows it wants, never how to find them. Something has to
look at the WHERE clause and decide: the rowid, an index, or every row. This
lesson adds that decision, five rules tried in order, and the commands that
show it.

## Where this fits

![Where 05.03 fits](figures/05.03-map.svg)

The parser hands over a tree for the statement; the executor runs a tree of
operators. Between them sits the planner, which picks how the bottom
operator reads the table and whether a sort is needed on top. Until now it
had only one answer, read every row; the previous lesson added faster ways
to read, and this lesson decides when to use them. Afterwards the engine
picks an index on its own, and EXPLAIN shows the choice in sqlite3's words,
so the two engines can be compared plan for plan.

## The idea

![The five rules, tried in order, each with an example from demo.db and the plan it gives.](figures/05.03-ladder.svg)

Look at `SELECT * FROM t WHERE id = 2 AND a = 6`. Two of its conditions
could each find the row without a scan: the rowid is fixed, and `a` has an
index. Either works; the rowid is cheaper, because it is one descent of one
tree instead of a descent of the index and then one of the table.

So the planner does not search for a perfect plan. It splits the WHERE
clause into the conditions joined by AND, notes which of them compare a
column with a constant, and tries five rules in order: the rowid equal to a
constant, an indexed column equal to one, the rowid bounded, an indexed
column bounded, and otherwise a scan. The first rule that matches wins.
Equalities come before ranges because they usually match fewer rows, and
the rowid comes before an index because it needs no second tree.

Whatever it picks, the full WHERE clause is still checked on every row the
plan reads (the Filter operator of 04.02 sits on top of the plan). That is
what keeps the planner small: a plan may read more rows than it needs, and
then it is slow, but whether a row matches is always decided by WHERE
itself, never by the plan.

### choose_access: how to read the table

Called once per statement that reads a table, SELECT, UPDATE and DELETE
alike, before any operator exists. It gets the table and the WHERE clause
and fills in an access path: a scan, a rowid lookup or range, or an index
lookup or range with its bounds. The operator of 05.02 is built from it.

### sort_needed: when ORDER BY costs nothing

A B-tree hands rows out in its own order: a table in rowid order, an index
in order of its first column and then rowid. When ORDER BY asks for exactly
that order, the Sort operator, which must read every row before it can hand
out the first, can be left out.

## How it works

### Writing choose_access, step by step

1. **Start from the scan, then try rule 1.** Before any rule is tried the
   access path is a scan, so a WHERE clause that matches no rule, or no
   WHERE at all, needs no code of its own. The WHERE clause is split into
   its ANDed terms, and `find_bounds` reports what they say about one
   column: an equality, a lower and an upper bound. Rule 1 asks about the
   rowid (`ROWID` stands for it, and for an INTEGER PRIMARY KEY column);
   an equality becomes a rowid range whose two ends are the same value, so
   the operator of 05.02 needs no separate case for it.

   ```
   acc->kind = ACCESS_SCAN;
   Expr *terms[64];
   int n = conjuncts(where, terms, 0, 64);
   Bounds b;
   find_bounds(t, terms, n, ROWID, &b);
   if (b.eq) {
       acc->kind = ACCESS_ROWID_EQ;
       acc->lo = acc->hi = b.eq;
       ...
       return 0;
   }
   ```

2. **Rule 2: an indexed column equals a constant.** Walk the table's
   indexes and ask about each one's first column. The first index with an
   equality wins, in the order the indexes were created; without knowing
   how many rows each would return, there is no better reason to prefer
   one. Like rule 1, it returns at once, so the order of the code is the
   order of preference and nothing later can overrule an earlier choice.

   ```
   for (Index *ix = t->indexes; ix; ix = ix->next) {
       Bounds ib;
       find_bounds(t, terms, n, ix->cols[0], &ib);
       if (ib.eq) {
   ```

3. **Rules 3 and 4: bounds on the rowid, then on an index.** The rowid's
   bounds were found for rule 1 already; if there is a lower or an upper
   one, the plan is a rowid range. Then a second loop over the indexes,
   this time for bounds. It has to be a second loop: an equality on any
   index must be preferred to a range on the rowid, so all the indexes are
   asked about equalities before the rowid's range is considered, and
   only then about ranges.

   Every rule copies the bounds into the access path along with whether
   each one is strict (`lo_incl`, `hi_incl`); nothing reads those yet,
   because the operators of 05.02 treat every bound as inclusive and leave
   the rest to the Filter.

### Why it is built this way

**Only conditions joined by AND count.** The WHERE clause is split at its
top-level ANDs, and each piece must hold for a row to match, so any one of
them may choose the rows to read. An OR is different: `a > 5 OR id = 3`
does not rule out a row that fails `a > 5`, so no single access path can
answer it, and it falls to the scan (sqlite3 runs two searches and merges
them; we do not).

**A bound is a column, a comparison and a constant.** For each column
`find_bounds` looks for `col = c`, `col > c` (and `<`, `<=`, `>=`) and
`col BETWEEN c1 AND c2`, with the constant on either side: `5 < a` is read
as `a > 5`. A constant is anything that does not depend on the row
(`is_constant`): `7`, `'x'`, `2 * 3`. An expression around the column, like
`a + 0`, is not the column, which is why it switches the index off. The first bound found on
each side is used, not the tightest: `a > 5 AND a > 10` reads from 5, and
the Filter throws away 6 to 10.

**Only an index's first column is looked at.** An index on `(b, c)` helps
conditions on `b` and nothing else. Using later columns needs the earlier ones
pinned by equalities, which is where sqlite3 goes further.

**A plan may read too much, never too little.** This is the one rule the
planner must not break, and the reason it can be so simple. Reading extra
rows costs time; reading too few gives a wrong answer that no later
operator can repair, because rows that were never read cannot be filtered
back in.

**When the sort can go.** A table plan produces rowid order, so `ORDER BY id`
(or `rowid`) ascending needs no sort, and since rowids are unique, later
ORDER BY terms cannot change anything. An index plan produces its first
column's order, so `ORDER BY a` alone, ascending, needs none; and an index
lookup on one value produces rowid order, so `ORDER BY id` alone is free
there too. Everything else gets a Sort, including any DESC: the cursor of
02.04 only steps forward, so a tree can hand out its order but not the
reverse.

**EXPLAIN QUERY PLAN mimics sqlite3 on purpose.** Its lines name the access
path the way sqlite3 does (`SEARCH t USING INDEX t_a (a>?)`), so a plan can
be set beside sqlite3's for the same query and compared line for line.
`explain_query_plan` prints SCAN or SEARCH from the access path's kind, and
USE TEMP B-TREE FOR ORDER BY when `sort_needed` asked for a Sort. Plain
`EXPLAIN` prints our operators instead, because that is what actually runs.
The parser marks the statement with which of the two was asked for, and the
executor builds the plan and prints it instead of running it.

## Break it

Let a lower bound pass for an equality: in `choose_access`, in the first loop
over the indexes, add `if (!ib.eq) ib.eq = ib.lo;` right after
`find_bounds(t, terms, n, ix->cols[0], &ib);`, then `make` (in
build/at/db/05.03/):

+        if (!ib.eq) ib.eq = ib.lo;

-->
<!-- verify: session cwd=project -->
```
$ ./db demo.db 'SELECT id, a FROM t WHERE a > 5' | wc -l
       0
$ ./db demo.db 'SELECT id, a FROM t WHERE a >= 5'
5155|5
$ ./db demo.db 'EXPLAIN QUERY PLAN SELECT id, a FROM t WHERE a > 5'
QUERY PLAN
`--SEARCH t USING INDEX t_a (a=?)
```

The plan now reads only the entries equal to 5. For `a > 5`, the Filter
rejects all of them and the answer is empty; for `a >= 5` it keeps the one
row with `a = 5` and loses every row above it. The re-check on top could fix
a plan that read too much; it is powerless against one that read too
little.

## Decide the boundary

This planner is **rule-based**: a fixed order of preferences, no knowledge
of the data. sqlite3 is **cost-based**: it estimates how many rows each
access path will produce and how many pages that will cost, and picks the
cheapest. After `ANALYZE`, which stores statistics about each index in the
file, sqlite3 plans `SCAN t` for `WHERE a >= 0` on the benchmark's table and
keeps the index for `WHERE a >= 999000`. That needs statistics, kept up to
date, and an estimate for every plan, all of which can be wrong in their own
ways. Rules are predictable and wrong in cases you can name, like the one
above. How skewed is your data, and who will notice when a plan goes bad?
