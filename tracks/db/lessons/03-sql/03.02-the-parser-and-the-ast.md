# 03.02 The parser and the AST

The tokenizer hands over a flat row of words. The parser finds the
structure in them and builds a tree that the rest of the engine can walk
without ever looking at text again.

## Where this fits

![Where 03.02 fits](figures/03.02-map.svg)

The parser sits just above the tokenizer, which it asks for one word at a
time. What it gives back is a tree: one node for the statement, holding
its parts (the columns, the table, the condition, the order), and a small
tree for every expression in it. Nothing above the parser reads SQL text:
the catalog in the next lesson and the code that runs statements in module
04 only ever see trees. After this lesson the engine can tell a
well-formed statement from a malformed one, and knows how every expression
in it is grouped.

## The idea

![The tree for one SELECT: a statement node with a branch for each clause, and an expression tree under WHERE.](figures/03.02-tree.svg)

`1 + 2 * 3` must come out as 7, not 9. The tokenizer gives five tokens in
a row and nothing that says which operator goes first. `10 - 4 - 3` must
be 3, not 9, though both operators are the same. A statement has the same
problem on a larger scale: `SELECT a FROM t WHERE a > 1 ORDER BY b` is a
list of words until something says that `a > 1` is the condition and `b`
the sort key.

The parser's answer is a tree. Each operator becomes a node whose children
are its operands, so the grouping is no longer a question: in the tree for
`1 + 2 * 3`, the `*` node sits under the `+` node, and evaluating the tree
bottom up gives 7. The statement becomes a node with one branch per
clause, as in the figure above. Building the tree is the parser's whole
job; it does not check that table `t` exists or that it has a column `a`.
A tree is many small nodes, so they all come from one **arena**: a block
of memory handed out in order and freed all at once when the statement
is done.

Statements are read by **recursive descent**: one function per piece of
the grammar, each looking at the current token to decide what comes next.
A SELECT's clauses come in a fixed order, so the function for SELECT
simply tries them in that order, and each optional clause announces itself
with its keyword.

Expressions need one more idea, because operators bind with different
strengths. Give each operator a number: `*` binds tighter than `+`, which
binds tighter than `<`, then `AND`, then `OR`. Now read an expression left
to right. Take the first operand; when an operator follows, read its right
side, but let that right side take only operators that bind *more
tightly* than this one. That single rule produces the grouping:

![1 + 2 * 3 - 4: the right side of + takes the tighter *, but not the -, which then takes 1 + 2 * 3 as its left side. On the right, the strengths op_prec() assigns.](figures/03.02-climbing.svg)

The right side of `+` sees `2`, then `*`, which binds more tightly, so
`2 * 3` goes in. Then it sees `-`, which binds no more tightly than `+`,
so it stops and hands back `2 * 3`. The `-` is still waiting, and it takes
everything built so far, `1 + 2 * 3`, as its left side. This is
**precedence climbing**, and it needs one function for all the levels
rather than one function per level.

### parse_binary: operators and precedence

Every expression in every statement goes through this function: the
result columns, WHERE, the values of an INSERT, the right side of SET,
ORDER BY. It is called with the weakest strength it may accept, reads one
operand, then keeps taking operators for as long as they bind at least
that tightly. It is short, but it is the place where `1 + 2 * 3` becomes
7.

### parse_select: the SELECT statement

When the statement starts with SELECT, this function builds its node: the
result columns first, then FROM, WHERE, ORDER BY and LIMIT, each one only
if its keyword is there. It also says no, clearly, to the parts of SELECT
this engine does not have (DISTINCT, GROUP BY, joins), instead of letting
them fail as a puzzling syntax error.

### db_exec: parse, run, repeat

A tree is no use until something runs it. The shell now hands the text
it collected to `db_exec`, in a new file, exec.c: ask the parser for one
statement, run it, free the arena, and go on to the next, stopping at the
first error. Running is a switch on the statement's kind. At this lesson
almost every kind is refused by name (`SELECT is not supported`), and
module 04 replaces those refusals one by one; only PRAGMA and BEGIN,
COMMIT and ROLLBACK do anything yet.

`SELECT is not supported` comes from exec.c, so it means the parser read
the whole statement and built its tree; that table `t` does not exist

token where it gave up: the `;` where WHERE needed a condition, and the
`2` that stands where the statement should have ended. Text that simply
stops in the middle is a third answer; the shell would wait for a `;`, so
pass it on the command line:

## How it works

### Writing parse_binary, step by step

1. **One operand, then a loop over operators.** Read an operand (a number,
   a name, a parenthesised expression, or one with a prefix such as `-` or
   NOT), then keep taking operators until one binds more loosely than the
   caller allows. Strength 0 means "not an operator", which is how an
   expression ends at a `,`, a `)`, FROM or `;` without this function
   knowing anything about them.
   ```
   Expr *left = parse_unary(ps);
   while (left) {
       int prec = op_prec(ps);
       if (prec == 0 || prec < min_prec)
           break;
       ...
   }
   return left;
   ```
2. **The right side, by recursion.** Step past the operator and read its
   right side with the same function, asking only for operators that bind
   more tightly, then loop with the new node as the left side. This is
   where `1 + 2 * 3` gets its shape: the call for the right side of `+`
   takes `2 * 3` and stops at anything weaker.
   ```
   int op = binary_op(ps->tok.type);
   advance(ps);
   Expr *right = parse_binary(ps, prec + 1);
   if (!right)
       return NULL;
   left = binary(ps, op, left, right);
   ```
3. **The forms that do not fit.** BETWEEN needs two more operands, IN a
   list in parentheses, IS may be followed by NOT. Reading one right
   operand for them would go wrong, so before step 2 they are handed, with
   the left side already read, to a function that knows each shape.

### Writing parse_select, step by step

1. **The keyword, the columns, the table.** The smallest SELECT is a list
   of expressions separated by commas, then maybe FROM and a name. Every
   failure returns -1 at once with the message already set (one global
   message, `errmsg`, which the shell prints).
   ```
   if (!expect(ps, TK_SELECT))
       return -1;
   do {
       ...
       if (!(rc->e = parse_expr(ps)))
           return -1;
   } while (accept(ps, TK_COMMA));
   ...
   if (accept(ps, TK_FROM)) {
       if (!(s->table = parse_name(ps)))
           return -1;
       ...
   }
   ```
2. **What a column can be.** `*` is stored as an empty expression and
   expanded once the table is known. `t.*` is the one place the parser
   must see two tokens ahead, so it saves its position, tries, and rewinds
   if the guess was wrong, and `t.a` still parses as a column. An alias is
   `AS name` or a bare name straight after, and only a plain name counts,
   so the FROM after a column is never swallowed as one.
   ```
   advance(ps);
   if (accept(ps, TK_DOT) && accept(ps, TK_STAR))
       continue;
   ps->z = save;
   ps->tok = tok;
   ```
3. **Say no by name.** DISTINCT, a join after the table, GROUP BY: each
   gets a message that says it is not supported.
   ```
   if (at(ps, TK_COMMA) || at(ps, TK_JOIN))
       return err("joins are not supported");
   ```
4. **The optional clauses, in SQL's order.** WHERE, then ORDER BY with
   ASC or DESC on each term, then LIMIT. Each one is announced by its
   keyword, so trying them in that order is all the grammar there is.
   ```
   if (accept(ps, TK_WHERE) && !(s->where = parse_expr(ps)))
       return -1;
   ```
5. **`LIMIT a, b`.** SQLite also accepts the older form in which the
   first number is the offset, so the two are swapped when a comma
   follows. What the function does not check is that the statement ends
   there. Its caller does, which is why `SELECT 1 2` failed at the `2`.

### Why it is built this way

**Why `prec + 1`.** When `parse_binary` reads the right side of an
operator, it asks for operators strictly tighter than the one it just
read. An operator of the same strength therefore stops the right side and
is picked up by the loop one level out, with everything so far as its
left side. That is what makes `10 - 4 - 3` mean `(10 - 4) - 3`: SQL's
binary operators all group from the left. Ask for `prec` instead and the
right side swallows the second minus too, giving `10 - (4 - 3)`, which is
9; sqlite3 says 3.

![The same tokens, two trees. With prec + 1 the first minus is grouped first; with prec the right side swallows the second minus too.](figures/03.02-assoc.svg)

That mistake would hide for a long time. Only chains of one strength are
regrouped, and for `+`, `*` and AND the regrouping almost never changes
the answer; `-` and `/` are where it shows.

**BETWEEN's AND is not a logical AND.** Inside the special forms, the
bounds of a BETWEEN are read at a strength above AND's. So in
`x BETWEEN 1 AND 9 AND 0` the lower bound stops at the first AND, which
BETWEEN then takes as its own, and the second AND is left to the loop as
a logical one.

**NOT is a prefix that binds loosely.** A minus sign in front of a number
binds tighter than anything. NOT is different: SQL wants `NOT a = b` to
mean `NOT (a = b)`, so the operand of NOT is read at the strength of a
comparison, not at the strength of a single operand. A unary `+` changes
no value, yet it is kept as a node of its own: `+n` is no longer a bare
column, and in 04.02 that decides whether a comparison converts its
other side.

**The parser does not look anything up.** The tree holds `t` and `a` as
plain text; whether they exist is checked when the statement runs. This
keeps the parser free of the catalog, and the next lesson depends on it:
when a database is opened, the CREATE TABLE statements stored inside it
are parsed again to rebuild the catalog, at a moment when there is no
catalog to look anything up in. So an expression node has two fields the
parser leaves at -1, the column a name refers to and that column's
affinity (the kind of value it prefers, 03.03); module 04 fills them in
once it knows the table, and turns a name that means the rowid into
E_ROWID.

**One arena per statement.** No node needs its own free, and an error
halfway through a statement can simply return NULL and leave the cleanup
to the arena. The one list kept elsewhere is INSERT's rows, which grow by
doubling while they are read: an arena cannot grow a block in place, so
that list lives on the heap until its length is known, then is copied in.

**Every other statement is the same pattern.** INSERT, UPDATE, DELETE,
CREATE, DROP and PRAGMA each get a function that tries its clauses in
order, like `parse_select`, and EXPLAIN is a flag set in front of any of
them. CREATE TABLE adds two things the
next lesson needs. It keeps the statement's own text, from the table's
name on, behind a fixed `CREATE TABLE ` prefix, because that text is what
the file stores as the table's description. And it parses constraints
this engine cannot enforce (UNIQUE, CHECK, REFERENCES and others) instead
of refusing them, and notes them in `s->unsupported`: a database that
sqlite3 wrote with them must still open, and such a table is then only
read, never written.

**Writes are wrapped before any exist.** `run_stmt` decides what a write
belongs to. Outside BEGIN it is a transaction of its own: committed when
it succeeds, rolled back when it fails, which 01.02's pager makes free
because the changed pages never reached the file. Inside BEGIN only the
failing statement may be undone, so the pager first keeps a copy of
every page the statement changes; a one-row INSERT skips that, because it
checks everything before it writes anything. 03.03's CREATE TABLE is the
first write to go through it.

## Break it

The strength a caller asks for decides where an expression stops. In
build/at/db/03.02/src/parse.c, in `parse_special`, read BETWEEN's lower
bound as a whole expression: change `e->b = parse_binary(ps, 5)` to
`e->b = parse_binary(ps, 1)`. Run `./learn run db --at 03.02` and try:

+        if (!(e->b = parse_binary(ps, 1)) || !expect(ps, TK_AND) || !(e->c = parse_binary(ps, 5)))

<!-- verify: session run="./learn run db --at 03.02" -->
```
db> SELECT 5 BETWEEN 1 AND 9;
Error: near ";": syntax error
db> SELECT a FROM t WHERE a BETWEEN 1 AND 9 ORDER BY a;
Error: near "ORDER": syntax error
```

AND binds more tightly than strength 1, so the lower bound took `1 AND 9`
as a logical AND. BETWEEN then looked for its own AND and found whatever
came after the 9. Every BETWEEN is now a syntax error, and it is reported
at the token after the upper bound, not at the AND that was taken.

## Decide the boundary

This parser is written by hand: about a thousand lines of C where every
rule is a function and every special case is an `if`. SQLite instead
writes its grammar in a file and generates the parser with Lemon, an LALR
parser generator. The generator checks the grammar for ambiguities and
makes the grammar file the documentation; a hand-written parser makes
precise error messages and odd corners (`LIMIT a, b` meaning
`LIMIT b OFFSET a`) easy, and needs no second tool. Every feature added
here (joins, GROUP BY, subqueries) adds rules that could clash with the
ones already written, and only a reader would notice. At what size does a
grammar become something you want a tool to check?
