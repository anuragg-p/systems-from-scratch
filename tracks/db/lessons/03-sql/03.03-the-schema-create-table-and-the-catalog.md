# 03.03 The schema: CREATE TABLE and the catalog

A database has to know its own tables: their names, their columns, and on
which page each one's B-tree starts. This engine, like SQLite, keeps that
list as an ordinary table inside the file, so CREATE TABLE is little more
than adding a row to it.

## Where this fits

![Where 03.03 fits](figures/03.03-map.svg)

The catalog is what turns names into places. The parser hands over a tree
that mentions a table by name; the catalog says which page that table's
B-tree starts on, what its columns are called, and how each column likes
its values stored. It stands on the B-tree layer and lives inside it: the
list of tables is itself a table, rooted on the first page of the file.
After this lesson CREATE TABLE and DROP TABLE work, and a file written by
sqlite3 opens here with all its tables known.

## The idea

![Page 1 after two CREATE TABLEs. Its rows name each table and the page its B-tree starts on; the columns live only in the CREATE text.](figures/03.03-page1.svg)

When a statement says `SELECT * FROM fruit`, the engine has to find
fruit's B-tree and know that its columns are `id` and `name`. That
knowledge has to survive closing the file, and since this file is meant
to be a real SQLite file, sqlite3 has to find it in the same place.

SQLite's answer is to describe the database with the database. Page 1 is
the root of a table called **sqlite_schema**, with one row per table and
index: its type, its name, the table it belongs to, its **root page**
(the page its B-tree starts on), and the CREATE statement that made it.
The B-tree code from module 02 stores these rows like any others.

Notice what is *not* in that row: a list of columns. The only description
of the columns is the CREATE statement's own text. To learn that fruit has
an `id` column, the engine parses
`CREATE TABLE fruit(id INTEGER PRIMARY KEY, name TEXT)` again with the
parser from the last lesson. The **catalog** this engine works with is the
list of tables it rebuilds that way, in memory.

Two pieces of code do this, one in each direction, and a third undoes the
first.

### create_table: CREATE TABLE

This runs when a CREATE TABLE statement executes, after the parser has
built its tree. It first refuses what the engine could not honour later: a
feature it does not support, a name it may not use, a column named twice.
Then it does three small things to the file: it makes an empty B-tree for
the new table (a table B-tree, keyed by rowid: that is the `1` passed to
`btree_create`), writes the table's row into sqlite_schema under a rowid
one above the largest there (the rule INSERT uses too, in 04.01), and adds
one to the **schema cookie**, a counter in the file header that tells
anyone else reading the file that the schema has changed.

![CREATE TABLE on an empty file, in order. Three steps change the file; the last rebuilds the catalog from it.](figures/03.03-create.svg)

### schema_load: read the catalog

This runs when the database is opened, and again after any statement that
changed the schema. It walks sqlite_schema from the first row to the last,
parses each CREATE statement, and builds the list of tables the rest of
the engine looks names up in: for each table its root page, its columns,
and each column's **affinity**, the kind of value it prefers to store
(module 04 uses it). The list is thrown away and built again from scratch
each time.

![The rows of page 1 on the left, the catalog in memory on the right. The column names and types come from parsing the CREATE text.](figures/03.03-catalog.svg)

### drop_object: DROP TABLE

DROP TABLE is CREATE run backwards. It finds the table's row in
sqlite_schema, and the rows of any indexes on it, gives every page of
each B-tree back to the freelist with 02.05's `btree_drop`, deletes the
rows, and bumps the cookie. The rows are collected in one pass and
deleted in a second, because a delete leaves the cursor unpositioned
(02.05), and a cursor that is still walking the table cannot afford that.

## Run it

Open a new file in the shell as it stands now, create two tables, and
ask the catalog about them:

<!-- verify: session -->
```
$ ./learn run db --at 03.03 -- schema.db
Running db as it stands at 03.03 (The schema: CREATE TABLE and the catalog). Its files are in build/at/db/03.03/
db: a SQL database, from scratch. Statements end with ;  .help for help
db> CREATE TABLE fruit(id INTEGER PRIMARY KEY, name TEXT);
db> CREATE TABLE veg(name);
db> .tables
fruit
veg
db> PRAGMA page_count;
3
db> PRAGMA schema_version;
2
```

Three pages: page 1 for the catalog, one empty B-tree each for fruit and
veg. The schema cookie is 2, one bump per CREATE. Rows cannot be put in
the tables yet; that is module 04. The CREATE text sits at the very end
of page 1, readable in the raw file:

<!-- verify: session -->
```
$ xxd -s 4032 -l 64 build/at/db/03.03/schema.db
00000fc0: 6672 7569 7466 7275 6974 0243 5245 4154  fruitfruit.CREAT
00000fd0: 4520 5441 424c 4520 6672 7569 7428 6964  E TABLE fruit(id
00000fe0: 2049 4e54 4547 4552 2050 5249 4d41 5259   INTEGER PRIMARY
00000ff0: 204b 4559 2c20 6e61 6d65 2054 4558 5429   KEY, name TEXT)
```

The byte `02` before `CREATE` is the root page. sqlite3 reads the same
catalog, all five columns of it:

<!-- verify: session -->
```
$ sqlite3 -list build/at/db/03.03/schema.db 'SELECT * FROM sqlite_schema;'
table|fruit|fruit|2|CREATE TABLE fruit(id INTEGER PRIMARY KEY, name TEXT)
table|veg|veg|3|CREATE TABLE veg(name)
```

The text stored is the statement from the table's name on, after a fixed
`CREATE TABLE `, which is also what sqlite3 stores. Back in the shell:

<!-- verify: session run="./learn run db --at 03.03 -- schema.db" -->
```
db> CREATE TABLE  IF NOT EXISTS  herb ( name TEXT , kind ) ;
db> .schema herb
CREATE TABLE herb ( name TEXT , kind );
db> CREATE TABLE nut(id INT PRIMARY KEY);
Error: a PRIMARY KEY that is not INTEGER PRIMARY KEY is not supported
```

A table that sqlite3 made with such a feature still opens. Here sqlite3
makes one with UNIQUE, which it backs with an index of its own:

<!-- verify: session -->
```
$ cd build/at/db/03.03
$ sqlite3 s3.db "CREATE TABLE u(a UNIQUE, b); INSERT INTO u VALUES (1, 'one');"
$ sqlite3 -list s3.db 'SELECT type, name, tbl_name, rootpage, sql FROM sqlite_schema;'
table|u|u|2|CREATE TABLE u(a UNIQUE, b)
index|sqlite_autoindex_u_1|u|3|
$ ./db s3.db .tables
u
```

The `./db` there is the build that `./learn run` just made. The second
row is that index. It has no CREATE text, and this engine could
not keep it up to date, so the catalog marks u read-only; from 04.01 on,
an INSERT into u is refused with that reason.

## How it works

### Writing create_table, step by step

1. **The three writes.** The working core is three calls: make an empty
   table B-tree, write the table's row into sqlite_schema, bump the
   schema cookie. The root page comes first because its number goes into
   the row.
   ```
   int create_table(Db *db, Stmt *s)
   {
       ...
       u32 root = btree_create(&db->pager, 1);
       schema_insert_row(db, "table", s->table, s->table, root, s->sql);
       schema_bump_cookie(db);
       return 0;
   }
   ```
2. **Refuse what cannot be kept.** The parser marks a statement that uses
   a feature this engine cannot maintain (UNIQUE, CHECK, AUTOINCREMENT, a
   PRIMARY KEY other than INTEGER PRIMARY KEY, ...). It does not refuse it
   itself, because the same parser must read such tables in files sqlite3
   made; only creating one is refused, here. Names starting with
   `sqlite_` are refused too: they belong to sqlite3's own tables.
   ```
   if (s->unsupported)
       return err("%s is not supported", s->unsupported);
   ```
3. **Names that clash.** A column named twice (ignoring case, as SQL
   names do), or a table name already used by a table or an index, since
   both share one set of names. With IF NOT EXISTS the statement quietly
   succeeds instead. All the checks come before the first write, so a
   CREATE that fails has changed nothing.

### Writing schema_load, step by step

1. **Start empty, then one table per row.** Throw the old catalog away
   and add sqlite_schema itself: there is no row for it, its five columns
   are fixed by the file format, and its root is page 1. Then walk page 1
   and turn every table row into a Table.
   ```
   arena_reset(&sc->arena);
   sc->tables = NULL;
   add_table(sc, builtin_schema_table(sc));
   ...
   for (int more = cursor_first(&c); more; more = cursor_next(&c)) {
       int n = record_decode(c.payload, c.npayload, v, 5);
       ...
       if (strcmp(type, "table") == 0) {
           ...
           add_table(sc, t);
       }
   }
   ```
2. **Copy the text out.** The decoded strings point into the page under
   the cursor, and those bytes change as soon as the cursor moves on, so
   each one is copied into the catalog's own arena first.
   ```
   char *name = keep_str(sc, v[1].s, v[1].type == V_TEXT ? v[1].n : 0);
   ```
3. **Parse the CREATE text.** The table's columns, their affinities and
   which column (if any) is the rowid all come from parsing the stored
   statement again. If the text cannot be parsed, the table is still
   added, marked opaque, so `.tables` lists it and a query on it gets a
   clear refusal. A WITHOUT ROWID table is opaque too: sqlite3 stores it
   as an index B-tree keyed by its primary key, not as rows under a
   rowid, so the code that reads tables cannot read it.
   ```
   Stmt *s = sql ? parse_schema_sql(sc, sql) : NULL;
   ...
   t = table_from(sc, s, root, sql);
   ```
4. **Everything else waits for a second pass.** An index or trigger row
   names a table that may come later in the file, so it is set aside and
   looked at once every table is known. An index row with no CREATE text
   is one sqlite3 made by itself for a UNIQUE or PRIMARY KEY constraint,
   like `sqlite_autoindex_u_1` in Run it; this engine cannot keep it up
   to date, so the table becomes read-only. So does a table with a
   trigger, or, until module 05 teaches the engine indexes, a table with
   any index at all.
   ```
   if (!later[i].sql) {
       t->readonly = "a UNIQUE or PRIMARY KEY constraint";
       continue;
   }
   ```

### Why it is built this way

**Rebuild, never patch.** After a CREATE the catalog in memory could be
updated by adding one table to the list. Instead it is thrown away and
read again from page 1. That costs a few parses, and buys one path for
everything: opening a file, creating a table, dropping one, and rolling a
transaction back all end with the same rebuild, so the catalog in memory
can never disagree with the file. A CREATE inside a transaction that is
then rolled back simply disappears on the next rebuild.

**Read what you cannot write.** A file from sqlite3 may use things this
engine does not maintain: a UNIQUE constraint, which needs an index the
engine would have to keep in step; a trigger; AUTOINCREMENT. Refusing to
open such a file would be unfriendly, and writing to such a table could
break what sqlite3 expects of it. So the table goes into the catalog
marked read-only, with the reason, and only writes will be refused.

**Only `INTEGER PRIMARY KEY` is the rowid.** Every table row already has a
64-bit key, the **rowid**. A column declared exactly `INTEGER PRIMARY KEY`
becomes another name for it, which is SQLite's rule. Any other primary
key, `INT PRIMARY KEY` included, is an ordinary column that sqlite3 backs
with a unique index it makes by itself, and a file that has the table but
not that index is one sqlite3 calls malformed. This engine does not keep
such an index, so CREATE TABLE refuses the table
(`Error: a PRIMARY KEY that is not INTEGER PRIMARY KEY is not supported`),
and a table like it in a file sqlite3 made is read-only here. The catalog
records which column, if any, is the rowid; the next module depends on it
when it stores and reads rows.

**Affinity comes from the type's spelling.** SQLite has no fixed list of
type names. `affinity_of` looks for pieces of the declared type in a
fixed order: INT first, then CHAR, CLOB or TEXT, then BLOB or no type at
all, then REAL, FLOA or DOUB, and anything else is NUMERIC. The order is
SQLite's and has odd corners: `FLOATING POINT` contains INT, so it gets
INTEGER affinity.

**The shell learns the catalog too.** `.tables` lists the tables in the
catalog, and `.schema` prints their stored CREATE text. To find a table's
indexes, `.schema` walks the rows of page 1 with a cursor, because there
is no SELECT yet to ask for them.

## Break it

In build/at/db/03.03/src/schema.c, delete the call to `schema_insert_row`
in `create_table`. Then run `./learn run db --at 03.03 -- orphan.db` and
create the same table twice:

<!-- verify: patch file=src/schema.c
-    schema_insert_row(db, "table", s->table, s->table, root, s->sql);
-->
<!-- verify: session run="./learn run db --at 03.03 -- orphan.db" -->
```
db> CREATE TABLE fruit(id INTEGER PRIMARY KEY, name TEXT);
db> .tables
db> PRAGMA page_count;
2
db> CREATE TABLE fruit(id INTEGER PRIMARY KEY, name TEXT);
db> PRAGMA page_count;
3
```

<!-- verify: session -->
```
$ sqlite3 -list build/at/db/03.03/orphan.db 'PRAGMA integrity_check'
*** in database main ***
Page 2: never used
Page 3: never used
```

Each CREATE succeeds: a root page is made and the cookie bumped. But the
rebuild that follows reads sqlite_schema, finds no row for fruit, and the
table is gone the moment it was made, so the second CREATE meets no name
clash and makes another. Pages 2 and 3 are still in the file, empty and
pointed at by nothing, which is what sqlite3's check reports: without
its catalog row, a B-tree is just lost space.

## Decide the boundary

This engine stores each table's definition as the SQL text that created
it, and parses it on every open. Another design stores the definition as
data: PostgreSQL, for instance, keeps a row per table and a row per column
in its system catalogs. Text is compact, human readable, and lets a new
column constraint appear without changing the file format; it pays with
a parser at open time, and with ALTER TABLE having to rewrite text. Rows
per column can be queried and changed directly, and pay with several
catalog tables that must agree. If the schema changed every minute instead
of once a year, which would you want?
