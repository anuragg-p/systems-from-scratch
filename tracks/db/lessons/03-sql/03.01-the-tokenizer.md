# 03.01 The tokenizer

A statement arrives as one string of bytes. Before anything can understand
it, something has to cut it into words: this keyword, that name, this
number, that string. The tokenizer does that, one word at a time.

## Where this fits

![Where 03.01 fits](figures/03.01-map.svg)

The engine can already keep rows in B-trees inside a file, but nobody can
ask it for them in SQL yet. This module builds the front of the database:
it reads the text of a statement, works out its structure, and keeps the
list of tables the statement may name. The tokenizer is the first step of
that front end. It is given raw text and gives back one word at a time;
the parser, in the next lesson, will be its main customer. After this
lesson the engine can tell the words of a statement apart, though not yet
what they mean, and the shell already uses them to see where a statement
really ends.

## The idea

![next_token() cutting a statement into tokens: keywords in accent, every space and the comment a token of their own, and TK_EOF at byte 54.](figures/03.01-tokens.svg)

Look at `price*2` in the statement above. A person sees a name, an
operator and a number at once. A program sees five bytes, and it has to
decide where each word ends: `price` stops at the `*` because a `*` cannot
be part of a name, and `2` stops at the space. The quoted text `'it''s'`
is harder: it contains two quote characters in the middle, and only the
last quote ends it.

So the tokenizer's job is narrow and exact: stand at some byte of the
text, decide what kind of word starts there, and say how many bytes it
takes. Such a word is a **token**: a type (keyword, name, number, string,
operator, or the end of the text, which the figure shows as TK_EOF) and a
stretch of the original text. Nothing is copied; a token is a pointer and
a length.

The rule that decides where a word ends is **maximal munch**: take the
longest run of bytes that still forms one token. `SELECTED` is a name, not
the keyword `SELECT` followed by `ED`; `<=` is one operator, not `<` and
`=`.

### next_token and its helpers

All of this is one function. Given a pointer into the statement, it
returns the token that starts there and its length; the caller moves past
that many bytes and asks again. It is a single switch on the first byte,
because one byte is almost always enough to know which rule applies.
Three kinds of token need more than a look at the next byte, so they get
helpers: quoted text, numbers, and words, which are looked up as keywords
only once they have been read whole.

![The first byte picks the rule. The three highlighted rows hand the rest of the token to scan_quoted(), scan_number() and keyword_type().](figures/03.01-first-byte.svg)

### sql_complete: has the statement ended?

The shell has to decide, after every line you type, whether to run what
it has or wait for more. Until this lesson it ran as soon as a line held
a `;` anywhere, so `SELECT 'a;` was cut off in the middle of its string.
A semicolon only ends a statement when it is a `;` token, not a byte
inside a string, a quoted name or a comment. With a tokenizer, that is
easy to ask: walk the tokens of everything typed so far, and the
statement is finished when the last one that is not a space or a comment
is a `;`. The shell now asks exactly that.

## How it works

### Writing next_token, step by step

1. **The shape: a switch on the first byte.** Each case sets a type and a
   length, and the lines after the switch put them into the token. The end
   of the text is a token of length 0, so a caller that keeps advancing by
   the length stays at the end and keeps getting TK_EOF instead of running
   past the NUL. With the one-byte punctuation in, `(`, `)`, `,` and `;`
   already work.
   ```
   switch (u[0]) {
   case 0:
       type = TK_EOF;
       break;
   case ';': type = TK_SEMI; n = 1; break;
   case '(': type = TK_LP; n = 1; break;
   ...
   }
   t->type = type;
   t->s = z;
   t->n = n;
   return n;
   ```
2. **Operators that may be two bytes.** `<` can be `<`, `<=` or `<>`, so
   look at the next byte before deciding. This is maximal munch in its
   smallest form: take the longer token when it exists. A lone `!` or `|`
   is not an operator in SQL, so those cases leave the type illegal.
   ```
   case '<':
       type = u[1] == '=' ? TK_LE : u[1] == '>' ? TK_NE : TK_LT;
       n = type == TK_LT ? 1 : 2;
       break;
   ```
3. **White space and comments.** A run of spaces is one token. `-` and `/`
   start comments when the next byte is `-` or `*`, and are operators
   otherwise. Every loop that scans ahead stops at the NUL, so a `/*` that
   is never closed runs to the end of the text instead of past it.
4. **Names, keywords, and everything else.** A letter or `_` starts a run
   of name characters, and only once the whole run is read does
   `keyword_type()` say whether it is a keyword. The check for a blob,
   `x'...'`, has to come before this one, or `x'41'` would be read as the
   name `x` followed by a string. Any other byte is one illegal byte, so
   nothing is ever skipped silently.
   ```
   } else if (is_id_start(u[0])) {
       n = 1;
       while (is_id_char(u[n]))
           n++;
       type = keyword_type(z, n);
   } else {
       n = 1;
   }
   ```
   After the first byte a name may also hold `$` (SQLite accepts `a$b`;
   a leading `$` is how SQLite writes a parameter, which this engine does
   not have) and any byte from 0x80 up, so a name written in UTF-8,
   accents and all, passes through whole.
5. **Quotes and numbers get functions of their own.** `scan_quoted` looks
   for the same quote character (or `]` for `[`) and steps over a doubled
   one, which is how SQL puts a quote inside a string. If the text ends
   first it returns TK_ILLEGAL, and the shell knows to wait for another
   line. `[...]`, which SQLite took from MS Access and SQL Server, has no
   such escape in SQLite: the first `]` ends it, and sqlite3 refuses
   `[a]]b]`. `scan_number` reads digits, a fraction and an exponent.
   ```
   if (u[n] == close) {
       if (close != ']' && u[n + 1] == close) {
           n += 2;
           continue;
       }
   ```

![As written, the doubled quote is stepped over and the string is one token of 7 bytes. Without the case, the quote at byte 3 ends the string and byte 4 starts a new one.](figures/03.01-doubled-quote.svg)

### Why it is built this way

**Finished means the last real token is a `;`.** That is all
`sql_complete` checks, plus two ways the text can end in the middle of
something. A string or quoted name that is still open comes back from
`scan_quoted` as TK_ILLEGAL, and the shell waits for its closing quote. A
comment left open also runs to the end of the text, but as a space token,
which the loop skips; so it gets a check of its own: a space token that
starts with `/*` and does not end with `*/`. The `t.n < 4` in that check is
for `/*/`, three bytes that start with `/*` and seem to end with `*/`,
using the same star twice.

**White space and comments are tokens.** It would be simpler to skip them
inside the tokenizer and never return them. Returning them instead means
every byte of the text belongs to exactly one token, so a caller that
walks the tokens always knows where it is. That is what lets the shell
ask "is this statement finished?" with the same code: a `;` that sits
inside a string or a comment is simply not a `;` token. The parser of the
next lesson pays for it with one line that skips every space token.

**The tokenizer is pulled, not run ahead.** Nothing turns the whole
statement into a list of tokens first. Its caller asks for the next token
when it needs one, so there is no list to allocate and free, and a syntax
error stops the work at the first bad token. A token points into the
original text, so its value is decoded only when it is needed: turning
`''` back into one quote is left to the parser, not done here.

**Keywords are found after the word is read.** The tokenizer reads a whole
run of letters, digits and underscores first, and only then looks it up
in the keyword table, ignoring case. This is maximal munch for words: it
is why `SELECTED` stays a name. The table is a plain list of 63 words
searched from the top. The length of each word is worked out once, on the
first call, so almost every entry is rejected by comparing a length and a
first letter, before any string compare; next to reading a page from
disk, that costs nothing.

**A number may not touch a name.** After the digits, if a letter or
digit follows, the whole run becomes one illegal token. Without that
rule, `12abc` would read as `12` then `abc`, and the parser would take
`abc` as a column alias (`SELECT 12 abc` is legal SQL), so a typo would
quietly rename a column. `1e` is caught the same way: an `e` with no
digit after it is not an exponent, so the number has run into a letter.
sqlite3 cuts the same places: `unrecognized token: "12abc"` and
`unrecognized token: "1e"`.

The open comment is a space token, so the last real token of the first
line is the `;` before it, and the shell ran the statement with the
comment still open. The rest of the comment then arrived as a statement
of its own: its last real token is the `/` of `*/`, so even the `;` in
`goes on;` did not end it, and the shell waited for one more.

## Decide the boundary

This tokenizer is a hand-written switch, about a hundred lines. Another
design describes the tokens with regular expressions and lets a generator
(lex, re2c) write the code; SQLite, like this engine, writes its own by
hand. A generator makes adding a token type a one-line change and pays
with a build step and code nobody reads. The two also differ in who is in
charge: here the parser pulls one token at a time, while SQLite's
tokenizer pushes each token into its generated parser. With a SQL dialect
that changes rarely, is a generator worth a second tool in the build?
