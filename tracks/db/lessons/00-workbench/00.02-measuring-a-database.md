# 00.02 Measuring a database

Every later lesson changes how the engine does its work, and each change can
make it faster or slower. This lesson runs the benchmark the track measures
itself by, and shows how each number in it is made, so you know what a number
means and when not to trust one.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

The benchmark stands outside the engine, where an application would. It feeds
SQL text to the shell and times the whole run, so every box in the picture is
inside every number, from cutting the text into words to waiting for the disk.
Beside it, the real sqlite3 does exactly the same work and gives the reference
line. After this lesson there is a fixed yardstick for every change that
follows; module 07 comes back to read the table closely.

## The idea

![How one number in the table is made: a fresh copy of the file, a warm-up, three timed runs of the whole process, and their median.](figures/00.02-one-number.svg)

Is 3,000 inserts a second fast? On its own the number says nothing. It
depends on the machine, on whether the data really reached the disk before
the engine said "done", and on how much of the time went to starting the
program at all. A database benchmark is mostly the work of taking those three
out of the answer.

The machine is taken out by running the real sqlite3 next to `./db`, on the
same workloads, one after the other, and reporting the ratio. "1.09x" means
`./db` did that work 9% faster than sqlite3 on this machine, today.

Durability is taken out by holding both engines to the same promise. Every
workload starts with the same three settings: a rollback journal (a copy of
the pages a commit is about to overwrite, kept beside the file until the
commit is safe), an `fsync` at every commit (the call that returns only once
the written data has reached the drive), and no `F_FULLFSYNC` (macOS's
stronger flush, which also makes the drive empty its own cache onto
permanent storage). A database that skips the `fsync` can
look many times faster and lose the last commit in a power cut; comparing
that with one that does not would measure the promise, not the engine. The
output says which promise was kept, every time.

Start-up is taken out by measuring it. Each engine runs an empty script five
times and the median is printed as "process start-up". It stays inside every
timing, because the one thing both engines can be timed by is the whole
process, but the reader can see how big it is.

The rest is about being fair and repeatable. The SQL is text fed to each
shell on stdin, so both pay to parse it. The random keys come from a fixed
seed, so every run asks for the same rows. Both get the same memory for
pages: 2000 KiB, which is sqlite3's default cache and `./db`'s 500 pages of
4096 bytes. Each engine builds its own base file (100,000 rows, and an index:
a second B-tree that finds rows by the column `a`, module 05) and every timed
run works on a fresh copy of it, so no run sees another's leftovers. The size
of each base file is reported as well. The sqlite3 used is the newest the
benchmark can find (Homebrew's before the system's), so the yardstick is
today's sqlite3 rather than whatever older copy the system ships.

Your numbers will differ, and so will a second run of your own. Two rows
stand apart already. The first is some three hundred times slower than the
second although both insert rows. There every row is its own transaction, and
a commit is a lot of work: create a journal file beside the database, copy
into it the pages about to change, flush it, write the new pages, flush
again, delete the journal. Counted for 1,000 such inserts, in
`build/at/db/finished/`, that is four `fsync` calls and two journalled pages
per commit:

```
$ (echo "CREATE TABLE t(id INTEGER PRIMARY KEY, b TEXT);"; for i in $(seq 1000); do echo "INSERT INTO t VALUES ($i, 'row $i');"; done) | DB_STATS=1 ./db auto.db

```

One transaction does all of that once. And the file is 16% bigger than
sqlite3's for the same rows; module 07 finds out why.

A quick run does not predict a full one. Delete by key comes out 1.18x here
and 0.72x in the full run: faster than sqlite3 in a file of 34 pages, slower
in one of 1,673 (the file sizes over 4096). And in a run this small,
start-up, which is nearly twice as long for sqlite3 as for `./db`, is a large
part of every timing. The benchmark's `--wal` option measures the other kind
of journal, a write-ahead log, which module 06 builds.

## How it works

### Writing the benchmark's `run_all`, step by step

`bench/bench.py` is short except for `run_all`, which turns the list of
workloads into the table. In the order you would write it:

1. **Write every script to a file, then run each one on each engine.** The
   SQL, with the three durability settings in front, is on disk before any
   clock starts, so the timed part never spends time making SQL text:

   ```
       for i, (name, ops, setup, sql) in enumerate(work):
           path = os.path.join(tmp, f"w{i}.sql")
           with open(path, "w") as f:
               f.write(prelude(wal) + sql)
           scripts[name] = path
       ...
       for name, ops, setup, _ in work:
           entry = {"name": name, "ops": ops}
           for e in engines:
               ...
               times = [one() for _ in range(args.repeats)]
   ```

2. **Let each engine build its own base file, untimed.** 100,000 rows in one
   transaction and the index, made by `./db` for `./db` and by sqlite3 for
   sqlite3; each base file's size is the table's last row.
3. **Prepare, then time, each run.** `one()` puts a fresh file in place (a
   copy of the base, or a new file with just the table) without timing it,
   and times only the run itself, so no run sees another's leftovers:

   ```
               def one():
                   if setup == "base":
                       copy_db(base[e.name], scratch)
                   ...
                   return e.run(scratch, scripts[name])
   ```

4. **Measure start-up once per engine.** Five runs of an empty script on a
   copy of the base file (an empty run costs next to nothing, so it can
   afford more of them); the median is what the table's last line reports.
5. **Warm up, keep the median, divide.** One run thrown away before the
   timed ones; ops per second is operations over the median, the spread is
   slowest over fastest, and each row's ratio is `./db`'s rate over
   sqlite3's.
6. **Refuse a run that failed.** `Engine.run` stops the whole benchmark if a
   run exits non-zero or writes anything to stderr. Without this, an engine
   that hit an error on the first statement would finish early and look
   very fast.

### Three decisions that shape the numbers

**The whole process is timed.** Each timed run starts the engine with the
workload's script on stdin and stops the clock when the process exits, so
the time includes starting the program, opening the file, parsing every
statement, the work itself and every `fsync`. Timing inside the engine would
be more precise, but sqlite3 cannot be timed from inside the same way, and
the comparison is the point. The price is that a small workload measures
start-up more than work, which is why start-up is printed and why the full
run is sized as it is:

![Start-up as a share of one timed run of `./db`: a third or more of most quick-run timings, a few percent of most full-run timings.](figures/00.02-startup-share.svg)

**One warm-up, then the median of three.** The first run of anything pays
for cold caches: the binary, the file system's copy of the base file. It is
run and thrown away. Of the three timed runs the median is kept, so a single
run slowed by something else on the machine does not move the number.
**Spread**, the slowest run over the fastest, is printed beside it as a
warning: when it is far above 1, read that row's ratio loosely. Even the
median moves between runs. Another full run of the same build, a minute
earlier on the same machine (busy with other work), gave 2,236 autocommit
inserts a second instead of 3,255, and 642,528 point lookups instead of
612,594. A change is worth believing when it moves a row by more than that.

**The durability settings are pinned, and stated.** Every script begins with

<!-- verify: session cwd=project run="python3 -c \"import sys; sys.path.insert(0, 'bench'); import bench; print(bench.prelude(False), end='')\"" -->
```
PRAGMA journal_mode=DELETE;
PRAGMA synchronous=FULL;
PRAGMA fullfsync=OFF;
```

sqlite3 obeys these. `./db` accepts `synchronous=FULL` and `fullfsync=OFF`
because they describe the only way it syncs, and refuses any other value, so
it cannot win a comparison by quietly syncing less (in
`build/at/db/finished/`):

<!-- verify: session at=finished cwd=project -->
```
$ ./db demo.db "PRAGMA synchronous=OFF"
Error: only synchronous=FULL is supported
```

## Decide the boundary

This benchmark measures wall-clock time for whole processes: what a user of
the shell would feel, noise included. The SQLite developers measure their own
changes differently: they count CPU cycles for a fixed workload under
cachegrind, which repeats to seven significant digits where wall-clock times
barely repeat to one, but is blind to time spent waiting for the disk. One
kind of number tells you what someone running the engine will see; the other
moves only when the code does. Which question do you need answered when you
change one line?

## Break it

Make `fsync` a no-op and see which numbers notice. In the finished engine's
`build/at/db/finished/src/util.c`, change `sys_fsync` so it counts the call
but skips it:

<!-- verify: patch file=src/util.c at=finished
-int sys_fsync(int fd)
-{
-    stats.fsyncs++;
-    return fsync(fd);
-}
@block
-->
```
int sys_fsync(int fd)
{
    stats.fsyncs++;
    return 0;
}
```

Run `./learn bench db` again; it rebuilds first. The first two rows:

<!-- verify: session run="./learn bench db" timeout=600 wait=300 more
line 3 ~ insert, autocommit +10000 +[\d,]+ +[\d,]+ +\d+\.\d\dx +\d+\.\d\d +\d+\.\d\d
line 4 ~ insert, one transaction +100000 +[\d,]+ +[\d,]+ +\d+\.\d\dx +\d+\.\d\d +\d+\.\d\d
-->
```
...
workload                              ops     db ops/s  sqlite3 ops/s  db/sqlite3   spread db, sqlite3
insert, autocommit                  10000        8,732          1,561       5.59x          1.04   3.02
insert, one transaction            100000    1,083,346        984,947       1.10x          1.03   1.02
```

From 3,255 inserts a second to 8,732, far outside the 2,236 to 3,255 of two
honest runs, and steady now. The other workloads commit once, or never, and
stayed within their usual noise: a free `fsync` cannot help them. The engine
is now cheating, and only the workload that commits ten thousand times shows
it.

What surprises is how much is left. With every flush free, an autocommit
insert is still more than a hundred times slower than one inside a
transaction: each commit still creates, fills and deletes a journal file and
writes its pages, and that file work costs more than the flushes did. What
the flushes cost depends on the moment, too. Waiting for a drive that other
programs are busy with costs more, which is also why the honest autocommit
row had the widest spread in the table. Timed alone on a quiet machine, 1,000
inserts at a time, five runs each, the no-op `fsync` less than doubles the
rate:

![1,000 autocommit INSERTs on this Mac, median of five runs. The no-op fsync less than doubles the rate; sqlite3 with F_FULLFSYNC drops to 78 a second.](figures/00.02-fsync.svg)

On macOS, `fsync(2)` moves the data from the computer to the drive but does
not make the drive write it from its own cache to permanent storage; its
manual page (`man 2 fsync`) says so and points to `F_FULLFSYNC`, which does.
sqlite3 uses `F_FULLFSYNC` when told to with `PRAGMA fullfsync=ON`, and its
autocommit rate falls from thousands a second to under 80. That is the price
of a commit that survives a power cut on this machine, and why both engines
leave it off by default.
