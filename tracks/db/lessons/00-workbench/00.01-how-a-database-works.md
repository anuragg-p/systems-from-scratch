# 00.01 How a database works

A database takes a sentence like `SELECT name FROM users WHERE id = 7`, reads a
few pieces of one file, and hands back `ken`. This lesson follows that sentence
through the whole engine before any part of it is built, then runs the finished
engine on your machine.

The engine is this course's own code, but the file it writes is a real SQLite
database: the real sqlite3 opens what this engine writes, and this engine reads
the tables and indexes sqlite3 writes. So what you learn about pages, records
and the journal is how SQLite itself keeps your data, and you can check any
step against sqlite3.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

This is the whole engine in one picture. A statement goes along the top row,
down the right side and back along the bottom row to the file, and the answer
comes back the same way. Each box is given something and gives something
back:

- **The shell** is given what you type. It waits for the semicolon, then hands
  over the whole statement as text.
- **The tokenizer** is given that text and gives back words: `SELECT`, `name`,
  `FROM`, `users`, `WHERE`, `id`, `=`, `7`.
- **The parser** is given the words and gives back a tree: a SELECT of the
  column `name`, from the table `users`, with the condition `id = 7`.
- **The catalog** is asked what `users` is. It answers with the table's
  columns and where in the file its rows begin.
- **The planner** is given the tree and decides how to read the table. `id` is
  the table's key, so it plans to look up row 7 directly instead of reading
  every row.
- **The executor** runs that plan and gives back rows: it asks for row 7,
  keeps the `name` column and prints it.
- **Records** turn a row into bytes and back. Row 7 is stored as a short run of
  bytes that decodes to the values 7 and `ken`.
- **The B-tree** is given a key and finds the row with it, by going from one
  page to the next down a tree of pages.
- **The pager** is given a page number and gives back that page's bytes: from
  memory if it has them, from the file if it does not.
- **The journal** makes a change all or nothing, so a crash halfway through
  a write cannot leave half of it in the file: a rollback journal keeps a copy
  of what a change overwrites, a write-ahead log (WAL) keeps the change itself
  until it is safe to copy in. A SELECT changes nothing and never touches it.
- **The file** is the database: one ordinary file, cut into pages of 4096
  bytes.

The track builds these from the bottom up, starting at the file, because every
other box stands on it. Module 01 makes the file a set of numbered pages and
packs rows into bytes, and both can be checked byte for byte against what the
real sqlite3 writes. Module 02 stores and finds rows by key in a
B-tree. Module 03 turns SQL text into a tree and keeps the catalog. Module 04
runs queries, module 05 adds indexes and the planner, module 06 makes commits
survive a crash, and module 07 measures where the time goes.

## The idea

![One SELECT through the engine. Each layer is one or two files in src/, and the module that builds it.](figures/00.01-one-statement.svg)

The engine is one C program, `./db`, about 8,000 lines that need nothing but
the C library, and one file. Everything it keeps lives in that file (and, for
the moment a commit takes, in a journal beside it); there is no server and no
other state. That makes the engine easy to run: point it at a file and type.

The file is a real SQLite database. That choice is the track's yardstick. The
real `sqlite3` program can open what `./db` writes, check its structure, and
read the same answers back, and `./db` can open what `sqlite3` writes. If the
two ever disagree about a byte, the bug is ours, and sqlite3's own
`PRAGMA integrity_check` usually says where.

### The shell
<!-- verify: mention names="src/main.c src/db.h repl()" at=finished -->


The shell, `src/main.c`, is the one part of the engine you talk to. It sits on
top of everything in the picture and does very little itself: it collects SQL
text and hands each complete statement to the engine, which runs it and prints
the rows.

It exists because SQL arrives three ways. A person types at a prompt, often
across several lines. A script pipes a file of statements into it. Another
program, or a quick question, passes one statement as an argument. All three
end in the same call; what differs is the prompt, when a statement is
considered finished, and what an error does to the exit status.

### The `Makefile`

The one file this lesson adds is the Makefile that builds `./db` from every
`src/*.c`. Beyond `-O2 -g`, its flags are about building the same way on
Linux and macOS. `-D_POSIX_C_SOURCE=200809L` asks the C library for the POSIX calls the engine
relies on (`pread`, `pwrite`, `getline`); asking for strict POSIX hides
everything else, so `_DEFAULT_SOURCE` and `_DARWIN_C_SOURCE` put Linux's and
macOS's own extras back. `-lm` brings in the maths library for the `floor` and
`ceil` that SQL expressions need. Every object depends on `src/db.h`, the
header every file includes, so changing a structure there rebuilds
everything. And in the early lessons some helpers have no caller yet, so
warnings about unused code are turned off rather than allowed to bury the ones
that matter.

## Run it

This lesson has nothing of its own to run yet, so run the finished engine,
the one the track ends with. From the repository root, `./learn run db` builds
it with the Makefile above and starts the shell on `learn.db`, a file that
does not exist yet. Make a table and ask the question from the top of this
lesson:

<!-- verify: session -->
```
$ ./learn run db
Running the finished db. Its files are in build/at/db/finished/
db: a SQL database, from scratch. Statements end with ;  .help for help
db> CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT);
db> INSERT INTO users(name) VALUES ('ada'), ('alan'), ('grace'), ('edsger'), ('barbara'), ('donald'), ('ken'), ('dennis');
db> SELECT name
   ...>   FROM users WHERE id = 7;
ken
db> .tables
users
db> SELECT * FROM nosuch;
Error: no such table: nosuch
db> .exit
```

`id INTEGER PRIMARY KEY` makes `id` the row's own number, its **rowid**: the
eight names were numbered 1 to 8 in the order they went in, which is why
row 7 is `ken`.

The program and `learn.db` are in `build/at/db/finished/`; the rest of this
section runs there. The file appeared, two pages long, and it starts the way
every SQLite file does:

<!-- verify: session -->
```
$ cd build/at/db/finished
$ wc -c learn.db
    8192 learn.db
$ xxd -l 16 learn.db
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
```

One-shot mode runs the statement given after the file name and exits:

<!-- verify: session -->
```
$ ./db learn.db "SELECT * FROM users WHERE id = 7"
7|ken
```

Now the real `sqlite3` (here 3.54.1 from Homebrew) on the same file. It checks
the whole structure, reads the row, adds one, and `./db` reads that back
(`-list` asks for plain rows, as `./db` prints them; in a terminal, a recent
sqlite3 draws a table around them instead):

<!-- verify: session -->
```
$ sqlite3 -list learn.db "PRAGMA integrity_check; SELECT name FROM users WHERE id = 7;"
ok
ken
$ sqlite3 learn.db "INSERT INTO users(name) VALUES ('brian');"
$ ./db learn.db "SELECT * FROM users WHERE id > 7"
8|dennis
9|brian
```

Two layers of the picture can be watched from outside. `EXPLAIN QUERY PLAN`
prints what the planner chose, and both engines choose the same:

<!-- verify: session -->
```
$ ./db learn.db "EXPLAIN QUERY PLAN SELECT name FROM users WHERE id = 7"
QUERY PLAN
`--SEARCH users USING INTEGER PRIMARY KEY (rowid=?)
```

and `DB_STATS=1` prints the engine's counters as it exits. The question read
two pages from the file: page 1, where the catalog lives, and page 2, the
table's only page. The nine hits are later requests for those same two pages,
answered from memory:

<!-- verify: session
vary "..." any
-->
```
$ DB_STATS=1 ./db learn.db "SELECT name FROM users WHERE id = 7"
ken
stats: pages read 2, cache hits 9, cache misses 2, ...
```

## How it works

### Writing the shell's `repl`, step by step

`main` has already opened the file and decided whether a person is typing:
standard input is a terminal, or the `-interactive` flag asks for prompts
anyway. `repl` is the loop that runs from then on, in `src/main.c`; `sql` is
a growable byte buffer (a `Buf`: bytes `p`, length `n`).

1. **Start with the loop: read a line, add it to a buffer, run the buffer
   once it holds a whole statement.** That is already a working shell for a
   script piped in:

   <!-- verify: quote at=finished -->
   ```
       for (;;) {
           ssize_t n = getline(&line, &cap, stdin);
           if (n < 0)
               break;
           buf_put(&sql, line, (size_t)n);
           buf_put(&sql, "", 1);           /* keep it a C string */
           sql.n--;
           if (sql_complete((const char *)sql.p)) {
               if (db_exec(&db, (const char *)sql.p) < 0)
                   failed = 1;
               sql.n = 0;
   ```

   The tokenizer and `db_exec` read up to a 0 byte, so one is appended and
   then not counted. Deciding "whole" is the first decision below.

2. **Prompt, but only for a person.** `db> `, or `   ...> ` when a statement
   is half typed; a script gets no prompts in its output.

   <!-- verify: quote at=finished -->
   ```
           if (interactive) {
               fputs(sql.n ? "   ...> " : "db> ", stdout);
               fflush(stdout);
           }
   ```

3. **Catch dot-commands and blank lines, only between statements.** With
   nothing buffered, a line starting with a dot goes to `dot_command` and a
   blank line is skipped. Mid-statement, a dot is SQL (the first decision
   below).
4. **At the end of the input, run what is left,** so a script whose last
   statement has no semicolon still has it run.
5. **Choose the exit status:** 1 if a statement failed and nobody was
   watching, 0 otherwise (the second decision below).

### Two decisions that are not obvious

**When is a statement finished?** The shell cannot run each line as it
arrives: `SELECT name` on one line and `FROM users WHERE id = 7;` on the next
are one statement. It cannot simply wait for a line that ends in `;` either,
because a semicolon can sit inside a string (`'a;b'`) or a comment. So after
every line it asks the tokenizer, the same one the engine uses, whether the
text so far is complete (step 1's `sql_complete`): true when the last real
token is `;` and no string, quoted name or comment is still open. Until then
the shell prints `   ...> ` and keeps reading. Dot-commands such as `.tables` are recognised only at the start of a
statement, so a line that begins with `.5` in the middle of one is still SQL.

![The loop in `repl()`: lines collect in a buffer until the tokenizer says the statement is complete.](figures/00.01-repl-loop.svg)

**What does an error do?** It depends on who is listening. One-shot mode
stops at the first failing statement and exits 1. A script on stdin keeps
going, so one bad line does not hide the rest, and exits 1 at the end. A
person at the prompt has seen the error already, so the shell exits 0:

<!-- verify: session -->
```
$ ./db learn.db "SELECT name FROM users WHERE id = 7; SELECT * FROM nosuch; SELECT 1"; echo "exit $?"
ken
Error: no such table: nosuch
exit 1
$ printf "SELECT 1;\nSELECT * FROM nosuch;\nSELECT 2;\n" | ./db learn.db; echo "exit $?"
1
Error: no such table: nosuch
2
exit 1
```

That is what lets a Makefile or another program use `./db` and notice failure,
while a typo at the prompt costs nothing. A bad file is caught before the
first prompt: opening it checks the header, starting with the 16 bytes you saw
above:

<!-- verify: session -->
```
$ ./db Makefile "SELECT 1"; echo "exit $?"
Error: file is not a database: Makefile
exit 1
```

## Decide the boundary

This engine is a program you run, and its results go straight to standard
output. SQLite is a library first: an application links it in, prepares a
statement once and steps through the rows itself, and the `sqlite3` shell is
only one client of that library. A library pays for it with an interface to
keep stable: statement objects, who owns each returned value and for how
long, errors as return codes rather than text. A program gets to print and
exit, and another program that wants its rows has to read them back out of
text. Who is the engine's first user: a person at a prompt, or another
program that wants the rows back?

Make the shell run every line as soon as it arrives. In the finished

and type the two-line SELECT again (`./learn run db` rebuilds it first):

<!-- verify: session -->
```
$ ./learn run db
Running the finished db. Its files are in build/at/db/finished/
db: a SQL database, from scratch. Statements end with ;  .help for help
db> SELECT name
Error: no such column: name
db>   FROM users WHERE id = 7;
Error: near "FROM": syntax error
```

The first line is a whole statement as far as the parser can tell, a SELECT
with no FROM, and it fails because without a table there is no column
`name`. The second line starts with `FROM` and is not a statement at all.
Where a statement ends is a fact about its tokens, not about lines.
