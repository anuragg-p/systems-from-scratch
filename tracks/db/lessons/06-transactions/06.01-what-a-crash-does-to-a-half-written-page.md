# 06.01 What a crash does to a half-written page

A commit writes its changed pages into the file one after another. A crash
between two of them leaves a file that is half the old database and half the
new one, and a crash in the middle of one page can leave that page half and
half too. This lab makes both happen and looks at what is left.

## Where this fits

![Where 06.01 fits](figures/06.01-map.svg)

So far a commit is simple: the pager writes every changed page back to the
file where it came from, then asks the operating system to make the file
durable. Nothing protects the moment in between, when some pages are new and
some are old. This module makes commits **atomic**, all or nothing, even if
the process dies or the power goes: first with a rollback journal that saves
the old pages before anything is overwritten (06.02) and puts them back after
a crash (06.03), then with a write-ahead log that never overwrites the
database during a commit at all (06.04). This lab adds no code. It runs the
engine as it is, with no protection yet, to see the problem the rest of the
module solves.

## The idea

Take a table of 2000 rows spread over 90 leaf pages and change every row:
`UPDATE t SET b = 'new'`. Until the commit, the changed pages live only in
memory. At commit the pager's `commit_unsafe` writes all 91 of them (the 90
leaves and page 1, whose header counts commits; the interior page above the
leaves is untouched, since no rowid moves) into the file, and then calls
`fsync` so the disk keeps them. It writes them sorted by page number, so the
writes go through the file from front to back, as sqlite3's do.

At this lesson that loop is the whole commit: there is no journal, and
`PRAGMA journal_mode` answers `off`. Kill the process after 46 of the 91
writes, and the file holds 46 new pages and 45 old ones. Every page is a
valid page on its own, so nothing looks broken; the database just answers
with half a transaction in it, and it has no way to know which half.

![UPDATE t SET b = 'new' with no journal: 91 pages to write, a crash after 46, and which rows changed.](figures/06.01-half-commit.svg)

It gets worse inside a page. A page is 4096 bytes, but nothing promises that
4096 bytes reach the disk in one piece: a drive writes in sectors, and a
power cut can stop it partway through a page. That leaves a **torn page**,
the start of the new version on top of the end of the old one. A page's
header and cell pointers sit at its start and its cells at its end, so a
torn page usually points into the wrong bytes.

### How the engine crashes on purpose

`DB_CRASH=<point>` makes the engine kill itself with `SIGKILL` at a named
point of a commit: no cleanup, no flushing, the file as it is at that
instant. `db-partial` fires after half the pages of a commit are written.
`db-torn` writes only the first half of the page in the middle of the
commit, then dies, which imitates what a power cut can do to one page.
`db-written` fires after every page is written, just before the `fsync`.

A `SIGKILL` ends the process, not the computer. What the process already
handed to the operating system with `write` sits in the operating system's
cache and still reaches the disk later. `fsync` is what makes the disk hold
it even if the operating system itself stops, in a power cut or a kernel
panic.

## Run it

`./learn run db --at 06.01` builds the engine as it stands at this lesson
in build/at/db/06.01/; run what follows there. Make the table with

Keep a clean copy, `t06.db`, to start each experiment from:

```

$ DB_CRASH=db-partial ./db demo.db "UPDATE t SET b = 'new';"

$ ./db demo.db "SELECT id FROM t WHERE b = 'new';" | wc -l
    1010
```

`ok`, and row 1983 is half updated.

## How it works

**Which rows survive is decided by page numbers, not by rows.** The pager
writes changed pages sorted by page number, so the crash keeps pages 1 and
3 to 47. Pages 4 to 47 hold rows 1 to 970. Page 3 holds rows 1961 to 2000:
it was the table's first leaf, and every split moved the older rows out to
new pages and kept the newest on page 3. So the 1010 survivors are the first
970 rows and the last 40. Half a transaction is not even a tidy half.

**Why the torn page says 111.** Page 47 held rows 949 to 970 in cells of 91
bytes. After `b = 'new'` its cells shrink, so the new page lays them out
differently: its header says 22 cells starting at offset 3898. Only the
first 2048 bytes of that new page reached the file. The cell pointers in
it point at 4087, 4078, and so on, in the second half, which still holds the
old page's text: `ooooo`. A cell is read as a length and a rowid, both
varints, and the byte `6f` (`o`) read as a varint is 111. Our engine reads
the 948 rows before page 47, all new, and stops there.

![Page 47 after the tear: the new header and pointers, the old cells, and what cell 0's pointer finds.](figures/06.01-torn-page.svg)

**A torn page does not have to look torn.** With `upper(b)` every cell keeps
its size and its place, so the new header and the old one say the same
thing, and every pointer lands on the start of a real cell. On page 3, the
cells in the first 2048 bytes (rows 1984 to 2000) are new, those in the
second half (1961 to 1982) are old, and row 1983 sits across the boundary.
Every structure in the file is consistent, so no check can complain.

![The same tear with a same-size update of the last 40 rows: half the cells of page 3 new, half old, row 1983 cut in two, integrity_check ok.](figures/06.01-silent-tear.svg)

**Nothing in the file can undo it.** Once a page is overwritten in place,
its old version is gone. To put a half-written commit right, a copy of
every page from before the commit has to be somewhere else, written before
the first page is overwritten. That is the rollback journal of the next
lesson.

## Break it

The commit ends with an `fsync`. In `src/pager.c`, in `commit_unsafe`,
delete the two lines after `crash_point("db-written");`:

```
    if (sys_fsync(p->fd) < 0)
        fatal("fsync: %s", strerror(errno));
```

then `make` and run the two crashes and a normal commit, each from a fresh
copy of `t06.db`:

<!-- verify: patch file=src/pager.c

-    if (sys_fsync(p->fd) < 0)
-        fatal("fsync: %s", strerror(errno));
-->
<!-- verify: session cwd=project
vary "..." any
-->
```
$ DB_CRASH=db-partial ./db demo.db "UPDATE t SET b = 'new';"
db: crash injected at db-partial
$ ./db demo.db "SELECT id FROM t WHERE b = 'new';" | wc -l
    1010
$ DB_CRASH=db-written ./db demo.db "UPDATE t SET b = 'new';"
db: crash injected at db-written
$ ./db demo.db "SELECT id FROM t WHERE b = 'new';" | wc -l
    2000
$ DB_STATS=1 ./db demo.db "UPDATE t SET b = 'new';"
stats: pages read 92, cache hits 24274, cache misses 92, evictions 0, pages written 91, fsyncs 0, ...
```

Exactly the results of the engine with its `fsync`, which also gives 1010
and 2000; only the count of fsyncs changed, from 1 to 0. Every crash here is
a `SIGKILL`, and the pages written before it were already the operating
system's to deliver. A missing `fsync` matters only when the operating
system stops too, and no crash injected into a process can show that, which
is why the torn page is imitated by writing half a page on purpose. Code
that forgets an `fsync` survives every kill there is.

## Decide the boundary

This engine, like SQLite, assumes the worst of the disk: a write can be torn
anywhere, so atomicity has to come from its own extra writes. Another
system can lean on the layer below: a drive that promises atomic 4096-byte
writes, or a copy-on-write filesystem such as ZFS that never overwrites a
block in place and so cannot tear one. That saves writing every changed
page a second time, and pays by trusting a promise the database cannot check
and that consumer drives do not always keep. What does your storage really
promise when the power goes, and how would you find out?
