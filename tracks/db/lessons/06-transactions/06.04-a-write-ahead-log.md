# 06.04 A write-ahead log

The rollback journal saves the old pages and overwrites the database. A
write-ahead log turns that around: a commit appends the new pages to a
second file and leaves the database alone, and the pages are copied home
later, at a checkpoint. A commit becomes one append and one `fsync`.

## Where this fits

![Where 06.04 fits](figures/06.04-map.svg)

The pager's commit has had one durable path so far, the rollback journal.
This lesson adds a second one, chosen with a PRAGMA and
remembered in the database header, so every later open uses it too. With a
log, a page can have a newer version in the log than in the database file,
so the pager's page reads change as well: they look in the log first. The
layers above the pager notice nothing. Afterwards a commit costs one wait
for the disk instead of four, and the log is in SQLite's own format, so
sqlite3 can read a log this engine left behind.

## The idea

![The rollback journal saves the old pages aside; the write-ahead log appends the new ones.](figures/06.04-two-ways.svg)

The journal needs four `fsync`s because it writes in two places in a strict
order: originals first, then the database, then the deletion. A log needs
only one place. Each commit appends its changed pages, one **frame** per
page, to `demo.db-wal`, and the last frame of the commit carries a
**commit mark**: the size of the database after the commit. Once those
frames are on the disk, the commit has happened, even though the database
file has not changed at all. Every frame also carries the log header's two
**salts**, numbers chosen anew each time the log starts over, so a frame
left in the file by an older log cannot pass for a new one.

Reading has to follow. The newest version of a page is now the last copy of
it in the log, if there is one, and the database file otherwise. The engine
keeps a small map from page number to the frame that holds its newest
version, and the pager asks it before reading the file. (The code calls
this map the log's index, `index_set` and `index_clear`; it has nothing to
do with the B-tree indexes of module 05.)

The log cannot grow for ever, so now and then a **checkpoint** copies the
newest version of every page in the log into the database file, makes the
file durable, and empties the log. This engine checkpoints when the log
reaches 1000 frames and when the database is closed, as sqlite3 does.

A crash can only cut the log short. Whatever is after the last complete
commit mark is ignored when the log is read back, so a half-appended commit
simply never happened, and the database file underneath was never touched.

### wal_open: read the log

Called when a database in WAL mode is opened. It checks the log's header,
walks the frames from the first while each one checks out, and builds the
page-to-frame map from every frame up to the last commit mark.

### wal_commit: append a commit

The pager's commit calls this in WAL mode. It appends one frame per changed
page, the commit mark on the last, syncs the log, and only then records the
new frames in the map.

### wal_checkpoint: copy the pages home

Copies the newest version of each page into the database file, syncs it,
and only then empties the log.

## How it works

### Writing wal_commit, step by step

1. **Append the pages, then tell the map.** One frame per changed page, a
   24-byte header that starts with the page number and then the page, after
   the last frame already in the log; then each page's new frame goes into
   the page-to-frame map that reads go through.

   ```
   for (u32 i = 0; i < n; i++) {
       put4(f, pages[i]->pgno);
       memcpy(f + FRAME_HDR, pages[i]->data, p->page_size);
       off_t off = frame_offset(p, w->nframes + 1 + i);
       must_pwrite(w->fd, f, flen, off, w->path);
   }
   for (u32 i = 0; i < n; i++)
       index_set(w, pages[i]->pgno, w->nframes + 1 + i);
   w->nframes += n;
   ```

2. **Mark the end of the commit.** The last frame carries the database's
   size in pages, every other frame 0. The mark is a promise that every
   frame of the commit before it is in the log. Without it, a crash after 45
   of a commit's 90 frames would leave 45 frames that a reader could not
   tell from a finished commit.

   ```
   put4(f + 4, i == n - 1 ? p->npages : 0);
   ```

3. **Chain every frame to the one before.** Each frame carries the header's
   two salts and a checksum over its first 8 bytes and its page, continued
   from the previous frame's. That is what lets one `fsync` do: the disk may
   store the frames in any order, and a power cut may tear the commit frame,
   mark intact and page half written, but a reader reaches the mark only
   through an unbroken chain of good frames.

   ```
   put4(f + 8, w->salt1);
   put4(f + 12, w->salt2);
   wal_checksum(w->bigendian, f, 8, &s0, &s1);
   wal_checksum(w->bigendian, pages[i]->data, p->page_size, &s0, &s1);
   ```

4. **Sync, then publish.** `fsync` the log, and its directory when the log
   is new, before the map hears of the new frames. The other way round, a
   read later in this process could see a commit that a power cut can still
   take away.

   ```
   if (sys_fsync(w->fd) < 0)
       fatal("fsync %s: %s", w->path, strerror(errno));
   if (fresh)
       fsync_dir(w->path);
   ```

### Writing wal_open, step by step

1. **Walk the frames; a commit mark makes them real.** An empty or missing
   log is a new one. Otherwise read the frames from the first, keep their
   page numbers pending, and when a frame with a commit mark arrives put the
   whole commit into the map at once. Mapped frame by frame, the first 45
   frames of a 90-frame commit cut short by a crash would come back as if
   committed.

   ```
   for (u32 frame = 1; frame_offset(p, frame) + (off_t)flen <= st.st_size; frame++) {
       if (!read_at(w->fd, f, flen, frame_offset(p, frame)))
           break;
       ...
       pending[npending++] = get4(f);
       if (get4(f + 4) != 0) {
           u32 first = frame - npending + 1;
           for (u32 i = 0; i < npending; i++)
               index_set(w, pending[i], first + i);
           npending = 0;
       }
   }
   ```

2. **Stop at the first frame that does not belong.** A torn commit frame
   keeps its mark, which sits in its first bytes, but fails the checksum;
   frames of an older log further along the file fail the salts.

   ```
   if (get4(f + 8) != w->salt1 || get4(f + 12) != w->salt2)
       break;
   ...
   if (s0 != get4(f + 16) || s1 != get4(f + 20))
       break;
   ```

3. **Remember where the last commit ended.** At each commit frame keep the
   frame count and the running checksum, so the next commit writes right
   after it and continues the chain from there. Taken from the last frame
   read instead, they would put the next commit after the frames of a
   transaction that never finished, and its mark would make those real too.

   ```
   w->nframes = frame;
   ...
   w->s0 = s0;
   w->s1 = s1;
   ```

4. **Trust the header only if it checks out:** the magic (either byte
   order), the version, this database's page size, and a checksum over the
   header itself. A header that fails, as after a crash while the first
   commit was writing it, means the log holds nothing usable, and the
   database file alone is the truth.

### Writing wal_checkpoint, step by step

1. **Copy every page home, then empty the log.** The map already points at
   the newest frame of each page, so each page is read once from the log
   and written once into the database file.

   ```
   for (u32 pgno = 1; pgno < w->frame_of_cap; pgno++) {
       if (w->frame_of[pgno] == 0)
           continue;
       wal_read(p, pgno, buf);
       write_page(p, pgno, buf);
   }
   ...
   if (ftruncate(w->fd, 0) < 0)
       fatal("truncating %s: %s", w->path, strerror(errno));
   index_clear(w);
   ```

2. **Sync the database before the log is emptied.** Emptied first, the log
   could be gone while the pages copied from it are still in the cache, and
   a power cut would take committed transactions with it. With the `fsync`
   in between, a crash anywhere before the log is cut leaves it whole, and
   the next open copies the same pages again, which changes nothing.

   ```
   if (sys_fsync(p->fd) < 0)
       fatal("fsync %s: %s", p->path, strerror(errno));
   ```

3. **A crash point at each end of that gap:** `checkpoint-partial` after
   the first page is copied, `checkpoint-done` once the database is synced.
   The run above crashed at the first and lost nothing.

**The checksum is the file format's.** `wal_checksum` keeps two running
sums over the data taken eight bytes at a time, each feeding the other, and
hands them on from one frame to the next: that is the chain of `wal_commit`,
and why a frame cannot be dropped or moved without breaking every checksum
after it. It reads the words in either byte order, because sqlite3 writes
its logs little-endian on most machines and a log it left must check out
too.

### Writing pager_set_journal_mode, step by step

1. **The switch of 06.02.** `PRAGMA journal_mode` calls it between
   transactions; so far it only changed how the next commit is written, and
   nothing in the file recorded the choice. The file's header now does, in
   bytes 18 and 19, and opening a file whose bytes say anything above 2 is
   refused as a format this engine does not know.

   ```
   int pager_set_journal_mode(Pager *p, int mode)
   {
       if (mode == p->journal_mode)
           return 0;
       if (p->ndirty)
           return err("cannot change the journal mode inside a transaction");
       ...
       p->journal_mode = mode;
       return 0;
   }
   ```

2. **Into WAL, the header goes first.** Bytes 18 and 19 tell every later
   open, this engine's or sqlite3's, to look in a log, so they are set to 2
   and committed with the rollback journal before the log is opened: a
   crash leaves the file in one mode or the other, never between.

   ```
   p->journal_mode = JOURNAL_DELETE;
   u8 *h = pager_write(p, 1);
   h[18] = h[19] = 2;
   if (pager_commit(p) < 0)
   ...
   return wal_open(p);
   ```

3. **Out of WAL, the log goes first.** It is checkpointed and closed before
   the header goes back to 1. The other way round, a crash in between would
   leave committed frames in a log that the next open, told by the header
   there is none, never reads.

   ```
   if (p->journal_mode == JOURNAL_WAL) {
       wal_close(p, 1);
       ...
       h[18] = h[19] = 1;
   ```

### Why it is built this way

**New salts for every new log.** Each time the log starts over, its header
gets new salts (`00000001 228094d4` in the run above). A new log is written
from the start of the file, and if the file was not cut to nothing first,
frames of an older log can still sit beyond the new ones, with checksums
that may well be valid; their salts give them away. The first salt counts
up, so it can never repeat the previous log's; the second is random, so it
is unlikely to match any older one. The checkpoint count next to them in
the header goes up by one at every checkpoint, as sqlite3's does.

**The map is rebuilt, not stored.** sqlite3 keeps it in a shared-memory file,
`demo.db-shm`, so that several processes can share one log. This engine
keeps it in memory and rebuilds it from the log at every open, which is
what sqlite3 also does when no other process has the database open.

**Page 1 is left alone when it can be.** In rollback mode every commit
rewrites page 1, to bump the change counter in the header. In WAL mode a
commit includes page 1 only when it changes anyway or the database grows,
which is why each of the three updates above wrote one frame, not two.

The rest is plumbing: the pager gains a pointer to its open log, its page
reads ask the log first, and `wal.c` keeps its own copies of the two small
file helpers of `journal.c`.

## Break it

Put the commit mark on the first frame instead of the last: in `wal_commit`,
change `put4(f + 4, i == n - 1 ? p->npages : 0);` to
`put4(f + 4, i == 0 ? p->npages : 0);`, then `make`. Change all 2000 rows,
which is 90 frames (pages 3 to 92), and crash after half of them are
appended:

      40

The log holds 45 frames, and the first one says "this commit is complete".
So reading the log takes frame 1, page 3 with rows 1961 to 2000, as a whole
commit: 40 rows of a transaction that never finished. The engine as written
leaves the same 45 frames with no mark among them, and the next open keeps
none of them: 0 rows.

## Decide the boundary

A log makes commits cheap: one sequential append and one `fsync`, and in
sqlite3 readers can keep reading the old versions while a writer appends.
It pays elsewhere. Every read checks the log first; every page is written
twice in the end, once to the log and once at the checkpoint; the log grows
until a checkpoint can run; and the log must always travel with its
database, as the 22 rows of the lone copy show. The rollback journal costs
more per commit and nothing afterwards. Does your workload commit often and
small, or rarely and big, and who copies your database files?
