# 06.02 The rollback journal and atomic commit

Before a commit overwrites a single page of the database, it copies the
original of every page it is about to overwrite into a second file, the
journal. Then it writes the new pages, and deletes the journal. That
deletion is the moment the transaction commits.

## Where this fits

![Where 06.02 fits](figures/06.02-map.svg)

The pager collects every page a transaction changes and, at COMMIT, hands
them over to be written into the file; the previous lab showed what a crash
in the middle of that does. This lesson puts the journal between the pager
and the file: it gets the changed pages, sorted by page number, and owns the
order in which the journal, the database and the disk are written. It uses
nothing above the pager. After this lesson a crash at any moment of a commit
leaves either the whole old database or a journal that can restore it; the
next lesson writes the code that does the restoring when the file is opened
again.

## The idea

The trouble in 06.01 was that a page, once overwritten, is gone. So keep it:
before touching the database, write the original of every page the commit
will change into `demo.db-journal`, and make sure it is on the disk. Now a
crash while the database is half written is harmless, because the next open
finds the journal and copies the originals back.

That leaves one question: how does the next open know whether to roll back?
If the journal is incomplete, the database was never touched and the journal
should just be deleted. If it is complete, the database may be half written
and the journal must be played back. And once the commit has finished, the
journal must not be played back at all. The answer is a mark, written last,
and a deletion:

1. Write the originals, with a header whose first 8 bytes are still zero.
   The header fills one 512-byte sector, the unit sqlite3 assumes a disk
   writes in, so the records after it start on a sector boundary.
2. `fsync` the journal and its directory (`fsync_dir`: without that, a new
   file's name can be lost in a power cut even when its bytes are not).
3. Write the real header (a **magic number** and the record count) and
   `fsync` again. Now the journal is **hot**: complete, and binding.
4. Write the new pages into the database, then `fsync` it.
5. Delete the journal. That is the **commit point**: before it, any crash
   rolls back; after it, the transaction has happened.

Each `fsync` is a barrier. Nothing after it can reach the disk before the
things written ahead of it, so the steps happen on the disk in the order
they happen in the code.

![journal_commit step by step, the crash points along it, and what the next open does after a crash at each.](figures/06.02-commit-order.svg)

### journal_write: copy the originals aside

Called by the commit with the dirty pages and a new, empty journal file. It
writes the header and one record per page that existed before the
transaction, then makes the journal durable, and only then hot.

### journal_commit: the commit, in order

The pager's commit calls this in rollback mode instead of writing pages
itself. It creates the journal, calls `journal_write`, writes the pages,
syncs the database and deletes the journal: the five steps above, with a
named crash point between each pair, so any gap can be crashed on purpose.

## How it works

### Writing journal_write, step by step

1. **A copy of each page.** A header that says how big a page is, then, for
   every page the commit will overwrite, its page number and its original
   bytes, read from the database file, which nothing has written over yet.

   ```
   must_pwrite(jfd, hdr, sizeof hdr, 0, jpath);
   ...
   for (u32 i = 0; i < n; i++) {
       u32 pgno = pages[i]->pgno;
       put4(rec, pgno);
       read_page(p, pgno, rec + 4);
       must_pwrite(jfd, rec, reclen, off, jpath);
       off += (off_t)reclen;
       nrec++;
   }
   ```

2. **Skip pages that are new.** A page past the old end of the file has no
   original; the header records the old page count instead, and rolling
   back cuts the file back to it.

3. **A checksum on every record,** seeded by a random **nonce** in the
   header, so that a record cut short or left over from an older journal is
   not copied into the database. sqlite3 checks it too before it plays a
   record back. (`put4` writes a 4-byte number, high byte first, as every
   number in the journal is stored.)

4. **The mark goes in last.** The header first goes out with its magic and
   record count as zeroes. A crash while the records are being written then
   leaves a journal whose first byte is 0: not hot, deleted unread, and the
   database, not yet touched, stays as it was.

5. **An fsync on each side of the mark.** Without the one before it, the
   disk may store the mark ahead of the records, and a power cut in between
   leaves a hot journal of half-written records for recovery to copy over
   good pages; the directory is synced there too, or the new file can lose
   its name. Without the one after it, the database is overwritten while
   the mark may still be in the cache, and a power cut leaves new pages
   beside a journal that is not hot.

   ```
   if (sys_fsync(jfd) < 0)
       fatal("fsync %s: %s", jpath, strerror(errno));
   fsync_dir(jpath);
   memcpy(hdr, journal_magic, 8);
   put4(hdr + 8, nrec);
   must_pwrite(jfd, hdr, 12, 0, jpath);
   if (sys_fsync(jfd) < 0)
   ```

### Writing journal_commit, step by step

1. **Start from the commit of 06.01.** Write every changed page in place,
   then `fsync` the file: the half-transaction machine of the last lab.

   ```
   int journal_commit(Pager *p, Page **pages, u32 n)
   {
       for (u32 i = 0; i < n; i++) {
           write_page(p, pages[i]->pgno, pages[i]->data);
       }
       if (sys_fsync(p->fd) < 0)
           fatal("fsync %s: %s", p->path, strerror(errno));
       return 0;
   }
   ```

2. **Put the journal in front.** Create it and fill it with `journal_write`
   before the first page is written; once that returns the journal is hot,
   and a crash anywhere in the loop is rolled back. `O_TRUNC` empties a
   journal an earlier crash left before it became hot.

   ```
   int jfd = open(jpath, O_RDWR | O_CREAT | O_TRUNC, 0644);
   ...
   journal_write(p, pages, n, jfd, jpath);
   ```

3. **Delete the journal, after the sync.** Deleting it is the commit. Done
   before the database's `fsync`, a power cut just after it could lose new
   pages still in the cache, with no originals left to restore them.

   ```
   close(jfd);
   if (unlink(jpath) < 0)
   ```

4. **A crash point in every gap:** `journal-partial` and `journal-hot` in
   `journal_write`, `db-partial`, `db-torn`, `db-written` and
   `before-delete` here, each a place where a crash leaves a different file
   behind. `db-torn` asks `crash_armed` whether it is the crash point about
   to fire, and if so writes half of the middle page before it dies, the
   torn page of 06.01.

### Why it is built this way

**The originals come from the file itself.** This pager writes nothing into
the database before COMMIT; changed pages wait in memory. So at commit time
the database still holds every original, and `journal_write` simply reads
each one back from the file, past the cache, whose copies are already the
new versions. The price is that a transaction must fit in memory; sqlite3 instead journals pages as it changes
them, so it can write ("spill") pages to the database before COMMIT, which
06.03 shows.

**Deleting is the commit.** Every crash point before the deletion, even
`before-delete`, where every new page is written and synced, leaves a hot
journal and so a rollback. After it there is no journal and nothing to undo.
One filesystem operation decides the fate of the whole transaction.

**The deletion itself is not synced.** After `unlink` there is no `fsync` of
the directory, which is also what sqlite3 does with `synchronous=FULL`. If
the power goes right after a commit, the journal's name can come back, and
the next open rolls that last transaction back: the database stays whole,
but a commit the program was told about is lost. sqlite3's
`synchronous=EXTRA` closes that gap with one more sync per commit.

**Four fsyncs, and why.** Journal contents, journal directory, journal
header, database. Each one is a wait for the disk, and they are what limits
autocommit inserts in 07.01.

**Choosing the mode.** `PRAGMA journal_mode` now accepts `delete`, the
journal of this lesson and the default, as well as `off`, the bare commit of
06.01. The switch is refused inside a transaction twice over: by the SQL
layer after a BEGIN, even before anything has changed, and by the pager
whenever it holds changed pages, whoever asks.

The crash came while the journal was still empty, an empty journal is not
hot, and so sqlite3 ignored it and kept the half-written database: 1010
rows changed, exactly as with no journal at all. A crash a little later is
stranger:

<!-- verify: session cwd=project -->
```
$ cp t06.db demo.db
$ DB_CRASH=journal-hot ./db demo.db "UPDATE t SET b = 'new';"
db: crash injected at journal-hot
$ sqlite3 -list demo.db "SELECT count(*) FROM t WHERE b = 'new'; PRAGMA integrity_check;"
2000
ok
```

The journal was hot, sqlite3 rolled it back, and every row is still
changed. The journal read its "originals" from a file that already held the
new pages, so it saved the new pages, and rolling back restored them. A
journal is only worth anything if it is complete and on the disk before the
first page it protects is touched.

## Decide the boundary

This engine keeps every change in memory until COMMIT and writes it all
then; in the terms of the CMU notes linked below it is **no-steal** (no
uncommitted page reaches the file) and **force** (every committed page is
written at commit). That is why its journal can be written at the last
moment, from the file. sqlite3 allows steal: it journals each page as it is
first changed, may spill pages early, and so handles transactions bigger
than memory, at the cost of journaling as it goes. Bigger systems go further
and log changes instead of pages. How big are your transactions, and how
much memory may one of them take?
