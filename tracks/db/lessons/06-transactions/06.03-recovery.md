# 06.03 Recovery

A journal left behind by a crash is a promise that the database can be put
back. Recovery keeps that promise: the next time the file is opened, before
anything reads it, a hot journal's pages are copied back and the journal is
deleted.

## Where this fits

![Where 06.03 fits](figures/06.03-map.svg)

The previous lesson made every commit leave either a finished database or a
hot journal next to it. Something has to act on that journal, and the only
moment it can is when a process opens the database again. So recovery is
the first thing the pager does when it opens a file, before it reads even
the header; above it nothing changes, and it uses only plain file reads and
writes below. After this lesson a crash in the middle of a commit is
invisible to the next reader, whether this engine or sqlite3 left the
journal.

## The idea

![What the next open does with a journal: nothing, delete it, or play it back.](figures/06.03-recovery.svg)

If there is no journal, the last commit finished. If there is one whose
first bytes are not the magic number, it never became hot: the crash came
while it was being written, the database itself was never touched, and the
journal can simply go. If it is hot, the last commit stopped somewhere
between overwriting its first page and deleting the journal, and the
database may be any mix of old and new pages.

Playing it back is plain copying. Each record holds a page number and that
page's original bytes; write the bytes back where the page lives, at
`(page number - 1) * page size`. Then cut the file back to the size it had
before the transaction, which drops any pages it added, make all of that
durable, and only then delete the journal.

The order is the whole design. Recovery can crash too. If it does, the
journal must still be there, so the next open starts the same recovery
again. Copying an original over a page that already holds it changes
nothing, so doing it twice is as good as doing it once.

### journal_recover: roll back a hot journal

Called by the pager when it opens a database, before anything else reads
the file. It does nothing when there is no journal, deletes one that never
became hot, and plays back one that did, then reports how many pages it
restored.

sqlite3 writes journals in a different rhythm, and recovery handles those
too. Start sqlite3 on the table, give it a transaction with a tiny page
cache so it must write pages into the database before it commits, and kill
it in the middle:

<!-- verify: session cwd=project
vary 3748 int
-->
```
$ cp t06.db demo.db
$ sqlite3 demo.db < <(echo "PRAGMA cache_size=10; BEGIN; UPDATE t SET b = 'sqlite was here';"; sleep 2) & sleep 1; kill -9 $!
[1] 3748
...
$ wc -c demo.db-journal
  381488 demo.db-journal
...
$ cp demo.db peek.db
$ ./db peek.db "SELECT id FROM t WHERE b = 'sqlite was here';" | wc -l
    1828
$ ./db demo.db "SELECT id FROM t WHERE b = 'sqlite was here';" | wc -l
db: rolled back an interrupted transaction (84 pages)
       0
$ ls demo.db*
demo.db
$ sqlite3 -list demo.db 'PRAGMA integrity_check'
ok
```

`peek.db` is a copy of the database alone, without its journal: 1828 rows of
an uncommitted transaction were already in the file. With the journal next
to it, our engine restored 84 pages and none of those rows are left.

Those 84 pages were not in one run. When its cache is full, sqlite3 writes
changed pages into the database before it commits, and before each such
spill it makes the journal hot up to that point, then carries on with a new
header and new records at the next sector boundary. This journal holds
twelve hot segments of seven records each, covering pages 4 to 87, and a
thirteenth whose header was not yet written; the database already held new
versions of pages 4 to 86. Reading only the first segment would have
restored 7 of those 83 pages.

![sqlite3's journal: twelve hot segments of seven records each, a thirteenth not yet hot, and the database pages it had already overwritten.](figures/06.03-sqlite-journal.svg)

## How it works

### Writing journal_recover, step by step

1. **Look for a journal, and copy its pages back.** No journal is the case
   on almost every open, and costs one failed `open`. Otherwise each record
   holds a page number and that page's original bytes, which go back where
   the page lives.

   ```
   int jfd = open(jpath, O_RDONLY);
   if (jfd < 0) {
       free(jpath);
       return 0;    /* no journal: the last transaction finished */
   }
   ...
   for (u32 i = 0; i < nrec; i++, off += 8 + ps) {
       ...
       u32 pgno = get4(rec);
       must_pwrite(p->fd, rec + 4, ps, (off_t)(pgno - 1) * ps, p->path);
   }
   ```

   A record for a page past the old page count is skipped: the transaction
   added that page, and cutting the file back (step 2) removes it.

2. **Finish in an order that survives a crash.** Cut the file back to its
   old page count, `fsync` it, and only then delete the journal and sync
   its directory. Until the journal is gone, a crash just means the next
   open starts again, and copying an original over a page that already
   holds it changes nothing.

   ```
   if (sys_fsync(p->fd) < 0)
       fatal("fsync %s: %s", p->path, strerror(errno));
   close(jfd);
   if (unlink(jpath) < 0)
       fatal("cannot delete %s: %s", jpath, strerror(errno));
   fsync_dir(jpath);
   ```

3. **Only a hot journal is played back.** A journal too short for a header,
   or without the magic, was cut off before `journal_write` made it hot,
   and so before the database was touched: it is deleted, and the database
   left as it is.

   ```
   if (fstat(jfd, &st) < 0 || st.st_size < 28 || !read_at(jfd, hdr, 28, 0) ||
       memcmp(hdr, journal_magic, 8) != 0) {
       close(jfd);
       unlink(jpath);
   ```

4. **Do not trust the sizes.** Every offset comes from the page and sector
   sizes in the header; unless both are powers of two in the ranges the
   format allows, recovery stops with an error rather than scatter whole
   pages to the wrong places.

5. **Read every segment, not just the first.** After a segment's records,
   round up to the next sector and look for another magic: the journal
   sqlite3 left in Run it has twelve. A record count of 0xffffffff, which
   sqlite3 may leave in a header, means as many records as fit in the
   file.

   ```
   hdr_off = (off + sector - 1) / sector * sector;
   if (hdr_off + 28 > st.st_size || !read_at(jfd, hdr, 28, hdr_off) ||
       memcmp(hdr, journal_magic, 8) != 0)
       break;
   ```

**Records stop at the first one that does not check out.** Each record
carries a checksum seeded with the header's nonce. A record cut short by the
crash, or left over from an older journal with a different nonce, fails it,
and recovery stops there. With this engine's journal that never happens,
because the journal is synced before it turns hot; it is there for journals
written by others, under weaker settings.

## Break it

Delete the journal first. In `journal_recover`, add `unlink(jpath);` just
before `u8 *rec = xmalloc(8 + ps);`, and remove the
`if (unlink(jpath) < 0) fatal(...)` near the end (the file is already gone),
then `make`. Crash a commit, then crash the recovery after it has restored
its first page:

## Decide the boundary

Here recovery happens lazily, in whichever process opens the database next,
and costs nothing when there was no crash beyond looking for a file. That
puts a rule on everyone: a hot journal must never be deleted, renamed, or
separated from its database, or the half-written transaction becomes
permanent (SQLite's documentation lists exactly these as ways to corrupt a
database). Another design never needs recovery: a copy-on-write store such
as LMDB writes new pages elsewhere and switches one root pointer to commit,
so the old version is always intact, and pays with space for two versions
and a more complex free-page scheme. Who opens your database after a crash,
and can you trust everyone who touches the files in between?
