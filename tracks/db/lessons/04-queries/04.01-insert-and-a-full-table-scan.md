# 04.01 INSERT and a full table scan

This is where SQL first touches the B-tree: INSERT turns a row of values
into a record stored under a rowid, and a scan turns records back into
rows, one per call, in rowid order.

## Where this fits

![Where 04.01 fits](figures/04.01-map.svg)

Module 03 left every statement as a tree and every table as an entry in
the catalog; module 02 can store and find records by rowid. This module
joins the two: it runs statements. A query runs as a small stack of
operators, each of which hands the one above it a row when asked, and at
the bottom of every stack is a scan reading a table's B-tree. This lesson
builds that bottom piece and the INSERT that fills the table; the next
three add filtering, sorting and limits, and UPDATE and DELETE. After this
lesson the engine can store rows written in SQL and read them all back.

## The idea

![A query as a stack of operators. The SELECT loop asks the top one for a row; each asks the one below; the scan at the bottom reads the leaf one cell per call. This lesson builds the scan.](figures/04.01-operators.svg)

Take a table `p(id INTEGER PRIMARY KEY, n INTEGER, s TEXT)` and the
statement `INSERT INTO p(n, s) VALUES ('42', 7)`. Two questions stand
between it and the B-tree. Under which rowid does the row go, since no id
was given? And what exactly gets stored: the text `'42'` in an INTEGER
column, the number 7 in a TEXT column? Then `SELECT * FROM p` asks the
reverse: turn whatever bytes are in the leaves back into values, row
after row.

The rowid question has a simple answer: unless the statement names one,
the new row gets one more than the largest rowid in the table. The values
question is answered by **affinity**, the column's preference from module
03: an INTEGER column turns text that is entirely a number into that
number (`'4.5'` becomes 4.5, while `'7x'` stays text), and a TEXT column
turns numbers into text. So the row is stored as 42 and `'7'`.

Reading is organised around one question that every operator answers:
"give me your next row". The SELECT loop asks the top operator, which
asks the one below it, and so on down to the scan, which answers by
moving a cursor one entry along the table's B-tree. Each answer is a
single row, or "no more". This is the **iterator model** (also called
Volcano, after the system that made it popular). Its appeal is that each
operator is small and knows nothing about the others, and that rows flow
one at a time: nothing is held in memory unless an operator truly needs
it. In this lesson the stack is the scan alone; a WHERE, an ORDER BY or a
LIMIT is refused until the next lessons add the operators for them.

The code below builds that bottom piece, the INSERT that fills the
table, and the evaluator that both statements need for their values.

### decode_row: a record back into values

Every operator that reads a table ends up here. Given a cursor sitting on
an entry, it unpacks the record into one value per column of the table,
including the INTEGER PRIMARY KEY column, which is not in the record at
all, as the next figure shows.

![Row 1 of p as xxd shows it: the cell's size, the rowid, a record header with one serial type per column, and two bytes of body. The id column is stored as NULL; decode_row() puts the rowid in its place.](figures/04.01-record.svg)

### scan_next: the table scan

The simplest operator there is and the bottom of every plan in this
module. Its first call puts the cursor on the table's first row; each
later call moves it to the next. Because a table's B-tree is ordered by
rowid, a scan returns rows in rowid order without any sorting.

### insert_row: one row into the table

The INSERT statement works out each value, applies affinity, and hands
the row here. This function chooses the rowid, checks the constraints,
builds the record and puts it into the B-tree.

![The four INSERTs of the run below, on a line of rowids. Without an id the row gets the largest rowid plus one; asking for a rowid that is taken is an error.](figures/04.01-rowids.svg)

### `eval`: an expression to a value

Both statements in this lesson are full of expressions. Each value in
`VALUES ('42', 7)` is one, and so is each item of a SELECT list: `id`,
`typeof(n)`, `n * 2`. So is a column's DEFAULT. Module 03 parsed each of
them into a small tree, but nothing could yet say what such a tree is
worth, and INSERT needs a value to store, SELECT one to print. So the
expression evaluator arrives with the first statements that run.

Evaluating is a walk down the tree. A leaf is a literal, which is its own
value, or a column, whose value the current row supplies. Any other node
first evaluates the nodes under it, then combines their values: `n * 2`
on a row where n is 21 is 42. What comes back is one value with its type:
an integer, a float, text, a blob or NULL.

## How it works

### Writing the scan (scan_next and decode_row), step by step

1. **Move the cursor, decode, hand back.** The first call puts the cursor
   on the table's first row and every later call moves it on. The cursor
   is only positioned when the first row is asked for, so a plan that is
   built and never run (EXPLAIN) reads nothing. The answer is the
   operator's own row, overwritten by the next call.
   ```
   static int scan_next(Op *op, Row **out)
   {
       int more = op->started ? cursor_next(&op->cur) : cursor_first(&op->cur);
       op->started = 1;
       if (!more)
           return 0;
       decode_row(op->table, &op->cur, &op->row);
       *out = &op->row;
       return 1;
   }
   ```
2. **Decode the record.** `decode_row` starts as one call to the record
   code from module 01. A record it cannot decode means a damaged file,
   and the engine stops.
   ```
   int n = record_decode(c->payload, c->npayload, row->cols, t->ncols);
   if (n < 0)
       fatal("database is corrupt: bad record in table %s, rowid %lld", t->name, (long long)c->rowid);
   ```
3. **Short records.** A file where sqlite3 ran
   `ALTER TABLE ... ADD COLUMN` has old rows with fewer values than the
   table has columns. The
   file format says the missing ones take the column's DEFAULT, which the
   catalog works out once when it loads the schema, so a short row costs
   a copy, not an evaluation.
   ```
   for (int i = n; i < t->ncols; i++)
       row->cols[i] = t->cols[i].dflt_value;
   ```
4. **Floats stored as integers.** sqlite3 stores 2.0 in a REAL column as
   the one-byte integer 2, to save space. The column's affinity says it is
   still a float, so it is turned back into one; without that, `price / 4`
   on a price of 2.0 is integer division and gives 0 instead of 0.5.
5. **The rowid column.** Last, the INTEGER PRIMARY KEY column gets the
   rowid, because the record holds NULL there (the figure above).
   ```
   if (t->rowid_col >= 0) {
       Value *v = &row->cols[t->rowid_col];
       memset(v, 0, sizeof *v);
       v->type = V_INT;
       v->i = c->rowid;
   }
   ```

### Writing insert_row, step by step

1. **The easy case: no rowid given.** Take one more than the largest
   rowid in the table, found by walking the right edge of the B-tree,
   build the record, and insert it under that key. Every error will jump
   to the one label at the end, which closes the cursor and frees the
   record buffer.
   ```
   i64 max = btree_max_rowid(&c);
   ...
   rowid = max + 1;
   ...
   record_build(&rec, vals, t->ncols);
   ...
   btree_insert(&c, rowid, rec.p, (u32)rec.n);
   done:
   cursor_close(&c);
   buf_free(&rec);
   return rc;
   ```
2. **A rowid the statement asked for.** It must be an integer (`'x'` is a
   datatype mismatch) and must not be taken. The seek lands on the first
   row at or after the key, so it has to be compared with the key to know
   whether the rowid is really there.
   ```
   if (cursor_seek_rowid(&c, rowid) && c.rowid == rowid) {
       rc = err("UNIQUE constraint failed: %s.%s", t->name, keyname);
       goto done;
   }
   ```
3. **The rowid column, then NOT NULL.** Whatever rowid was chosen, the
   column that aliases it now holds it as its value. NOT NULL is checked
   after that on purpose: an `id INTEGER PRIMARY KEY NOT NULL` column left
   out of the INSERT is NULL until it is given the chosen rowid, and must
   not be refused for that.
4. **NULL in the record's rowid column.** The file format stores the
   rowid once, as the cell's key; a second copy in the record would waste
   space and could disagree with it. So the column is set to NULL just
   while the record is built, and put back after.
   ```
   saved = vals[t->rowid_col];
   memset(&vals[t->rowid_col], 0, sizeof(Value));
   ```

### Why it is built this way

**Check first, write last.** Because every check in `insert_row` comes
before its first write, a one-row INSERT that fails has changed nothing.
That is why `run_stmt` (03.02) lets a one-row INSERT inside BEGIN skip the
copies of changed pages it keeps for any other write that might fail
halfway: there is nothing to undo.

**The next rowid is the largest plus one, not a counter.** Finding the
largest rowid is a walk down the right edge of the B-tree, a few pages,
and there is no counter to store or keep in step. The price is that after
the row with the largest rowid is deleted, its rowid will be handed out
again; SQLite's AUTOINCREMENT exists for tables that must never reuse
one, and this engine does not support it. When the largest rowid is
already 9223372036854775807, this engine says `database or disk is full`;
sqlite3 instead tries random unused rowids.

**A row's text is not copied.** The values `decode_row` produces point
straight into the page in the cache: a text value is a pointer and a
length into the record. That makes reading a row nearly free, but the
values are good only until the cursor moves on. Every operator built on
the scan has to respect that, and the ones that keep rows (sorting, in
04.03) copy them.

### Writing `exec_insert`, step by step

`exec_insert` is the INSERT statement itself: it turns each row of
VALUES into one value per column of the table and hands it to
`insert_row`.

1. **The skeleton: evaluate, place, store.** For every row of VALUES,
   evaluate each expression, put the value in its column's place, and
   store the row. The row arena is emptied after each row, so a long
   VALUES list does not pile up memory.
   ```
   for (int r = 0; r < s->nrows; r++) {
       ...
       for (int i = 0; i < nmap; i++) {
           ...
           vals[map[i]] = v;
       }
       ...
       if (insert_row(db, t, vals, rowid) < 0)
           return -1;
       arena_reset(&db->rowa);
   }
   ```
2. **Which column each value goes to.** Without a column list, value i
   goes to column i. With one, each name is looked up once, before any
   row, into `map`. A name that is not a column but is `rowid`, `oid` or
   `_rowid_`, sqlite3's three names for the rowid, maps to -2: that value
   is the row's key, not a column.
   ```
   if (c < 0 && is_rowid_name(s->names[i]))
       c = -2;    /* the rowid itself */
   ```
3. **Defaults, then affinity.** A column the statement left out gets its
   DEFAULT, or NULL. Then every column's value goes through
   `apply_affinity`, and this is where `'42'` becomes 42 (spaces around
   the number are allowed; anything else after it keeps the text).
   ```
   apply_affinity(&vals[i], t->cols[i].affinity, &db->rowa);
   ```
4. **Refuse before anything is stored.** No such table, a table the
   catalog marked read-only (03.03), sqlite_schema itself, a VALUES row
   of the wrong width: each is an error before the first `insert_row`.

### Writing `exec_select`, step by step

`exec_select` is the loop at the top of the figure: it builds the plan,
asks it for rows, and prints each one.

1. **The skeleton: plan, pull, print.** Ask the top operator for a row
   until it says there are no more, evaluate each result column on that
   row, print it, and empty the row arena.
   ```
   if (plan_query(db, t, s->where, s->order, s->norder, s->limit, s->offset, &plan) < 0)
       return -1;
   ...
   while ((rc = plan.root->next(plan.root, &row)) == 1) {
       for (int i = 0; i < n; i++)
           if (eval(db, cols[i], row, &out[i]) < 0) {
       ...
       print_row(db, out, n);
       arena_reset(&db->rowa);
   ```
2. **Names first, once.** Before the first row, `*` becomes one column
   expression per column of the table, and `resolve_expr` binds every
   name to its column's place in the row, so evaluating a row never
   searches by name.
3. **Let the cache breathe.** Between two rows nothing holds a page, so
   every 256 rows the loop calls `pager_shrink` (01.02), and a scan of a
   big table keeps the cache at its size.
4. **No FROM, and EXPLAIN.** `SELECT 1 + 2` gets a "Constant row"
   operator that hands out one empty row, so the same loop prints `3`.
   EXPLAIN builds the plan, prints its operators, and never runs it.

### Writing `eval`, step by step

1. **Leaves first.** A switch on the kind of node. A literal already
   holds its value, put there by the parser; a column takes the value the
   current row has in its place.
   ```
   int eval(Db *db, Expr *e, Row *row, Value *out)
   {
       switch (e->op) {
       case E_INT: case E_REAL: case E_STR: case E_BLOB:
           *out = e->v;
           return 0;
       case E_COLUMN:
           ...
           *out = row->cols[e->col];
           return 0;
       ...
       }
       return err("internal error: unknown expression %d", e->op);
   }
   ```
2. **Inner nodes call `eval` on their children.** That recursion is the
   whole trick: in `n * 2 + 1` the left side of the `+` is another node,
   and neither node needs to know. A failure deep down (an unknown
   function, say) sets the error message where it happens and comes back
   up as -1, so each caller only checks the sign.
   ```
   case E_ADD: case E_SUB: case E_MUL: case E_DIV: case E_REM:
       if (eval(db, e->a, row, &a) < 0 || eval(db, e->b, row, &b) < 0)
           return -1;
       return eval_arith(e->op, a, b, out);
   ```
   The arithmetic itself is in `eval_arith`, which keeps integers as
   integers until a result overflows, and gives NULL for a division by
   zero, as sqlite3 does.
3. **NULL in, NULL out.** NULL means unknown, so nearly every operator
   with a NULL operand has a NULL answer: an unknown n plus one is still
   unknown. Each case checks for that before its real work. `IS NULL` is
   the exception, since asking that question is its whole job.
   ```
   if (a.type == V_NULL || b.type == V_NULL) {
       set_null(out);
       return 0;
   }
   ```
4. **Text that did not exist before.** Most results fit in a value as
   they are: a number, or a pointer to text that already lives somewhere,
   in the page or in the statement. `||` makes new text, and that needs
   memory. It comes from `db->rowa`, an arena the SELECT loop empties
   after each row, so a query over a million rows uses the memory of one,
   and nothing is freed piece by piece.
   ```
   Value x = to_text(&db->rowa, &a), y = to_text(&db->rowa, &b);
   char *s = arena_alloc(&db->rowa, (size_t)(x.n + y.n + 1));
   ```

**The rest of expr.c is helpers.** The scalar functions (`typeof`,
`length`, `abs`, `lower`, `upper`, `coalesce`, `ifnull`) are a switch on
the name. LIKE already works, because matching a pattern needs no order
between values; `=`, `<`, AND and OR wait for the next lesson's rules for
NULL and affinity. Values print the way sqlite3 prints them, floats
included, so the same query shows the same text in both shells.

## Decide the boundary

This engine hands one row per call up the stack. Each operator costs a
function call per row, and every row is decoded whether or not the query
needs all its columns. Analytical engines instead pass a batch of many
rows per call (the vectorized model), or let an operator
produce its whole output at once (the materialization model), and pay in
memory and in more complex operators. For an engine whose typical query
touches ten rows, the per-row call is noise. How many rows would a query
have to touch before it is not?
