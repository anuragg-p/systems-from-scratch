# 04.04 UPDATE and DELETE

UPDATE and DELETE change rows that a search finds. The finding and the
changing have to be kept apart, or the changes get in the way of the
search that is still going on.

## Where this fits

![Where 04.04 fits](figures/04.04-map.svg)

UPDATE and DELETE stand beside SELECT at the top of this module. They
find their rows with the same stack of operators, a scan with a filter on
it, and then, instead of printing each row, they change the table's
B-tree, using the insert and delete from module 02. After this lesson the
engine runs its whole SQL subset on a table: it can add rows, read them,
change them and remove them.

## The idea

![UPDATE t SET id = id + 100 done in two phases, and what would happen if the scan changed rows as it went: row 1 moves ahead of the cursor and is met again, for ever.](figures/04.04-two-phase.svg)

Take `UPDATE t SET id = id + 100` on rows 1, 2 and 3. Changing a rowid
moves the row: row 1 becomes row 101, which in a B-tree ordered by rowid
is a different place, ahead of rows 2 and 3. Now imagine the search for
rows to update is a scan still walking the tree. It moves row 1 to 101,
goes on to 2 and 3, then arrives at 101, which also matches, and moves it
to 201. It never reaches the end. This is the **Halloween problem**, named
for the day in 1976 when it was found in IBM's System R.

The fix is to do the work in two phases. First run the search to the end
and keep only the rowids of the rows it found. Then change those rows one
at a time, finding each again by its rowid. The search finishes before
the first change, so nothing a change does can be seen by it.

This also gives SQL's meaning for SET for free. Every expression on the
right of SET is worked out from the row as it was before the statement,
so `UPDATE t SET n = id, id = n` swaps the two columns instead of copying
one into the other.

Indexes would be one more thing to keep in step with every change. They
come with module 05, and [05.01](../05-indexes/05.01-an-index-is-a-btree.md)
adds the lines here that keep them right.

### exec_update: UPDATE

The rowids have been collected when this code starts. For each one it
reads the old row, works out the new values from it, and checks that the
change is allowed: a new rowid must be free, and NOT NULL columns must
stay filled. Then it takes the old row out of the table if its rowid
moved, and stores the new row with module 02's insert, which replaces a
row that has the same rowid: when the rowid stays, the row is simply
overwritten in place.

### exec_delete: DELETE

Simpler: for each collected rowid, find the row and delete it from the
table's B-tree.

Moving every row up by 100 works, each row once. Moving them up by 1
fails, in both engines, because row 1 would land on row 2, which still
exists. And SET reads the old row, so the second UPDATE is a swap:

```

```

A statement that fails halfway leaves nothing behind. Here row 1 is
changed first (`10 / 1` is 10); row 2 then fails, since `10 / 0` is NULL
in SQL and n may not be NULL:

```

db> UPDATE u SET n = 10 / n;

db> SELECT * FROM u;
1|1
2|0
```

The search half is the same plan a SELECT would use. It still scans the
whole table to find one id; module 05 turns `id = 30` into a single seek.

## How it works

### Writing exec_update, step by step

1. **Collect first, then visit each row by rowid.** Run the WHERE
   clause's plan to the end and keep only the rowids it finds; that list
   is the whole fix for the Halloween problem. Then seek each rowid,
   build the new row, and insert it under its rowid, which replaces the
   row in place when the rowid did not change. A row that is no longer
   there is skipped, and the seek must be checked against the rowid,
   since it lands on the next row when the one asked for is missing.
   ```
   if (collect_rowids(db, t, s->where, &ids, &n) < 0)
       return -1;
   ...
   for (i64 k = 0; k < n && rc == 0; k++) {
       if (!cursor_seek_rowid(&c, ids[k]) || c.rowid != ids[k])
           continue;
       ...
       btree_insert(&c, newid, rec.p, (u32)rec.n);
       arena_reset(&db->rowa);
   }
   ```
2. **Read the old row and copy it.** Its values point into the page this
   loop is about to change, so they are copied out first (why, below).
   ```
   decode_row(t, &c, &old);
   keep_row(db, &old);
   ```
3. **New values from the old row.** Start the new row as a copy of the
   old one, then evaluate each SET expression against the *old* row and
   store the result, with the column's affinity, in the new one.
   Evaluating against the old row is what makes `SET n = id, id = n` a
   swap.
   ```
   memcpy(newv, oldv, (size_t)t->ncols * sizeof(Value));
   ...
   if (eval(db, s->sets[i], &old, &v) < 0) {
   ```
4. **A new rowid must be free.** It is the old one unless SET changed the
   INTEGER PRIMARY KEY (or the rowid itself), and it must be an integer.
   If it changed, no other row may already have it: this is where
   `SET id = id + 1` fails, row 1 meeting row 2.
   ```
   if (newid != old.rowid) {
       if (cursor_seek_rowid(&c, newid) && c.rowid == newid) {
   ```
5. **NOT NULL, then move the row.** NOT NULL is checked as INSERT checks
   it, still before any change, so a refused row is left exactly as it
   was. Only then, if the rowid moved, is the old row deleted; the new
   record is built with NULL in the rowid column, as INSERT does.
   ```
   if (newid != old.rowid) {
       if (cursor_seek_rowid(&c, old.rowid) && c.rowid == old.rowid)
           btree_delete(&c);
   }
   ```

### Writing exec_delete, step by step

1. **The same collection, then a seek per rowid**, exactly as in UPDATE,
   and a delete of the row the cursor lands on.
   ```
   if (collect_rowids(db, t, s->where, &ids, &n) < 0)
       return -1;
   ...
   for (i64 k = 0; k < n; k++) {
       if (!cursor_seek_rowid(&c, ids[k]) || c.rowid != ids[k])
           continue;
       btree_delete(&c);
       arena_reset(&db->rowa);
   }
   ```
2. **Seek every time.** A delete leaves the cursor unpositioned: the leaf
   it stood in may have emptied and gone back to the freelist. The next
   rowid on the list still says exactly where to go, so the loop seeks it
   afresh instead of stepping the cursor on.

### Why it is built this way

**Only rowids are collected.** The first phase keeps 8 bytes per row, not
a copy of the row. A rowid is the one thing about a row that stays put
while the B-tree changes around it: pages split and merge, cells move
between pages, but rowid 2 is still rowid 2. So each row is looked up
again by rowid in the second phase, and a row that has meanwhile gone is
simply skipped. Like the SELECT loop (04.01), the collecting loop lets
the cache shrink every 256 rows, since it holds no page between them.

**The old row is copied before anything changes.** Values read from a
row point into its page in the cache (04.01), and an update is about to
change that very page. When the rowid moves, the old row is deleted
before the new record is built, and the new record reuses the old value
of every column SET did not mention. Without the copy, those values are
read from a page the delete has just rearranged: without the copy, after
`UPDATE t SET id = id + 100`, rows holding `apple`, `banana` and `cherry`
come out holding `anana`, `cherry` and `anana`.

**A failed statement is undone by the code around it.** The loop stops at
the first error, possibly after changing rows. It does not undo them
itself: `run_stmt` (03.02) does. Outside a transaction it drops the
statement's changes, and inside one it puts back the pages this
statement changed. That is why table u above still holds 1 in row 1.

Three rows went in, one came out, and nothing complained. Row 1 moved to
rowid 2, and inserting under a rowid that is taken replaces the row
there, so row 2 was simply overwritten. Then the second phase took rowid
2 from its list, found the row it had just moved, and moved it again,
onto 3, and then onto 4. The list of rowids stands for a list of rows
only while no two rows can share a rowid; that check is what keeps it
so. The file itself is perfectly sound, which is why sqlite3's check
finds nothing: no page is damaged, two rows of data are just gone.
sqlite3 refuses the statement, as the unbroken engine does.

## Decide the boundary

This engine always collects the rowids first, so the cost of an UPDATE
includes a list as long as the number of rows it changes: 8 MB for a
million rows. An engine can skip the list when it can prove the change
cannot be met again by the search, for example when the update changes no
column the scan is ordered by, which here would mean neither the rowid
nor the column of the index being walked. Engines with multi-version
storage avoid the problem differently: the search reads the table as it
was when the statement began, and never sees the changes at all. Is the
list worth keeping for its simplicity, or is the common case, an update
of a few columns that moves no row, worth a second path?
