# 04.03 ORDER BY and LIMIT

ORDER BY cannot hand out its first row until it has seen the last one;
LIMIT can stop as soon as it has enough. Both fit the one-row-at-a-time
model, from opposite ends: one waits, the other quits early.

## Where this fits

![Where 04.03 fits](figures/04.03-map.svg)

Sort and limit are the last two operators of a SELECT, stacked above the
filter, so a full plan reads from the bottom: scan, filter, sort, limit.
The sort is the only operator in the engine that keeps rows; every other
one passes each row on as soon as it has it. The limit is the only one
that stops asking for more. After this lesson a query can say in what
order it wants its rows and how many of them, and SELECT on one table is
complete.

## The idea

Ask for `SELECT id, n FROM t ORDER BY n LIMIT 3` over 3000 rows. The row
with the smallest n might be the very last one in the table. So no
operator can hand out the first row of a sorted result before it has
looked at every row: sorting has to collect everything, sort it, and only
then start answering. An operator like that is called a
**pipeline breaker**: rows stop flowing through it one at a time.

LIMIT is the opposite. `SELECT id FROM t LIMIT 3` needs three rows, so
once it has handed out three, it has no reason to ask for a fourth. In
the pull model that is free: the operator simply stops asking, the scan
below it is never asked to move again, and the rest of the table is never
read. On the 3000-row table of Run it that is 3 pages read instead of
59. Put a sort between them and the saving is gone, because the sort
reads everything on the limit's first request.

![The same table of 3000 rows on 59 pages, two queries. LIMIT alone stops after three rows and three pages; with a Sort below it, every row is read before the first comes out.](figures/04.03-breaker.svg)

What does sorted mean when a column holds numbers, text and NULL
together? The same order WHERE uses for comparisons: NULL first, then
numbers by value, then text, then blobs.

![One column holding five kinds of value, sorted both ways. DESC is the exact reverse, so NULL ends up last.](figures/04.03-order.svg)

Two pieces of code.

### sort_next: sort the rows

The sort operator. On the first request it pulls every row from below,
keeps its own copy of each, sorts the copies by the ORDER BY terms, and
then answers each request with the next row in order.

### limit_next: LIMIT and OFFSET

The operator at the top. It first throws away OFFSET rows, then passes
on at most LIMIT rows, and after the last one answers "no more" without
asking the operator below for anything.

## How it works

### Writing sort_next, step by step

1. **Two halves in one function.** The first call pulls every row from
   below and sorts them; every call, the first included, then hands out
   the next row of the sorted array until there are none. The pulling
   loop is what makes the sort a pipeline breaker, and what read all 59
   pages in Run it.
   ```
   if (!op->started) {
       op->started = 1;
       ...
       while ((rc = op->child->next(op->child, &r)) == 1) {
           ...
       }
       ...
   }
   if (op->pos >= op->nrows)
       return 0;
   SortRow *s = &op->rows[op->pos++];
   ```
2. **Grow the array as rows arrive.** Nobody knows the number of rows in
   advance, so the array doubles whenever it is full, starting at 256;
   doubling keeps the total copying proportional to the number of rows.
   ```
   if (op->nrows == cap) {
       cap = cap ? 2 * cap : 256;
       op->rows = xrealloc(op->rows, (size_t)cap * sizeof(SortRow));
   }
   ```
3. **Copy the row, and its keys.** The row's values point into a page of
   the cache (04.01), which will hold other data once the scan below moves
   on, so every value is copied into the sort's own arena before the next
   row is asked for. Each ORDER BY term is evaluated once and stored
   beside the row, copied too (why, below).
   ```
   for (int i = 0; i < r->ncols; i++)
       s->cols[i] = keep(&op->sort_arena, r->cols[i]);
   ```
4. **Sort.** C's `qsort` gives the comparison function no way to receive
   extra data, so the ORDER BY terms reach it through two variables in the
   file. That is safe here because only one statement runs at a time. Each
   row also carries its arrival number, for ties (below).
   ```
   sort_terms = op->order;
   sort_nterms = op->norder;
   qsort(op->rows, (size_t)op->nrows, sizeof(SortRow), sort_cmp);
   ```

### Writing limit_next, step by step

Short, but every line matters.

1. **Pass one row through, counting it.** The simplest version asks the
   operator below for a row and hands it on. `seen` counts every row
   taken from below.
   ```
   static int limit_next(Op *op, Row **out)
   {
       int rc;
       ...
       rc = op->child->next(op->child, out);
       if (rc == 1)
           op->seen++;
       return rc;
   }
   ```
2. **Stop before asking.** The rows handed on so far are `seen - offset`.
   Once that reaches the limit, answer "no more" without calling the
   operator below; a negative limit never stops. This early return is
   what kept the first query in Run it at three pages.
   ```
   if (op->limit >= 0 && op->seen - op->offset >= op->limit)
       return 0;
   ```
3. **Skip the offset first.** Before that check, while fewer rows than
   OFFSET have been taken from below, take one and throw it away. `seen`
   counts those skipped rows too, which is why the check in step 2
   subtracts the offset.

### Why it is built this way

**Keys are worked out once per row.** Before sorting, the sort evaluates
each ORDER BY term for each row and stores the result beside the row's
copy. The comparison function then only compares stored values. Sorting
n rows takes about n log n comparisons, so evaluating an expression like
`lower(name)` inside the comparison would do it some twenty times per
row for a few thousand rows instead of once.

**Ties keep their arrival order.** C's `qsort` is not stable: rows with
equal keys can come out in any order. SQL allows that, but a query that
answers differently from run to run is unpleasant. So each copied row
also records its arrival number, and the comparison falls back to it
when every key is equal. That is why the three rows with n = 0 above came
out as 1000, 2000, 3000.

**The copies live in one arena.** Thousands of small copies of values
would mean thousands of `malloc` calls and as many `free`s. The sort
takes them all from its own arena and drops the arena when the operator
is closed. The whole result is in memory, which is the price of this
design: a sort larger than memory has nowhere to go.

**ORDER BY may name a result column.** `ORDER BY 2` means the second
column of the result, and `ORDER BY v` may name an alias given in the
SELECT list. Before the plan is built, such a term is swapped for that
column's expression, so the sort only ever sees expressions.

**LIMIT is read once.** The limit and the offset are evaluated before the
first row exists, so they cannot mention a column (`LIMIT id` is
`no such column: id`), and a value that is not a whole number is a
datatype mismatch, as in Run it. A negative OFFSET counts as 0.

## Break it

In build/at/db/04.03/src/exec.c, in `limit_next`, stop when
`op->seen >= op->limit` instead of when
`op->seen - op->offset >= op->limit`. Run
`./learn run db --at 04.03 -- lim.db` and ask for three rows after
skipping two, over ids 1 to 6:

<!-- verify: patch file=src/exec.c old="op->seen - op->offset >= op->limit" new="op->seen >= op->limit" -->
<!-- verify: session run="./learn run db --at 04.03 -- lim.db" -->
```
db> CREATE TABLE t(id INTEGER PRIMARY KEY);
db> INSERT INTO t VALUES (1), (2), (3), (4), (5), (6);
db> SELECT id FROM t LIMIT 3 OFFSET 2;
3
```

<!-- verify: revert file=src/exec.c -->
<!-- verify: fact cmd="rm -f right.db; ./db right.db \"CREATE TABLE t(id INTEGER PRIMARY KEY); INSERT INTO t VALUES (1), (2), (3), (4), (5), (6); SELECT id FROM t LIMIT 3 OFFSET 2;\" | paste -sd, - | sed \"s/,/, /g\"" expect="3, 4, 5" -->
The right answer is 3, 4, 5.

![The counter seen counts every row taken from below, skipped ones included. As written the condition subtracts the skipped rows; broken, it stops one row after the offset.](figures/04.03-limit.svg)

`seen` counts every row taken from below, including the two that OFFSET
threw away. Compared with the limit directly, it is already 2 before any
row is handed on, so only one row gets through. Without an OFFSET the two
conditions agree, which is how a bug like this survives: `LIMIT 3` alone
still prints 1, 2, 3.

## Decide the boundary

This sort holds every row in memory and sorts them all, even when LIMIT
will keep three. Two other designs are common. A **top-N** sort keeps
only the best N rows seen so far in a small heap, so `ORDER BY n LIMIT 3`
needs memory for three rows instead of three thousand. An **external**
sort writes sorted runs to disk and merges them, so it can sort more than
fits in memory; SQLite does this. Both cost code, and the external one
costs disk writes. Which would you build first: the one that saves memory
on every LIMIT query, or the one that makes very large sorts possible?
