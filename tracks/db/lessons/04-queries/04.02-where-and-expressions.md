# 04.02 WHERE and expressions

WHERE keeps the rows a condition is true for. In SQL that is subtler than
it sounds: a value can be NULL, meaning unknown, and a comparison with
something unknown is neither true nor false.

## Where this fits

![Where 04.02 fits](figures/04.02-map.svg)

The filter sits directly on top of the scan in the stack of operators. It
asks the operator below for rows and passes on only those the WHERE
condition holds for, which it decides by evaluating the condition's
expression tree, the one the parser built, against each row. Above it is
whatever wants rows: the sort and limit of the next lesson, the SELECT
loop, and UPDATE and DELETE, which find their rows the same way. After
this lesson queries can pick rows, and every comparison, AND and OR follows
SQLite's rules for NULL and for values of different types.

## The idea

![Three rows through WHERE n < 6. The condition is true for one, false for one, and NULL for the row whose n is NULL. Only true passes.](figures/04.02-filter.svg)

Take three rows, `(1, 5)`, `(2, NULL)` and `(3, 7)`, and the query
`SELECT id FROM t WHERE n < 6`. Row 1 passes and row 3 does not. Row 2 is
the interesting one: its n is unknown, so whether it is below 6 is
unknown too. SQL's answer is that the comparison gives NULL, and WHERE
keeps a row only when the condition is *true*. So row 2 is dropped, and
it is dropped again by `WHERE NOT n < 6`, because the opposite of unknown
is still unknown.

That makes logic three-valued: true, false and unknown. AND and OR extend
in the only sensible way. If one side of an AND is false, the whole is
false, whatever the other side is; if one side of an OR is true, the whole
is true. Otherwise, if either side is unknown, so is the answer.

![AND and OR with NULL. In the shaded rows the left side settles the answer on its own, and the right side is never evaluated.](figures/04.02-truth.svg)

The second difficulty is that values have types, and a column may hold
any of them. So every comparison needs an answer even between a number
and a piece of text. SQLite's answer is one order for all values, the one
`value_compare` already gives index keys (02.01): NULL, then numbers by
value (an integer and a float compare exactly), then text byte by byte,
then blobs. And before comparing, a column's affinity
converts the other side, so that `n = '5'` finds the row whose n is 5 in
an INTEGER column. Two literals have no affinity, so `1 = '1'` is false:
a number is never equal to text.

![One order for every value, and three comparisons that show affinity at work, with the answers both engines give.](figures/04.02-compare.svg)

Three pieces of code carry this.

### filter_next: keep the rows WHERE is true for

The operator. Each time it is asked for a row, it asks the operator
below for rows until one makes the condition true, and hands that one up.
It does not know what is above or below it, so the same filter serves
SELECT, UPDATE and DELETE. For EXPLAIN it carries the condition printed
back from its tree, every node in brackets.

### eval_compare: compare two values

Every comparison in the engine ends here: `=`, `<`, `IS`, and the
comparisons inside BETWEEN and IN. BETWEEN is two of them, `x >= lo` and
`x <= hi`, joined with the same three-valued AND. IN compares the left
side with each item in turn: a match is true, no match is false, and no
match with a NULL among the items is unknown, because the NULL might
have been the match.

### eval_logic: AND and OR

The three-valued AND and OR from the table above.

## How it works

### Writing eval_compare, step by step

1. **Compare and answer 1 or 0.** The simplest version asks the
   engine-wide order which value is smaller and turns that into the
   answer the operator wants. For two numbers or two strings this is
   already right.
   ```
   int c = value_compare(&a, &b);
   int r = 0;
   switch (op) {
   case E_EQ: case E_IS: r = c == 0; break;
   case E_NE: case E_ISNOT: r = c != 0; break;
   case E_LT: r = c < 0; break;
   ...
   }
   set_int(out, r);
   ```
2. **NULL makes the answer unknown.** In that order NULL is the smallest
   value of all, so step 1 alone would say `NULL < 6` is true. For every
   ordinary operator a NULL on either side must give NULL before any
   comparing happens. IS and IS NOT are the exception, and go first:
   they exist so that NULL can be asked about, so two NULLs are the same
   and NULL differs from anything else.
   ```
   if (op == E_IS || op == E_ISNOT) {
       ...
   } else if (a.type == V_NULL || b.type == V_NULL) {
       set_null(out);
       return;
   }
   ```
3. **Affinity before comparing.** If one side is a column with a numeric
   affinity and the other is not numeric, the other side is turned into a
   number when it looks like one; a TEXT column turns a side with no
   affinity into text. This is what makes `n = '5'` find the row whose n
   is 5. The rules, and their order, are SQLite's (Go deeper has the
   page). The two values were passed by copy, so converting them changes
   nothing in the row itself.

### Writing eval_logic, step by step

1. **Evaluate both sides, then combine.** Each side is read as true,
   false or unknown (1, 0 or -1): a number counts as true when it is not
   zero, and NULL is unknown.
   ```
   if (eval(db, e->a, row, &a) < 0)
       return -1;
   int ta = value_truth(&a);
   ...
   if (eval(db, e->b, row, &b) < 0)
       return -1;
   int tb = value_truth(&b);
   if (e->op == E_AND) {
       ...
   ```
2. **Stop when the left side decides.** A false left side settles an AND,
   a true one settles an OR, and the right side is never evaluated. That
   is quicker, and it also means an error on the right (say, an unknown
   function) is never raised when it cannot matter:
   `SELECT 0 AND nosuch(1)` prints 0. (sqlite3 checks function names
   before it runs anything, so it refuses that statement.)
   ```
   if (e->op == E_AND && ta == 0) {
       set_int(out, 0);
       return 0;
   }
   ```
3. **Combine, false before unknown.** For AND, a false right side wins;
   only then does an unknown on either side make the answer NULL; only
   then is it true. Asked the other way round, `NULL AND 0` would be NULL
   instead of 0. OR is the mirror image.
   ```
   if (tb == 0)
       set_int(out, 0);
   else if (ta == -1 || tb == -1)
       set_null(out);
   ```

### Why it is built this way

**Affinity comes from the column side only.** Each operand carries the
affinity of the column it came from, or none if it is a literal or a
computed value. That is why `n = '5'` and `1 = '1'` give different
answers: in the second, neither side is a column, so nothing is converted
and a number is never equal to text. The items of an IN list never lend
their affinity, even when they are columns: SQLite defines
`a IN (x, y)` as `a = +x OR a = +y`, and a unary plus strips affinity.

**A dropped row leaves nothing behind.** Evaluating a condition can
allocate memory: `name || 'x'` builds new text. That memory comes from an
arena reset after every row the filter drops, so scanning a million rows
to keep three uses the memory of one row, not a million.

**The shell's .schema becomes a query.** Until now `.schema` walked page
1 with a cursor because there was no other way to ask. With WHERE
working, it runs an ordinary statement,
`SELECT sql || ';' FROM sqlite_schema WHERE sql IS NOT NULL`.


Comparisons now fall through to the ordering, where NULL is the smallest
value of all. So NULL equals NULL, NULL is below 6, and row 2 joins the
answer to `n < 6`. Nothing crashes and every answer looks plausible,
which is what makes this kind of bug dangerous: `WHERE n = NULL`, which
must never match, now finds a row.

## Decide the boundary

SQL makes NULL mean "unknown" and carries the unknown through every
comparison and every AND and OR. Most programming languages do the
opposite: null is a value, `null == null` is true, and a condition is
true or false. SQL's choice is consistent and lets a query state
honestly what it does not know, but it is a steady source of surprises:
`WHERE n < 6 OR NOT n < 6` does not return every row, and one NULL in a
NOT IN list empties the result. `IS` and `IS NOT` exist as the way out.
If you were designing a query language today, would you keep the third
value?
