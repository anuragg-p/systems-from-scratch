# 06.04 patch: applying a diff

A diff is only half of the job: patch is the program that reads one and makes
its changes in a file. This lesson builds it. It applies what the system's diff
prints, finds where a change goes when the file has gained or lost lines since
the diff was made, and leaves the file alone when a change does not fit.

## Where this fits

![Where 06.04 fits](figures/06.04-map.svg)

patch is the last box of module 06's strip and the second program of its
column. It stands on the diff engine's line splitter from 06.01 and on module
01's growable array, which holds the result line by line. It needs neither the
table nor Myers' search: the diff it reads already says what changed.
After this lesson the module is a pair that works both ways: the system's patch
applies what our diff prints, and ours applies what the system's diff prints.

## The idea

![patch looking for where a hunk's old lines are: the header says line 1, the file has two lines more at the top, and the six lines are found at line 3.](figures/06.04-offset.svg)

A hunk says which lines it expects to find and where: `@@ -1,6 +1,6 @@` and the
lines marked ' ' and '-' are six lines of the old file from line 1. The
obvious patch goes to that line, checks that those lines are there, and puts
the hunk's new lines, ' ' and '+', in their place. That works on the file the
diff was made from.

A diff is usually applied somewhere else, though: to another copy of the file,
which someone has edited since. Put two lines on top of the old contents, a
note and a blank line, and the six lines are now at line 3. The obvious patch
looks at line 1, finds the note, and has to give up, although the change would
fit perfectly two lines further down. This is what the context lines are for:
they let patch recognise the place, not only check it. So when the lines are
not at the stated line, patch looks one line on, one line back, two on, two
back, and so on, and takes the nearest place where all the old lines are, as
in the figure. The distance is the hunk's **offset**, and the next hunk starts
its own search from its stated line moved by that offset, since lines added
near the top of a file move every hunk below them.

A hunk whose lines are nowhere to be found does not apply. Then this patch
changes nothing at all, so a file is never left half patched.

### `read_hunk`

Reads one hunk: its header, then lines until it has as many old lines (' ' and
'-') and new lines (' ' and '+') as the header's counts say. An empty line
counts as an empty context line, whose space an editor or a mail program took
off; a `\ No newline at end of file` line takes the newline off the line before
it.

### `find`

Where a hunk applies: from its stated line, moved by the last hunk's offset,
outwards in both directions, never before the end of the last hunk and never
past the end of the file. `fits()` compares the hunk's old lines with the file's
from one place, and stops at the first that differs.

### `apply`

Applies a file's hunks in order: the file's lines up to the place a hunk was
found, then the hunk's new lines in place of its old ones, and after the last
hunk the rest of the file. It builds the result as a list of line pointers,
into the file and into the patch, and counts the hunks that did not apply.
`patch_file()` writes the result only when that count is 0. The rest of
`tools/patch/patch.c` is the program around them: reading the patch into lines
with 06.01's `diff_text()`, the file names from the `---` and `+++` lines, and
the options `-p`, `-o`, `-s` and `-i`.

one's offset, and 21 for the third, which searches outwards 10 lines.

## How it works

### The header's counts say where a hunk ends

A hunk has no end marker. The next hunk's `@@`, or the next file's `---`, could
be told apart, but a line of text can start with either, so `read_hunk()` reads
exactly as many lines as the header promises:

```
    for (i++; old < h->na || new < h->nb; i++) {
```

and stops with an error if a line has a mark it does not know before the counts
are used up. So the counts must be right. The line number need not be, as the
search below shows.

### Hunks in order, never overlapping

`find()` searches outwards from where the hunk is expected, the closest place
first, so that of two places a hunk would fit the one nearer its stated line
wins:

```
    for (long d = 0; want + d <= hi || want - d >= lo; d++) {
```

`lo` is where the last hunk ended. Each hunk must come after the one before, as
diff prints them, and two hunks never claim the same line. That is the
**invariant** `apply()` keeps with `done`: every line of the file before it has
been copied or replaced once, and no hunk may start before it. The diff that
06.02's Break it printed, with lines 7 and 8 in two hunks, is refused here for
that reason, while the system's patch applies it.

### All or nothing

The result is a list of pointers to lines, in the file and in the patch, and
nothing is copied until every hunk has been placed. Only then is it written, to
a new file beside the old one, which is renamed over it: a crash in the middle
leaves the old file, not half of each.

## Decide the boundary

This patch refuses a hunk unless every one of its old lines is in the file. The
system's patch tries harder. When the lines are not all there, it drops the
first and last lines of context and looks again, then two of each, its
**fuzz**; a hunk that still does not fit goes to a `.rej` file, and the hunks
that did fit are applied. Here is a copy of the book where someone else changed
line 701, the line the second hunk changes:

<!-- verify: session needs="diff patch" -->
```
$ sed '701s/Yes/Yes, sir/' data/book.txt > clash.txt
$ cp clash.txt mine.txt; bin/patch mine.txt book.diff; echo "exit $?"
patching file mine.txt
patch: mine.txt: hunk #2 (line 10 of the patch) does not apply: its lines are not in the file
patch: mine.txt: 1 of 3 hunks did not apply: the file is not changed
exit 1
$ cp clash.txt sys.txt; patch sys.txt book.diff; echo "exit $?"
patching file sys.txt
exit 0
$ diff clash.txt sys.txt | grep -A 3 '^705c'
705c704
< "Yes."
---
> "No."
```

Ours says which hunk failed and changes nothing. The system's patch, with fuzz,
found a `"Yes."` four lines further on with the same blank lines around it, and
changed that one, Watson's answer to Holmes's next instruction, with an exit
status of 0 and, without `-v`, no word about it. Fuzz finds the right place when the
nearby lines were only slightly edited, and a wrong one when the text repeats
itself. When a patch does not quite fit, would you rather have it refused, or
applied as well as it can be and checked by you?

## Break it

Look only at the stated line. In `build/at/dsa/06.04/tools/patch/patch.c`, in
`find()`, change

```
    for (long d = 0; want + d <= hi || want - d >= lo; d++) {
```

to

<!-- verify: patch file=tools/patch/patch.c
-    for (long d = 0; want + d <= hi || want - d >= lo; d++) {
@block
-->
```
    for (long d = 0; d < 1; d++) {
```

and build and patch the moved contents and the other copy of the book again:

<!-- verify: session -->
```
$ make -s
$ (echo "A note at the top."; echo; cat old.txt) > moved.txt
$ bin/patch moved.txt change.diff
patching file moved.txt
patch: moved.txt: hunk #1 (line 3 of the patch) does not apply: its lines are not in the file
patch: moved.txt: 1 of 1 hunk did not apply: the file is not changed
$ (printf 'A note.\n\n'; sed 3000,3009d data/book.txt) > theirs.txt
$ DS_STATS=1 bin/patch theirs.txt book.diff 2>&1 | grep -v array
patching file theirs.txt
patch: theirs.txt: hunk #1 (line 3 of the patch) does not apply: its lines are not in the file
patch: theirs.txt: hunk #2 (line 10 of the patch) does not apply: its lines are not in the file
patch: theirs.txt: hunk #3 (line 19 of the patch) does not apply: its lines are not in the file
patch: theirs.txt: 3 of 3 hunks did not apply: the file is not changed
stats: patch: files 1, hunks 3, failed 3, places tried 3, lines compared 3
```

One place tried for each hunk and one line compared at each, the first, which
differs. On the file the diff was made from, this patch still works, and that
is all it can do: two lines put on top of a file are enough to stop every hunk.
The search is what lets a diff travel to a copy that has moved on. Put the line
back.

## Go deeper

- `man patch` on your machine, the section "Patch Application" (on the Mac's
  patch): the first guess, the stated line plus the offset of the previous
  hunk, the scan forwards and backwards, fuzz, and reject files.
- [GNU diffutils manual, Detailed Description of Unified Format](https://www.gnu.org/software/diffutils/manual/html_node/Detailed-Unified.html) -
  what a hunk's header and lines promise, which is all patch has to go on.
- [James Coglan, The Myers diff algorithm: part 1](https://blog.jcoglan.com/2017/02/12/the-myers-diff-algorithm-part-1/) -
  why, of all the shortest scripts, a diff should keep changes together and
  line them up with the structure of the text: a hunk that does is easier to
  place in a copy that has changed.
