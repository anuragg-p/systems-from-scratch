# 06.01 The longest common subsequence, as a table

diff's job is to say which lines changed between two versions of a file. This
lesson finds the lines the two versions have in common, as many as can be kept
in order, by filling in a table of smaller answers, the same method 05.03 used
for the distance between two words. The table gives the right answer quickly,
and on files of a few megabytes it needs gigabytes of memory.

## The idea

![The table for a = ABCABBA and b = CBABAC, filled a row at a time from the bottom: each cell is the length of the longest common subsequence of a from line i on and b from line j on.](figures/06.01-table.svg)

Take the six lines of the book's contents, I to VI, as `old.txt`, and a
`new.txt` that drops II, has "Murder" for "Mystery" in IV, and adds VII. The
system's `cmp` compares the two byte by byte and stops at the first difference,
in line 2. Comparing line 1 with line 1, line 2 with line 2 and so on does no
better: once II is gone, every line after it sits one place higher, and five of
the six lines look changed. What really changed is two lines out and two in.

The useful question is the other way round: which lines stay. Keep as many
lines as both files have, in the same order, and every other line of the old
file was deleted and every other line of the new one inserted. The kept lines
are a **longest common subsequence** (LCS); a subsequence is what is left of a
sequence after taking some of its items out, the rest kept in order. Here it is
I, III, V and VI: four lines, so 6 - 4 = 2 lines deleted and 2 inserted, and no
script does it with fewer.

Trying every subsequence of the old file does not finish: n lines have 2^n
subsequences, and for 60 lines that is more than a billion billion. A table
does it instead, from smaller questions of the same kind. Let L[i][j] be the
length of the LCS of what is left of a from line i on and of b from line j on.
When nothing is left of either, it is 0. Otherwise look at the first line left
of each:

- equal: keep both, and L[i][j] = L[i+1][j+1] + 1;
- not equal: at most one of them can be kept, so drop one or the other,
  whichever leaves more: L[i][j] = max(L[i+1][j], L[i][j+1]).

Every cell needs only cells below it and to its right, so the table is filled
from the bottom right corner up, row after row, and L[0][0], the whole of a
against the whole of b, comes last. The figure fills it for the pair from
Myers' paper, a = A B C A B B A and b = C B A B A C, one letter to a line. Row
7 and column 6 are the empty ends, all 0; each row above is worked out from the
row below it; and L[0][0] is 4.

### `diff_text` and `diff_number`

`diff_text()` splits a file's bytes into lines that point into those bytes and
keep their newline, so a last line without one is a different line from the
same text with one. `diff_number()` gives every line a number through module
01's hash table: a line seen before, in either file, gets the number it got
then. From then on, comparing two lines is comparing two numbers, however long
the lines are.

### `fill` and `diff_table`

The table is one block of (n+1) x (m+1) cells of 32 bits, row i starting at
`i * (m+1)`. `fill()` sets the bottom row and the right column to 0, then fills
the rows from the bottom up, each from right to left, by the two rules above.
`diff_table()` numbers the lines, gets the block from `new_table()`, which
refuses one bigger than a set limit, fills it, and reads the lines in common
off the first cell.

### `tools/diff/diff.c`

The command reads both files, picks the algorithm (`--algo=table`, the only one
so far) and, as the system's diff does, says "Files a and b differ" with exit
status 1, or nothing with 0. `tools/diff/gen.py` makes pairs of files for the
growth harness, such as `versions`: a stretch of the book and a copy with 16
small edits.

## How it works

### Why the two rules are right

When a[i] and b[j] are equal, some longest common subsequence of what is left
keeps the two of them as a pair: take any longest one, and its first pair can be
moved to a[i] and b[j], which are equal and come before every other line left,
without making it shorter. When they differ, no common subsequence can pair
them, so a[i] or b[j] goes unused, and the best is the better of the two
smaller questions. Each cell is right when the cells it reads are right, and the
empty ends are right by definition, so the whole table is.

That is **dynamic programming**: a big question answered from a table of
smaller questions of the same kind, each answered once, in an order where every
answer a cell needs is already there. A plain recursive function with the same
two rules asks the same smaller questions over and over, which is why it does
not finish either; the table asks each of its (n+1)(m+1) questions once.

### The invariant: below and to the right are filled

`fill()` keeps one **invariant**: when it fills a cell, the cell below it, the
cell to its right and the cell to its lower right already hold their answers.
The two loops keep it:

```
    for (size_t i = n; i-- > 0;) {
        L[i * w + m] = 0;
        for (size_t j = m; j-- > 0;) {
```

The rows go from the bottom up, so the row below is complete; each row goes
from right to left, starting from the 0 of the right column, so the cell to the
right was filled one step earlier. Fill a row from left to right and each cell
would read its neighbour before it holds anything.

### Numbers, not lines

Each cell compares two lines, and the book's table has 142 million cells. The
comparison is of the numbers `diff_number()` gave the lines:

```
            if (A[i].id == B[j].id) {
```

so the bytes of each line are read once, when it is numbered, and a cell costs
under a nanosecond here: the book's 142 million cells took a tenth of a second,
reading and numbering included.

### Where it stops: memory

The time stays small; the memory does not. Every pair of lines has its 4-byte
cell, however few of the pairs matter. The limit that stopped the 1.7 MB pair
is the code's own, `DIFF_MAX_BYTES` in `lib/diff.h`, 4 GB, checked before
anything is allocated:

```
    if (mb > (double)(DIFF_MAX_BYTES >> 20))
```

so that a large file gets an ordinary error instead of a machine that runs out
of memory. It marks where the table stops being worth it here, not a law: more
memory moves the wall, and twice the lines still need four times as much.

## Decide the boundary

At this lesson the answer is one number, L[0][0], and each row needs only the
row below it. Two rows, 2 x (m+1) cells, would give the same count in the same
time, and that is how 05.03's edit distance keeps its table. This table keeps
every row because the next lesson walks back through it to find which lines are
kept. The lines can be found in little memory too: Hirschberg's method, which
Myers' paper cites, does it in linear space by divide and conquer, finding where
the answer crosses the middle of the table and then solving each half the same
way, at the price of computing parts of the table more than once. Which costs
you more: work done twice, or memory that grows with the product of the files'
lengths?

## Break it

Forget the +1 for a pair of equal lines. In `build/at/dsa/06.01/lib/diff.c`, in
`fill()`, change

```
                L[i * w + j] = L[(i + 1) * w + j + 1] + 1;
```

to

<!-- verify: patch file=lib/diff.c
-                L[i * w + j] = L[(i + 1) * w + j + 1] + 1;
@block
-->
```
                L[i * w + j] = L[(i + 1) * w + j + 1];
```

and build and compare again:

<!-- verify: session -->
```
$ make -s
$ bin/diff old.txt old.txt
Files old.txt and old.txt differ
$ DS_STATS=1 bin/diff old.txt new.txt 2>&1 | grep 'diff:'
stats: diff: lines 6 and 6, common 0, deleted 6, inserted 6
$ DS_TRACE=1 bin/diff a.txt b.txt 2>&1 | grep -e 'row 0' -e 'lcs: length'
trace: lcs: row 0: 0 0 0= 0 0= 0 0
trace: lcs: length 0
```

A file now differs from itself. The table still sees where lines are equal (the
`=` marks are where they were) but never counts one: the rule for equal lines is
the only place anything is counted, so every cell is 0 and every line is
deleted and inserted again. Put the +1 back.

  Introduction to Algorithms, 4th edition, chapter 14, Dynamic Programming:
  section 14.4, Longest common subsequence, builds the same table from the
  front of the two sequences instead of the back, and section 14.3 names the
  two properties this lesson relied on, optimal substructure and overlapping
  subproblems.
- [Jeff Erickson, Algorithms, chapter 3, Dynamic Programming](https://jeffe.cs.illinois.edu/teaching/algorithms/book/03-dynprog.pdf) -
  "The Pattern: Smart Recursion" turns a recursion into a table filled in a
  chosen order, and "Edit Distance" fills one for two words, where any path of
  arrows from one corner to the other is an optimal edit sequence; a footnote
  there says the longest common subsequence is edit distance with insertions
  and deletions only.
