# 06.03 Myers: the shortest path of edits

The table of 06.01 refuses a pair of 1.7 MB files, because it would need 4.9 GB.
This lesson replaces it with Eugene Myers' search, which finds a script just as
short by spreading out from the start one edit at a time and keeping only the
furthest point each number of edits can reach. On two versions of a file it
looks at a few thousand points where the table filled hundreds of millions.

## Where this fits

![Where 06.03 fits](figures/06.03-map.svg)

Myers is the third box of module 06's strip, on the diff rail: it is the search
git's diff will use in module 10. It takes the table's place as diff's default
and makes the same kind of edit script, so the hunk printer of 06.02 prints its
result unchanged. It keeps the points it reaches in module 01's growable array
and still numbers the lines with module 01's hash table. After this lesson diff
compares files of any length quickly, as long as they differ in a few places.

## The idea

![Myers' search on the edit graph of ABCABBA and CBABAC: in each round d, the furthest point d edits can reach on each diagonal, until one of them is the far corner.](figures/06.03-search.svg)

Two versions of a long file differ in a few places. The table fills a cell for
every pair of lines, but the path the walk takes through it stays close to the
diagonal from corner to corner, and almost every cell is never on it. A search
that starts at the corner and looks only as far from that diagonal as the
changes take it would not need the rest.

Think of the table's corners as points of a grid, the **edit graph**: point (x,
y) means x lines of a and y lines of b are dealt with, from (0, 0) to (n, m).
A step right deletes line x of a, a step down inserts line y of b, and where
line x of a equals line y of b a diagonal step keeps the line, for nothing. (The
grid is drawn as Myers draws it, with a's lines across the top, so the step
that deleted in 06.02's walk, down, is a step right here.) An edit script is a
path from (0, 0) to (n, m), and a shortest script is a path with the fewest
steps that are not diagonal. Call that number D.

Myers searches by the number of edits, d = 0, 1, 2, and so on. Name each
diagonal line of the grid by **k** = x - y. Every edit moves a path one diagonal
over, so after d edits it ends on one of k = -d, -d+2, ..., d. On each of those
the search keeps a single point, the furthest along that d edits can reach.
Round d finds each one from round d-1: one more edit, down from the point on
k+1 or right from the point on k-1, whichever lands further on, then as many
free diagonal steps as the lines allow. That run of equal lines is a **snake**.
The first round in which a point reaches (n, m) is D. The figure runs the pair
from Myers' paper: round 0 cannot move, since A is not C; round 2 already
reaches (2, 4) on diagonal -2; round 5 reaches (7, 6). Five edits, as the table
found.

Round d works out d+1 points, and the snakes add a step for each kept line, so
the search looks at roughly (n + m) x D points, not n x m. When the files share
almost everything, D is small and the search is close to reading the files
once.

### `search` and `came_down`

The rounds. For each diagonal of round d, `came_down()` says whether the edit
came from k+1 (down) or k-1 (right), by the rule above; the point after the edit
is followed down its snake, counted, and kept with `keep()`, which refuses to
keep more than the table would have been allowed. The search ends at the round
that reaches (n, m) and returns that round's number.

### `backtrack`

Every round's points are kept, round d from index d(d+1)/2 of one array, so the
path can be found again: from (n, m), each round's point came from round d-1's
point on k+1 or k-1, by the same rule the search used, after one edit and then
its snake. The walk back pushes the snake's kept lines and the edit as it goes,
last first, and turns the script round at the end.

`diff_myers()` puts the two together and counts the script's lines, and diff
gains `--algo=myers`, its default from now on; `--algo=table` stays.

## How it works

### Why keeping one point per diagonal is safe

The search throws away every way of reaching a diagonal but the furthest. That
is safe because a point further along a diagonal is never worse than one
nearer. Take two snakes on the same diagonal, one starting further on: if the
nearer one gets as far as where the other starts, from there they follow the
same lines and stop at the same place; if it stops before, the other is ahead
anyway. So an edit from a further point, followed by its snake, ends at least as
far as the same edit from a nearer one. That is Myers' Lemma 2: a furthest
d-edit point is one edit and a snake from a furthest (d-1)-edit point. Taking the
whole snake is safe for the same reason; a kept line costs nothing.

### The invariant, and the tie

After round d, the kept points hold, for every diagonal k from -d to d, the
furthest x that d edits can reach on it. `came_down()` keeps it, comparing the
two neighbours of round d-1:

```
    return k == -d || (k != d && at(v, d - 1, k - 1) < at(v, d - 1, k + 1));
```

On the edge diagonals there is only one neighbour. On a tie it goes right, a
deletion, so a change deletes before it inserts, as 06.02's walk does. The two
may still pick different shortest scripts: on the figure's pair this search
keeps C A B A, the table's walk C B B A.

### The memory: D squared, not n times m

Round d's points start at d(d+1)/2 in one array of 32-bit numbers:

```
    return ((const int32_t *)v->data)[d * (d + 1) / 2 + (k + d) / 2];
```

so D rounds keep (D+1)(D+2)/2 numbers at most: 19 on the figure's pair, 4 bytes
each, the 76 bytes above. That grows with the size of the change, not the size
of the files. The diagonals are not cut off at the edges of the grid, so some
kept points lie past them: (3,7) in round 4 is past the last line of b. The
snake loop never follows a step off the grid, and no such point reaches the
corner. Myers' paper says the same of its own figure of this search.

## Decide the boundary

Myers is quick when D is small, and D is not always small. On two files that
share only their blank lines:

<!-- verify: session
line 6 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
line 8 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
-->
```
$ python3 data/gen.py unrelated 8000 -o u8k
$ DS_STATS=1 bin/diff -q --algo=table u8k.1 u8k.2 2>&1 | grep -e diff: -e lcs
stats: diff: lines 8000 and 8000, common 1746, deleted 6254, inserted 6254, hunks 0
stats: lcs: cells 64016001, bytes 256064004
$ time bin/diff -q --algo=table u8k.1 u8k.2 > /dev/null
  0.03s user 0.01s system 90% cpu 0.050 total
$ time bin/diff -q u8k.1 u8k.2 > /dev/null
  0.23s user 0.06s system 97% cpu 0.290 total
$ DS_STATS=1 bin/diff -q u8k.1 u8k.2 2>&1 | grep myers
stats: myers: d 12508, diagonals 78237541, cells 78239287, bytes 312950164
```

D is 12508, and the search looks at 78 million points to the table's 64
million, each dearer (a jump to another round's point, a push onto the array),
and keeps 313 MB of them, more than the whole table. When D grows with the
files, (n + m) x D is n squared again, and so is D squared. The system's diff
meets the same case another way: unless asked for the fewest changes, it takes
shortcuts and may print a longer script.

<!-- verify: session needs=diff -->
```
$ python3 data/gen.py unrelated 2000 -o u2k
$ diff u2k.1 u2k.2 | grep -c '^<'
1608
$ diff -d u2k.1 u2k.2 | grep -c '^<'
1601
$ DS_STATS=1 bin/diff -q u2k.1 u2k.2 2>&1 | grep diff:
stats: diff: lines 2000 and 2000, common 399, deleted 1601, inserted 1601, hunks 0
```

1608 lines deleted where 1601 will do. This diff is always exact, and keeps
every round. Myers' paper gives a refinement that keeps the time and needs
memory only in proportion to n + m, by searching from both ends at once and
splitting the problem where they meet; it does about twice the work. Do the
files you compare differ in a few places, or all over?
