# 06.02 From the table to hunks: unified output

At 06.01 diff can only say that two files differ, and by how many lines. This
lesson reads which lines out of the table, by a walk from its first cell to its
last, and prints them the way `diff -u` does: each change with a few unchanged
lines around it, in hunks the system's patch can apply.

## Where this fits

![Where 06.02 fits](figures/06.02-map.svg)

Hunks are the second box of module 06's strip, on the same diff rail as the
table, which git reuses in module 10 to print the changes between two commits.
The walk stands on the whole table that 06.01 fills, and the printer on the
edit script the walk makes. After this lesson diff prints what changed, line
for line the same as the system's `diff -u` on the files tried here, and the
system's patch turns the old file into the new one with it.

## The idea

![The walk from the first cell of the table for ABCABBA and CBABAC to its far corner, then the edit script it reads off, printed as one hunk with 3 lines of context and as four with none.](figures/06.02-walk.svg)

The table knows how many lines are kept, not which. Its cells say more than
the number in the corner, though: L[i][j] is how much is still in common from
line i of a and line j of b on. Start at L[0][0] and walk. Where the two lines
are equal, keep the line and step to the lower right. Where they are not, step
to whichever neighbour, below or to the right, holds the larger number: down
deletes a's line, right inserts b's line. On a tie, step down, so a change
lists its old lines before its new ones, as diff does. When a is used up, what
is left of b is inserted; when b is, what is left of a is deleted. The steps,
in order, are the **edit script**: every line of both files once, each marked
keep (' '), delete ('-') or insert ('+'). The figure walks the table of 06.01's
pair, a = ABCABBA and b = CBABAC: two deletions, a kept C, and so on to the
corner, nine steps for 7 + 6 lines with 4 in common.

The script is the answer, but not one anybody wants to read. For the book
against a copy with three small edits it is 11923 lines long, every one of them
printed to show eight that changed. The **unified format** prints only the
changes, each with up to three unchanged lines before and after it, its
**context**, so a reader, and patch, can see where it goes. A change with its
context is a **hunk**, headed by where it is in each file: `@@ -698,7 +697,7 @@`
is 7 lines of the old file from line 698, and 7 of the new one from line 697.
Two changes with six or fewer unchanged lines between them would share context
lines, so they go in one hunk.

### `walk`

The walk above, from (0, 0) to (n, m), one edit per step pushed onto the
script's array, each with where it stands in both files.

### `next_hunk`

Finds the next change at or after a given edit, backs up to `context` edits
before it, and runs forward over every change that is no more than 2 x
`context` unchanged lines from the last, then `context` edits past that.

### `print_hunk`

Counts the hunk's lines in each file for its header, then prints its lines: a
kept line with ' ', and in each run of changes the deleted lines with '-' first
and then the inserted ones with '+'.

### `print_header`

The two lines before the hunks, `---` with the old file's name and the time it
last changed, `+++` with the new file's, in the format GNU diff prints.
`diff_unified()` then prints hunk after hunk, and `-u`, `-U N` (N lines of
context) and `-q` (only "Files a and b differ") are new options of diff.

## How it works

### The invariant of the walk

At every step, the lines kept so far plus L at the cell where the walk stands
is L[0][0]. It holds at the start, and each step keeps it: where the lines are
equal the cell is L[i+1][j+1] + 1, so keeping the line and stepping
diagonally loses nothing; where they are not, the cell is the larger of its two
neighbours, and the walk steps to that one. So when it reaches the corner,
where L is 0, it has kept L[0][0] lines, a longest common subsequence. The
choice is this line of `walk()`:

```
        } else if (j == m || (i < n && L[(i + 1) * w + j] >= L[i * w + j + 1])) {
```

`>=` and not `>`: on a tie both neighbours keep the invariant, and down puts the
deletion first.

### Joining hunks

`next_hunk()` stops a hunk when the next change is further away than the
context of both could reach:

```
        if (next == n || next - end > 2 * context)
```

With 3 lines of context, two changes 6 unchanged lines apart print those 6
lines once, as the end of the first change's context and the start of the
second's; 7 apart, and the hunks are separate, with nothing in common.

### The line numbers

A hunk's header counts lines from 1. A count of 1 is left out (`-2` is line 2
only), and a count of 0, a hunk with no lines in that file, names the line
before the place, so `+1,0` is "nothing, just after line 1" and `-0,0` the
start of an empty file. `print_range()` gets the place as a script position,
counted from 0, which is the number of the line before it:

```
    if (count == 0)
        fprintf(out, "%zu,0", start);
    else if (count == 1)
        fprintf(out, "%zu", start + 1);
```

This corner of the format is easy to get wrong. The Mac's own diff, in its
fast mode, gets it wrong for a line put before the first line of a file:

<!-- verify: session needs=diff -->
```
$ printf 'b\n' > x.txt; printf 'a\nb\n' > y.txt
$ bin/diff -U0 x.txt y.txt | tail -n +3
@@ -0,0 +1 @@
+a
$ diff -U0 x.txt y.txt | tail -n +3
@@ -1,0 +1 @@
+a
$ diff -d -U0 x.txt y.txt | tail -n +3
@@ -0,0 +1 @@
+a
```

`-1,0` says "after line 1", and the Mac's patch, given that, puts the `a` after
the `b`. With `-d`, which asks it for the fewest changes, the system's diff
writes `-0,0`, as ours does.

## Decide the boundary

A pair of files can have more than one shortest script. On the figure's pair:

<!-- verify: session needs=diff -->
```
$ printf '%s\n' A B C A B B A > a.txt; printf '%s\n' C B A B A C > b.txt
$ bin/diff a.txt b.txt | tail -n +3 | paste -s -d ' ' -
@@ -1,7 +1,6 @@ -A -B  C -A  B +A  B  A +C
$ diff -u a.txt b.txt | tail -n +3 | paste -s -d ' ' -
@@ -1,7 +1,6 @@ -A -B  C +B  A  B -B  A +C
```

Both delete three lines and insert two; ours keeps C B B A, the system's C A B
A. This diff takes whatever the walk's tie rule gives, and spends nothing on
choosing. Others spend work to choose the script a person reads most easily,
for example one that keeps a block of code's closing brace with the block it
closes rather than with the block before. Both are correct for patch. When the
reader of your diffs is a person, how much work is the most readable of the
shortest scripts worth?

## Break it

Join hunks too seldom. In `build/at/dsa/06.02/lib/diff.c`, in `next_hunk()`,
change

```
        if (next == n || next - end > 2 * context)
```

to

<!-- verify: patch file=lib/diff.c
-        if (next == n || next - end > 2 * context)
@block
-->
```
        if (next == n || next - end > context)
```

and build, then compare twenty numbered lines with a copy where lines 5 and 10
are changed, four unchanged lines apart:

<!-- verify: session -->
```
$ make -s
$ for i in $(seq 20); do echo "line $i"; done > lines.txt
$ sed -e 's/^line 5$/LINE 5/' -e 's/^line 10$/LINE 10/' lines.txt > lines2.txt
$ bin/diff lines.txt lines2.txt | tail -n +3
@@ -2,7 +2,7 @@
 line 2
 line 3
 line 4
-line 5
+LINE 5
 line 6
 line 7
 line 8
@@ -7,7 +7,7 @@
 line 7
 line 8
 line 9
-line 10
+LINE 10
 line 11
 line 12
 line 13
```

Two hunks, and lines 7 and 8 are in both: the first hunk's context after line 5
and the second's before line 10 overlap. With the rule as it was, the system's
diff and ours print one hunk, `@@ -2,12 +2,12 @@`, with each line once. Nothing
here is wrong enough for the system's patch to refuse, since each hunk's lines
are really in the file; the diff is only longer, and says two changes are
unrelated when they share their context. Put the rule back.
