# 07.03 Topological order, and what is out of date

The walk makes a target once for every path to it, makes everything every
time, and can leave a build out of date behind it. This lesson builds in
the order the search of 07.02 finished the nodes, which puts every target
after everything it needs, so one pass makes each target once; and it makes
a target only when it is out of date, by comparing the files' modification
times. On the track, a second run has nothing to do, and after one file
changes, `bin/make -n` prints the same bytes as the system's make.

## Where this fits

![Where 07.03 fits](figures/07.03-map.svg)

Topological order is the third box in make's strip. It is the order the
depth-first search of 07.02 already leaves behind, so there is nothing new
to search; what is new is the pass over it, and the question asked at each
target. Below it, the file system says when each file last changed. After
this lesson our make does what the system's make does for this track:
after an edit it rebuilds what the edit touched and nothing else, and it
can build the track in place of the system's make. The walk stays, as
`--algo=recurse`, to measure against.

## The idea

Run the walk on diamond.mk in an empty directory and it touches common.h,
liba, common.h again, libb and app. liba was made from a common.h that has
since been made again: by the rule make itself was given, liba is now out
of date, the moment the build that made it ends. On the track, the same
thing happens to the library: the walk archives it once for each tool, and
each tool is linked against the archive of its own path, so when it ends,
nine of the ten tools are older than the library on the disk.

Both fixes come from the search. A **topological order** of a graph lists
every node after all the nodes it needs. The search has one: a node is
done only after everything it needs is done, so the order it finished the
nodes in, kept in `order`, is a topological order. Go along it once, and
each target comes up once, after everything it needs has had its turn.

At each target, make asks whether it is **out of date**: whether its file
is missing, or something it needs was made in this run, or is a file newer
than it. Newer means a later **modification time**, the time the file
system records each time a file is written. A target that is not out of
date is **up to date**, and its recipe does not run. A phony target, one
`.PHONY` names, is never a file, and always counts as out of date.

![The build in order on the cut-down build after touch table.c: each target checked once, in the search's finishing order, and the list of what is out of date growing.](figures/07.03-order.svg)

The figure is the cut-down build of 07.01, built once, then with table.c
touched. Step through it: the sources are files with no rule, which must
be there; freq.o and util.o are up to date; table.o is older than table.c,
so it is made; then the library and both tools are out of date because
something they need was made in this run, and `all` because it is phony.
Four recipes run, and sort.o is never touched.

### `out_of_date`

The question asked at each target, with the answer's reason for the trace.
A phony target is out of date; a node with no rule must be a file that
exists, and is never made; a missing file is out of date; otherwise each
thing it needs is looked at, in order, and the first that was made in this
run, or is newer, decides it. `newer()` compares two times to the
nanosecond.

### `build_in_order`

The pass: along `order`, skipping each target that is up to date, running
the recipe of each one that is not, and then calling `made()`, which marks
the target as made in this run and forgets its time, so that the next
target to ask reads the new one. `main()` gains `--order`, which prints the
order and stops, and `--algo=recurse` and `--algo=topo`, the default.

## How it works

### Why the finishing order is a build order

When the search finishes a node, every node it needs is done already. Each
of its edges was looked at before it finished: a new node was entered then,
and since it was deeper on the path, it finished first; a done node had
finished before; and an open one would have been a cycle, which stops
make. So in `order`, every node comes after everything it needs. The
textbooks draw an edge from what comes first to what comes after, and so
take the finishing order backwards; our edges point from a target to what
it needs, so the finishing order is the build order as it stands.

### Made in this run

A target is out of date when something it needs was made in this run, even
if that thing's file is no older than it was:

```
        if (u->remade) {
            trace("check %s: %s was made", node->name, name(m));
            return 1;
        }
        if (file_time(m) && newer(u->mtime, t->mtime)) {
```

Without the first test, `-n` would be wrong: it runs nothing, so after
`touch lib/heap.c` the file heap.o is no newer than before, and times alone
would call the library up to date. Break it shows that. A phony
prerequisite has no file and no time at all, and is made every time, so
what needs it must be made every time too. The **invariant** of the pass:
when it reaches a target, everything the target needs has been decided,
made or found up to date, and `made()` has recorded which.

## Decide the boundary

"Out of date" here is a comparison of two clock times. Our make reads them
to the nanosecond. GNU make 3.81, the system's make on a Mac, reads whole
seconds, so two files written in the same second look the same age to it.
Set liba half a second older than common.h in the walk's directory:

<!-- verify: session -->
```
$ cd dia
$ touch -d 2025-01-01T10:00:00.2 liba
$ touch -d 2025-01-01T10:00:00.7 common.h
$ ../bin/make -n -f ../tools/make/examples/diamond.mk
touch liba
touch app
$ make -n -f ../tools/make/examples/diamond.mk
make: `app' is up to date.
$ cd ..
```

(GNU make 4, the usual one on Linux, reads the fractions too, and agrees
with ours.) A one-second grain misses an edit made within a second of the
last build, and misses the walk's leftover above, made in a few
milliseconds. Any clock misses a file
put back with an old time, as `cp -p` or unpacking an archive does, and is
fooled by two machines whose clocks disagree. Another make could remember a
hash of each file's contents from the last build and rebuild when that
changes, paying a read of every input on every run, and a place to keep the
hashes. Which costs you more: reading every file each time, or now and then
a build that is quietly out of date?

## Break it

Forget "made in this run". In `build/at/dsa/07.03/tools/make/make.c`, in
`out_of_date()`, delete these four lines:

            trace("check %s: %s was made", node->name, name(m));

then build with the system's make, change heap.c again, and ask:

<!-- verify: session -->
```
$ make -s
$ touch lib/heap.c
$ bin/make -n | cut -c 1-60
mkdir -p build/lib
cc -std=c11 -O2 -g -Wall -Wextra -Wno-unused-parameter -Wno-
$ DS_STATS=1 bin/make -s 2> stats.txt; grep 'stats: make' stats.txt
stats: make: recipes run 12, commands 24, files checked 94, most at once 1
```

`-n` now lists only the compile of heap.o, and none of the eleven recipes a
real build runs: nothing really changed, so the library's time says it is
up to date. The real build still runs all 12, because by then heap.o's time
has really changed. A make whose `-n` lies is a make nobody can preview a
build with. Put the lines back and `make -s` again.

## Go deeper

- [Algorithms, 4th edition, 4.2 Directed Graphs](https://algs4.cs.princeton.edu/42digraph/) (Sedgewick and Wayne) -
  "Cycles and DAGs": topological sort by depth-first search
  (Topological.java), the propositions that reverse postorder in a DAG is
  a topological order and that it takes time proportional to V + E.
- [Jeff Erickson, Algorithms, chapter 6, Depth-First Search](https://jeffe.cs.illinois.edu/teaching/algorithms/book/06-dfs.pdf) -
  "Topological Sort": why the reversal of any postordering of a dag is a
  topological ordering, the argument of How it works with the edges drawn
  the other way.
- [MIT 6.006, Spring 2020, Lecture 10: Depth-First Search](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/resources/mit6_006s20_lec10/) (Demaine, Ku, Solomon) -
  the notes' "Topological Sort": a finishing order, and the claim, with its
  proof, that its reverse is a topological order of a DAG.
- [Stuart Feldman, Make - A Program for Maintaining Computer Programs](https://wolfram.schneider.org/bsd/7thEdManVol2/make/make.pdf) -
  "Basic Features": make depends on "the date and time that a file was last
  modified", and what it rebuilds after defs, or only y.c, has changed.
