# 07.04 Building in parallel: a queue of ready work

make now builds each target once, in order, one recipe at a time. Most of
the track's recipes do not need each other, though: its 33 objects could
all be compiled at once. This lesson keeps, for each target, a count of
the things it needs that are not finished yet, and a queue of the targets
whose count is 0. `bin/make -j N` runs up to N recipes from the queue at
once, and on the track a build from nothing goes from 2.6 seconds to 0.45.

## Where this fits

![Where 07.04 fits](figures/07.04-map.svg)

The ready queue is the last box in make's strip, and a new structure for
the library, `lib/readyq.c`: a growable array of module 01 and the index of
its front. It works on the targets the search of 07.02 reached, and on the
graph's edges read backwards, from a node to the targets that need it,
which the graph now records too. After this lesson make runs independent
recipes side by side, as many at a time as it is told, and the module's
make is complete: it builds this track in place of the system's make,
nearly as fast.

## The idea

Building in order is safe because each target comes after everything it
needs. But the order is one line, and a line runs one recipe at a time.
Look at what the order really demands instead: a target may start once
everything it needs is finished, and not before. At the start of a build
from nothing, that is every object; once the library's objects are all
finished, it is the library; once the library is finished, every tool.

So give each target a count: how many of the things it needs are not
finished. A target whose count is 0 is **ready**, and goes on a
**queue**, a list that is taken from at the front and added to at the
back, first in, first out. make takes ready targets off the front and
starts their recipes, up to N at a time. When a recipe ends, its target is
**finished**, and every target that needs it has one fewer thing to wait
for; any count that falls to 0 puts that target on the queue. A target
that comes off the queue up to date has nothing to run, and is finished at
once. This is **Kahn's algorithm** for a topological order, with a number
of recipes running at once instead of one name printed at a time.

![bin/make -j 2 on the cut-down build, one frame per turn of the queue: each target's count of unfinished prerequisites, the ready queue, and the two recipes running.](figures/07.04-queue.svg)

Step through it: the cut-down build of 07.01 from nothing, with `-j 2`. The
five sources need nothing, so they are ready first, and come off the queue
up to date; that brings every object's count to 0. Two objects run at a
time, and as each one finishes, the counts above it fall: the library
waits for both of its objects, both tools wait for the library, and so the
two tools become ready together, in the turn the library finishes.

### `readyq_init`, `readyq_push` and `readyq_pop`

The queue, in `lib/readyq.c`: target numbers in an array, a push at the
end and a pop at `head`, an index that moves along as items come off.
Nothing is ever moved, so both cost the same however long the queue is.

### `finished`

What happens when a target is finished: each target that needs it, if the
search reached it, waits for one fewer; at 0 it goes on the queue. For
that the graph now keeps each edge twice: `graph_edge()` also records, in
the node needed, which node needs it.

### `build_queue`

The loop. Every target the search reached starts with a count of the
things it needs, and those at 0 are queued, in the search's order. Then:
while fewer than `jobs` recipes run and the queue is not empty, take the
front target, finish it at once if it is up to date, or start its recipe;
then wait for any running command to end. A recipe of several lines is a
`Job`, which starts its next line when the last one ends, and its target
is finished when there is none left. `main()` gains `-j N`, which picks
this way of building, also named `--algo=queue`.

wall-clock time: about seven compilers at work at once. 96 targets went
through the queue, each once.

## How it works

### Never too early

The **invariant**: a target is on the queue, or running, only when its
count is 0, which is when everything it needs, that this build wants, is
finished. The count starts at the number of things it needs, and falls by
one only when one of them is finished, here:

```
        if (--dep->waiting == 0) {
            trace("ready %s", dep->name);
            readyq_push(q, d);
        }
```

A target is finished only after the last line of its recipe has ended, not
when it starts, so nothing reads a half-written file. Each count falls to
0 once, so each target is queued once: 96 pushes for the 96 targets `all`
needs. That is also why the queue never reuses the room before its front:
it can never hold more items than there are targets.

### Only what the goals need

`finished()` skips a target the search did not reach, such as `clean`,
which no goal needs. Without that check its count would fall too, and a
target nobody asked for would be built.

### The queue's order

Kahn's algorithm gives a topological order too, but not the search's:
everything that is ready now comes off the queue before anything it makes
ready, so the order goes up the graph in rounds, all the objects, then the
library, then all the tools. With `-j 1`, one recipe at a time, the
commands come out in that order, not the order of a build without `-j`:

<!-- verify: session -->
```
$ rm -rf build
$ DS_TRACE=1 bin/make -n > /dev/null 2> serial.txt
$ DS_TRACE=1 bin/make -n -j 1 > /dev/null 2> queue.txt
$ grep 'run ' serial.txt | sed -n 23,26p
trace: run build/lib/edit.o
trace: run build/libds.a
trace: run bin/diff
trace: run build/edit/edit.o
$ grep 'start ' queue.txt | sed -n 23,26p
trace: start build/lib/edit.o
trace: start build/edit/edit.o
trace: start build/freq/freq.o
trace: start build/grep/grep.o
$ make -s
```

Both are right: in each, every target comes after everything it needs.
One more difference shows only with `-j`: a rule with two targets and one
recipe, `one.o two.o: defs.h`, runs its recipe once for each target, since
both are ready together and neither file exists yet; one at a time, the
second finds its file already made. GNU make 3.81 does the same.

## Decide the boundary

The queue is first in, first out: of the ready targets, the one that has
waited longest starts first, whatever its recipe costs. In a `-j 8` build
here, `build/edit/edit.o`, the slowest compile of the track at about 0.19
seconds, is the 24th recipe to start, finishes after the library is
archived, and its link is the last to finish. A make that knew how long
each recipe took, from an earlier build, could keep the ready targets in a
heap, module 02's, ordered by the longest chain of work still above each
one, and start that one first; it would have to keep those times, and
trust them. Is the time that would save worth a memory of every build?

## Break it

Queue a target as soon as any one of its prerequisites is finished, not
when all of them are. In `build/at/dsa/07.04/tools/make/make.c`, in
`finished()`, change

```
        if (--dep->waiting == 0) {
```

to

```
        if (--dep->waiting >= 0) {
```

and build and run again:

<!-- verify: session -->
```
$ make -s
$ bin/make -n -j 2 -f tools/make/examples/diamond.mk
touch common.h
touch liba
touch libb
touch app
touch app
$ rm -rf build
$ bin/make -s -j 8 2> errors.txt
$ grep '^make:' errors.txt
make: *** [bin/diff] Error 1
make: *** Waiting for unfinished jobs....
```

app is queued when liba finishes and again when libb does, so it is made
twice; with real recipes it would start before libb existed. On the track,
bin/diff is queued as soon as its own object is compiled, and its link
starts before the library exists: the compiler cannot find
`build/libds.a`, and the build stops, waiting for the recipes already
running. Put the line back and `make -s` again.
