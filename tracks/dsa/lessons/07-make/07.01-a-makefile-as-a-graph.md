# 07.01 A makefile as a graph

make's job is to build a project: everything after what it needs, each thing
once. This lesson reads a makefile into a graph, a node for each name and an
edge for each "needs", and builds it the obvious way, by recursion. The order
comes out right, but the recursion makes a thing once for every path to it:
on this track, 482 commands where the system's make runs 86.

## Where this fits

![Where 07.01 fits](figures/07.01-map.svg)

The graph is the first box in make's strip. It stands on module 01: the
nodes are kept in a growable array, each node's list of what it needs is
another, and the hash table finds a node by its name. Above it are two parts
of make that come whole with this lesson and are not taught: the reader,
which turns the lines of a makefile into rules and variables, and the
runner, which hands each line of a recipe to the shell. After this lesson
our make reads this track's own Makefile, every tool's part of it included,
and builds the track: in the right order, and far too often.

## The idea

A makefile says what each file needs and how to make it. The smallest one
in the project is `tools/make/examples/diamond.mk`:

<!-- verify: file path=tools/make/examples/diamond.mk -->
```
app: liba libb
	touch app
liba: common.h
	touch liba
libb: common.h
	touch libb
common.h:
	touch common.h
```

Each rule names a **target**, app; after the colon, its **prerequisites**,
the files it needs; and on the lines under it, each starting with a tab,
its **recipe**, the commands that make it. To build app, make must first
have liba and libb, and both of those need common.h.

That is a **graph**: each name is a **node**, and "app needs liba" is an
**edge** from app to liba. The edges have a direction, so it is a directed
graph. For each node make keeps the nodes it needs, in the order the
makefile names them: an **adjacency list**. A name can turn up in many
rules (in this track's build, 32 targets need `lib/ds.h`), and every
mention must find the same node. That is the hash table of 01.02, mapping
each name to its node's index in the array.

The obvious way to build the target make is asked for, its **goal**, is a
recursion, which this module calls the **walk**: build each thing the
target needs, the same way, then run its recipe. Nothing is made before
what it needs, so the order is right. But the walk remembers nothing. In
diamond.mk it comes to common.h twice, once below liba and once below libb,
and runs its recipe both times: a node is made once for every path to it
from the goal.

![A cut-down copy of the track's build beside its graph: both tools need the library, so the walk comes to the library and its two objects twice, and to ds.h six times.](figures/07.01-graph.svg)

The figure is a cut-down copy of this track's build, with short names: two
tools, freq and sort, each linked from its own object and the library,
which is archived from two objects. Both tools need the library, so the
walk makes the library and both of its objects twice: 10 recipes where 7
would do. The track itself has 10 tools on one library of 21 objects.

### `graph_init`, `graph_node` and `graph_edge`

The graph, in `lib/depgraph.c`. The nodes live in an array in the order
they were added, and a node is known by its index there. `graph_node()`
asks the table for the name first, and adds a node only when it is new,
with an empty list of needs, putting its index in the table.
`graph_edge()` adds one node to another's list, unless it is there already:
a makefile may name a prerequisite twice, or in two rules.

### `add_rule`

Where a rule of the makefile becomes part of the graph, in
`tools/make/read.c`. Each target is a node, marked as having a rule, and
needs each prerequisite, which is a node too. A prerequisite that no rule
names as a target, such as `lib/util.c`, is a node with no rule: a file
that must be there.

### `walk` and `make_node`

The recursion. `walk()` goes down each node a target needs, in order, and
then hands the target to `make_node()`, which runs its recipe, every time.
A node with no rule must be a file that exists, or make stops: "No rule to
make target". The walk counts how deep it is, for the two ways it can go
wrong, which How it works comes to.

### `print_graph`

`bin/make --graph` prints the graph and stops: each node and the nodes it
needs, in the order they were added, then the phony ones. The output is a
makefile with the recipes left out, so the graph can be read and checked.

## How it works

### One node for each name

The graph's **invariant**: each name is exactly one node. Everything after
depends on it, since an edge records a node's index, and two nodes called
`lib/ds.h` would be two different things to the walk. `graph_node()` keeps
it by asking the table before it adds:

```
    long *i = table_get(&g->index, name, len);
    if (i != NULL)
        return *i;
```

That is a lookup for every name of every rule, and a hash table makes each
one cost about the same however many names there are. Break it takes the
lookup away.

### Edges in the makefile's order

A target's list of needs keeps the order the makefile gave, each node once.
The order matters: make builds what a target needs in that order, which is
how, from 07.03 on, `bin/make -n` prints its commands in the order the
system's make does. When
a target has several rules, the reader puts the prerequisites of the one
with the recipe first, as GNU make does (`put_first()` in
`tools/make/read.c`).

### Every path, every time

The walk visits a node once for each path to it from the goal, so its work
grows with the number of paths, not the number of nodes. On the track
every library file is reached by 10 paths, one through each tool. Put
diamonds one under another, each needing the next, and the paths double
with every diamond: 07.03 measures that.

Remembering nothing also hides a **cycle**, a path from a node back to
itself, which no build order can satisfy. The walk cannot tell a node it
is in the middle of from one it reaches by another way, so the only sign it
has is depth: a path with more edges than there are nodes must pass some
node twice.

<!-- verify: session exit=2 -->
```
$ bin/make -n -f tools/make/examples/cycle.mk
make: a cycle in what 'all' needs: the walk went deeper than the 4 targets there are
```

It says there is a cycle, not where. And every level of the walk is a call
on the C stack, so it stops at `WALK_DEEPEST`, 10000 levels, before a long
chain of targets can overflow it. 07.02 brings a search that needs
neither check.

### What the reader leaves out

Our make reads the part of the makefile language this track uses: rules,
several targets or rules for one target, tab-started recipes (`@` in front
to keep a line quiet), variables set with `=` and `+=` and used as `$(NAME)`
or `${NAME}`, `include` with a glob, comments, lines continued with a
backslash, and `.PHONY`; and the options `-n`, `-s`, `-f FILE` and
`NAME=VALUE`. Everything else is an ordinary error that names the line:
`:=` and `?=`, functions such as `$(wildcard ...)`, automatic variables
such as `$@` and `$<`, pattern and suffix rules, conditionals, `define`,
`export`, `-include` and order-only prerequisites. GNU make's built-in
rules and variables are not there at all: `CC`, for one, is empty unless
the makefile or the environment sets it.

<!-- verify: session exit=2 -->
```
$ printf 'X := 1\n' > bad.mk; bin/make -f bad.mk
make: bad.mk:1: ':=' is not supported: only = and +=
$ printf 'a:\n\techo $@\n' > bad.mk; bin/make -f bad.mk
make: bad.mk:2: '$@' is not supported: write $(NAME), ${NAME} or $$
```

## Decide the boundary

`graph_edge()` refuses a second copy of an edge by reading through the
node's whole list. A real target needs a few dozen things, and the scan
costs nothing. A target that needs tens of thousands makes it quadratic:

<!-- verify: session
line 3 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
line 6 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
-->
```
$ python3 -c 'print("all: " + " ".join("f%d" % i for i in range(20000)))' > wide.mk
$ time bin/make --graph -f wide.mk > /dev/null
  0.16s user 0.00s system 99% cpu 0.164 total
$ python3 -c 'print("all: " + " ".join("f%d" % i for i in range(40000)))' > wide.mk
$ time bin/make --graph -f wide.mk > /dev/null
  0.63s user 0.00s system 99% cpu 0.638 total
```

Twice the prerequisites, four times the time. Another make could keep the
edges in a hash table of their own, keyed by the pair of nodes, and find a
duplicate in one lookup however long the list, paying an entry for every
edge of the graph. How many prerequisites does the largest target in your
builds have?

## Break it

Take the lookup out of `graph_node()`, so that every mention of a name adds
a new node. In `build/at/dsa/07.01/lib/depgraph.c`, delete these three
lines:

<!-- verify: setup
$ sleep 1
-->

<!-- verify: patch file=lib/depgraph.c
-    long *i = table_get(&g->index, name, len);
-    if (i != NULL)
-        return *i;
-->
```
    long *i = table_get(&g->index, name, len);
    if (i != NULL)
        return *i;
```

and build and run again:

<!-- verify: session -->
```
$ make -s
$ bin/make --graph -f tools/make/examples/diamond.mk
app: liba libb
liba:
libb:
liba: common.h
common.h:
libb: common.h
common.h:
common.h:
$ bin/make -n -f tools/make/examples/diamond.mk
make: *** No rule to make target 'liba', needed by 'app'.  Stop.
$ bin/make -n
make: Nothing to be done for 'all'.
```

Three nodes are called common.h now, and the liba that app needs is a new
node with no rule, not the liba below it. On the project it is quieter and
worse: make builds the makefile's first target, and the `all` that comes
first in the Makefile, an empty rule placed there so that it is the
default, is a different node from the `all` that the last line gives every
tool. So it needs nothing, and make says, with status 0, that there is
nothing to do. Put the lines back and `make -s` again.

## Go deeper

- [Stuart Feldman, Make - A Program for Maintaining Computer Programs](https://wolfram.schneider.org/bsd/7thEdManVol2/make/make.pdf) -
  the paper that introduced make, as printed in the Seventh Edition Unix
  manual (1978). Its abstract says it in one line: the description file
  "really defines the graph of dependencies", and make searches that graph
  depth first. The section "Basic Features" builds a program from three
  objects, two of which share the header defs: a diamond, as in
  diamond.mk.
- [Algorithms, 4th edition, 4.2 Directed Graphs](https://algs4.cs.princeton.edu/42digraph/) (Sedgewick and Wayne) -
  the section "Graph representation": a vertex-indexed array of adjacency
  lists, as `lib/depgraph.c` keeps, and the digraph API built on it.
