# 07.02 Depth-first search, and finding a cycle

The walk of 07.01 remembers nothing, so it cannot say where a cycle is,
only that it went too deep. This lesson gives the graph a search that marks
every node as new, open or done. It enters each node once, and the moment
it meets an open node again it has found a cycle, which make now reports
with every target on it, before it builds anything.

## Where this fits

![Where 07.02 fits](figures/07.02-map.svg)

Depth-first search is the second box in make's strip. It works on the
graph of 07.01, and keeps the path it is on in one of module 01's growable
arrays. make runs it first, from the goals, before any building: after this
lesson make refuses a makefile whose targets need each other in a circle,
and names the circle. The build is still the walk; the search also leaves
behind the order in which it finished the nodes, which 07.03 builds by.

## The idea

A **cycle** is a path of edges from a node back to itself. Say someone
gives diamond.mk's libb a header that records app's version, made by
running app:

<!-- verify: skip reason="two rules the reader types into loop.mk in Run it, not a file of the project" -->
```
libb: version.h
version.h: app
```

Now libb needs version.h, which needs app, which needs libb. No order can
build all three, each after what it needs. The walk of 07.01 would go round
until its path was longer than there are targets, and then say only that
there is a cycle somewhere. To say where, the search must know which nodes
it is in the middle of.

So the search gives every node one of three states. A node is **new** until
the search first reaches it. Then it is **open**: the search is still going
through what it needs, so it lies on the **path** from the goal down to
where the search is now. When everything it needs is done, it is **done**
too, and leaves the path. The search starts by opening the goal, then
repeats one step: take the next edge of the node at the end of the path.
If it leads to a new node, open that node and go on from there. If it leads
to a done node, that node is finished already, reached by a second way, and
there is nothing to do. If it leads to an open node, that node is on the
path: the path from it to here, and the edge back to it, is a cycle.
Because it always goes deeper first, from the newest node opened, it is a
**depth-first search**.

![Depth-first search on loop.mk, one frame per line of its trace: each node new, open or done, the path on the right, until an edge leads to an open node.](figures/07.02-search.svg)

Step through it. common.h is done before libb is entered, so when libb's
first edge leads to it again, that is a second way to a done node, not a
cycle. Then libb's second edge reaches version.h, and version.h's edge
leads to app, which is open: app, libb and version.h are the cycle, read
straight off the path.

### `graph_search`

The search, in `lib/depgraph.c`. The path is an array of frames, one for
each open node, each holding the node and how far through its needs the
search has got. The loop looks at the frame on top: when all its needs
have been looked at, the node is done, goes on the end of `order` and comes
off the path; otherwise it takes the next need and does what its state
says. `enter()` opens a node and pushes its frame. A cycle is read off the
path, from the open node that was met up to the top, and the function
returns -1. It starts from each goal in turn, and a goal that is done
already is skipped.

### `report_cycle`

What make says about a cycle: every target on it, each needing the next,
the first one again at the end, on stderr; then it exits with status 2.
`main()` runs the search before anything is built.

## How it works

### Why three states, and not two

A search that only marks nodes as seen or not cannot tell the two reasons
for meeting a seen node: a second way to a node that is finished, which
every shared prerequisite gives (common.h, or `lib/ds.h` in the track), and
a way back to a node it is still inside, which is a cycle. Call every seen
node a cycle and the diamond is one; ignore seen nodes and no cycle is
ever found. The third state is what separates them. Break it removes it.

The **invariant**: the open nodes are exactly the nodes on the path, in
order, each needing the next. `enter()` marks a node open as it pushes its
frame, and the same step that marks it done pops the frame:

```
                node->state = NODE_DONE;
                *(long *)array_push(order) = top->node;
                trace("leave", (long)path.len - 1, node);
                array_pop(&path);
```

So an open node met on an edge is somewhere on the path, and the frames
from it to the top, with the edge back, are a cycle.

### Each node once, each edge once

A node is entered only while it is new, and is never new again, so the
search enters each node it can reach once and follows each of its edges
once: its work grows with the nodes and edges, where the walk's grows with
the paths. On a chain of N diamonds, each needing the next, the search
enters 3N + 1 nodes and follows 4N edges, and the walk comes to nodes
2^(N+2) - 3 times.

### The path in an array

The walk is a recursion, one call on the C stack for each level, which is
why it stops at 10000 levels. The search keeps its path in an array on the
heap, so its depth is limited by memory, not the stack, and the path is
there to read when it meets a cycle. A chain of 100001 targets, each
needing the next:

<!-- verify: session -->
```
$ python3 -c 'print("\n".join("t%d: t%d" % (i, i + 1) for i in range(100000)))' > chain.mk
$ DS_STATS=1 bin/make -n -f chain.mk 2>&1 | grep -e '^make:' -e depgraph
make: what 't0' needs goes more than 10000 levels deep: too deep for the walk
stats: depgraph: nodes 100001, edges 100000, walk visits 10001, walk edges 10000, search visits 100001, search edges 100000
```

The search went all the way down; the walk, which runs after it here,
stopped. From 07.03 on the walk is no longer what builds.

## Decide the boundary

Our make stops at a cycle and names all of it. The system's make, GNU make,
does something else with the same file:

<!-- verify: session -->
```
$ make -n -f loop.mk
touch common.h
touch liba
make: Circular version.h <- app dependency dropped.
touch libb
touch app
```

It drops one edge, the one that closed the cycle (version.h needs app),
says so, and builds the rest as if the edge were not there: version.h, if
it had a recipe, would be made from whatever app was on the disk, before
app is made again. A build that always goes on is kind to a makefile with
a harmless loop in it; a build that stops never makes a file from
something stale. Which would you rather find out about on the day the loop
stops being harmless?

## Break it

Take away the third state: let a done node count as a cycle too. In
`build/at/dsa/07.02/lib/depgraph.c`, in `graph_search()`, delete the
branch for a done node:

<!-- verify: setup
$ sleep 1
-->

<!-- verify: patch file=lib/depgraph.c
-            } else if (next->state == NODE_DONE) {
-                trace("again", (long)path.len, next);
-->
```
            } else if (next->state == NODE_DONE) {
                trace("again", (long)path.len, next);
```

and build and run again:

<!-- verify: session -->
```
$ make -s
$ DS_TRACE=1 bin/make -n -f tools/make/examples/diamond.mk
trace: enter 0 app
trace: enter 1 liba
trace: enter 2 common.h
trace: leave 2 common.h
trace: leave 1 liba
trace: enter 1 libb
trace: cycle 2 common.h
make: array: element 18446744073709551615 of 2
$ bin/make -n
make: array: element 18446744073709551615 of 4
```

With two states, the shared common.h looks like a cycle. Then the code that
reads the cycle off the path looks for common.h's frame, which is not
there, and counts down past the bottom of the array: the index it asks for,
18446744073709551615, is -1 as an unsigned 64-bit number, which the array
refuses. Every project with a shared header now fails. Put the lines back
and `make -s` again.

## Go deeper

- [Jeff Erickson, Algorithms, chapter 6, Depth-First Search](https://jeffe.cs.illinois.edu/teaching/algorithms/book/06-dfs.pdf) -
  "Classifying Vertices and Edges" gives each vertex the same three states,
  new, active and finished, and shows that the active vertices always form
  a directed path; "Detecting Cycles" stops at an edge to an active vertex,
  as `graph_search()` does.
- [Algorithms, 4th edition, 4.2 Directed Graphs](https://algs4.cs.princeton.edu/42digraph/) (Sedgewick and Wayne) -
  "Cycles and DAGs": directed cycle detection with depth-first search
  (DirectedCycle.java), and the proposition that a digraph has a
  topological order if and only if it has no directed cycle.
- [MIT 6.006, Spring 2020, Lecture 10: Depth-First Search](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/resources/mit6_006s20_lec10/) (Demaine, Ku, Solomon) -
  the notes' "Cycle Detection": keep the ancestors on the path back to the
  start, and prove that a cycle makes the search follow an edge to one.
