# 09.01 Huffman codes: a greedy tree

A file spends 8 bits on every byte, whether the byte is the commonest
letter in it or one that turns up twice. This lesson gives gzip its first
way to make a file smaller: short codes for common bytes and long ones for
rare bytes, built by Huffman's rule with the heap of 02.04.

## Where this fits

![Where 09.01 fits](figures/09.01-map.svg)

This lesson is the first box in gzip's strip, the Huffman tree, in a new
column for module 09's two programs, gzip and gunzip. It stands on the heap
of module 02: the ring on the heap rail in gzip's column is this use, the
tree built by taking the two smallest items off the heap, again and again.
Everything after it in the module reads or writes bytes in codes like
these. After this lesson gzip can say how small a file would be in
Huffman's code alone, and print that code; it writes no compressed file
yet.

## The idea

The book is 562404 bytes, 4499232 bits as bytes. 'e' takes 8 bits each of
its 52886 times, and so does 'Z' each of its 2. The obvious first saving is
a **fixed-length code**: the book uses only 78 different bytes, 7 bits can
number 128 things, so every byte could take 7 bits. That is 3936828 bits,
12.5% less, and it is all a code of one length can do.

To do better, common bytes must get shorter codes than rare ones. The
trouble is reading them back: if 'e' is 0 and 'h' is 01, the bits 001 do not
say where one code ends. A **prefix code** removes the doubt: no code is
the start of another, so the reader takes bits until they spell a code and
knows that code is complete. A prefix code is a binary tree. Each byte is a
leaf, and its code is the path from the root, 0 for a left branch and 1 for
a right one, so the length of a byte's code is the leaf's **depth**. The
size of the file in that code is each byte's count times its depth, added
up. The question is which tree makes that sum smallest.

David Huffman's answer, from 1952, is **greedy**: it makes the choice that
looks best now and never goes back on it. Start with each byte as a tree of
one node, weighed by its count. Take the two lightest trees, join them under
a new node that weighs their sum, and put that back. When one tree is left,
it is the code.

![Huffman's tree for abracadabra, built by bin/gzip --huffman: the two lightest trees joined until one is left, then each byte's code read off it, and the same lengths numbered in order](figures/09.01-tree.svg)

The figure does it for "abracadabra", whose bytes are a 5 times, b and r
twice, c and d once. c and d are joined first, then b and r, then those two
pairs, then a with the rest. a ends one level down and the other four three
levels down: 5 x 1 + 6 x 3 = 23 bits. As bytes the word is 88 bits, and in
the best fixed-length code, 3 bits for each of five letters, 33.

"The two lightest, again and again" is what the heap of 02.04 is for: its
top is always the smallest item, and a pop or a push costs about log2(n)
steps. Each join is two pops and a push. Here the heap is the natural tool,
not a faster one. Bytes are at most 256 symbols (DEFLATE's own alphabet has
288), so looking at every tree for the two lightest at each join would take
no time worth measuring either. This lesson has no slow version to race;
its "obvious way" is the fixed-length code, and the measure is bits.

A compressed file does not keep the tree. Two trees can give every byte the
same length, and only the lengths decide the size, so the codes are numbered
from the lengths by a fixed rule: the **canonical code**, shortest codes
first, and the codes of each length counting up in byte order. The last
frame of the figure shows it. A writer then sends only the lengths, and the
reader numbers them the same way (09.02 reads such a file; 09.04 writes
one).

### `huff_lengths`

The tree, from an array of counts. Every node lives in one array, the
leaves first and each join after them, and records only its parent. A join
is always made after the two below it, so walking the array back from the
last join, the root, reaches each parent before its children and gives
every node its depth. The heap's comparison, `lighter()`, settles ties: on
equal counts the leaf of the smaller byte comes first, then the older join,
so the same counts make the same tree on every machine. It returns the
longest length.

### `huff_codes`

The canonical numbering, in the three steps RFC 1951 gives: count the codes
of each length; find the first code of each length; hand out each length's
codes in symbol order, counting up from its first.

### `show_huffman`

What `bin/gzip --huffman` does: count the bytes of a file, build their code,
and print each byte's count, length and code, then the total. At this
lesson that is all bin/gzip does; on its own it prints its usage.

## How it works

### Why the two lightest cannot be beaten

Two facts, on abracadabra's numbers. First, in a best code no byte sits
higher in the tree than a commoner one. Swap a (5 times, depth 1) with c
(once, depth 3): each a costs 2 bits more, the c 2 bits less, and the total
grows by (5 - 1) x (3 - 1) = 8, to 31 bits. So the two rarest bytes can
always be the two deepest leaves, side by side, as c and d are.

Second, joining them leaves a smaller problem of the same kind: four
symbols, a 5, b 2, r 2 and n1 2, where n1 stands for "c or d". Any code for
the four becomes a code for the five by giving n1's leaf two children; that
adds one bit to each of n1's 2 bytes, so it costs exactly 2 more, whatever
the code. The best code for the four, 21 bits, therefore gives the best for
the five, 23. The same argument holds for the four, and so on down to a
single tree. Each greedy join is safe, and that is the whole algorithm.

### The canonical numbering keeps it a prefix code

The **invariant** of `huff_codes()` is that no code is the start of a longer
one, and one line keeps it, at each step from one length to the next:

```
        code = (code + (unsigned long long)count[len - 1]) << 1;
```

The codes of a length start one past the last code of the length before,
with a 0 put after it, so a longer code begins with a pattern beyond every
shorter code, never with one of them. For abracadabra, a is 0; the 3-bit
codes start past it, at 1 shifted twice: 100. The tree's own paths gave c
100, d 101, b 110 and r 111; the canonical code gives b 100, c 101, d 110 and
r 111. Same lengths, same 23 bits, and only five small numbers to write
down. Ties are why this matters: another best tree for abracadabra gives a
1 bit, b 2, r 3, c and d 4, also 23 bits (5 + 4 + 6 + 4 + 4). Whatever tree
the lengths came from, the canonical numbering of them is one code.

### One kind of byte

A file of one byte value makes a tree of one node, at depth 0, and a code
of no bits cannot be read back. `huff_lengths()` gives it one bit instead:

```
        lengths[s] = counts[s] > 0 ? (unsigned char)(used == 1 ? 1 : depth[s]) : 0;
```

## Break it

Make the heap hand back the heaviest tree instead of the lightest. In
`lib/huffman.c`, in `lighter()`, change
`return x->count < y->count ? -1 : 1;` to
`return x->count > y->count ? -1 : 1;`, then build and run the word and the
book again:

<!-- verify: patch file=lib/huffman.c old="return x->count < y->count ? -1 : 1;" new="return x->count > y->count ? -1 : 1;" -->
<!-- verify: session -->
```
$ make -s
$ printf abracadabra | DS_TRACE=1 bin/gzip --huffman
trace: huffman: tree of 5 symbols
trace: huffman: join 'a' 5 + 'b' 2 = n1 7
trace: huffman: join n1 7 + 'r' 2 = n2 9
trace: huffman: join n2 9 + 'c' 1 = n3 10
trace: huffman: join n3 10 + 'd' 1 = n4 11
byte      count  bits  code
'a'           5     4  1110
'b'           2     4  1111
'c'           1     2  10
'd'           1     1  0
'r'           2     3  110
11 bytes, 5 different: 88 bits as bytes, 37 bits in these codes (5 bytes)
$ bin/gzip --huffman data/book.txt
gzip: huffman: a code of 65 bits, longer than 32
```

Each join is now the heaviest tree, so it is taken again at once, and the
tree becomes a chain: a, the commonest letter, at the bottom with 4 bits,
and d, the rarest, at the top with 1. It is still a prefix code, and every
byte still decodes, but 37 bits is worse than the 33 of the fixed-length
code. On the book the chain is so deep that `huff_codes()` refuses it, with
an ordinary error. The greedy choice only works in the right direction. Put
the line back.

## Go deeper

- [RFC 1951, DEFLATE](https://www.rfc-editor.org/rfc/rfc1951) by Peter
  Deutsch, section 3.2.2, "Use of Huffman coding in the 'deflate' format":
  the rule that codes of one length are consecutive and shorter codes come
  first, so a code is given by its lengths alone, and the three steps that
  `huff_codes()` follows.
- [Algorithms, chapter 4, Greedy Algorithms](https://jeffe.cs.illinois.edu/teaching/algorithms/book/04-greedy.pdf)
  by Jeff Erickson, the section "Huffman Codes": the exchange argument
  above as a lemma (the two least frequent characters can be deepest
  siblings) and a proof by induction, and the construction with a priority
  queue and arrays of parent and child indices, as `huff_lengths()` keeps
  them.
- [An Explanation of the Deflate Algorithm](https://zlib.net/feldspar.html)
  by Antaeus Feldspar, the part on Huffman coding: a tree built by joining
  the two lowest weights, and the extra rules that let DEFLATE rebuild the
  tree from its code lengths.
- David Huffman, "A Method for the Construction of Minimum-Redundancy
  Codes", Proceedings of the IRE 40(9), 1952: the paper the algorithm comes
  from.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th
  edition, the chapter on greedy algorithms, its section on Huffman codes:
  the same proof, and the running time with a min-priority queue.
