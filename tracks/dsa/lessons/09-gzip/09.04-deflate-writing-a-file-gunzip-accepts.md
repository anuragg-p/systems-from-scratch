# 09.04 Deflate: writing a file gunzip accepts

gzip finally writes a .gz file: the tokens of 09.03, in Huffman codes as in
09.01, in blocks laid out exactly as 09.02 reads them. The system's gunzip
opens what it writes, and on the book it comes within 3% of the system's
own gzip.

## Where this fits

![Where 09.04 fits](figures/09.04-map.svg)

This is the deflate box, last in gzip's strip, and the second half of the
deflate rail's dot in gzip's column: the format is now written as well as
read. The rail runs on to git in module 10, which compresses every object
it stores this way. Deflate stands on everything before it in the module:
LZ77 finds the repeats, Huffman's tree gives the codes, and inflate's tables
of lengths and distances say how to write them. After this lesson gzip turns
a file into a .gz file that any gunzip opens, and module 09's job is done
both ways.

## The idea

09.03 turns the book into tokens: 10726 literals and 94587 matches. What is
left is to write them as bits a reader understands, and DEFLATE offers
three forms for each block. The obvious one is the **fixed** codes: the RFC
gives them once and for all, so nothing is sent before the data. But they
fit no file in particular: a literal takes 8 or 9 bits whether it is 'e' or
'Z'. Written that way the book is 278222 bytes.

A **dynamic** block uses codes built for its own counts, as 09.01 built
them for bytes, but over all of DEFLATE's symbols: literals, the end of the
block, and the length codes, with a second code for the distances. The
reader has to be told the codes first, so the block starts with a
**header**: the code lengths, run-length coded, and those in a third
Huffman code of their own. On the book's blocks of 16384 tokens the header
is a few hundred bits and pays for itself many times over: 223193 bytes.
On a short input it does not. And a **stored** block, the bytes as they
are, is the best a block of random bytes can do.

So the writer does not choose a form in advance. It prices each block in
all three, to the bit, and writes the cheapest:

![One block priced three ways before it is written: abracadabra stored, in the fixed codes and in its own codes, the parts of each, and the first block of the book the same three ways](figures/09.04-block.svg)

For "abracadabra" (seven literals and one match) the fixed codes win, 79
bits, because the dynamic block's header alone is 130 bits. For the first
block of the book, 77409 bytes, its own codes win by a fifth.

### `put`

The bit writer, the mirror of 09.02's `bits()`: values go in from their
lowest bit, and a byte leaves whenever 8 bits are waiting.

### `write_stored` and `write_tokens`

A stored block: the 3 bits, zeros up to a byte boundary, LEN and its
complement NLEN, then the bytes, 65535 at most a block. And the tokens of a
coded block: a literal's code, or a length's code and its extra bits then a
distance's code and its extra bits, and the end-of-block code last.

### `plan_dynamic` and `write_header`

A dynamic block's codes and the header that states them. Both codes are
built from the block's counts with no code longer than 15 bits (below).
Their lengths are one run of numbers, cut short where the last ones are
zeros, and written with 16 (repeat the last length 3 to 6 times), 17 (3 to
10 zeros) and 18 (11 to 138 zeros). Those items get a Huffman code of their
own, at most 7 bits, whose lengths go first, 3 bits each, in the RFC's
order. `plan_dynamic()` adds up the header's exact size as it goes.

### `write_block` and `deflate_raw`

`write_block()` counts a block's symbols, prices it stored, fixed and
dynamic, and writes the cheapest (or the one `--blocks=` forces).
`deflate_raw()` takes the input 16384 tokens at a time from the LZ77 parse,
writes each as a block, marks the last one, and pads the stream to a byte.

### `huff_lengths_limited`

`huff_lengths()` of 09.01 with a limit on the longest code, beside it in
lib/huffman.c (How it works).

### `gz_pack` and `gzip_one`

The gzip member around the data: the header (the name and time of a file,
none for standard input), the DEFLATE data, the CRC-32 and the size.
`gzip_one()` makes FILE.gz and removes FILE, as the system's gzip does;
`-c` writes to standard output, `-k` keeps the file, `-1` to `-9` set the
chain bound of 09.03, from 4 tries to 4096.

## How it works

### Bits in the order inflate takes them

DEFLATE sends numbers lowest bit first but Huffman codes highest bit first,
and `put()` sends whatever it is given lowest bit first. So each code is
reversed once, when its codes are made, and every symbol after that is a
single `put()`. `make_codes()` does it:

```
        for (int k = 0; k < c->len[s]; k++)
            r |= ((codes[s] >> k) & 1) << (c->len[s] - 1 - k);
        c->rev[s] = r;
```

### Every block is priced before it is written

A block's cost in each form can be added up exactly before a bit is
written: stored is its bytes plus about 5 for each piece of up to 65535,
fixed is each symbol's count times the RFC's lengths plus extra bits, and
dynamic is the planned header plus each count times the block's own
lengths. Then:

```
        form = sb <= fb && sb <= db ? DEFLATE_STORED : fb <= db ? DEFLATE_FIXED : DEFLATE_DYNAMIC;
```

So every block goes out in its cheapest form, and a file of random bytes
grows only by the few bytes its stored blocks' headers take. The dynamic
price comes from the same `plan_dynamic()` whose header is then written, so
the price and the bits cannot disagree.

### The 15-bit limit

In the code-length alphabet, 0 to 15 are lengths and 16, 17 and 18 are
repeats, so a length of 16 or more cannot be written at all. Huffman's tree
for skewed counts can be deeper than that, as the letters above showed.
`huff_lengths_limited()` keeps the tree's order but flattens it: while the
deepest code is too long, it halves every count, rounding up so that no
symbol drops to 0, and builds the tree again.

```
    while ((longest = huff_lengths(c, n, lengths)) > maxbits) {
```

Halving brings the rare counts closer to the common ones, so the tree is
less lopsided; once every count is 1 it is balanced, 9 bits for 288
symbols, so the loop ends. The result is no longer the best code: for the
letters, one halving gave 10 bits at most and a block of 28643 bits of data
(28819 less the 3 block bits and the 173 of the header), against 28634 for
Huffman's own unwritable 18-bit code, 9 bits more. Exact algorithms exist
(package-merge), but the case is rare: on the book, rebuilds 0.

### Complete codes

Huffman's tree on two or more symbols uses every bit pattern. So the only
codes this gzip could write with a pattern to spare are a lone symbol's
1-bit code (the literal and length code of an empty block, which holds only
the end of block, or a distance code with one of its codes used) and a
distance code with no codes at all, for a block of literals only. RFC 1951
(3.2.7)
allows both for distances, and zlib reads a lone 1-bit code of either kind
and an empty distance code; what it refuses is an incomplete code of any
other shape. A block made by hand whose literal and length code had one
1-bit and one 2-bit code, leaving the pattern 11 unused, was read by
bin/gunzip and refused by Apple's gunzip ("data stream error"), but
Huffman's tree never makes such a code. `at_least_two()` still gives a code
with fewer than two symbols a partner that is never used, so that every
code this gzip writes uses every pattern. It is belt and braces, not
something a reader needs: with it switched off, Apple's gunzip, GNU gzip,
Python's zlib and bin/gunzip read back every one of 98 test files.

## Decide the boundary

This gzip's parse is greedy: at each place it takes the longest match and
moves past it. zlib, inside the system's gzip, first looks one byte
further: if the match that starts at the next byte is longer, it writes
this byte as a literal and takes that one. RFC 1951 calls it **lazy
matching**. Measured in a copy of this project with that one change made in
`lz77_parse()` (five lines, not in the course's code): the book at -6 comes
to 216969 bytes, against the system's 216849 and our 223193, and the 5.5 MB
text of `data/gen.py text 1000000` to 2464467 against the system's 2463014.
It also took that text 0.56 seconds instead of 0.30, since nearly every
match is looked for twice. Greedy is simpler and about 3% bigger; lazy is as small as
the real thing and slower, unless the second search is made cheap the way
zlib makes it. Which matters more for your files: the last 3%, or the
simplest parse that is right?

## Break it

Take the 15-bit limit out of the literal and length code. In
`lib/deflate.c`, in `plan_dynamic()`, change
`huff_lengths_limited(lc, 286, HUFF_MAX_BITS, h->lit.len);` to
`huff_lengths(lc, 286, h->lit.len);`, then build and compress the letters
again:

<!-- verify: patch file=lib/deflate.c old="huff_lengths_limited(lc, 286, HUFF_MAX_BITS, h->lit.len);" new="huff_lengths(lc, 286, h->lit.len);" -->
<!-- verify: session needs="gzip" -->
```
$ make -s
$ bin/gzip -c --algo=none fib.txt > fib.gz
$ gzip -t fib.gz
gzip: data stream error
gzip: fib.gz: uncompress failed
$ bin/gunzip -t fib.gz
gunzip: fib.gz: code lengths that run past the 259 the block says
```

gzip wrote the file without complaint, and neither reader can open it. The
unlimited tree gave the rarest letters 16, 17 and 18 bits, and in the
code-length alphabet 16, 17 and 18 do not mean lengths, they mean repeats.
Read back, the header's lengths turn into runs that go past the end of the
list, and the block is nonsense from there. The system's gzip and ours both
refuse it, each in its own words. Put the line back.

## Go deeper

- [RFC 1951, DEFLATE](https://www.rfc-editor.org/rfc/rfc1951), sections
  3.2.5 to 3.2.7: the length and distance codes with their extra bits, the
  fixed codes, and the dynamic header that `write_header()` writes, its
  code-length alphabet of 0 to 15 and the repeats 16, 17 and 18, and the
  order of the code-length code's lengths. Section 4 describes lazy
  matching.
- [RFC 1952, GZIP](https://www.rfc-editor.org/rfc/rfc1952), section 2.3:
  the header `gz_pack()` writes, with the meaning of XFL 2 and 4 and OS 3.
- [An Explanation of the Deflate Algorithm](https://zlib.net/feldspar.html)
  by Antaeus Feldspar, the closing sections: how the trees are sent as
  code lengths, run-length coded, and why keeping codes to 15 bits is the
  tricky part.
- [zlib's doc/algorithm.txt](https://github.com/madler/zlib/blob/master/doc/algorithm.txt):
  zlib's lazy evaluation, and which levels leave it out for speed.
