# 09.02 Inflate: reading a real gzip file

gunzip turns a .gz file back into the bytes it holds. This lesson reads the
format exactly as RFC 1951 and RFC 1952 lay it out, down to the order of
the bits, so that bin/gunzip opens what the system's gzip wrote and checks
that every byte came out right.

## Where this fits

![Where 09.02 fits](figures/09.02-map.svg)

This is the inflate box, second in gzip's strip, and it brings the module's

the system's .gz files open, and a damaged one is refused with a message
saying what is wrong, never turned into wrong bytes.

## The idea

Making a file smaller leaves room for choices. Reading one leaves none: the
system's gzip wrote its file to a format, and a reader that is wrong by one
bit anywhere reads garbage from there on. So the job here is to take a real
file apart exactly, and then to make sure it was read right.

A gzip file is one or more **members**. A member is a header of at least 10
bytes (1f 8b, which says gzip; 08, the method; flags saying which optional
fields follow, such as the file's name; a time; and two bytes about the
compressor), then the compressed data, then a **trailer** of 8 bytes: the
**CRC-32** of the original bytes, a 32-bit check value computed from all of
them, and how many there were.

The compressed data is **DEFLATE**, a stream of bits cut into **blocks**.
Each block starts with 3 bits: one says whether it is the last, two give its
type. A **stored** block holds bytes as they are. The other two hold
**symbols** in Huffman codes: a **fixed** block in codes the RFC gives once
and for all, a **dynamic** block in codes of its own, which it first states
as code lengths, themselves in a Huffman code. A symbol is a literal byte
(0 to 255), the end of the block (256), or a length (257 to 285) followed by
a distance in a second code: copy that many bytes from that far back in what
has been written. A length and a distance are a **match**.

Bits are taken from the lowest bit of each byte up. A number, such as a
block's type, is read lowest bit first; a Huffman code is read from its
first bit, the highest, one bit at a time, until the bits so far are a
code. Here is a real file, 29 bytes that the system's gzip made from "hello
hello hello" and a newline, read the way bin/gunzip reads it:

![A 29-byte file from the system's gzip read field by field: the header, the block's 3 bits, the codes of seven literals, a match that copies bytes it is still writing, the end of the block, and the trailer's CRC-32 and size](figures/09.02-bits.svg)

Seven literals, then one match: length 10, distance 6. The match is longer
than its distance: when it starts only 6 of its bytes exist ("ello h"), and
the last 4 ("ello") are copied from bytes the match itself has just
written. That is allowed, and it is why the copy goes a byte at a time. DEFLATE itself carries no check: the trailer's CRC-32 and size are
the only proof that the bytes came out as they went in, and gunzip writes
nothing until both agree.

Reading a code a bit at a time is the obvious way, and it is never too slow
to use: the work is a few steps per symbol, the same for every symbol in
the file. The faster way looks at 9 bits at once in a table of 512 entries
that says which symbol they start with and how long its code really is. The
short codes, which Huffman gives the common symbols, take one look; the few
longer ones go on a bit at a time. Run it measures what the table saves,
and it is less than the counts promise.

### `bits`

The bit reader: the next k bits as a number, lowest first. Bytes are loaded
into a 64-bit buffer whose lowest bit is always the next to be read. Past
the end of the input it loads zeros, and `cut_short()` notices if any of
them is ever used.

### `build`

A Huffman code made ready to read, from its lengths: how many codes of each
length, the first code of each length (the canonical numbering of 09.01),
the symbols in the order of their codes, and the 512-entry table for codes
of up to 9 bits. Lengths that claim more codes than there are bit patterns
are an error.

### `decode_bits` and `decode_table`

The two ways to read one symbol, picked by `gunzip --algo=bits` or `table`
(the default). `decode_bits()` adds a bit at a time; the codes of each
length are consecutive numbers, so "is this a code of this length, and
whose" is one subtraction. `decode_table()` peeks at 9 bits and looks them
up, falling back to `decode_bits()` for a longer code.

### `codes`, `stored`, `fixed` and `dynamic`

`codes()` reads a block's symbols until 256: a literal is written, a length
and a distance are copied from the output. `stored()` skips to the next
byte, checks LEN against NLEN, its complement, and copies LEN bytes. `fixed()` builds the RFC's fixed codes once. `dynamic()` reads
the block's three counts, the 3-bit lengths of the code-length code (in the
RFC's odd order), then the lengths of the two real codes in that code, with
16, 17 and 18 meaning runs.

### `inflate_raw`

The blocks, one after another, until the one marked last; it returns how
many input bytes the data took, so the caller finds what follows.

### `crc32`, `header`, `gz_unpack` and `gunzip_one`

The gzip side, in tools/gzip/gz.c and gunzip.c. `crc32()` computes the
check with a table of what each byte value contributes. `header()` checks
the magic number and the method and skips the optional fields the flags
announce. `gz_unpack()` reads member after member: header, `inflate_raw()`,
then the trailer, compared with the bytes that came out. `gunzip_one()`
reads a whole file, unpacks it in memory, and writes only when everything
checked.

## How it works

### A table indexed by the code backwards

A code's first bit is its highest, but it arrives first, into the lowest
bit of the buffer. So the 9 bits `decode_table()` peeks at hold a code of
length len reversed in their low len bits, and whatever follows above them.
`build()` reverses each short code once and fills every entry whose low
bits are it, one for each value of the bits above:

```
        for (unsigned e = r; e < (1u << TABLE_BITS); e += 1u << len)
            c->table[e] = (unsigned short)(i << 4 | len);
```

A 3-bit code fills 64 of the 512 entries, a 9-bit code one. Each entry
holds the symbol and its true length, so only that many bits are used up.

### A code never claims more patterns than exist

A dynamic block's code lengths come from the file, and a damaged file can
claim anything. Before a code is used, `build()` checks that its lengths
fit in a binary tree:

```
        left = 2 * left - c->count[len];
        if (left < 0)
```

`left` counts the bit patterns of length len that no shorter code has
taken; each code of that length takes one, and more codes than patterns
is an error. Fewer codes than patterns is allowed
(RFC 1951 itself gives a lone distance code one bit, with one pattern
unused), and a pattern no symbol has is an error when it is read.

### The invariant: nothing is read from outside

Whatever the bytes, inflate reads only inside the input, and copies only
from bytes it has written. Past the input's end the reader loads zeros and
`cut_short()` turns any use of them into "the data ends in the middle of a
block". Every count the file gives is checked before it is used, and the
one that matters most is a match's distance:

```
        if (back > out->len)
```

A match then copies from the output itself, a byte at a time, which is
what makes an overlapping match work: each byte it reads was written
before it is needed.

```
            unsigned char b = (unsigned char)out->data[out->len - back];
```

## Break it

Copy a match from one byte too near. In `lib/inflate.c`, in `codes()`,
change `out->data[out->len - back]` to `out->data[out->len - back + 1]`,
then build and read the hello file again:

<!-- verify: patch file=lib/inflate.c old="out->data[out->len - back]" new="out->data[out->len - back + 1]" -->
<!-- verify: session -->
```
$ make -s
$ DS_TRACE=1 bin/gunzip -c hello.gz
trace: inflate: block 1: fixed (last)
trace: inflate: 0: literal "h"
trace: inflate: 1: literal "e"
trace: inflate: 2: literal "l"
trace: inflate: 3: literal "l"
trace: inflate: 4: literal "o"
trace: inflate: 5: literal " "
trace: inflate: 6: literal "h"
trace: inflate: 7: match distance 6 length 10 "llo hllo h"
trace: inflate: 17: literal "\n"
trace: inflate: end of block 1: 87 bits, 18 bytes
gunzip: hello.gz: the data's CRC-32 is a8e6f8ce, but the trailer says df8a7c3b
```

Every code still decodes: the block ends where it should, after 87 bits
and 18 bytes, and the size in the trailer agrees. Only the bytes are wrong,
and DEFLATE has no way to know. The trailer's CRC-32 is what catches it,
which is why it is there, and why gunzip writes nothing before checking.
Put the line back.

## Go deeper

- [RFC 1951, DEFLATE](https://www.rfc-editor.org/rfc/rfc1951), sections
  3.1.1 (how bits are packed into bytes: numbers from their lowest bit,
  Huffman codes from their highest) and 3.2.3 to 3.2.7: the block header,
  stored blocks, the length and distance tables that `codes()` uses, the
  fixed codes, and the dynamic block's header with its code-length
  alphabet, 16, 17 and 18, sent in the order 16, 17, 18, 0, 8, 7, 9, ...
- [RFC 1952, GZIP](https://www.rfc-editor.org/rfc/rfc1952), section 2.3,
  the member format: every header field and flag that `header()` checks,
  the reserved flag bits, and the trailer. Section 8 is sample code for the
  CRC-32, the same table method as `crc32()`.
- [zlib's doc/algorithm.txt](https://github.com/madler/zlib/blob/master/doc/algorithm.txt),
  the part on decompression: zlib's inflate looks up 9 bits of a
  literal/length code at once, as `decode_table()` does, and sends a longer
  code to a second table instead of a bit at a time.
- [An Explanation of the Deflate Algorithm](https://zlib.net/feldspar.html)
  by Antaeus Feldspar: the three kinds of block, and an LZ77 example whose
  match, like the hello file's, is longer than its distance.
