# 09.03 LZ77: finding repeats with a hash table

gzip's second idea: bytes that have been seen before are written as a
pointer back to them. The work is finding, at every byte, the longest
earlier copy of what follows. This lesson does it by trying every earlier
place, then with a hash table of three-byte strings, and on the book the
two find the same matches in 3 seconds and in 0.03.

## The idea

Huffman's code alone takes the book to 56% of its size. But text repeats
itself far more than its letter counts show: " the ", "Holmes", "said he",
whole phrases. 09.02 read a file where "hello" came back as a **match**, a
pair (distance, length) meaning "the next length bytes are the ones
distance bytes back". Writing such pairs is **LZ77**, after Ziv and
Lempel's paper of 1977. DEFLATE allows a distance of up to 32768, the
**window**, and a length of 3 to 258: a match of 1 or 2 bytes costs more
than the bytes themselves.

The parse is greedy. At each place, find the longest match that starts
somewhere in the window; if it is 3 bytes or more, write it and skip past
it, or else write the byte as a **literal** and move on one. Everything
depends on finding that longest match, and the obvious way is to try every
earlier place in the window, nearest first, and compare bytes. On the book
that is 3275711270 places tried: every byte has up to 32768 places behind
it, and almost all of them fail at the first byte.

Most of those tries never had a chance. A match of 3 bytes or more starts
with the same three bytes, so only the earlier places where those three
bytes stood are worth a try. A **hash table** keyed on three-byte strings
can list them: for each hash, a **chain** of the places with that hash,
newest first. Finding a match is then walking one chain:

![LZ77 over "abracadabra abracadabra", one token a frame: each place looks up the chain of its next three bytes; an empty chain gives a literal, and a chain is tried nearest first for the longest match](figures/09.03-chains.svg)

The first seven places find empty chains and go out as literals, each
place going into the table as the parse passes it. At 7, the chain of
"abr" holds 0: a match of 4 bytes, "abra", 7 back. At 12 the chain holds 7
and 0. The nearer gives 4 bytes, the farther all 11: the longest wins.
Trying every place in the window tries 51 places on this text; the chains
try 3, and find the same matches.

### `match_scan`

The obvious way, kept as `gzip --lz77 --algo=scan`: for each distance from
1 to the window, count the bytes that agree, and keep the longest (of equal
lengths, the nearer). It stops early only if a match reaches the most that
can match.

### `insert` and `match_hash`

The table is two arrays: `head[h]`, the newest place whose three bytes hash
to h, and `prev[p % 32768]`, the place before p on the same chain. `insert()`
puts a place at the head of its chain. `match_hash()` first inserts every
place before the current one, then walks the chain of the current three
bytes, nearest first, comparing bytes as the scan does. It stops when the
chain ends, when a place is out of the window, or after `chain` tries, a
bound set by `--chain=N` (128 unless given; 0 for none).

### `lz77_parse`

The greedy parse: at each place the longest match, by whichever way was
chosen, or a literal. It hands out **tokens**, a literal byte or a match,
some at a time, which is how 09.04 will take them a block at a time.

### `show_lz77`

What `gzip --lz77` prints: the tokens counted, literals and matches, and the
bytes the matches stand for. With `DS_TRACE=1` each token is printed as it
is found.

## How it works

### Why the scan is slow but not quadratic

While the input is shorter than the window, each byte has every byte
before it to try, and twice the input is four times the work: the first
doubling above, from 21 KB, inside the window, to 42 KB, has a ratio of
3.2, and the later ones 2.2. Past 32 KB the
window caps it: each byte tries at most 32768 places, however long the
file. That is linear, with a constant of up to 32768 tries a byte. The
chains are linear too, with a constant of a few: on the book, 7.7 places a
byte.

### A different table from freq's

freq's table of module 01 answers "is this word here, and where is its
count?": it stores every key, compares whole keys, grows by doubling, and
keeps every entry for good. This one only has to name candidates, and it
is shaped by the window:

- **Fixed size.** 32768 heads, one per 15-bit hash, and 32768 links, one
  per place in the window: the same memory for a file of any size.
- **No keys.** A place is just a number. Its key is the three bytes at that
  place in the input, so a hash collision costs nothing but a failed
  comparison, which the search makes anyway.
- **Nothing is deleted.** A place more than 32768 back ends the walk, and
  its link is written over when a place 32768 later takes the same slot.
- **Newest first.** A new place goes at the head of its chain, so the
  nearest candidates come first: a short distance takes fewer bits to
  write, and a bound on the tries drops only the farthest.

The hash is one multiplication:

```
    return (x * 2654435761u) >> (32 - HASH_BITS);
```

x is the three bytes as one number; multiplying by a large odd number
stirs all 24 bits into the top ones, and the top 15 are the hash, as
freq's FNV-1a in 01.03 stirs every byte of a word.

### The invariant: every earlier place is on its chain

When a chain is walked for the place pos, every place before pos must
already be on its chain, and pos itself must not be:

```
    for (; z->hashed < pos; z->hashed++)
        insert(z, z->hashed);
```

The places inside a match were skipped by the parse, but they go in all
the same; leave them out and a later repeat of the bytes they start is
never found. pos goes in only on the next call, after its own search, so a
chain never offers pos as a match for itself. That is why the chains
with no bound find exactly the scan's matches: a match of 3 bytes or more
starts with the same three bytes, so its place is on the chain.

### The bound

A chain of a common string, such as " th", can be thousands of places
long, and most of them give short matches. `--chain=N` stops the walk after
N tries; with 128, the book loses 41 bytes of matches out of 551719. The
real gzip's levels, -1 to -9, set a bound like this one among other
things, and 09.04 puts this bound behind the same options.

## Break it

Give the hash table only the first byte to go on. In `lib/lz77.c`, in
`hash3()`, change `return (x * 2654435761u) >> (32 - HASH_BITS);` to
`return x & 0xff;`, which is 256 chains instead of 32768, then build and
parse the book again:

times as many bytes go out as literals: 55613 against 10726. It is the
lesson of freq's summed hash in 01.03 again: a hash that does not spread
its keys turns a table back into a list. Put the line back.

## Go deeper

  "Compression algorithm details": a chained hash table on three-byte
  strings, searched for the longest match, with singly linked chains; and
  "lazy matching", which 09.04 comes back to.
- [zlib's doc/algorithm.txt](https://github.com/madler/zlib/blob/master/doc/algorithm.txt),
  the part on compression: chains searched from the most recent string,
  never pruned, cut at a length the compression level sets, and the
  levels' trade between speed and size.
