# 10.04 diff between commits, and the merge base

Two questions about two commits: what changed between them, and where
their histories split. diff answers the first by walking the two trees
side by side and passing over every subtree that has the same name in
both, and runs module 06's diff on each file that changed. merge-base
answers the second by walking back from both commits at once, newest first
on 02.04's heap, marking which of the two reaches each commit.

## Where this fits

![Where 10.04 fits](figures/10.04-map.svg)

This is the last box in git's strip, and the end of the diff rail: the
ring in git's column is module 06's diff, Myers' search of 06.03 and the
hunks of 06.02, now run on two blobs instead of two files. The heap and the
hash table come back too: merge-base takes the newest commit off 02.04's
heap, and keeps one parsed commit per name in 01.02's table. The walk over
two trees stands on what 10.02 showed, that a tree's name stands for
everything under it, and the walk over history on 10.03's commits. After
this lesson git does what this module set out to do: init, add, commit,
log, diff and merge-base, on a repository the real git reads and checks.

## The idea

![diff of first and second: the two top trees walked side by side in git's order; b/, the same tree on both sides, is passed over and never opened, d/ and d/e/ are opened, and f.txt is the one change.](figures/10.04-diff.svg)

To say what changed between two commits, the obvious way is to read
everything: open every tree of both commits, read every blob, pair the
files up by path, and compare their bytes. It is right, and on a project
of 16,000 files with one changed it opens 4,146 trees and reads 32,002
blobs to find that one file.

10.02 already holds the way out. A tree's name is the hash of its entries,
which hold their own names, all the way down: two trees with the same name
hold the same files with the same bytes. So diff walks the two top trees
together, entry by entry, in git's order, the way a merge walks two sorted
lists. An entry with the same name, mode and object on both sides is
passed over: if it is a directory, nothing under it is opened at all. A
directory whose names differ is opened on both sides and walked the same
way. A file whose names differ is a change, and only its two blobs are
read, to print the patch with module 06's diff. The work grows with the
depth of the change, not with the size of the project.

The second question is where two branches split: their **merge base**,
the newest commit that both histories hold, which a merge starts from. The
obvious way asks, for each commit in one history, newest first, whether the
other history holds it, by walking the whole other history again. The
better way walks back from both commits at once, newest first, as log did,
and **paints** each commit it meets with which of the two reached it. The
first commit painted by both is the merge base:

![The merge base of main and side: popped newest first, third and second are reached from main, the side commit from side, and first from both, which makes it the merge base.](figures/10.04-base.svg)

### `walk_skip`

The two trees side by side. Their entries are merged in git's order with
10.02's `tree_cmp()`. The same name, mode and object: passed over, a whole
subdirectory for one comparison of 20 bytes. A subdirectory that differs:
opened on both sides, recursively. A file that differs: a change. A name on
one side only: everything under it is gone, or new.

### `flatten` and `walk_all`

The obvious way, kept as `diff --algo=all`: `flatten()` opens every tree of
a commit and reads every blob, and `walk_all()` pairs the files of the two
commits by path and compares their bytes.

### `show_change`

One file's patch, as the real git prints it: the `diff --git` line, a new,
deleted or changed mode, the `index` line with both blobs' names, then
module 06's `diff_text()`, `diff_myers()` and `diff_unified()` on the two
blobs. A blob with a NUL in its first 8000 bytes is "Binary files ...
differ" instead.

### `paint` and `rewalk`

`paint()` is merge-base: both commits go on 02.04's heap, marked 1 and 2;
each commit popped passes its marks on to its parents; a commit with both
marks is a merge base, and its marks go on as stale; the walk stops when
only stale commits are left. `rewalk()` is the obvious way, kept as
`merge-base --algo=rewalk`: for each commit of the second history, newest
first, a walk of the whole first history to see whether it is there.

## How it works

### Equal names mean equal contents, all the way down

Skipping is safe because of what 10.02 showed: a tree's name is the SHA-1
of its entries, each of which carries the name of what is below it. If two
trees have the same name, they have the same entries, so their
subdirectories have the same names too, and so on to the blobs. The test
that lets `walk_skip()` pass over a whole subdirectory is one comparison
of 20 bytes, and of the mode:

```
            if (x->mode == y->mode && memcmp(x->oid, y->oid, 20) == 0) {
```

The mode matters because it is not in the blob. A blob's name covers its
bytes and nothing else; whether the file is executable is written in the
tree that lists it. Break it shows what is lost without that half of the
test.

### What a merge base is, and why the stale marks end the walk

The real git's documentation defines it: one common ancestor is better
than another if the other is its ancestor, and a merge base is a common
ancestor that has none better. Painting finds them. A commit marked both 1
and 2 is reached from both sides, so it is common; everything behind it is
common too, but no better, so it is marked stale and its marks go on as
stale. Since the heap gives commits newest first, by the time the queue
holds nothing but stale commits, every common ancestor that could still be
best has been found. Two can be: with merges that cross, each branch having
merged the other, there are two best common ancestors, and `--all` prints
both. A last pass drops any candidate that another one reaches.

### Where this diff differs from the real git's

Both run Myers' search, but the real git's is not always the shortest:
its `--minimal` has it "spend extra time to make sure the smallest
possible diff is produced", and this git always does that. So on files
that differ in many places the two can print different hunks that make the
same change. The real git's hunk headers can name the function a hunk is
in (`@@ -3,7 +3,7 @@ int main(void)`); this git's do not, as module 06's
did not. And the real git looks for renamed files by default: d/g.txt
moved to d/h.txt is a rename to it, and a deletion and an addition to this
git, as to the real git's `diff --no-renames`.

## Go deeper

This is the last lesson of the track. Over ten modules you have written a
growable array and a hash table; insertion sort, merge sort, quicksort and
a heap; an editor's text in a gap buffer and a piece table; a regular
expression run as an automaton; a trie, a Bloom filter and edit distance;
two diffs and patch; a build order from a graph; breadth-first search,
Dijkstra and A*; and Huffman codes and LZ77 in a compressor. Each tool was
written the obvious way first, then the better way, and measured. In this
module they work together: deflate stores the objects, merge sort orders
the paths add finds, the heap and the table walk the history, and diff
compares what changed, in a git that the real one reads and checks. What
it leaves out, packs, merging and checkout among it, is where to go next,
and the material below covers it.

- [git diff](https://git-scm.com/docs/git-diff) - `--minimal`,
  `--no-renames`, `diff.renames` (true by default), and `myers`, "the
  basic greedy diff algorithm. Currently, this is the default."
- [git merge-base](https://git-scm.com/docs/git-merge-base) - the
  definition of a best common ancestor that `paint()` follows, the
  drawing of a merge base on two lines of history, and under DISCUSSION
  the criss-cross merge with two merge bases, which `--all` prints.
- [James Coglan, The Myers diff algorithm: part 1](https://blog.jcoglan.com/2017/02/12/the-myers-diff-algorithm-part-1/) -
  the start of a series on "the default diff algorithm used by Git", the
  search `show_change()` runs on each changed file.
- [Building Git](https://shop.jcoglan.com/building-git/) by James Coglan -
