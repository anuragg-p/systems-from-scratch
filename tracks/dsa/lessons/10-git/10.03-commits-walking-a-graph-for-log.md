# 10.03 Commits: walking a graph for log

A **commit** is a small text object: the name of a tree, the names of the
commits it was made on top of, who made it and when, and a message. This
lesson writes commits, branches and `log`, which walks the history back
from a commit and prints every commit once, newest first, with 02.04's heap
and 01.02's hash table doing the walking.

## Where this fits

![Where 10.03 fits](figures/10.03-map.svg)

This is the third box in git's strip, and the end of the heap rail: the
ring in git's column is 02.04's heap, which is log's queue of commits
still to print, ordered by date. log also keeps the names of the commits
it has met in 01.02's hash table, with the FNV-1a and the doubling of
01.03. A commit points at one top tree of 10.02, and like everything else
it is an object of 10.01. After this lesson bin/git commits, keeps
branches, and prints a history that the real git prints byte for byte the
same; 10.04 then compares two commits and finds where two branches split.

## The idea

![log of the merge: each frame takes the newest commit off the heap and prints it, and pushes its parents unless the table of names seen already has them.](figures/10.03-log.svg)

`cat-file -p` of the first commit Run it makes shows all of it:

<!-- verify: skip reason="the commit Run it makes, printed there by cat-file -p HEAD; shown here before Run it" -->
```
tree dcd498446ac96829dc31ffa4625d0c6bafd91ef4
author A U Thor <author@example.com> 1700000000 +0000
committer C O Mitter <committer@example.com> 1700000000 +0000

first
```

The first commit has no parent line; every later one has one, and a
**merge** has two. A **branch** is a file, .git/refs/heads/main, holding a
commit's name, and HEAD says which branch is in use. Committing writes a
commit whose parent is the branch's commit, then moves the branch to it.
So each commit points back at its parents, never forward at its children:
the history is a graph, a set of commits joined by arrows that all
point back in time, and the only ways into it are the newest commits.

The job of `log` is to start at one commit and print every commit it can
reach, each once, newest first. A walk has to remember two things. The
commits it has found but not printed yet: its queue, from which it
takes the newest each time. And the commits it has found already, so that
a commit two paths lead to, like the one a branch started from, is queued
and printed once.

The obvious way keeps both as plain lists: search the queue end to end for
the newest commit, and search the list of names seen from the start before
queueing a parent. On a line of n commits each new parent is compared with
every name before it, n(n-1)/2 comparisons in all: 8 billion for 128,000
commits. The better way keeps the queue in a heap ordered by the
committer's date, so the newest is always on top and taking it costs a few
comparisons, and the names seen in a hash table, so a lookup costs about
one probe. The figure walks the five commits of Run it that way.

### `commit_read` and `commit_create`

`commit_read()` parses a commit, checking each part: the tree line first,
then the parent lines, the author and the committer with its date, a blank
line and the message. `commit_create()` writes one: the author and committer
come from the GIT_AUTHOR_ and GIT_COMMITTER_ variables (or `.git/config`),
and the message is cleaned as `git commit -m` cleans it.

### `ref_read`, `ref_write` and `rev_parse`

`ref_read()` follows "ref: refs/heads/main" in HEAD to the branch's file and
reads the name there. `ref_write()` replaces a branch's file through a lock
file renamed over it. `rev_parse()` turns what a person types into a name:
the start of an object's name, HEAD, a branch, and after any of them ~N
(the Nth first parent), ^N (the Nth parent) and ^{tree}.

### `walk_heap` and `walk_list`

log's two ways, picked by `--algo=heap`, the default, or `--algo=list`.
`walk_heap()` pops the newest commit off 02.04's heap, prints it, and for
each parent asks 01.02's table whether it has been seen; a new one goes
into the table and onto the heap. `walk_list()` does the same with two
growable arrays, scanned end to end. The command line also gains
commit-tree, commit and branch.

The list of names seen made 127,992,000 comparisons, which is exactly
16000 x 15999 / 2; the table made 23,392 probes. Yet the clock moves by a
quarter, 0.48 seconds against 0.37: most of the time is reading the
commits, about 23 microseconds each to open, inflate and hash, and both
ways read all 16,000. The comparisons grow as n squared and the reading as
n, so the gap opens with length. On 128,000 commits, measured once each on
this machine (an Apple M4 Pro; your times will differ, the counts will
not), the lists take 12.2 seconds, the heap and the table 3.4, and the real
git 3.7. Writing that history took gen.py 46 seconds, which is why it is
not in the block.

## How it works

### Why the newest first is right across a merge

A commit is made after its parents, so, with clocks that are right, every
commit is newer than all of its ancestors. While log walks, every commit it
can reach and has not printed is either on the heap or has a descendant on
the heap: it was reached by a path from the start, and the first unprinted
commit on that path was pushed when the one before it was printed. A
descendant is newer, so the newest commit on the heap is the newest of all
those not printed yet. Taking it each time prints the whole history in
date order, across any number of branches.

A plain first-in, first-out queue would not. On the figure's history it
holds third and side after the merge, prints third, queues second behind
side, and prints side before second: merge, third, side, second, first.
The heap gives merge, third, second, side, first, which is the real git's
order. Clocks are not always right: a commit whose date is older than its
parent's can come out after it. The real git's plain log has the same
weakness, and its `--date-order` and `--topo-order` forbid a parent before
its children at the cost of more work; this git has neither.

### The invariant: a commit goes onto the heap once

A parent is put in the table before it is pushed, and pushed only if the
table did not have it:

```
            if (table_get(&seen, p, 20) != NULL) {
```

So each commit is read once, pushed once and printed once, and the heap
holds no more commits than there are lines of history open at once: here
two, on a long line one. Ties are settled too. Two commits from the same
second come out in the order they were met, by a sequence number, which is
the real git's order for a plain log:

```
    return x->seq < y->seq ? -1 : x->seq > y->seq;
```

### When the heap itself matters

On a single line the heap never holds two commits, and its 16,000 pops
cost no comparisons at all: there the table did all the work. The heap
earns its place when many lines run at once. gen.py's `wide` shape makes
16 branches whose dates interleave, joined by one merge; on 6,400 commits
of it the list was scanned 95,895 times to find the newest, and the heap
made 44,794 comparisons, about 7 per commit where the list looks at 15.

## Break it

Forget the commits already seen. In
`build/at/dsa/10.03/tools/git/commit.c`, in `walk_heap()`, change

```
            if (table_get(&seen, p, 20) != NULL) {
```

to

<!-- verify: patch file=tools/git/commit.c
-            if (table_get(&seen, p, 20) != NULL) {
@block
-->
```
            if (0) {
```

and build and log the merge again:

```
$ make -s
$ bin/git -C "$repo" log --oneline merged
b2a7015 Merge side
f59a714 third
04edf9e second
4e71d40 on a side branch
4531ec6 first
4531ec6 first
$ git -C "$repo" log --oneline --no-decorate merged
b2a7015 Merge side
f59a714 third
04edf9e second
4e71d40 on a side branch
4531ec6 first
```

first is the parent of both second and the side branch's commit, so both
pushed it, and it is printed twice. On this history that is one line too
many. Without the table a commit is printed once for every path that
leads to it, and each merge can double the number of paths to everything
below it: on a real history with many merges, the old commits would be
printed over and over. Put
the line back.
