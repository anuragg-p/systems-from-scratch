# 10.02 Trees and the index: a directory as a hash

A blob names one file's bytes. A **tree** names a whole directory: it is an
object that lists the directory's entries, each a mode, a name and the name
of another object. This lesson writes the **index**, the sorted list of
files the next commit will hold, `add` to fill it, and `write-tree` to turn
it into trees, building again only the trees whose files changed.

## Where this fits

![Where 10.02 fits](figures/10.02-map.svg)

This is the second box in git's strip, and the end of the sorting rail: the
ring in git's column is 02.02's merge sort, which puts in order the paths
add finds on disk before it merges them into the index, two sorted lists in
one pass. Every tree is an object of 10.01, named by SHA-1 and stored with
deflate, and the index lives in 01.01's growable arrays. Above it, the
commits of 10.03 each point at one top tree, and 10.04's diff walks two of
them. After this lesson one name stands for a whole directory, and the real
git's ls-files and write-tree agree with this git on the index it wrote.

## The idea

![d/e/f.txt changed: add forgets the cached trees above it, then write-tree builds d/e, d and the top again, bottom up, each with a new name, while b is taken from the cache.](figures/10.02-trees.svg)

A commit has to record every file of a project, in every directory, and it
should be able to do it with one name. 10.01 already names each file's
bytes, as a blob. git names a directory the same way: a tree object holds,
for each entry, its mode in octal (100644 for a file, 100755 for an
executable, 40000 for a directory), a space, its name, a NUL, and the 20
bytes of the entry's object. A subdirectory is an entry whose object is
the subdirectory's own tree. So the top directory's tree, by its name,
stands for every file below it.

Between the files on disk and the trees, git keeps the index, the file
.git/index. It has one entry per file, sorted by path: the path, the mode,
the blob's name, and what `stat()` said of the file when it was added.
`git add` hashes files into blobs and puts them in the index;
`git write-tree` builds the trees of whatever the index holds, bottom up,
since a tree cannot be named before the trees inside it are.

The obvious write-tree builds every tree every time. Most of them have not
changed: in a project of 64,000 files where one file changed, only the
trees of the directories on that file's path can be different. So the index
also keeps **cached trees** (git calls the extension TREE): for each
directory, how many index entries are under it and the name of the tree it
made last time. When an entry changes, add forgets the cached tree of every
directory above it, and write-tree builds only the ones forgotten. The
figure follows one change, to d/e/f.txt.

### `index_read` and `index_write`

The index file in git's version 2 format: "DIRC", the version and the
number of entries; each entry's 62 bytes of stat data, blob and flags, then
its path, padded with NULs to a multiple of 8 bytes; then extensions, of
which this git writes TREE, the cached trees; and last the SHA-1 of
everything before it. `index_read()` checks all of it, entry by entry, and
reads version 3 too. An extension it does not know is skipped if its name
starts with a capital letter, as the format allows, and refused if not.

### `index_add`

`git add`: walk the directories named, collect the paths of the files
found, sort them with 02.02's `sort_merge()`, and then merge two sorted
lists, the index and the files found. A file found is hashed and stored
(10.01's `object_write()`); an index entry whose file is gone is dropped;
and every entry added, changed or dropped forgets the cached trees above
it.

### `tree_cmp`, `tree_entries` and `build`

`tree_cmp()` is git's order of tree entries, which How it works comes back
to. `tree_entries()` reads a tree object and checks it: a mode git writes,
a name with no '/' that is not "." or "..", 20 bytes, and every entry in
git's order. `build()` makes one directory's tree from the index entries
under it: they are next to each other in the index, and so are each
subdirectory's, so it builds those first, recursively, then its own; with
the cache it takes a directory whose cached tree is still good as it is.
write-tree's `--algo=all` keeps the obvious way, every tree built.

## How it works

### git's order, found by trying it

The entries of a tree must be in order: the real git's fsck calls a tree
out of order an error (treeNotSorted). But git's documentation never says
which order. It is not plain byte order. Making "b c" and b/c with the real
git and reading its tree shows "b c" first, which plain byte order would
not do, since "b" is shorter than "b c". The rule that fits is: compare
the names' bytes, but count a directory's name as if it ended in '/'. "b
c" is "b" then a space (0x20), and the directory b compares as "b/"
(0x2f), so "b c" comes first. `tree_cmp()` is that rule:

```
    int ca = alen > n ? (unsigned char)a[n] : adir ? '/' : 0;
```

The index needs no such rule. It is sorted by the bytes of whole paths
(gitformat-index: "no special casing of directory separator '/'"), and a
whole path already has its '/': "b c" against "b/c" is a space against a
'/'. So the index's order is git's tree order, and `build()` never sorts;
it only checks each entry against the one before, and dies if the index is
out of order.

### Why one change renames every tree above it, and nothing else

A tree's bytes hold its entries' names, and its own name is the SHA-1 of
those bytes. Change d/e/f.txt and its blob has a new name; d/e's tree lists
that name, so d/e's bytes change and so does its name; d's tree lists d/e's
name, and so on to the top. A tree none of whose entries changed has the
same bytes as before, so the same name: b's here, and every blob but
f.txt's. That is a **Merkle tree**: a tree of hashes in which each node's
name covers everything below it. It works the other way too. Two trees with
the same name hold the same files with the same bytes all the way down,
which is what 10.04's diff stands on.

### The invariant: a cached tree is good only while nothing under it changed

`cache_invalidate()` runs for every entry added, changed or dropped, and
marks the cached tree of the top and of each directory on the entry's path
with -1. `build()` trusts a cached tree only when it has not been marked,
when it covers as many index entries as are there now, and when its object
is still in the repository:

```
    if (use_cache && ct->count >= 0 && (size_t)ct->count == hi - lo && object_exists(ct->oid)) {
```

### Why the clock does not follow the counts

At 64,000 files the cache builds 1,400 times fewer trees, and saves about
a quarter of the time. Both ways read the whole index, 64,000 entries and
5.9 MB, check its SHA-1, and write it all back with a new one; a
write-tree with nothing to build still took about 0.06 seconds. Building
8585 small trees that are all stored already is the smaller part: each is
hashed, found to be there, and never compressed or written. The cache pays
more when the trees are new and each must be deflated and written, and the
real git also reads it to compare the index with the last commit without
opening any tree. Break it shows what that trust costs when the cache is
wrong.

marked, so write-tree hands back the old top tree, ccb8ad7, without
building anything, and the real git, which reads the same cache, does the
same. Only the obvious way, which trusts nothing, finds the tree the index
really describes. A commit made now would record the old files. A cache
that is not forgotten when what it describes changes lies to everyone who
trusts it. Put the line back.

## Go deeper

- [gitformat-index](https://git-scm.com/docs/gitformat-index) - the index
  as `index_read()` reads it: the 12-byte header, entries "sorted in
  ascending order on the name field ... no special casing of directory
  separator '/'", the padding to a multiple of eight bytes, the rule that
  an extension whose name starts with 'A' to 'Z' may be ignored, and under
  "Cache tree" the TREE extension: entry count, subtree count, the name,
  and -1 for a tree that is gone.
- [Pro Git, 10.2 Git Internals - Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) -
  the section "Tree Objects": the entries `cat-file -p` prints, the modes,
  and a tree built by hand with update-index and write-tree.
- [git fsck](https://git-scm.com/docs/git-fsck) - the list of FSCK
  MESSAGES: treeNotSorted is an error, a "." or ".." name and a
  zero-padded mode are warnings; `tree_entries()` refuses all of them.
- [Building Git](https://shop.jcoglan.com/building-git/) by James Coglan -
  a book that rebuilds git in a high-level language, the index and the
  Merkle-tree-based commit model included.
