# 10.01 Objects: a hash is a name

git keeps every version of every file as an **object**, named by the SHA-1
hash of its bytes and stored, compressed, under that name. This lesson
writes SHA-1, the zlib format around module 09's DEFLATE, and the store of
objects, all in git's own format: the real git reads what this git writes,
and this git reads what the real git writes.

## Where this fits

![Where 10.01 fits](figures/10.01-map.svg)

This is the first box in git's strip, and the end of the deflate rail: the
ring in git's column is module 09's deflate (09.04) and inflate (09.02),
used again to store every object compressed. Around them it adds two
pieces of its own to the library: SHA-1, which names an object, and the
zlib format, two bytes in front of the DEFLATE data and a checksum behind.
Every buffer is 01.01's growable array. Everything git keeps later is an
object too: a directory in 10.02, a commit in 10.03. After this lesson
bin/git makes a repository, stores a file's bytes, and finds them by name.

## The idea

![hello.txt as a blob: the header and the file's 6 bytes, the name they hash to, the path that name gives, and the 21 bytes stored there: the zlib header, one fixed DEFLATE block and the Adler-32.](figures/10.01-object.svg)

A version control system keeps every version of every file, so it needs a
name for each version: where to put it, and how to find it again. Numbers
handed out in order say nothing about the bytes: two people who save the
same file get two numbers and two copies, and nothing in a number tells
whether the bytes behind it are still the ones that were saved.

git names a version by its content instead. The bytes go behind a short
**header**: the type of the object, a space, the size in decimal, and a NUL
byte. A file's bytes make a **blob**, so a file holding "hello" and a
newline is the 13 bytes `blob 6`, NUL, `hello`, newline. The object's name
is the **SHA-1** of those 13 bytes. SHA-1 is a **hash function**: it turns
any number of bytes into 20 bytes, the same 20 for the same input on every
machine, and in practice different ones for any other input. Written in
hexadecimal the name is 40 digits, ce013625... in full in the figure. The
object is compressed and stored in the file .git/objects/ce/013625...: the
first two digits name a directory, the other 38 the file.

That one rule gives three things that numbers cannot. The same bytes get
the same name wherever and whenever they are saved, so they are stored
once: writing them again finds the file there and stops. Different bytes
get a different name, so an object is never overwritten; a change is a new
object. And a name can be checked: inflate the file, hash what comes out,
and compare it with the name the file is stored under.

There is no slow version of this lesson to set beside a fast one. Naming
by hash and storing by name is the obvious way, and its cost is one pass of
SHA-1 and one of deflate over the bytes.

### `compress`, `sha1_update` and `sha1_final`

SHA-1, written from FIPS 180-4. `sha1_update()` takes bytes in pieces of
any size and runs `compress()` on each 64-byte block as soon as it is whole.
`compress()` stretches the block's 16 words to 80 and mixes them into a
state of five 32-bit words, in 80 rounds with four functions and four
constants. `sha1_final()` pads the last block: a 1 bit, zeros, and the
length of the input in bits as the last 8 bytes. The five words, written
big-endian, are the 20 bytes of the name.

### `zframe_adler32`, `zframe_pack` and `zframe_unpack`

The zlib format of RFC 1950, around the raw DEFLATE of module 09.
`zframe_pack()` writes two header bytes, 78 01: DEFLATE with a 32 KB
window, made at the fastest level, with five check bits that make the pair
a multiple of 31. Then the DEFLATE data, from 09.04's `deflate_raw()` with
gzip -1's short search, and last the **Adler-32** of the bytes before
compression: two running sums kept modulo 65521. `zframe_unpack()` checks
the header, inflates with 09.02's `inflate_raw()`, and checks the sum.

### `object_name`, `object_write` and `object_read`

`object_name()` hashes the header and the bytes. `object_write()` names an
object and stops if its file is there already; otherwise it compresses the
header and the bytes, writes them to a temporary file in the object's
directory, makes it read-only, and renames it into place. `object_read()`
reads the file, inflates it, checks the type and the size in its header,
and hashes the bytes again: an object whose bytes are not its name is
damaged, and said to be.

### `repo_init`

`repo_init()` makes `.git` with its objects and refs directories, a HEAD
that names the branch main, and a config. The rest of repo.c finds the
repository and reads that config, as How it works describes.

### `cmd_hash_object` and `cmd_cat_file`

The commands, in git.c. `cmd_hash_object()` is
`git hash-object`: a file's name as a blob, and with `-w` the blob stored.
`cmd_cat_file()` is `git cat-file`: an object's type (`-t`), size (`-s`)
or content (`-p`), given its name or the first 4 or more digits of it.

## How it works

### Why a hash can be a name

SHA-1 has 2^160 possible outputs. If it spreads inputs evenly over them,
two different inputs share a name by accident with odds that do not
matter: among a billion objects, the chance that any two collide is about
n^2 / 2^161, under one in 10^30. So git uses the name alone to say "these
bytes", and never compares the bytes themselves. The danger is a collision
made on purpose: in 2017 the SHAttered attack made one, and since version
2.13 the real git uses a hardened SHA-1 that detects it. This one is FIPS
180-4 as written, without that check; git's own plan is to move to
SHA-256. Only the hash would change, not the idea.

### The invariant: a file's bytes are its name

Everything in the repository depends on one invariant: the bytes in
.git/objects/xx/yyyy... hash to xxyyyy.... `object_write()` keeps it by
writing only under the name it has just computed, through a temporary file
renamed into place, so a reader sees no object or a whole one, never half
of one. `object_read()` does not trust it: after inflating, it hashes the
bytes again and refuses the object if they disagree:

```
    if (memcmp(real, name, 20) != 0) {
```

That one comparison catches a damaged disk, a file copied to the wrong
name, and, as Break it shows, a SHA-1 that computes the wrong thing. The
zlib wrapper's own checks, the header's multiple of 31 and the Adler-32,
are a second line behind it: DEFLATE itself carries no check at all.

### What this git leaves out, and where it differs on purpose

This git is a learner's program that runs next to repositories that
matter, among them this course's own checkout. So it differs from the
real one in four ways, each on purpose, so that no mistake in it or in an
experiment can reach a repository you care about. It looks for `.git`
only in the directory it is given, never above, as Run it showed. It
refuses a repository whose objects are packed or named with SHA-256, with
an ordinary error: it reads only loose SHA-1 objects. It writes only to
repositories its own `init` made, which say `[dsa] ours = true` in
`.git/config`; it reads any. And it reads no settings but `.git/config`,
so your own git's name and settings never enter a commit.

It is also a core, not the whole of git. Over this module it gains init,
hash-object, cat-file, add, ls-files, write-tree, ls-tree, commit-tree,
commit, branch, log, diff and merge-base. There is no checkout, merge,
status, tag or reflog, no packs, no .gitignore (add takes every file but
`.git`), and diff does not look for renamed files. What is missing is an
ordinary error or simply absent, never a crash.

## Break it

Make SHA-1 count the length in bytes, not bits. In
`build/at/dsa/10.01/lib/sha1sum.c`, in `sha1_final()`, change

```
    uint64_t bits = s->len * 8;
```

to

<!-- verify: patch file=lib/sha1sum.c
-    uint64_t bits = s->len * 8;
@block
-->
```
    uint64_t bits = s->len;
```

and build, then store hello.txt again in the same repository:

<!-- verify: session needs=git -->
```
$ make -s
$ bin/git -C "$repo" hash-object -w hello.txt
51f316d198afbc19f758d503a77ac81e8d36cadc
$ git -C "$repo" hash-object hello.txt
ce013625030ba8dba906f756967f9e9ca394464a
$ git -C "$repo" cat-file -p 51f316d
hello
$ bin/git -C "$repo" cat-file -p ce01362
git: object ce013625030ba8dba906f756967f9e9ca394464a is damaged: its bytes are the object 51f316d198afbc19f758d503a77ac81e8d36cadc
$ git -C "$repo" fsck --strict --no-progress
error: ce013625030ba8dba906f756967f9e9ca394464a: hash-path mismatch, found at: .git/objects/51/f316d198afbc19f758d503a77ac81e8d36cadc
notice: HEAD points to an unborn branch (main)
notice: No default references
dangling blob ce013625030ba8dba906f756967f9e9ca394464a
dangling blob 76c9be84fa6c2ca1fd8d80b5e0d694d99d42ef9a
$ echo $?
1
```

It is still a hash: the same bytes get the same name, 51f316d, every
time. But it is not SHA-1, so it is not the name anyone else computes. The
real git's cat-file reads the file at that path on trust; only fsck hashes
the bytes, and finds the hello blob filed under a name not its own. And
this git can no longer read the object it wrote before the change: its
check now computes the wrong name for good bytes. A name is only a name if
everyone computes it the same way. Put the line back.
