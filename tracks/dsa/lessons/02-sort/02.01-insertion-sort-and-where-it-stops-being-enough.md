# 02.01 Insertion sort, and where it stops being enough

The track's second tool is `sort`, which prints the lines of its input in
order, byte for byte the same as the system's sort. This lesson sorts the
obvious way, the way a hand of cards is sorted, and measures how big an
input it can take before it stops being usable.

## Where this fits

![Where 02.01 fits](figures/02.01-map.svg)

This lesson opens module 02's column of the map: the sort tool, and the
first box of the module's strip, insertion sort. Sorting is a rail of the
library, and its first dot is here, in sort's column: from now on any tool
that needs its data in order can ask the library for it. The ring on the
array's rail in the same column is sort keeping the lines it reads in the
growable array of 01.01. After this lesson the track can put any text file
in order, the same order the system's sort gives, as long as the file is
not too big; the rest of the module is about that limit.

## The idea

![Insertion sort on the first eight words of A Scandal in Bohemia: each line in turn slides left past the bigger lines before it](figures/02.01-insertion.svg)

Module 01 checked freq against a shell pipeline with two sorts in it:
`tr` cuts the text into words, one to a line, `sort` brings equal words
together so `uniq -c` can count them, and a second sort orders the counts.
This module writes that sort. Its rule is simple to state: every line of
the input, in byte order (the order of the system's sort with `LC_ALL=C`,
where `B` comes before `a`, and a line that is the start of another comes
first), nothing added or lost.

The obvious way to sort is how most people sort a hand of cards. Keep the
cards already sorted on the left. Take the next card, and slide it left
past every card bigger than it; it stops at the first card that is not
bigger, or at the front. Then the sorted part is one card longer. That is
**insertion sort**. The figure runs it on the first eight words of "A
Scandal in Bohemia", one to a line: `to sherlock holmes she is always the
woman`. Each step compares the new line with its neighbour on the left
until one is not bigger: "she" goes past "to" and "sherlock" and stops at
"holmes", three comparisons. The whole sort takes 18 comparisons.

### `sort_insertion`

The sorts of the library do not know what a line is. Each takes an array
of pointers, `v`, its length `n`, and a comparison function, a `Cmp`, that
says whether one item comes before another; `ctx` is passed to it
untouched. So the same sorts will order lines here, and anything else a
later tool can write a comparison for. Every call of the
comparison goes through `compare()`, which counts it: `DS_STATS=1` prints
that count, and it is the work the sort does. A **move** is one pointer
written into the array; the lines themselves never move.

### `compare_lines`

The sort tool comes whole but for this function: it reads every line into
an array (01.01's), handles `-r`, `-n`, `-u`, `-k` and `-t` as the system's
sort does, and writes the lines out. `compare_lines()` is the order it
hands to the library: by the keys (the whole line, without `-k`), then by
the whole line, byte by byte, when the keys are equal, as the system's sort
does as a last resort. With `-u` that last resort is skipped, so lines
with equal keys stay equal and only the first of them is printed.

## How it works

### The invariant

At the top of each pass of the outer loop, `v[0..i)` is in order; the
comment above the function says so. The pass takes `x = v[i]` out, moves
each bigger line one place right while it scans left, and writes `x` into
the gap with `v[j] = x;`. That line restores the **invariant** for
`v[0..i+1)`: everything left of `j` is not bigger than `x` (the scan
stopped there, or `j` is 0), and everything right of it was bigger and
kept its order. When `i` reaches `n`, the whole array is in order.

Holding `x` aside and shifting is cheaper than swapping it left one place
at a time: a swap writes two pointers, a shift writes one.

### Why the time goes as n squared

Each line is compared with the lines before it until one is not bigger.
For a line in a random place that is, on average, half of the lines
before it. Summed over all n lines that is about n times n / 4 comparisons:
for the 105885 words, n*n/4 is 2802908306, and the sort took 2771597506.
Already in order, each line stops at the first comparison: n - 1, 105884.
In reverse order, each line goes all the way to the front: n(n-1)/2.
The count of moves follows the comparisons, so the time does too.

This is what **grows as n squared** means: the cost of one more line is
proportional to the lines already there. Doubling the input doubles the
lines and doubles what each one costs, which is the ratio of 4 the harness
printed.

### Stable, and why `-u` needs it

The scan stops at the first line that is not bigger than `x`:

```
while (j > 0 && compare(&o, v[j - 1], x) > 0) {
```

A line equal to `x` stops it, so equal lines never pass each other and
keep the order they came in. A sort with that property is **stable**. The
system's sort with `-u` prints the first line of each run of equal ones,
first in the input; with a stable sort that is simply the first of the run
in the sorted array, and `write_lines()` prints exactly that. (A sort that
is not stable gets the same result another way: `compare_lines()` then
adds the input order as a last tiebreak, through `by_index`. 02.03 and
02.04 bring sorts that need it.)

## Break it

Let equal lines pass each other. In `lib/sort.c`, in `sort_insertion()`,
change `> 0` to `>= 0` in the scan, and rebuild:

<!-- verify: patch file=lib/sort.c
-        while (j > 0 && compare(&o, v[j - 1], x) > 0) {
@block
-->

```
while (j > 0 && compare(&o, v[j - 1], x) >= 0) {
```

<!-- verify: session -->
```
$ make -s
$ printf 'b 1\na 2\nb 3\na 4\n' | bin/sort -u -k1,1
a 4
b 3
$ printf 'b 1\na 2\nb 3\na 4\n' | sort -u -k1,1
a 2
b 1
$ DS_STATS=1 bin/sort data/book.txt | cmp - <(sort data/book.txt) && echo same
stats: lines: read 11922, peak bytes 848532
stats: array: pushes 11922, grows 12, moves 16376
stats: sort: comparisons 37017961, moves 37020571
same
```

With `-k1,1` the lines `a 2` and `a 4` have equal keys. Each `a` line now
slides past the `a` before it, so the last one of the input ends up first
and `-u` keeps it. The system's sort keeps the first. The book still sorts
to the same bytes, because without `-k` equal lines are identical and no
one can tell which came first; it only costs more, 37017961 comparisons
against 33615695, since every run of equal lines (2610 empty lines among
them) is now walked to its start. Put `> 0` back.

## Go deeper

- [Algorithms, 4th edition, 2.1 Elementary Sorts](https://algs4.cs.princeton.edu/21elementary/) by Sedgewick and Wayne - insertion sort's counts on the page: about N^2/4 compares on average, N-1 at best, about N^2/2 at worst, and the exchanges equal to the number of inversions; and why it does well on partially sorted arrays, as `sorted.txt` showed.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th edition, chapter 2, sections 2.1 and 2.2 - insertion sort proved correct with a loop invariant, the same one as above, and its best and worst cases worked out.
- Knuth, *The Art of Computer Programming*, volume 3, section 5.2.1, Sorting by Insertion - the method and its exact average, and the ideas for making the insertion cheaper.
- [toybox's sort.c](https://github.com/landley/toybox/blob/master/toys/posix/sort.c) - a small real sort to read beside this one: it reads every line into an array of pointers and calls the C library's `qsort()` with its own key comparison, with the same whole-line last resort.
