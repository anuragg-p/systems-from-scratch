# 02.03 Quicksort, and the input that breaks it

Quicksort sorts inside the one array, with no second array to merge
through, and on most inputs it is as fast as merge sort. Written the
obvious way, it has inputs that make it as slow as insertion sort, and one
of them is a file already in order. This lesson finds them, then fixes the
sort so that no input is its worst case.

## Where this fits

![Where 02.03 fits](figures/02.03-map.svg)

This lesson is the third box of module 02's strip, quicksort, on the
sorting rail in sort's column. The library gets two more sorts with the
same arguments as the first two: the obvious quicksort and the one that
fixes it. The sort tool lists both, as `--algo=quick-first` and
`--algo=quick`, and keeps merge sort as its default, so its output does
not change. After this lesson the track can sort in place, and knows
what one well-chosen input can do to a sort.

## The idea

![Quicksort with the first line as the pivot: one partition of the eight lines, then the same lines already in order, where every pass takes one line off](figures/02.03-partition.svg)

Merge sort needs `aux`, a second array as long as the one it sorts. Sorting
inside the array itself means moving lines only by swapping them. The
classic way, behind the C library's `qsort()` in the systems McIlroy
tested (Go deeper), is **quicksort**:

1. Pick one line, the **pivot**.
2. **Partition**: swap the lines around so that every line smaller than
   the pivot is on its left, and every other line on its right. The pivot
   is then in the place it will have in the sorted output, for good.
3. Sort the left side and the right side the same way.

There is no merge: once each side is sorted, the whole range is. The first
frame of the figure is one partition of 02.01's eight lines with the
obvious pivot, the first line, `to`. Seven comparisons, one with each other
line; six are smaller, `woman` is not, and `to` swaps into place 6.

How fast that is depends on where the pivot lands. In the middle, each
side is half the range, and the halving gives log2(n) levels of about n
comparisons each, as in merge sort. At an end, one side is empty and the
other has every line but the pivot: a pass of n comparisons has taken one
line off. The rest of the figure is the same eight lines already in order.
Every pivot is the smallest line left, every pass takes one line off, and
the passes cost 7 + 6 + ... + 1 = 28 comparisons, more than insertion
sort's 18 on the lines as read. On a hundred thousand lines that is five
billion.

### `quick_first`

The obvious quicksort. The scan keeps `v[lo+1..m]` for the lines smaller
than the pivot: each smaller line found is swapped to `++m`. At the end the
pivot at `lo` swaps with `v[m]`, the last smaller line. Instead of calling
itself for both sides, it calls itself for the smaller side and goes round
its loop for the larger one. `sort_quick_first()` is its entry point.

### `quick3`

The fix, in two parts. The pivot is a line chosen at random from the range,
swapped to the front first, with `below()`, a small random number
generator; so no particular order of the input lines up the pivots badly.
And the partition splits three ways, keeping the lines equal to the pivot
in the middle (`v[lt..i)`), where they are done with; only the smaller
and the bigger lines go on to the next passes. `sort_quick()` is its entry
point. `swap()` exchanges two pointers and counts the two moves.

## How it works

### The partition's invariant

In `quick_first()`, while `i` scans the range, `v[lo+1..m]` holds the lines
smaller than the pivot and `v[m+1..i)` the others:

```
for (size_t i = lo + 1; i < hi; i++)
    if (compare(o, v[i], pivot) < 0)
        swap(v, ++m, i);
swap(v, lo, m);
```

A smaller line found at `i` swaps with the first of the others, at `m+1`,
which grows the smaller part by one and moves that other line to the end
of the others. When the scan ends, the pivot swaps with `v[m]`: the smaller
lines stay on its left, and the pivot is in its final place. The test is
`< 0`, so a line equal to the pivot counts as "not smaller" and goes right.
That is the whole problem with equal lines.

### Three ways, and the pivot at random

`quick3()` keeps three parts as it scans: `v[lo..lt)` smaller than the
pivot, `v[lt..i)` equal to it, `v[gt..hi)` bigger, and `v[i..gt)` not
looked at yet. Each comparison moves one line into its part, and the next
passes work only on the smaller and bigger parts. On a file of 20000
copies of one line that is one pass: 19999 comparisons, where the first
quicksort makes 199990000.

The random pivot answers the sorted file. With the first line as the
pivot, one common order of input, sorted, gets the worst pivot at every
pass. With a pivot chosen at random, no order does: each pass is as likely
to split near the middle as anywhere, and the expected count is about
2n ln n comparisons, 1.39 n log2(n), on any input, fewer when lines
repeat. Bad luck is still possible, as a run of bad dice is; a bad input
no longer is. The seed of `below()` is fixed, so a run makes the same
choices, and the same counts, every time.

### The stack stays shallow on any input

Both quicksorts call themselves only for the smaller side and loop on the
larger one. The smaller side is at most half the range, so the calls nest
at most log2(n) deep, 17 for these words. Had the obvious quicksort
called itself for both sides, it would nest 105885 deep on `sorted.txt`
and could run off the end of its stack. Here a bad input costs time,
never a crash.

A swap can carry a line past an equal one, so neither quicksort is
**stable**; `-u` still keeps the first of equal lines, because for these
sorts `compare_lines()` breaks ties by input order (02.01).

## Decide the boundary

This sort picks its pivot with a random number generator whose seed is
fixed, so that its counts are the same on every run. The price is that its
"random" pivots are the same for the same input, and an input can be built
to defeat them. McIlroy's paper shows how: a comparison function that
decides the lines' values only as the sort asks about them, always so that
the pivot is low. His adversary, the paper's appendix, run against this
library's `sort_quick()` on 20000 lines, built a file that costs it
199939942 comparisons every time it is sorted. The same 20000 lines,
shuffled, cost 349762.

A seed taken from the clock or the system's random source at each run
would make a file built that way harmless the next time, and cost
repeatable counts. Other sorts give up on quicksort past a depth and switch
to a sort with a guarantee, such as the heapsort of the next lesson. Does
your sort see input from people who might want it to be slow?

## Break it

Keep the three-way split, but take the first line as the pivot again. In
`lib/sort.c`, in `quick3()`, delete the line that swaps a random line to
the front, rebuild, and time sorted lines again (`--limit 30`, so that a
slower machine prints every row too):

```
        swap(v, lo, lo + below(seed, hi - lo));     <- delete this line
```

## Go deeper

- [A Killer Adversary for Quicksort](https://www.cs.dartmouth.edu/~doug/mdmspe.pdf) by M. D. McIlroy, Software: Practice and Experience, 1999 - four pages: the adversary, why it works against "any implementation of quicksort - even a randomizing one" that it can supply the comparison to, and its 20-line appendix, the code run above.
- [Algorithms, 4th edition, 2.3 Quicksort](https://algs4.cs.princeton.edu/23quicksort/) by Sedgewick and Wayne - the partition, the ~2 N ln N average and ~N^2/2 worst case, the random shuffle that protects against it, and 3-way partitioning (Dijkstra's Dutch national flag) for equal keys.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th edition, chapter 7, Quicksort - the analysis of the worst and expected cases, and section 7.3, the randomized version.
- Knuth, *The Art of Computer Programming*, volume 3, section 5.2.2, Sorting by Exchanging - quicksort's history and its exact average counts.
