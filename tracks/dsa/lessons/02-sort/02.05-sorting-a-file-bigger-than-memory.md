# 02.05 Sorting a file bigger than memory

Every sort so far holds all the lines in memory at once, so the biggest
file it can sort is the memory it has. With `-S`, sort holds no more than
a set number of bytes: it sorts what fits, writes it to a file as a sorted
run, and at the end merges the runs through a heap. The output is the same
bytes.

## Where this fits

![Where 02.05 fits](figures/02.05-map.svg)

This lesson is the sorted-runs box of module 02's strip, and it is all in
the sort tool's own column: it uses two pieces the library already has
there, the sorting rail for each run and 02.04's heap rail for the merge.
Nothing changes in the library. sort gains `-S`, the most memory it may
hold, and `-T`, the directory its runs go in, both as the system's sort
has them. After this lesson the size of a file sort can handle is set by
the disk, not by memory.

## The idea

![sort -S 100b on the eight lines: three sorted runs written out, then a heap with one entry per run merges them, one line out per pop](figures/02.05-runs.svg)

sort reads every line into an array and then sorts the array. For a file
of 2.4 MB that means 4.8 MB in memory, by sort's own count: each line is
held as its bytes, a NUL, a 16-byte header, and an 8-byte pointer in the
array. A file of 20 GB of lines like these would need about 40 GB. On a laptop with 16 GB the obvious sort never
finishes: it runs the machine out of memory, or into swapping so slow it
might as well have.

The way out is to sort it in pieces. Read lines until the memory allowed
is full; sort them (merge sort, as before) and write them to a file of
their own, a **run**, already in order; let them go and read on. At the
end there are a few dozen sorted files instead of one unsorted one, and
02.02 already knows how to combine sorted lists: merge them. Merging needs
only the front line of each run in memory, however long the runs are.

Merging two runs compares two front lines. Merging sixteen means finding
the smallest of sixteen front lines, again and again, which is exactly
the job of 02.04's heap: keep one entry per run, ordered by its front
line; pop the run with the smallest, write that line, read the run's next
line, and push the run back. Each line out costs a pop and a push, a few
comparisons for each level of a heap that is five levels deep for sixteen
runs, and memory holds sixteen lines. The figure does it on the
eight lines of 02.01 with `-S 100b`, room for three of them at a time.

### `spill`

Called when the next line would take the bytes held past the cap: it
sorts the lines held, writes them to a new run file in the `-T`
directory, frees them, and sets `held` back to 0.

### `merge_runs`

Merges up to sixteen run files into one output through a heap of `Run`s,
each with its file and its next line. It unlinks each file as soon as it
has it open: the data stays readable through the open file, and the name
is gone; `remove_runs()`, run as sort exits, deletes any run not reached
yet. With `-u` it drops
a line equal to the last one written, as `write_lines()` does in memory.

### `merge_all`

While there are more than sixteen runs, it merges the first sixteen into
a new run, which takes their place at the front of the list, so runs stay
in input order. Then it merges what is left straight to the output.
Sixteen at a time is `MERGE_WAYS`, the GNU sort's default batch too.

## How it works

### Two invariants, one in each half

While reading, `held` is the bytes of the lines in the array, and it
stays within the cap: before a line is added, the lines held are spilled
if the new one would take `held` past it. `spill()` keeps that true by
setting `held = 0;` after it lets the lines go. A line bigger than the
whole cap is still taken, alone (the `lines.len > 0` in the test), or it
could never be read.

While merging, the heap holds exactly one entry for each run that has
lines left, keyed by the run's next line. A pop takes the smallest of
those, which is the smallest line not yet written of all the runs,
because each run is in order. Pushing the run back with its next line
restores the invariant.

### Equal lines keep their order across runs

Runs are numbered in input order, and on a tie between two front lines
`run_cmp()` puts the earlier run first. Within a run equal lines are in
input order already (merge sort, the default, is stable; for a sort that
is not, 02.03 made the input order the last tiebreak), so equal lines come
out in the order they came in, and `-u` keeps the first
of them, as it does without `-S`. `merge_all()` puts each merged run at
the front of the list, where the runs it replaced were, for the same
reason.

### Why it grows faster than n log n

Each merge reads its runs from files and writes what it makes to another
file, or to the output. How many merges a line goes through is what the
heap's pushes count: one push per line per merge. At 256000 lines the cap
of 1 MB makes 12 runs, one merge, and 256000 pushes. At 2048000:

<!-- verify: session timeout=120 -->
```
$ python3 data/gen.py lines 2048000 > big.txt
$ DS_STATS=1 bin/sort -S 1M big.txt > /dev/null
stats: lines: read 2048000, peak bytes 1048576
stats: array: pushes 10962448, grows 31, moves 32928
stats: runs: written 96, merges 7
stats: sort: comparisons 26910352, moves 29622421
stats: heap: pushes 8914352, pops 8914352, comparisons 72703864, moves 64664402
```

96 runs and 7 merges, and 8914352 pushes: each line went through the
heap 4.35 times on average. `merge_all()` merges the first sixteen runs
into one at the front of the list, and the next merge takes that run in
again with the next fifteen, and so on down the list: the lines of the
first runs are read and written by all seven merges, those of the last
by one. With the memory fixed, more input means more runs, and every
extra sixteen runs adds a pass over everything merged so far. That is the
ratio near 3 at the top of the harness's table.

## Decide the boundary

This sort merges its runs as a chain: sixteen into one, then that one with
the next fifteen. It keeps the runs in input order with one list and one
loop, and the lines of the first runs go through every link of the
chain: 4.35 merges a line on average for 96 runs, more as the input
grows. Merging as a tree instead, every group of sixteen runs into a new
run, then every sixteen of those, and so on, puts each line through the
same number of merges, log16 of the runs rounded up: 2 for 96 runs, 3 up
to 4096 runs. It costs a second list of runs, kept in order, for each
round.

Knuth describes another lever, **replacement selection**: feed the run
being written from a heap, so that a line read that is not smaller than
the last one written can still join it. On input in random order its
runs come out about twice as long as memory, half as many. Is your data
bigger than memory by a little, or by a hundred times?

## Break it

Forget to say that memory is empty again. In `tools/sort/sort.c`, in
`spill()`, delete `held = 0;`, and rebuild. Use a smaller file, 10000
lines, and a cap of 64 KB:

```
    held = 0;     <- delete this line
```

Still the same bytes out, but 8628 runs and 576 merges, where the right
code writes 8 runs and merges them once. After the first run, `held`
stays above the cap for good, so every line is spilled as soon as it is
read: a run of one line, a file created, written, opened and unlinked for
each. On the 100000 lines of Run it the same mistake takes over two
minutes. A bug that never shows in the output, only in the time and in
the counts. Put the line back.

## Go deeper

- Knuth, *The Art of Computer Programming*, volume 3, section 5.4, External Sorting, and 5.4.1, Multiway Merging and Replacement Selection - merging k runs with a tree of the runs' front items, replacement selection, whose runs average twice the memory on random input, and the patterns of merging that the rest of 5.4 compares.
- [GNU coreutils manual, sort invocation](https://www.gnu.org/software/coreutils/manual/html_node/sort-invocation.html) - `-S` (1024-byte units unless a suffix says otherwise, `b` for bytes), `-T` and `TMPDIR` for where the temporary files go, and `--batch-size`, "Merge at most nmerge inputs at once", 16 by default.
- [Algorithms, 4th edition, 2.4 Priority Queues](https://algs4.cs.princeton.edu/24pq/) by Sedgewick and Wayne - Multiway, its client that merges several sorted input streams into one through an index priority queue, the merge of `merge_runs()`.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th edition, section 6.5, Priority queues - the operations `merge_runs()` uses: insert, and extract the minimum.
