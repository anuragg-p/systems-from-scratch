# 02.02 Merge sort

Two lists that are each in order can be combined into one in a single
pass. Merge sort is built on that: sort each half, then merge the halves.
It takes the book's words from thirteen seconds to three hundredths of
one.

## Where this fits

![Where 02.02 fits](figures/02.02-map.svg)

This lesson is the second box of module 02's strip, merge sort, on the
sorting rail that 02.01 started in sort's column. The library gets a
second way to sort, with the same arguments as the first, and the sort
tool makes it its default: the same lines in, the same comparison, the
same bytes out, only the order in which pairs of lines are compared
changes. Insertion sort stays, behind `--algo=insertion`, so the two can
be timed side by side. After this lesson sort keeps up with the system's
sort on millions of lines.

## The idea

![Merge sort on the same eight lines: runs of one merged into runs of two, then four, then all eight, in the order the code does them](figures/02.02-merges.svg)

At the end of 02.01, sorting the book's 105885 words took thirteen and a
half seconds and 2.8 billion comparisons, and the time grew four times
with each doubling of the input. Insertion sort's trouble is that a line
moves one place per comparison: a line that belongs a thousand places to
the left costs a thousand comparisons to get there.

Merging is the cheap step. Take two piles of cards, each already in
order, face up. The smaller of the two top cards is the smallest card of
all: take it, and look again at the two cards now on top. Every
comparison puts one card in its final place, so two piles of n cards in
all take at most n - 1 comparisons, and fewer when one pile runs out
first: the rest of the other is copied without looking.

**Merge sort** uses that step for the whole job. Split the lines into two
halves, sort each half the same way, and merge them. A half is sorted by
splitting it again, down to pieces of one line, which are in order by
themselves. The figure runs it on the eight lines of 02.01, in the order
the code does it: the left half all the way down and back before the right
half starts. Each row of the figure makes fewer comparisons than it has
lines, 4, 4 and 7, and there are three rows: 15 comparisons in all, where
insertion sort took 18. With eight lines the difference is small. With a
hundred thousand it is everything.

### `merge`

Merges `v[lo..mid)` and `v[mid..hi)`, each already in order, into
`v[lo..hi)`. It first copies the range into `aux`, a second array of the
same size, and merges from there back into `v`: the output can then
overwrite `v` freely, since the lines it reads are in `aux`. `i` walks the
left run and `j` the right; when one of them has run out, the rest comes
from the other with no comparison.

### `merge_sort`

The recursion: a range of fewer than two lines is done; otherwise sort the
left half, sort the right half, merge. `mid` is computed as
`lo + (hi - lo) / 2` rather than `(lo + hi) / 2`, which could overflow for
an array near the top of `size_t`.

### `sort_merge`

The entry point, with the same arguments as `sort_insertion()`: it
allocates `aux` once, for the whole sort, sorts, and frees it. The sort
tool's table of algorithms gets a `merge` row, and `merge` becomes the
default.

## How it works

### Why n log n

Look at the figure by rows. Every row merges runs that cover all n lines
once, and a merge costs at most one comparison per line it writes: each
row costs at most n comparisons. Each row's runs are twice as long as the
row above, so after log2(n) rows there is one run. For 105885 words that
is 17 rows (2 to the 17th is 131072), and at most 17 * 105885 = 1800045
comparisons; the sort took 1634788.

That is **n log n** growth: n log2(n). Doubling n doubles the rows' width
and adds one row, so the time grows a little more than twice: from 2048000
to 4096000 words, log2(n) goes from 21 to 22. The harness cannot tell that
apart from n, and says "about n". Insertion sort's n squared is different
in kind: one doubling, four times the work.

It is also about as well as any sort can do that only compares pairs of
lines. There are n! orders the input could be in, and each comparison
answers yes or no, so in the worst case a comparison sort needs at least
log2(n!) of them, which is about n log2(n).

### On a tie, the left line goes first

```
else if (compare(o, aux[j], aux[i]) < 0)
    v[k] = aux[j++];
else
    v[k] = aux[i++];
```

The right line is taken only when it is strictly smaller. When the two
are equal, the left one, which came earlier in the input, goes first. That
keeps every merge, and so the whole sort, **stable**: lines that compare
equal leave in the order they came, which is what `-u` relies on to print
the first of each run of equal lines (02.01).

### Input already in order is cheap, but not free

Merge `sorted.txt` again and each merge compares only until the left run
runs out, half the lines of each row:

<!-- verify: session -->
```
$ DS_STATS=1 bin/sort sorted.txt > /dev/null
stats: lines: read 105885, peak bytes 3078655
stats: array: pushes 105885, grows 15, moves 131064
stats: sort: comparisons 865998, moves 1774858
```

865998 comparisons, about half of 1634788. Insertion sort did this input
in 105884. Every merge still copies all its lines through `aux`, so the
moves are the same as before, 17 rows of about n each.

## Decide the boundary

Merge sort needs `aux`, a second array as long as the first. Here that is
8 bytes a line, next to the line itself and its header in memory (3078655
bytes for these 105885 words), so sort pays about a quarter more. A
library sort of a hundred million small items pays a second array of a
hundred million.

A sort can work in place, inside the one array, with a few variables
besides; the next lesson's quicksort does. It gives up stability, and, written
the obvious way, the guarantee: merge sort makes at most about n log2(n)
comparisons on any input at all. Does your sort need to be stable and
never slow, or to fit in the memory the data already takes?

## Break it

Take the right line on a tie. In `lib/sort.c`, in `merge()`, change
`< 0` to `<= 0`, and rebuild:

<!-- verify: patch file=lib/sort.c
-        else if (compare(o, aux[j], aux[i]) < 0)
@block
-->
```
else if (compare(o, aux[j], aux[i]) <= 0)
```

<!-- verify: session -->
```
$ make -s
$ printf 'b 1\na 2\nb 3\na 4\n' | bin/sort -u -k1,1
a 4
b 3
$ printf 'b 1\na 2\nb 3\na 4\n' | sort -u -k1,1
a 2
b 1
$ bin/sort words.txt | cmp - sorted.txt && echo same
same
```

The sort is no longer stable: of `a 2` and `a 4`, equal by the key, the
later one now comes out first, and `-u` keeps it, where the system's sort
keeps the first. On the words, where equal lines are identical, nothing
shows. It is the same failure as 02.01's Break it, from a different line
of a different sort: stability is a property of each comparison a sort
makes, and one wrong one is enough. Put `< 0` back.

## Go deeper

- [Algorithms, 4th edition, 2.2 Mergesort](https://algs4.cs.princeton.edu/22mergesort/) by Sedgewick and Wayne - the same top-down merge sort with an auxiliary array, the proof that it uses between 1/2 N lg N and N lg N compares, the bottom-up version without recursion, and the lower bound: no compare-based sort can guarantee fewer than lg(N!), about N lg N, compares.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th edition, section 2.3 (merge sort as divide and conquer, and its recurrence) and chapter 4 (solving such recurrences); section 8.1 for the lower bound on comparison sorts.
- Knuth, *The Art of Computer Programming*, volume 3, section 5.2.4, Sorting by Merging - merging from its origins, and the many ways of arranging the merges.
