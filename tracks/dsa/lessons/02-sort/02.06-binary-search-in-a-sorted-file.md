# 02.06 Binary search in a sorted file

A file in sorted order can be searched without reading it through: look at
the line in the middle, and it says which half the answer is in. This
lesson writes `look`, the Unix tool that prints the lines of a sorted file
that begin with a string, and finds a word among millions in a few dozen
reads.

## Where this fits

![Where 02.06 fits](figures/02.06-map.svg)

This lesson is the last box of module 02's strip, binary search, and it
adds the second tool of the module's column: look, next to sort. look
needs nothing from the library's sorting: it needs a file that is already
sorted, which is what sort makes. The two together are the module's point
about order: sort pays once, up front, and every search of the result
after that is cheap. After this lesson the track can find a line in a
sorted file of any size while reading only a few blocks of it.

## The idea

![look she on a sorted file of 24 lines: each probe looks at the line nearest the middle of the part the first match can be in, and keeps one half](figures/02.06-halving.svg)

`look Holm words.txt` prints every line of `words.txt` that begins with
`Holm`. If the file is sorted, those lines sit together, and the first of
them is the first line that is not smaller than `Holm` when only the
first four bytes of each line are compared. The obvious way to find it is
the way `grep` would: read from the top, a line at a time, until one is
not smaller. On a dictionary of a million words that reads, on average,
half the file.

A sorted file allows something better. Look at the line in the middle. If
it is smaller than `Holm`, the first match is after it, and the whole
first half can be forgotten; if not, the first match is that line or one
before it, and the second half can be forgotten. Each look halves the part
of the file the answer can be in, so a file of n lines takes about
log2(n) looks, a **probe** each: 20 for a million lines, 30 for a billion.
That is **binary search**.

A file is not an array of lines, though. Lines have different lengths, so
"the line in the middle" has no address. look works in bytes instead: it
keeps a range of offsets, `[lo, hi)`, takes the middle byte, and probes
the first line that starts after it. The figure runs it on 24 words from
"A Scandal in Bohemia", sorted, looking for `she`: four probes, then the
two lines that begin with it, `she` and `sherlock`.

### `find_scan`

The obvious way, kept as `--algo=scan`: from offset 0, read a line,
compare it, and go to the next, until a line is not smaller than the
string. It returns the offset of that line.

### `find_binary`

The same answer by halving, the default. `lo` and `hi` are byte offsets;
each probe reads the first line starting at or after the middle byte,
using `line_start()`, and moves `lo` past that line or `hi` down to it.
When no line starts between the middle and `hi`, it probes the line at
`lo` instead, which always makes progress. Around these two, look comes
whole: `byte_at()` reads the file through a buffer of one 4096-byte
block, with `pread()`, counting each block it has to read, as a disk
would; `line_at()` reads one line from an offset; and `main()` prints the
matching lines from the offset found, exiting 0 if it printed one and 1 if
not, as the system's look does.

## How it works

### The invariant, and the probe that always makes progress

`find_binary()` keeps one **invariant**, which the comment above it
states: every line that starts before `lo` is smaller than the string, and
the line at `hi`, if `hi` is not the end of the file, is not. At the start
both hold trivially, with `lo` = 0 and `hi` = the file's size. Each probe
keeps them:

```
if (compare(line, key, klen) < 0)
    lo = next;
else
    hi = at;
```

A smaller line moves `lo` past itself, to `next`, where the following line
starts; a line that is not smaller becomes the new `hi`. When `lo` reaches
`hi`, the line there is the first that is not smaller: the first match,
if there is one.

The probe has to land inside `[lo, hi)`, or the loop never ends.
`line_start()` of the middle byte can be `hi` itself, when the middle is
in the last line of the range; then the probe is the line at `lo`, which
is inside the range: `lo` is always the start of a line, 0 or a `next`.
Either way `lo` grows or `hi` shrinks.

### Comparing only as many bytes as the string

`compare()` looks at no more of the line than the string's length: a line
that begins with the string compares equal to it, and a line shorter than
the string and equal as far as it goes, such as `she` against `sherlock`,
is smaller. So all the lines that begin with the string form one run in
the sorted file, and the search finds its start.

### The file must be sorted the same way

The halving is only right if the file is in the order `compare()`
assumes: byte by byte, as `LC_ALL=C sort` writes it. In another order, a
probe that says "smaller" no longer says anything about the lines before
it, and look misses lines that are there, without any error. That is why
the lesson sorted `words.txt` in the C locale, and why the system's look
says in its manual that the file must be sorted.

## Decide the boundary

look searches a plain sorted text file: no index, nothing to build or
keep up to date but the order itself, and any prefix found in log2(n)
probes. The price is paid when the file changes: one new line means
writing it in its place, which moves everything after it, or sorting the
file again. A hash table, module 01's, finds an exact key in about one
probe and takes new keys cheaply, but cannot answer "every line that
begins with `Holm`": its order is the hash's, not the keys'. A B-tree, as
a database keeps on disk, does both, at the cost of a structure of its
own. Is your file written once and searched many times, and are the
searches by prefix or range, or only by exact key?

## Break it

Send the lines that match to the left as well as the smaller ones. In
`tools/look/look.c`, in `find_binary()`, change `< 0` to `<= 0`, and
rebuild:

<!-- verify: patch file=tools/look/look.c
-        if (compare(line, key, klen) < 0)
@block
-->
```
        if (compare(line, key, klen) <= 0)
```

<!-- verify: session -->
```
$ make -s
$ DS_STATS=1 bin/look Holm words.txt; echo "exit $?"
stats: look: probes 14, blocks read 5, lines printed 0
stats: array: pushes 80, grows 1, moves 0
exit 1
$ DS_STATS=1 bin/look --algo=scan Holm words.txt; echo "exit $?"
Holmes
stats: look: probes 494, blocks read 1, lines printed 1
stats: array: pushes 3091, grows 2, moves 8
exit 0
```

Nothing found, and exit status 1, the answer for "no such line". With
`<= 0`, a probe that lands on `Holmes` moves `lo` past it, as if it were
smaller. The invariant breaks: a line before `lo` is no longer always
smaller than the string. The search ends just after the match, the line
there does not begin with `Holm`, and look prints nothing. The scan,
which does not use `find_binary()`, still finds it. Put `< 0` back.
