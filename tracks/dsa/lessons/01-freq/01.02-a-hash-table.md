# 01.02 A hash table

freq at 01.01 compares each word with every different word before it. This
lesson gives it a hash table: the word's own bytes are turned into a number
that picks one short list, and only that list is searched. On the book,
freq then looks at 119 times fewer words.

## Where this fits

![Where 01.02 fits](figures/01.02-map.svg)

The hash table is the second box in module 01's strip, and the first dot
on the library's hash table rail, which runs on to grep, spell, diff, make
and git. It stands on the growable array of 01.01, which holds its
entries. freq asks it where a word is among the words counted so far.
After this lesson freq counts in two ways: the list, kept for comparison,
and the table, now the default. The table is quick on the book, and the
growth harness finds where it is not.

## The idea

![Counting "the cat sat on the mat, the act": each word's summed bytes pick one bucket, only that bucket's list is walked, and "act" collides with "cat".](figures/01.02-chain.svg)

The list looks at every word because nothing tells it where a word might
be. Suppose the word itself said where to look. Turn it into a number, its
**hash**, and let the number pick one of many **buckets**; keep each word
in the bucket its hash picks. To find a word, hash it and look in that one
bucket. With 1024 buckets for the book's 7818 different words, a bucket
holds about 8 of them, not 7818.

The first hash anyone writes adds up the bytes: "the" is 116 + 104 + 101 =
321. There are 1024 buckets, a power of two, so the bucket is the hash's
low 10 bits, `321 & 1023`, which is 321. Two different words can have the
same hash: "cat" and "act" both add up to 312. That is a **collision**, and
it is why a bucket is a list of entries, and finding a word means walking
its bucket's list and comparing each entry with it. Each comparison is a
**probe**. In the figure freq counts "the cat sat on the mat, the act": no
word looks outside its own bucket, the second and third "the" each find it
at the first probe, and "act" is compared with "cat" before it goes in.

### `hash_sum`

The bytes, added up, in 64 bits.

### `table_init`

An empty table: 1024 buckets, each `-1`, an empty list, and an `Array` of
`Entry` for the entries themselves, with `hash_sum()` as its hash.

### `find`, `table_get` and `table_put`

The entries live in the array in the order they were added. A bucket holds
the index of its first entry, and each entry the index of the next one in
the same bucket, or -1. `find()` hashes nothing: it is given the hash,
takes the bucket from its low bits, and walks the list, comparing a key's
bytes only when the whole 64-bit hash kept in the entry matches.
`table_get()` returns the address of a key's value, or NULL.
`table_put()` returns it too, after adding the key with the value 0 if it
was not there: a copy of the key goes at the end of the entries array and
at the head of its bucket's list.

### `count_table`

freq's table maps a word to where it is in `words`, the array of 01.01.
`table_get()` finds it, and that word's count goes up; a new word is put in
the table with the index it is about to have, and `add_word()` pushes it.
`main()` gains `--algo=list` and `--algo=table`, the default, picked by
`pick()`.

Quadratic, worse than the list's n^1.6, and it gets there later: at 512000
words the table takes 0.32 s where the list took 5.4. There are two
reasons, and the next lesson takes each apart. The number of buckets is
fixed at 1024, so a text with ten times the different words has lists ten
times as long. And adding bytes up is a poor way to spread words over the
buckets: the sums of English words fall in a narrow range, and every
anagram shares one.

## How it works

### The invariant, and the head of the list

The table's **invariant**: every entry is on exactly one list, the one its
hash picks, `hash & (nbuckets - 1)`. `find()` relies on it to look in one
bucket only. `table_put()` keeps it as it links a new entry in, at the head
of its bucket's list, which costs the same however long the list is:

```
    e->next = t->buckets[b];
    t->buckets[b] = (long)(t->entries.len - 1);
```

### The hash is kept, and compared first

Each entry keeps its key's 64-bit hash, so most entries of a list are
turned down by comparing two numbers, and only an equal hash costs a
comparison of bytes:

```
        if (e->hash == h && e->len == len && memcmp(e->key, key, len) == 0)
```

The kept hash also means a key is never hashed twice. With the sum, equal
hashes are common, which is why the bytes must still be compared; Break it
shows what happens when they are not.

### The value is an index, not a pointer

The pointer `table_put()` returns is good until the next put: a put pushes
onto the entries array, and a push may move it, as 01.01 showed. So freq
keeps in the table where a word is in `words`, not a pointer to it, and
the counts stay in `words`. For the same reason the buckets and the `next`
links are indexes: the entries can move to a bigger block and every link
still holds.

## Decide the boundary

This table chains: each bucket is a list, threaded through the entries
array. The other common design, **open addressing**, keeps the entries in
the bucket array itself and, on a collision, tries the next slot. It needs
no links, and a probe reads memory right next to the last one; but the
table must never fill up, so it grows well before it is full, and deleting
a key has to leave a marker behind so later searches walk past the hole.
Here an entry, once added, stays at its index for good. Which matters more
for what you store: memory read close together, or entries that never move?

## Break it

Compare the hashes only, not the words. In
`build/at/dsa/01.02/lib/table.c`, in `find()`, change

```

```
