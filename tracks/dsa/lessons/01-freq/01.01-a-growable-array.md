# 01.01 A growable array

freq prints the most common words of a text, and this lesson writes it the
obvious way. To keep the words it needs the track's first structure: an
array that grows as long as words keep coming, by moving to a block twice
its size whenever it is full.

## Where this fits

![Where 01.01 fits](figures/01.01-map.svg)

This lesson opens module 01's column: freq at its top, and the growable
array, the first box of the strip and the first dot on the library's array
rail. The rail runs on to every tool after this one but route, starting
with sort, which keeps its lines in one. The array stands on nothing but
the C library's `malloc()`. After this lesson freq counts the words of the
book and prints the ten most common, the same counts as the shell pipeline
it copies. On a large text it slows down badly, which is what the next two
lessons fix.

## The idea

![freq's array of words as the book's first lines are read: when the block is full, every word moves to a block twice as big, and the copies add up to fewer than the words.](figures/01.01-doubling.svg)

The shell already counts words. Doug McIlroy's pipeline turns every run of
letters into a line of its own, lowercases it, sorts the lines so the same
words sit together, counts each run, and sorts by the count:

<!-- verify: skip reason="the pipeline's shape, to read; Run it types it on the book" -->
```
tr -cs A-Za-z '\n' | tr A-Z a-z | sort | uniq -c | sort -rn | head -n N
```

freq does the same in one program, and the obvious way: read a word, look
for it among the words seen so far, and add one to its count, or add the
word with a count of 1. At the end, pick out the ten largest counts.

The first problem is C's own. An array has the size it was born with, and
freq cannot know how many different words a text has (7818 in the book,
more in a bigger one) or how long the longest is (18 letters in the book;
in a file of one long line, as long as the file). A fixed size is either
wasteful or too small. freq needs an array that grows.

A **growable array** keeps its elements one after another in a block of
memory with room to spare: `len` elements in use, room for `cap`. Adding
one at the end, a **push**, is a copy into the next free slot, until the
block is full. Then everything moves to a bigger block. How much bigger
decides the cost. Grow by 8 slots at a time and every eighth push copies
the whole array, so n pushes copy about n squared over 16 elements: the
quadratic trap of 00.01 again. Double instead, and the move that copies k
elements buys room for k more pushes before the next move. In the figure,
"doyle", the 9th different word of the book, finds the 8 slots full and
moves them into a block of 16; "red", the 17th, moves 16 into a block of
32. Over the whole book the words array grows 11 times, to 8192 slots, and
copies 8184 words in all: fewer copies than words.

### `array_init` and `array_push`

An `Array` (in `lib/ds.h`) is `data`, `len`, `cap` and `size`, the bytes of
one element, so the same code keeps words, letters or pointers.
`array_init()` makes an empty one, which takes no memory until the first
push. `array_push()` returns room for one more element at the end, for the
caller to fill in; when the block is full it first moves to one twice the
size, 8 slots to begin with. It copies by hand, with `xmalloc()`,
`memcpy()` and `free()`, rather than with `realloc()`, so that every move
is seen and counted: with `DS_STATS=1` it prints its pushes, its grows and
its moves, the elements those grows copied.

### `next_word`

Reads the next word into `buf`, an `Array` of `char`, a letter at a time:
it skips anything that is not a letter, then pushes letters, lowercased,
until one is not. Because `buf` grows, a word can be as long as the input.

### `count_list`

The obvious search: compare the word with every word seen so far, in the
order they first came, and add one to the count of the one that matches.
If none does, `add_word()` pushes it onto `words`, the array of `Word`s,
with a count of 1.

### `top_select`

The ten most common, in ten passes over all the words, each taking the
best one not taken yet. `rank()` says which of two words ranks higher: the
higher count, and on equal counts the word that is bigger byte by byte.
That is where `sort -rn` leaves lines with the same number, so freq's ties
come out in the pipeline's order. `main()` reads `-n N` (N words, 0 for
all of them) and the files, or standard input.

## How it works

### Doubling, and what it costs

The test that keeps the array's **invariant**, that `len` never passes
`cap` and elements 0 to `len - 1` are in the block at `data`, is the first
line of `array_push()`:

```
    if (a->len == a->cap) {
        size_t cap = a->cap ? 2 * a->cap : 8;
```

With doubling, an array that has grown to n slots has copied 8 + 16 + ...
+ n/2 elements, which is n - 8: less than one copy for each element it
holds. One push now and then copies everything, but over many pushes the
cost per push is a constant: it is constant **amortized**, shared out over
the pushes that the big copy made room for. The price is memory: just after
a grow, half the block is empty.

### A pointer into the array goes stale

`array_push()` can move every element to a new block and free the old one.
So a pointer to an element, such as the `Word *` that `array_at()` returns,
is good only until the next push. `count_list()` never holds one across a
push, and `ds.h` says so beside the type. Code that keeps one and pushes
reads freed memory, and may not notice for a long time.

### Why freq slows down

`count_list()` compares each word with every different word seen so far.
That is fine on the book and hopeless on a library: the cost of each word
grows with the vocabulary. The structure of the next lesson finds a word
among millions about as fast as among ten.

## Decide the boundary

This array doubles. Just after it grows, half its block is unused, so a big
array can hold as much empty memory as data. Growing by half instead, to
1.5 times the size, leaves at most a third empty, but copies each element
about twice on average instead of once, and grows more often. Some
libraries do one, some the other. For the data you keep, which costs more:
memory standing empty, or time spent copying?

## Break it

Grow by 8 slots instead of doubling. First the counts as they are, on one
word of 200000 letters and one of 400000, which `buf` has to hold:

<!-- verify: session -->
```
$ python3 -c "print('a' * 200000)" > long.txt
$ python3 -c "print('a' * 400000)" > long2.txt
$ DS_STATS=1 bin/freq long.txt > /dev/null
stats: freq: words 1, distinct 1, list probes 0, rank comparisons 0
stats: array: pushes 200001, grows 17, moves 262136
```

In `build/at/dsa/01.01/lib/array.c`, in `array_push()`, change

```
        size_t cap = a->cap ? 2 * a->cap : 8;
```

to

<!-- verify: patch file=lib/array.c
-        size_t cap = a->cap ? 2 * a->cap : 8;
@block
-->
```
        size_t cap = a->cap + 8;
```

and build and run again:

<!-- verify: session
line 9 ~   \d+\.\d\ds user \d+\.\d\ds system \d+(\.\d+)?% cpu \d+\.\d+ total
-->
```
$ make -s
$ DS_STATS=1 bin/freq long.txt > /dev/null
stats: freq: words 1, distinct 1, list probes 0, rank comparisons 0
stats: array: pushes 200001, grows 25001, moves 2499900000
$ DS_STATS=1 bin/freq long2.txt > /dev/null
stats: freq: words 1, distinct 1, list probes 0, rank comparisons 0
stats: array: pushes 400001, grows 50001, moves 9999800000
$ time bin/freq long2.txt > /dev/null
  0.14s user 0.00s system 99% cpu 0.147 total
```

2.5 billion letters copied to keep 200000, and twice the word copies four
times as many: quadratic, as strcat was. `memcpy()` is fast, so the clock
is slower to show it than the counts: 0.147 s here for 400000 letters,
against 5 ms with doubling, and 2.1 s for a word of 1.6 million. On the
book the cost is real but hidden, 981 grows and 3822048 elements copied
instead of 14 and 8208. Put the line back.
