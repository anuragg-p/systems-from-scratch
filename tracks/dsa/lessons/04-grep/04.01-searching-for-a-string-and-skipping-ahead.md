# 04.01 Searching for a string, and skipping ahead

grep prints the lines of a text that hold a pattern. This lesson builds it
for a fixed string, `grep -F`, in two ways: the obvious one, which tries the
string at every place in the text, and Horspool's, which compares from the
string's end and skips ahead. On the book the skip reads a tenth of the
bytes; each of the two has an input that makes it slow, and macOS's own
`grep -F` falls into one of them.

## Where this fits

![Where 04.01 fits](figures/04.01-map.svg)

grep is the tool of module 04, and the string search is the first box of
its strip. It needs nothing from the library: it is two loops over the
bytes of the text and a table of 256 numbers worked out from the pattern.
Above it, grep reads each file whole into memory, asks the search where the
next match is, and prints, counts or numbers the line around it. After this
lesson grep prints the same lines as the system's `grep -F`, with the same
exit status, and the next three lessons give it regular expressions.

## The idea

![Horspool's search for "woman" along line 3284 of the book, one position at a time: the bytes compared from the pattern's end, the byte under its last byte, and how far that byte moves the pattern on.](figures/04.01-horspool.svg)

To find "Sherlock Holmes" in the book, the obvious search puts the string
at the first byte of the text and compares byte by byte. At the first byte
that differs it moves the string on by one and starts again. Each place it
tries is a **position**, and each byte of text it compares is **examined**.
On the book that is 558060 positions and 560223 bytes examined: most
positions fail at their first byte, so the search reads each byte of the
text about once. It can never read fewer, because it tries every position.

A search can read fewer if it compares the string's last byte first. Say the
string is "woman", 5 bytes, and the text has a comma where the string's
last byte would go. "woman" has no comma, so none of the 5 positions that
cover that comma can match, and the search moves on by 5 without looking at
the bytes it passes. If the byte is one the string has, an "o" say, it
moves on just far enough to put the string's last "o" over it: 3, for
"woman". Which byte gives which move is worked out once from the pattern,
into a **shift table** with one entry for each of the 256 byte values. This
is **Horspool's search** (Nigel Horspool, 1980), a simpler form of Boyer and
Moore's of 1977.

The figure runs it on line 3284 of the book. It tries 7 positions and
examines 14 bytes to find "woman" at 24; trying every position takes 25
positions and 30 bytes. The longer the string, the further each move: for
"Sherlock Holmes" on the whole book, 58947 bytes instead of 560223.

### `search_init`

Copies the pattern and fills the shift table: every byte moves the pattern
its whole length, then each byte of the pattern but the last, from left to
right, moves it as far as that byte is from the pattern's end, so a byte
that comes twice keeps the smaller move. With -i the pattern is kept in
lower case, and every byte of the text goes through a 256-byte map before
it is compared; without -i the map leaves each byte as it is.

### `search_scan`

Every position, comparing from the pattern's first byte. It counts
positions and bytes examined for `DS_STATS=1`, and prints a line for each
position with `DS_TRACE=1`.

### `search_horspool`

Compares from the pattern's last byte back to its first. On a mismatch, the
byte of the text under the pattern's last byte picks the move. It also
counts the positions it passed over without trying them, as skipped.

### `next_fixed`

grep's way to the next line with the string in it. It hands the search the
whole rest of the text, newlines and all, and only when the string is found
walks back to the start of its line. The lines between two matches are
never split apart or read, except with -v or -n, which need them:
`grep_text()` walks them to print them or to number the next match. The
rest of `grep.c` reads the options and each file and prints the lines, as
the system's grep does, and `--algo=scan` picks the obvious search.

## How it works

### Why the skip never passes a match

Horspool keeps one **invariant**: no position before the one it is at can
match. Say the byte of the text under the pattern's last byte is c, and the
table says to move on by k. The table holds, for c, how far the last c
among the pattern's first m - 1 bytes is from its end (m is the pattern's
length), or m if there is none. So at each of the k - 1 positions passed
over, some byte of the pattern other than c would sit on that c, and the
position fails there: none of them can match. The table is filled so:

```
    for (int c = 0; c < 256; c++)
        s->shift[c] = len;
    for (size_t i = 0; i + 1 < len; i++)
        s->shift[s->pat[i]] = len - 1 - i;
```

The second loop stops before the pattern's last byte. If it went on, that
byte would get a move of 0, and on a mismatch with it under the last place
the search would stay where it is, comparing the same bytes for ever.

### The text, not its lines

grep could split the text into lines and search each one; `next_fixed()`
searches the whole rest of the text instead, and goes back for the line
only around a match:

```
    const char *p = find(&search, buf + at, end - at);
    if (p == NULL)
        return end;
    size_t start = (size_t)(p - buf);
    while (start > at && buf[start - 1] != '\n')
        start--;
```

Finding the newlines first would mean reading every byte, which is just
what the skip avoids. Mike Haertel, who wrote GNU grep, gives this as one
of the reasons for its speed, beside Boyer and Moore's skip.

### Each search has its own bad input

The scan is slow when most positions match for a long way before they
fail: 99 a's and a b, in a run of a's, compares about 100 bytes at every
position, n times m for a text of n bytes. Horspool is slow when the last
byte matches and the byte under it moves the pattern only a little: b and
99 a's compares back over 99 a's to the b, and the a under its last byte
moves it on by 1. Neither input is in the book; each is easy to make.

## Decide the boundary

This grep skips with one table, 256 moves picked by one byte of the text,
which wins on ordinary text and is n times m on a run of one letter. The
Knuth-Morris-Pratt search works out a table from the pattern itself and
never goes back in the text: its time is in proportion to the text and the
pattern together on any input, but it reads every byte, as the scan does.
Boyer and Moore's full search keeps a second table, of moves worked out
from the part of the pattern that did match, and takes the larger of its
two moves, at the price of more code and a table as long as the pattern.
Which costs you more: reading every byte of every file, or the rare file
that is one letter over and over?

## Go deeper

- [Mike Haertel, why GNU grep is fast](https://lists.freebsd.org/pipermail/freebsd-current/2010-August/019310.html) -
  a short email from GNU grep's author: it avoids looking at every input
  byte, by Boyer-Moore, and it avoids breaking the input into lines,
  looking for the newlines only around a match, as `next_fixed()` does.

  Substring Search ([its page](https://algs4.cs.princeton.edu/53substring/)) -
  the brute-force search, Knuth-Morris-Pratt, the mismatched character
  rule of Boyer-Moore (this lesson's table), and Rabin-Karp; the page
  asks for an input on which that rule alone does badly, such as the b and
  99 a's above.
