# 04.02 Parsing a regular expression

A fixed string cannot say "colour or color", or "a capital letter and then
small ones". A regular expression can. This lesson reads `grep -E`'s
patterns into a tree, with one function for each rule of their grammar, and
matches the tree against each line the obvious way: take one choice, and
when what follows fails, go back and take the other.

## Where this fits

![Where 04.02 fits](figures/04.02-map.svg)

The regex parser is the second box of module 04's strip. It turns the
pattern's text into a tree, which the matcher of this lesson walks and the
next two lessons turn into a machine. Like the string search, it needs
nothing from the library. Above it, grep now finds the next matching line
in one of two ways: a fixed string, searched for in the whole text, or an
expression, tried on each line in turn. After this lesson grep prints the
same lines as the system's `grep -E` for every pattern its dialect has.

## The idea

![The tree the parser makes of (a|b)*abb, beside the four rules of the grammar, one function each: a sequence nests to the left, the star holds only the group, and the group's inside is parsed by the first rule again.](figures/04.02-tree.svg)

A **regular expression** describes a set of strings: `colou?r` is "colour"
or "color", `[A-Z][a-z]+` a capital letter and then one or more small ones.
`grep -E` reads one by four rules, loosest first:

- an expression is one or more sequences with `|` between them: any one of
  them may match;
- a sequence is repetitions one after another;
- a repetition is an atom followed by any number of `*` (any number of
  times, none included), `+` (once or more) and `?` (at most once);
- an atom is a byte, `.` (any byte), a **bracket expression** such as
  `[a-z]` (one byte of a set), `^` or `$` (the start or the end of the
  line), or a whole expression in parentheses.

Rules like these are a **grammar**. Each names the next, tighter one, and
the last names the first again, through the parentheses. Together they set
the **precedence**: in `ab|c*` the `*` holds only the c, the sequence holds
a and b, and the `|` holds the two sequences. The text has none of this
structure written in it, so before anything can be matched the pattern is
**parsed**: read once, left to right, into a **tree**, with a node for each
operator and the parts it applies to as its children.

The parser has one function for each rule, each calling the next, and the
one for an atom calls the first again for a group: a **recursive descent
parser**. The figure shows the tree for `(a|b)*abb`, the lines with an a or
a b repeated, then abb. Its 10 nodes are what `DS_STATS=1` counts.

Matching the tree against a line, the obvious way is to walk it. Start at
the line's first byte. At a choice, a `|`, a `?`, or one more time round a
loop, take one way first, the left side or the longer match, and go on; if
what follows fails, go back to the choice and take the other way. This is
**backtracking**. If no way works from the first byte, start again from
the second, and so on to the end of the line.

### `parse_alt`, `parse_cat`, `parse_repeat` and `parse_atom`

The four rules, loosest first. `p` is where the parser is in the pattern.
Each function reads what its rule covers and returns its tree, built with
`node()`, which also keeps the part of the pattern the node came from for
the traces. Patterns this grep leaves out, such as `{2,3}` and `\w`, stop
it with an ordinary error that says which part.

### `parse_class`

A bracket expression, from after its `[` to its `]`: ranges, classes such
as `[:digit:]`, a `]` first or a `-` first or last standing for itself,
and a `^` first for every byte but these.

### `re_parse`

Sets the parser at the start of the pattern and parses an expression: the
whole pattern is the first rule.

### `bt`, `go_on` and `loop`

The backtracker. `bt()` matches one node at a byte of the line and then
calls `go_on()` with what is left; at a choice it tries the first way and,
if that fails, the second. `loop()` is one more time round a `*` or `+`,
or stopping.

### `re_backtrack`

Tries a match from each byte of the line in turn.

### `next_regex`

grep's way to the next matching line for an expression: each line in turn,
handed to the matcher. Without `-F`, grep now reads the pattern as an
expression, as `grep -E` does, and `-E` says so.

## How it works

### Precedence is the order of the calls

`parse_alt()` calls `parse_cat()` for each side of a `|`; `parse_cat()`
calls `parse_repeat()` for each piece of a sequence; `parse_repeat()`
calls `parse_atom()` and then wraps it in a node for each `*`, `+` or `?`
after it. A node made deeper in the calls ends lower in the tree, so the
deeper the rule, the tighter it binds: no table of precedences is needed.
A sequence nests to the left, because the loop in `parse_cat()` makes the
sequence so far the left child of each new join:

```
        Re *r = parse_repeat();
        seq = seq ? node(RE_CAT, seq, r, from) : r;
```

so `abb` is CAT(CAT(a, b), b), as in the figure.

### Where a sequence stops

```
    while (p < pend && *p != '|' && !(*p == ')' && depth > 0)) {
```

A sequence ends at a `|`, which belongs to the rule above it, at a `)`
that closes a group, or at the end of the pattern. `depth` counts the
groups open, so a `)` with no `(` before it is a byte like any other: POSIX
says so, and both the BSD and the GNU grep read it that way.

### One kind of node for every byte

A literal, `.`, and a bracket expression all become one kind of node,
RE_CHAR, holding a set of 256 bits, one for each byte value it accepts.
With -i the parser adds each letter's other case to the set. The matcher,
and the machines of the next two lessons, never need to know which of the
three a node was written as.

### What is left lives on the stack

`bt()` is given a node, a byte of the line, and what is left of the
pattern after that node, as a list of `Next` entries kept in the C stack's
own frames. Taking the other way at a choice is returning from the call
that took the first. A loop entry also holds where its last time round
began, and a time round that read nothing is not repeated, or `(a*)*`
would go round for ever. The calls nest a few deep for each byte read, and
past 10000 the matcher stops with an ordinary error rather than run out of
stack.

## Decide the boundary

This grep parses the pattern into a tree first. Rob Pike's matcher, the
one Brian Kernighan explains, has no tree and no parser: about 30 lines of
C walk the pattern's text directly, for a byte, `.`, `^`, `$` and `*`. It
is shorter, and it is all a byte-and-star dialect needs. The tree costs a
parser of about 200 lines; it buys `|`, groups, `+`, `?`, bracket
expressions, errors that say which part of the pattern is wrong, and a
structure that the next lesson turns into a machine. Will your patterns
ever need a group or an alternative?

The sequence now reads the `|` too, as an atom, and an atom that is no
operator is a byte. `parse_alt()` never sees a `|`, so the tree has no
alternative in it: 25 nodes, thirteen bytes in a row, looking for the
text "Holmes|Watson" itself, which is in no line of the book. A rule
that does not stop where the grammar says hands the next rule's operator
to the wrong one. Put the line back.
