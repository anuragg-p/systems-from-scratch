# 04.04 Caching the states: a DFA built as it runs

The NFA of 04.03 reads each byte once, but for each byte it works out the
same few lists of states again and again. This lesson remembers them: each
list becomes one state of a new machine the first time the text leads to
it, with a table of where each byte takes it, so that after the first few
lines nearly every byte costs one lookup. The states are kept in a cache of
fixed size, and the lesson ends on the patterns that overflow it.

## Where this fits

![Where 04.04 fits](figures/04.04-map.svg)

The DFA cache is the last box of module 04's strip. It stands on the NFA of
04.03: each of its states is a list of NFA states, and a transition it has
not seen yet is worked out by the NFA's own step. It uses the library: the
hash table of 01.02 finds a state by its list of NFA states, and a growable
array of 01.01 holds the states. From this lesson it is how `grep -E` runs,
and grep is done: -F with Horspool's skip, -E with a machine that reads each
byte once and mostly by one lookup, both printing the system's lines.

## The idea

![The DFA for a?a?a?aaa built while it reads aabaaa and then aaa: each set of NFA states becomes a state the first time it comes, and is found again after.](figures/04.04-dfa.svg)

On the book, `Holmes|Watson` keeps the NFA busy with 1096291 live states
over 533815 bytes read: for every byte, a walk over a list and the arrows
out of it. Yet the list after a byte depends only on the list before it and
the byte, and few different lists ever come up: for this pattern, on the
whole book, 12.

So remember them. The first time a list comes up, make it one state of a
new machine, a **deterministic finite automaton**, a **DFA**, which is in
exactly one state at a time because each of its states stands for a whole
set of the NFA's. Each DFA state has a table with an entry for each of the
256 byte values, the state that byte leads to, empty until the byte first
comes. Running the DFA is one lookup a byte. An empty entry is a **miss**:
the NFA's step works it out once and the answer goes in the entry; a full
one is a **hit**. A hash table keyed by the list itself finds each list
again, so a list worked out a second time comes back as the state it
already is.

The figure runs the 04.03 figure's line again, aabaaa, and then aaa. The
first three sets are new and are built as D0, D1 and D2. At the b the NFA's
work leads back to the set of D0, which the hash table already has; the
next two a's are hits, and the last a builds D3, which holds the match
state. On the second line every byte is a hit: the NFA does no work at all.

Some patterns need more states than any text will pay for, so the cache
holds at most a fixed number of them, 10000 unless `--cache` says. When it
is full and another is needed, every state is thrown away and the building
starts again.

### `state_for`

The DFA state for a list of NFA states: the list is sorted and looked up
in the `Table` of 01.02, its bytes the key. A new list becomes a new state
with all 256 entries empty (-1), after `flush()` if the cache is full; the
state notes whether it holds the match state, and whether the line would
match if it ended there (a `$` waiting).

### `step`

A transition not worked out yet: the NFA's step from the state's NFA
states on that byte, with the start added again, as in `nfa_match()`; the
list it gives is turned into a state by `state_for()`, and kept in the
state's table.

### `dfa_match`

Runs the DFA on a line: one lookup a byte, and `step()` on a miss. It
stops at a state that holds the match state, or at one with no NFA states
at all, from which nothing can match.

### `flush`

The cache is full: every state is freed, the hash table emptied, and the
state a line starts in is built again when the next line comes. In
`grep.c`, `use_regex()` builds the DFA on top of the NFA, `--algo=dfa` is
the default, and `--cache=N` sets the most states kept at once.

## How it works

### A set of states is a state

The list of live NFA states after a byte is all the NFA knows about the
line so far, so two moments with the same list have the same future: one
DFA state can stand for both. That a set of an NFA's states can be made one
state of a DFA is Rabin and Scott's result of 1959, the **subset
construction**; built ahead of time, it gives a DFA with a state for every
set that can come up. Here a set is looked up by its bytes, so the same set
must always be the same bytes:

```
    qsort(l->ids, (size_t)l->len, sizeof *l->ids, by_id);
    size_t keylen = (size_t)l->len * sizeof *l->ids;
    long *have = table_get(&d->cache, l->ids, keylen);
```

The NFA adds states in the order it reaches them, which can differ for the
same set; sorted, they cannot.

### Why some patterns need many states

With k `(a|b)` after the `a`, whether a line matches depends on the byte
k + 1 from its end, and the machine does not know where the end is until
it gets there. So it must carry with it which of the last k + 1 bytes were
a's: 2^(k+1) different sets of NFA states, a DFA exponentially larger than
its pattern. Built ahead of time, every one of them would exist before the
first line. Built as it runs, there is at most one new state for each byte
read, and at most `--cache` at once, about a kilobyte each for the table of
256 next states: memory stays bounded whatever the pattern, and the price
is time when the states a text needs do not fit.

### A transition is kept only if its state still exists

```
    long flushes = st.flushes;
    int to = state_for(d, &d->work);
    if (st.flushes == flushes)
        state(d, from)->next[c] = to;
```

Building `to` may fill the cache and empty it, and then the state `from`
is gone: its number belongs to some other state, or to none. The
**invariant** is that every entry in every state's table names a state
that is in the cache now. In the same way `dfa_match()` takes its pointer
to the array of states again after every miss, since building a state may
move the growable array to a bigger block, as in 01.01.

## Decide the boundary

This DFA keeps at most 10000 states and, when the cache is full, throws
them all away and starts again: memory stays bounded, and a text that
needs more states than that pays for the NFA's work and for building a
state at most bytes, several times what the NFA alone costs. RE2 does the
same, and watches as it goes: when the cache fills again before it has
read 10 bytes for each state in it since it was last emptied, it gives up
on the DFA and runs the NFA instead. A bigger cache costs memory on every
search and only moves the cliff. How big a cache would you give it, and
how should the matcher tell that it is losing?

## Break it

Never keep a transition, so every byte is worked out again. In
`build/at/dsa/04.04/lib/dfa.c`, in `step()`, delete these three lines
(the compiler would warn about `flushes` if only the last two went):
