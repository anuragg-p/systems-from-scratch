# 03.01 An editor, and its text in one array

This module's tool is `edit`, a text editor for the terminal that comes
whole in this lesson. What the module builds is the structure that holds
its text, and this lesson starts with the obvious one: every byte of the
file in one array. Then it measures what a key costs as the file grows.

## Where this fits

![Where 03.01 fits](figures/03.01-map.svg)

This lesson opens module 03's column: edit at its top, and the first box
of the strip, the text in an array. edit is the finished editor of this
course's kilo track, derived from antirez's kilo: raw mode, keys, the
screen, scrolling, search and saving are kilo's, and are not taught again
here (the kilo track, `/t/kilo` on this site, builds them a lesson at a
time). What is new is that the text sits behind an interface of five
calls, and the module's lessons change what stands behind it. This
lesson's array is the editor's own block of bytes, which grows by doubling
as 01.01's growable array does. After it you can open, change and save a
file on the terminal, and replay a script of edits with no screen, which
is how the module measures each structure. The question that runs through
the module is whether a key costs the same in a file of ten lines as in one
of ten million.

## The idea

![Typing "fat " at byte 4 of "the cat sat\n" in one array: the first key moves the text to a block twice as big, then every key moves every byte after it up one place](figures/03.01-shift.svg)

An editor holds the text of a file and changes it where the cursor is. To
edit, the text is a row of bytes: "the cat sat" and a newline is 12 bytes.
A **position** is a place between bytes, from 0, before the first, to 12,
after the last; inserting at 4 puts the new bytes before the "c". A
newline is a byte like any other, and the editor finds the lines itself.

The obvious way to keep those bytes is one array, in order. Reading is as
cheap as it can be: the byte at position i is element i. Changing the text
is another matter. To put "f" in at position 4, every byte from 4 to the
end first moves up one place, to open a hole, and "f" goes into it; to
take a byte out, every byte after it moves back down. In the figure the
file is read into a block exactly its size, so the first key also moves
the whole text to a block twice as big. After that, each of the four keys
of "fat " moves the 8 bytes after the cursor: 32 bytes moved for 4 keys.
The "!" typed before the newline moves 1. A key costs as many bytes as
there are after it, so typing near the top of a large file moves nearly
all of it, every key.

### `text.h`

The interface. A text is `len` bytes, and the editor can insert `n` bytes
at a position, erase `n` bytes from one, read them, write the whole text to
a file, and free it. `TextOps` is a table of five function pointers, one
for each call, and every structure that holds a text begins with a
`Text`, which points to its own table. That is C's way of writing an
interface: the editor calls `text_insert()` and never learns which
structure is behind it.

### `text.c`

What every structure shares. `text_insert()`, `text_erase()` and
`text_read()` check the positions they are given before calling the
structure's own function: a position past the end is a bug in the editor,
and stops the program with a message. `text_load()` reads a whole file into
one block, and the `DS_TRACE` helpers print each call, which is what the
figure is drawn from.

### `flat_insert` and `flat_erase`

An insert grows the block if it is full, to twice its size, as 01.01's
array does, then moves the bytes from `pos` to the end up by `n` with
`memmove()` and copies the new bytes into the hole. An erase moves the
bytes after the erased ones down over them. Both count the bytes they
move, for `DS_STATS`.

### `flat_read` and `flat_open`

A read is one `memcpy()` from where the bytes are. Opening reads the file
into a block exactly as big as it is.

### `editorInsertText`, `editorEraseText` and `replay`

Every change the editor makes, a key, Enter, Backspace, goes through
`editorInsertText()` or `editorEraseText()`, which call the interface and
keep the editor's own count of newlines up to date. `replay()` is the
`--replay` mode: it reads a script of edits, one a line (`goto 4`,
`type fat`, `back 1`, `print`), and makes them through the same two
functions, with no terminal.

About 2 ms a key, on an Apple M4 Pro; your times will differ, the bytes
moved will not. `memmove()` is fast: measured the same way, a key costs
about 0.2 ms at 10 MB, 1.9 ms at 100 MB and 19 to 20 ms at 1 GB. A screen
at 60 frames a second draws one every 16.7 ms, so the array keeps up with
typing in files of a few hundred megabytes and falls behind at about a
gigabyte, where it also needs twice the file in memory once grown. Typing
in one place is its easy case; the next lesson measures edits all over a
file, where it does far worse.

## How it works

### One table of functions per structure

Each structure fills in one `TextOps` and hands it out through the `Text`
at the start of its own struct. For the array:

```
static const TextOps flat_ops = {"flat array", flat_insert, flat_erase, flat_read, flat_write, flat_free};
```

`text_insert()` calls `t->ops->insert`, here `flat_insert()`, which casts
the pointer back to a `Flat`: the `Text` is its first member, so the two
are the same address. Each later lesson adds a structure by writing one
more table, and the editor does not change.

### The invariant, and the hole

The array's **invariant**: `data[0]` to `data[len - 1]` are the text, in
order, and `len` is never more than `cap`. An insert keeps it in two lines:

```
    memmove(f->data + pos + n, f->data + pos, t->len - pos);
    memcpy(f->data + pos, s, n);
```

The bytes are moved with `memmove()`, not `memcpy()`, because where they
come from and where they go overlap: moving 8 bytes up by one, the last 7
of the source are the first 7 of the destination. `memcpy()` is allowed to
copy in any order and get that wrong; `memmove()` copies as if through a
spare buffer.

### Doubling, from a block exactly full

`flat_open()` reads the file into a block of exactly its size, so the
first insert always grows it, and copies the whole file once. From then on
the block doubles, as the growable array of 01.01 did: each grow buys as
much room as it copied, so growing costs about a byte per insert, on
average. What does not average out is the `memmove()`, paid again on every
key, in full.

### The editor reads only what it shows

The editor itself does not grow with the file. It keeps the row on the top
line of the screen and where that row starts, and finds the other rows it
needs by reading on from there: a screen costs about a screenful of bytes,
in a file of any size. What grows is the structure's work, here the bytes
after the cursor. One read does cover the whole text: on a terminal the
editor counts the lines once, at open, for the status bar. The replay
never does.

## Decide the boundary

This editor keeps the text as bytes and finds lines by reading them. kilo,
and the kilo track, keep an array of rows, one string per line: going to
line 500000 is then one step, but each line costs a separate allocation
and a pointer, and an Enter near the top moves every row after it. Visual
Studio Code began with an array of lines too, and measured a 35 MB file
of 13.7 million lines taking about 600 MB that way. Does your editor need
to find line N at once, or can it afford to read for it?

## Break it

Make the array grow by exactly what it needs instead of doubling. First,
1000 keys at the end of the book, where nothing moves:

<!-- verify: session -->
```
$ python3 -c "print('goto end'); print('type ' + 'x' * 1000)" > end.txt
$ DS_STATS=1 bin/edit --replay end.txt data/book.txt
stats: edit: inserts 1000, erases 0, bytes read 0
stats: flat array: bytes loaded 562404, inserts 1000, erases 0, bytes moved 0, grows 1, bytes copied 562404
```

Then in `build/at/dsa/03.01/lib/flat.c`, in `flat_insert()`, change

```
        size_t cap = 2 * f->cap;
```

to

<!-- verify: patch file=lib/flat.c
-        size_t cap = 2 * f->cap;
@block
-->
```
        size_t cap = t->len + n;
```

and build and run it again:

<!-- verify: session -->
```
$ make -s
$ DS_STATS=1 bin/edit --replay end.txt data/book.txt
stats: edit: inserts 1000, erases 0, bytes read 0
stats: flat array: bytes loaded 562404, inserts 1000, erases 0, bytes moved 0, grows 1000, bytes copied 562903500
```

Every key now finds the block full and copies the whole book to a block
one byte bigger: 1000 grows, 562903500 bytes copied, a thousand times what
doubling copied. The text is the same. On this machine the clock hardly
shows it, about 9 ms against 2, because copying half a megabyte is quick;
as in 01.01, the counts tell it better. On the 100 MB file the same 1000
keys would copy 100 GB. Put the line back.

## Go deeper

- Charles Crowley, [Data Structures for Text Sequences](https://www.cs.unm.edu/~crowley/papers/sds.pdf) (1998) -
  section 3 on why reads in an editor are almost always next to the last
  one, and section 5.1, "The array method": every insert and delete moves
  the items after it, which suits text that is seldom changed.
- [Build Your Own Text Editor, chapter 4, A text viewer](https://viewsourcecode.org/snaptoken/kilo/04.aTextViewer.html) -
  the section "Multiple lines" keeps the file as an array of rows, `erow`,
  each its own string: the design this editor leaves for one row of bytes.
- [antirez's kilo.c, `erow`](https://github.com/antirez/kilo/blob/323d93b29bd89a2cb446de90c4ed4fea1764176e/kilo.c#L81-L90) -
  the row of the original, and on [line 675](https://github.com/antirez/kilo/blob/323d93b29bd89a2cb446de90c4ed4fea1764176e/kilo.c#L675)
  the same `memmove()` inside one row.
- [Open Data Structures, 2.1 ArrayStack](https://opendatastructures.org/ods-cpp/2_1_Fast_Stack_Operations_U.html) -
  a list in an array: add(i, x) costs time in proportion to n - i, the
  elements it shifts, and Lemma 2.1 shows that resizing by doubling costs
  O(m) over m operations.
