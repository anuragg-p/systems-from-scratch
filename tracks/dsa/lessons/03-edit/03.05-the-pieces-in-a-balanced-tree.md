# 03.05 The pieces in a balanced tree

The piece table of 03.04 finds a position by walking its list, and every
edit makes the list longer. This lesson keeps the same pieces in a balanced
tree, where each node knows the length of the text under it: finding a
position is one step a level, and thirty thousand pieces make eighteen
levels.

## Where this fits

![Where 03.05 fits](figures/03.05-map.svg)

This lesson is the last box of module 03's strip, the balanced tree: the
piece table again, its two buffers read the same way, with the list of
pieces replaced by a tree that keeps itself balanced. It stands behind the
same interface as the structures before it, undo works on it unchanged,
and it becomes the editor's default. After this lesson the module's
question has its answer: opening a file copies nothing, and an edit
anywhere costs a few dozen steps, whether the file has ten lines or ten
million; it grows only as the logarithm of the number of pieces.

## The idea

![The pieces of "the cat sat\n" in an AVL tree, as "fat ", "!" and "." are typed: each node shows its piece and the length of the text under it; when one side of a node grows two taller than the other, one or two rotations mend it](figures/03.05-tree.svg)

The list's trouble is that a piece does not know where it starts, so
finding byte 15 means adding up lengths from the first piece; and storing
each piece's start would make an edit near the top change every piece after
it. A tree can keep sums that an edit changes in only a few places.

Keep the pieces as the nodes of a **binary tree**, each node with at most
two children, in the order of the text from left to right: a node's left
**subtree** (the child and everything under it) is the text before the
node's piece, its right subtree the text after it. Each node also keeps the
length of all the text under it. To find byte 15 once "fat " is typed (the
figure's sixth frame), start at the root, `add 0+4`: its left subtree holds
4 bytes and its own piece 4 more, so byte 15 is on its right, at 15 - 8 =
7. There, `orig 4+8` has nothing on its left, and byte 7 is in its own
piece. Two nodes looked at; for 31994 pieces, about 18, where the list
walks half of them on average.

That holds only while the tree is **balanced**, every path from the root
short. Pieces added in order, typing at the end of a file, say, would each
go to the right of the last, and the tree would be a list leaning right.
This tree is an **AVL tree** (Adelson-Velsky and Landis, 1962): each node
also keeps its **height**, the levels from it down to its lowest leaf, and
its two subtrees may differ in height by at most one. An insert or a
removal can break that rule only on the path to where it changed, and only
by one, so on the way back up each node of the path is checked, and where
its sides are two apart a **rotation** mends it: a child moves up into the
node's place and the node moves down to the other side, which keeps the
order of the text and moves a level from the tall side to the short one.
In the figure the first edit already needs two.

### `rotate_right`, `rotate_left` and `balance`

A rotation at a node: its left child (or right) goes up, the node goes down
to that child's other side, and the child's inner subtree moves across to
the node. `balance()`, called on each node on the way back up, rotates
where the two sides are two apart, and rotates the tall child first when
its inner side is the taller: two rotations.

### `find`, `insert_at`, `remove_at` and `set_len`

`find()` goes down from the root by the lengths on the left. The other
three add a node so that its piece starts at a position, take out the node
whose piece starts at one, or change one piece's length: each goes down one
path and fixes the lengths on the way back up, the first two calling
`balance()`. A removed node with two children is replaced by the first node
after it, the leftmost of its right subtree.

### `cut`, `ptree_insert`, `ptree_erase`, `copy` and `ptree_open`

`cut()` makes a position a boundary between pieces, splitting the piece it
is inside. An insert lengthens the piece before it when the new bytes
follow that piece's bytes in the add buffer, as the list did; otherwise it
cuts and adds a node. An erase cuts at both ends and removes every node
between. A read copies, in order, what falls in its range from the left
subtree, the node's piece and the right subtree. Opening maps the file, as
in 03.04, as the one node of the tree.

## How it works

### Three rules, kept at every node

The tree keeps three **invariants**: read from left to right, its pieces
are the text; each node's `sum` and `height` are those of its subtree; and
the heights of each node's two subtrees differ by at most one. Each can be
checked at a node from its children alone, so a change repairs them on its
way back up the one path it went down: `update()` works out a node's height
and sum from its children's, and `balance()` calls it first.

### Finding a position by the lengths on the left

```
        size_t l = sum(n->left);
        if (pos < l) {
            n = n->left;
        } else if (pos < l + n->span.len) {
            *off = pos - l;
            return n;
        } else {
            pos -= l + n->span.len;
            n = n->right;
        }
```

Each step goes down a level, and only one sum is read at each. An edit
changes the length of the text under each node on its path, and no other:
that is why the tree can keep sums the list could not.

### What a rotation keeps

```
    Node *l = n->left;
    trace_rotation("right", n);
    n->left = l->right;
    l->right = n;
    update(n);
    update(l);
```

Before, the text under `n` reads: `l`'s left subtree, `l`'s piece, `l`'s
right subtree, `n`'s piece, `n`'s right subtree. After, with `l` on top, it
reads the same five in the same order; only who is whose child has
changed. So every sum and height outside the two is unchanged, and only `n`
and `l` are worked out again, `n` first, since it is now below `l`.

### Why the tree stays shallow

Count the fewest nodes an AVL tree of height h can have. Its root has a subtree of
height h - 1 and, at the least, one of h - 2, each as small as it can be in
the same way: N(h) = 1 + N(h - 1) + N(h - 2), with N(1) = 1 and N(2) = 2.
These grow as the Fibonacci numbers do, by about 1.618 a level, so n nodes
are never more than about 1.44 log2(n) levels high. For the 31994 pieces
above the bound is 21.6; the tree was 18.

## Decide the boundary

This tree is AVL by choice: one rule, about heights, that any node can
check from its two children, and one repair, the rotation, used the same
way after an insert and after a removal. A **red-black tree** is balanced
less strictly, by colouring nodes, and rotates less often, but mending its
colours after a removal takes a page of cases. Visual Studio Code keeps its
text in what its team calls a piece tree: a piece table, with several
buffers and its pieces in a red-black tree, each node holding the length
and the number of line breaks of its left subtree, so that finding a line
is a walk down the tree too. A treap or a splay tree is balanced only on
average, or over many operations. Is a rotation saved worth a harder
removal?

## Break it

A tree that never rotates. First, the text and the counts as they are,
for pieces added at both ends of a file in turn:

<!-- verify: session -->
```
$ python3 -c "import sys; sys.stdout.write('goto end\ntype ab\ngoto 0\ntype >\n' * 6000)" > ends.txt
$ (cat ends.txt; echo print) | bin/edit --replay - cat.txt > before.txt
$ DS_STATS=1 bin/edit --replay ends.txt cat.txt 2>&1 | grep tree
stats: piece tree: bytes mapped 12, bytes loaded 0, bytes added 18000, inserts 18000, erases 0, pieces 12001, nodes visited 454880, rotations 11974, height 14
```

Then in `build/at/dsa/03.05/lib/ptree.c`, in `balance()`, delete
everything between `update(n);` and `return n;`, so that it only works out
the node's height and length again:

```
    int b = height(n->left) - height(n->right);
    if (b > 1) {
        if (height(n->left->left) < height(n->left->right))
            n->left = rotate_left(n->left);
        return rotate_right(n);
    }
    if (b < -1) {
        if (height(n->right->right) < height(n->right->left))
            n->right = rotate_right(n->right);
        return rotate_left(n);
    }
```

at the end of a file or a log growing line by line, are what the rotations

## Go deeper

- [Text Buffer Reimplementation](https://code.visualstudio.com/blogs/2018/03/23/text-buffer-reimplementation) by Peng Lyu, Visual Studio Code -
  why its team left an array of lines for a piece table, then put the
  pieces in a red-black tree ("Boost line lookup by using a balanced
  binary tree"), with line break counts in each node.
- [Open Data Structures, section 9.4](https://opendatastructures.org/ods-cpp/9_4_Discussion_Exercises.html) -
  the end of the red-black tree chapter, on AVL trees: the Fibonacci
  argument for a height of at most about 1.44 log n, and the facts, left
  for the reader to prove, that an insert needs at most two rotations and a
  removal can need on the order of log n.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th
  edition - chapter 13, Red-Black Trees, for rotations and the other way to
  balance; chapter 17, Augmenting Data Structures, whose first section keeps
  the size of each subtree in its root to find the ith element, as this
  tree keeps lengths to find the ith byte.
- Charles Crowley, [Data Structures for Text Sequences](https://www.cs.unm.edu/~crowley/papers/sds.pdf) -
  sections 6 and 7: the pieces are a sequence themselves, kept by a
  simpler sequence structure, and with very many pieces he suggests a gap
  buffer or a second level for them; a tree is another answer.
