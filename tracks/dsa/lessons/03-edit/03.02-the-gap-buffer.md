# 03.02 The gap buffer

In one array, every key moves every byte after the cursor. A gap buffer
keeps the text in one array still, but with a stretch of unused room, the
gap, kept where the editing is: a key typed there fills one byte of the
gap and moves nothing.

## Where this fits

![Where 03.02 fits](figures/03.02-map.svg)

This lesson is the second box of module 03's strip, the gap buffer. It
stands behind the same interface as the array of 03.01, so the editor above
it does not change: it picks one structure or the other when it opens a
file, and the gap buffer becomes the default. Below it there is only a
block of memory, which grows by doubling as the array's did. After this
lesson typing in one place costs the same in a file of any size, and the
replay can run the same edits on both structures, which is how this lesson
finds the input that still hurts.

## The idea

![A gap buffer on "the cat sat\n": the gap moves to the cursor once, carrying the bytes between across, then each key fills one byte of it; Backspace widens it again](figures/03.02-gap.svg)

Typing is mostly in one place: a word, then the next, at the same cursor.
In one array each of those keys pays for the whole text after the cursor,
again and again, to open a hole one byte wide. The hole could be opened
once, and wide: keep the unused room of the block in the middle of the
text, right at the cursor, instead of after the end. That room is the
**gap**. The text before the cursor is at the start of the block, the text
after it at the end, and the gap is everything between.

A key typed at the gap goes into its first byte, and the gap is one byte
shorter. Nothing else moves. Backspace takes the byte just before the gap
into it, and the gap is one byte longer. Only an edit somewhere else costs
anything: the gap moves there first, and moving it carries the bytes
between where it was and where it goes across to its other side.

In the figure the file "the cat sat\n" is opened with the gap after it, 16
bytes. The first key at position 4 moves the gap there, carrying "cat
sat\n", 8 bytes, to the end of the block. Then "f", "a", "t" and a space
each fill one byte of the gap: 8 bytes moved for four keys, where the array
moved 32. Typing "!" at 15 carries "cat sat", 7 bytes, back across, and
Backspace after it moves 1.

### `move_gap`

Moves the gap to position `pos`: if `pos` is before the gap, the bytes from
`pos` to the gap go to just before the far end of the gap; if after, the
bytes just after the gap come back to its start. Either way one
`memmove()` of exactly the distance, and that distance is what `DS_STATS`
counts as bytes moved.

### `grow`

When the gap is used up: a new block twice as big, the text before the gap
copied to its start, the text after the gap to its end, and all the new
room between them is the new gap.

### `gap_insert` and `gap_erase`

An insert moves the gap to `pos`, grows the block if the gap is too small,
and copies the bytes into the start of the gap. An erase moves the gap to
`pos` and widens it over the `n` bytes after it.

### `gap_read` and `gap_open`

A read copies what it needs from before the gap, then from after it.
Opening reads the file into a block with 16 bytes to spare, the first gap,
after the text.

### `editorPickAlgo`

`main()` now takes `--algo=array` or `--algo=gap`, the default from here
on, and `editorPickAlgo()` turns the name into the function that opens
that structure.

## How it works

### The invariant, and where a position is

The gap buffer's **invariant**: the text before the gap is `data[0]` to
`data[gap - 1]`, the text after it is `data[end]` to `data[cap - 1]`, and
`gap <= end`. The gap itself, `data[gap]` to `data[end - 1]`, holds nothing
the text needs. So position p of the text is `data[p]` when p is before
the gap, and `data[p + (end - gap)]` after it, which is all `gap_read()`
does. `move_gap()` keeps the invariant by moving bytes and the two edges
together:

```
        memmove(g->data + g->end - k, g->data + pos, k);
        g->gap = pos;
        g->end -= k;
```

### Why nearby edits are cheap

The cost of an edit is the distance from the last edit, not the size of the
text. A key right after the last one is distance 0; a word typed after
moving back a line is the length of that line. Only a jump pays for what it
jumps over, once. That is why typing is linear in the keys, whatever the
file, and edits at random places are not: a random jump in a text of n
bytes is n/3 on average, and n/64 words in a text of n lines is n squared
over a constant.

### Amortized: what doubling buys, and what it does not

When the gap is used up, `grow()` copies the whole text into a block twice
as big, and the new gap is as big as the old block. That copy costs the
length of the text, but it buys that many keys before the next one. Spread
over the keys it pays for, each key costs at most a byte or two of copying:
the cost is amortized, as 01.01's pushes were, constant on average over any
run of keys. It is
not constant for each key. The one key that finds the gap of a 1 GB file
used up copies 1 GB while the person waits.

### An erase goes through the gap too

`gap_erase()` moves the gap to `pos` and then widens it over the bytes
after it:

```
    size_t moved = move_gap(g, pos);
    g->end += n;
```

So Backspace, which erases the byte before the gap, first carries that
byte across the gap (1 byte moved, in the trace above) and then takes it
in. Erasing at the gap's start, with nothing moved, would need a second way
to erase; this keeps one.

## Decide the boundary

This buffer has one gap, which follows the edits. GNU Emacs keeps its
buffers the same way and moves the gap only when an edit comes, not when
the cursor moves, which is why its manual warns that the first edit in a
far part of a large buffer can be slow. An editor with several cursors, or
a replace that changes every match of a word through a file, pays the
whole distance between edits again and again. Splitting the text into
blocks, each with a gap of its own, limits a move to one block, at the
cost of first finding the block. Are your edits in one place at a time, or
in many places at once?

## Break it

Erase without moving the gap first. In `build/at/dsa/03.02/lib/gap.c`, in
`gap_erase()`, change

```
    size_t moved = move_gap(g, pos);
```

to

<!-- verify: patch file=lib/gap.c
-    size_t moved = move_gap(g, pos);
@block
     g->end += n;
-->
```
    size_t moved = 0;
```

The same line is in `gap_insert()`: change only the one in `gap_erase()`.
Then type ">" at the start of "one two three" and Backspace over the "o"
of "two":

<!-- verify: session -->
```
$ make -s
$ printf 'one two three\n' > three.txt
$ printf 'goto 0\ntype >\ngoto 8\nback 1\nprint\n' | DS_TRACE=1 bin/edit --replay - three.txt
trace: gap buffer: insert 0 ">": moved 14 | ">" [15] "one two three\n"
trace: gap buffer: erase 7 1: moved 0 | ">" [16] "ne two three\n"
>ne two three
```

The erase widened the gap over the byte just after it, wherever the gap
happened to be: the "o" of "one", not the "o" of "two". With the line put
back, the same script prints `>one tw three`. Nothing crashed, and the
text is still the right length: the wrong byte is simply gone.

  section 5.2, "The gap method", with its other name, the split buffer,
  and the point that the gap need not move when the cursor does, only when
  an edit comes; section 9.1 sets it beside the array and the linked list.
- [GNU Emacs Lisp Reference Manual, The Buffer Gap](https://www.gnu.org/software/emacs/manual/html_node/elisp/Buffer-Gap.html) -
  a real editor's buffer, and the delay of the first edit far from the
  last.
- [Open Data Structures, 2.5 DualArrayDeque](https://opendatastructures.org/ods-cpp/2_5_Building_Deque_from_Two.html) -
  a list kept as two array stacks back to back, the front one stored
  backwards: the same shape as the text on either side of a gap, with
  add(i, x) costing the distance to the nearer end.
- Cormen, Leiserson, Rivest and Stein, *Introduction to Algorithms*, 4th
  edition, chapter 16, Amortized Analysis - its section on dynamic tables
  proves that a table that doubles when full costs a constant amortized
  per insert.
