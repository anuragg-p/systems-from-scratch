# 03.04 The piece table: a list of pieces

The array and the gap buffer both keep every byte of the text in one block:
opening a file copies all of it, and an edit far from the last one moves
bytes. A piece table moves no text at all. The file stays as it is, every
typed byte goes on the end of a second buffer, and the text is a list of
pieces of the two.

## Where this fits

![Where 03.04 fits](figures/03.04-map.svg)

This lesson is the fourth box of module 03's strip, the piece table. It
stands behind the same interface as the array and the gap buffer, so the
editor does not change, and undo works on it as it is. Underneath are two
buffers and a linked list: the file, mapped into memory by the operating
system rather than read, and a buffer of everything typed since. The gap
buffer stays the default: for plain typing this list is no better. After
this lesson the replay opens a file of any size without copying it, and the
next lesson puts the list in a tree.

## The idea

![A piece table on "the cat sat\n": the original file and the add buffer never change; each edit only changes the list of pieces that says which parts of them, in what order, are the text](figures/03.04-pieces.svg)

Both structures so far pay to keep the text in one block, in order. A
piece table gives that up and keeps two buffers. The **original** is the
file as it was opened, never changed. The **add buffer** holds every byte
inserted since, in the order they were typed, and is only added to. The
text is a list of **pieces**, each a run of bytes from one buffer: which
buffer, where in it the run starts, and how long it is. Read the pieces in
order, and you read the text.

In the figure, the file "the cat sat\n" opens as one piece, `orig 0+12`:
12 bytes of the original from its byte 0. Typing "f" at 4 puts "f" at the
end of the add buffer, at 0, and cuts the piece in two around a new one:
`orig 0+4`, `add 0+1`, `orig 4+8`. No byte of the file has moved. "a", "t"
and a space go on the end of the add buffer, right after the "f", so the
piece `add 0+1` only gets longer, to `add 0+4`. The "!" at 15 cuts
`orig 4+8` and adds two pieces. Backspace drops the piece of the "!", but
not the "!": nothing is taken out of a buffer. So the "." typed next
cannot lengthen a piece, since the add buffer now ends in the orphaned
"!", and starts a piece of its own.

The cost has moved, not gone. A piece knows its length, but not where in
the text it starts. To find position 15 once "fat " is typed, the list is
walked from the first piece, adding up lengths: 4, then 8, then 16, which
passes 15, so position 15 is byte 7 of the third piece. Each edit adds a
piece or two, and every later edit walks past them.

### `buffers_open`

Opens the file and maps it into memory with `mmap()`: the operating system
sets aside addresses for the whole file and reads a page of it only when
something touches that page. Nothing is copied when it opens. A pipe, an
empty file, or anything `mmap()` refuses is read in with `text_load()`
instead.

### `buffers_add`

Puts n bytes on the end of the add buffer, growing it by doubling, and says
where they start.

### `find`

Walks the list from its head, taking each piece's length off the position
until it falls inside a piece; returns that piece, the offset in it, and
the piece before it, for an insert to link after.

### `pieces_insert`

Puts the bytes on the end of the add buffer, finds the place, and then one
of three things: the piece before ends exactly where the new bytes start
in the add buffer, so it gets longer; the place is between two pieces, so a
new piece goes there; or the place is inside a piece, which is cut in two
around the new one.

### `pieces_erase`

Finds the piece the first erased byte is in, then cuts it in two (when all
the erased bytes are inside it), or shortens it, drops the pieces wholly
erased after it, and moves the start of the next one past the rest.

### `pieces_read` and `pieces_open`

A read walks to the piece the position is in and copies from it and the
pieces after it. Opening maps the file and makes one piece of all of it.

## How it works

### The invariant, and two buffers that never change

The piece table's **invariant**: the pieces of the list, in order, each read
from its buffer, are the text; and no piece is empty. Nothing is ever
written into the original, and nothing already in the add buffer is ever
written over. That second rule is what lets a piece be three numbers: the
bytes it names will be there, unchanged, for as long as the table lives.
`buffers_add()` only ever writes past the end:

```
    memcpy(b->add + b->addlen, s, n);
    b->addlen += n;
```

### Typing on makes no new piece

```
    if (off == 0 && prev != NULL && prev->span.buf == ADD && prev->span.start + prev->span.len == start) {
        prev->span.len += n;            /* typing on: the piece before is the end of the add buffer */
```

A key typed right after the last one goes at the end of the piece just
made, and its byte at the end of the add buffer, right after that piece's
bytes: the piece gets one byte longer. So typing a page costs one piece,
not one per key. A Backspace or a key typed elsewhere in between leaves the
add buffer ending in something else, and the next key needs a new piece.

### Why a piece does not know where it is

A piece could keep its position in the text, and finding a position would
be a search, not a walk. But an insert near the start would change that
number for every piece after it. Crowley's paper says the same: the
running total is not kept, because it would all have to be updated after
each edit. The next lesson keeps lengths in a tree, where an edit changes
only the totals on one path.

### The file is mapped, so saving writes a new one

Every `orig` piece points into the file as it was opened. Saving must not
write the new text over that file: POSIX leaves it unspecified whether a
private mapping sees the file change under it, and says that reading a page
past the end of a file that has been cut short is a bus error. So the
editor writes the text to a new file beside the old one and renames it into
place. The old file is whole until the new one is, and the pieces keep
reading it. One thing this changes:

<!-- verify: session -->
```
$ printf 'one\n' > a.txt; ln a.txt b.txt
$ printf 'goto 0\ntype >\nsave\n' | bin/edit --algo=pieces --replay - a.txt
$ cat a.txt b.txt
>one
one
```

`b.txt` was another name for the same file. After the save, `a.txt` names
the new file and `b.txt` still names the old one.

## Decide the boundary

This editor saves by writing a new file and renaming it over the old one,
which keeps the mapped original valid and never leaves half a file on disk.
It costs that hard links to the file are broken, as above, that a symbolic
link is replaced by a plain file, and that the directory must be writable.
kilo writes over the file in place, which keeps links, and could not work
under a piece table that maps that file. A third way is to read the whole
file in when it is opened, as the gap buffer does, and give up opening a
file of any size at once. Which of your files have other names?

In `build/at/dsa/03.04/lib/pieces.c`, in `pieces_insert()`, change

```

```

to

Then type "abc" at the start of "one two", "X" at its end, and "Y" after
"abc":

<!-- verify: session -->
```
$ make -s
$ printf 'one two\n' > two.txt
$ printf 'goto 0\ntype abc\ngoto end\ntype X\ngoto 3\ntype Y\nprint\n' | DS_TRACE=1 bin/edit --algo=pieces --replay - two.txt 2>&1 | grep -v undo: | tail -3
trace: piece list: insert 3 "Y": walked 2 | add 0+4 "abcX" | orig 0+8 "one two\n" | add 3+1 "X"
abcXone two
X
```

"Y" went on the add buffer at 4, after the "X" at 3, and the piece
`add 0+3` before the cursor grew by one byte, to `add 0+4`. Its fourth byte
is the "X". The text now has an "X" where "Y" was typed, and the "Y" is in
no piece at all. With the line as it was, the "Y" gets a piece of its own,
`add 4+1`, and the text reads `abcYone two`. Put the line back.
