# 03.03 Undo and redo: two stacks

Until now Ctrl-Z only said that the editor keeps no history. This lesson
gives it one: every change to the text is noted as an edit, the edits go
on a stack, and undo takes the last one off and does its opposite. A
second stack holds what was undone, for redo.

## Where this fits

![Where 03.03 fits](figures/03.03-map.svg)

This lesson is the third box of module 03's strip, the undo stacks. It sits
between the editor and the text: every change the editor makes is noted
here as well as made, and undo and redo make their changes through the
same interface as the editor's own, so they work on whichever structure
holds the text, the array, the gap buffer, and the two still to come. The
stacks themselves are the growable array of 01.01, taken from the library
as it is. After this lesson Ctrl-Z and Ctrl-Y undo and redo on the
terminal, and the replay takes `undo` and `redo`.

## The idea

![Undo and redo as two stacks: typing "fat " is one edit, four Backspaces another; undo moves each to the undone stack doing its opposite, redo moves one back, and a new edit forgets what was undone](figures/03.03-stacks.svg)

The obvious way to undo is to keep a copy of the text before each change.
It is simple, and it is correct, and it costs the whole text every time.
The typing script of 03.02 types 32000 keys into a file of 6.3 MB: a copy
per key would be 200 GB, and a copy per word still several gigabytes.

What changed is far smaller than the text. Typing "fat " at position 4 is
fully described by "insert 4 'fat '"; four Backspaces at the end of "the
fat cat\n" by "erase 8 'cat\n'", with the bytes kept, so they can be put
back. Call each of these an **edit**. Its opposite is as easy to write
down: the opposite of inserting bytes at p is erasing that many from p, and
the opposite of erasing bytes from p is inserting the same bytes at p.

Edits are undone in the reverse of the order they were made: the last one
first. That is a **stack**, a list that is only added to and taken from at
one end, its top. Each change pushes an edit onto the done stack. Undo pops
the top edit, does its opposite to the text, and pushes it onto a second
stack, the undone stack. Redo pops that, does the edit again, and pushes it
back onto the first. A new edit empties the undone stack: an edit undone
there was made to a text that has changed since, and doing it again would
put bytes where they no longer belong.

The figure runs this on "the cat\n": type "fat " at 4, go to the end,
Backspace four times, undo twice, redo once, then type ">" at the start and
try to redo again. Four keys make one edit, and four Backspaces another:
undo works on edits, not on keys.

### `undo_init`

Two empty stacks, each a growable `Array` of `Edit`.

### `undo_note`

Notes a change the editor has just made. First it forgets everything on
the undone stack. Then, if the change was typed and continues the edit on
top (a key typed where the last one ended, or a Backspace just before the
last one), it adds the bytes to that edit; otherwise it pushes a new edit.

### `undo_undo` and `undo_redo`

Pop the top edit of one stack, make its opposite (or itself, for redo)
through `text_insert()` or `text_erase()`, push it onto the other stack,
and say in a `Change` what was done and where the cursor goes.

### `editorUndo`

Ctrl-Z and Ctrl-Y call it. It undoes or redoes, then keeps the editor's
view of the text right, as after any change, and moves the cursor to where
the change was, scrolling to it if it is off the screen. In
`editorProcessKeypress()`, any key that does not type ends the edit being
typed, and `replay()` does the same for any command but `type` and `back`.

## How it works

### What one edit is

`undo_note()` joins a typed change to the edit on top only when it
continues it:

```
    if (typed && u->typing && top != NULL && top->erase == erase &&
        (erase ? pos + n == top->pos : top->pos + top->bytes.len == pos)) {
```

A typed insert continues an insert that ends where it starts; a typed erase
(Backspace) continues an erase that starts where it ends. `u->typing` says
the edit on top is still being typed: any key that does not type, a cursor
move, a paste, a save, an undo, clears it through `undo_break()`. So "fat",
then an arrow key, then "cat" are two edits even if they touch.

### The invariant

The stacks' **invariant**: doing the opposites of the edits on the done
stack, top first, turns the text back into the file as it was opened; and
the edits on the undone stack, top first, can be done again to the text as
it is now. Undo and redo each move one edit across and change the text to
match, so both halves still hold. A new edit changes the text without
going through the undone stack, which breaks the second half for every
edit on it; that is why `undo_note()` starts by forgetting them all:

```
    while (u->undone.len > 0)           /* a new edit: what was undone is gone for good */
        forget(array_pop(&u->undone));
```

### Backspace keeps its bytes backwards

Each Backspace takes the byte before the last one taken, so a run of them
meets the bytes from the end. Putting each new byte at the front would move
all the others, as in 03.01. Instead an erase that is typed pushes them on
the end, in the order they come, `"\n"`, `"t"`, `"a"`, `"c"`, marks itself
`backwards`, and is turned round once, by `straighten()`, when it is
undone. A push on the end of a growable array costs the same however long
it is, and so does a pop: each stack is the array of 01.01, with `len` as
its top, which is why undo costs one edit's bytes, never the depth of the
history.

## Decide the boundary

This history is a line: when a new edit comes after some undos, what was
undone is forgotten. Vim keeps it instead. Its undo is a tree: the undone
changes become a branch, `:undolist` lists the branches, and `g-` and `g+`
step through every state the text has been in, by time. It costs keeping
every edit for as long as the file is open, and a way to show the tree.
Would you rather lose an undone change for good, or have to find your way
through every version of the text?

## Break it

Keep the undone edits when a new edit comes. In
`build/at/dsa/03.03/lib/undo.c`, at the top of `undo_note()`, delete the
two lines that forget them:

```
    while (u->undone.len > 0)           /* a new edit: what was undone is gone for good */     <- delete this line
        forget(array_pop(&u->undone));                                                            <- and this one
```

"hello" was typed at position 0, undone, and then ">" typed at 0. The redo
puts "hello" back at position 0, as if nothing had happened since: before
the ">", not after it where it was typed. With the lines in place the redo
does nothing and the text is `>ab`. Undo something larger, and the
position can be past the end of the text:

<!-- verify: session exit=2 -->
```
$ printf 'goto 2\ntype xyz\nundo\ngoto 0\ndelete 3\nredo\n' | bin/edit --replay - ab.txt
edit: gap buffer: insert at 2, past the end of 0 bytes
```

"xyz" was typed at 2 and undone; then all three bytes of the text were
deleted, and the redo asks to insert at 2 in a text of 0 bytes. The check
in `text_insert()` stops it there; without it, the gap buffer would move
bytes from past the end of its block into the text. Put the two lines back.
