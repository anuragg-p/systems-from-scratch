# 00.02 Measuring growth

One run of a program says little about how it will do on a bigger input.
This lesson's harness runs a command on inputs that double in size and
divides each time by the one before: that ratio says how the time grows,
and so how long ten or a thousand times the input will take.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

The growth harness is this module's second box in the strip, next to the
slow and fast paste of 00.01. It is not part of any tool and uses nothing
of the library: it makes an input, runs a command on it, ours or the
system's, and times it. Every later module measures with it: freq's two
ways of finding a word in module 01, the sorts of module 02, and each tool
after them. After this lesson any program can be put on the bench, and how
its time grows read off in one command.

## The idea

![The doubling test on both versions of paste, a row at a time: the strcat version takes about 4 times as long at each doubling, the other stays at a few milliseconds.](figures/00.02-race.svg)

In 00.01 the slow paste took 0.109 s on the book. That alone says nothing:
a tenth of a second is fine. What told us something was the next two runs,
on two and four books, at four times the time per doubling. That is the
whole method, and this lesson automates it.

Suppose a program's time on an input of size n is about a times n to some
power k, written a n^k. The constant a is the machine: its speed, its
compiler, its disk. Double n and the time becomes a (2n)^k, which is 2^k
times what it was. So the **ratio** of the two times is 2^k, and the
machine's a cancels out. A ratio of 2 means the time grows as n does
(**linear**), 4 as n squared (**quadratic**), 8 as n cubed; the power is
log2 of the ratio. That is why the times below will differ on your machine
and the ratios will not. The power is the program's **order of growth**,
written n^2 or n, with the constant left out: on a big enough input it
decides everything, whatever the constant.

Two things get in the way of measuring it. A run of a few milliseconds is
mostly the time to start a program, which does not grow with n at all, so
its ratio says nothing. And the inputs have to come in any size, and be the
same bytes on every run and every machine, or the times are not comparable.

### `grow.py`

`bench/grow.py` runs a command on an input of n units, times it, keeps the
fastest of three runs, doubles n and runs it again, until a run takes more
than two seconds (`--limit`) or n passes `--max`. The input's path goes
after the command's last argument. It prints a ratio only where both runs
took 20 ms or more, and its last line is a verdict: the middle of the last
three ratios, as a power of n. It runs the command with `LC_ALL=C` and its
output thrown away, and takes an exit status of 1 as success, as look, grep
and diff use it to say "none" or "different". `./learn bench dsa` runs it
on the project at a lesson.

### `gen.py`

`data/gen.py KIND N` prints N units of one kind of input, made from the
book. The harness uses `text` unless `--input` says otherwise: words of the
book picked at random, ten or so to a line, with commas and full stops, and
one word in ten made up from syllables, such as "tavomi". The made-up words
come from a stock that grows with N, so the number of different words keeps
growing with the text, as it does in a real library. There are kinds for
the later tools too: lines, sorted lines, numbers, a dictionary. Its random
numbers come from a small generator of its own (splitmix64), so a seed gives
the same bytes on any machine and any Python.

## How it works

### Twenty milliseconds

Every run includes starting the program: 2 to 3 ms here, the whole of the
fast paste's first rows. A program whose time is a n^k plus a start-up cost
gives ratios of 2^k only once a n^k is much bigger than the start-up. So
the harness keeps out of the verdict any ratio where either run is short:

```
MIN_SECONDS = 0.02
```

and the strcat table above shows its first ratio at 128000 words, where
the runs are 30 and 111 ms.

### The fastest of three, and the middle of three

Noise only ever adds time: another program running, a cold cache. So of
three runs of the same input the fastest is the nearest to the program's
own cost, and that is the one kept. A run over a second is not repeated:
it is long enough for the noise to be small, and repeating it would cost
the most. The verdict then takes the last three ratios, from the largest
inputs, where the growth shows best, and keeps the middle one, so one odd
row cannot decide it:

```
    last = sorted(ratios[-3:])
    r = last[len(last) // 2]
    k = math.log2(r) if r > 0 else 0.0
```

k is the power of n. For an n log n program, like the good sorts of module
02, the ratio is a little over 2 and k a little over 1.

## Decide the boundary

The harness times whole runs with a clock: what a person waiting for the
program feels, start-up, cache misses and other programs included. The
counters of `DS_STATS=1` count the work instead: exact, the same on every
machine and every run, and blind to what a step costs. A byte `strlen()`
reads is far cheaper than a word fetched from main memory, and both count
as one. When the clock and the count disagree about how a program grows,
which one do you believe?

## Break it

The ratio is the power of n only because n doubles. In
`build/at/dsa/00.02/bench/grow.py`, near the end of `main()`, change

```
            n *= 2
```

to

            n += opts["start"]
