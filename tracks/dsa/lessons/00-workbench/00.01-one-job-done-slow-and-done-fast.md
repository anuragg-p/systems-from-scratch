# 00.01 One job, done slow and done fast

This track builds ten Unix tools in C, each on a library of data structures
you write and each checked against the real tool. This first lesson shows
the whole track, then does one small job two ways that differ in a single
line: one stops finishing as its input grows, the other does not.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

The map has a column for each module, its tool at the top. Under the
tools run the structures more than one tool stands on: the library (an

Follow one command through it: `bin/freq data/book.txt`, from module 01.

uniq -c | sort -rn` prints the same counts, which is how the track checks
freq, and the growth harness of the next lesson runs it on inputs twice as
big, again and again, and says how its time grows.

The order is the order the structures are needed in. freq is first
because the array and the hash table are under almost everything: the
array's rail runs on to every later tool but route, the hash table's to
grep, spell, diff, make and git. sort is second because sorted order and
the heap come back, the heap in route. git is last because it stands on
the most: the array, the hash table, sorting, the heap, diff and deflate.
Each tool is held to the system's own: the same bytes as sort and grep, a
diff that patch applies, a file gunzip opens.

This module builds no structure. It sets up the workbench: the build, the
library's first file, a book to run on, and a way to tell a program that
will keep finishing from one that will not.

## The idea

![Joining one, two and three with commas: strcat reads everything joined so far before each piece, 22 bytes to copy 13; remembering the end reads none.](figures/00.01-strcat.svg)

The job is `paste -s`: join the lines of a file into one line, with a tab
between them, or the characters `-d` gives. The obvious way to write it in
C keeps the line as a C string, its bytes followed by a 0 byte, `'\0'`, and
adds each piece to the end with `strcat()`. It works, and on a small file
it is instant.

But `strcat()` is not told where the string ends. It finds out the way
`strlen()` does: it reads from the first byte until it meets the `'\0'`. So
before each piece it reads everything joined so far. Joining `one`, `two`
and `three` with commas is five pieces, three lines and two commas, and
finding the end reads 0, 3, 4, 7 and 8 bytes: 22 bytes read to copy 13.
Each piece costs as much as all the pieces before it. A file with twice the
lines has twice as many pieces, each reading a line twice as long, so it
costs four times as much.

The fix is to remember where the end is: keep the length in a variable,
copy each piece there, and add its length. Nothing is read twice.

### `add`

`bin/paste` does the job both ways, with the same output: `--algo=strcat`
finds the end with `strlen()` before each piece, as `strcat()` would, and
`--algo=end`, the default, remembers it. They differ in one line of
`add()`, which also counts the bytes it reads. The rest of
`tools/paste/paste.c` is paste itself: the `-d` list, one line out for each
file, standard input for none. Only `-s` is here.

### The workbench

The lesson also brings what every later tool is built with. The Makefile
archives the files of `lib/` as `build/libds.a` and reads every
`tools/*/tool.mk`, each of which links one tool into `bin/`. Our tools are
always `bin/<name>`; the bare name, `paste`, is the system's. `lib/ds.h` is
the library's header, and `lib/util.c` holds what every tool needs and
none is about: `die()` prints `paste: message` and exits with status 2, as
sort and grep do; `xmalloc()` never returns NULL; `open_input()` opens a
file, or standard input for `-`. It also prints the counters: every tool
and structure counts its own work, and with `DS_STATS=1` in the
environment prints a `stats:` line for each as it exits. `data/book.txt`
is The Adventures of Sherlock Holmes, 562404 bytes, the text every tool
runs on.

the program. The counters say where the time went:

To copy 2.2 million bytes, the slow way read 107 billion, 4.0 times as
many at each doubling. `strlen()` is fast, over 60 billion bytes a second
here, and it is still the whole cost. At this rate a hundred books, 56 MB,
would take 0.109 seconds times ten thousand: about 18 minutes.

## How it works

### The one line

The whole difference is in `add()`:

```
        end = strlen(out);        /* look at every byte so far for the NUL */
```

against

```
        end = len;                /* or just remember it */
```

The second one is right only because of an **invariant**, a fact the code
keeps true at every step: `len` is the number of bytes in the line, and
`out[len]` is its `'\0'`. The two lines after the copy keep it:

```
    out[end + n] = '\0';
    len = end + n;
```

The slow version keeps the same invariant but works the length out again
every time.

### Linear and quadratic

The fast version's work is **linear**: it grows in proportion to the input.
The slow version's is **quadratic**: piece k reads the k pieces before it,
so n pieces read about 1 + 2 + ... + n, which is n(n+1)/2, and the work
grows with the square of the input: ten times the input, a hundred times
the work. On the book both are still quick; the difference is in how they
grow, which the next lesson measures.

### Room to spare

`reserve()` makes room for the line by doubling its block whenever it is
too small. The block starts at 4096 bytes, so the 2.2 MB line of four books
moves to a bigger block ten times, not once for each of its 95375 pieces.
Module 01 builds that idea into a structure of its own and counts what it
costs.

## Decide the boundary

<!-- verify: mention names="strcpy()" outside reason="a C library function this project does not call" -->

This code keeps the length beside the C string. The C library's own strings
carry no length: `strlen()`, `strcat()` and `strcpy()` all find the end by
looking for the `'\0'`. That keeps a string to one pointer, but makes its
length a walk over it, and no string can hold a 0 byte. Most later
languages store the length with the bytes, as every structure in this track
will, and pay one more word per string and an interface that must pass the
length along. When a string will be added to again and again, or may hold
any byte at all, which do you want to be the one value you pass around?

## Break it

A C string cannot hold a 0 byte. Give paste a line with one inside it, and
look at the bytes each version prints:

<!-- verify: session -->
```
$ printf 'one\0two\nthree\n' | bin/paste -s | od -c
0000000    o   n   e  \0   t   w   o  \t   t   h   r   e   e  \n
0000016
$ printf 'one\0two\nthree\n' | bin/paste -s --algo=strcat | od -c
0000000    o   n   e  \t   t   h   r   e   e  \n
0000012
$ printf 'one\0two\nthree\n' | paste -s - | od -c
0000000    o   n   e  \0   t   w   o  \t   t   h   r   e   e  \n
0000016
```

The fast version and the system's paste keep all of `one\0two`. The slow
one copied all seven bytes too, but its next `strlen()` stopped at the 0
byte, three bytes in, so the tab was written there, over the 0 byte, and
`three` after it, over `two`. Not knowing where the end is costs time on every
input, and on this one it costs bytes. (macOS's paste needs the `-` to read
standard input.)
