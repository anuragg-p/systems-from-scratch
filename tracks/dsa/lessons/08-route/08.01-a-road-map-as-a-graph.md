# 08.01 A road map as a graph

Every search in this module asks one question over and over: which roads
leave this junction? This lesson reads the map into a form that answers it
in one step, adjacency lists, and uses them for the first job on a real
map: finding which parts of it no road joins together.

## Where this fits

![Where 08.01 fits](figures/08.01-map.svg)

route is module 08's tool, the column lit at the top of the map, and this
lesson is the first box in the strip under it: the road graph. Below it is

After this lesson route reads central London and tells you how its streets

## The idea

The map is central London, taken from OpenStreetMap
([openstreetmap.org/copyright](https://www.openstreetmap.org/copyright)),
whose data is open under the Open Database License (ODbL 1.0). It is
`tools/route/london.map`, and it holds two lists. The first gives 17260
**junctions**, each as a pair of numbers: metres east and metres north of
the map's south-west corner. The second gives 22498 **roads**, each as a
line `A B METRES`: the two junctions it joins and its length along its
bends. A road goes both ways. A point where a road only bends is not a
junction; the map keeps only ends and the points where three or more roads
meet.

That is a **graph**: things (the junctions, which books call vertices or
nodes) and links between pairs of them (the roads, called edges), each
link with a number on it (its length, called its weight). The number of
roads at a junction is its **degree**.

A search stands at a junction and needs its roads. The obvious way to find
them is the file's own list: read all 22498 roads and keep those with this
junction at one end. That is right, and reads every road for every
junction looked at: for each junction of London once, 17260 times 22498
reads, 388 million.

The fix is to keep each junction's roads together, so that finding them
costs only as much as there are of them. That is an **adjacency list**:
for each junction, the list of roads that leave it. The map below is
`tools/route/tiny.map`, a dozen junctions made up to follow by hand, and
its lists:

![tiny.map as a graph: 12 junctions and 21 roads, each with its length. Below it the arrays first, to and len: junction 3's five roads are arcs 10 to 14, from where first says 3's arcs start to where 4's start](figures/08.01-lists.svg)

The lists are three arrays for all the junctions together. Each road
becomes two **arcs**, one out of each of its ends, so 21 roads
are 42 arcs. The arcs out of junction 0 come first, then those out of 1,
and so on: `to[a]` is where arc a leads and `len[a]` its metres.
`first[j]` says where junction j's arcs start, and `first[j+1]` where they
stop. Junction 3's roads are arcs 10 to 14: to 0, 1, 2, 4 and 9.

### `build_lists`

`roadgraph_load()` reads the file into the plain list of roads, as the file
has it, and then calls this to build the arrays. It takes two passes over
the roads. The first counts each junction's roads, and adds the counts up
so that each junction's start is the sum of the counts before it. The
second puts each road's two arcs in place, with a cursor for each junction
that says where its next arc goes.

### `pieces`

`--info` uses the lists for its last line: how many **pieces** the map
falls into, a piece being junctions that roads join, with no road out of it
(books say connected component). It is a flood fill: mark a junction that
is in no piece yet and push it on a stack; then keep taking a junction off
the stack, marking and pushing each junction its roads reach that has no
mark. When the stack is empty the piece is whole. With `--graph=edges` it
finds a junction's roads the obvious way instead, by reading every road.

## How it works

### Counting, then placing

The first pass of `build_lists()` counts each road at both its ends, one
place along:

```
for (long r = 0; r < g->m; r++) {
    g->first[g->road_a[r] + 1]++;
    g->first[g->road_b[r] + 1]++;
}
for (int j = 0; j < g->n; j++)
    g->first[j + 1] += g->first[j];
```

After the count, `first[j+1]` holds junction j's degree; after the running
sum, `first[j]` holds the degree of every junction before j, which is
exactly where j's arcs start. That is why `first[]` has n+1 entries: the
last is 2m, the end of the last junction's arcs, and `first[j+1]` is always
there to stop at. The **invariant** the rest of the module relies on: the
arcs out of junction j are `to[first[j]]` up to `to[first[j+1] - 1]`, all
of them and nothing else. The second pass keeps it by giving each junction
a cursor, `next[j]`, that starts at `first[j]` and moves on one with each
arc placed; when every road is placed, each cursor has stopped exactly at
the next junction's start.

Three arrays instead of a list per junction: three allocations instead of
17260, no pointer stored per arc, and each junction's arcs side by side in
memory. The layout is often called compressed sparse row. The price is that
it is built once: adding a road would move every arc after it.

### Marked when pushed

In `pieces()` a junction gets its piece number when it goes on the stack,
not when it comes off. So no junction goes on the stack twice, and the
stack never holds more than n junctions, which is the size it is given.
Marking it on the way off instead would let it be pushed once from each of
its neighbours that came off the stack before it did. The order in which the fill visits junctions does
not matter here, only that it reaches all of them; the next lesson's search
is the same loop with a queue in place of the stack, and there the order is
the whole point.

## Decide the boundary

route packs the adjacency lists into arrays, built once when the map is
read: a junction's roads cost its degree to find, and the map two ints per
arc. Another program could keep an n by n table with a mark for every pair
of junctions a road joins, an adjacency matrix: one look answers "is there
a road from a to b?", but London's would have 298 million entries, all but
45 thousand empty, and finding a junction's roads would read a row of
17260. A map whose roads close and reopen while it is used would want a
growable list per junction (the array of 01.01). Does your graph change
while you search it, and is it dense or, like a road map, almost empty?

## Break it

Count each road at one end only. In `build/at/dsa/08.01/lib/roadgraph.c`,
in `build_lists()`, delete the line that counts the second end:

-    g->first[g->road_b[r] + 1]++;
-->

Then build and ask for the tiny map and London again:

```

$ bin/route --info tools/route/tiny.map

       1 junction  with 0 roads
       3 junctions with 1 road
       6 junctions with 2 roads
       2 junctions with 3 roads
pieces 2: junctions in each, the largest first: 11, 1
$ bin/route --info tools/route/london.map
junctions 17260, roads 22498, 1621.4 km of road
    2310 junctions with 0 roads
    7658 junctions with 1 road
    7036 junctions with 2 roads
     256 junctions with 3 roads
pieces 3336: junctions in each, the largest first: 9602, 124, 46, 38, 28, 28, 27, 26, 25, 25, ...
```

The map file lists every road with its smaller junction first, so a
junction is counted only for its roads to higher numbers. On the tiny map
junction 11 has no road to a higher number: it gets no arcs at all and is
a piece of its own. The second pass still places all 42 arcs, so each
junction's arcs run on into the next junction's share and overwrite them.
It does not crash: `first[12]` is now 21, so the arcs are all written
inside the array of 42, and the half past 21 is never read. The map just
falls apart, into 3336 pieces in London. Nothing checks the invariant at
run time; a wrong count gives a wrong graph, silently. Put the line back
and run `make -s` again.
