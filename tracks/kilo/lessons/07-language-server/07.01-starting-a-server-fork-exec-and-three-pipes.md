# 07.01 Starting a server: fork, exec and three pipes

kilo starts clangd as a child process, with a pipe to its standard input and
a pipe from its standard output, and a third pipe whose only job is to say
whether the start worked. This lesson starts the server and stops it again;
nothing is said to it yet.

## Where this fits

![Where 07.01 fits](figures/07.01-map.svg)

This lesson builds the start piece, at the bottom right of the map, and
brings in the server beside it: both are this lesson's on the map. The
editor now sits between two outside worlds: the terminal above it, and
below it a program that knows the file's language. The start piece is
handed the file's name once; it finds the server for it, starts it as
another process joined to the editor by two pipes, and at exit stops it
and waits until it is gone. Behind it are the operating system's calls
that make processes and pipes. After this lesson opening a C file starts
clangd and quitting stops it; the editor edits and saves as before, and a
file with no server is edited as if the module were not there.

## The idea

kilo knows nothing about C. It cannot tell that a name is misspelt, or where
a function is defined. clangd can: it is the clang compiler's front end kept
running as a **language server**, a program that reads the code of one
language as a compiler does and answers an editor's questions about it, in
messages of the **Language Server Protocol** over its standard input and
output. So kilo has to run a second program and hold the other ends of its
input and output.

A **file descriptor** is the small number a process uses for an open file,
terminal or pipe: 0 is its standard input, 1 its standard output, 2 its
standard error. A **pipe** is a one-way channel in the kernel with two
descriptors, one to write into and one to read from. Starting clangd takes
four steps:

- `pipe()` three times: one pipe for clangd's input, one for its output, one
  more for the start itself.
- `fork()` makes a copy of the calling process, the **child**: the same
  code, a copy of the memory, and the same descriptors, the same numbers
  meaning the same pipes. Both copies return from `fork()`, the child with
  0, kilo with the child's process id, its **pid**.
- In the child, `dup2()` puts the read end of the first pipe on 0 and the
  write end of the second on 1. kilo closes the ends it does not use.
- The child calls `execvp()`, which replaces the program running in that
  process with clangd, found in `PATH` as a shell finds it. The descriptors
  stay. clangd reads 0 and writes 1, and never learns they are pipes to
  kilo.

Here are the descriptors at each step, with the numbers they really get:

![Starting clangd at 07.01, step by step: kilo alone with 0, 1 and 2; three pipe() calls make 3 and 4 (in), 5 and 6 (out), 7 and 8 (err); fork() copies all of them into the child; the child moves 3 to 0, 6 to 1 and /dev/null to 2, and kilo closes 3, 6 and 8, keeping 4 to write to the server and 5 to read from it; exec closes every end marked close-on-exec, and the child is clangd with 0, 1 and 2 only](figures/07.01-fork-exec.svg)

The third pipe answers a question `fork()` leaves open. `execvp()` either
replaces the child and never returns, or fails and returns (clangd is not
installed), and the parent cannot see which. So kilo marks every pipe end
**close-on-exec** (the flag `FD_CLOEXEC`): the kernel closes it when an
exec succeeds. The child holds the write end of the third pipe and kilo
reads its other end. If the exec works, that write end is closed, no writer
is left, and kilo's `read()` returns 0 bytes, end of file. If it fails, the
child writes its `errno`, the 4 bytes of an `int`, into the pipe and exits.

![The third pipe after fork(). Left: exec works and closes the child's write end, so kilo's read() returns 0 bytes. Right: exec fails (KILO_LSP=no-such-server), the child writes errno 2 in 4 bytes and exits with 127, and kilo says lsp: cannot start no-such-server: No such file or directory](figures/07.01-exec-fails.svg)

The code is a new file, `lsp.c`, with a header, `lsp.h`, for the one
function `kilo.c` calls and the one it calls back.

### `lspServerFor`

The table of servers kilo knows, `LSPDB`, has two entries, C (`.c`, `.h`)
and C++ (`.cpp`, `.hpp`, `.cc`), and both run `clangd`. This returns the
first entry with an ending that ends the file's name, or NULL.

### `lspSpawn`

The steps above, with standard error pointed at `/dev/null`: clangd writes
a log there as it works, which on the terminal would print over kilo's
screen. Then it waits on the third pipe. On success it keeps its two ends in
`L.in` and `L.out`, makes them **non-blocking**, so that a read or write
that cannot go on returns at once instead of waiting, and returns the pid.

### `lspEnd`

Stops the server: closes both pipes, gives it `ms` milliseconds to exit,
kills it if it has not, and waits for it either way.

### `lspStart`

Called once, from `main()`, after the file is read. The environment variable
`KILO_LSP` names a command to run instead of the table's, for any file; set
and empty, it means no server. It registers `lspStop` to run at exit and
says `lsp: started clangd (pid N)`, or, when the start fails, why.

### `lspStop`

At exit, `lspEnd()` within `LSP_STOP_MS`, 500 milliseconds.

Outside these: `struct lspState L`, all the client knows, as `E` is for the
editor; `lspSay()`, a message with any control byte made a `?`; `lspNow()`,
a clock for timeouts; and in `kilo.c`, `#include "lsp.h"` and the call in
`main()`. The Makefile builds `kilo.c lsp.c`.

## How it works

### Every end nobody uses is closed

A `read()` on a pipe returns end of file only when no process anywhere
holds its write end open. After `fork()` every end is open twice, so each
side closes what it does not use. kilo, right after the fork:

```
    close(in[0]); close(out[1]); close(err[1]);
```

and the child's copies are closed by the exec, because of one line before
the fork:

```
    for (j = 0; j < 6; j++) fcntl(fds[j],F_SETFD,FD_CLOEXEC);
```

Leave one open and something waits forever. If kilo kept `err[1]`, its
read of the third pipe would never see end of file, even after a good exec.
If clangd kept `in[1]`, the write end of its own input, kilo closing its end
at exit would no longer tell it to stop. Break it shows the first.

### A pid of 0

`L.pid` is 0 when no server runs, and that 0 is dangerous: to `waitpid()` a
pid of 0 means "any child in my process group", and to `kill()` "every
process in my process group", kilo included. So every function that stops
the server first checks that there is one:

```
    if (L.pid == 0) return 0;
```

While the module was being written, a server whose pipe broke was stopped
twice, the second time with `L.pid` already 0, and the editor said
`exited (status 0)` over the real message; this check fixed it. The
**invariant** is that `L.pid` is not 0 exactly while there is a child that
has not been waited for: `lspEnd()` sets it to 0 only after `waitpid()`
returns, and a failed start has already waited for its child in
`lspSpawn()`.

Waiting matters. A child that exits stays in the process table, a
**zombie** holding its exit status, until its parent collects the status
with `waitpid()`, which is **reaping** it. `lspEnd()` closes the pipes,
which ends clangd's input, then asks `waitpid()` with `WNOHANG` every 10 ms
whether it has gone; past the deadline it sends `SIGKILL`, which no program
can catch, and waits. `atexit()` runs `lspStop()` before the core's
`editorAtExit()`, registered earlier, so the terminal is put back only once
the server is gone, at most 500 ms later.

### The resize signal across fork()

Between `fork()` and the exec, the child is a copy of kilo, signal handlers
and all. A resize in that moment would make the child run
`handleSigWinCh()` from 02.01 and draw a whole screen: onto the terminal,
or, after the `dup2()`, into the very pipe kilo reads the server from. So
`lspSpawn()` blocks SIGWINCH before forking:

```
    sigprocmask(SIG_BLOCK,&winch,&old);
```

A blocked signal is not lost: it waits, **pending**, until it is unblocked.
The parent unblocks it as soon as `fork()` returns, and a resize that came
meanwhile is drawn as usual. The child sets SIGWINCH back to its default
action and unblocks it too, because the set of blocked signals is inherited
across exec: with that line left out, the server starts with signal 28,
SIGWINCH on macOS, still blocked (checked with a small server that lists
its blocked signals).

## Decide the boundary

kilo runs the server as another process and talks to it through pipes. A
crash or a hang in clangd cannot take the unsaved file down with it, any
program in any language can be the server, and the editor stays the small
C program it was. The cost is that everything said between them must be
turned into bytes and back, and every answer waited for. An editor could
instead link the language's tools into itself as a library: calls are
direct and fast, the two share memory, and they share crashes too, since a
bad pointer in the library is a bad pointer in the editor. Whose bugs may
take your file down?

## Break it

Leave the pipes open across the exec. In `build/at/kilo/07.01/lsp.c`, in
`lspSpawn()`, delete the line that marks them close-on-exec:

<!-- verify: patch file=lsp.c
-    for (j = 0; j < 6; j++) fcntl(fds[j],F_SETFD,FD_CLOEXEC);
-->
```
    fds[3] = out[1]; fds[4] = err[0]; fds[5] = err[1];
    for (j = 0; j < 6; j++) fcntl(fds[j],F_SETFD,FD_CLOEXEC);    <- delete this line
```

and run it:

<!-- verify: session hangs=3 -->
```
$ ./learn run kilo --at 07.01 -- sum.c
Running kilo as it stands at 07.01 (Starting a server: fork, exec and three pipes). Its files are in build/at/kilo/07.01/
lsp.c:120:20: warning: unused variable 'j' [-Wunused-variable]
  120 |     int fds[6], e, j;
      |                    ^
1 warning generated.
```

After the warning about `j`, nothing: no screen. kilo is stuck in
`lspSpawn()`, before its first frame; Ctrl-Q does nothing, as nothing reads
it, and nor does Ctrl-C, since raw mode has turned off the keys that send
signals. clangd started fine, but the exec kept every pipe end open in it
(`lsof -p` on that clangd lists descriptors 3 to 8), the third pipe's write
end too, so kilo's `read()` waits for an end of file that only clangd's
death can bring.

From another terminal, stop the newest clangd, this one: `pkill -n clangd`.
At once kilo carries on and draws its screen, which ends:

<!-- verify: skip reason="the bottom two rows of the editor's screen after the server is killed from another terminal; captured on a 12 x 72 pseudo-terminal with track.py's Screen" -->
```
sum.c - 8 lines                                                      1/8
lsp: started clangd (pid 74795)
```

The read returned 0 bytes, which `lspSpawn()` takes for a good exec: the
message is about a server already gone. Keys pressed while it hung waited
in the terminal and are read now; if Ctrl-Q was all you pressed, kilo quits
at once, and `lspEnd()` reaps the dead clangd on the way out. Put the line
back.

## Go deeper

<!-- verify: mention names="posix_spawn() socketpair()" outside reason="POSIX calls this project does not make; named as alternatives" -->

- [POSIX, `posix_spawn()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/posix_spawn.html) - fork and exec in one call, with "file actions" such as dup2 and close done in the child. Look for what happens when the exec fails after the call has returned: the child "shall exit with exit status 127", which tells the parent less than the third pipe does.
- [POSIX, the exec functions](https://pubs.opengroup.org/onlinepubs/9799919799/functions/exec.html) - "File descriptors open in the calling process image shall remain open in the new process image, except for those whose close-on-exec flag FD_CLOEXEC is set", and there is no return from a successful exec.
- [POSIX, `socketpair()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/socketpair.html) - "an unbound pair of connected sockets", each end both read and written: one pair could do the work of the two pipes.
- [The Language Server Protocol, 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/) - the section "Implementation Considerations" lists the ways a server may be reached: stdio, as here, a named pipe, a socket, or Node's IPC, chosen by a command-line argument, and `--clientProcessId` so a server can exit when its editor dies.
