# 07.04 Keys and the server at once: poll()

kilo now waits for the keyboard and the server in one call, `poll()`,
which sleeps until either has something. An answer from the server is seen
the moment it arrives, and an idle editor stops waking up to look.

## Where this fits

![Where 07.04 fits](figures/07.04-map.svg)

This lesson builds the wait piece, at the left of the row of the client's
features, just under the core's key reading. Before the core reads a key,
it hands the wait piece the keyboard; the wait piece sleeps until a key or
the server's pipes need attention, lets the messages piece below it write
and read, and returns when a key is there. The core reads the key exactly
as before. After this lesson an answer reaches the screen about 0.2 ms
after the server writes it, and an idle kilo with a server running does
not run at all.

## The idea

kilo has two things to wait for, the keys and the server, and one thread to
do the waiting. Since 07.02 it has waited for a key with a `read()` that
gives up after a tenth of a second, and looked at the server each time it
gave up. That works, at two costs. kilo wakes ten times a second while
nothing happens. A build of kilo that counted its wake-ups woke 53 times
in a run left idle for 5 s with a small scripted server, the run the
figure below shows; with clangd, it woke 98 times in 10 idle seconds. And
an answer that arrives just after a look waits for the next one: from the
scripted server writing its answer to the screen showing it, a median of
45.5 ms and at worst 100.3 ms in 20 runs (56.4 ms and 101.9 ms in a
second 20).

`poll()` waits for several things at once. kilo gives the kernel an array
of descriptors, each with the events it wants to hear of, `POLLIN` for
"there is something to read" and `POLLOUT` for "there is room to write",
and a timeout, here -1, for none. The kernel puts the process to sleep until
at least one of them is ready, then fills in `revents`, what happened to
each. A pipe whose writer has closed counts as readable: the read will
return end of file.

kilo's array has two entries, sometimes three: the keyboard and the
server's output, always, and the server's input only while bytes wait in
`L.tx` to be written. When `poll()` returns, kilo writes what it can and
reads what has come, both without blocking, then goes back to sleep, unless
the keyboard is ready, in which case it returns and the core reads the key.

With `poll()` the counting build did not wake once in the idle seconds,
with either server. It woke twice in the whole run with the scripted
server, and twice with clangd: once for the server's answer to
`initialize`, and once for the Ctrl-Q that ended the run. The delay from
answer to screen fell to a median of 0.2 ms, at worst 0.7 ms (1.2 ms in
the second 20 runs).

### `lspWaitKey`

The loop above. While a server runs, it builds the array, calls `poll()`,
and after any wake-up calls `lspPump()` from 07.02, which writes and reads
whatever it can; when the keyboard is ready it returns. With no server, it
returns at once. In `editorReadKey()` it takes the place of 07.02's
`lspPump()` call:

```
    lspWaitKey(fd);     /* the keyboard and the language server at once */
    while ((nread = read(fd,&c,1)) == 0);
```

The second line is the core's own, back as it was before the module.

### A server that does not read, in `lspSend`

kilo never blocks on the server, so a server that stops reading would make
the bytes waiting for it in `L.tx` grow without end. Before it queues a new
message, `lspSend()` checks how much is already waiting, and past 8 MB
stops the server with `lsp: clangd is not reading; stopped`.

## How it works

### POLLOUT only while something waits

```
        if (L.tx.off < L.tx.len) {
            p[2].fd = L.in;
            p[2].events = POLLOUT;
            n = 3;
        }
```

A pipe with room in it is always ready for writing. Ask about the server's
input when there is nothing to write, and `poll()` answers "ready" at once,
every time, and kilo never sleeps: Break it does exactly that. So the third
entry is there only while `L.tx` holds bytes, a message the pipe did not
take whole; then kilo wakes when the server has read some and there is room
again, writes more, and drops the entry once the queue is empty.

### After any wake-up, both directions

`lspWaitKey()` does not look at which entry woke it before it calls
`lspPump()`. It does not need to: both pipes are non-blocking, so a write
with no room and a read with nothing to read return at once, and trying
both costs two calls. A key and a message that arrive together are both
dealt with in one wake-up, the message first.

### Signals, and no server

```
        if (r == -1 && errno == EINTR) continue;
```

A signal that arrives while `poll()` sleeps, such as the resize, can end it
early with `EINTR`. The resize handler has already drawn the new screen by
then, so the loop simply calls `poll()` again. With no server running, at
any time, because none was started, the start failed or the server has
gone, `while (L.pid)` is false at once and the core's own loop waits for
the key, a read at a time, exactly as before the module existed.

The **invariant** is that kilo never makes a call that can block on the
server. Both pipe ends have been non-blocking since 07.01; every read and
write of them returns at once; and the one place kilo sleeps is `poll()`,
which always includes the keyboard. The only waits on the server are the
ones kilo chooses and bounds: the start, which waits for the exec; a server
that has closed its pipe, which `lspGone()` gives 100 ms to exit before it
kills it; and the stop at exit, at most 500 ms. The 8 MB bound is the
other half: never blocking means never refusing a message either, and
without a limit a server that stops reading would take kilo's memory
instead of its time.
That matters once kilo sends the file's text, from 07.05 on: with a 5 MB
file and a server that has stopped reading, keys are still answered, and
once more than 8 MB is waiting, the server is stopped.

## Decide the boundary

kilo does everything on one thread, and `poll()` decides what to do next.
Nothing is shared between threads, so nothing needs a lock, and the order
of events is plain: a key, then a message, then a frame. The cost is that
anything slow holds everything: while kilo parses a 16 MB answer, it reads
no keys. Another editor could give the server a thread of its own that sits
in a blocking `read()` and parses what comes, which is simple to write and
never holds up the keys. But every structure both threads touch then needs
a lock, and here that is the editor's whole state: `E`, a single global
read and written everywhere in `kilo.c`, and the screen itself. How much do
the two sides share?

## Go deeper

<!-- verify: mention names="select()" outside reason="another way to wait for many descriptors; this project uses poll()" -->

- [POSIX, `poll()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/poll.html) - the events (`POLLIN`, `POLLOUT`, and `POLLHUP`, for "a pipe or FIFO has been closed by the last process that had it open for writing"), a timeout of -1 to "block indefinitely", and `EINTR`.
- [POSIX, `select()`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/select.html) - the older call for the same job, with three sets of descriptors as bitmaps, "inherently limited from operating on file descriptors larger than FD_SETSIZE".
- [Linux, epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html) - the kernel keeps the list of descriptors, so a program watching thousands does not hand them all over on every call; read the part on level-triggered and edge-triggered events.
- [FreeBSD and macOS, kqueue(2)](https://man.freebsd.org/cgi/man.cgi?query=kqueue&sektion=2) - one queue for descriptors, signals, timers and processes: `EVFILT_PROC` with `NOTE_EXIT` would tell kilo when the server exits.
- [libuv, Design overview](https://docs.libuv.org/en/v1.x/design.html) - an event loop built on these ("epoll on Linux, kqueue on OSX and other BSDs"), and how one turn of it works out how long to block for I/O from its timers.
