# 07.02 Messages: Content-Length and JSON-RPC

A pipe carries bytes, not messages. Every message between kilo and the
server is a header that gives its length, an empty line, and exactly that
many bytes of JSON. This lesson writes the first message of the protocol,
`initialize`, and reads clangd's answer back, whole, as bytes.

## Where this fits

![Where 07.02 fits](figures/07.02-map.svg)

This lesson builds the messages piece, the wide row of the map just above
the server. Everything the client will do goes through it: the pieces above
hand it messages to send, and it hands them each message that has come in
whole. Below it are the two pipes of 07.01 and the server at their other
end. It knows how a message is framed, and nothing of what one means. After
this lesson kilo says its first words to clangd, and the message line shows
how long the answer was and how it begins.

## The idea

At 07.01 kilo holds a pipe to clangd and a pipe from it, but a pipe keeps
no boundaries. If clangd writes a 2008-byte answer with one `write()`, kilo
may read it in three pieces; if clangd writes two answers quickly, one
`read()` may return both. The reader needs to know where each message ends.

The Language Server Protocol says so with a header in front of each
message: lines of the form `Name: value`, each ended by `\r\n`, then an
empty line, then the body. The header that must be there is
`Content-Length`, the body's length in bytes. Here is the first message
kilo sends at this lesson, byte for byte, with each `\r\n` written out:

<!-- verify: skip reason="the bytes of one message as the server read them, with \r\n written out and kilo's pid in it" -->
```
Content-Length: 108\r\n
\r\n
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"processId":88879,"rootUri":null,"capabilities":{}}}
```

The body is **JSON**, a text format for data: objects of `"key": value`
pairs in braces, arrays in brackets, strings in double quotes, numbers,
`true`, `false` and `null`. Its shape is **JSON-RPC 2.0**, which has three
kinds of message. A **request** has an `id`, a `method` and its `params`,
and must be answered. A **response** carries the same `id` and either a
`result` or an `error`. A **notification** has a method and params but no
id, and gets no answer. `initialize` is a request: kilo's pid, and what the
editor can do, which here is nothing yet.

![The initialize frame as a strip of bytes: Content-Length: 108, \r\n, the empty line \r\n, then the 108 bytes of the body, counted. Under it the three shapes of JSON-RPC: a request (id, method, params), a response (the same id, result or error) and a notification (method, params, no id)](figures/07.02-frame.svg)

Reading is the other half. kilo keeps every byte the server has sent in a
buffer, `L.rx`, and after each read looks at its front: if a whole message
is there, header and all `Content-Length` bytes of body, it takes it off and
acts on it, and looks again; if not, the bytes wait for the next read. Here
is a short answer, written by a small scripted server in pieces of 10, 30
and 131 bytes:

![A reply of 171 bytes written in three pieces, 0.255 s apart: kilo's buffer holds 10 bytes after the first read, 40 after the second, 171 after the third, and only then is the whole message, a header of 23 bytes and a body of 148, taken off the front, leaving the buffer empty](figures/07.02-split-reads.svg)

kilo looks at the server whenever it is waiting for a key and the key read
times out, every tenth of a second: `editorReadKey()` now calls `lspPump()`
each time its `read()` returns nothing. 07.04 does better.

### `jsonQuote`

kilo writes its messages with printf-style formats. The one thing a format
cannot do safely is put text inside quotes: a `"`, a backslash or a newline
in the text would end the string or break the JSON. This writes text as a
JSON string, those characters escaped. Nothing sends text yet.

### `lspFrame`

Is a whole message at the front of the buffer? It reads the header a line at
a time, each through `lspHeaderLine()`, which takes the length from
`Content-Length` (in any case of letters) and ignores any other header.
It returns the whole message's length, 0 when more bytes are needed, or -1
when the header is damaged.

### `lspSend`

Puts the header and the body at the end of `L.tx`, the bytes waiting to go,
and calls `lspFlush()`, which writes as many of them as the pipe takes now.
`lspRequest()` builds a request with the next id and sends it.

### `lspRead`

Reads what the server has written, at most a megabyte at a time, onto the
end of `L.rx`, then takes off every whole message and hands each to
`lspHandle()`. At this lesson that says
`lsp: N bytes from clangd:` and the body's first 50 bytes.

### `lspInitialize`

Sends `initialize`, right after the start, and notes its id in `L.initid`.

Outside these: `lspPump()`, which writes what waits, reads what came, and
draws the screen again if a message changed it; `lspGone()`, which reaps a
server that has closed its pipe and says how it ended; `lspKill()`, which
stops one that cannot be talked to; and the buffer helpers. The Makefile
adds `json.c`.

## How it works

### A damaged header stops the server

```
        if (n == -1) {
            lspKill("lsp: bad message from %s; stopped");
```

When `lspFrame()` cannot read a header, the stream is lost: with no length
to go by, there is no telling where the next message starts, and guessing
would act on bytes from the middle of one. So kilo stops the server and
says `lsp: bad message from clangd; stopped`. A header with no
`Content-Length`, two that differ, a sign or a letter in the number, or a
lone `\n` for `\r\n` all end that way. A body that is not good JSON, which
the next lesson can tell, will only be dropped, since its header still said
where it ends.

### Caps on the header and the body

```
        if (x > LSP_BODY_MAX) return -1;    /* too long, or absurd */
```

The length is checked as each digit is read, against 16 MB. Without the
check, a length of 26 digits would overflow the `long`, which C leaves
undefined, and any huge length that fit would have kilo wait for a body
that never comes, keeping every byte that does. A body of exactly 16 MB is
read, and the message after it too. The header has a cap of its own,
`LSP_HEADER_MAX`, 4096 bytes: that much with no empty line is no header,
and the server is stopped instead of being waited on for ever.

### Writes the pipe does not take

The pipe to the server is non-blocking (07.01), and holds only so much. A
`write()` may take part of a message and return how many bytes it took, or
take none and fail with `EAGAIN`. Blocking would be worse: a server that
stopped reading would freeze the editor inside `write()`. So `lspFlush()`
writes what it can and leaves the rest in `L.tx`, and the next look writes
more. The message goes out whole, in order, however many writes it takes.

### SIGPIPE

Writing to a pipe whose reading end is closed, because the server died or
closed its input, sends the writer the signal SIGPIPE, and its default
action ends the process: kilo would vanish mid-edit with the file unsaved
and the terminal raw. `lspInitialize()` sets SIGPIPE to be ignored before
the first write, so the write fails with `EPIPE` instead, and `lspFlush()`
treats that as the server gone: a server that closes its input and stays
is stopped, with `lsp: NAME exited (signal 9)`.

The **invariant** is that `L.rx` always starts at the start of a message.
Its front moves only by whole messages:

```
        L.rx.off += n;
```

and whatever cannot be framed stops the server, whose `lspEnd()` throws the
buffer away with it. So every call to `lspFrame()` can read a header from
the first byte.

## Decide the boundary

The protocol puts the length in front of the message. The reader never
scans the body, the body may hold any bytes at all, and one call can tell
whether a message is complete. But one bad header loses the whole stream:
everything after it is bytes with no known start. A protocol could instead
mark the end of each message, with a newline after it, as many line-based
protocols do: a reader that meets damage skips to the next newline and is
back in step, but the body may never contain the mark, so a newline inside
it must be escaped, and the reader must look at every byte to find the end.
Can you trust the other end to count?

## Break it

Make the header promise one byte more than the body has. In
`build/at/kilo/07.02/lsp.c`, in `lspSend()`, add one to the length:

<!-- verify: patch file=lsp.c old="(unsigned long)len);" new="(unsigned long)len+1);" -->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
    hlen = snprintf(head,sizeof(head),"Content-Length: %lu\r\n\r\n",(unsigned long)len+1);
```

```
./learn run kilo --at 07.02 -- sum.c
```

The message line says `lsp: started clangd (pid N)`, and goes on saying it.
Ten seconds later it has not changed:

<!-- verify: skip reason="the bottom two rows of the editor's screen ten seconds after it started, captured on a 12 x 72 pseudo-terminal with track.py's Screen" -->
```
sum.c - 8 lines                                                      1/8
lsp: started clangd (pid 77715)
```

clangd read the header, then the 108 bytes of the body, and is waiting for
the 109th, the last one the header promised. kilo has nothing more to send,
so the message is never complete and never answered. The editor itself
works on, as it does with any server that stays silent. At Ctrl-Q kilo
closes the pipe, clangd sees the end of its input and exits, and kilo quits
as quickly as before. Nothing in the bytes could have told clangd that the
header was wrong: the length is the only word on where a message ends. Put
the line back.

## Go deeper

- [JSON-RPC 2.0 Specification](https://www.jsonrpc.org/specification) - the request, notification and response objects, and that "The Server MUST NOT reply to a Notification"; a response has a result or an error, never both. Error -32601 is "Method not found".
- [The Language Server Protocol, 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/) - "Base Protocol", "Header Part": Content-Length is required, Content-Type has a default, and every header field is ended by `\r\n`.
- [RFC 9110, HTTP Semantics, 8.6 Content-Length](https://www.rfc-editor.org/rfc/rfc9110.html#name-content-length) - the header the protocol copies, a "decimal non-negative integer number of octets", and the warning that a recipient "MUST anticipate potentially large decimal numerals and prevent parsing errors due to integer conversion overflows".
