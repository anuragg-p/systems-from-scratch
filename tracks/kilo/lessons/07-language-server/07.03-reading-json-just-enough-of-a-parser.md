# 07.03 Reading JSON: just enough of a parser

kilo learns to read JSON: a small reader that turns a message's body into a
tree of values, and a few getters that read that tree safely whatever shape
it has. With them kilo can tell which request an answer belongs to, and it
says when clangd is ready.

## Where this fits

![Where 07.03 fits](figures/07.03-map.svg)

This lesson builds the JSON piece, in the row of the client's features, just
above the messages piece. The messages piece hands it the body of each
message that has come in whole; it gives back a tree, which the rest of the
client reads and then frees. It knows nothing of kilo or of the protocol:
it would read any JSON. After this lesson kilo knows an answer from a
request, matches an answer to the request it sent, and reads the server's
name and version out of its answer to `initialize`.

## The idea

At 07.02 the message line shows the first 50 bytes of clangd's answer,
`{"id":1,"jsonrpc":"2.0","result":{"capabili`. To act on it kilo needs to
know that it is a response, that its id is 1, and what is inside `result`.
That means reading JSON, and JSON nests: a value is one of six kinds, null,
a boolean, a number, a string, an array or an object, and arrays and
objects hold values, which may be arrays and objects in turn. clangd's
2008-byte answer holds 117 values, six levels deep.

A grammar where things hold things of the same kind is read naturally by
**recursive descent**: one function for each kind of value, each reading
what it recognises and calling the others for what is inside it.
`jsonValue()` looks at the next character and decides: a `"` starts a
string, a `[` or `{` an array or object, a `-` or a digit a number, and
`n`, `t` or `f` the words `null`, `true` and `false`. `jsonList()` reads an
array or an object: the opening bracket, then values, each read by calling
`jsonValue()`, separated by commas, then the closing bracket. When one of
those values is an array, `jsonValue()` calls `jsonList()` again, and the
stack of calls grows as the text nests. Step through `{"a":[1,"x"]}`:

![That text read by jsonParse(), a step at a time: where the reader is in it, and the calls on the stack with the depth each has reached, the object at depth 1 and the array inside it at depth 2; the last step shows the check that stops a 65th level](figures/07.03-descent.svg)

What comes back is a **tree**: one `struct json` for each value, with its
type and its number or string. An array's or object's elements are a list,
the first in `child` and each one's `next` the one after it, and a member of
an object carries its `key`. Here is clangd's answer, trimmed to the members
kilo reads at this lesson, and its tree:

![clangd 21's answer to initialize trimmed to {"id":1,"jsonrpc":"2.0","result":{"serverInfo":{"name":"clangd","version":"Apple clangd version 21.0.0 (clang-2100.1.1.101) mac+xpc arm64-apple-darwin25.6.0"}}} on the left; on the right the tree of struct json it becomes, each object's members a list of children with their keys, and the path result, serverInfo, name to the string "clangd"](figures/07.03-tree.svg)

Reading the tree has to be safe against anything a server sends: a member
missing, a number where a string should be, `null` where an object should
be. So each getter takes NULL, or a value of the wrong type, and gives back
NULL or a default. `jsonGet(j,"serverInfo")` on something that is not an
object is NULL; `jsonStr()` of NULL is the default you pass. The code that
reads a message chains them, with no check between:

```
    const char *name = jsonStr(jsonGet(info,"name"),L.name);
```

The code is the rest of `json.c`, which knows nothing of kilo, and a few
lines of `lsp.c`.

### `jsonString`

Reads a string at its opening quote and returns its bytes decoded: each
escape such as `\n` or `é` becomes the bytes it stands for, in UTF-8,
the encoding kilo's text is in.

### `jsonNumber`

Checks the text against JSON's grammar for a number, then lets `strtod()`
work out its value.

### `jsonList` and `jsonValue`

The two functions of the descent above, the one calling the other.

### `jsonParse`

The whole message: exactly one value, white space around it allowed and
nothing else, or NULL. `jsonFree()` frees a tree.

### The getters

`jsonGet()` finds an object's member by its key, `jsonIs()` tests a type,
`jsonInt()` gives a number that is a whole `int` or a default, and
`jsonStr()` a string or a default.

### `lspInitialized`

The answer to `initialize`. If its `result` is not an object, the server
did not start properly and is stopped. Otherwise it takes the name from
`serverInfo.name`, and from `serverInfo.version` the first word that
starts with a digit, and says `lsp: clangd 21.0.0 ready`.

`lspHandle()` now parses each body. A body that is not JSON is dropped and
counted. A message with a method is something the server sends of its own
accord, and is left alone for now; one without is an answer, and its `id`
says which request it answers.

## How it works

### A cap on the depth

```
    if (++r->depth > JSON_MAX_DEPTH) return NULL;
```

The reader calls itself once a level: each `[` or `{` costs a call to
`jsonValue()` and one to `jsonList()`, two frames on the C stack, and the
stack is a fixed size, 8 MB for the main thread on this Mac. Text is cheap
to write and deep nesting costs nothing to send, so without a cap a server
decides how deep kilo's stack goes. `JSON_MAX_DEPTH` is 64, ten times the
six levels of clangd's answer; a message nested 64 deep is read, 65 deep is
an error at once, and so is one nested 300000 deep. The cap bounds
`jsonFree()` too, which calls itself once a level on the way down.

### A cap on the values

A body may be 16 MB, and `[0,0,0,...]` of that size is about eight million
values. Each is a `struct json` of its own, so the tree would take about
450 MB. `jsonNew()` counts the values of a message and gives up past
`JSON_MAX_VALUES`, a million.

### Strings: one allocation, and UTF-8 out

```
    out = o = malloc(q-p+1);
```

A string's decoded bytes are never more than its text: `\n` is two
characters for one byte, `é` six for two, and one `\u` escape gives at
most three bytes. So the reader finds the closing quote, allocates the
text's length once, and decodes into it. JSON escapes a character beyond
U+FFFF the way UTF-16 does, as a **surrogate pair** of two `\u` escapes,
the first in D800 to DBFF, the second in DC00 to DFFF: one character, four
bytes of UTF-8. Half a pair alone stands for no character, and becomes
U+FFFD, the replacement character, EF BF BD. So does `\u0000`: the decoded
string ends with a `'\0'` for C's string functions, and a zero inside it
would cut it short.

![What the reader makes of four escapes: \n is 0A; é is C3 A9; the pair 😀 is one character, F0 9F 98 80; a lone \ud83d is U+FFFD, EF BF BD](figures/07.03-escapes.svg)

A raw control byte inside a string, a newline say, is an error: JSON allows
those only as escapes.

### Numbers: the grammar first

```
    j->number = strtod(buf,NULL);
```

`strtod()` reads more than JSON allows: `01` as 1, `0x1A` as 26, `1.` as
1, all of which JSON forbids. So `jsonNumber()` walks the grammar itself (an
optional minus, then `0` or a digit 1 to 9 and more digits, then an
optional fraction and exponent, each with at least one digit) and only then
copies those characters into a buffer for `strtod()`, which needs a C
string: the body has no `'\0'` after the number. A number longer than 63
characters is an error.

The **invariant** is that `jsonParse()` returns a whole tree or nothing,
and that one call, `jsonFree()`, frees a whole tree. Every way out of the
reader that is not a success frees what it has built; in `jsonList()`:

```
bad:
    jsonFree(list);
    return NULL;
```

Each element is linked into the list as soon as it is read, so freeing the
list frees them too. A caller never sees half a tree, and never has to
know how far a bad message got.

### Which request an answer belongs to

```
    n = method ? 0 : jsonInt(id,0);
```

An answer is a message with no method. Its id must be a whole number that
fits an `int` (`1.0` is 1; `1.5`, `"1"` and `null` are not ids at all), and
it counts only when kilo is waiting for that id. Anything else is ignored.

## Decide the boundary

kilo builds a tree of every message, then reads the few members it wants.
The reader is simple and the code that uses it is simpler, chains of
getters, but each message is allocated whole even when two members are
wanted: for clangd's answer to `initialize`, 117 values to read three
strings. A reader could instead go through the text once and report what it
meets as it goes, "an object starts", "a key, `serverInfo`", "a string",
with no tree: nothing allocated, any size of message, but every use must
then keep track of where it is in the nesting, in code of its own. How big
are the messages, and how much of each do you read?

## Break it

The depth check is there for a server that sends something absurd, so be
that server. Write this script as `build/at/kilo/07.03/deep.sh`: a header,
a body of 200000 `[` and 200000 `]`, and then `cat`, which reads whatever
kilo sends and keeps the server alive:

<!-- verify: patch file=deep.sh create
@block
-->
```
#!/bin/sh
printf 'Content-Length: 400000\r\n\r\n'
printf '%200000s' '' | tr ' ' '['; printf '%200000s' '' | tr ' ' ']'
cat > /dev/null
```

<!-- verify: session -->
```
$ chmod +x build/at/kilo/07.03/deep.sh
```

Run kilo with it as the server,
`KILO_LSP=./deep.sh ./learn run kilo --at 07.03 -- sum.c` (`./learn run`
starts kilo in the lesson's folder, where the script is). The message line
says `lsp: started deep.sh (pid N)` and stays so: the message came, was 200000
levels deep, was dropped at its 65th, and the editor edits as before. Quit
with Ctrl-Q.

Now take the check out. In `build/at/kilo/07.03/json.c`, in `jsonList()`,
delete the line:

<!-- verify: patch file=json.c
-    if (++r->depth > JSON_MAX_DEPTH) return NULL;
-->
```
    json *list, *last = NULL, *item;

    if (++r->depth > JSON_MAX_DEPTH) return NULL;    <- delete this line
```

and run it the same way:

<!-- verify: session exit=245 wait=3 -->

```
$ KILO_LSP=./deep.sh ./learn run kilo --at 07.03 -- sum.c
Running kilo as it stands at 07.03 (Reading JSON: just enough of a parser). Its files are in build/at/kilo/07.03/

```

The screen appears, `lsp: started deep.sh (pid N)`, and about a second
later kilo is gone: the shell's prompt comes back where the cursor was.
`./learn` passes on how kilo ended as its exit status, 245, which is 256
minus 11, and 11 is SIGSEGV, the signal for a bad memory access: the calls
ran off the end of the stack. The terminal is still raw, so type `reset`
and press Enter, though it may not show. On this Mac a small program
calling the reader without its check got through 58090 levels and no more,
about 140 bytes of stack a level. Put the line back.

## Go deeper

- [RFC 8259, The JSON Data Interchange Format](https://www.rfc-editor.org/rfc/rfc8259) - section 6 on numbers ("Leading zeros are not allowed"), section 7 on strings, where a character past the Basic Multilingual Plane "is represented as a 12-character sequence, encoding the UTF-16 surrogate pair", section 8.2 on lone surrogates, whose effect "is unpredictable", and section 9, "An implementation may set limits on the maximum depth of nesting".
- [JSONTestSuite](https://github.com/nst/JSONTestSuite) - files of JSON that a parser must accept (`y_`), must reject (`n_`) or may do either with (`i_`), written for the article "Parsing JSON is a Minefield", which it links.
- [The Unicode FAQ, UTF-8, UTF-16, UTF-32 and BOM](https://www.unicode.org/faq/utf_bom.html) - "What are surrogates?", how a pair becomes one code point, and why "Unpaired surrogates are invalid in UTFs".
