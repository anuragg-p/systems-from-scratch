# 07.05 Telling the server what you see: didOpen and didChange

Once clangd has answered initialize, kilo tells it which file is open and
gives it the whole text as the editor holds it, unsaved changes and all.
Each time the keys pause it sends the text again, if it no longer matches
a copy of what it sent last. At exit it ends the session in the protocol's
order.

## Where this fits

![Where 07.05 fits](figures/07.05-map.svg)

This lesson builds the sync piece, which keeps the server's idea of the
file the same as the screen. It reads the editor's rows, the text a save
would write, and hands its messages to the messages piece below, which
frames them and writes them down the pipe. The wait piece tells it when the
keys have paused. Nothing new shows on the screen yet, but from now on the
server works on the text you see, and the next two lessons ask it about
that text.

## The idea

At 07.04 the message line says `lsp: clangd 21.0.0 ready`, and that is all
clangd knows: kilo has not said a word about any file. Delete a letter of a
variable's name and do not save: the file on disk still compiles, and the
mistake exists only in kilo's rows. A server that read the file from disk
would answer questions about a text you are no longer looking at. So the
editor sends the text, and once a file is open, what the editor sent is the
file as far as the server is concerned.

After initialize's answer kilo sends **initialized**, a notification that
ends the handshake, then **didOpen**, another notification, with four
things: the file's name as a URI, its language (`"c"`), a **version**
number, 1, and the whole text. From then on kilo
keeps a **copy**: the text it last sent. Whenever the keys pause, kilo makes
the text from the rows again and compares it with the copy. If the two
differ it sends **didChange** with the whole new text and the next version,
and the new text becomes the copy.

"The keys pause" means 300 ms with no key. Each key starts the 300 ms
again, so a burst of typing is one message, sent after its last key:

![The nine keys of " /* ok */" on a time line, typed in 0.26 s: the 300 ms wait starts again at each key and runs out only after the last, and one didChange leaves 302 ms after it. Nine keys, one message](figures/07.05-pause.svg)

Two rules finish the session. A request from the server is answered with
the protocol's error -32601, "method not found": kilo does none of what a
server may ask, and says so rather than leave it waiting. And at Ctrl-Q
kilo sends **shutdown**, a request, waits for its answer, sends **exit**, a
notification, and waits for the server to end, all within half a second.

![One session between kilo and clangd: initialize and its answer; initialized (52 bytes); didOpen with the whole text, version 1; one didChange, version 2, after a burst of keys; at Ctrl-Q, shutdown (44 bytes), its answer, null (38), and exit (33). Sizes from one run](figures/07.05-session.svg)

### `lspOpen`

This sends didOpen. It makes the copy with `editorRowsToString()`, which
`editorSave()` uses for what it writes to disk, sets the version to 1,
quotes the text with `jsonQuote()` (07.02) and sends it with `lspNotify()`,
`lspRequest()` without an id. `lspInitialized()` calls it after sending
initialized, having read in the server's answer whether it takes changes
at all: a sync kind of 0, None, in its `textDocumentSync` means no
didChange is sent.

### `lspUri`

A **URI** names the file the way a link names a web page: `file://`, then
the absolute path, which `lspAbsolute()` makes with `realpath()` (for a
file not saved yet, from the current directory and the name). `lspUri()`
writes every byte that is not a letter, a digit or one of `- . _ ~ /` as
`%` and two hex digits: the space in `sam ple` becomes `%20`. Nothing left
in a URI then needs quoting in JSON.

### The pause, in `lspWaitKey`

07.04's wait gains a deadline, 300 ms from the moment kilo starts waiting
for a key. Until it passes, poll() waits only for the time that is left;
when poll() returns with nothing, `lspPause()` runs once, and the wait goes
on with no deadline, as at 07.04.

### `lspSendText`

At the pause: the text again, compared with the copy, and a didChange if
they differ.

### `lspSendChange`

Queues the didChange, or puts it in the place of one still waiting whole.

### `lspNotFound`

The error for a request from the server, with its own id sent back.

### `lspStop`

Shutdown, exit, the process's end, each waited for with `lspWaitServer()`,
a poll() on the server alone that gives up at the deadline. Initialize also
says `"didSave":false` now: a save tells the server nothing new.

## How it works

### A copy to compare with, not a note of each edit

```
if ((size_t)len == L.textlen && memcmp(text,L.text,len) == 0) {
    free(text);
    return;
}
```

kilo could have told the server about each edit from inside every function
that changes a row. It compares instead, and no edit function has a hook.
Nothing can be missed: whatever changed the rows, the next pause finds it.
And nothing is sent for what changes nothing: arrow keys send no message,
nor does an `x` typed and deleted within the pause, although the status bar
says `(modified)`.

The copy is also what the server's answers are about. Every position it
sends back, an error's line and column in 07.06, counts in the text it was
sent, which can be a pause behind the rows. The **invariant**: `L.text` is
byte for byte the text of the last didOpen or didChange kilo queued for the
server. It is set in two places only, `lspOpen()` and `lspSendText()`, each
time to exactly the text it then quotes and sends.

### The pause

```
long long pause = lspNow()+LSP_PAUSE_MS;
...
if (r == 0 && !paused) {
    paused = 1;
    lspPause();
}
```

kilo calls `lspWaitKey()` before it reads each key, so each key sets the
deadline afresh. Measured with a timing proxy between kilo and clangd: nine
keys, one didChange, 301 to 302 ms after the last key. Short enough that
the server has your text well inside half a second; long enough that a
burst of keys is one message.

### A waiting change is replaced

A slow server may still have the last didChange waiting in kilo's queue
when the next is ready, and sending both would have it parse a text already
out of date. So `lspSendChange()` writes the new message over the old,
provided no byte of the old has gone: a message half written cannot be
taken back, and `lspFlush()` forgets its place as soon as it starts to go.
With a server made slow on purpose, versions 2 and 4 arrive and 3 never
does.

### Goodbye, in half a second

`lspStop()` runs before the terminal is put back (atexit() calls the
functions it was given last first), so you wait for it with the terminal
still raw, and it kills the server at 500 ms. clangd goes at once: Ctrl-Q
to kilo's exit took 0.026 s, and 0.013 to 0.025 s with the tees in
between. A server that never reads costs 0.504 to 0.510 s.

## Decide the boundary

kilo sends the whole text each time. It cannot drift: whatever went wrong
before, the next didChange puts the server's text right. But the bytes grow
with the file.

<!-- verify: fact cmd="wc -c < kilo.c | tr -d ' '" expect=36993 -->
`kilo.c` at this lesson is 36993 bytes, and one key typed into it sends a
didChange of a little over 38 KB. clangd says in its answer that it takes
incremental changes too: an edit as a range and its new text, a few dozen
bytes. A client that sends those must describe every edit exactly, in the
server's columns. One wrong offset, and the server's text differs from the
screen from then on, with nothing to notice it: every error it reports is
about another file. How big are the files, and how often do they change?

## Break it

Make the pause zero. In `build/at/kilo/07.05/lsp.c`, change the limit:

<!-- verify: patch file=lsp.c old="#define LSP_PAUSE_MS 300" new="#define LSP_PAUSE_MS 0" -->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
#define LSP_PAUSE_MS 0              /* no key for this long: the keys have paused */
```

Run kilo with the script as above, and type the same nine keys on the third
row. The second terminal fills with didChange frames as you type, versions
2 to 10, each the whole file with the third row one character longer. Quit,
and count them:

<!-- verify: skip reason="the log of the editor's run above; a replay cannot type into the editor (checked by hand, the pause 0, with clangd 21)" -->
```
$ grep -c textDocument/didChange build/at/kilo/07.05/to.log
9
```

With a deadline of 0, poll() returns at once each time kilo starts to wait
for a key, so the pause comes before every key, and every key that changed
the text sends all of it. In `kilo.c` that would be 38 KB a key, each
parsed by clangd. Put the line back.

## Go deeper

- [The Language Server Protocol 3.17, Text Document Synchronization](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_synchronization) - the three kinds a server can ask for, None, Full and Incremental, and that a client cannot opt out of didOpen, didChange and didClose; [didOpen](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_didOpen), after which "the document's content is now managed by the client".
- [TextDocumentContentChangeEvent](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocumentContentChangeEvent) - the two forms of a change: a range and its text, or only "the new text of the whole document", which is all kilo sends.
- [Shutdown](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#shutdown) and [exit](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#exit) - why there are two: shutdown asks the server to stop work but not to exit; exit ends it, with status 0 only if shutdown came first.
