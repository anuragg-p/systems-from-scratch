# 08.03 One Ctrl-Z, one thought: steps

A step is now a run of keys of one kind, typing or deleting, so one Ctrl-Z
takes back a word, not a letter. And undo and redo put the cursor back where
the step began or ended.

## Where this fits

![Where 08.03 fits](figures/08.03-map.svg)

This lesson builds the steps piece, at the left of the row under the core,
fed by the key handler down the left side of the map. Every key passes
through it before it acts, and it decides whether that key ends the step
the history is filling or carries it on; the records still go into the
history as before, only grouped differently. After this lesson a word typed
in one go is one Ctrl-Z, a row typed into many times is kept once, and the
cursor goes back to where the step began.

## The idea

At 08.02 every key is a step. Type a sentence of sixty characters and it
takes sixty Ctrl-Zs to take back, each one leaving the cursor where it was.
That is not how anyone thinks of what they did. They typed a sentence, then
deleted a word, then pressed Enter.

So a **step** is now a **run** of keys of one kind with no other key
between them. There are three kinds of key:

- typing: a printable character, Tab, or a byte above 127 (part of a
  character such as an e with an acute accent);
- deleting: Backspace, Ctrl-H, Delete;
- other: every other key, Enter, the arrows, Ctrl-S, Ctrl-Z among them.

A key of another kind than the keys before it ends the open step, and an
other key always does. A step is opened only by its first record, so a key
that changes nothing, an arrow say, makes no step; Enter's records make a
step of their own, which the next key closes. These kinds are VS Code's;
Vim's steps are its commands, as Decide the boundary shows. Run it's eight
keys make three steps:

![The eight keys of Run it on a line, each with its kind under it: Down, other; a, n, d and a space, typing; Enter, other; Backspace twice, deleting. A bracket over each step: the four typed keys, Enter, the two Backspaces. 8 keys, 3 steps](figures/08.03-runs.svg)

A run of typing changes one row many times, and every change used to make a
record of the row as it was just before. Only the first is needed: it holds
the row as it was before the whole run. So `undoSave()` leaves a `U_CHG` of
a row out when the open step's last record is already of that row. This is
Vim's rule: "When saving a single line, and it has been saved just before,
it doesn't make sense saving it again. Saves a lot of memory when making
lots of changes inside the same line." Vim checks its ten last changes;
kilo checks one.

![The bytes the history holds after a line of 60 characters is typed into an empty row: 57 as one step, one step, one record and the empty row it kept; 5190 as 60 steps, a step and a record for each character and the row as it was before each one](figures/08.03-one-record.svg)

And a step remembers two places of the cursor: where it was before the
first record, and where it was when the step was closed. Ctrl-Z puts it at
the first, Ctrl-R at the second.

### `undoKind`

The kind of a key: deleting, typing or other.

### `undoKey`

Called with every key before the key acts, in the place where 08.02 called
`undoClose()`. It closes the open step when the key is an other key or of a
different kind than the keys before it, then remembers this key's kind.

### `undoSave`

A `U_CHG` of a row is not recorded when the open step's last record is a
`U_CHG` or a `U_INS` of the same row.

### `undoClose`

Keeps in the step it closes where the cursor is now.

### `undoCursor`

Puts the cursor on a row and column of the file, scrolling so that it
shows.

### `editorUndo`

Puts the cursor where the step began.

### `editorRedo`

Puts the cursor where the step ended.

Outside these: the cursor's two places in `struct undoStep` and the kind
in `struct undoState`, the three kinds, and where `undoSave()` keeps the
cursor as it opens a step.

## How it works

### Two kinds of key, and the rest

```
    if (c == BACKSPACE || c == CTRL_H || c == DEL_KEY) return UNDO_DELETING;
    if (c == TAB || c < 0 || (c >= ' ' && c < ARROW_LEFT)) return UNDO_TYPING;
    return UNDO_OTHER;
```

`c < 0` is there for the bytes above 127. `editorReadKey()` reads into a
`char`, which is signed on some machines and not on others: on a Mac with
an Apple processor the first byte of an e with an acute accent, 0xC3, comes
as -61, on Linux on the same kind of processor as 195. Both are typing, so
the two bytes of such a character are one step with the letters around
them. A control character that reaches the text, Ctrl-A say, is an other
key: a step of its own. The step ends here:

```
    if (kind == UNDO_OTHER || kind != U.kind) undoClose();
    U.kind = kind;
```

### Leaving a record out is safe

```
    if (U.open && type == U_CHG) {
        s = &U.undo[U.numundo-1];
        if (s->rec[s->numrec-1].at == at && s->rec[s->numrec-1].type != U_DEL)
            return;
    }
```

Every change to the text goes through a row function, and every row
function makes a record, except for the `U_CHG`s this rule leaves out. So
while the step's last record stays its last, every change since was a
change of the text of row `at`: a change of another row would have been
recorded, and would now be the last record, and no row was inserted or
deleted, since those are always recorded. Row `at` is still where it was.
Undone, a `U_CHG` puts back the row's text from before all of those
changes, and a `U_INS` deletes the row whatever it holds; either way the
text is what it was before the record. Only the last record is looked at,
because rows may have been inserted or deleted after an older one, and then
its "row `at`" is another row.

What it saves was measured with a build of kilo that counts its history
after every key. A line of 60 characters typed into an empty row, as one
step: 57 bytes, one step (32 bytes), one record (24) and the empty row it
kept (1). The same line as 60 steps, Ctrl-L, a key that does nothing, typed
after each character: 5190 bytes, 3360 for 60 steps and records and 1830
for the row as it was before each character, 1 to 60 bytes with its
`'\0'`. At 08.01 and 08.02, where every key was a step, typing cost that.

### The cursor's two places

A step keeps the cursor in the file, not on the screen: the row and column
counted from the start of the file, `E.rowoff+E.cy` and `E.coloff+E.cx`.
`undoSave()` keeps the first place when it opens a step:

```
        step.row0 = E.rowoff+E.cy;          /* where the step begins */
        step.col0 = E.coloff+E.cx;
```

and `undoClose()` the second. `undoCursor()` puts it back: a row above or
below the screen becomes its top line, as a search puts its match, and a
column past the screen's width scrolls the view right. It does not move the
cursor to a row's end; the place is put back as it was, even past the end
of a row, where the core lets the cursor be.

The **invariant** is that a step is whole before it is taken back:
`editorUndo()` and `editorRedo()` both call `undoClose()` first, whoever
calls them, and the cursor's second place is kept there.

## Decide the boundary

What is one step? Vim says "One undo command normally undoes a typed
command, no matter how many changes that command makes", and, while typing
in Insert mode, "Do not sync ... unless cursor key has been used": the
changes "before and after these keys can be undone separately". Helix keeps
a history state "if not in insert mode", and commits changes when leaving
it. Emacs makes each command a change group, but some are "amalgamating":
for `self-insert-command`, typing, and `delete-char` "a boundary is
inserted only every 20th command". Zed groups transactions made less than
300 ms apart, by the clock. VS Code ends a step between "different
operation types", typing, deleting left, deleting right and other, and on
Enter, a cursor move, or a delete over lines. kilo's kinds are VS Code's, with no clock and no count:
a pause in typing does not end a step, and a long run is one step however
long. What does the person at the keyboard think of as one thing?
