# 08.04 The saved point, and a bound on memory

kilo now knows which place in its history is the file on disk, so
"(modified)" goes when an undo gets back there and comes back past it. And
the history holds at most 8 MB: its oldest steps go first.

## Where this fits

![Where 08.04 fits](figures/08.04-map.svg)

This lesson builds the saved point, under the save piece, and lights the
history again, which it bounds. Each save tells the saved point where the
file on disk stands in the history; after every undo and redo, the saved
point tells the status bar whether the text is that file. Every record now
counts its bytes on the way into the history, and the oldest steps leave by
the other end. After this lesson "(modified)" tells the truth after undo
and redo, and a long session cannot make kilo's history grow without end.

## The idea

Two things are still wrong. Undo every change back to the file as it was
opened, and the status bar still says "(modified)", and Ctrl-Q still warns
about unsaved changes that are not there: the core counts changes, and an
undo is one more. And the history grows with every key for as long as kilo
runs.

For the first, kilo needs to know where the file on disk is in the history.
The **saved point** is a height of the undo stack: the number of steps under
the text that is on disk. It is 0 when the file is opened, and a save sets
it to the stack's height. After an undo or a redo the text is the file
exactly when the stack is back at that height, so `E.dirty` becomes
`U.numundo != U.saved`.

A height can stop meaning anything. Save, undo below the save, and make a
new edit: the redo stack, which held the way back to the saved text, is
emptied. The stack can reach the same height again, with another text on
it. So the saved point becomes -1, which no stack height equals, and the
file stays modified until the next save.

![The undo stack with the saved point beside it, and the status bar under it, step by step: opened, the point at the bottom and the file not modified; a step typed, modified; saved, the point moves up to the top of the stack; Ctrl-Z, the stack below it, modified; Ctrl-R, at it again, not modified; Ctrl-Z and another letter typed, the step that led back to it gone, the point greyed out: it cannot be reached, and the file stays modified until the next save](figures/08.04-saved-point.svg)

For the second, kilo counts what the history holds in `U.bytes`: each
record's own size and its text with the `'\0'`, and each step's size, 24
and 32 bytes on a 64-bit machine.
Before a record is made, if it would take the count past `UNDO_MAX_BYTES`,
8 MB, the oldest steps are dropped until it fits. If the open step and the
new record alone do not fit, the history is given up, as when memory runs
out, and the change is made anyway.

![The history as a row of steps against its bound, 8 MB: new steps join at one end, and when a new record would take the count past the bound, the oldest steps fall off the other end, never the open one, the saved point moving down one with each](figures/08.04-bound.svg)

The records and their swap are Vim's design; the saved point is one
number kept beside the stack. Vim can walk its history by writes:
`:earlier {N}f` goes to the text "{N} file writes before".

### `undoSave`

Works out what the new record needs: its own size, the row's text and its
`'\0'` unless it is a `U_INS`, and a step's size if it opens one. While
that would take the history past `UNDO_MAX_BYTES`, it drops the oldest step
on the undo stack, never the open one, and takes the saved point down one.
If it still does not fit, it gives the history up: `undo: change too big to
remember`.

### `editorUndo`

After the step is undone, the file is modified unless the undo stack is at
the saved point.

### `editorRedo`

The same, after the step is redone.

Outside these: the saved point and the count in `struct undoState`;
`UNDO_MAX_BYTES` and `undoSize()`; the count kept wherever a record is made,
applied or freed; `editorSave()` closing the open step and setting the
saved point; and the saved point set to 0 by `undoClear()`, to -1 by
`undoGiveUp()`, and to -1 by a new edit below it.

## How it works

### Where the point is set

In `editorSave()`, after a good write:

```
    undoClose();            /* the step typed so far ends here */
    U.saved = U.numundo;    /* the text on disk is the one after these steps */
```

The open step is closed first. Otherwise the keys typed after the save
would join the step typed before it, and the text on disk would be in the
middle of a step, where no undo can stop.

### Three ways to lose it

The saved point becomes -1, out of reach, in three places. A new edit after
undoing below it, in the code that empties the redo stack:

```
        if (U.saved > U.numundo) U.saved = -1;  /* the text on disk was among them */
```

Dropping steps for memory: each step dropped from the bottom takes the
point down one, and below 0 it is -1. Dropping exactly the steps under it
leaves it at 0, the bottom of the stack, still reachable. And giving the
history up, when every step goes.

### Counting what the history holds

```
    return sizeof(*r) + (r->text ? (size_t)r->len+1 : 0);
```

is `undoSize()`, what one record holds. `U.bytes` goes up when a record is
made or a step opened, down when one is freed, and in `undoApply()` down by
what a record held and up by what it now holds. The bound is kept when a
record is made, not on undo or redo: an undo can take the count past it by
the text it takes in, a whole typed row, say. With nothing left to redo the
count is within the bound again, and the next record trims the history.

The count is not `malloc()`'s own overhead, and the arrays of steps are not
shrunk when steps leave them, as `E.row` is not when a row is deleted: it
counts what the history holds, not what the process uses.

The **invariants**, after every undo and redo: the file is shown modified
exactly when the undo stack is not at a reachable saved point; and whenever
it is shown clean, the text is the file as last opened or saved. A stronger
one does not hold. Type `a` at the start of a row and delete it with
Backspace: the text is the file again, but that was two steps, a typing
and a deleting, and the status bar says "(modified)", as the core counts
it. Two Ctrl-Z, and it is clean.

## Decide the boundary

kilo bounds its history in bytes, what memory costs. So does Emacs: its
undo lists are trimmed to `undo-limit` and `undo-strong-limit`, where "size
is counted as the number of bytes occupied", and when one command's changes
pass `undo-outer-limit`, "Emacs discards the info and displays a warning",
as kilo says `change too big to remember`. Vim bounds it in changes instead,
what the user counts: `'undolevels'` is the "Maximum number of changes that
can be undone", 1000 by default on Unix, and its help warns that "a single
change can already use a large amount of memory". A count is easy to
promise and to explain; bytes are what actually runs out. And Vim can keep
the history past the session: with `'undofile'` set, it "will automatically
save your undo history when you write a file and restore undo history when
you edit the file again", so an undo tomorrow can still take back today's
changes. kilo's history goes when kilo exits. What runs out first, and
what does the user expect to still have tomorrow?
