# 09.02 The API is a table

kilo describes what a script may ask of it as a table of C functions, each
with its name and the types of its arguments and result, and hands all of
them to Lua as `kilo.api` through one C function that checks and converts
every call. The editor's side never sees Lua.

## Where this fits

![Where 09.02 fits](figures/09.02-map.svg)

This lesson builds the API, in the row of pieces 09.01 began, right above
the interpreter: a table of the editor's operations, each in the editor's
own terms. Below it, the interpreter reads the table and makes a Lua
function of every entry; above it, the API reads the rows of the file and
the cursor, along the arrow that joins it to the core's rows. After this lesson a script can ask
how many lines the file has, read any of them, find the cursor and say
something; and kilo can print the whole list of what a script may call,
without starting Lua at all.

## The idea

In 09.01, `print` needed a C function of its own that read Lua's stack:
how many arguments, each made into text. An editor that scripts can drive
needs dozens of such functions: read lines, change them, move the cursor,
map a key. Written the same way, each would read the stack and check its
own arguments by hand, and each would know about Lua.

So the functions are written in the editor's own terms instead. An API
function takes an array of plain values, a few types of them, and returns
one: `get_lines(start, end)` takes two integers and returns lines. A
**table** says, for every function, its name, its arguments' names and
types, and its result's type. One C function, the **dispatcher**, stands
behind every name: it checks the arguments against the table's entry,
converts them, calls the function, converts the result back, and turns a
failure into a Lua error. A new function is a C function and a line of the
table, with no Lua in either.

![The table the API is, as kilo --api-info prints it: for each function its name, its arguments' names and types, and the type of what it returns. Nothing in it is Lua](figures/09.02-table.svg)

The table is data, so it can be printed: `kilo --api-info` lists it and
exits without making a Lua state. Neovim is built around the same idea, at
a larger scale and generated rather than written: its build reads the
declarations in src/nvim/api/*.h and, in Neovim's own documentation,
"generates dispatch-functions mapping RPC API method names to public C API
functions, converting/validating arguments and return values". The same
parse makes `vim.api` for Lua and the metadata `nvim --api-info` prints.

### `api.h`

The types between the two sides, and nothing else. `ApiType` names six:
nil, boolean, integer, string, lines and position. `ApiValue` is a type and
the member of a union that type uses; `ApiError` says a function failed, and
why. `ApiFunc` is an entry of the table, and `ApiFn` the shape of every
function: `(ApiValue *args, int nargs, ApiError *err)`, returning an
`ApiValue`. Neither `kilo.c` nor this file includes a Lua header.

### `apiGetLines`

`get_lines(start, end)`: a copy of the rows `[start, end)`, or a failure if
that is not a range of the file. `apiRange()` makes the check, and
`apiFail()` fills the error.

### `apiGetCursor`

The cursor as a position: the row of the file and the byte in it, counted
from 0, so the screen's scroll is added in.

### `apiMessage`

The message line, through 09.01's `editorMessage()`.

### `apiInfo`

The table printed, a line per function. `main()` calls it for
`--api-info`, before it looks at the terminal.

### `scriptCheck`

Is one Lua value of one API type? If not, what it is instead, for the
error: Lua's name for its type, `float` for a number with a fraction, or
what is wrong inside a table.

### `scriptTake`

A Lua value, already checked, as an `ApiValue`.

### `scriptPushIn`

An `ApiValue` as a Lua value: a lines value becomes a Lua list.

### `scriptDispatch`

The dispatcher: the count, every type, the call, the result.

### `scriptOpen`

Now also makes `kilo.api`: for each entry of the table a Lua function,
stored under the entry's name.

Outside these: the table `API` itself, the three functions too small for a
region (`line_count`, `get_name`, `is_modified`), the helpers that make and
free values (`apiValue()`, `apiString()`, `apiFree()` and their kin), and
`scriptRelease()`, which frees what `scriptTake()` made.

## How it works

### Two sides that share only types

Nothing in `kilo.c` knows what Lua is, and nothing in `script.c` knows what
a row is. They meet in `api.h`:

```
typedef struct {
    ApiType type;
    union {
        int boolean;
        long long integer;
        ApiString string;
        struct { ApiString *line; int count; } lines;
        struct { long long row, col; } position;
    } u;
} ApiValue;
```

Neovim's is the same shape, in src/nvim/api/private/defs.h: an `Object`
with a type, `kObjectTypeNil` to `kObjectTypeLuaRef`, and a union, and `typedef
struct { ErrorType type; char *msg; } Error;`. A Neovim API function fails
as kilo's does, by filling the error and returning normally; its caller
checks. In kilo that is `apiFail()`, which fills `err` printf-style and
returns nil, and the dispatcher, which looks at `err.set` after the call.

<!-- verify: mention names="src/nvim/api/private/defs.h" outside reason="Neovim's source, read at v0.12.6; not this project's" -->

### One function behind every name

![kilo.api.get_lines(0, 2), step by step: the two Lua values on the dispatcher's stack; each checked against the entry for get_lines, integer and integer; made into two ApiValues and passed to the C function; the lines it returns, a value of type lines; pushed back as a Lua table of two strings](figures/09.02-dispatch.svg)

`kilo.api` is a table of 6 Lua functions, and all of them are the same C
function, `scriptDispatch()`. What tells them apart is an **upvalue**, a
value Lua keeps with a C function when it is pushed as a **closure**: here,
a pointer to the function's entry in the table.

```
    for (f = API; f->name; f++) {
        lua_pushlightuserdata(L,(void *)f);
        lua_pushcclosure(L,scriptDispatch,1);
        lua_setfield(L,-2,f->name);
    }
```

The dispatcher reads its entry back with
`lua_touserdata(L,lua_upvalueindex(1))` and checks the count, then every
argument, before anything is converted:

```
    for (i = 0; i < n; i++)
        if (!scriptCheck(L,i+1,f->args[i],why,sizeof(why)))
            return luaL_error(L,"%s: argument %d (%s): expected %s, got %s",
                              f->name,i+1,f->argnames[i],apiTypeName(f->args[i]),why);
```

That loop is the **invariant**: an API function runs only with arguments
of the types its entry names, so `apiGetLines()` reads
`args[0].u.integer` with no check of its own. Neovim's generator writes the
same two checks into every RPC wrapper it makes, "Wrong number of
arguments" and "Wrong type for argument", once per function in generated
C; kilo has them once, in a loop over data.

### Who frees what

An argument string is lent, not copied: `scriptTake()` points the
`ApiValue` at Lua's own bytes, which the manual promises stay valid while
the value is on the stack, and it is, until the call returns. A result is
the other way round. The function allocated it, a copy of the rows here,
and the dispatcher frees it with `apiFree()`. But pushing it into Lua makes
strings and a table, which needs memory, and a memory error is a jump, as
09.01 showed: past the `apiFree()` that follows, and the copy would leak.
So the push runs in a protected call of its own, and the free comes after
it whatever happened:

```
    lua_pushcfunction(L,scriptPushIn);
    lua_pushlightuserdata(L,&ret);
    status = lua_pcall(L,1,nret,0);
    apiFree(&ret);
    if (status != LUA_OK) return lua_error(L);
```

### Counting from 0, and from 1

Rows and columns count from 0, a range `[start, end)` holds `start` and not
`end`, and anything outside the file is an error, never cut to fit. That is
Neovim's rule too: "Most of the API uses 0-based indices, and ranges are
end-exclusive." But Neovim clamps an index past the file to the nearest
valid one unless `strict_indexing` is set, an argument of
`nvim_buf_get_lines()`; kilo is always strict, so `get_lines(0, 5)` on two rows is an error and not two lines.
Lua's lists count from 1, so `get_lines(0, 2)[1]` is row 0. Neovim's cursor
counts rows from 1 ("(1,0)-indexed"); kilo's, from 0, like everything else
in its API.

## Decide the boundary

kilo writes one table and one dispatcher. Lua's own libraries are written
the other way: every C function checks its own arguments, as `str_rep()` in
lstrlib.c does with `luaL_checkinteger(L, 2)`. That needs no table and no types of the editor's own, and is the
simplest way for a handful of functions with one caller. Neovim goes the
other way from kilo: the table is generated from the C declarations at
build time, `src/gen/gen_api_dispatch.lua` reading the headers, and one
parse serves Lua, msgpack-RPC for other programs, and `--api-info`. Nothing
can forget a check or drift from the list, and the price is a generator
and a build step to keep working. kilo's table, written by hand, sits
between: no build step, and two ways in, Lua and `--api-info`, each of
which reads the same table. How many functions will there be, and how many
ways in?

## Break it

Take the type check out of the dispatcher. In
`build/at/kilo/09.02/script.c`, in `scriptDispatch()`, delete the four
lines of the loop:

```

        if (!scriptCheck(L,i+1,f->args[i],why,sizeof(why)))       <- delete
            return luaL_error(L,"%s: argument %d (%s): expected %s, got %s",       <- delete
                              f->name,i+1,f->argnames[i],apiTypeName(f->args[i]),why);      <- delete
```

and open the file as before:

```
./learn run kilo --at 09.02 -- notes.txt
```

The build warns that `why` and `scriptCheck()` are no longer used. At
Ctrl-E:

<!-- verify: skip reason="lines typed at the editor's Ctrl-E prompt with the patch made, each with what the message line then said; captured on an 8 x 80 pseudo-terminal with track.py's Editor" -->
```
#kilo.api.get_lines("a", "b")                  0
kilo.api.get_lines('a', 1)[1]                  hello world
kilo.api.get_lines(0.5, 1)[1]                  hello world
kilo.api.get_lines('1', 2)[1]                  second line
```

No error. `scriptTake()` asks Lua for each value as an integer, and Lua
gives 0 for what is not one: `"a"` and `"b"` became 0 and 0, a range of no
rows, so the answer is an empty list; `'a'` and `0.5` became row 0; and the
string `'1'`, which Lua can read as a number, became 1. Every call returned
something that looks like an answer to a question nobody asked. The
function was right and the checks were in the one place that was taken
away; a script with a typo now reads the wrong rows and is never told. Put
the lines back.
