# 09.06 Drawing from a script: highlights and the status bar

A script can now colour any bytes of any row, in a set of highlights of its
own, write the left part of the status bar, and ask which part of the file
the screen shows, or move it. The editor draws the highlights over each row
after the core has drawn it.

## Where this fits

![Where 09.06 fits](figures/09.06-map.svg)

This lesson builds the highlights piece, at the right of the row of the
module's pieces in kilo.c. Scripts fill it through the API; the frame
hands it each row once the core has drawn that row, and it draws the row's
highlights over it, the line up the right side of the map to the frame. It
also gives the frame the status bar's text when a script has set one.
After this lesson a script can show what it finds in the text, numbers,
mistakes, matches, where the user will see it, without a line of C.

## The idea

A script can change the text and answer keys, and it still cannot change
what one cell of the screen looks like. Colour is module 06's, and module
06 is C: every new thing to colour means a change to kilo.c and a compile.

A **highlight** is three things: a row, a range of its bytes, [start, end)
counted from 0 as everywhere in the API, and a style: one of the colours
red, green, yellow, blue, magenta and cyan, or bold, underline or reverse.
`add_highlight(ns, row, start, end, style)` adds one. The core draws the
frame as it always has, and after each row the editor goes back over it and
writes the highlighted characters again, in their style.

Every highlight belongs to a **namespace**, a number a script gets from
`create_namespace(name)`: the same name gives the same number, and `""` a
new one each time. `clear_namespace(ns)` removes one namespace's
highlights and no other's, so two scripts that each clear and redraw their
own never wipe each other's. Neovim's `nvim_create_namespace` is the same
function, down to the empty name: "If `name` matches an existing namespace,
the associated id is returned. If `name` is an empty string a new,
anonymous namespace is created."

![Two scripts' highlights on the same three rows, the numbers in yellow in namespace 1 and the spaces at the ends of rows in reverse in namespace 2; clear_namespace(2), and the reverse is gone while every yellow stays](figures/09.06-namespaces.svg)

A highlight stays where it was put: on its row number, at its bytes, until
it is cleared. When the text changes, the script puts its highlights again,
on TextChanged from 09.05, and on CursorMoved too, since a move can scroll
other rows into view.

![A row put in above a highlighted word. In kilo the highlight stays on its row number, now over the row that moved into that place, until the script puts it again; in Neovim an extmark moves down with the word](figures/09.06-moves-or-not.svg)

The status bar's left part, the file's name and line count, is the
script's to replace with `set_statusline(text)`; `""` gives the editor's
own back. And three functions say and set what the screen shows:
`get_view()` gives the file's row and column at the screen's top left,
`get_size()` the rows and columns of text the screen has room for, and
`set_view(position)` moves the view.

### `apiAddHighlight`

Checks what it can when the highlight is added: the namespace exists, the
row is in the file, 0 <= start <= end, and the style is one of the nine.
Whether the bytes are in the row is left to the drawing, since the row may
change before then. Then it appends the highlight to the list, up to
`HIGHLIGHT_MAX`, 10000.

### `apiCreateNamespace`

Finds the name among the namespaces made so far, or makes a new one, up to
`NAMESPACE_MAX`, 64.

### `apiClearNamespace`

Takes one namespace's highlights out of the list, keeping the others in
their order: a later highlight is drawn over an earlier one.

### `editorDrawHighlights`

Called by the frame after each row and its `ESC [ 0 K`, with the row's
number: draws that row's highlights over it.

### `editorStatusLine`

Called by the frame with the left part it made: puts the script's text in
its place, cut so that the cursor's `row/rows` still fits on the right.

### `apiSetView`

Sets the view's row and column, then brings the cursor into it.

Outside these: the tables `STYLES` and of highlights and namespaces;
`set_statusline`, which cleans the text as messages are cleaned (a tab a
space, any other control byte a `?`); `get_view` and `get_size`; and the
two calls in `editorRefreshScreen()`.

## Run it

Make the program in this lesson's folder, and a file with numbers, three
spaces at the end of its second row, and a tab at the start of its third:

<!-- verify: session -->
```

$ printf 'width = 640\nheight = 480   \n\tpixels = 307200\n' > build/at/kilo/09.06/sizes.txt
```

Put this in `build/at/kilo/09.06/init.lua`, two small scripts and a status
line, each with its own namespace:

<!-- verify: patch file=init.lua create
@block
-->
```lua
-- The rows the screen shows: the first one's number, and their text.
local function shown()
  local top, rows = kilo.api.get_view()[1], kilo.api.get_size()[1]
  local last = math.min(top + rows, kilo.api.line_count())
  if last <= top then return top, {} end
  return top, kilo.api.get_lines(top, last)
end

-- Every number on the screen in yellow.
local numbers = kilo.api.create_namespace('numbers')
local function paint_numbers()
  kilo.api.clear_namespace(numbers)
  local top, lines = shown()
  for i, line in ipairs(lines) do
    for s, e in line:gmatch('()%d+()') do
      kilo.api.add_highlight(numbers, top + i - 1, s - 1, e - 1, 'yellow')
    end
  end
end

-- Spaces at the end of a row, in reverse.
local spaces = kilo.api.create_namespace('spaces')
local function paint_spaces()
  kilo.api.clear_namespace(spaces)
  local top, lines = shown()
  for i, line in ipairs(lines) do
    local s = line:find('%s+$')
    if s then kilo.api.add_highlight(spaces, top + i - 1, s - 1, #line, 'reverse') end
  end
end

-- The cursor's row and byte, in the status bar.
local function where()
  local pos = kilo.api.get_cursor()
  kilo.api.set_statusline(kilo.api.get_name() .. ' - row ' .. pos[1] + 1 .. ', byte ' .. pos[2])
end

for _, event in ipairs({'BufReadPost', 'TextChanged', 'CursorMoved'}) do
  kilo.api.create_autocmd(event, paint_numbers)
  kilo.api.create_autocmd(event, paint_spaces)
  kilo.api.create_autocmd(event, where)
end
```

and start the editor on the file:

<!-- verify: skip reason="starts the full-screen editor; its screens below were captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->
```

```

## How it works

### Drawing over a finished row

![The bytes kilo writes for one row: the row and ESC [ 0 K, as the core writes them; then the second pass, a carriage return, ESC [ n C to the highlight's first cell, the style's code, the highlighted characters again, and ESC [ 0 m](figures/09.06-drawn-over.svg)

The frame calls the highlights once for each row it draws, after the row:

```
        abAppend(&ab,"\x1b[0K",4);
        editorDrawHighlights(&ab,filerow);
```

For the third row of the file above, what kilo writes is the core's row,
then `\r`, `ESC [ 17 C`, `ESC [ 33 m`, `307200`, `ESC [ 0 m`: back to the
row's start, seventeen cells right, yellow on, the six characters again,
and every style off. The core's code for a row is untouched, and so is
what it draws when no script has a highlight.

Getting to the right cell takes three conversions. The highlight is in
bytes of the row; a tab before it widens on the screen, as 03.03 widens
it:

```
        for (k = 0; k < to; k++) {          /* bytes of chars to columns of render */
            if (k == from) a = b;
            b += r->chars[k] == TAB ? 8-b%8 : 1;
        }
```

Then the columns are cut to the part of the row the screen shows, from the
view's left column `E.coloff` for `E.screencols`. And `ESC [ n C` counts
cells, not bytes, so the cells before the highlight leave out the bytes
that continue a UTF-8 character. A control byte in the range is stepped
over with `ESC [ C`, never written. The **invariant** is that a highlight
never writes outside its row's cells: whatever a script asks for, the
second pass starts at the row's first cell, writes at most the cells the
first pass wrote, and ends with every style off.

### Checked when drawn

A highlight is checked against the row as the row is when it is drawn,
not as it was when it was added:

```
        if (from > r->size) from = r->size;
        if (to > r->size) to = r->size;
        if (from >= to) continue;
```

Added at the prompt, a highlight on bytes 3 to 100 of `width = 640` colours
`th = 640`, and one on bytes 20 to 30 of the second row, which has 15,
draws nothing. Delete the `dt` of `width` and the first lies on what is now
at bytes 3 to 9, ` = 640`; the yellow, put again since, is drawn over its
`640`, a later highlight over an earlier. So the list never has to be fixed
when the text changes, and a stale highlight is at worst in the wrong
place, never out of the row. The list is plain: for each row it draws, the
frame looks at every highlight, up to 10000. Ten thousand on one row make
one frame of some 150 KB, each drawn over the row in turn.

### Before the frame

09.05 fires TextChanged and CursorMoved at the top of the main loop, after
a key's work and before the frame. That order is what makes the scripts
above work: the frame that shows a changed row already has its new
highlights. To see what a highlight does when nobody puts it again, add one
by hand at the prompt, `ns = kilo.api.create_namespace('')
kilo.api.add_highlight(ns, 1, 0, 6, 'green')`: `height` is green. With the
cursor at the start of the first row, press Enter. The rows move down, the
yellow and the reverse follow them, and the green stays on row 1, now
`[g:width ]= [y:640]`.

### What the screen shows

A script that paints only the rows on the screen needs to know which they
are: `get_view()` and `get_size()`, the core's `E.rowoff` and `E.coloff`,
`E.screenrows` and `E.screencols`. `set_view(position)` sets the first
two. The row must be in the file and the column not past the longest row.
Then the cursor, if the new view leaves it off the screen, is moved into
it as little as that takes, to the view's first or last row or column and
then to its row's length; and if that row ends left of the view's column,
the view's column comes back to its end, as the core does when an arrow
takes the cursor onto a short row.

Moving the view is not an event, and that matters to a script like the one
above. Make a longer file,

<!-- verify: session -->
```
$ seq -f 'row %g of 12' 12 > build/at/kilo/09.06/rows.txt
```

open it the same way, and at the prompt type `kilo.api.set_view({6, 0})`.
The screen shows rows 7 to 12, every number yellow: the cursor was on row
1, above the view, so it moved to row 7, and CursorMoved painted. Now
`kilo.api.set_view({4, 0})`. The cursor, on row 7, is inside rows 5 to 10,
so it stays, nothing fires, and rows 5 and 6 come up plain until the next
key that moves the cursor. A script that moves the view should paint
after it.

## Decide the boundary

kilo's highlights are a list of row numbers and bytes. They are simple to
add, to clear and to draw, and the editor never touches them when the text
changes; the script pays for that by putting all of its highlights again
after every change. Neovim keeps **extmarks**, "buffer annotations that
track text changes in the buffer", in a tree: in its extmark.c, "Marks sit
in a MarkTree datastructure which provides both efficient mark
insertations/lookups and adjustment to text changes". They are moved by
calls to `extmark_splice`, which `nvim_buf_set_lines`, for one, makes after
its change, so a mark on a word stays on the word. The editor pays, in every edit, and in
the code of a tree that marktree.c says was inspired by "the marker tree
data structure of the Atom editor". Neovim's function of kilo's shape,
`nvim_buf_add_highlight`, is deprecated (since API level 13); a range is
highlighted with an extmark's `hl_group` instead. Who should pay for an
edit: the editor once, or every script each time?
