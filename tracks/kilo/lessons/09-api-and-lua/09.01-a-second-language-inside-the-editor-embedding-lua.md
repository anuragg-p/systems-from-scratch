# 09.01 A second language inside the editor: embedding Lua

kilo links the Lua interpreter into itself, starts one Lua state when it
opens, runs the user's init file in it, and gives Ctrl-E a prompt to type a
line of Lua at. Every way from kilo's C into Lua is a protected call, so a
script that fails comes back as a message, never as a crash.

## Where this fits

![Where 09.01 fits](figures/09.01-map.svg)

This lesson builds three pieces of the map at once: the prompt, in a new
row under the core's pieces; the interpreter, in the row below it, in a
file of its own; and the scripts, outside the editor. The core hands the
interpreter a file to run when the editor opens, and any line typed at the
prompt; the interpreter runs them and hands back text for the message line.
The box named Lua is Lua itself, a library this course did not write, with
that file of kilo's around it. After this
lesson the editor runs a script of yours when it starts, and any line of
Lua you type; a script can say something, and nothing more yet.

## The idea

Every feature so far was C in `kilo.c`, a compile and a restart. The person
using an editor wants to add to it without that: a key that comments out a
line, a check before every save, a few lines loaded when the editor starts.
So the editor needs a second language inside it, one that runs code the
editor was never compiled with.

An interpreter can be a library. Lua's manual says so: "Lua is implemented
as a library, written in clean C", and "it works embedded in a host client,
called the embedding program or simply the host." kilo becomes the host.
Four things are new:

- A **state**, a `lua_State`, is one whole Lua world: its globals, its
  memory and the garbage collector that frees it. `luaL_newstate()` makes
  one, `luaL_openlibs()` opens the standard libraries in it, and kilo keeps
  it until it exits.
- C and Lua pass values over a **stack**: C pushes a value, calls, and reads
  the results off the top; a C function that Lua calls finds its arguments
  on a stack of its own and pushes what it returns.
- A C function is a Lua value. kilo sets the global `print` to its own
  `scriptPrint()`, so a script's `print("hi")` writes to the message line,
  where the standard one would write over the screen.
- Every call from C into Lua is a **protected call**, `lua_pcall()`. An
  error inside it, a script's or Lua's own, comes back as a status and a
  message on the stack, and kilo goes on.

![The same init.lua, with an error on line 2, run two ways. Above, inside lua_pcall(): the error comes back as a message on the stack, init.lua:2: attempt to concatenate a nil value (global 'nme'), and kilo shows it and opens the file. Below, with lua_call(): Lua prints PANIC: unprotected error in call to Lua API, abort() ends kilo, and the terminal is left in raw mode](figures/09.01-protected-call.svg)

Neovim is built the same way, in src/nvim/lua/executor.c: `nlua_init()`
makes its state with the same two calls; `nlua_pcall()` is "Like lua_pcall,
but use debug.traceback as errfunc."; and `nlua_error()` "Converts a Lua
error into a Vim error message", such as `E5108: Lua: ...`.

<!-- verify: mention names="nlua_init() nlua_pcall() nlua_error() src/nvim/lua/executor.c" outside reason="Neovim's source, read at v0.12.6; not this project's" -->

Lua is the one thing in this track that is not written here. A language is
a project of its own; this module is about how an editor lets one in, and
Neovim and Redis too embed a Lua someone else wrote. kilo links **Lua
5.4.9**. Neovim's docs say "Lua 5.1 is the permanent interface for Nvim
Lua", built with LuaJIT where it can be, and Redis keeps Lua 5.1.5 in its
tree. What this module's scripts use is the same in both but for one thing:
5.4 has integers, as Run it shows, and 5.1 only floating-point numbers,
which Neovim makes integers as they enter its API.

### `scriptProtected`

The one door into Lua: it pushes a C function and one pointer, calls
`lua_pcall()`, and says the error if there was one.

### `scriptReport`

The error on top of the stack, its first line only, in the message line.

### `scriptFileIn`

Runs a file, read by `lua_load()` through `scriptRead()` and named by the
part of its path after the last `/`, which Lua puts in front of its errors.

### `scriptEvalIn`

A line typed at the prompt: tried as an expression and shown, else run as a
statement.

### `scriptPrint`

`print()`, joining its arguments with tabs as Lua's does, into the message
line.

### `scriptStart`

Called from `main()` once the file is read: `scriptNew()` makes the state
and, in a protected call, `scriptOpen()` opens the libraries, makes an empty
global table `kilo` for later lessons to fill, and replaces `print`; then
the init file runs. At exit `scriptStop()` puts the terminal back first,
then closes the state.

### `editorPrompt`

In `kilo.c`: a line typed in the message line, with its own loop of drawing
and reading keys, as `editorFind()` from 05.01 has. Ctrl-E calls it with
`lua: `. Beside it, `editorMessage()` puts a script's text in the message
line through `editorClean()`, which makes a tab a space and any other
control byte a `?`.

Outside these: `script.h`, the limits and what each file calls of the
other; `CTRL_E`; and the Makefile, which builds `kilo.c script.c` and links
Lua's library.

## How it works

### One stack between two languages

![Lua's stack as C sees it while kilo runs the line 1+1 typed at the prompt: empty; the line compiled into a function and pushed; after lua_call(), the result 2 on top; print() called with it, which reads it as text; popped, empty again. Each slot numbered from the bottom, 1 up, and from the top, -1 down](figures/09.01-stack.svg)

An API call names a slot by an index: "index 1 represents the first element
(that is, the element that was pushed onto the stack first)" and "index -1
also represents the last element (that is, the element at the top)". A C
function that Lua calls gets a stack of its own, so `scriptEvalIn()` finds
the line's pointer at index 1. It reads it, empties the stack, pushes
`return 1+1;` and compiles it into a function named `=lua`, which is why its
errors start `lua:1:`:

```
    lua_pushfstring(L,"return %s;",line);
    if (luaL_loadbuffer(L,lua_tostring(L,1),lua_rawlen(L,1),"=lua") != LUA_OK) {
        lua_settop(L,0);
        if (luaL_loadbuffer(L,line,strlen(line),"=lua") != LUA_OK) return lua_error(L);
    } else {
        lua_remove(L,1);
    }
    lua_call(L,0,LUA_MULTRET);
```

`return x = 5;` does not compile, so `x = 5` is compiled as it is, a
statement, and gives no values. Lua's own prompt, `lua.c`, does the same
with the same `"return %s;"`. The values that come back go to the global
`print`, so a script that replaces `print` changes what the prompt shows.

<!-- verify: mention names="lua.c" outside reason="Lua's stand-alone interpreter, lua/src/lua.c, which kilo does not build" -->

C leaves the stack as it found it. The state lives for the whole run, and
nothing would ever pop a value left on it. `lua_pcall()` "always removes
the function and its arguments from the stack"; on an error it leaves one
value, the message, and `scriptReport()` pops it once it is shown.

### An error is a jump

The manual: "Internally, Lua uses the C longjmp facility to handle errors.
[...] A protected environment uses setjmp to set a recovery point; any error
jumps to the most recent active recovery point." `lua_pcall()` sets the
point, and an error anywhere inside, in a script or in `luaL_error()` called
from C, does not return: it jumps there, past every C function in between,
which never finish. Memory they meant to free afterwards, or a file they
meant to close, stays as it is. So `scriptFileIn()` closes the file before
it raises a compile error, not after:

```
    status = lua_load(L,scriptRead,&r,name,NULL);
    fclose(r.fp);
    if (status != LUA_OK) return lua_error(L);
```

And `scriptProtected()` does nothing before the call that could fail. It
pushes a C function and a **light userdata**, a bare C pointer, and neither
push needs memory; compiling a chunk or making a string does, and "Most
functions in the API can raise an error, for instance due to a memory
allocation error." Outside a recovery point such an error has nowhere to
jump. That is the **invariant**: C never calls into Lua outside a protected
call. The line that keeps it is the only `lua_pcall()` in kilo, in
`scriptProtected()`; the `lua_call()`s in `scriptFileIn()` and
`scriptEvalIn()` run inside it:

```
    status = lua_pcall(L,1,0,0);
```

What comes back is a script's text on its way to the terminal, so it is
cleaned: the first line only, and every control byte a `?`, or an `error()`
holding `ESC [ 2 J` would clear the screen.

### Where the init file is, and when it runs

`$KILO_INIT` if it is set (set and empty: none), else
`$XDG_CONFIG_HOME/kilo/init.lua`, else `$HOME/.config/kilo/init.lua`, the
shape of Neovim's "$XDG_CONFIG_HOME/nvim/init.vim (or init.lua)". The time
differs. Neovim loads the user's config at step 8 of its start and the
files named on its command line at step 18, so its init.lua runs before any
file is read. kilo calls `scriptStart()` after `editorOpen()`, so an init
file can look at the file being opened, once 09.02 gives it a way to.

## Decide the boundary

kilo embeds Lua, as Neovim and Redis do: "a powerful, lightweight,
embeddable scripting language", its manual says, and on this Mac kilo goes
from 53320 bytes at 05.02 to 318072 at 09.01, a whole language included.
An editor could have a language of its own instead: Vim's Vimscript "is used
for the startup vimrc file, syntax files, and many other things", and "Most
of the GNU Emacs text editor is written in the programming language called
Emacs Lisp", over primitives in C. The language fits the editor, and its
authors maintain a language too. It could have none: a feature is a change
to the source and a compile, as in this track's core and in Helix's
releases (a plugin system, in Scheme, is an open pull request). Or
extensions could be WebAssembly, as Zed's are: "Procedural parts of
extensions are written in Rust and compiled to WebAssembly", run inside
Zed's process with file access limited to the extension's own directory and
other powers granted by a capability system. Who will write the extensions,
and what are you willing to maintain for twenty years?

## Break it

Call into Lua without the protection. In `build/at/kilo/09.01/script.c`, in
`scriptProtected()`, make the protected call a plain one:

<!-- verify: patch file=script.c
-    status = lua_pcall(L,1,0,0);
@block
-->
```
    lua_call(L,1,0); status = LUA_OK;
```

and run it with the init file that has the typo. kilo dies without putting
the terminal back, so afterwards type `stty sane` and Enter, even if you
cannot see what you type:

<!-- verify: session
ignore /\$ exit/
-->
```
$ KILO_INIT=init.lua ./learn run kilo --at 09.01 -- notes.txt
Running kilo as it stands at 09.01 (A second language inside the editor: embedding Lua). Its files are in build/at/kilo/09.01/
PANIC: unprotected error in call to Lua API (init.lua:2: attempt to concatenate a nil value (global 'nme'))
```

No screen, and kilo is gone. With no recovery point anywhere, Lua's
`luaD_throw()` calls the **panic function** that `luaL_newstate()`
installed, which prints that line, then `abort()`: "If an error happens
outside any protected environment, Lua calls a panic function (see
lua_atpanic) and then calls abort, thus exiting the host application."
`abort()` runs no exit handlers, so `disableRawMode()` never runs and the
terminal stays raw: output steps across the screen, since a newline no
longer returns to the left edge, and in bash what you type is not shown.
`stty sane` and Enter bring it back. Any script's error would end the editor
this way, unsaved text and all; 09.08 returns to this with a panic function
of kilo's own. Put the line back.
