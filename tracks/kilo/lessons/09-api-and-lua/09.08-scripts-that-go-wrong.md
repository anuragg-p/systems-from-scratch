# 09.08 Scripts that go wrong

A script is someone else's code running inside the program that holds your
unsaved file. This lesson gives kilo guards against the scripts a protected
call does not catch, one that never ends and one that takes all the
memory, and says plainly what the guards still cannot stop.

## Where this fits

![Where 09.08 fits](figures/09.08-map.svg)

This lesson builds the guards piece, beside the interpreter in the row of
the Lua side. It stands between Lua and the machine: Lua asks it for every
byte of memory it uses, and while a script runs, Lua hands it control every
so often so that it can look at the keyboard. Nothing above it changes: the
API, the keys and the events are as they were. After this lesson a script
that loops for ever is stopped by Ctrl-C, one that fills memory gets an
error at 64 MB and gives the memory back, and in both cases the file you
were editing is still there to save.

## The idea

Since 09.01 every way into Lua is a protected call, so an error in a script
comes back to kilo as a message and the editor goes on. But a loop that
never ends raises no error, and neither does a table that grows until the
machine runs out. On the project at 09.07, which has none of this lesson's
code, `while true do end` typed at the Ctrl-E prompt was still running
after 3 s and had to be killed, file and all;
`#string.rep('x', 200 * 2^20)` answered `209715200`, and Lua went on
holding 212642 KB; and `os.exit(0)` left the editor with a change unsaved. The standard is module
07's: never a crash, a hang, or a lost file.

Three guards, each a few lines in `script.c`:

**A hook.** Lua can call a C function of the program's every so many
instructions it runs, a **count hook**. kilo's runs every 100000, about
every 0.2 ms here; it looks at the keyboard without waiting, and if the
person has pressed Ctrl-C, it raises the error "interrupted" inside the
script. The protected call catches it like any other.

**An allocator.** Lua does not call `malloc()` itself: it asks one function
of the program for all its memory. kilo's counts what Lua holds and refuses
to let it pass 64 MB. Lua turns the refusal into the error "not enough
memory".

**No way around the editor.** `os.exit` is replaced, in the editor, by a
function that raises an error saying to use `kilo.api.quit()`. And the
text a script prints has been cleaned since 09.01: a control byte reaches
the message line as `?`, never the terminal as a command.

Neovim does not do the first. Its Lua glue, src/nvim/lua/executor.c and
the files beside it, calls no `lua_sethook` at v0.12.6, and an issue still
open in its tracker, #6800, says that "if you write an endless loop inside
`:lua` then it can't be interrupted" (read in the source and the issue; not
run here). What it has is `vim.wait`, which checks for an interrupt while it
waits. The hook kilo has is Redis's, which embeds Lua 5.1 to run scripts
inside the database server: its src/script_lua.c sets one with the same
count as kilo's, to "detect scripts timeout":

<!-- verify: skip reason="a line of Redis's src/script_lua.c, not of this project" -->
```
    lua_sethook(lua,luaMaskCountHook,LUA_MASKCOUNT,100000);
```

<!-- verify: mention names="executor.c script_lua.c" outside reason="Neovim's and Redis's source files, not this project's" -->

![Lua's instructions as a line of ticks, the hook every 100000 of them, each time a look at the keyboard that finds nothing, until a look finds Ctrl-C: the hook raises "interrupted", and the error goes up through the script to the protected call, which says it in the message line](figures/09.08-hook.svg)

### `scriptHook`

The count hook: reads what is waiting on the keyboard, finds a Ctrl-C or
returns, then raises "interrupted" with the script's place in front.

### `scriptAlloc`

The allocator. It keeps `S.used`, what Lua holds now, and refuses a growth
past `SCRIPT_MAX_MEMORY`.

### `scriptPanic`

What Lua calls for an error outside any protected call. Nothing should
ever get here.

### Back from a script that went wrong, in `scriptProtected`

At the outermost return, after any error, a full collection, and a Ctrl-C
forgotten. Around these, `scriptNew()` now makes the state with
`lua_newstate()` and the allocator, where up to 09.07 it called
`luaL_newstate()`, and `scriptOpen()` replaces `os.exit`.

## How it works

### What the hook may do

Each time it is called, the hook looks at the keyboard:

```
        while (poll(&pfd,1,0) == 1 && (pfd.revents & POLLIN) &&
               (n = read(STDIN_FILENO,buf,sizeof(buf))) > 0)
            for (i = 0; i < n; i++)
                if (buf[i] == 3) S.interrupted = 1;
```

In raw mode Ctrl-C is not a signal; since 01.01 it is the byte 3, which
waits on the keyboard with anything else typed. `poll()` with a wait of 0
asks whether there is anything, and the hook reads all of it, looking for a
3 and throwing the rest away: those keys were typed at a script that was
not listening, and playing them into the file later would be worse. The
hook must never wait, since it runs inside the script it is timing.

It raises the error with `luaL_where(L,0)` in front, level 0: a count hook
runs inside the function it stops, so that is where the script was,
`init.lua:1:`. Then it sets the count to 1:

```
        if (!S.interrupted) return;
        lua_sethook(L,scriptHook,LUA_MASKCOUNT,1);
```

From then on every instruction raises "interrupted" again, so a script that
catches errors with `pcall()` cannot catch this one and carry on:
`while true do pcall(function() while true do end end) end` still stops.
Back at the outermost protected call, the count goes back to 100000. Redis
does the same, so "the user will not be able to catch the error with
pcall".

The **invariant** is that no script can keep the editor from its next key.
The hook keeps it for every script that is running Lua code, and only for
those. Lua's manual says of the count hook: "This event only happens while
Lua is executing a Lua function." Two kinds of script slip past:

- A loop inside one C function. A pattern that backtracks runs inside
  Lua's pattern matcher, a single call:
  `string.find(string.rep('a', 16), string.rep('a*', 16) .. 'b')`
  took 15 s here under `kilo -l`, and each two more `a`s multiply that by
  about fifteen. Ctrl-C pressed during it at the prompt was not seen at
  all: the call ended, the line with it, and the message line said `nil`.
- A finalizer that never ends. Lua runs a `__gc` function with hooks off
  (its lgc.c: "stop debug hooks during GC metamethod"), so this line at the
  prompt hangs the editor, Ctrl-C or not:
  `setmetatable({}, {__gc = function() while true do end end}) collectgarbage()`.
  At exit kilo puts the terminal back before it closes the state and runs
  the finalizers, so a hang there at least ends with Ctrl-C, a signal
  again.

For those, the way out is the one Break it uses: kill kilo from another
terminal. The hook also has a price, and it is not one look every 100000
instructions: with a count hook set, Lua takes its slower path for every
instruction, to count it down. An empty loop of 10 million turns took 15
ms with no hook, under `kilo -l`, and 22 ms in the editor. Lua's own `lua`
program avoids that by setting its hook only when SIGINT arrives; kilo
cannot, since in raw mode no signal comes.

### The allocator's contract

![What Lua holds, as a meter from 0 to 64 MB, while a table grows for ever: it fills with blocks until one more would pass the limit; the allocator returns NULL, Lua raises "not enough memory", the error reaches the protected call, and the full collection after it brings the meter back down to some tens of kilobytes](figures/09.08-allocator.svg)

Lua calls one function for every block: a new one (`ptr` NULL), one to
free (`nsize` 0), one to grow or shrink. kilo's refuses only growth past
the limit:

```
    if (nsize > osize && S.used-osize+nsize > SCRIPT_MAX_MEMORY) return NULL;
```

It never refuses to shrink, since Lua counts on that, and keeps
`S.used` to what `realloc()` really did. A refusal is not a crash: Lua
raises a memory error, which unwinds the script to the protected call like
any other. After any error at the outermost return, kilo runs a full
collection, so that what the script filled is given back now and the next
allocation does not fail too: the 26 KB in Run it. One more thing changes
with the limit: recursion without end,
`local function f() return 1 + f() end f()`, gives `not enough memory`,
not Lua's `stack overflow`, which it gave at 09.07: the memory runs out
first.

Neovim's `nlua_init()` in executor.c makes its state with
`luaL_newstate()`, as kilo did until this lesson.

### The panic function

Lua calls the panic function for an error that no protected call catches.
The one a state made by `luaL_newstate()` has writes a line and calls
`abort()`, which leaves the terminal raw. kilo's puts the terminal back,
writes `kilo: Lua panic:` and the error on standard error, and exits 1,
without closing a state that is in no shape to be closed. 09.01's Break it,
an unprotected call, reaches it: with the call in `scriptProtected()` made
a plain `lua_call()`, and an init file whose second line is
`print('hello ' .. nme)`, the editor at this lesson ends at once with this
on standard error, status 1, and a terminal that works:

## Decide the boundary

![Where extension code runs, in three panels. Neovim: Lua inside the editor's process, no count hook in its Lua glue, and an open issue saying a loop that never ends cannot be interrupted. VS Code: extensions in a separate extension host process, with the editor's own permissions, kept from slowing the editor's own work. Zed: WebAssembly run inside the editor's process, with only the extension's own directory of files and what the capability system grants](figures/09.08-trust.svg)

kilo runs a script inside the editor's own process, with all its trust: a script can
read and write any file, and the guards above are courtesy, not walls.
Neovim does the same, Lua in the editor's process, one state; so does
Emacs, most of which is Lisp. Calls are direct and fast, and one bad
plugin is the editor's problem. VS Code runs extensions in another
process, the extension host, "To ensure that extensions cannot interfere
with the stability and performance of VS Code", and every call between an
extension and the editor crosses from one process to the other. It is not
a wall either: "The extension host has the same permissions as VS Code
itself". In Zed,
"Procedural parts of extensions are written in Rust and compiled to
WebAssembly"; a WebAssembly runtime inside Zed's process runs them, gives
each only its own directory of files, and what they may do beyond that is
"governed by a capability system". Who writes the extensions, and what is
the worst one may do?

## Break it

Take the hook out. In `build/at/kilo/09.08/script.c`, in `scriptStart()`,
delete the line that sets it:

<!-- verify: patch file=script.c
-    lua_sethook(S.L,scriptHook,LUA_MASKCOUNT,SCRIPT_HOOK_COUNT);
-->

Make the file again:

<!-- verify: session -->
```
$ printf 'the first line\n' > build/at/kilo/09.08/notes.txt
```

Open a second terminal first. This kilo can be stopped only from there,
and it will leave the first terminal in raw mode; `reset` (or
`stty sane`), typed even if it does not show, then Enter, puts it back.

Start the editor as in Run it, type `unsaved` and a space, and press
Ctrl-T, then Ctrl-C. Nothing happens. The 3 waits on the keyboard, and nothing will read
it: kilo is inside the loop. From another terminal,
`ps -o %cpu,time,comm -p $(pgrep -n kilo)` shows it using a whole
processor:

<!-- verify: skip reason="a reading of the running editor's processor use; the numbers change from run to run" -->
```
 %CPU      TIME COMM
 95.2   0:02.92 ./kilo
```

There is no way back into it from its own terminal. Stop it from the other
one with `pkill -n kilo`. The editor is gone, and so is the `unsaved` you
typed: the file still says `the first line`. And kilo had no chance to put the
terminal back, since SIGTERM ends it without running its exit functions:
the terminal is still in raw mode. Here, in zsh, the prompt itself worked,
but `cat` then showed Enter as `^M` and never ended a line, and in bash
what was typed at the prompt did not show; in zsh `reset` put the terminal
right. Put the line back.
