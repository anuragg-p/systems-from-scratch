# 09.07 Asking, opening, leaving: input(), open(), quit()

Three functions let a script do what until now only the person at the
keyboard could: ask a question and wait for the answer, put another file
in place of this one, and end the session. Each has to be careful about
the one thing a script does that a key does not: it is still running.

## Where this fits

![Where 09.07 fits](figures/09.07-map.svg)

This lesson works in two pieces of the map: the API, which gains three
functions, and the prompt, which until now only Ctrl-E used. A script
calls the API, as before; the API now calls down into the prompt, which
draws the screen and reads keys the way the core does, and into the core's
own reading of a file. Leaving stays the main loop's to do; the API only
asks for it. After this lesson "go to line", "switch to the header" and
"save and leave" are a few lines of Lua each.

## The idea

A "go to line" key has to ask which line. Everything a script could do
until now was work on what is already there: read rows, change rows, move
the cursor, draw. It could not ask the person a question, could not leave
this file for another, and could not end the session. A script that can do
none of those is still a guest in the editor.

**input()** runs the editor's own prompt, the one Ctrl-E shows, from inside
a script, and returns what was typed, or nil for Escape. The script stops
on that line until Enter or Escape, and then goes on with the answer as if
it had called any other function.

**open()** reads another file in place of this one, as the command line
would. It refuses while there are unsaved changes, since reading a file
throws the rows away, and it refuses a file it cannot read, rather than let
the core's reading of it end the editor.

**quit()** does not leave. It sets a mark, and kilo leaves when the script
has returned to the editor and the main loop comes round again. Without
`true` it refuses unsaved changes, as Ctrl-Q warns about them.

Neovim has the waiting kind as `input()`, which "Prompts the user to enter
text on the command-line, and returns the text as a String"
(runtime/doc/vimfn.txt), and a Lua prompt, `vim.ui.input` in
runtime/lua/vim/ui.lua, which takes a function to call with the answer
instead. Opening is `:edit`, which with unsaved changes stops at E37, "No
write since last change (add ! to override)", and leaving is `:q[uit]`;
`:q[uit]!` is "Quit without writing, also when the current buffer has
changes."

![The call stack while input() waits, from the bottom: main's loop, editorProcessKeypress() with the key Ctrl-O, editorScriptKey() offering it to the scripts, the protected call and the mapped Lua function, kilo.api.input() through the dispatcher, and on top editorPrompt(), drawing the screen and reading keys in a loop of its own](figures/09.07-nested-loop.svg)

### `apiInput`

Cleans the prompt the script gave, as every text from a script is cleaned
before it reaches the terminal, cut to 63 bytes, and calls `editorPrompt()`
from 09.01 with it. NULL from the prompt, for Escape, is nil; a line is
returned as a string, and the prompt's copy is freed.

### `apiOpen`

Checks, in order: a save going on, unsaved changes, a name that is empty or
holds a NUL byte, and a file that is there but cannot be read. Then it
frees every row, puts the cursor and the view at the top, and calls the
core's `editorOpen()`, which reads the file, takes its name, and fires
BufReadPost from 09.05, so a script that colours a file colours the new one
too.

### `apiQuit`

Refuses unsaved changes without `force`, and otherwise sets `editorQuit`.

### Leaving, in `editorAfterKey`

The line that reads the mark, the first of the function that already runs
at the top of `main()`'s loop, before the frame is drawn.

## Run it

its header, and an init file with three keys. `./learn run` puts Lua's
source in the folder before it builds; to build there with make yourself,
fetch it first as 09.01 shows.

```
$ cat > build/at/kilo/09.07/init.lua <<'EOF'
local api = kilo.api
-- Ctrl-O: go to a line, asked for.
api.set_keymap('<C-o>', function()
  local s = api.input('Go to line: ')
  local n = tonumber(s or '')
  if n and n >= 1 and n <= api.line_count() then
    api.set_cursor({math.floor(n) - 1, 0})
  elseif s then
    api.message('no line ' .. s)
  end
end)
-- Ctrl-A: from x.c to x.h, and back.
api.set_keymap('<C-a>', function()
  local base, ext = api.get_name():match('^(.*)%.([ch])$')
  if base then api.open(base .. (ext == 'c' and '.h' or '.c')) end
end)
-- Ctrl-X: save, and leave.
api.set_keymap('<C-x>', function()
  if api.save() then api.quit(false) end
end)
EOF
```

## How it works

### A key loop inside the key loop

`main()` loops: draw, read a key, act on it. Ctrl-O is mapped, so acting on
it is calling a Lua function, inside a protected call. That function calls
input(), which calls `editorPrompt()`, which is a loop too: draw, read a
key, until Enter or Escape. The figure above is the stack at that moment.
Two things follow.

The keys typed at the prompt are read by the prompt itself, with the
core's `editorReadKey()`, and never reach `editorProcessKeypress()`. No
mapping and no KeyPress function from 09.05 sees them, so a script cannot
lock itself out of its own question.

And the editor is in the middle of a call into Lua for as long as the
person takes to answer. Lua is waiting on a C function, the C function is
waiting on the keyboard, and nothing else runs: in this project there is
nothing else, but every frame drawn meanwhile is the prompt's, not the main
loop's. The prompt can be used from any place a script runs, a BufWritePre
function included: one that asks for a note to put at the top of the file
gets its answer into the file before it is written.

### Why quit() only sets a mark

![The Ctrl-X of Run it, which saves and then calls quit(false), in three steps: the mark editorQuit set while the Lua function and the C functions under it are still on the stack; the function returns, the protected call ends and the stack is C alone; at the top of main's loop the mark is read, exit(0), and the functions registered with atexit() put the terminal back and close the Lua state](figures/09.07-quit-mark.svg)

`exit()` does not return, but it does not end the process at once either:
it first runs every function registered with `atexit()`. kilo has two. The
core's puts the terminal back. 09.01's, `scriptStop()`, puts it back too
and then closes the Lua state, which frees everything Lua holds, runs every
finalizer a script left, and frees the stack the running functions live on.
Called from inside a script, that last step would pull the state out from
under the call that is running. So the mark waits for the one place where
no Lua function is on the stack, the top of the main loop:

```
    if (editorQuit) exit(0);
```

The **invariant** is that the Lua state is closed only from C, with no Lua
function on the stack. The mark keeps it for quit(), and `scriptStop()`
keeps it for any other `exit()` that happens inside a script:

```
    if (S.L && S.depth == 0) lua_close(S.L);
```

`S.depth` counts the calls into Lua going on now, one inside another. The
mark has a second effect, which is visible: whatever comes after quit() in
the script still runs. Break it shows what that is worth.

### open() tries the file first

The core's `editorOpen()` was written for the command line: a file that is
there but cannot be read is the end of the program, `perror()` and
`exit(1)`. From inside a script that would be an exit with Lua on the
stack. So open() opens the file once itself and closes it:

```
    if ((fp = fopen(path,"r")) != NULL) fclose(fp);
    else if (errno != ENOENT) return apiFail(err,"cannot read %.60s: %s",path,strerror(errno));
```

Only a file
that is not there at all, `ENOENT`, goes on to the core, which makes it a
new, empty file of that name, as `kilo new.txt` does. A name with a NUL byte in it is refused
before that, by comparing `strlen()` with the length Lua gave: C would read
"c\0.txt" as "c". And during a save's own events open() is refused with "a
save is going on", checked before "unsaved changes", which during most
saves is also true but not the reason.

## Decide the boundary

kilo's input() waits: the script reads top to bottom,
`local s = api.input(...)`, and nothing else happens until the answer
comes. Neovim has both shapes. `input()` waits as kilo's does, and Neovim's API docs say
what that costs: "If the editor is waiting for user input in a "modal"
fashion (e.g. an |input()| prompt), a deferred request will block"
(runtime/doc/api.txt). `vim.ui.input({opts}, {on_confirm})` "Prompts the
user for input, allowing arbitrary (potentially asynchronous) work until
`on_confirm`": the script hands over the rest of its work as a function,
and is written inside out. Its default in ui.lua still calls
`vim.fn.input`, and gives nil "if the user aborted the dialog", as kilo's
does; it is the callback's shape that leaves room for the "potentially
asynchronous", and a caller written that way does not care whether the
prompt behind it waited. kilo has one loop and nothing that runs on its
own, so waiting costs it nothing yet. Can anything
else need to happen while the person is thinking?

## Break it

Make quit() leave at once. In `build/at/kilo/09.07/kilo.c`, in `apiQuit()`,
change the line that sets the mark:

<!-- verify: patch file=kilo.c old="editorQuit = 1;" new="exit(0);" -->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
    exit(0);
```

Run it as before, type `x`, and at Ctrl-E type a line that quits and then
writes a file:

<!-- verify: skip reason="a line typed at the editor's prompt, not a shell command" -->
```
kilo.api.quit(true) io.open('after.txt', 'w'):write('ran'):close()
```

Enter. kilo leaves at once, with status 0, and the terminal is as it should
be: `scriptStop()` put it back, then found a call still running and left
the state alone. But there is no `build/at/kilo/09.07/after.txt`: the rest
of the line never ran. Without the change the file is there and says
`ran`. The state was never closed either: a script's finalizer that writes
a file (a `__gc` function) wrote nothing with the change, and did without
it.

<!-- verify: mention names="build/at/kilo/09.07/after.txt" outside reason="a file the line typed at the prompt writes, only without the change" -->

The worst case is a save. An init file whose BufWritePre function calls
`kilo.api.quit(true)`, to save and leave on Ctrl-S, run on a file holding
`x`, with `y` typed and Ctrl-S: with the change kilo leaves before the
write, and the file on disk still says `x`. Without it, the save finishes,
then kilo leaves, and the file says `yx`. The script asked to leave after
the save, and the save was lost. Put the line back.
