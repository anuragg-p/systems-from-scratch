# 09.10 Features as scripts

Three features of an editor, written as Lua plugins on this module's API
without a line of new C: vi's two modes, colours for C and Lua, and find
with go to a line. Each is set beside the C it stands in for, to see what a
script does as well, what it does worse and why, and what it cannot do at
all.

## Where this fits

![Where 09.10 fits](figures/09.10-map.svg)

This lesson builds no piece of C. It fills the box at the bottom of the
map, the scripts outside the editor, with three plugins that an init file
loads. They reach the editor as every script does: through the API table,
the keymaps, the events and the highlights of this module's earlier
lessons. After it, the module's claim, that the editor can be extended
without compiling it, has been tested on real features, and its limits
are named.

## The idea

"The editor is extensible" is a claim. A fair test of it: could the
editor's own features have been written as scripts? This lesson takes
three. Find is the core's C, from module 05. Colour is module 06's C, not
in this lesson's project (the core and module 09). vi's two modes are in
no part of the track. Each is written in Lua on `kilo.api` alone.

![Three features as scripts: what each is, or would be, in C; the plugin that does it in Lua; and the API functions each plugin calls](figures/09.10-could-have-been.svg)

The plugins are three files in the project's `plugins/` folder. An init
file loads each with Lua's own `require('plugins.vi')`, which finds
`plugins/vi.lua` through `package.path`: after Lua's own folders under
/usr/local, its default ends with `./?.lua`, and kilo runs in the
project's folder. Each file returns a table
(vi.lua's holds its mode), and `require` keeps it: it "starts by looking into the
package.loaded table to determine whether modname is already loaded", the
Lua manual says. So a plugin runs once, however many scripts ask for it;
`dofile` would run it again and make its autocommands twice.

<!-- verify: mention names="require() dofile() package.path package.loaded require('plugins.vi') require('plugins.vi').mode" outside reason="Lua's own functions and tables, as the init file and the prompt use them" -->

### `plugins/vi.lua`

One KeyPress function (09.05), which sees every key before any mapping or
the editor, holds both modes. In normal mode it looks the key's name up in
a table of functions: h, j, k, l, 0 and $ move with `get_cursor`,
`get_lines` and `set_cursor`; x, dd and o change rows with `set_lines`
(09.03); i, a and o switch to insert mode. A printable key it does not know
is taken and does nothing, as in vi; a named key goes back to the editor:

```
  elseif normal[key] then
    normal[key]()
  elseif #key > 1 and key:sub(1, 1) == '<' then
    return false                        -- a named key: the editor's own
  end
```

In insert mode it gives back every key but Escape, which steps the cursor
back one, as vi does. The mode is in the status bar, by `set_statusline`
(09.06). What it lacks against vi: counts, every operator but dd, visual
mode, `.`; dd keeps the column where vi goes to the first character; and
keys typed at kilo's own prompts never reach it, since those loops read
their own keys (09.07).

### `plugins/colour.lua`

Module 06's classes and colours, with 06's own lists of C keywords and
types, and Lua's besides. It is 09.06's yellow-numbers script grown up: a
namespace of its own and one function, `colour()`, run on BufReadPost,
TextChanged and CursorMoved, which clears the namespace, picks the
language from `get_name`, asks `get_view` and `get_size` which rows the
screen shows, reads them with `get_lines`, and puts an `add_highlight` on
each number, string, comment, keyword and type. One question the screen's
rows cannot answer: does the top row start inside a `/*` comment? So it
first reads every row above the view, colouring nothing:

```
  if top > 0 then
    for _, s in ipairs(api.get_lines(0, math.min(top, count))) do comment = scan(s, lang, comment, none) end
  end
```

That loop is the price of being a plugin, below. Smaller differences from
06: the spaces that start a row inside a comment are coloured, a control
character is not drawn reversed, and Lua's long strings are not read.

### `plugins/find.lua`

Ctrl-N, given with `set_keymap` (09.04), starts a find as the core's Ctrl-F
does: it notes `get_cursor` and `get_view`, and a KeyPress function takes
every key while the find lasts. A character adds to the query and the
search starts again from the top, over the rows from `get_lines`; the
match's row goes to the top of the screen with `set_view`, the cursor onto
it with `set_cursor`, and the match is drawn blue. Down and Up go to the
next and previous match; Enter stays; Escape puts back the cursor and the
view. `set_view` is the one function the API gained for these plugins:
without it Escape could not put back the exact view. Ctrl-O is 09.07's go
to a line, on `input()`. Against Ctrl-F, the query shows with `message()`,
not as a prompt with a cursor, and a character above 127 cannot be typed
into it: it arrives as one `<xNN>` key per byte.

core's own find, is still there to compare.

## How it works

### What the colours cost

For this track, the time from a typed key to the end of its frame was
measured on a 1068-line C file, the core's own kilo.c at 05.02, the median
of 40 keys. Module 06 is not in this lesson's project, so its colours were
measured in the project at 06.05, the core and module 06; colour.lua, and
no colours at all, in this lesson's:

| | at the top of the file | at main(), row 1050 |
|---|---|---|
| module 06, in C | 0.57 ms | 0.43 ms |
| colour.lua | 0.81 ms | 11.63 ms |
| no colours | 0.46 ms | 0.40 ms |

At the top the plugin costs a quarter of a millisecond more than the C; at
row 1050, eleven. To see the work itself, copy the core's kilo.c beside
this lesson's project:

<!-- verify: session -->
```
$ ./learn files kilo --at 05.02
Wrote kilo as it stands at 05.02 (Next match, previous match, and going back) to build/at/kilo/05.02/
$ cp build/at/kilo/05.02/kilo.c build/at/kilo/09.10/big.c
```

<!-- verify: mention names="big.c" outside reason="a copy of the core's kilo.c the reader makes, not a file of this project" -->

Open `big.c` as `sum.c` was opened, press Ctrl-E, and time a hundred calls
of the plugin's function:

<!-- verify: skip reason="a line typed at the editor's prompt, not a shell command" -->
```
c = require('plugins.colour') t = os.clock() for i = 1, 100 do c.colour() end print((os.clock() - t) * 10 .. ' ms')
```

<!-- verify: mention names="os.clock()" outside reason="Lua's own function, typed at the prompt" -->

On a terminal 24 rows by 80 it said `0.01444 ms` a call. Ctrl-O, `1050`,
Enter, and the same line again: `4.71056 ms`. A typed key calls it twice,
for TextChanged and for CursorMoved: most of the 11.63.

The difference is a state per row. Module 06 keeps in every row whether it
ends inside an open comment, `hl_oc`; when a row changes it colours that
row again, and the next only if that answer changed. colour.lua has nowhere
to keep a state that follows the rows, and TextChanged says that the text
changed, not where. So it reads every row above the view, on every key. It
would need a piece the API lacks: an event that says
which rows changed (Neovim's `nvim_buf_attach`, whose `on_lines` is
"Called on linewise changes", given the first and last line changed), or
marks that move with the text (Neovim's extmarks).

<!-- verify: fact cmd="wc -l < plugins/find.lua | tr -d ' '" expect=105 -->
In lines, `plugins/colour.lua` is 113, 94 of them code, where module 06
adds 411 to kilo.c, 261 of them code; `plugins/vi.lua` is 89 and
`plugins/find.lua` 105.

### Keys that arrive at once

Paste a line of sixty letters into `sum.c` in insert mode, so that they
arrive together. All sixty arrive, in order, though not all by the usual
road. colour.lua runs twice on every key, so a few keys into the paste the
count of 09.08's hook runs out inside it, and the hook reads the rest of
the paste while the plugin works: in a copy of the project that counted,
it kept the last 53 bytes. `editorReadKey()` takes those before anything
new from the terminal, so the plugin's work on each key costs time, never
keys. A plugin that runs on every key is a script running while the person
types, and 09.08's guard is in the path of the typing.

### What a script still cannot do

![Four things a script cannot do in kilo, the piece of an editor each would need, and that piece in Neovim](figures/09.10-frontier.svg)

Some limits are a function away; set_view was one. Four are not:

- **Wait for time, or work in the background.** kilo has no timer, and in
  the finished project module 07 already waits on a poll() of its own: one
  loop has to own all the waiting. In Neovim that loop is libuv: "Platform
  and I/O facilities are built upon libuv" (vim_diff.txt), and `vim.uv`
  gives Lua its bindings.
- **More than one file.** The core's `E` is one file. Neovim has buffers,
  a type of its API, which the `nvim_buf_` functions take;
  `nvim_create_buf` "Creates a new, empty, unnamed buffer."
- **Highlights that move with the text.** kilo keeps a list, put again on
  TextChanged (09.06). Neovim's extmarks sit in a tree, marktree.c, which
  every edit adjusts through `extmark_splice`, and each can carry "a
  priority value for the highlight group"; its treesitter colouring uses
  100.
- **Windows.** The screen is the core's, one file in one view. Neovim's
  API has a Window type, `nvim_win_set_cursor` sets the cursor "in the
  window", and floating windows "are displayed on top of normal windows".

Each is a different editor, not a missing function: a loop, a list of
buffers, a tree of marks, a list of windows, each reaching into all of the
core.

## Decide the boundary

How much of an editor should be script? Emacs is mostly script: its manual
says "Most of the editing commands in Emacs are written in Lisp; the few
exceptions could have been written in Lisp but use C instead for
efficiency", and the C parts are primitives that Lisp calls. Vim's
normal-mode commands are C (normal.c "Contains the main routine for
processing characters in command mode"), with its own language beside
them, used "for the startup vimrc file, syntax files, and many other
things". Neovim
writes features in Lua over its C API: its keymaps, and its language
server client (runtime/lua/vim/lsp/client.lua, where this track's was
module 07's C); what every edit goes through, `nvim_buf_set_lines` in
src/nvim/api/buffer.c and the marks' tree in marktree.c, is C. kilo now
has its core in C and three features as scripts, one of them eleven
milliseconds a key slower than its C at the end of a long file. What must
be fast, and what must be changeable?

## Break it

Load vi before find. In `build/at/kilo/09.10/init.lua`, move the last line
up one:

<!-- verify: mention names="build/at/kilo/09.10/init.lua" outside reason="the init file the reader made in Run it" -->

<!-- verify: patch file=init.lua
 require('plugins.colour')
+require('plugins.vi')

-require('plugins.vi')
-->
<!-- verify: skip reason="init.lua as the reader changes it; the patch above makes the change" -->
```
require('plugins.colour')
require('plugins.vi')
require('plugins.find')
```

Open `sum.c` again, press Ctrl-N, and type `total`. The `t` goes to vi,
which takes a printable key it does not know and does nothing: the query
stays empty. The `o` goes to vi too, which opens an empty row under the
first and switches to insert mode. Now vi gives keys back, so `t`, `a`
and `l` reach the find, whose query is `tal`:

<!-- verify: skip reason="rows of the editor's screen and its bottom two rows, styles written out; captured on a 14 x 60 pseudo-terminal with track.py's Screen" -->
```
    [g:int] to[b:tal] = [r:0];
...
-- INSERT -- sum.c                                      7/12
Search: tal (Use ESC/Arrows/Enter)
```

The first Escape goes to vi, back to normal mode, and the find goes on.
The second reaches the find, which puts back the cursor and the view, on a
file of 12 lines: one is the empty row nobody meant to make.

Neither plugin is wrong. KeyPress functions run in the order they were
made, and the first that returns true has the key (09.05); vi in normal
mode takes every printable key, and find takes every key while it lasts.
The order of the `require` lines is the only rule there is. Drawing has the
same rule: highlights are drawn in the order they were added (09.06).
Loaded as find, colour, vi, a search for `int` shows each match green, not
blue: the cursor moves to it, CursorMoved runs find's function and then
colour.lua's, and colour.lua's green is drawn last. Neovim makes mappings
per mode and gives an extmark's highlight a priority; kilo has neither.
Put the line back.
