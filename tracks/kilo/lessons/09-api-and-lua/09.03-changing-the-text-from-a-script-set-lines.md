# 09.03 Changing the text from a script: set_lines

One API function, `set_lines(start, end, lines)`, lets a script insert,
delete and change rows: it replaces a range of rows by a list of lines,
checks everything before it changes anything, and puts the cursor where it
belongs afterwards. `set_cursor` and `save` come with it.

## Where this fits

![Where 09.03 fits](figures/09.03-map.svg)

This lesson adds to the API piece of 09.02, and the arrow between it and
the core's rows now carries changes as well as reads. A script's change
goes through the dispatcher to the API, and the API makes it with the same
functions the core uses when a key is typed: delete a row, insert a row.
Nothing above the rows can tell a script's change from a typed one. After
this lesson a script can rewrite any part of the file, move the cursor and
save, which is everything a command that edits needs; what it cannot yet do
is run when a key is pressed.

## The idea

After 09.02 a script can read every byte of the file and change none of
them. It needs a way to put text in, take it out and replace it. One
function does all three: replace the rows `[start, end)` by these lines.
On the five rows a to e, counting from 0:

- `set_lines(1, 3, {'X', 'Y'})` replaces b and c: a change.
- `set_lines(2, 2, {'new'})` replaces nothing, an **empty range**, so it
  inserts before row 2.
- `set_lines(1, 3, {})` replaces b and c by no lines: a delete.

![set_lines on the same five rows, step by step: a change, rows 1 and 2 replaced by two new lines; an insert, an empty range at row 2 and one new line before it; a delete, two rows replaced by none; and a call with a line holding a newline, refused, every row where it was](figures/09.03-set-lines.svg)

Every argument is checked before the first row changes: the range must be
a range of the file, and no line may hold a newline, since a row is one
line. A call that fails changes nothing. When it is right, the rows of the
range are deleted, the lines inserted, and the cursor put by a rule, so
that it stays on the text the user was looking at.

Neovim's version is `nvim_buf_set_lines()`, in src/nvim/api/buffer.c, and
it reads the same: "To insert lines at a given index, set `start` and `end`
to the same index. To delete a range of lines, set `replacement` to an
empty array."

<!-- verify: mention names="nvim_buf_set_lines() src/nvim/api/buffer.c" outside reason="Neovim's source, read at v0.12.6; not this project's" -->

### `apiSetLines`

The checks, then the change through `editorDelRow()` from 04.03 and
`editorInsertRow()` from 03.01, then the cursor.

### `apiSetCursor`

`set_cursor({row, col})`: anywhere inside the text, refused elsewhere, the
view scrolled as little as shows it, by `editorShowCursor()`.

### `apiSave`

`save()` is Ctrl-S: `editorSave()`, and `true` unless it failed, when the
message line says why.

### `editorScriptReturned`

Called by `scriptProtected()` each time a script has returned to the
editor, not one inside another: it puts the cursor back inside the text
if anything left it outside.

by Ctrl-Q as many times as it asks, open the file again, and press Page

the message line says `5`, a row the file does not have, and the bar now
says `3/2`. Ask again and it says `2`, the row just past the last.

## How it works

### Everything is checked before anything changes

The dispatcher from 09.02 has made sure of the types: two integers, and a
list of strings. `apiSetLines()` checks the rest, in order, and returns at
the first problem:

```
    if (!apiRange(start,end,err)) return apiValue(API_NIL);
    for (j = 0; j < n; j++)
        if (memchr(line[j].s,'\n',line[j].len))
            return apiFail(err,"a line cannot hold a newline (line %d)",j+1);
```

Only after the last check does a row change. That is the **invariant**:
`set_lines` changes every row it was asked to, or none. A script that gets
an error can trust the file is as it was, and try something else.
`nvim_buf_set_lines()` keeps the same order. It validates first ("Index out
of bounds", "'start' is higher than 'end'", and a newline in an item is
refused for Lua and RPC callers: "'%s' item contains newlines"), saves the
range for undo, and only then changes the buffer. In kilo any byte but a
newline, a NUL or a tab or a carriage return, is taken as it is.

### Delete, then insert, with the core's own functions

```
    for (j = end-1; j >= start; j--) editorDelRow(j);
    for (j = 0; j < n; j++) editorInsertRow(start+j,line[j].s,line[j].len);
```

The deletes go from the end of the range down, so each row deleted is
still at the index it had: deleting row `start` first would move the rest
up under the loop. Then each line goes in at its place.

These are the core's own: `editorInsertRow()` from 03.01 and
`editorDelRow()` from 04.03, which shift the rows after the one they touch,
make the new row's render, and count the file dirty. Because of that, everything that
watches those functions sees a script's change with no code for it here.
In the finished project, which has modules 06 to 08 too, a row a script
puts in is coloured as a typed one is, it is sent to the language server,
and one Ctrl-Z takes the script's change back. In Neovim the change goes
through its own buffer functions in the same way, `ml_delete_buf()`,
`ml_append_buf()`, then `changed_lines()`, which raises the buffer's change
count.

### Where the cursor goes

![The cursor rule in three small panels, each before and after a call: a cursor below the range stays on its line, its row moved by the number of rows the range gained or lost; a cursor inside the range stays on its row, or goes up to the range's new last row when the range shrank past it, its column cut to the row; a cursor above the range does not move](figures/09.03-cursor-rule.svg)

The cursor is a row and a byte of the file, and the rows under it have just
changed. There are three cases, and the code is one each:

```
    if (row >= end) {
        row += n-(end-start);
    } else if (row >= start) {
        if (n > 0 && row > start+n-1) row = start+n-1;
        if (n == 0) row = start < E.numrows || E.numrows == 0 ? start : E.numrows-1;
        size = row < E.numrows ? E.row[row].size : 0;
        if (col > size) col = size;
    }
```

Below the range, the cursor stays on its line, which moves by as many rows
as the range grew or shrank: the header went in above, and the cursor went
from row 1 to row 2, counted from 0, with its `second`. Above the range, nothing moves. Inside
it, the line the cursor was on is gone, so it keeps its row if the new
lines reach that far and else goes up to the last of them; with no new
lines, to the row that took the range's place, or the file's last row.
The column is cut to the row it lands on. Neovim's rule differs inside the
range: its `fix_cursor()` keeps the cursor on the same line number, and
only clamps it to the last line when lines were deleted.

<!-- verify: mention names="fix_cursor()" outside reason="Neovim's source, read at v0.12.6; not this project's" -->

### After every script, the cursor is in the text

`set_lines` keeps its own cursor right, but the rule must hold whatever a
script did, and the core itself can break it: Page Down on a short file
leaves the cursor on the screen's last row, below the text. A script that
read that place and computed a row from it would be wrong, and the next
call that used it would be refused. So the one door into Lua, 09.01's
`scriptProtected()`, checks on the way out, when no other script is still
running:

```
    if (S.depth == 0) editorScriptReturned();
```

and `editorScriptReturned()` brings the cursor to the row just past the
last at most, and inside its row. That is what Run it's Page Down showed:
the script saw row 5, and when it returned the cursor was on row 2.

## Decide the boundary

kilo has one function that changes text, and every other edit a script
wants is made of it. Neovim, too, has a small number of general functions,
`nvim_buf_set_lines()` and `nvim_buf_set_text()`, the second for "only
modifying parts of a line", and its own implementation, not built on the
first. The surface is small, and it is a promise: `nvim_buf_set_lines()`
has been in the API since its first level. The other way is a function for
each thing a script might want, insert a line, delete one, replace one:
easy to call, and every one of them has to keep working, the same way, for
as long as scripts use it. Neovim had such functions once; the only callers
of `nvim_buf_set_lines()` in its API files now are the deprecated ones,
`buffer_insert` and `buffer_set_line` among them, kept as wrappers around
it. What will you have to keep stable for years?
