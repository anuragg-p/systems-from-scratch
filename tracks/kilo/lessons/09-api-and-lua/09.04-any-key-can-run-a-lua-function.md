# 09.04 Any key can run a Lua function

A script can now give a key a Lua function to run in place of what the
editor does with it. C cannot hold a Lua function, so kilo keeps an integer
that Lua gives it for one, and hands the integer back when the key comes.

## Where this fits

![Where 09.04 fits](figures/09.04-map.svg)

This lesson builds the keymaps piece, at the left of the row of the
module's pieces in kilo.c. The core's key handler hands it every key it
reads, before its own switch: the line down the left side of the map. If
a script has given that key a function, the keymaps piece calls it, through
the interpreter below it, and the key is taken; the function, like any
script, reaches the editor only through the API. After this lesson an
init file can add commands to the editor, on any key but the way out, and
a command can still end in what the editor itself does for a key.

## The idea

Since 09.01 Lua code has run at the `lua: ` prompt, a line at a time, and
since 09.03 it can change the text. A line typed at a prompt each time is
not a feature. "Ctrl-D puts a copy of this line below it" is: written once,
in the init file, and used for ever after with one key.

The difficulty is what the editor keeps. A Lua function is a value inside
Lua's world, moved by Lua's garbage collector and freed when nothing in
that world refers to it any more. C has no type for it, and a pointer to it
would not keep it alive. What Lua offers is the **registry**, a table that
belongs to C: its manual calls it "a predefined table that can be used by
any C code to store whatever Lua values it needs to store". `luaL_ref`
takes the value on top of the stack, stores it in the registry under a free
integer key, and returns that integer, a **reference**. The registry is
always reachable, so the function in it is never collected. C keeps the
small integer; to call the function, it pushes `registry[n]` back onto the
stack. `luaL_unref` gives the slot back, and the function, if nothing else
holds it, can then be collected.

![A function kept by reference, step by step: the function on Lua's stack, an argument of set_keymap; luaL_ref moves it into the registry and returns an integer; the integer stored in kilo's table of keys; the key pressed: the integer looked up, the function pushed from the registry and called; the key mapped again: the old integer given back with luaL_unref](figures/09.04-reference.svg)

Neovim does exactly this. Its type for the integer is **LuaRef**, `typedef
int LuaRef;` in src/nvim/types_defs.h, with the comment "Opaque handle to a
lua value. Must be free with `api_free_luaref` when not needed anymore!";
src/nvim/lua/executor.c makes one with `luaL_ref(lstate,
LUA_REGISTRYINDEX)` in `nlua_ref`, pushes it back with `lua_rawgeti` in
`nlua_pushref`, and calls it with `nlua_call_ref`.

So the API gains a type, function, and three functions that take a key by
its name: `set_keymap(key, fn)`, `del_keymap(key)` and `feed_key(key)`.
Every key the editor can read has a name: a printable character is itself
(`"x"`, `"<"`), `"<C-a>"` to `"<C-z>"` are the control keys, `"<Enter>"`,
`"<Esc>"`, `"<Up>"`, `"<PageDown>"` and the rest are the named keys, and
`"<xNN>"`, two hex digits, is any other byte. Ctrl-Q alone is refused: it
is how the user leaves, and no script may take that away.

`feed_key` is the other half. A function mapped to Ctrl-S replaces the
save; `feed_key("<C-s>")` inside it does what the editor itself does for
Ctrl-S, and saves. So a mapping can wrap the editor's own action instead of
redoing it.

![Three layers: at the bottom the editor's C functions; above them kilo.api, made from the table of 09.02; at the top kilo.keymap.set and kilo.lines, written in Lua. Beside each, Neovim's name for the same layer: the C functions in src/nvim/api, vim.api generated from them, and vim.keymap in runtime/lua/vim/keymap.lua](figures/09.04-layers.svg)

And on top of the API, kilo now has some Lua of its own, compiled into the
binary: `kilo.keymap.set(keys, fn)`, which takes a key or a list of keys,
and `kilo.lines()`, an iterator over the rows. Neovim's `vim.keymap.set` is
the same idea: Lua, in runtime/lua/vim/keymap.lua, that calls
`vim.api.nvim_set_keymap` for each mode it is given.

### `scriptCallIn`

Calls the function behind a reference: `lua_rawgeti()` pushes it from the
registry, then one argument if there is one, and `lua_call()` asks for one
result, kept as true or false. `scriptCall()` runs it through 09.01's
protected way in, so an error in the function comes back as a message. And
`scriptUnref()` gives a reference back.

### `editorKeyByName`

A key's name to the key, or -1. A printable character is itself; a name
in `KEYNAMES` is that key, in either case; `<C-x>` is the letter's
control code, its low five bits; `<xNN>` is the byte.

### `apiSetKeymap`

The key from its name (`apiKey()`, which refuses Ctrl-Q), its slot in the
table of keys, and the reference the dispatcher made from `fn` stored
there, after the one that was there is given back.

### `apiDelKeymap`

Gives the reference back and empties the slot; a key with nothing mapped
is an error.

### `apiFeedKey`

Puts the key in `editorFed` and calls the core's `editorProcessKeypress()`,
which takes the key from there instead of reading one.

### `editorScriptKey`

The core offers it every key it reads. Ctrl-Q never goes further than its
first line; any other key with a function in its slot is passed to
`scriptCall()`, and taken.

### The Lua on top

`SCRIPT_LUA`, 18 lines of Lua in a C string, run once when the state is
made, after `kilo.api`, under the chunk name `kilo.lua`.

Outside these: in `editorProcessKeypress()`, the read and one line before
the switch, below; the table `editorKeymap` and `editorKeymapSlot()`, which
finds a key's slot (the 256 bytes, then the arrows and the other named
keys); in script.c, `API_FUNCTION`, checked and turned into a reference by
the dispatcher.

## Run it

Make the program in this lesson's folder, and a small Lua file to edit:

<!-- verify: session -->
```
$ ./learn files kilo --at 09.04

$ printf 'local x = 1\nprint(x)\n' > build/at/kilo/09.04/demo.lua
```

Put this in `build/at/kilo/09.04/init.lua`:

<!-- verify: patch file=init.lua create
@block
-->
```lua
-- Ctrl-D: a copy of the cursor's line, below it.
kilo.keymap.set('<C-d>', function()
  local row = kilo.api.get_cursor()[1]
  local line = kilo.api.get_lines(row, row + 1)[1]
  kilo.api.set_lines(row + 1, row + 1, {line})
end)

-- Ctrl-T: comment the cursor's line out, or back in.
kilo.keymap.set('<C-t>', function()
  local row = kilo.api.get_cursor()[1]
  local line = kilo.api.get_lines(row, row + 1)[1]
  if line:sub(1, 3) == '-- ' then line = line:sub(4) else line = '-- ' .. line end
  kilo.api.set_lines(row, row + 1, {line})
end)

-- Ctrl-S: save as the editor does, then count it.
local saves = 0
kilo.keymap.set('<C-s>', function()
  kilo.api.feed_key('<C-s>')
  saves = saves + 1
  kilo.api.message('saves so far: ' .. saves)
end)
```

and start the editor on the Lua file with it as the init file (09.01:
`KILO_INIT` names one; `./learn run` builds kilo with Lua as it did there):

```

```

Press Ctrl-D. On a terminal 8 rows by 72 columns:

<!-- verify: skip reason="a screen the full-screen editor draws, captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->

Ctrl-T again takes the `--` and its space off, and a third time puts them

Now Ctrl-S. The bottom two rows are


## How it works

### Who holds the reference

The reference is made by the dispatcher of 09.02, which has one more type
to check and convert now. An argument of type function is pushed again and
stored:

```
        lua_pushvalue(L,idx);
        v.u.function = luaL_ref(L,LUA_REGISTRYINDEX);
```

From then on exactly one place owns it. `set_keymap` keeps it in the key's
slot, giving back the one that was there:

```
    if (*slot) scriptUnref(*slot);
    *slot = args[1].u.function;
```

and if the API function fails, a key name that names no key or Ctrl-Q, the
dispatcher gives it back itself, since nothing kept it. The **invariant**:
every reference kilo holds is in exactly one place, a key's slot; 09.05
adds the other place, an event's list. A reference in no place is a
function Lua can never collect, and one in two places would be given back
twice.

You can watch the integers. At the prompt, list the keys of the registry
that hold functions:
`local t = {} for k, v in pairs(debug.getregistry()) do if type(v) ==
'function' then t[#t+1] = k end end print(table.concat(t, ' '))`. With
this init file it says `4 5 6`: the three mappings. Map Ctrl-D again,
`kilo.keymap.set('<C-d>', print)`, and the same line says `5 6 7`: the new
reference was made, 7, before the old, 4, was given back. Map Ctrl-T to
`print` too and it says `4 6 7`: `luaL_unref` had put 4 on a list of free
slots, and the next `luaL_ref` took it from there.

### One line before the switch

The core's key handler changes in two lines:

```
    int c = editorFed != -1 ? editorFed : editorReadKey(fd);
    if (editorFed == -1 && editorScriptKey(c)) return;  /* a script took it */
```

Every key the user types is offered to the scripts first, and a key they
take never reaches the switch. `editorScriptKey()` begins with

```
    if (c == CTRL_Q) return 0;
```

which is the guarantee: whatever a script has asked for, Ctrl-Q goes to the
editor. `set_keymap` and `feed_key` refuse it as well, but those refusals
only make the error early; this line is what holds. A key the editor reads
somewhere else, inside find or at a prompt, is never offered: those loops
read their own keys, and there an `x` is typed even if `x` is mapped.

### Names, and keys that are the same key

Some names are one key twice, because the terminal sends one byte for both.
Enter sends 13, carriage return (raw mode turned off the driver's change of
it into a newline), and Ctrl-M is M's low five bits, also 13: `"<C-m>"`
and `"<Enter>"` name the same slot, and so do `"<C-i>"` and `"<Tab>"`. kilo
cannot tell them apart. Ctrl-H,
byte 8, is not Backspace here: the Backspace key sends 127 on the
terminals kilo targets, so mapping `"<C-h>"` leaves Backspace alone.

### A fed key skips the scripts

`feed_key` sets `editorFed` and runs the whole key handler, which uses
that key and offers it to no script, because of the `editorFed == -1` in
the second line. Without it, the Ctrl-S function above would feed Ctrl-S,
which would run the function, which would feed Ctrl-S. That was tried:
with the condition taken out and a Ctrl-S mapping that counts its calls
and feeds Ctrl-S, one press gives `C stack overflow` in the message line,
the count is 99, and nothing is saved. Lua counts the calls nested
through C and refuses the 200th (`LUAI_MAXCCALLS` in its llimits.h); each
round here is two of them. Neovim's nearest is
`nvim_feedkeys` with the mode flag `n`, "Do not remap keys".

### A function that fails

The mapped function runs inside the protected call of 09.01, so its error
is a message, not a crash, with its place in the init file in front. Press
Down past the last row, to the empty one below it, and Ctrl-D: the message
line says `init.lua:4: get_lines: [3, 4) is not a range of the file's 3
rows`, and nothing else happens. The key is still taken: the editor does
not fall back to its own action for a key whose function failed.

## Decide the boundary

kilo's C gives scripts a thin layer, a table of functions, and puts the
convenience on top in Lua: `kilo.keymap.set` is a few lines of Lua around
`set_keymap`. Neovim goes much further: `vim.keymap` is Lua, and so is its
language server client, runtime/lua/vim/lsp/client.lua, which in this track
was module 07's C. Emacs goes furthest; its manual says "Most of the
editing commands in Emacs are written in Lisp; the few exceptions could
have been written in Lisp but use C instead for efficiency." The other way
is everything in C, as this track's core is: fast, one language, and a
compile for every change. The price of crossing over is small but real: at
the prompt here, a million calls of an empty Lua function took about 6 ms,
and a million calls of `kilo.api.line_count()` 37 to 46 ms, about 40 ns
each. Who should be able to change it, and how fast must it run?

## Break it

Forget to give the old reference back. In
`build/at/kilo/09.04/kilo.c`, in `apiSetKeymap()`, delete the line:

<!-- verify: patch file=kilo.c
-    if (*slot) scriptUnref(*slot);
-->
```
    slot = editorKeymapSlot(key);
    if (*slot) scriptUnref(*slot);     <- delete this line
    *slot = args[1].u.function;
```

Run the editor as before, press Ctrl-E, and map one key a hundred thousand
times, each time to a new function, measuring Lua's memory, in kilobytes,
around it:
`n = collectgarbage('count') for i = 1, 100000 do
kilo.api.set_keymap('<C-y>', function() return i end) end collectgarbage()
print(collectgarbage('count') - n)`. The message line says

<!-- verify: skip reason="the editor's message line after a line typed at its prompt, captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->
```
9856.5908203125
```

where the unchanged code says `-3.7060546875`. Nearly 10 MB is held, about
100 bytes for each function and its slot in the registry, and none of it
can ever be freed: the key's slot holds only the newest integer, so the
99999 others are in the registry with nothing that knows their numbers.
Nothing on the screen looks wrong. Put the line back.
