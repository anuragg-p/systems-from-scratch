# 09.05 Events: autocommands

kilo now names a few moments in its own work, a file read, before and
after a save, a change to the text, the cursor moved, a key about to be
handled, and calls the Lua functions a script has bound to each. Vim and
Neovim call such a binding an **autocommand**.

## Where this fits

![Where 09.05 fits](figures/09.05-map.svg)

This lesson builds the events piece, in the middle of the row of the
module's pieces in kilo.c. The core calls it from inside its own work: the
save (the short line down from the core's file functions on the map), the
read, the loop that waits for keys, and the key handler, just ahead of the
keymaps piece of 09.04. Each time, it calls the functions scripts bound to
that moment, through the interpreter below it. After this lesson a script
can act when the editor does something: clean the file before every save,
whichever key saved it, or keep a count up to date as you type.

## The idea

A mapped key runs when the user asks for it. Some things should run when
the editor does something. Trailing spaces should go before every save,
from Ctrl-S, from a script's `save()`, from a mapping that feeds Ctrl-S. A
count of the words should change after every change, typed or made by
another script. Mapping every key that might do either would be fragile
and incomplete. The editor knows when it saves; so the editor should say
so.

kilo names six **events**:

| event | when |
|---|---|
| BufReadPost | a file is in the editor: once at start, after the init file |
| BufWritePre | at the start of a save, before the rows are made into the bytes to write |
| BufWritePost | after a save that worked |
| TextChanged | after a key's work, if the text changed |
| CursorMoved | after a key's work, if the cursor is somewhere else |
| KeyPress | before the editor, or a mapping, sees a key |

The first five are Vim's names, and Neovim's: its autocmd.txt describes
BufWritePre as "Before writing the whole buffer to a file", TextChanged as
"After a change was made to the text in the current buffer in Normal mode".
`create_autocmd(event, fn)` binds a function to an event and returns an id
for `del_autocmd(id)`; Neovim's is `nvim_create_autocmd`, which takes a Lua
`callback`. Each function is kept as a reference, as 09.04's mappings are.

To know whether the text changed, kilo keeps the **changed tick**, a count
that goes up by one in each function of the core that changes a row, and
never goes down. `get_changedtick()` returns it. A script that remembers it
can tell later, with one comparison, whether anything has changed since.
Neovim has the same count under the same name, `b:changedtick`, "The total
number of changes to the current buffer"; in its source the increment is
`buf_inc_changedtick`, reached from `changed()` in src/nvim/change.c.

![Keys on a time line, the changed tick under them: a typed letter and the tick goes up by one; an arrow and it stays; Enter in the middle of a row and it goes up by two, the row put in and the row cut. TextChanged fires after each key where the tick moved, and only there](figures/09.05-tick.svg)

Two rules keep this from turning on itself. While an event's functions
run, no event fires. And the tick is noted after TextChanged's functions
have run, so the change a function makes is not heard as another change.

KeyPress is the odd one out. It fires before the editor sees the key, with
the key's name as its argument, and a function that returns true has
**taken** the key: no mapping and no editor action follow. With it a script
can change what every key means; 09.10 builds vi's two modes on it.

### `editorFire`

Calls the functions bound to an event, in the order they were made, each
with one string, and returns whether a KeyPress function took the key.
Nothing happens if an event is already running. It walks the list by id,
so a function may make or delete autocommands while it runs: only those
made before the event began are called, and a deleted one is not.

### `apiCreateAutocmd`

Finds the event by its exact name, refuses past `AUTOCMD_MAX` (64), and
adds the function with the next id; ids are never given twice.

### `apiDelAutocmd`

Gives the reference back and closes the gap, keeping the order.

### `editorAfterKey`

Called at the top of `main()`'s loop, after a key's work and before the
screen is drawn: TextChanged if the tick is not the one it noted last time,
then CursorMoved if the cursor's place is not; then it notes both.

### `editorScriptKey`

09.04's function now fires KeyPress, with the key's name from
`editorKeyName()`, before it looks for a mapping.

Outside these: `E.changedtick` and its six increments; the calls to
`editorEvent()` in `editorOpen()`, `editorSave()` and `main()`; the table
`EVENTS` and the list of autocommands; `get_changedtick`; and in `save()`
and `feed_key()`, a refusal to save while a save's events run.

## Run it

Make the program in this lesson's folder, and a file with spaces at the
end of its first line and a tab at the end of its second:

<!-- verify: session -->
```
$ ./learn files kilo --at 09.05
Wrote kilo as it stands at 09.05 (Events: autocommands) to build/at/kilo/09.05/
$ printf 'hello world  \nsecond line\t\n' > build/at/kilo/09.05/notes.txt
```

Put this in `build/at/kilo/09.05/init.lua`:

<!-- verify: patch file=init.lua create
@block
-->
```lua
-- Before every save: no spaces or tabs at the end of a line.
kilo.api.create_autocmd('BufWritePre', function()
  for row, line in kilo.lines() do
    local trimmed = line:gsub('%s+$', '')
    if trimmed ~= line then kilo.api.set_lines(row, row + 1, {trimmed}) end
  end
end)

-- After every change: the words in the file, in the message line.
kilo.api.create_autocmd('TextChanged', function()
  local words = 0
  for _, line in kilo.lines() do
    for _ in line:gmatch('%S+') do words = words + 1 end
  end
  kilo.api.message(words .. ' words')
end)
```

and start the editor on the file:

<!-- verify: skip reason="starts the full-screen editor; its screens below were captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->
```
KILO_INIT=init.lua ./learn run kilo --at 09.05 -- notes.txt
```

Type `a`: the message line says `4 words` (`ahello` is one). Type a space:
`5 words`. Now Ctrl-S. On a terminal 8 rows by 72 columns:

<!-- verify: skip reason="a screen the full-screen editor draws, captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->
```
a hello world
second line
~
~
~
~
notes.txt - 2 lines                                                  1/2
5 words
```

The file on disk is `a hello world` and `second line`, 26 bytes, with no
space or tab at the end of either. But the message line does not say `26
bytes written on disk`. BufWritePre's function changed two rows, so the
tick moved, and after the key's work TextChanged fired and said the count,
over the save's message, before the screen was drawn. Press Ctrl-S again:
nothing is left to trim, the tick stays, and the line says `26 bytes
written on disk`.

Now take over the keyboard. Press Ctrl-E and type
`kilo.api.create_autocmd('KeyPress', function(k) if k:match('^%l$') then
kilo.api.feed_key(k:upper()) return true end end)`, then Enter. The message
line says `3`, the new autocommand's id. Every lowercase letter is now
taken and fed back as its capital; any other key, the function returns
nothing, and the editor has it as before. Press Down, Left twice, and type
`new` and a space:

<!-- verify: skip reason="the top two rows and the bottom two of the editor's screen, captured on an 8 x 72 pseudo-terminal with track.py's Editor" -->
```
a hello world
NEW second line
...
notes.txt - 2 lines (modified)                                       2/2
6 words
```

`kilo.api.del_autocmd(3)` at the prompt, and an `x` types an `x` again.

## How it works

### Where the core says what it is doing

![One Ctrl-S on a time line: BufWritePre, and the trimming function changes two rows; the rows made into the bytes to write; the write; BufWritePost. Then, after the key's work, TextChanged, since the tick moved](figures/09.05-save-events.svg)

Each event is one call in the core's own code. In `editorSave()`:

```
    editorEvent("BufWritePre");
    char *buf = editorRowsToString(&len);
```

BufWritePre comes before the rows are made into the string to write, so
what its functions change is saved; BufWritePost comes only after a write
that worked. BufReadPost is fired at both of `editorOpen()`'s returns, for
a file that is not there too, and once more in `main()`, after the init
file has run, because at the first read no script was there to hear it.

The tick goes up in six places, each beside the core's own `E.dirty++`:
inserting and deleting a row, inserting, appending and deleting characters
in a row, and the cut when Enter splits a row. Why not use `E.dirty`? A
save sets it back to 0; the tick only ever goes up, so two readings of it
that are equal mean nothing changed in between, a save or not.

### After the key's work

TextChanged is not fired at each change. A mapped key whose script changes
a hundred rows would call every TextChanged function a hundred times, each
seeing a text half done. kilo fires it
once, after the key's work, in `editorAfterKey()`, by comparing the tick
with the one it noted after the last key:

```
    if (tick != -1 && tick != E.changedtick) editorEvent("TextChanged");
    if (tick != -1 && moved) editorEvent("CursorMoved");
    tick = E.changedtick;
```

The tick is noted after the functions have run. A TextChanged function that
changes the text, as the trim does to the save, does not fire TextChanged
again; the next key that changes something does. Neovim's normal.c does the
same: `apply_autocmds` with `EVENT_TEXTCHANGED`, then
`curbuf->b_last_changedtick = buf_get_changedtick(curbuf);`. And because
this runs before the screen is drawn, the frame that shows a change also
shows what the scripts did about it.

![A TextChanged function that changes the text, step by step: a key changes the text and TextChanged fires; the function's own change raises the tick, which is noted after it returns, so nothing fires; the next key that changes the text fires it once more](figures/09.05-nesting.svg)

### A key's way in

A key the user types now goes through three hands: KeyPress functions, in
order, until one returns true; then a mapping, if the key has one; then the
editor's switch. All three are behind the first line of
`editorScriptKey()`, `if (c == CTRL_Q) return 0;`, so a KeyPress function
that takes every key still never sees Ctrl-Q. A fed key, as in 09.04, skips
all of them. Neovim's nearest is `vim.on_key`, a function called for every
key "after mappings have been applied but before further processing", and
since 0.11 able to throw a key away by returning an empty string; kilo's
KeyPress comes before the mappings.

### No nesting

`editorFire()` begins:

```
    if (editorRunning) return 0;
    editorRunning = event;
```

While one event's functions run, every other event is skipped, not queued.
Here it matters when a function saves: a TextChanged function that calls
`save()` saves, and BufWritePre and BufWritePost do not run inside it.
Vim's rule is the same, in autocmd.txt: "By default, autocommands do not
nest. For example, if you use ":e" or ":w" in an autocommand, Vim does not
execute the BufRead and BufWrite autocommands for those commands." Its
autocmd.c skips such an event (`goto BYPASS_AU`); kilo's names are exact,
where Vim's are case-insensitive.

A save inside a save is refused outright: in a BufWritePre or BufWritePost
function, `save()` and `feed_key('<C-s>')` fail with `a save is already
going on`.

### A function that fails

A function that raises an error is said in the message line, and the next
one runs. The save does not care what its functions did:
`editorEvent()` returns nothing, and the write follows it. Bind
`function() error('post failed') end` to BufWritePost at the prompt, type a
character and press Ctrl-S: the message line says `lua:1: post failed`,
and the file on disk has the character. The **invariant** is that a save
writes the file whatever the scripts did; a script can change what is
written, before it is written, and nothing else.

## Decide the boundary

kilo calls scripts at moments it names, as Vim's autocommands do and as
Emacs's hooks do: its manual says "A hook is a variable where you can store
a function or functions ... to be called on a particular occasion by an
existing program." The editor chooses the moments and promises to keep
them; a script can hear only those. Emacs also offers the other way,
advice: "The advice feature lets you add to the existing definition of a
function". Any function is then a moment, so a script can hook into
anything, and nothing it hooks into is promised to stay as it is. A third
way needs no help from the editor at all: a script that looks every so
often at the tick and acts when it moved, at the cost of a delay and of
waking when nothing happens. Which moments will you promise to keep?

## Break it

Hear the scripts' own changes. In `build/at/kilo/09.05/kilo.c`, in
`editorAfterKey()`, make the check a loop that fires TextChanged until the
tick stops moving:

<!-- verify: patch file=kilo.c old="if (tick != -1 && tick != E.changedtick) editorEvent(\"TextChanged\");" new="while (tick != -1 && tick != E.changedtick) { tick = E.changedtick; editorEvent(\"TextChanged\"); }" -->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
    while (tick != -1 && tick != E.changedtick) { tick = E.changedtick; editorEvent("TextChanged"); }
```

Run the editor as before. It works: the word count changes nothing, so the
loop goes round once. Now, at the prompt, bind a function that adds a
character to the first row:
`kilo.api.create_autocmd('TextChanged', function() local l =
kilo.api.get_lines(0, 1)[1] kilo.api.set_lines(0, 1, {l .. '!'}) end)`.
The message line says `3`. The next key hangs the editor for good: open a
second terminal to end it from, and know that this one will be left in raw
mode, which `reset` and Enter put right. Type any letter.

Nothing more is drawn: the screen keeps the frame from before the key.
And Lua says nothing, since no error is ever raised. Each
round adds a `!`, the tick moves, and the loop goes round again, before the
screen is ever drawn. Ctrl-C and Ctrl-Q do nothing, since no key is read.
From another terminal, `ps -o %cpu,rss -p $(pgrep -n kilo)` shows it at
77 to 93 per cent of a processor, and its resident memory growing, from
4016 KB to 5184 KB over three seconds, while the first row grows a `!` at a
time. `pkill -n kilo` ends it. The file on disk is as it was at the last
save: the letter and the unsaved work since are gone, and the terminal is
left in raw mode; type `reset` and Enter, even if you cannot see it. Without the change, the same
function adds one `!` for each key that changes the text.
