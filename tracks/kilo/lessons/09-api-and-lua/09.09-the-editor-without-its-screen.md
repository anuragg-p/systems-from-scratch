# 09.09 The editor without its screen

`kilo -l script.lua file` reads the file, runs the script against it with
the same `kilo.api`, and exits, with no terminal, no screen and no keys.
None of the API's functions changes for it: they never knew there was a
screen.

## Where this fits

![Where 09.09 fits](figures/09.09-map.svg)

This lesson builds the last piece of the module, at the bottom right of the
map, outside the program's own rows: a second door into the editor. Through
it a script reaches the interpreter, and through that the same API and the
same rows a key reaches, but nothing of the editor's face is there: no raw
mode, no screen, no loop waiting for keys. After this lesson kilo is also a
command that edits files from a script, in a shell, a build or a test,
with the same Lua a key would run.

## The idea

Every lesson so far needed a terminal and a person at it. A script that
upper-cases a file, or trims every file of a project, needs neither; it
needs the rows, and the functions that read and change them. Since 09.02
those functions take and give only the API's own plain types and work on
`E`, the editor's state. Whatever they have to say goes through one
function, `editorMessage()`, and only that one decides where it goes. The
only ones that draw are the ones that wait at a prompt for a key: input(),
and feeding Ctrl-E or Ctrl-F.

So `main()` chooses. With a file name it does what it always did: raw
mode, the window's size, the file, the init file, the loop. With
`-l script.lua` and maybe a file, it reads the file, starts Lua with no
screen, runs the script, and returns: 0, or 1 when the script failed. In
between, the same `kilo.api`.

What is different is what has no meaning without a screen. A message, and
`print()`, become a line on standard output, an error a line on standard
error, the bytes as they are: nothing is being drawn, so there is nothing
for a control byte to break. `input()` is an error, `no keyboard`, and so
is feeding Ctrl-E or Ctrl-F, which would wait for a key that cannot come.
Keys that do not wait can still be fed; they act on a view the size of a
24 by 80 terminal, since the core's Page Down needs a number of rows. No
init file runs, so a script does the same on every machine. `os.exit`
stays, since there is no unsaved editor to lose. And nothing is saved
unless the script calls `save()`.

Neovim has the same door: `nvim -l {script}` "Executes Lua {script}
non-interactively (no UI) with optional [args] after processing any
preceding Nvim |cli-arguments|, then exits. Exits 1 on Lua error.", and
under it `print()` writes to the output, as kilo's does. Beside it is
`--headless`, "Start without UI", for an editor that keeps running for
other programs to talk to (both in runtime/doc/starting.txt).

### `editorRunScript`

The other door, called by `main()` for `-l`: notes that there is no
screen, gives `E` the size of a 24 by 80 terminal, reads the file if one is
named, and runs the script with `scriptRun()`.

### With no screen, in `editorMessage`

Under `-l` the bytes go out as they are, with a newline, to standard error
for an error and standard output for the rest; the cleaning for the message
line is skipped.

### `scriptRun`

A new state, Lua's libraries and `kilo.api`, as for the editor but without
the hook and with `os.exit`, and the script run through the same protected
way in as everything else.

## Run it

Make the program in this lesson's folder, a file, and a script that
upper-cases it (`./learn run` supplies Lua's source, as in 09.07):

<!-- verify: session -->
```
$ ./learn files kilo --at 09.09
Wrote kilo as it stands at 09.09 (The editor without its screen) to build/at/kilo/09.09/
$ printf 'hello\nWorld\n123\n' > build/at/kilo/09.09/notes.txt
$ cat > build/at/kilo/09.09/upper.lua <<'EOF'
-- upper.lua: every line in capitals, and saved.
local n = 0
for row, line in kilo.lines() do
  local up = line:upper()
  if up ~= line then
    kilo.api.set_lines(row, row + 1, {up})
    n = n + 1
  end
end
kilo.api.save()
print(n .. ' lines upper-cased')
EOF
$ ./learn run kilo --at 09.09 -- -l upper.lua notes.txt
Running kilo as it stands at 09.09 (The editor without its screen). Its files are in build/at/kilo/09.09/
2 lines upper-cased
$ cat build/at/kilo/09.09/notes.txt
HELLO
WORLD
123
```

No screen was drawn, and the shell had its terminal the whole time. The


The error is on standard error, where a shell or a build expects it, with
the script's place in front, and the status is 1. Nothing was saved: the
change to row 0 lived only in the editor's rows, which went with the
process. And the API is 24 functions, the table printed a line each, with
no Lua started for it.

## How it works

### What main() skips

```
    if ((argc == 3 || argc == 4) && strcmp(argv[1],"-l") == 0)
        return editorRunScript(argv[2],argc == 4 ? argv[3] : NULL);
```

This comes before `enableRawMode()`, so the terminal is never touched, and
before the loop, so nothing that only the loop does happens. Two things
follow that a script can see. TextChanged and CursorMoved never fire under
`-l`: they are fired from the top of the loop, after a key's work, and
there is no loop. A script that registers a TextChanged function, changes a
row and saves prints what its BufWritePre function printed, and nothing
from TextChanged; the save's own events fire as in the editor. And
`quit()` does nothing a script would notice: its mark is read at the top of
the loop, so a line printed after `kilo.api.quit(true)` is printed, and the
script ends when it ends, with status 0.

`main()` also never calls `scriptStart()`, so the count hook of 09.08 is
not set, and costs nothing: there is no keyboard for it to look at.

### Errors and the exit status

`scriptRun()` returns -1 when the script failed, and `editorRunScript()`
makes that 1, the status `main()` returns. The error itself went where
every error goes, through `scriptReport()` to `editorMessage()`, marked as
an error, so it lands on standard error with the script's place in front,
as `bad.lua:2:` did. A script that wants another status can say so:
`os.exit` is Lua's own here, and `os.exit(3)` ends kilo with status 3.

### One function knows whether there is a screen

```
    if (!editorScreen) {
        FILE *out = error ? stderr : stdout;
        fwrite(s,1,len,out);
        fputc('\n',out);
        return;
    }
```

`editorMessage()` is where the API's `message()`, Lua's `print()` and every
error a script raises end up. In the editor they are cleaned and cut to the
message line; here they are written whole. The **invariant** is that no API
function writes to the terminal itself: each says what it has to say
through `editorMessage()`, and only that function, with `editorScreen`,
knows which door was used; the few that draw a prompt are refused before
they draw when there is no screen. That is what lets the same Lua run both
ways: a
`trim()` function that strips trailing spaces, run under `-l` on one file
and from a key in the editor on another with the same text, leaves the two
files the same, byte for byte.

### What the tests gain

The editor needs a pseudo-terminal, keys typed one at a time, and a screen
read back from escape codes, which is how every earlier test of this track
works. A script under `-l` needs `subprocess.run()`: its output, its
status, and the file. This module's tests run random calls of every API
function that way, 2000 to a script, under AddressSanitizer and
UndefinedBehaviorSanitizer: 5000 calls took 0.6 s with no screen.

## Decide the boundary

![Neovim as its documentation describes it: running nvim starts the builtin UI client, which starts nvim --embed as a child process, the server, and talks to it over msgpack-RPC; other programs connect to a server the same way, as clients of its API. Beside it kilo: the screen and the key loop inside its one process, and kilo -l, which leaves them out and uses the same API](figures/09.09-ui-client.svg)

kilo's screen is inside the editor: the frame, the keys and the rows live
in one process, and `-l` is the editor with that part left out. Only the
API is shared by the two. Neovim went further. Its docs say: "Nvim has a
client-server architecture: by default when you run `nvim`, this starts
the builtin UI client, which starts a `nvim --embed` server (child) process
that the UI client connects to" (runtime/doc/tui.txt), and `--embed`
means "Use stdin/stdout as a msgpack-RPC channel, so applications can
embed and control Nvim via the RPC |API|". Its news for 0.9 says: "The
|TUI| is changed to run in a separate process (previously, a separate
thread was used)." And vim_diff.txt puts it in one line: "all UIs,
including the builtin |TUI| are just plugins that connect to a Nvim server
(via |--server| or |--embed|)." A screen can be another program entirely.
The price is that what a screen shows has to reach it
over that channel, and be kept in step with the editor. kilo has one
screen, in the terminal it was started in. How many kinds of screen will
there be, and where will they run?

## Break it

Make `message()` draw the screen itself, so a message shows at once even
while a long script runs. In `build/at/kilo/09.09/kilo.c`, in
`apiMessage()`, add a line after the one that is there:

<!-- verify: patch file=kilo.c
     editorMessage(args[0].u.string.s,args[0].u.string.len,0);
+    editorRefreshScreen();
-->
<!-- verify: skip reason="the lines as the reader changes them; the patch above makes the change" -->
```
    editorMessage(args[0].u.string.s,args[0].u.string.len,0);
    editorRefreshScreen();
```

Build it, still in the lesson's folder, and run a script that says how many
lines there are, into a file:

<!-- verify: session -->
```
$ make -s
$ printf "kilo.api.message(kilo.api.line_count() .. ' lines')\n" > count.lua
$ ./kilo -l count.lua notes.txt > out.txt
$ head -3 out.txt | cat -v
^[[?25l^[[HHELLO^[[0K^M
WORLD^[[0K^M
123^[[0K^M
$ tail -2 out.txt | cat -v
^[[0K^[[7mnotes.txt - 3 lines                                                          1/3^[[0m^M
^[[0K^[[1;1H^[[?25h3 lines
```

`cat -v` shows each escape byte as `^[` and each carriage return as `^M`.
Without the change, `out.txt` holds 8 bytes, `3 lines` and a newline; now
it holds 291. A whole frame went out first, drawn for a terminal that is
not there: the cursor hidden and sent home, the three rows, 19 rows of `~`
for a 22-row view, the status bar in reverse video, the cursor shown. The
`3 lines` came after it, because `editorMessage()` writes through standard
output's buffer, which is written at exit, and the frame went out at once
with `write()`. A tool that reads kilo's output now reads escape codes,
and the invariant is gone: an API function writes to the terminal. Put the
line back.
