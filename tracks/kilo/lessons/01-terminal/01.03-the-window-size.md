# 01.03 The window size

To fill the screen, kilo has to know how many rows and columns it has.
This lesson asks the kernel, and when the kernel does not know, asks the
terminal itself.

## Where this fits

![Where 01.03 fits](figures/01.03-map.svg)

This lesson builds the window size, the box at the top right of the map,
beside the terminal it learns the size from. Below it is the frame, which
the size feeds: how many rows to draw and how wide. Behind it are the
kernel, which keeps a size for every terminal, and the terminal, which can
report where its cursor is. After this lesson kilo knows the size of its
window when it starts; the frame, in 02.01, is the first thing to use it,
and measures again whenever the window is resized.

## The idea

![The usual way, one ioctl() that reads the size the kernel keeps; and the way round when the kernel says 0: move the cursor as far as it goes and ask the terminal where it ended up.](figures/01.03-ask.svg)

The kernel keeps a size for every terminal. The terminal program sets it
when it opens a window and again on every resize, and any program can read
it: `ioctl()` with the request `TIOCGWINSZ` fills a `struct winsize`,
whose `ws_row` and `ws_col` are the rows and columns. That is the normal
way, one system call.

Sometimes the kernel says 0 columns, because nobody ever set the size: on a
serial line, say, or a pseudo-terminal whose program did not set it. Then
kilo asks the terminal, with two things from 00.02. A cursor movement stops
at the edge of the screen. And `ESC [ 6 n` makes the terminal report where
its cursor is, as `ESC [ row ; col R` on the key stream. So: ask where the
cursor is, move it 999 columns right and 999 rows down, ask again, and put
it back. The second answer is the bottom right corner, and the bottom right
corner is the size. On a 24 by 80 terminal whose cursor stood at the top
left, the first answer is `ESC [ 1 ; 1 R` and the second `ESC [ 24 ; 80 R`.

### `getWindowSize`

Asks the kernel first, about standard output, the terminal kilo draws on.
If that fails or says 0 columns, it goes round by the terminal as above,
with `getCursorPosition()` doing the asking, and moves the cursor back to
where it was before the 999s.

### `getCursorPosition`

Writes `ESC [ 6 n` and reads the answer from standard input, a byte at a
time, up to its `R`, then checks it starts with ESC and `[` and reads the
two numbers with `sscanf()`. It returns -1 if the answer is not of that
shape, or never comes.

### `updateWindowSize` and `initEditor`

`updateWindowSize()` puts the size in `E.screenrows` and `E.screencols`,
two fields this lesson adds to `E`, or prints why it could not and exits.
`initEditor()` sets `E` up for a session: for now that is only measuring
the window, and later lessons add the cursor, the rows and the file name
to it.

### `main`, measuring in raw mode

`main()` now calls `initEditor()` right after `enableRawMode()`, and prints
the size once, since there is no screen to fill yet. The order is not
kilo's original: see How it works.

## How it works

### The answer comes in with the keys

The terminal's answer arrives on standard input, exactly as if you had
typed it, so the terminal driver treats it as typed. In cooked mode it
would echo it on the screen and hold it until a line ended with Enter, and
`getCursorPosition()`, reading a byte at a time, would wait for that Enter.
That is why `main()` switches raw mode on first and measures after:

```
    enableRawMode(STDIN_FILENO);
    ...
    initEditor();
```

In raw mode the answer is not echoed, and `read()` hands it over a byte at
a time as it comes. kilo's original measures first and switches to raw
mode after; Break it puts that order back.

### 999, and the edges

`ESC [ 999 C` asks to move 999 columns right and `ESC [ 999 B` 999 rows
down. That is more than any screen you are likely to have, and a
VT100-style terminal stops the cursor
at its right and bottom margins instead of wrapping or scrolling, so the
cursor ends up in the corner whatever the size. The cursor movement does
not need to know the size to find it.

### When nobody answers

`getCursorPosition()` stops reading at the `R`, or after 31 bytes, or when
`read()` comes back empty after its tenth of a second: a terminal that
never answers costs a tenth of a second, not a hang. Then the answer does
not parse, `getWindowSize()` returns -1, and `updateWindowSize()` says so
and exits. Sending standard output away from the terminal shows it: the
kernel has no window size for `/dev/null`, the question goes there instead
of to the terminal, and no answer ever comes back:

<!-- verify: session cwd=project exit=1
line 2 ~ Unable to query the screen for size \(columns / rows\): .+
-->
```
$ ./kilo x > /dev/null
Unable to query the screen for size (columns / rows): Operation not supported by device
```

The reason after the colon is the last error the C library saw, and it
differs between systems; this one is macOS. kilo exits with status 1, and
`exit(1)` still runs the `atexit()` handler, so the terminal is cooked
again. It was still raw when the message went out, though, so its `\n`
moved down a row without going back to the first column: your prompt may
come back out to the right, a small reminder of what `OPOST` does.

## Decide the boundary

kilo asks the kernel, and the terminal only when the kernel has no answer.
Another program could always ask the terminal: it would work on a line
where nobody ever told the kernel a size, and it would get the size of the
window as the terminal sees it. It would pay with a round trip to the
terminal at every start, a cursor that jumps to the corner and back, and
the need to be in raw mode before it can measure anything. Who should be
the authority on the size of a window: the kernel, which is told, or the
terminal, which is the window?

## Break it

Measure before raw mode, the way kilo's original does. In
`build/at/kilo/01.03/kilo.c`, in `main()`, move `initEditor();` from after
`enableRawMode(STDIN_FILENO);` to before it:

<!-- verify: patch file=kilo.c
+    initEditor();
     enableRawMode(STDIN_FILENO);
     /* The window is measured in raw mode. When the kernel does not know its
      * size, the terminal is asked, and its answer must reach us a byte at a
      * time. The original kilo measures first and enters raw mode after:
      * the answer then waits for an Enter nobody types, and kilo hangs. */
-    initEditor();
-->

On a normal terminal nothing changes: the kernel knows the size, and the
terminal is never asked. Give it a terminal the kernel knows nothing about,
`stty rows 0 cols 0`, and run it:

<!-- verify: skip reason="needs a terminal that answers ESC [ 6 n, and the replay's terminal does not. Checked under bash and zsh on a 0 x 0 pseudo-terminal whose Screen answers as a terminal does" -->
```
$ stty rows 0 cols 0
$ ./learn run kilo --at 01.03
Running kilo as it stands at 01.03 (The window size). Its files are in build/at/kilo/01.03/
^[[5;1R
```

kilo stops there. The terminal answered, the driver echoed the answer
(`^[[5;1R` here: your row number is wherever your cursor was), and
`read()` is waiting for the line to end. Press Enter, and kilo parses the
first answer and asks the second question, whose answer is echoed in the
bottom right corner and waits in the same way. Press Enter again and the
second read starts with the newline left over from the first line, so it
does not parse: kilo prints `Unable to query the screen for size` and exits
with status 1. (Ctrl-C ends the wait at once too: raw mode is not on yet,
so it is still a signal, and there is nothing to put back.) Put
`initEditor();` back after `enableRawMode()`, and give
the kernel its size back with `stty rows 24 cols 80`, using your numbers.
