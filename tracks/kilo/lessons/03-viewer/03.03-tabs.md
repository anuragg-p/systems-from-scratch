# 03.03 Tabs

A tab is one byte in the file and up to eight columns on the screen. Each row
now gets a second copy of its text, as the screen should show it, with every
tab turned into spaces, and the cursor is placed by counting the columns the
tabs before it take up.

## Where this fits

![Where 03.03 fits](figures/03.03-map.svg)

This lesson builds render, on the right-hand side of the map between the rows
below it and the frame above it: a second copy of each row, made the way the
screen should show it. The rows stay exactly as the file has them; the frame
now draws the rendered copy, and places the cursor by it. After this lesson a
file with tabs looks the way it does in any other program, and the cursor
sits on the character it is on.

## The idea

![The project's Makefile after Page Down: at 03.02 the tab goes to the terminal and leaves old text, wraps and scrolls; at 03.03 the row is drawn from its spaces.](figures/03.03-rawtabs.svg)

Until now each row went to the terminal as the file has it, tabs and all, and
the terminal did what it does with a tab byte: it moved its cursor on to the
next tab stop, every 8 columns. Three things go wrong with that, and the
project's own Makefile, whose commands start with a tab, shows all of them.
The tab moves the cursor without writing over the columns it passes, so
whatever the screen held there stays: on the left of the figure, `#   make`
from the frame before. The row is cut at `E.screencols` bytes, but on the
screen it is 7 columns wider than its bytes, so it runs past the edge, wraps
onto the next row, and the frame, a line too long, scrolls the screen up by
one. And the cursor is placed by counting bytes: on the `$` after the tab,
byte 1 of its row, it is drawn in column 2, while the `$` is in column 9.

The way out is to never send a tab. Each row gets a **render**: its bytes
with every tab replaced by spaces, as many as it takes to reach the next
column that is a multiple of 8. In `ab`, tab, `c`, the tab is at column 2, so
it becomes 6 spaces and the `c` lands in column 8; in tab, `one`, the tab is
at column 0 and becomes 8 spaces. The frame draws render, which has no tabs,
so every column is written and the cut counts real columns. The cursor is
placed by walking its row's bytes up to it and counting each tab as the
columns it fills.

![Two rows, their bytes and their render: each tab becomes the spaces up to the next multiple of 8, and the cursor is placed by the same count.](figures/03.03-render.svg)

### `editorUpdateRow`

This makes a row's render from its chars. It counts the tabs first, to
allocate enough for the worst case, 8 columns each, then copies the bytes
across: a tab becomes one space and then more spaces until the column is a
multiple of 8. `rsize` is render's length, and render ends with a `'\0'` like
chars. It runs whenever a row's chars is made: at this lesson from
`editorInsertRow`, so every row of the file is rendered as it is read. A
check from the original stops the editor if a line has so many tabs that the
size would not fit in 32 bits.

### The cursor, in `editorRefreshScreen`

The frame's last step was to put the cursor at column `E.cx+1`. Now it walks
the cursor's row from `E.coloff` up to the cursor, one column for each byte
and, for a tab, the columns up to the next tab stop, and puts the cursor
where the count ends. The count starts at 1, because the columns in
`ESC [ row ; col H` count from 1. The walk reads chars, where the cursor's
place is a byte, and gets the same answer render would.

## How it works

### Two copies, and which one is the truth

The row now holds its text twice. chars is the file, byte for byte, and is
what the editor changes and, from lesson 04.04, writes back. render is
derived from chars and only ever drawn. The **invariant** is that render is
always chars with its tabs expanded, which holds because every piece of code
that makes or changes a row's chars calls `editorUpdateRow` next: here
`editorInsertRow`, and in module 04 each edit. The cursor, `E.cx`, counts
bytes of chars, so it means the same thing whatever the tabs do on the
screen.

### Tab stops at multiples of 8

The padding stops when the next column is a multiple of 8:

```
            while(idx % 8 != 0) row->render[idx++] = ' ';
```

and the cursor walk counts to the same stops:

```
            if (j < row->size && row->chars[j] == TAB) cx += 7-((cx-1)%8);
```

antirez's kilo pads `while((idx+1) % 8 != 0)` and counts `7-((cx)%8)`, which
puts its tab stops at columns 7, 15, 23 and so on: one column short of every
terminal's, and of `expand`'s. In the original, `ab`, tab, `c` shows as
`ab     c`, five spaces; here it is `ab      c`, six. Each of the two lines
must agree with the other; Break it changes one of them.

### A limit kept from the original: the view's offset counts bytes

`E.coloff` counts bytes of chars, because `editorMoveCursor` moves it a byte
at a time, but the frame applies it to render, from `r->render+E.coloff`. On
a row with a tab before the left edge of the view the two disagree. A row of
100 x's, a tab and `end`, on 44 columns, shows it: after 101 Rights the
cursor is on the `e` of `end`, `E.coloff` is 58, and the frame draws render
from column 58, which is 42 x's and two of the tab's four spaces. `end` is
at render column 104 and never comes into view, and the cursor, counted past
the tab to column 49, is drawn at the right edge, as far as the terminal
lets it go. This track keeps the original's behaviour here.

## Decide the boundary

kilo stores render beside chars in every row: twice the memory for text, and
a pass over the row on every change, in exchange for a frame that copies
bytes straight out. Another editor could keep chars only and expand tabs
while it draws, paying on every frame instead of on every change, and with
no second copy to keep in step. The original had one more reason to store
render: its syntax highlighting, left out of the core (module 06 brings it
back), keeps a colour for every byte of render. How often does your editor draw, compared with how
often it changes a row?

## Break it

Put back the original's tab stops in one of the two places. In
`build/at/kilo/03.03/kilo.c`, in `editorUpdateRow`, change the padding loop
to the original's:

The tab now takes 7 columns: the `$` is drawn in column 8. The cursor walk
was not changed: it still counts the tab up to the next multiple of 8, and
draws the cursor in column 9, on the `(`, one place right of the `$` it is
on. Every character after a tab on every row is now
drawn one column left of where the cursor says it is. The two copies of the
rule have to agree; the original has the same rule in both places, one
column off in each. Put the line back.

  a step-by-step rebuild of kilo by another author. "Rendering tabs" adds

  stops 8 apart by default.
