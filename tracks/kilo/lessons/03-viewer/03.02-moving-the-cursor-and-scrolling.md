# 03.02 Moving the cursor, and scrolling

The arrow keys and Page Up and Page Down now move the cursor through the
file, and the view scrolls whenever the cursor would leave the screen. Two
numbers, a row offset and a column offset, say which part of the file the
screen shows.

## Where this fits

![Where 03.02 fits](figures/03.02-map.svg)

This lesson builds the cursor, at the bottom left of the map: the first of the
actions the key handler, just above it, hands keys to. An arrow or a page key
comes down the left side as one key, the handler passes it here, and the
cursor moves; when it would leave the screen, the view over the rows, at the
bottom right, moves instead. The frame then draws the rows from their new
place. After this lesson kilo is a viewer you can move around a file of any
length and any width.

## The idea

![nato.txt on a 6 x 20 terminal: the window of 5 rows by 20 columns over the file, the two offsets that place it, and the cursor, before and after one more Down.](figures/03.02-window.svg)

At 03.01 the screen shows the top left corner of the file and nothing else.
To see the rest, the editor needs a place in the file and a way to slide the
screen over it. kilo keeps both in four numbers. `E.cx` and `E.cy` are where
the cursor is on the screen, column and row, counting from 0. `E.rowoff` is
the file row shown on the top line, and `E.coloff` the file column shown in
the leftmost column. The cursor's place in the file is the sum of the two:
row `E.rowoff+E.cy`, column `E.coloff+E.cx`. The frame has drawn file row
`E.rowoff+y` on screen row `y`, from column `E.coloff`, since 03.01, so to
move the view all the editor has to do is change these numbers.

The figure is `nato.txt`, ten lines, on a terminal 6 rows by 20 columns: 5
rows for text, 20 columns. Press Down five times. The first four move the
cursor down the screen, `E.cy` from 0 to 4. The fifth would take it off the
bottom, so the view scrolls instead: `E.rowoff` becomes 1 and the cursor
stays on the bottom row, now on the long `foxtrot` line, file row 5. Press
Right 24 times along that line. After 19 the cursor is in the last column,
`E.cx` 19, and the next five scroll the view: `E.coloff` 5. The cursor is at
file row 1 + 4 = 5, column 5 + 19 = 24. One more Down goes to `golf`, which
is 4 characters long. The cursor cannot stay at column 24 of a 4-character
row, so it is pulled back to the end of `golf`, column 4.

### `editorMoveCursor`

One step for one arrow key. Left goes one column left; at the left edge of a
scrolled view it scrolls left instead, and at the start of a row it goes to
the end of the row above. Right goes one column right while it is inside the
row, scrolling at the right edge, and from the end of a row to the start of
the next. Up and Down go one row, scrolling at the top and bottom of the
screen. Down stops one row past the last row of the file. After the step,
whatever it was, a cursor left past the end of its new row is pulled back to
that end.

### Page Up and Page Down, in `editorProcessKeypress`

A page key first puts the cursor on the top row of the screen (Page Up) or
the bottom row (Page Down), then makes `E.screenrows` single moves up or down
with `editorMoveCursor`, which scrolls the view by a screenful. The four
arrows get cases here too, which call `editorMoveCursor` directly.

## How it works

### Two invariants, kept after every key

`editorMoveCursor` keeps two things true. The cursor is on the screen:
`E.cx` stays between 0 and `E.screencols-1` and `E.cy` between 0 and
`E.screenrows-1`, because every branch that would step past an edge changes
an offset instead. And the cursor is never further right than just past the
last character of its row. That one is kept by the pull-back at the end,
applied whatever the key was:

```
    if (filecol > rowlen) {
        E.cx -= filecol-rowlen;
        if (E.cx < 0) {
            E.coloff += E.cx;
            E.cx = 0;
        }
    }
```

When the end of the row is left of the screen, `E.cx` goes negative, and the
view scrolls left by just that much: the cursor ends at the left edge, on the
end of a row whose text can be wholly off the screen, as `golf` is in the
figure and ` *` was above. The second invariant is what the editing lessons
rely on: the cursor always marks a place inside the row, or just after it,
where a character can go.

### Left at the top of a scrolled screen

At the start of a row, Left goes to the end of the row above. antirez's kilo
always does that with `E.cy--`. On the top row of a scrolled view that makes
`E.cy` -1, above the screen, and the view does not scroll. Tried on
`nato.txt` with `delta` on the top row: Left at its start sends the cursor to
`ESC [ 0 ; 8 H`, a row 0 that does not exist, and two Ups later the frame
sends `ESC [ -2 ; 6 H`, which is not a valid sequence at all. This track
scrolls up instead, as Up does:

```
                    if (E.cy == 0)
                        E.rowoff--;
                    else
                        E.cy--;
```

### Page Down goes to the bottom row first

Without that first jump, Page Down from the top row would spend its first
`E.screenrows-1` moves taking the cursor down the screen, and only the last
one would scroll: the view would move by a single line. Starting from the
bottom row, every one of the moves scrolls. The jump does not look at the
file, though, a behaviour kept from the original: on a file shorter than the
screen, Page Down puts the cursor on the bottom row, among the tildes, far
past the row where Down stops. On a 2-line file and a 10-row terminal it
lands on row 9; Down stops at row 3.

## Decide the boundary

kilo keeps the cursor as a place on the screen, and scrolls inside each
branch of `editorMoveCursor` that reaches an edge. Another design keeps the
cursor as a place in the file and leaves the offsets alone while it moves;
then, just before drawing, one function compares the cursor with the window
and moves the window to contain it. That puts scrolling in one place instead
of in every branch, and any code that moves the cursor, a search that jumps to a match
for one, gets scrolling for free. kilo's way needs no step before the frame,
but every piece of code that moves the cursor must scroll for itself. Where
would you rather have the scrolling: next to every move, or once before
every frame?
