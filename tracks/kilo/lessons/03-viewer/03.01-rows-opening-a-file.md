# 03.01 Rows: opening a file

The editor reads the file named on its command line into memory as an array
of rows, one per line, and draws as many of them as fit on the screen. This is
the step from an empty screen to a viewer.

## Where this fits

![Where 03.01 fits](figures/03.01-map.svg)

This lesson builds the rows, at the bottom right of the map: the editor's own
copy of the file, filled from the file once, when the editor starts. The way
back to the screen begins here and goes up the right-hand side: the rows are
drawn into the frame, which goes up to the terminal. (Render, between them,
comes with 03.03; until then the rows go to the frame as they are.) Along the
bottom to their left are the actions that will read and change them: the
cursor moves over them next, and edit, save and find come in modules 04 and
05. After this lesson kilo opens a file and shows its first screenful.

## The idea

![notes.txt: its 41 bytes split at each newline into four rows, each a copy of one line, and the screen drawn from them.](figures/03.01-rows.svg)

A text file is a run of bytes with a newline byte, `\n`, at the end of each
line. A screen is rows. The editor goes from one to the other on every frame,
and it makes that cheap by splitting the file once, when it opens it, into
one entry per line that holds the line's bytes without the newline.

Take `notes.txt`, 41 bytes: `kilo`, a line of 30 bytes, an empty line and
`end`, each followed by a newline. kilo reads it into four rows. `E.row[0]`
holds `kilo`, size 4; `E.row[1]` the 30-byte line; `E.row[2]` nothing, size 0;
`E.row[3]` `end`. `E.numrows` is 4. Each row's bytes are followed by a `'\0'`
that its size does not count, so a row is also a C string. Drawing is then a
loop down the screen: screen row 1 shows file row 0, row 2 shows file row 1,
and so on while there are rows; after the last, a tilde.

### `editorInsertRow`

A row is an **erow**: its size and a pointer to its bytes, `chars`. The rows
are one array, `E.row`, of `E.numrows` entries. `editorInsertRow` puts a copy
of a line in at a given position: it grows the array by one entry with
`realloc`, moves the entries from that position on down by one with
`memmove`, and copies the line's bytes, with the `'\0'` after them, into a
new allocation. Opening a file only ever adds at the end, at `E.numrows`;
inserting in the middle is there for Enter, which splits a line in lesson
04.02.

### `editorOpen`

This opens the file and reads it a line at a time with `getline`, which
allocates a buffer, grows it to fit each line, and returns the line's length
including its newline. Each line has its ending stripped and is added as a
row. The file's name is kept in `E.filename`. A file that does not exist is
not an error: the editor starts with no rows, shows the welcome, and creates
nothing on disk. Any other failure, a file it may not read for one, prints the
reason and exits.

### Drawing a row, in `editorRefreshScreen`

Screen row `y` now shows file row `E.rowoff+y`. Past the last row it draws
the tilde, and the welcome only when the file has no rows at all. Otherwise
it appends the row's bytes from column `E.coloff`, at most `E.screencols` of
them, then the erase and `\r\n` every line ends with. Both offsets stay 0 for
now; lesson 03.02 moves them.

## How it works

### Line endings

`editorOpen` strips every `\n` and `\r` at the end of a line, not just one
byte:

```
        while (linelen && (line[linelen-1] == '\n' || line[linelen-1] == '\r'))
            line[--linelen] = '\0';
```

Files written on Windows end their lines with `\r\n`, a carriage return and
then the newline. antirez's kilo has an `if` here, which strips the `\n` and
leaves the `\r` in the row; Break it shows what that `\r` does on the screen.
A last line with no newline needs nothing stripped, and is read like the
others: a file of `abc`, a newline and `last line, no newline` opens as two
rows.

### One file row, one screen row

The row is cut at the screen's width before it is appended:

```
            if (len > E.screencols) len = E.screencols;
```

A terminal that is given a line longer than its width wraps it onto the next
row. Then one file row would take two screen rows, every row after it would
land one lower than the frame counts, and the frame's last `\r\n` would fall
on the bottom row and scroll the screen up. Without this line, `kilo.c` on the
same 10 by 44 terminal opens with its fifth line, ` *`, at the top: the
wrapped rows pushed the first four off the screen. The **invariant** is that
each row of the frame is at most one screen row wide, so screen row `y` is
always file row `E.rowoff+y`.

### A row is a copy, and a C string

`editorOpen` hands `getline` the same buffer for every line, so a row cannot
point into it; `editorInsertRow` copies the bytes into an allocation of its own:

```
    E.row[at].chars = malloc(len+1);
    memcpy(E.row[at].chars,s,len+1);
```

The `+1` copies the `'\0'` after the line too: `getline` ends what it reads
with one, and the stripping loop writes one over each byte it takes off. So
`chars[size]` is always `'\0'`, and a row can be handed to C's string
functions without its size; lesson 05.01's search does exactly that.

## Decide the boundary

kilo keeps the file as an array of lines, each in its own allocation. Finding
line n is one index, and drawing a screen is a walk down the array. The cost
is in changing the lines: inserting or deleting a line moves every entry
after it, and the whole file sits in memory from the moment it is opened.
An editor could instead keep the text in one block with an empty gap at the
cursor, so that typing only fills the gap; it then has to find where each
line starts, by searching for newlines or by keeping an index of them, and
drawing needs lines on every frame. Which does your
editor do more often: find lines, or change long files in the middle?

## Break it

Strip one byte, as the original does. In `build/at/kilo/03.01/kilo.c`, in
`editorOpen`, change the `while` of the stripping loop to an `if`:

<!-- verify: patch file=kilo.c
-        while (linelen && (line[linelen-1] == '\n' || line[linelen-1] == '\r'))
+        if (linelen && (line[linelen-1] == '\n' || line[linelen-1] == '\r'))
-->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
        if (linelen && (line[linelen-1] == '\n' || line[linelen-1] == '\r'))
```

Make a file with Windows line endings in the project's directory, and open
it:

<!-- verify: session host -->
```
$ printf 'first\r\nsecond\r\n' > build/at/kilo/03.01/crlf.txt
```

```
./learn run kilo --at 03.01 -- crlf.txt
```

<!-- verify: skip reason="a picture of the editor's full screen, from a 10 x 44 pseudo-terminal; verify cannot replay a full-screen program" -->
```
+--------------------------------------------+
|                                            |
|                                            |
|~                                           |
|~                                           |
|~                                           |
|~                                           |
|~                                           |
|~                                           |
|~                                           |
|                                            |
+--------------------------------------------+
```

Two rows, both empty on the screen. Each row now ends in its `\r`, and the
frame sends it as it is: `first`, then the `\r`, which takes the terminal's
cursor back to column 1, then `ESC [ 0 K`, which erases from there to the end
of the line. The text is in memory, `first` plus a `\r`, 6 bytes; the screen
just erases it as soon as it is drawn. With the `while` put back, the same
file shows `first` and `second`.
