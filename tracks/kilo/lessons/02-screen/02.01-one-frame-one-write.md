# 02.01 One frame, one write

The editor now draws its own screen. After every key it builds the whole
screen in memory, top to bottom, as one string of text and escape sequences, and
hands it to the terminal in a single `write()`.

## Where this fits

![Where 02.01 fits](figures/02.01-map.svg)

This lesson builds the frame, the wide box in the middle of the map: the way
back to the terminal for everything the editor shows. Keys come down the left
side to the key handler; once the handler has dealt with a key, the frame is
drawn again and goes up to the terminal, above it, in one write. The window
size, at the top right, tells the frame how big to be. The pieces that will
fill it come in module 03: the rows of a file and their rendering, below it
on the right, and the status bar beside it. After this lesson the editor shows
a real screen instead of a list of key codes: a column of tildes with a
welcome line, drawn again whenever the window changes size.

## The idea

![One frame on a 10 x 44 terminal: each line of bytes on the left draws the row of the screen beside it, and all 116 bytes go out in one write().](figures/02.01-frame.svg)

Until now the editor printed a line per key and let the terminal scroll. A
screen editor cannot work like that. It must put text on any row, overwrite
what is there, and leave nothing of the last screen behind. The terminal can
do all of that when it is asked with escape sequences (00.02): short strings of
bytes that start with ESC, byte 27, which the terminal acts on instead of
printing. Four kinds are enough for a whole screen:

| bytes | what the terminal does |
|---|---|
| `ESC [ H` | moves the cursor to row 1, column 1 |
| `ESC [ 0 K` | erases from the cursor to the end of its line |
| `ESC [ ? 25 l`, `ESC [ ? 25 h` | hides the cursor, shows it again |
| `ESC [ 3 ; 7 H` | moves the cursor to row 3, column 7 (both count from 1) |

kilo draws a **frame**, the whole screen, after every key. The figure is the
first one on a terminal 10 rows by 44 columns, 116 bytes: hide the cursor and
go to the top left; for each of the 9 rows the editor uses, a tilde (on row
4, the welcome), an erase to the end of the line and a carriage return and
newline, `\r\n`; nothing on the bottom row; the cursor put back and shown.

All of it is collected in memory first and goes to the terminal with one
`write()`. A terminal draws what it receives as soon as it receives it. If the
editor wrote each piece as it made it, the terminal could show the screen
between any two pieces: half the old frame and half the new, with the cursor
seen racing across it.

### `abAppend`

The frame is built in an **append buffer**, `struct abuf`: a pointer to the
bytes so far and their length, empty to start with (`ABUF_INIT`). `abAppend`
grows it with `realloc` and copies one piece onto the end. If `realloc`
fails, the piece is dropped and the frame goes out short: half way through a
frame there is nothing better to do.

### `abFree`

Once the frame is written, its bytes are freed; the next frame starts from an
empty buffer again.

### `editorRefreshScreen`

This draws one frame, and main calls it before reading every key. It starts
the buffer with the cursor hidden and moved to the top left, appends a line
for each of `E.screenrows` rows, moves the cursor to `E.cy`, `E.cx` (still 0
and 0: nothing moves it yet), shows the cursor, and writes the buffer out.
The welcome goes on row `E.screenrows/3`; every other row is a tilde, the
mark vi uses for a line past the end of the file. The code for the welcome
and the tildes is indented one level deeper than the loop needs: lesson 03.01
wraps it in an `if`.

### `handleSigWinCh`

When the window changes size, the kernel sends the editor the signal
SIGWINCH. This handler measures the window again, pulls the cursor back inside
it if the window shrank, and draws a frame at the new size at once, without
waiting for a key; it draws from inside the signal handler itself, a shortcut
the original takes too. `initEditor` installs it with `signal()`. Ctrl-L gets
a case of its own that does nothing: the screen is drawn again after every
key, so any key, Ctrl-L included, redraws it.

## How it works

### Every line is rewritten

The **invariant** a frame keeps is that after it, every row the editor uses
shows exactly what the frame put there, and nothing of the frame before. Two
things keep it. The frame starts at the top left with `ESC [ H`, so its first
line lands on row 1 whatever the cursor was doing. And every line is erased
to its end as it is written:

```
                abAppend(&ab,"~\x1b[0K\r\n",7);
```

kilo could instead clear the whole screen first, with `ESC [ 2 J`, and the
screen would end up the same. But then every cell is blanked and drawn again
on every key, and a terminal that draws in the middle of the frame shows an
empty screen for that moment. Erasing each line just after its text means a
cell only ever goes from its old content to its new one.

### The bottom row stays empty

One row is held back when the window is measured, in `updateWindowSize`:

```
    E.screenrows -= 1;
```

Every line of the frame ends in `\r\n`, and a newline on a terminal's bottom
row scrolls the whole screen up by a line. If the frame used all 10 rows, its
last `\r\n` would push row 1 off the top, and the frame would be drawn one row
higher than the editor thinks it is. With 9 rows, the ninth `\r\n` takes the
cursor to row 10 and nothing scrolls. Lesson 03.04 puts the message line on
that row, written with no newline after it.

### One write, counted

![Four screens of 232 bytes on 24 x 80: with the buffer, one write() each; with every piece written at once, 51 each.](figures/02.01-writes.svg)

Counted on a 24 by 80 terminal, starting kilo and pressing Ctrl-L three times
draws four screens: 928 bytes in 4 calls to `write()`. Changed so that
`abAppend` writes each piece out at once, the same 928 bytes take 204 calls,
51 a frame, and 22 of each 51 are the single spaces that pad the welcome. The
terminal may draw after any one of them. Hiding the cursor while the frame is
drawn is the same idea on a small scale: it is seen only where the frame
leaves it.

### The welcome, on a narrow window

The welcome is padded with `(E.screencols-welcomelen)/2` spaces, where
`welcomelen` counts the string's six bytes of `ESC [ 0 K` and `\r\n`, which
take no room on the screen. So the text sits 3 columns left of the middle: on
44 columns it starts in column 6, with 11 columns free after it. On a window
narrower than 33 columns that comes out negative, and the loop
`while(padding--)`, which stops only at zero, would count down away from it,
appending a space at a time and never drawing. antirez's kilo does exactly
that: on a 30-column terminal it writes nothing, keeps a CPU busy and grows by
more than 50 MB a second. Here a negative padding is made 0 first:

```
                if (padding < 0) padding = 0;
```

The text itself is cut to the window's width: `%.*s` with `E.screencols`
takes at most that many characters of it. Uncut, on a window narrower than
its 28 columns, it would wrap onto the row below, and the frame, one row too
tall, would scroll up the screen. From 03.01 the welcome is drawn only when
the file is empty.

## Decide the boundary

kilo sends every row on every key, whether it changed or not. With a file on
the screen (module 03), a frame on 24 by 80 is between about 800 and 1,450
bytes; one key on a 9600-baud serial line, about 960 bytes a second, would
take more than a second to show. curses, a library many full-screen terminal
programs are built on, keeps a copy of what the screen shows, compares the new
screen with it, and sends what it takes to turn one into the other. The price
is that copy, the comparison on every refresh, and a library between the
editor and the terminal. kilo pays in bytes instead, and on a local terminal
they cost almost nothing. Is the link between your editor and its screen one
where bytes are free, or one where each of them is a wait?

## Break it

Take the erase out of the tilde lines. In `build/at/kilo/02.01/kilo.c`, in
`editorRefreshScreen`, change the line

<!-- verify: patch file=kilo.c
-                abAppend(&ab,"~\x1b[0K\r\n",7);
+                abAppend(&ab,"~\r\n",3);
-->
```
                abAppend(&ab,"~\x1b[0K\r\n",7);
```

to

<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
                abAppend(&ab,"~\r\n",3);
```

So that the terminal has something on it for the frame to land on, print a
file first, with `cat build/at/kilo/02.01/Makefile`, then start the editor
again:

```
./learn run kilo --at 02.01
```

On the same 10 by 44 terminal:

<!-- verify: skip reason="a picture of the editor's full screen over the shell's earlier output, from a 10 x 44 pseudo-terminal; verify cannot replay a full-screen program" -->
```
+--------------------------------------------+
|~                                           |
|~lean:                                      |
|~       rm -f kilo                          |
|~    Kilo editor -- version 0.0.1           |
|~PHONY: all clean                           |
|~ ./learn run kilo --at 02.01               |
|~unning kilo as it stands at 02.01 (One fram|
|~, one write). Its files are in build/at/kil|
|~/02.01/                                    |
|                                            |
+--------------------------------------------+
```

Each tilde now stands at the start of whatever was on its row before: the end
of the Makefile, the command, and the line `./learn run` printed. Each tilde
covered one character and the rest stayed. Only the welcome's row is clean,
because the welcome string carries its own `ESC [ 0 K`. Ctrl-L changes nothing:
the frame never asks for an erase, so old text stays until some frame writes
over it. This is what the invariant protects; without the erase, a screen
shows the history of everything drawn on it. Put the line back.
