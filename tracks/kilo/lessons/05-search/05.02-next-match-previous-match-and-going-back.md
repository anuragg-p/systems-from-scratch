# 05.02 Next match, previous match, and going back

In the search prompt the arrow keys now step through the matches: Down or
Right to the next row that holds the query, Up or Left to the one before,
around the ends of the file. And Escape gives the search up, putting the
cursor and the view back exactly where they were.

## Where this fits

![Where 05.02 fits](figures/05.02-map.svg)

This lesson finishes the find piece, along the bottom of the map, and with
it the editor this track builds. The key handler above it still calls it
for Ctrl-F, and it still runs its own loop of drawing and reading keys;
now more of those keys mean something. It reads the rows to its right and
changes none of them, and its screen goes up the right-hand side as
always. After this lesson you can visit every match in a file, and back
out of a search without losing your place.

## The idea

![The rows of f.txt that hold line 2: typing finds row 2; Down goes on to row 20 and then 21; Up at row 2 goes back around the end of the file to row 29](figures/05.02-next-prev.svg)

05.01 left two things undone. A search always lands on the first row that
holds the query, so in a file of `line 1` to `line 30`, typing `line 2`
finds row 2, and rows 20 to 29, which hold `line 2` too, can only be
reached by typing more. And Escape does what Enter does, so a search you
give up on still leaves you at its match, wherever that was.

**Next and previous.** The search loop of 05.01 already starts from the
row after `last_match` and steps by `find_next`, wrapping at the ends. A
typed character sets `last_match` to -1, so the search starts above row 0
and steps down. An arrow key changes only the direction: Down or Right
sets `find_next` to 1, Up or Left to -1, and `last_match` stays the row of
the match on the screen. So the same loop starts next to that match and
walks away from it, one row at a time, until a row holds the query. Past
the last row it goes on at the first, and above the first at the last.
With `line 2`: Down from row 2 is row 20; Up from row 2 tries row 1, then
wraps to 30, and stops at 29.

**Going back.** Before the loop starts, save the four numbers that place
the cursor: `E.cx` and `E.cy` on the screen, `E.coloff` and `E.rowoff` for
the view (03.02). On Escape, put all four back. Enter leaves them where
the search put them.

![Where the cursor and the view are before the search, at a match, after Escape with all four numbers put back, and after Escape with only cx and cy put back](figures/05.02-going-back.svg)

### `editorFind`

The region of this lesson is the Escape case: it copies the four saved
numbers back before the search ends. The rest of the lesson's code is
also in `editorFind()`: the four `saved_` variables, set from `E` before
the loop; two `else if` branches that turn the arrows into a direction;
and the prompt, which now says `(Use ESC/Arrows/Enter)`. The search loop
itself is unchanged from 05.01.

## How it works

### An arrow changes the direction, not the query

```
} else if (c == ARROW_RIGHT || c == ARROW_DOWN) {
    find_next = 1;
} else if (c == ARROW_LEFT || c == ARROW_UP) {
    find_next = -1;
```

These branches leave `query` and `last_match` alone. That is the whole
trick: `last_match` is both "the row of the match on the screen" and
"where the next search starts", and only a change to the query resets it
to -1, which means "start from the top, going down". The line of 05.01
that keeps that rule is `if (last_match == -1) find_next = 1;`: even Up,
pressed when there is no match yet, searches from the top down.

The loop tries at most `E.numrows` rows; started from a match, the last
row it tries is the match's own. So with one match in the file, Down comes
back to it, and with none, nothing moves. It steps by rows, not by matches: a row that
holds the query twice is one stop, at its first match, and Down goes on to
the next row.

### A place on the screen is four numbers

The cursor's place in the file is row `E.rowoff+E.cy`, column
`E.coloff+E.cx`. A search sets all four: the match's row goes to the top
(`E.rowoff`, and `E.cy` is 0), and its column goes into `E.cx`, with
`E.coloff` scrolled if need be. So going back has to put back all four;
any two of them alone describe a different place, as Break it shows.
Because they are copied once, before the loop, the arrows can wander
through the matches for as long as you like, and Escape still goes back to
where the search began, not to the previous match.

### Keys above 255

The branches run in order, and every key that is not one of the delete
keys, Enter, Escape or an arrow reaches `isprint(c)`. For Home, End, Page Up and Page
Down, `c` is a code above 255, from `editorReadKey()`. C defines
`isprint()` only for the values of an `unsigned char` and for `EOF`; on
macOS it returns 0 for all of 1000 to 1008, so those keys are ignored.
The original kilo has the same test, and this track keeps it.

## Decide the boundary

In kilo a search is a mode: Ctrl-F enters it, Enter or Escape leaves it,
and the query is forgotten when it ends. The next Ctrl-F starts from an
empty prompt and from the top of the file.

Another editor could keep the last query and give "find again" a key of
its own, as vi does with `n`: no prompt, just the next match after the
cursor. It pays with state that lives between searches, a key that does
nothing until a search has been made, and a second way into the same
loop. Is a search something you visit, or a command you repeat?

`editorFind()`, delete the line that restores the view:
