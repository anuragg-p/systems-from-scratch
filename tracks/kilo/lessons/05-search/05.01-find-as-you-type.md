# 05.01 Find as you type

Ctrl-F turns the message line into a search prompt. Each key typed there
searches the file again from its first row, and the first row that holds
the query jumps to the top of the screen, with the cursor on the match.

## Where this fits

![Where 05.01 fits](figures/05.01-map.svg)

This lesson builds the find piece, along the bottom of the map between
cursor and save. The key handler above it has had a case for Ctrl-F since
04.01 that did nothing; now it calls this code. Find reads the rows, as
save does, and changes none of them: it only moves the cursor and the
view, and the screen goes up the right-hand side as always. Unlike the
other three actions it does not return after one key, but runs a small
loop of its own, drawing the screen and reading keys, until Enter or
Escape. After this lesson you can get to any text in the file by typing
it.

## The idea

![Each query is searched for from row 1 down: r is first found in row 4, re and ret in row 5, and retx in no row, so nothing moves](figures/05.01-as-you-type.svg)

Until now, getting to a word meant pressing Down and Right until the
cursor was there. In a file of a thousand lines that is a lot of presses,
and you have to know where the word is.

kilo searches **incrementally**: there is no "search" key to press after
the query. Every key that changes the query starts the search again, from
the top of the file, and the screen follows at once. With `hello.c`, a
six-line C program:

- `r` is first in row 4, `printf`, at byte 2 of the row (byte 0 is the
  tab). Row 4 goes to the top of the screen and the cursor onto the `r`.
- `re` is not in rows 1 to 4, so the search goes on to row 5, `return`.
- `ret` is there too, in the same place.
- `retx` is in no row. Nothing moves: the screen stays where `ret` put it.

Backspace takes the last character off the query, and that is a change
too, so it searches again. Enter or Escape ends the search, and the cursor
stays on the match, ready to edit there. Case matters: the comparison is
of bytes, so `Ret` does not find `return`.

### `editorFind`

The whole search, called from the Ctrl-F case of the key handler. It
keeps the query in a buffer of 256 characters and a `'\0'`, and then
loops: put `Search: <query> (Use ESC/Enter)` on the message line, draw
the screen, read one key with `editorReadKey()`, change the query, and
search. Only Enter or Escape gets out of the loop; until then the editor's
main loop is waiting for `editorProcessKeypress()` to return. Any key
other than a printable character, Backspace, Delete, Ctrl-H, Enter or
Escape changes nothing.

The search itself starts at the row after `last_match` and steps by
`find_next`, wrapping around the ends of the file, and tries each row once
with `strstr()`. In this lesson every search starts over: any change to
the query sets `last_match` to -1, "no match yet", so the first row tried
is row 0, and `find_next` is always 1. The wrapping and the other
direction are for 05.02's arrow keys.

The rest of the lesson is outside the function: `#include <ctype.h>` for
`isprint()`, the Ctrl-F case that calls `editorFind()`, and the help line,
which gains `Ctrl-F = find`.

## How it works

### Search `chars`, put the cursor in `chars`

```
match = strstr(E.row[current].chars,query);
if (match) {
    match_offset = match-E.row[current].chars;
    break;
}
```

A row has two copies of its text (03.03): `chars`, as the file has it,
and `render`, with each tab turned into spaces. The cursor column `E.cx`
counts bytes of `chars`, and the cursor code turns it into a screen
column. So the match's place must be a place in `chars` too, and the
search looks there. The original kilo searches `render` and then uses the
place it found as a column of `chars`. In a row with no tab before the
match the two are the same; after a tab, they are not:

![Row 5 as chars and as render: ret is at byte 1 of chars but byte 8 of render, because the tab is one byte in chars and eight spaces in render](figures/05.01-chars-render.svg)

`strstr()` also needs the `'\0'` at the end of `chars`: it reads up to
the terminator, not up to `size`. 04.01's invariant, that every row ends
in a `'\0'`, is what makes `chars` a string it can search.

### The match at the top of the screen

```
last_match = current;
E.cy = 0;
E.cx = match_offset;
E.rowoff = current;
E.coloff = 0;
```

The match's row becomes the first row of the view and the cursor goes to
the top line, so the match is always on screen. If its column is past the
right edge, the view scrolls right just enough to put the cursor in the
last column, as the join of 04.03 does. The test is `E.cx >=
E.screencols`; the original kilo has `>`, which lets a match in exactly
the column after the last one leave the cursor off the screen: on a
44-column screen it asks for column 45, and what is typed there goes into
the row unseen.

### A query that finds nothing changes nothing

The view moves only `if (match)`. A query with no match leaves the screen
where the last match put it, so a typing mistake in the query does not
throw the view back to the top. Backspace then searches again for the
shorter query, from the top, and finds the same row.

## Decide the boundary

kilo searches from the top of the file every time the query changes. It
is simple, the same query always lands on the same row, and the first
match in the file is never skipped.

Another editor could start from the cursor and search forward, as vi and
less do, so a search finds the next place after where you are, not the
first place in the file. It pays with a search whose result depends on
where the cursor was, and a file searched in two pieces, cursor to end
and then start to cursor. Should a search start where you are, or where
the file starts?
