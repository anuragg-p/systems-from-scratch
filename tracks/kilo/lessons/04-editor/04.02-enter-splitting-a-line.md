# 04.02 Enter: splitting a line

Enter cuts the row at the cursor: what is left of the cursor stays, the
rest becomes a new row below it, and the cursor goes to the start of that
row. It is the first edit that changes how many rows the file has.

## Where this fits

![Where 04.02 fits](figures/04.02-map.svg)

This lesson adds to the edit piece, along the bottom of the map. The key
handler above it has had a case for Enter since 04.01 that did nothing;
now it calls this code. The edit works on the rows to its right: it adds a
row to them, with the function of 03.01 that puts a new row in at any
position, and the new row goes up the right-hand side to the screen,
through render and frame, like every other. After this lesson you can
break a line in two and open new lines anywhere, so with 04.01 you can
type a file from nothing.

## The idea

![Enter at column 5 of hello world: the bytes from the cursor on are copied into a new row below, the old row is cut at the cursor, and the rows after it move down one place](figures/04.02-split.svg)

Until now, Enter did nothing. With the cursor on the space in
`hello world`, Enter must leave `hello` on that line, put ` world` on a new
line under it, and push every line below down by one.

The rows of the file are one array, `E.row`, in file order. A new line is
a new element of that array, and 03.01 already has the function that adds
one at any position: `editorInsertRow()` grows the array by one element,
moves the elements from that position on down one place, and fills the
gap with a copy of the bytes it is given. So the split takes three steps,
the halves of the figure:

1. Copy the end of the row, from the cursor on, into a new row just below
   it: 6 bytes, ` world`, and the `'\0'` after them.
2. Cut the old row at the cursor: a `'\0'` at column 5 and `size` 5. Its
   block keeps all 12 bytes; the ones after the new `'\0'` are no longer
   part of the row.
3. Render the old row again. The new row was rendered when it was made.

Then the cursor goes to the start of the next screen line, or, on the
bottom line, stays there while the view scrolls down one row. Either way
it is at column 0, and a view scrolled right goes back to the left edge.

### `editorInsertNewline`

It finds the file row and column under the cursor, as 04.01's insert does,
and handles three cases before the one in the figure. A cursor past the
end of its row counts as being at the end, so Enter there copies nothing
and opens an empty row below. At column 0 it inserts an empty row above
instead of copying the whole row, and the row moves down with the cursor.
And below the last row there is no row to cut: one row past the end of the
file, Enter adds an empty row and jumps straight to the cursor code at
`fixcursor`; further down, it does nothing.

The only other change is in `editorProcessKeypress()`, where the Enter
case now calls this function.

## How it works

### The row pointer is taken again

The middle of the split is these three lines:

```
editorInsertRow(filerow+1,row->chars+filecol,row->size-filecol);
row = &E.row[filerow];
row->chars[filecol] = '\0';
```

`row` pointed into `E.row` before the call, and `editorInsertRow()` grows
`E.row` with `realloc()`. When the block cannot grow where it is,
`realloc()` moves it to a new address and frees the old one. On a 64-bit
build a row's struct is 24 bytes (two `int`s and two pointers), so a file
of three rows has a 72-byte array, and the fourth row needs 96 bytes;
here, on a Mac, that move happens. Every pointer into the old array is
then a pointer into freed memory. So the second line takes `row` again
from the new array before anything goes through it. That is the
**invariant** this code keeps: no pointer into `E.row` survives a call
that adds or removes a row. The pointer into `chars` that the call is
given is safe: it points into the row's own block of bytes, which the call
does not move.

![E.row grows from 72 bytes to 96 and moves; a row pointer taken before the call still points into the freed block](figures/04.02-realloc.svg)

### The copy brings its own `'\0'`

`editorInsertRow()` copies `len+1` bytes: the bytes it was asked for and
the one after them, which it expects to be a `'\0'`. Here that byte is
`row->chars[row->size]`, the old row's own terminator, and it is there
because 04.01 keeps a `'\0'` after every row. One invariant held by one
function is what another function counts on.

### Cutting is two stores

The old row is not copied or shrunk: a `'\0'` at the cut and a smaller
`size` are enough, and the 6 bytes after the cut stay allocated until the
next `realloc()` of that row: the next character typed there asks for
`size+2` bytes, and the block shrinks to fit.

## Decide the boundary

kilo keeps the file as an array of rows, so Enter inserts into an array:
every row after the cursor moves down one place, and the array may be
copied whole to a bigger block. For a few thousand lines that is nothing.
In a file of a million lines, Enter near the top moves about 24 MB of row
structs.

VS Code started with the same design, an array of line objects, and
replaced it with a piece tree: the text stays in a few large buffers, and
a balanced tree of pieces says which spans of them make up the file, with
line breaks counted in the tree. It pays in code, and in a buffer that is
no longer one string per line. Do you expect files of a million lines, or
lines a person can read?

## Break it

Keep the stale pointer. In `build/at/kilo/04.02/kilo.c`, in
`editorInsertNewline()`, delete the line that takes `row` again after the
call:

<!-- verify: patch file=kilo.c
     editorInsertRow(filerow+1,row->chars+filecol,row->size-filecol);
-    row = &E.row[filerow];
-->

Make the file again and open it:

<!-- verify: session -->
```
$ printf 'hello world\nsecond\nthird\n' > build/at/kilo/04.02/f.txt
```

```
./learn run kilo --at 04.02 -- f.txt
```

Press Right five times and Enter. kilo is gone: no new screen is drawn,
and the shell's prompt comes back over the old one. On this Mac, kilo is
killed by a segmentation fault (signal 11) when the cut goes through the
old pointer. A process killed by a signal runs no exit handler, so the
terminal is left in raw mode (01.01): depending on your shell, what you
type does not show, or each line of output starts where the last one
ended. Type `reset` and press Enter to put it right.

To see the cause named, build the same code with AddressSanitizer, which
checks every memory access, and send its report to a file instead of the
raw terminal. In the project's folder:

<!-- verify: skip reason="needs the editor driven by hand between the commands; the report's addresses and pid differ on every run" -->
```
$ cd build/at/kilo/04.02
$ cc -fsanitize=address -g -o kilo kilo.c
$ ASAN_OPTIONS=log_path=asan ./kilo f.txt
```

Right five times and Enter again; then `reset`, and:

<!-- verify: skip reason="AddressSanitizer's report: its addresses and pid differ on every run" -->
```
$ grep -A2 -e ERROR -e 'freed by' asan.*
==77149==ERROR: AddressSanitizer: heap-use-after-free on address 0x607000000098 at pc 0x000102fcaffc bp 0x00016ce36210 sp 0x00016ce36208
READ of size 8 at 0x607000000098 thread T0
    #0 0x000102fcaff8 in editorInsertNewline kilo.c:423
--
freed by thread T0 here:
    #0 0x000103979350 in realloc+0x80 (libclang_rt.asan_osx_dynamic.dylib:arm64e+0x41350)
    #1 0x000102fca1d0 in editorInsertRow kilo.c:342
```

A read of 8 bytes, `row->chars`, from memory the `realloc()` in
`editorInsertRow()` freed. The full report also says where: 8 bytes inside
a 72-byte region, the old array of three rows. Without AddressSanitizer
the same bug can just as well run on with whatever those bytes hold, and
fail somewhere else, later. Put the line back, go back up with
`cd ../../../..`, and `./learn run` builds kilo as before.
