# 04.03 Deleting, and joining lines

Backspace deletes the character left of the cursor. At the start of a
line there is none, so it joins the line onto the end of the one above,
and the file has one line fewer.

## Where this fits

![Where 04.03 fits](figures/04.03-map.svg)

This lesson finishes the edit piece, along the bottom of the map. The key
handler above it has had a case for Backspace, Delete and Ctrl-H since
04.01 that did nothing; now it calls this code. The edit works on the rows
to its right, this time the other way: bytes come out of a row, and a
whole row comes out of the array of rows. The changed rows go up the
right-hand side to the screen, through render and frame, as before. After
this lesson every change to the text can be made, and undone by hand.

## The idea

![Backspace with the cursor at column 5 of hello world: the o goes, and the bytes after it, the '\0' too, move one place left](figures/04.03-delete.svg)

Until now a wrong letter stayed: there was no way to take a byte out of
the text. Backspace has two jobs, and which one depends on where the
cursor is.

**In the middle of a row** it deletes the byte just left of the cursor.
With the cursor on the space in `hello world`, that is the `o` at column
4. The bytes after it, the `'\0'` included, move one place left over it,
and `size` goes from 11 to 10. The block is not made smaller: its last
byte is simply no longer used. The cursor moves one column left; at the
left edge of a view scrolled to the right, the view scrolls back one
column instead.

**At column 0** there is no byte to the left, only the line break between
this row and the one above. Deleting a line break joins the two rows. With
the cursor at the start of `second`, the second line of the file:

1. Note where the rows will meet: the length of the row above,
   `hello world`, 11.
2. Append the 6 bytes of `second` to that row. Its block grows to 18
   bytes: `hello worldsecond` and a `'\0'`.
3. Delete the `second` row: free its bytes, and move the rows after it up
   one place in `E.row`.
4. Put the cursor where the rows met: one row up, column 11.

![Backspace at the start of second: the row is appended to hello world, then deleted, and third moves up](figures/04.03-join.svg)

At the very start of the file, row 0 and column 0, there is nothing to
delete or join, and Backspace does nothing. Below the last row it does
nothing either.

### `editorRowDelChar`

The middle-of-a-row case on one row: move the bytes after column `at` one
place left with `memmove()`. It moves `row->size-at` bytes: the
`size-at-1` after the deleted one, and the `'\0'`, which keeps 04.01's
invariant that every row ends in one.

### `editorRowAppendString`

Grows a row by `len` bytes with `realloc()`, copies the new bytes to its
end, and writes the `'\0'` after them. Then, as every change to a row
does, it renders the row again and counts a change.

### `editorDelRow`

Takes row `at` out of the file: `editorFreeRow()` frees its `chars` and
its `render`, and `memmove()` moves the rows after it up one place, the
opposite of what `editorInsertRow()` does. The array itself is not made
smaller; the next `editorInsertRow()` reallocs it to fit anyway.

### `editorDelChar`

Backspace itself: it decides between the cases above, calls the row
functions, and moves the cursor or the view. In `editorProcessKeypress()`
the case for Backspace, Ctrl-H and Delete now calls it, so all three keys
do the same thing here, as in the original kilo: they delete left of the
cursor. Delete in most editors deletes to the right. Ctrl-H is byte 8, the
ASCII backspace, which some terminals send for the Backspace key.

## How it works

### The join: the order of four lines

```
filecol = E.row[filerow-1].size;
editorRowAppendString(&E.row[filerow-1],row->chars,row->size);
editorDelRow(filerow);
row = NULL;
```

Each line has to come where it is. The meeting point is the size of the
row above *before* the append: read after it, it would be 17, and the
cursor would land after `second` instead of before it. The append copies
from `row->chars`, so it must come before `editorDelRow()` frees those
bytes. And after the delete, `row` still points at `E.row[filerow]`, which
now holds the next row, `third`, or, when the joined row was the last one,
a slot past the end that still names the freed blocks. Setting `row` to
`NULL` keeps the `if (row) editorUpdateRow(row);` at the end of the
function away from it. Without that line, joining the last row of a file
renders a deleted row: its `render` is freed a second time, and on this
Mac kilo dies on the spot.

### Keeping the cursor on the screen

After a join the cursor column is the length of the row above, which can
be more than the screen is wide. Then the view scrolls right just far
enough to put the cursor in the last column:

```
if (E.cx >= E.screencols) {
    int shift = (E.cx-E.screencols)+1;
    E.cx -= shift;
    E.coloff += shift;
}
```

`E.coloff+E.cx`, the file column, is the same before and after: the
shift only moves the screen. It keeps the **invariant** that the cursor
code of 03.02 keeps on every move: `E.cx` is between 0 and the last
column, `E.coloff` is never negative, and their sum is where the cursor is
in the row. Here the
original kilo computes `(E.screencols-E.cx)+1`, the same difference turned
around, and Break it shows what that does.

### Rendered twice

`editorRowDelChar()` renders the row before it counts the byte as gone,
so that render is made from one byte too many: the old last byte, which
after the move is a `'\0'`. `editorDelChar()` renders the row again right
after, from the right size, so it never reaches the screen. The original
kilo does it in this order too; it is kept, as most of its small oddities
are, so the two files can be read side by side.

## Decide the boundary

kilo forgets a deleted byte at once: nothing records it, and a wrong
Backspace can only be fixed by typing the text again. Another editor could
record every change, the byte, where it was and whether it went in or out,
and walk that record backwards for undo. It pays in memory for the record,
in code at every place the text changes, and in rules for which changes
are undone together. How much is one wrong keystroke allowed to cost you?

## Break it

Put back the original kilo's arithmetic. In
`build/at/kilo/04.03/kilo.c`, in `editorDelChar()`, change the shift to
`(E.screencols-E.cx)+1`:

<!-- verify: patch file=kilo.c
-            int shift = (E.cx-E.screencols)+1;
+            int shift = (E.screencols-E.cx)+1;
-->

Make a file whose first line is wider than your screen, 200 zeros, with a
short line after it, and open it:

<!-- verify: session -->
```
$ printf '%0200d\nabc\n' 0 > build/at/kilo/04.03/long.txt
```

```
./learn run kilo --at 04.03 -- long.txt
```

Press Down, to the start of `abc`, and Backspace. On a terminal 44
columns wide:

<!-- verify: skip reason="a screen the full-screen editor draws (10 x 44 pseudo-terminal), not a shell transcript" -->
```

~
~
~
~
~
~
~
long.txt - 1 lines (modified)            1/1
HELP: Ctrl-Q = quit
```

The joined line, 203 characters long, looks empty, and the cursor sits in
the last column. Type `|` and nothing appears. The join point is column
200, so `shift` is (44 - 200) + 1, which is -155. Taking -155 from `E.cx`
moves the cursor right, to 355, and adding it to `E.coloff` makes the
view start 155 bytes *before* the row. So kilo asks the terminal for
column 356, which a 44-column terminal does not have, and draws the row
from memory that is not the row at all. On this Mac those bytes were
zeros, which a terminal draws as nothing; on a terminal 120 columns wide
the same run showed stray bytes such as `(s` before the zeros. The text
itself is fine: the `|` went in at column 200, because `E.coloff+E.cx` is
still 200. Only the screen arithmetic broke, and with it every frame that
reads the row. Put the line back.
