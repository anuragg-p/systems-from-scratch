# 04.04 Saving

Ctrl-S writes the rows back to the file: every row with a newline after
it, joined into one string and written over the old contents. And Ctrl-Q
now warns before it throws unsaved changes away.

## Where this fits

![Where 04.04 fits](figures/04.04-map.svg)

This lesson builds the save piece, along the bottom of the map next to
edit. The key handler above it has had a case for Ctrl-S since 04.01 that
did nothing; now it calls this code. Its label says what it does: rows to
the file. It reads the rows, to the right of the edit piece, and hands
them to the kernel to write: where 03.01 read the file into rows, this
writes the rows back into the file. After this lesson kilo is an editor
you can use: open a file, change it, save it, and be stopped before you
quit with work unsaved.

## The idea

![The three rows of f.txt after an edit, and the 19-byte string the save writes: each row followed by a newline](figures/04.04-rows-to-string.svg)

Everything typed so far has lived in memory and gone at Ctrl-Q, as 04.01
showed. The file on the disk is a string of bytes with a `'\n'` at the end
of each line; the editor's copy is an array of rows with no newlines in
them at all, since 03.01 took them off. Saving turns one into the other.

**One string.** Add up the rows' sizes plus one newline each, allocate
that, and copy the rows in one after another, a `'\n'` after each. For
`hello`, `second` and `third` that is 5 + 6 + 5 bytes and 3 newlines: 19.
Every line gets a `'\n'`, the last one too, whatever the file had: a file
holding `x\r\ny`, with Windows line ends and none at the end, is saved as
`x\ny\n`.

**Over the old file.** Open the file for writing, creating it if it does
not exist. Cut it to exactly 19 bytes. Write the 19 bytes in one `write()`.
Close it. Then the file holds the rows, and nothing else.

![What f.txt holds at each step: 25 bytes before; the first 19 of them after the cut; the new 19 after the write. Without the cut, the old last 6 bytes stay behind the new text](figures/04.04-truncate.svg)

The cut is the step that is easy to forget. Opening a file for writing
does not empty it, and a write only replaces the bytes it covers. When the
new text is shorter than the old, as here after ` world` was deleted, the
old file's last 6 bytes would stay behind the new 19.

### `editorRowsToString`

The one string. It counts first and copies second, so it needs one
allocation. `*buflen` is the length to write, 19; the buffer has one more
byte, a `'\0'` at the end, which is never written.

### `editorSave`

Opens the file with `O_RDWR|O_CREAT` and mode `0644` (the mode is used only
when the file is created, and less your umask: `rw-r--r--` with the usual
umask of 022), cuts it with `ftruncate()` and writes the string with one
`write()`. On success it clears `E.dirty`, so the status bar loses its
`(modified)`, and the message line says how many bytes went out. On any
failure it says `Can't save! I/O error:` and the reason from
`strerror()`, and leaves `E.dirty` as it was: the changes are still
unsaved, and the status bar still says so.

### `editorProcessKeypress`: Ctrl-S, and Ctrl-Q with unsaved changes

The Ctrl-S case calls `editorSave()`, and the help line gains
`Ctrl-S = save`. Ctrl-Q changes too. With `E.dirty` set, it no longer
quits: it says `WARNING!!! File has unsaved changes. Press Ctrl-Q 3 more
times to quit.`, and counts down with each press; the fourth press in a
row quits. Any other key starts the count again.

## How it works

### Cut first, then write

```
int fd = open(E.filename,O_RDWR|O_CREAT,0644);
if (fd == -1) goto writeerr;
...
if (ftruncate(fd,len) == -1) goto writeerr;
if (write(fd,buf,len) != len) goto writeerr;
```

`open()` has a flag that empties the file as it opens it, `O_TRUNC`. kilo
does not use it, because of what a failure would leave. With `O_TRUNC`,
the file is 0 bytes from the moment it is opened, and a `write()` that
then fails, on a full disk say, leaves an empty file: the old text is gone
and the new one never arrived. With `ftruncate()` to the new length
first, a failed write leaves the old bytes, cut or padded to the new
length. That is still damage, but most of the old text survives.

The same goes for kilo dying between the two calls: the middle line of
the truncate figure is the file it leaves. The save is not
**atomic**, done entirely or not at all; the comment above the two lines
says as much, "a bit safer, under the limits of what we can do in a small
editor".

A `write()` may also write fewer bytes than it was given; kilo checks the
count and calls a short write an error rather than writing the rest.

### Clean only after a good write

`E.dirty = 0` comes after the `write()` and `close()`, on the success path
only. That keeps the one promise the status bar makes: no `(modified)`
means the file on the disk holds what the screen shows. Every error path
jumps over it to `writeerr`.

### The count that resets

```
if (E.dirty && quit_times) {
    editorSetStatusMessage("WARNING!!! File has unsaved changes. "
        "Press Ctrl-Q %d more times to quit.", quit_times);
    quit_times--;
    return;
}
```

`quit_times` is `static`, so it keeps its value from one key to the next.
The `return` skips the last line of `editorProcessKeypress()`, which sets
the count back to 3. Every other key reaches that line, so only Ctrl-Q
pressed four times in a row, with nothing between, quits with changes
unsaved. A saved file has `E.dirty` at 0, and Ctrl-Q quits at once.

## Decide the boundary

kilo saves in place: it cuts and rewrites the very file it opened. A
power cut at the wrong moment leaves a file that is neither the old text
nor the new one.

Another editor could write the text to a new file beside the old one,
force it to the disk with `fsync()`, and then `rename()` it over the old
name, which replaces the old file in one step: anyone who opens that name
sees the old file or the new one, never half of each. It pays in other
ways. The new file is a new file: hard links to the old one still point at
the old text, and its owner and permissions must be copied over by hand.
The editor needs permission to create files in the folder, not just to
write this one. And even then, how much survives a crash depends on the
file system, and on also syncing the folder. Which would you rather risk
losing in a crash: the last edit, or the file?

- [antirez's kilo.c, `editorRowsToString`](https://github.com/antirez/kilo/blob/323d93b29bd89a2cb446de90c4ed4fea1764176e/kilo.c#L633-L657) and [`editorSave`](https://github.com/antirez/kilo/blob/323d93b29bd89a2cb446de90c4ed4fea1764176e/kilo.c#L829-L852) - the original, the same code, with its comment on truncate and a single write; the quit count is in [`editorProcessKeypress`](https://github.com/antirez/kilo/blob/323d93b29bd89a2cb446de90c4ed4fea1764176e/kilo.c#L1187-L1254).
- [Build Your Own Text Editor, chapter 5](https://viewsourcecode.org/snaptoken/kilo/05.aTextEditor.html) - "Save to disk" explains `ftruncate()` against `O_TRUNC` the same way, and notes that more advanced editors write to a new, temporary file; "Dirty flag" and "Quit confirmation" follow.
- [open(2)](https://man7.org/linux/man-pages/man2/open.2.html) - `O_CREAT` and the mode, which the umask reduces; `O_TRUNC`, which cuts the file to length 0.
- [truncate(2)](https://man7.org/linux/man-pages/man2/ftruncate.2.html) - `ftruncate()`: data past the new length is lost, and a file made longer reads as zero bytes in the new part.
- [write(2)](https://man7.org/linux/man-pages/man2/write.2.html) - a successful `write()` may write fewer bytes than asked, and does not mean the data is on the disk: only `fsync()` says that.
- [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) - an existing new path "will be atomically replaced", the step the temporary-file way is built on.
- Dan Luu, [Files are hard](https://danluu.com/file-consistency/) - why "write a temporary file and rename it" is less simple than it sounds: what POSIX promises across a crash, and what file systems really do.
