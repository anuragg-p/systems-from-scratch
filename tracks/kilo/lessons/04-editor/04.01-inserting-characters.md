# 04.01 Inserting characters

A typed key now changes the text: its byte goes into the row under the
cursor, the row is drawn again, and the cursor moves past it. This is the
lesson where the viewer of module 03 starts to edit.

## Where this fits

![Where 04.01 fits](figures/04.01-map.svg)

This lesson starts the edit piece, along the bottom of the map: the code
that changes a line of the file in memory. The key handler above it now
passes it every key that has no other job. An edit changes the rows, to
its right: the lines of the file as 03.01 read them. From the rows, the
way back to the screen goes up the right-hand side, through the render
step of 03.03, which makes the copy of a row the screen shows, and the
frame of 02.01. After this lesson you can open a file and type into it
anywhere, even below its last line, and the status bar says the file has
changed, though nothing writes the change to the disk until 04.04.

## The idea

![Typing a comma with the cursor at column 5 of hello world: the row grows by one byte, the bytes from the cursor on move one place right, and the comma goes into the gap](figures/04.01-insert.svg)

Until now, a key with no case of its own did nothing. Open a file whose
first line is `hello world`, move the cursor onto the space after `hello`
and type a comma: the line must become `hello, world`, with the cursor
after the comma, ready for the next key.

A row keeps its text in `chars`, a block of heap memory holding the line's
bytes followed by a `'\0'`, and in `size`, the number of bytes before the
`'\0'`. `hello world` is 11 bytes, so its block is 12. Putting a byte in at
column 5 takes three steps, the rows of the figure:

1. Grow the block by one byte, to 13.
2. Move the 7 bytes from column 5 to the end, the `'\0'` included, one
   place to the right. That leaves a gap at column 5.
3. Store the comma in the gap and count it: `size` is 12.

Two things follow every change to a row. The row's `render` is made again
from `chars`, because the screen draws `render` and never `chars`. And the
editor notes that the file has changed since it was opened, so the status
bar can say `(modified)`.

Then the cursor moves one column right. In the last column of the screen
it cannot, so the view scrolls one column instead, and the cursor stays in
the last column: the next key still lands just after this one.

### `editorRowInsertChar`

It changes one row and knows nothing of the cursor or the screen: it is
given a row, a column and a byte. Its second branch is the three steps
above. Its first branch handles a column past the end of the row, filling
the gap with spaces before the byte; 03.02 pulls the cursor back to the end
of any row shorter than its column, so in this editor that branch is only
a guard. The `+2` in both `realloc()` calls is one byte for the new
character and one for the `'\0'`.

### `editorInsertChar`

It works out where in the file the cursor is, row `E.rowoff+E.cy` and
column `E.coloff+E.cx` as 03.02 defined them, and calls
`editorRowInsertChar()` there. The cursor can be below the last row: one
row past the end of the file, or on the bottom line after Page Down on a
short file. Then there is no row to insert into, so it first adds empty
rows with `editorInsertRow()` until the cursor's row exists, and types
into that.

### `editorProcessKeypress`, and the rest

The rest of the lesson sits outside these two functions: the `dirty`
count in `E`, the `(modified)` in the status bar, and a `default:` case in
`editorProcessKeypress()` that hands every key not named above it to
`editorInsertChar()`. Enter, Backspace, Delete, Ctrl-H, Ctrl-S and Ctrl-F
get cases that do nothing yet, so they do not go into the text as bytes
before their lessons (04.02 to 05.01) give them work. Home and End get a
case of their own too: the original kilo has none for them, so it inserts
the low byte of their key codes into the text.

## How it works

### The `'\0'` moves too

The move in the second branch copies `row->size-at+1` bytes: the bytes
from the cursor to the end, plus the `'\0'` after them.

```
row->chars = realloc(row->chars,row->size+2);
memmove(row->chars+at+1,row->chars+at,row->size-at+1);
row->size++;
```

Without the `+1` the terminator would stay where it was and be overwritten
by the last moved byte, and the byte after the new end would be whatever
`realloc()` left there. The row would draw correctly, since everything
that draws it counts bytes with `size`. Code that reads `chars` as a C
string would not: the split of 04.02 copies the end of a row, `'\0'` and
all, and the search of lesson 05.01 runs `strstr()` on `chars`. So the
code keeps an **invariant**, a fact that holds between any two keys: every
row's `chars` holds `size` bytes and then a `'\0'`. The `+1` in the
`memmove()` keeps it here; in the padding branch it is the line that
stores `'\0'` at `row->size+padlen+1`.

`memmove()` and not `memcpy()`: the bytes are copied onto an overlapping
range of the same block, one place along, and only `memmove()` is defined
for overlapping ranges.

### `render` is made again from `chars`

The second invariant: a row's `render` is always the render of its current
`chars`. `editorUpdateRow()` keeps it, called at the end of
`editorRowInsertChar()` after every byte. It rebuilds the whole render,
which for a line of normal length is cheap; Break it shows what the screen
does when it is skipped.

### A count, not a flag

`E.dirty` counts changes. `editorRowInsertChar()` counts one, and
`editorInsertChar()` counts another, so one key adds 2. Reading the file
counts too, because `editorOpen()` builds the rows with `editorInsertRow()`,
which counts each row; that is why `editorOpen()` sets `E.dirty` back to 0
when it is done. Only zero or not zero is ever used.

### Every byte without a case is text

`editorReadKey()` returns a plain byte for any key that is not an escape
sequence, and the `default:` case inserts it. So control keys go in as
text: Ctrl-A puts byte 1 into the line. A terminal draws nothing for most
control codes, but the cursor code counts every byte of `chars` as a
column. On `second`, Ctrl-A and then `x` show `xsecond` with the cursor
on the `e`, though the next key goes in before the `s`, one column to the
left. The original kilo does the same.

## Decide the boundary

kilo keeps each line in its own block and makes room for every typed byte
by moving the rest of the line. For lines a person types, that is a few
dozen bytes per key, and the code is a dozen lines.

Another editor could keep a **gap buffer**: the text in one array with an
empty gap at the cursor, so that typing is a single store into the gap and
only moving the cursor far away moves bytes. It pays with a buffer that
does not look like the file and with more care whenever the cursor jumps.
A file that is one line of 2 MB, a minified script say, makes kilo move
up to 2 MB for every key typed near its start, and render all of it again. How long are the lines you
expect to edit, and how far does the cursor jump between edits?

- [malloc(3)](https://man7.org/linux/man-pages/man3/realloc.3.html) - `realloc()`: the block may move to a new address (the old one is then freed), and the bytes added are not set, which is why the padding branch writes its own `'\0'`.
- [memmove(3)](https://man7.org/linux/man-pages/man3/memmove.3.html) - like `memcpy()`, except that the two ranges may overlap.
- Charles Crowley, [Data Structures for Text Sequences](https://www.cs.unm.edu/~crowley/papers/sds.pdf) (1998) - section 1 names kilo's layout, the "line span method", next to the gap method and the piece table; the paper finds the gap method or the piece table the best in almost all cases.
