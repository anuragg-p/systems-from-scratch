# 00.01 How a terminal editor works

kilo is a text editor that runs in a terminal: it opens a file, moves
through it, changes it, saves it and searches it, and draws its own screen.
This lesson follows one key press through the whole editor before any part
of it is built, then runs the finished editor on your machine.

The editor is antirez's kilo, which Salvatore Sanfilippo wrote in 2016 as a
small editor in one C file, with no library between it and the terminal.
The code in these lessons is his, without its syntax highlighting, built up
one function at a time under the same names, so you can open
[his kilo.c](https://github.com/antirez/kilo/blob/master/kilo.c) beside any
lesson and find the function it is about.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

This is the whole editor in one picture. A key comes down the left side,
the editor acts on it along the bottom, and the new screen goes back up the
right side to the terminal. Each box is given something and gives something
back:

- **The terminal** is given your key presses and turns them into bytes. It
  is given bytes back and turns them into the picture you see. In raw mode
  it hands over every byte the moment it is typed.
- **Read a key** is given those bytes and gives back one key. A letter is
  one byte; an arrow is three.
- **The key handler** is given the key and decides what it means: move,
  find, save or change the text.
- **Cursor**, **find**, **save** and **edit** are the four things a key
  can do: move the cursor and scroll the view, search as you type, write
  the file, insert or delete.
- **Rows** are the file's lines, in memory, one string each. An edit
  changes them; the file on disk changes only when you save.
- **Render** is given a row and gives back the row as the screen shows it,
  each tab turned into spaces.
- **The status bar** names the file, says how long it is and whether it has
  changed, and shows messages.
- **The window size** says how many rows and columns there are to fill.
- **The frame** is given all of that and gives back the whole screen as
  bytes, which go to the terminal in one write.

The track builds these in the order you need them to see anything at all.
Module 01 is the terminal: raw mode, reading a key, the window size.
Module 02 draws a frame, so there is a screen. Module 03 reads a file into
rows and makes a viewer of it, with a cursor, tabs and a status bar.
Module 04 makes it an editor that changes and saves the file, and module 05
adds search. Every step runs: before there is a screen, the editor prints
the code of each key you press, and before there is a file, it draws an
empty screen.

## The idea

![One key, ! typed at the end of world, through the finished kilo: each step, the module that builds it, and the screen it ends with.](figures/00.01-one-key.svg)

A program in a terminal cannot draw the way a program with a window does.
All it has is a stream of bytes in each direction: the terminal sends the
keys you press, and the program sends back text and short commands, called
**escape sequences**, that move the cursor or erase a line. Everything kilo
does is built on those two streams.

Picture a file `hello.txt` with two lines, `Hello` and `world`, and the
cursor just after `world`. You press `!`. The terminal sends one byte, 33.
kilo reads it, finds it is not a key with a job of its own, so it is text,
and inserts it into its copy of the second line, which becomes `world!`. It
moves its cursor one column right. Nothing on the screen has changed yet.
Then kilo draws the whole screen again from what it holds: every row, the
status bar, the message line, and the cursor at row 2, column 7. That is
192 bytes, sent in one write, and the terminal turns them into the picture.

That is the whole editor: a loop that draws the screen, then waits for one
key and acts on it, forever. The finished `main()` ends in exactly that:

<!-- verify: mention names="main() editorRefreshScreen() editorProcessKeypress() editorReadKey() editorSave() editorMoveCursor() editorInsertChar() kilo.c" at=finished -->
<!-- verify: quote at=finished -->
```
    while(1) {
        editorRefreshScreen();
        editorProcessKeypress(STDIN_FILENO);
    }
```

`editorProcessKeypress()` reads one key with `editorReadKey()` and switches
on it: Ctrl-S calls `editorSave()`, an arrow calls `editorMoveCursor()`, and
any key without a case of its own goes to `editorInsertChar()`. None of
these touches the screen. They change one global, `E`, and the next turn of
the loop draws `E`.

### The state: one global

`E`, a `struct editorConfig`, is everything the editor knows: the rows of
the file, where the cursor is, which part of the file the screen shows, the
screen's size, the file's name, whether it has changed since it was saved,
and the message under the status bar. Apart from the terminal's settings,
saved to be put back at exit, and a count of how many more times Ctrl-Q
must be pressed to quit with unsaved changes, there is no other state. The
screen is never changed in place, so it cannot disagree with `E` for longer
than one key.

### Before the first key

Before its loop, `main()` puts the terminal in raw mode (01.01), measures
the window (01.03) and reads the file into rows (03.01). Then it sets the
help message that the bottom line shows first, and the loop starts.

This lesson has no code of its own yet, so run the finished editor, the one
the track ends with. From the repository root this builds it and opens


## How it works

### Draw everything, after every key

kilo never works out what changed on the screen. After every key it sends
the whole screen again: on a 24 by 80 terminal showing the start of
`kilo.c` itself, that is 1542 bytes for every key. A terminal takes that
in no time, and in return the drawing code has one job, turning `E` into
bytes, instead of two, working out what changed and changing only that.
The frame is built in memory and written with one `write()` (02.01), so the
terminal never shows a screen half drawn.

### A key is finished before the next is read

Each key is read whole, acted on, and done with before the screen is drawn
and the next key is read. There are no threads, and no timer redraws the
screen. Two things step outside the loop. Ctrl-F runs a small loop of its
own, drawing and reading keys until Enter or Escape (05.01). And a resize,
which the kernel announces with a signal, is measured and drawn at once by
the signal's handler, whatever kilo was doing (02.01).

### Bytes, and nothing between

The two streams of bytes are all kilo uses. It does not ask a library which
escape sequences this terminal understands; in the words of its README, it
"uses fairly standard VT100 (and similar terminals) escape sequences", named
for DEC's VT100 terminal. Lesson 00.02 shows both streams on your own
terminal.

## Decide the boundary

kilo writes VT100 escape sequences straight into its output. Another editor
could look them up instead: the terminfo database describes each kind of
terminal by the name in `$TERM`, and the curses library reads it. `tput`
asks it for the sequence that moves the cursor to row 5, column 10:

<!-- verify: session host -->
```
$ TERM=xterm-256color tput cup 4 9 | od -c
0000000  033   [   5   ;   1   0   H
0000007
$ TERM=vt52 tput cup 4 9 | od -c
0000000  033   Y   $   )
0000004
```

The first is the sequence kilo writes. The VT52, the DEC terminal before the
VT100, wanted other bytes. An editor that asks terminfo runs on both, and
pays with a library, a database that must describe the terminal correctly,
and one more way to be wrong. kilo pays nothing and runs on terminals that
understand the VT100's sequences. How many kinds of terminal does your
editor have to run on?

## Break it

Stop the drawing. In `build/at/kilo/finished/kilo.c`, delete the call to
`editorRefreshScreen()` from the loop at the end of `main()`:

<!-- verify: quote at=finished -->
```
        editorRefreshScreen();
```

<!-- verify: patch file=kilo.c at=finished

-        editorRefreshScreen();
         editorProcessKeypress(STDIN_FILENO);
-->

Run it on a new file, `./learn run kilo -- blind.txt` (it rebuilds first),
and type `Hello`, Enter, `world`, then Ctrl-S.

Nothing appears: no welcome, no text, no message. The window still shows
whatever was in it before. The editor is working all the same: the rows
changed, and Ctrl-S wrote `blind.txt`, 12 bytes. Now drag a corner of the
window to resize it. The whole screen appears at once, with both lines in
it:

<!-- verify: skip reason="kilo's full screen after a resize: the replay can neither resize its terminal nor follow kilo's cursor moves. Checked on a pseudo-terminal resized from 10 x 44 to 12 x 44" -->
```
Hello
world
~
~
~
~
~
~
~
~
blind.txt - 2 lines                      2/2
12 bytes written on disk
```

A resize is the one other place that draws (02.01), and it draws from the
same `E`. The screen is only a picture of `E`, and nothing else in kilo
knows it is there. Press Ctrl-Q, and put the line back.
