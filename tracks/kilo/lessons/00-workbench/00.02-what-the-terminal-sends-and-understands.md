# 00.02 What the terminal sends and understands

Between kilo and you there is a terminal, and the only thing the two ever
exchange is bytes. This lesson looks at both streams on your own terminal,
before kilo touches either: what each key sends, and what a terminal does
with the bytes a program writes.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

The pieces this lesson lights up are the three that touch the terminal: the
terminal itself at the top, reading a key just below it on the left, where
the keys come down, and the frame on the right, where the screen goes back
up. Keys arrive from the terminal as bytes, and every screen kilo draws goes
back to it as one long run of bytes. Nothing of kilo is built yet. After
this lesson you can read both streams, and they are all kilo ever works
with.

## The idea

![What ten keys send: a key with a character sends that character's byte; the others send ESC and a few more bytes.](figures/00.02-keys.svg)

A **terminal** is the program that owns the window you type in, such as
macOS's Terminal or xterm. It is not part of the kernel, and not part of
the programs it runs. Between it and them sits the kernel's terminal
driver, which by default does some work of its own on both streams; module
01 switches most of that off.

Keys first. A key with a character on it sends that character's code in
ASCII: `a` is 97. A few keys send **control codes**, the numbers below 32,
which name an action instead of a character: Enter sends 13, a carriage
return; Tab sends 9; Escape sends 27. Backspace sends 127, which ASCII
calls DEL. Holding Ctrl clears the top three bits of a letter's code:
`q` is 113, so Ctrl-Q is 113 & 0x1f, 17, and Ctrl-A to Ctrl-Z are 1 to 26.

The keys with no character on them, the arrows, Home and End, Page Up and
Page Down, Delete, send several bytes: an **escape sequence**, the byte 27
followed by `[` and a letter, or `[`, a digit and `~`. Up is 27 91 65,
written `ESC [ A`. Some terminals send Home and End as `ESC O H` and
`ESC O F` instead. kilo turns each sequence back into one key (01.02).

The other direction works the same way. Most bytes a program writes are
drawn where the cursor is, and the cursor moves on. A carriage return
(`\r`, 13) takes the cursor back to the first column; a line feed (`\n`,
10) moves it down a row. An escape sequence is a command: ESC, `[`, numbers
separated by `;` (after a `?` in a few), and one letter that says what to
do. kilo uses these:

| bytes | what the terminal does |
|---|---|
| `ESC [ row ; col H` | moves the cursor; `ESC [ H` alone goes to row 1, column 1 |
| `ESC [ 0 K` | erases from the cursor to the end of the line |
| `ESC [ 7 m`, `ESC [ 0 m` | reverse video on; all attributes off |
| `ESC [ ? 25 l`, `ESC [ ? 25 h` | hides the cursor; shows it |
| `ESC [ 999 C`, `ESC [ 999 B` | moves the cursor right, or down, until the edge stops it |
| `ESC [ 6 n` | asks where the cursor is; the answer, `ESC [ row ; col R`, comes back on the key stream, as if typed |

![kilo's whole first screen on a 6 by 20 terminal: 108 bytes, each line of them drawing one row.](figures/00.02-first-screen.svg)

That is all a screen is made of. kilo's first screen of a one-line file, on
a terminal 6 rows by 20 columns, is 108 bytes: hide the cursor and go to
the top left; each row, then an erase to the end of the line and `\r\n`;
the status bar between reverse video on and off; the message; and the
cursor moved into place and shown again.

## Run it

Nothing is built yet, so look at the two streams with tools you already
have. `od -c` prints every byte it reads, a printable one as itself and the
others as an escape like `\n` or a number in octal. Start it:

<!-- verify: session -->
```
$ od -c
```

and type `a`, the Up arrow, `b` and Enter, then Ctrl-D to end its input:

<!-- verify: session send="a esc [Ab enter ctrl-d" -->
```
a^[[Ab
0000000    a 033   [   A   b  \n
0000006
```

The first line is the terminal driver echoing what you typed, with the
unprintable ESC shown as `^[`. The second is what `od` read: `033` is 27 in
octal, so the Up arrow is the three bytes ESC, `[`, `A`, just as the figure
says. And Enter came through as `\n`, 10, not the 13 the key sends: the
driver turned the carriage return into a line feed on the way. Raw mode
(01.01) switches that off, and the echo too.

Now the other way. `printf` writes bytes, and `\033` in its format is the
byte 27:

<!-- verify: session -->
```
$ printf 'abcdef\033[3D\033[0K!\n'
abc!
```

`abcdef` left the cursor after the `f`. `ESC [ 3 D` moved it three columns
left, onto the `d`; `ESC [ 0 K` erased from there to the end of the line;
and `!` was written where the cursor stood. Reverse video works the same
way. Run `printf 'normal \033[7mreverse\033[0m normal\n'` and the middle
word shows in reverse; piped into `od -c`, it is plain bytes like any
others:

<!-- verify: session -->
```
$ printf 'normal \033[7mreverse\033[0m normal\n' | od -c
0000000    n   o   r   m   a   l     033   [   7   m   r   e   v   e   r
0000020    s   e 033   [   0   m       n   o   r   m   a   l  \n
0000036
```

To see kilo's own bytes, record them. `script` runs a program on a terminal
of its own and copies everything the program writes into a file. In the
folder of the editor 00.01 ran (the core's, at 05.02), make a one-line file,
tell the kernel the window is 6 rows by 20 columns, and run kilo under
`script`:

<!-- verify: skip reason="kilo runs full-screen inside script, which the line-based replay cannot drive. Checked under zsh and bash on a 24 x 80 pseudo-terminal" -->
```
$ cd build/at/kilo/05.02
$ printf 'ab\n' > ab.txt
$ stty rows 6 cols 20
$ script -q k.log ./kilo ab.txt
```

kilo draws a screen of 6 by 20 in the corner of your window. Press Ctrl-Q,
then drag a corner of the window a little: the terminal tells the kernel
its real size again. `cat -v` shows the log with ESC as `^[` and the
carriage returns as `^M`:

<!-- verify: skip reason="the log the skipped script run above wrote. Checked on a 24 x 80 pseudo-terminal" -->
```
$ cat -v k.log
^[[?25l^[[Hab^[[0K^M
~^[[0K^M
~^[[0K^M
~^[[0K^M
^[[0K^[[7mab.txt - 1 lines 1/1^[[0m^M
^[[0KHELP: Ctrl-S = save ^[[1;1H^[[?25h
```

These are the 108 bytes of the figure. That is the macOS `script`; on
Linux the same recording is `script -q -c './kilo ab.txt' k.log`, and its
log also has a first and a last line of its own, saying when the recording
started and stopped.

## How it works

### Escape is two things at once

The byte 27 is the Escape key, and it is also the first byte of every arrow
and every other key without a character. Nothing in the bytes tells the
two apart. What differs is timing: a terminal writes all the bytes of a
sequence at once, and after the Escape key nothing follows until you press
something else. kilo uses exactly that, with a wait of a tenth of a second
(01.02).

### Ctrl is arithmetic, and some keys are the same key

Ctrl-letter is the letter's code with the top three bits cleared, so it can
only make the 32 control codes. Several of them already belong to keys:
Ctrl-M is 13, the same byte as Enter; Ctrl-I is 9, the same as Tab; Ctrl-[
is 27, the same as Escape. A program receives the byte, not the key, so it
cannot tell Ctrl-M from Enter. Ctrl-S and Ctrl-Q, 19 and 17, have a job of
their own in the driver: by default they stop and restart the terminal's
output, which is why kilo, whose save and quit keys they are, turns that
off (01.01).

### The terminal keeps the picture

A terminal remembers what is on its screen, and a program can only send it
more bytes. There is no way to read the screen back; the one question a
program can ask is where the cursor is, `ESC [ 6 n`. So kilo keeps its own
copy of everything that should be on the screen, and redraws whole screens
from it (02.01).

### The driver works on the way out, too

The driver changes output as well as input. By default it turns every
`\n` a program writes into `\r\n`, so a line feed also goes back to the
first column; that is why `printf 'abc\n'` in a shell starts the next line
at the left edge. kilo turns that off too, and writes `\r\n` itself
wherever it wants a new line, as in every row of the figure above.

## Break it

Switch that output processing off in your shell's terminal, for one
command. `stty -onlcr` stops the driver turning `\n` into `\r\n`, and
`stty onlcr` puts it back:

<!-- verify: skip reason="the lines stair-step by column, and the line-based replay starts every line at column 0. Checked under zsh and bash on a pseudo-terminal" -->
```
$ stty -onlcr; printf 'one\ntwo\nthree\r\n'; stty onlcr
one
   two
      three
$
```

Each `\n` moved the cursor down a row and nothing more, so each line
starts where the last one ended. The last line ends in `\r\n`, the way kilo
ends its rows, and the prompt after it is back at the left edge. With
output processing off, a program has to send the carriage return itself.
