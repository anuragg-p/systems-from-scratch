# 03.01 Kernel traps

`kernelvec` and `kerneltrap` give the hardware somewhere to jump when it
interrupts the kernel, and a way back to exactly where it was.

## Where this fits

![Where 03.01 fits](figures/03.01-map.svg)

Traps are how the outside world gets into the kernel. Below this layer is
the hardware, which can stop whatever a hart is doing and jump somewhere
else. Above it, the timer, every device, and later every system call and
every fault in a user program arrive through a trap. Until now nothing could
interrupt the kernel, and a fault in it went nowhere: the machine just went
silent. After this lesson an interrupt in the kernel is handled and
returned from, and a bug in the kernel prints a panic instead of silence.

## The idea

![`kernelvec` pushes the caller-saved registers at fixed offsets; `tp` goes in but never comes back out.](figures/03.01-kernelvec-frame.svg)

Module 03 opens the kernel to the outside: this lesson is the entry point
for traps taken while the kernel runs, 03.02 makes the timer interrupt every
hart ten times a second, and 03.03 routes device interrupts so the keyboard
works.

A **trap** is the hardware forcing a jump out of the code that is running.
Interrupts (the timer, a device), exceptions (a bad address, an illegal
instruction) and system calls are all traps. When one happens, the hardware
does very little. It records where the hart was in **`sepc`** and why in
**`scause`**, notes in **`sstatus`** the mode it came from (bit SPP) and
whether interrupts were on (bit SPIE), turns interrupts off, and jumps to
the address in **`stvec`**. The instruction **`sret`** undoes exactly that:
back to the address in `sepc`, in the mode SPP names, with interrupts on
again if SPIE says they were. For an interrupt, `sepc` is the instruction
that had not run yet; for an exception, it is the instruction that failed.

Here is why that is not enough. Suppose a timer interrupt arrives in the
middle of `kalloc`, with the address of the free list sitting in register
`a5`. The handler is C code, and C code uses `a5` as it likes. When `kalloc`
resumes, its pointer is garbage. The interrupted code cannot protect itself:
it never knew the interrupt happened.

So the handler's first job is to save the registers C code may overwrite,
and its last job is to put them back exactly as they were, then return to
the interrupted instruction. In between it can find out what happened and
deal with it.

### `kernelvec`

`kernel/kernelvec.S:kernelvec` is where `stvec` points while the kernel runs,
so it is the first code to run after any trap in the kernel. It has to be
assembly, because it runs before anything is saved: it pushes the registers
on the current stack, calls `kerneltrap`, pops them, and returns to the
interrupted instruction with `sret`. `trapinithart` puts its address in
`stvec` on every hart; the rest of the lesson's plumbing is a read and a
write function in `riscv.h` for each register named above.

### `kerneltrap`

`kernel/trap.c:kerneltrap` is the C half: it finds out what the trap was
and deals with it. An exception in the kernel is a bug, so for one of those
it prints the three registers that describe it and panics.

## How it works

### Writing `kernelvec`, step by step

1. **Save, call, restore, return.** The bare `call kerneltrap` followed by
   `sret` breaks at once: `call` overwrites `ra`, and the C code overwrites
   any registers it likes, so the interrupted code resumes with garbage in
   them. So make a frame on the current stack, store the registers in it,
   call, load them back, and give the frame back before `sret`.
   ```
   kernelvec:
           addi sp, sp, -256
           sd ra, 0(sp)
           ...
           call kerneltrap
           ld ra, 0(sp)
           ...
           addi sp, sp, 256
           sret
   ```
   There is no need to switch stacks: a trap taken in the kernel is already
   on a kernel stack. The 256 bytes are 32 slots of 8, one per register,
   which also keeps `sp` a multiple of 16 as the calling convention wants.
   The `.align 4` above the label matters too: `stvec` uses its two low
   bits to choose a mode, so the address it holds must have them clear.
2. **Save what C may clobber.** A C function may overwrite `ra`, `t0`-`t6`
   and `a0`-`a7`; `gp` and `tp` are saved as well, though compiled C never
   touches them. Register xN goes in slot (N - 1) * 8: `ra` is x1, `gp` x3,
   `tp` x4, `t0`-`t2` x5-x7, `a0`-`a7` x10-x17, `t3`-`t6` x28-x31. The `s`
   registers are left out on purpose: the calling convention makes
   `kerneltrap` put them back itself. Slot 8 would be `sp` (x2), which is
   put back by arithmetic instead.
3. **Do not load `tp` back.** It holds the hart's number (lesson 01.02). From
   lesson 04.04 on, the interrupted code may resume on a different hart, and
   an old `tp` would make that hart believe it was another one.

### Writing `kerneltrap`, step by step

1. **Ask what happened.** `devintr()` reads `scause` and handles the
   interrupts this module adds: a timer tick (lesson 03.02) returns 2, a
   device (lesson 03.03) returns 1. A 0 means an exception in the kernel, a
   bad pointer or an illegal instruction, which is a bug: `unexpected`
   prints `scause`, `sepc` and `stval` and panics.
   ```
   uint64 scause = r_scause();
   ...
   if((which_dev = devintr()) == 0){
     if(unexpected(scause, &sepc)){
       ...
     }
   }
   ```
   Here `unexpected` never returns. The inner `if` is room for a kernel
   that expects some exceptions and resumes after them at a new `sepc`;
   this one expects none.
2. **Check the trap belongs here.** Panic unless it came from supervisor
   mode with interrupts off. A trap from a user program arriving here
   would mean `stvec` was left pointing at the wrong code. Interrupts are
   off on the way in and `kerneltrap` never turns them on, so one trap
   never interrupts another halfway.
   ```
   if((sstatus & SSTATUS_SPP) == 0)
     panic("kerneltrap: not from supervisor mode");
   ```
3. **Keep `sepc` and `sstatus`.** Read them first thing, write them back
   last. Nothing needs it yet; from lesson 04.04 other processes can run in
   the middle of `kerneltrap`, their traps overwrite both registers, and
   without the write-back `sret` would return into someone else's code.

**The invariant:** when `sret` runs, every register and the interrupted pc
and mode are exactly as they were when the trap hit.

How `devintr` tells the cases apart, from the `scause` register:

![Bit 63 of `scause` splits interrupts from exceptions, and `devintr` turns the code into 2, 1 or 0.](figures/03.01-scause.svg)

(The store sits at 0x80000302 now, because the kernel lost a few

instruction that failed. The store runs again, faults again, and the hart
goes round that loop forever, as busy as it can be and printing nothing.
Returning does not cure an exception; that is why `kerneltrap` panics
instead. Take the store out of `main.c` when you are done.

The invariant itself takes longer to break visibly. Make the final
`addi sp, sp, 256` in `kernelvec.S` 248, so every trap returns with `sp`
8 bytes low. Nothing returns from a trap at this lesson. In the next few,
a tick only ever interrupts an idle loop that never returns, so the stack
just creeps down, 8 bytes a tick, until it runs off its slice. The damage
shows at once when processes run, in the 07.02 build: make the change in
`build/at/xv6/07.02/kernel/kernelvec.S` and run `./learn run xv6 --at 07.02`:

<!-- verify: patch at=07.02 file=kernel/kernelvec.S


An interrupted function, when it returns, loads its return address from
8 bytes too low, the slot where it saved its frame pointer, which is an
address on the stack. The stack is not executable, so the jump faults:
`scause` 0xc, an instruction page fault, with `sepc` equal to `stval`
because the faulting address is the pc. 0x8001a9b8 is in hart 0's slice
of `stack0`; other runs fault in another hart's slice, or on a process's
kernel stack.

## Decide the boundary

xv6 has two entry points: `kernelvec` for traps taken in the kernel, and
`uservec` (06.01) for traps from user space. A trap from the kernel needs no
stack switch and no page-table switch. A trap from user space needs both.

Another kernel could have one entry that always switches stacks, and handle
both cases the same way. Linux has a single entry path that checks where it
came from. That is one path to read and get right, and the kernel-mode case
pays for checks it does not need.

xv6 chose two because the cases differ. How different is a trap in the kernel
from a trap in a process, and is that worth two code paths?
