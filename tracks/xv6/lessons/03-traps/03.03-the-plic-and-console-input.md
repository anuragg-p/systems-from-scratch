# 03.03 The PLIC and console input

`plic_claim`, `plic_complete` and `consoleintr` carry a key pressed at the
terminal into the kernel, where it waits in a line buffer until a program
reads the whole line.

## Where this fits

![Where 03.03 fits](figures/03.03-map.svg)

This lesson connects the devices to the trap layer, and finishes the console
driver with its input half. Below it, the serial port and the disk signal an
interrupt controller, which passes the interrupt on to a hart. Above it, the
shell will sleep in a read until a whole line has been typed. After this
lesson the kernel knows which device interrupted it, and you can type at
it, mistakes and all.

## The idea

![One register, read to claim and written to complete. Between the two, the PLIC holds line 10 back.](figures/03.03-claim-complete.svg)

Type `ecoh`, notice the typo, press Backspace twice, type `ho`, press Enter.
The shell must receive `echo` and a newline, once, and nothing before the
Enter. Two problems stand between the key and the shell.

The first is knowing a key arrived at all. Devices do not interrupt a hart
directly. Each one raises a numbered line into the **PLIC**, the
platform-level interrupt controller, which interrupts a hart. All the hart
learns from the trap is "some device". So it asks the PLIC which one: that
is a **claim**. It handles that device, then tells the PLIC it is done: a
**complete**. Until then, the PLIC holds that device's next interrupt back.

The second is editing. Characters arrive one interrupt at a time, but a
program wants whole, corrected lines. So the kernel keeps the line being
typed in a buffer of its own, where Backspace can still take characters
back, and hands the line to the reader only when Enter arrives.

### `plic_claim` and `plic_complete`

`kernel/plic.c:plic_claim` and `kernel/plic.c:plic_complete` are the two
halves of that conversation with the PLIC. The trap code calls the first to
learn which device interrupted, runs that device's handler, and calls the
second with the same number when it is done.

### `consoleintr`

`kernel/console.c:consoleintr` is the line editor. The serial port's
interrupt handler calls it once for every byte you type. It echoes the
character, applies Backspace and the other editing keys, and when a line is
finished, publishes it for whoever reads the console. The reader comes with
lesson 05.07; waking a reader that is already waiting comes with sleeping
and waking, in lesson 04.03.

## How it works

### Writing `consoleintr`, step by step

1. **Store, echo, publish.** The simplest version appends each character at
   `e` and echoes it, so you can see what you typed. When a character ends
   the line, it moves `w` up to `e`: a reader must not see half a line that
   may still be edited.
   ```
   consoleintr(int c)
   {
     ...
     consputc(c);
     cons.buf[cons.e++ % INPUT_BUF_SIZE] = c;
     if(c == '\n' || c == C('D') || cons.e-cons.r == INPUT_BUF_SIZE){
       cons.w = cons.e;
     }
     ...
   }
   ```
   The positions only ever count up; `% INPUT_BUF_SIZE` turns one into a
   place in the 128-byte buffer.
2. **Enter sends a carriage return.** Terminals send `\r` for Enter, not
   `\n`. Without turning one into the other before storing it, no line would
   ever end, and the shell would wait forever.
3. **A full buffer.** Store a character only while `cons.e - cons.r` is below
   the buffer size, or new typing would overwrite input not yet read. A
   buffer that fills up is published as if it were a line (the third
   condition in step 1), so a reader can drain it.
4. **Erase, and keys that are not input.** The editing keys get cases of
   their own. Control-H and Delete move `e` back one place and echo a
   backspace, but only while `e != w`: everything before `w` already belongs
   to the reader. Control-U does the same back to the start of the line, and
   Control-P stores nothing (lesson 04.01 makes it print the process table).
   ```
   case C('H'): // Backspace
   case '\x7f': // Delete key
     if(cons.e != cons.w){
       cons.e--;
       consputc(BACKSPACE);
     }
   ```
5. **The lock.** All of it runs under `cons.lock`, because the reader
   (lesson 05.07) runs on another hart, moving `r` and copying out of the
   same buffer at the same time.

### Three positions in one buffer

Storing and erasing are one idea. `r` is where the reader reads next, `w`
the end of the last finished line, and `e` where the next typed character
goes. The characters between `w` and `e` are the line still being typed.
Backspace only moves `e`, never past `w`, so a line already handed over can
never be erased; Enter moves `w` up to `e`, and in that moment the line
becomes readable.

![Typing moves `e`, erasing moves it back, and Enter moves `w` up to `e` so the line becomes readable.](figures/03.03-cons-buf.svg)

### Claim and complete: one register, two meanings

`plic_claim` and `plic_complete` are one line each, so there is nothing to
walk through, only a point to notice. They use the same PLIC register for
this hart. Reading it is the claim: it returns the device's number and, as
a side effect, marks it in service. Writing the same number back is the
complete, and only then does the PLIC pass that device's next interrupt on.

Before any of that, the PLIC has to be told which interrupts to pass on at
all. A device gets through to a hart only if its priority is above zero
(`plicinit` gives the UART priority 1; the priorities are one 32-bit word
per device, so the UART's, device 10, is at `PLIC + 10*4`), its bit is set
in that hart's enable word, and its priority is above that hart's
threshold. `plicinithart` sets the enable bit and a threshold of 0 on every
hart, so whichever hart is free can take the interrupt. The price is that
all three are told, and two may claim the same one. The PLIC gives the
number to the first and 0 to the others, who then have nothing to do and
nothing to complete.

### The UART side

Between `devintr` and `consoleintr` sits the serial port's own handler,
`uartintr`. Its receive half loops on `uartgetc` until it returns -1,
because the UART holds incoming bytes in a small queue and several may be
waiting by the time the interrupt is taken; each one goes to `consoleintr`.

`uartinit` turns on two interrupts: one for a byte received, and one for
"ready to send", which the UART raises whenever it has nothing left to
send, typed keys or not. The transmit half is here to answer that second
one. Nothing fills its buffer until processes write to the console (05.07),
so for now `uartstart` finds it empty and reads the `ISR` register, which
is what tells the UART the interrupt was seen.

### End of file is a character too

Control-D is stored like any other character and publishes the line just as
Enter does, so the reader can see where it was. When the read of lesson
05.07 reaches it, the read returns 0 bytes, and 0 bytes is what "end of
file" means to a Unix program.
(A read that has already collected some characters returns those first and
leaves the Control-D for the next read.)

**The invariant:** the interrupt handler never blocks and never sleeps. It
only edits the buffer, under the console's lock, and (from 04.03) wakes the
reader. The echo does spin, waiting for the UART to take each character,
but that wait is bounded by the hardware; waiting for another process to
do something is what a handler may never do.

## Break it

In `plic_complete`, delete the store, so the function does nothing. Boot,
and type `echo one` and Enter:

<!-- verify: patch file=kernel/plic.c
-  *(uint32*)PLIC_SCLAIM(hart) = irq;
-->
<!-- verify: session run="./learn run xv6 --at 03.03" hangs
lines 4-5 unordered
-->
```
...
xv6 kernel is booting

hart 2 starting
hart 1 starting
```

The boot reaches the hart lines as before, and then nothing you type
appears, not even the first key. The UART's first interrupt is a "ready to
send" one, raised as soon as the boot messages are out, before you touch
the keyboard. The kernel claims it and never completes it, so the PLIC
treats the UART as still being served and passes on nothing more from it,
keys included. The disk goes the same way: in the 07.02 build, the first
that reads the disk, this change stops the boot after the hart lines, before
`init: starting sh`. The disk's first interrupt is claimed and never
completed, so the read after it never finishes.

## Decide the boundary

xv6 does all line editing in the kernel, inside the interrupt handler:
`consoleintr` handles erase and kill before the shell sees anything. Another
system could hand the raw characters to a process and let it edit, as raw-mode
programs do; the shell would then need its own editor. Unix settled on the
kernel doing it by default, in the terminal driver, with a mode to turn it off.
The cost of the kernel doing it: the interrupt handler holds a lock and runs a
loop for every key, and the line discipline is fixed and tiny.

What decides it is who owns the policy for what Backspace means.
