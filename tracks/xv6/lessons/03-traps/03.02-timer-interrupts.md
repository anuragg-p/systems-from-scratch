# 03.02 Timer interrupts

`timerinit` and `clockintr` make every hart's clock interrupt it ten times a
second, so the kernel gets the CPU back whether or not the running code ever
gives it up.

## Where this fits

![Where 03.02 fits](figures/03.02-map.svg)

The trap entry from the last lesson gives interrupts somewhere to land; this
lesson makes the first ones arrive, on a schedule. Below it is the clock
built into every hart. Above it, the scheduler will use this tick to take
the CPU away from a process that never stops, and programs that sleep for a
while will count it. After this lesson the kernel has a heartbeat and a
clock.

## The idea

![`time` climbs steadily; each `clockintr` moves `stimecmp` 1000000 counts past now, which also lowers the interrupt.](figures/03.02-stimecmp.svg)

Picture a user program that does `for(;;);`. It never makes a system call
and never waits for anything, so it never enters the kernel on its own. If
the only way into the kernel were the program's own choice, that hart would
belong to the loop forever, and so would the machine if three such programs
ran.

The one thing a running program cannot refuse is an interrupt. So each hart
sets an alarm: a deadline on its clock. When the clock passes it, the hart
traps into the kernel, and the kernel sets the next deadline before it
returns. The kernel is now guaranteed to run again, on every hart, at a
steady rate.

The clock is a counter called `time` that QEMU advances 10 million times a
second. A deadline 1,000,000 counts ahead is a tenth of a second away, so
each hart is interrupted ten times a second: one **tick**.

An interrupt has three gates to pass before a hart takes it. The source
must be pending: for the timer, `time` has passed the deadline. The hart
must accept that source: its bit in `mie`, of which `sie` is supervisor
mode's view, so the timer bit 01.02 set in `sie` and the one this lesson
sets in `mie` are the same switch. And interrupts must be on at all: bit
SIE in `sstatus`, which `intr_on` sets. That is why the first deadline can
be armed during boot, long before `kernelvec` is installed: the timer may
go pending early, but nothing is taken until `main` reaches `intr_on` in its
last loop.

### `timerinit`

`kernel/start.c:timerinit` arms the alarm on each hart, once, during boot.
It runs in machine mode, because the switches it has to flip can only be
set there, and it sets the first deadline. This lesson adds the call to it
in `start`, at the spot lesson 01.02 left for it, before the `mret`.

### `clockintr`

`kernel/trap.c:clockintr` runs on every tick, called by the trap code when
the cause is the timer. It counts the tick and sets the next deadline.
(Waking anyone who waits on the clock comes with lesson 04.03.) The new
`trapinit` call in `main` only sets up the lock that guards the count.

## How it works

### The deadline is a supervisor register

Older RISC-V machines keep the deadline in a memory-mapped timer block that
only machine mode may write, which is why classic xv6 needs a machine-mode
interrupt handler that forwards every tick to the kernel. This kernel uses
the **Sstc** extension instead, which adds a register, `stimecmp`, that
supervisor mode can write directly. Machine mode only has to unlock it,
once: that is what `timerinit`'s three switches do (let the interrupt
through, turn Sstc on, and let supervisor mode read `time`, which is bit 1
of `mcounteren`).

### Only hart 0 counts

All three harts take a tick ten times a second, but `ticks` is the kernel's
wall clock, so it must go up once per tick, not three times. Only hart 0
increments it. It still does so under a lock (lesson 02.03), because one
writer is not the whole story: other code reads `ticks`, and from lesson
04.03 on, whatever sleeps waiting for the clock checks it under that same
lock, and hart 0 wakes it there.

### Setting the next deadline is what stops the interrupt

The timer interrupt is not something that fires once and is gone. It stays
raised for as long as `time` is past `stimecmp`. Writing a new deadline in
the future is therefore the only thing that lowers it. Every hart does this
on every tick.

**The invariant:** after every timer interrupt, `stimecmp` is in the future.

The new deadline is counted from now, not from the old deadline. A tick that
ran late pushes the schedule back a little, instead of leaving a pile of
missed ticks to fire one after another.

In `build/at/xv6/03.02/build/kernel/kernel.asm` that address is inside
`kerneltrap`. Ask a few more times and each hart is in `kerneltrap`, in
`devintr`, or at the `wfi` it keeps returning to.

The hart lines still print because interrupts come on only in `main`'s last
loop. From then on the first timer interrupt is never cleared. `stimecmp`
still holds the old deadline, `time` is already past it, and the interrupt
is pending again the moment `sret` re-enables interrupts. The hart takes the trap, runs `clockintr`,
returns, and is interrupted again, endlessly; there is no time left for the
real work. The deadline in `stimecmp` is not a hint but the only way the
interrupt gets turned off.

![With `stimecmp` left in the past, the interrupt stays pending and the hart does nothing but take it.](figures/03.02-never-cleared.svg)

## Decide the boundary

xv6 asks for a fixed tick: one interrupt every 0.1 s on every hart, whether
anything is waiting or not. It is the simplest way to keep time and to
preempt.

Another kernel could run **tickless**: set `stimecmp` only to the next thing
that needs a wakeup, the nearest sleeper's deadline or the end of the running
process's slice, and let an idle hart sleep without being interrupted. Linux does
this, saving power on idle machines and paying with timer-queue code. A
periodic tick wakes every hart ten times a second for nothing.

For a teaching kernel on QEMU, power is no concern. What decides it is whether
idle CPUs have to stay asleep.
