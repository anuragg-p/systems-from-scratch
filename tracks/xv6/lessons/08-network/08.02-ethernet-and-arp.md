# 08.02 Ethernet and ARP

The Ethernet layer puts addresses on frames, and ARP finds out which card on the
network answers to a given IP address.

## Where this fits

![Where 08.02 fits](figures/08.02-map.svg)

The card driver can move frames, but every frame needs a destination written on
it, and that destination is the address of a card, not of a host. Everything above
this layer knows the other end only by its IP address. This layer sits on the card
driver and under IP: it wraps outgoing packets in a frame addressed to the right
card, and sorts incoming frames by what they carry. After this lesson xv6 can find
any machine on its local network, and answer when a machine asks about xv6.

## The idea

![The ARP request xv6 sends before its first DNS query, byte by byte as it left the card: 42 bytes, Ethernet header then ARP packet.](figures/08.02-arp-packet.svg)

An Ethernet frame starts with a 14-byte header: the card it is for, the card it is
from, and a number saying what is inside, an IP packet or an ARP packet. A card
keeps only the frames addressed to it, or to the **broadcast** address
ff:ff:ff:ff:ff:ff, which reaches every card on the network.

xv6 lives on a small network that QEMU makes up. xv6 is 10.0.2.15; the host
machine, and the gateway to everything beyond it, is 10.0.2.2; QEMU answers DNS
questions at 10.0.2.3. QEMU plays both of those hosts itself, and gives each a
made-up card address: 52:55 followed by its IP address.

To send a DNS question to 10.0.2.3, xv6 must write a card address in the
header, and nothing in "10.0.2.3" says which card it is. IP addresses name hosts;
Ethernet addresses name cards on one network. Something has to connect the two.

**ARP**, the Address Resolution Protocol (RFC 826), does it the direct way: it
asks everyone. xv6 broadcasts "who has 10.0.2.3? tell 10.0.2.15". Every card hears
it, and the one host that owns 10.0.2.3 replies to xv6 alone: "10.0.2.3 is at
52:55:0a:00:02:03". xv6 writes that down, and from then on sends straight to that
card without asking again.

The same thing happens the other way round. When QEMU wants to deliver a packet to
xv6, it asks who has 10.0.2.15, and xv6 must answer with its own card's address,
52:54:00:12:34:56, or nothing can reach it.

### eth_send

Every packet leaving xv6 passes through here on its way to the card. It writes the
Ethernet header, to, from and what is inside, in front of the packet, and hands
the whole frame to the driver.

### net_rx

Every frame that arrives enters the network stack here, called from the card's
interrupt handler; this lesson adds that call to `virtio_net_intr` (08.01). It
throws away frames meant for another card and sends ARP packets to `arp_rx`. IP
packets are dropped for now: the branch that sends them up to the next layer
comes with 08.03.

### arp_rx

This is xv6's half of the conversation when someone else asks or answers. It
learns addresses from the ARP packets it sees, and replies at once when the
question is about xv6.

### arp_resolve

IP calls this before it sends anything (08.03): give me the card for this
address. If the answer is already known it returns at once; if not, it asks the
network and waits for a reply, for up to three seconds.

## How it works

### Writing net_rx, step by step

1. **Start with the easy case: a frame for this card.** Step past the 14-byte
   header and send the rest where its type says. The type is big-endian on the
   wire, so it is read through `ntohs`.
   ```
   void
   net_rx(char *frame, int len)
   {
     ...
     char *payload = frame + sizeof(struct eth);
     len -= sizeof(struct eth);
     switch(ntohs(eth->type)){
     case ETHTYPE_ARP:
       arp_rx(payload, len);
       break;
     }
   }
   ```
   Anything else, IPv6 for instance, falls through and is dropped. From 08.03 on IP
   gets its own case.
2. **Drop frames too short to have a header,** before reading one.
3. **Drop frames for other cards.** A broadcast reaches every card, and on a shared
   cable so does everything else; keep only what is addressed to this card or to
   the broadcast address.

### Writing arp_rx, step by step

1. **Start with the case that must work: a question about xv6.** Read the two IP
   addresses and answer straight to the asker's card. Without this reply nothing on
   the network can reach xv6.
   ```
   void
   arp_rx(char *pkt, int len)
   {
     ...
     uint32 sip = ntohl(a->sip);
     uint32 tip = ntohl(a->tip);
     ...
     if(tip == MYIP && ntohs(a->op) == ARP_REQUEST)
       arp_send(ARP_REPLY, a->sha, a->sha, sip);
   }
   ```
2. **Check that it is a whole ARP packet for IPv4 over Ethernet.** ARP can carry
   other kinds of addresses, with other lengths; reading one of those as ours would
   take garbage for addresses.
3. **Ignore a sender of 0.0.0.0.** A host checking whether an address is free sends
   a probe with no sender address of its own (RFC 5227); there is nothing to learn
   from it.
4. **Learn under the cache lock, and answer after it.** Refresh a sender already
   known, and add the sender if the packet is about xv6. The reply goes out only
   after the lock is released, so no lock is held while the frame is copied to the
   card.
   ```
   acquire(&arpcache.lock);
   if(tip == MYIP || arp_find(sip))
     arp_insert(sip, a->sha);
   release(&arpcache.lock);
   ```

### Writing arp_resolve, step by step

1. **Start with the common case: the answer is cached.** Every IP send passes
   through here, and almost every time the address is already known. Look, copy it
   out, return 0; the loop around it is for the times it is not.
   ```
   int
   arp_resolve(uint32 ip, uint8 *mac)
   {
     for(int t = 0; ; t++){
       acquire(&arpcache.lock);
       struct arpent *e = arp_find(ip);
       if(e){
         memmove(mac, e->mac, ETHADDR_LEN);
         release(&arpcache.lock);
         return 0;
       }
       release(&arpcache.lock);
       ...
     }
   }
   ```
2. **Ask, ask again every second, and give up after three.** A request or a reply
   can be lost, and without the repeat a single lost frame would cost the full
   three seconds. `ARP_RETRY` and `ARP_WAIT` count clock ticks, ten a second
   (03.02).
   ```
   if(t % ARP_RETRY == 0)
     arp_send(ARP_REQUEST, broadcast, zeroes, ip);
   ```
3. **Sleep one tick between looks.** `tick_wait` returns -1 if the process has been
   killed meanwhile, so a killed sender does not wait out the three seconds.
4. **Hold no lock while sending or sleeping.** The cache lock is released before
   the request goes out and before the sleep, because `arp_rx` needs that lock to
   store the very answer this loop is waiting for.

### Why it is built this way

**Headers are written in front, not copied.** Every layer above leaves 14 free
bytes in front of its packet, so `eth_send` writes the Ethernet header in place.
Nothing is copied until the driver copies the finished frame into the card's
buffer.

**Learn from the questions too.** RFC 826 does not only answer; it learns, and
`arp_rx` follows it. An ARP packet from a host already in the cache refreshes that
entry. A packet about xv6, question or answer, adds its sender, because that host
is about to talk to xv6. That is how the cache in Run it came to hold 10.0.2.2. A
question about some other host teaches nothing, so on a busy network the cache
does not fill up with every machine that ever asked anything.

![Both directions. xv6 asks for 10.0.2.3 before its first DNS query; QEMU asks for 10.0.2.15 before it delivers the host's datagram, and xv6 learns 10.0.2.2 from the question.](figures/08.02-exchange.svg)

**Wait on the clock, not on the answer.** When the address is unknown,
`arp_resolve` must wait, but for what? Sleeping until a reply arrives would need
the reply to wake it, and if no reply ever comes, nothing ever would. The one event
sure to come is the clock (03.02). So it sleeps one tick at a time and looks at the
cache again, asks again every second in case the question was lost, and gives up
after three seconds.

**The receive side never waits.** `net_rx` and `arp_rx` run inside the card's
interrupt handler, where there is no process to put to sleep. `arp_rx` may send a
reply, since sending never waits (08.01), and it lets go of the cache's lock before
it does, so no lock is held while the frame is copied to the card.

**The cache trusts forever.** It holds eight addresses, replaces the oldest when
full, and never forgets one. Eight is room to spare on QEMU's network, which has
two other hosts, and enough for the few neighbours a small LAN has; a packet for
anywhere farther goes to the gateway's card. Never forgetting is safe on QEMU's
network, where addresses never change, and wrong on a real one, where a host can
swap its card and keep its IP.

Besides the protocol structures, `net.h` gets xv6's own address and the gateway
and netmask that IP uses from 08.03 on, and the byte-order helpers: every field
on the wire is big-endian, and RISC-V is little-endian.

**Invariant:** a frame xv6 sends as an IP packet is addressed to a card that
answered for that IP address; nothing above `arp_resolve` ever guesses one.

One question per datagram, no answer, and neither `hello` ever reaches the card:
QEMU will not deliver to an address nobody claims, so it throws them away. xv6
still learns 10.0.2.2 from each question; it just never says so. Once xv6 starts
asking questions of its own, QEMU learns xv6's card from them the same way, and
the failure gets subtler: hosts xv6 has spoken to can reach it, strangers cannot.

## Decide the boundary

xv6 makes the sending process wait for the ARP answer, up to three seconds,
inside `sendto` (08.04). Linux queues the packet on the unresolved neighbour
entry instead, returns from `sendto` at once, and sends the packet when the
reply arrives, or drops it if none does. Waiting is the simplest thing that
works; queueing means `sendto` never blocks on the network, at the cost of a
queue per unknown neighbour and a timer to empty it. Who should wait for an
answer from the LAN: the program that asked to send, or the kernel on its behalf?
