# 08.05 A DNS lookup

`nslookup` turns a name into IPv4 addresses by asking a DNS server: it builds one
question, sends it, and reads the answer.

## Where this fits

![Where 08.05 fits](figures/08.05-map.svg)

With sockets a user program can send and receive datagrams, and this is the first
program that does something useful with them. People use names and the network
moves numbers, so before anything can reach a named machine, someone has to say
which address that name stands for, and the only one who knows is a server
outside this machine. The lookup is a user program on top of sockets; nothing in
the kernel changes for it. After this lesson xv6 can turn a name into an address,
with an answer that comes from the real internet.

## The idea

![The 29 bytes nslookup example.com sends to 10.0.2.3, port 53: a 12-byte header, then the question. Offsets count from the start of the UDP data.](figures/08.05-query.svg)

The **Domain Name System** maps names to records: addresses, aliases, mail
servers. Finding an answer can take many steps, from the root servers down through
`com` to the servers that know `example.com`, and that work is done by a
**recursive resolver**. `nslookup` does none of it. It is a **stub resolver**: it
sends one question to one resolver, sets the flag that says "recursion desired, do
all of it for me", and waits. The resolver at 10.0.2.3 is QEMU, which passes the
question on to the resolver your host uses and sends the answer back as if it were
its own.

A DNS message (RFC 1035) is a 12-byte header, then the question, then any answer
records. The header carries an **id** the asker picks and the answer copies, so the
two can be matched, some flags, and a count of each kind of record. The question is
a name, the type of record wanted (A, an IPv4 address) and the class (IN, the
internet).

Names are not sent with dots. Each part goes as a length byte followed by that
many characters, and a 0 byte ends the name: `www.mit.edu` is 3 w w w 3 m i t 3 e
d u 0. A reader always knows where each part ends without searching for anything.

The answer can hold more than addresses. `www.mit.edu` comes back as two aliases,
CNAME records saying "that name is really this one", followed by the address of
the last one. The lookup keeps the addresses and skips everything else.

### dns_query

This builds the question that goes out: the header, then the name part by part,
then the type and class. It is also where a name like `bad..name` is refused,
before anything is sent.

### dns_answer

This reads what came back. It checks that the message really answers this
question, steps over the question the server repeated, then walks the answer
records and keeps each IPv4 address. The bytes come from outside the machine, so it
trusts no length in them until it has checked it.

## How it works

### Writing dns_query, step by step

1. **Start with a good name.** Write the header, six big-endian 16-bit numbers
   starting with the id and the "recursion desired" flag; then one label per part
   of the name; then the 0 byte that ends it, the type and the class.
   ```
   int
   dns_query(char *name, int id, uchar *msg)
   {
     put16(msg, id);
     put16(msg + 2, DNS_RD);
     ...
     while(*s){
       ...
       msg[off++] = n;
       memmove(msg + off, s, n);
       off += n;
       ...
     }
     msg[off++] = 0;
     ...
     return off + 4;
   }
   ```
2. **Find each part by the next dot, and allow a trailing one.** After each part
   the loop steps over one dot, so `mit.edu.` simply ends at the end of the string.
3. **Refuse bad parts, and queries that would not fit.** A part shorter than 1 or
   longer than 63 characters, or one that would push the query past 512 bytes with
   the 5 bytes still to come, returns -1 before anything is sent. 512 bytes is the
   largest DNS message UDP may carry (RFC 1035); anything bigger needs TCP.
   ```
   if(n < 1 || n > 63 || off + 1 + n + 5 > MAXMSG)
     return -1;
   ```
4. **Refuse an empty name.** If no label was written, there is nothing to ask.

### Writing dns_answer, step by step

1. **Start with the part that matters: the answer records.** Walk them one by one,
   step over each record's name and its 10 bytes of type, class, time to live and
   data length, and keep the 4 data bytes of each address. The time to live says
   how many seconds the answer may be kept; `nslookup` keeps nothing, so it never
   reads it.
   ```
   int
   dns_answer(uchar *msg, int len, int id, uint *addrs, int max)
   {
     ...
     for(int i = 0; i < ancount; i++){
       off = skipname(msg, len, off);
       ...
       int rdlen = get16(msg + off + 8);
       off += 10;
       ...
       off += rdlen;
     }
     return n;
   }
   ```
2. **Is this the answer to our question?** At least a header, the same id, and the
   response flag set; a stray datagram or an old answer fails here. "No such name"
   is a valid answer with no addresses, so it returns 0.
3. **Step over the questions first.** The server repeats the question before the
   answers, and names have no fixed length, so the only way past it is to skip each
   name and then 4 bytes of type and class.
4. **Check every length before using it.** The fixed part must be there before it
   is read, and the data length comes from the message, so it is checked against
   the message's real length too.
   ```
   if(off < 0 || off + 10 > len)
     return -1;
   ...
   if(off + rdlen > len)
     return -1;
   ```
5. **Keep IPv4 addresses, step over everything else.** A record of type A, class IN
   and 4 bytes of data is an address; anything else, like a CNAME, is skipped by its
   data length.

### Writing nslookup's `main`, step by step

1. **Start with the lookup itself.** Build the question, open a socket on any free
   port, send the question to the resolver, wait for a datagram, and read the
   answer out of it.
   ```
   int
   main(int argc, char *argv[])
   {
     ...
     int len = dns_query(name, id, msg);
     ...
     int fd = socket(0);
     ...
     if(sendto(fd, msg, len, DNS_SERVER, DNS_PORT) != len){
       ...
     }
     ...
       len = recvfrom(fd, msg, sizeof(msg), &src, &sport);
     ...
     int n = len < 0 ? -1 : dns_answer(msg, len, id, addrs, MAXADDR);
     ...
   }
   ```
2. **Pick an id.** Any number will do, as long as it changes from one lookup to the
   next: it is what lets `dns_answer` tell the answer to this question from a stray
   one, or from a late answer to an earlier lookup. `nslookup` mixes its pid with
   the clock.
3. **Wait for the server, not for anyone.** A datagram from another address or
   port is not the answer, so the program reads again.
   ```
   do {
     len = recvfrom(fd, msg, sizeof(msg), &src, &sport);
   } while(len >= 0 && (src != DNS_SERVER || sport != DNS_PORT));
   ```
4. **Set an alarm before sending, and stop it after.** Without it a lost question
   would leave `nslookup` waiting for ever; the alarm is a child process, as in
   `udpecho` (08.04).
   ```
   int a = alarm(50, "nslookup: no answer from 10.0.2.3");
   ```

### Why it is built this way

**An empty part is refused.** A part of length 0 can only mean the root, the end of
a name, so `bad..name` would end the name in the middle. `dns_query` refuses any
part shorter than 1 character or longer than 63: the top two bits of a length byte
are kept for pointers (below), which leaves 63 as the longest part. A single
trailing dot, as in `mit.edu.`, is fine.

**Names in the answer point backwards.** Spelling out the name in every answer
record would waste a message that must fit in 512 bytes. So a length byte with its
top two bits set is a **pointer** instead: with the next byte it gives the offset
of the rest of the name. Both records in the answer below name `example.com` with
the two bytes c0 0c, "the name at offset 12", the one in the question. To step
over a name, the reader only needs to know that a pointer ends it.

![The 61-byte answer. Both records name example.com with the two bytes c0 0c: a pointer back to offset 12, where the question spelled it out.](figures/08.05-answer.svg)

**Walk, never jump.** Names have no fixed length, so nothing after the header is at
a known offset. The only way to the answers is through the question, and through
each record in turn, reading each length before using it. **Invariant:** every
byte `dns_answer` reads is at an offset already checked against the length of the
message. A short or garbled message gives "bad answer", never a read past the end.

**"No such name" is an answer, not an error.** The low four bits of the flags are
the response code. 3 means the name does not exist, and the lookup prints
`has no address`; any other non-zero code is a bad answer.

**A deadline built from processes.** UDP never says that a datagram was lost, so a
question without an answer looks just like an answer still on its way. xv6's
system calls have no timeouts, so `nslookup` makes one, the way `udpecho` does: a
child that sleeps 50 ticks, five seconds at ten ticks a second (03.02), prints
`no answer from 10.0.2.3` and kills its parent, which stops waiting on its socket
(08.04). The alarm starts before `sendto`, so that its five seconds cover the
whole exchange, including up to three seconds `sendto` may spend waiting for ARP
(08.02). If the answer comes first, `stopalarm` kills the child and then waits
for it, so that the child does not stay behind as a zombie (06.04).

Read as records from the wrong place, the bytes soon claim a data length that runs
past the end of the message. For `example.com` it is the pointer c0 0c that names
the second answer, read as a length: 49164. The bounds check catches it, and
nothing is read past the end.

Now put the loop back and break the question instead: in `dns_query`, leave out
the 0 byte that ends the name (`msg[off++] = 0;`). Booted with a recording, as in

```
    10.0.2.15.49152 > 10.0.2.3.53: [udp sum ok] 23758+ [|domain]
```

The datagram is fine (`udp sum ok`), but `tcpdump` cannot read the question. The
first byte of the type, 00, now ends the name, so the type and class are read one
byte late and the message ends one byte before the question does. What happens
next is up to the resolver your host uses, since QEMU only passes the question on.
Here it dropped the question without a reply, and after five seconds the alarm
spoke: `nslookup: no answer from 10.0.2.3`. A resolver that answers a garbled
question with an error code gives `bad answer` instead.

## Decide the boundary

`nslookup` asks once, waits five seconds, and remembers nothing. Unix puts the
stub resolver in the C library (`getaddrinfo`) rather than in the kernel or in
each program, and most systems add a caching daemon so a name is asked for once
per time to live, not once per program. Retrying, trying a second server, and
switching to TCP for a big answer all live there too, and none of it ever needed
the kernel. Name lookup is in user space here as well; what, if anything, about
it belongs in the kernel?
