# 08.04 Sockets

A socket is a process's end of the network: a UDP port it owns, and a queue where
datagrams for that port wait until the process reads them.

## Where this fits

![Where 08.04 fits](figures/08.04-map.svg)

IP and UDP can carry a datagram to a port, but so far nothing owns a port, and a
datagram that arrives has nowhere to go. Sockets are the layer between the network
stack and processes. Below them, UDP delivers each datagram from the card's
interrupt; above them, programs use three new system calls to take a port, send,
and wait for an answer. After this lesson a user program can speak UDP, which is
all the DNS lookup of the next lesson needs.

## The idea

![A socket bound to port 2000 with two datagrams waiting, each in its own page. The interrupt handler appends at the tail; a process takes from the head, and sleeps on the socket while the queue is empty.](figures/08.04-queue.svg)

`udpecho 2000` wants to say "I am port 2000; give me whatever arrives there". The
trouble is timing. A datagram for port 2000 arrives in the card's interrupt
handler, at a moment of the network's choosing, when `udpecho` may be busy or
asleep. Something has to catch it and hold it until `udpecho` asks.

That something is the socket: a port number and a queue. The interrupt side
appends each datagram for the port to the queue, and wakes whoever is waiting. The
process side takes the oldest one off, and sleeps when there is none. It is the
shape of a pipe (06.06), with whole datagrams instead of a stream of bytes.

Programs see three calls (`user/user.h`):

```
int socket(int port);
int sendto(int fd, const void *buf, int n, uint ip, int port);
int recvfrom(int fd, void *buf, int n, uint *ip, int *port);
```

`socket` takes a port and returns a file descriptor; `sendto` sends one datagram
to an address and port; `recvfrom` waits for one and says who sent it. An IP
address is just a number here: 10.0.2.2 is 0x0a000202.

### sockalloc

`socket()` calls this to claim a port for a new socket. A port belongs to one
socket at a time, and port 0 means "any free port, I do not care which", which is
what a program that only asks questions wants.

### socksend

`sendto()` calls this to send one datagram. It copies the program's bytes into a
fresh page, leaving room in front for the headers the layers below will write
(08.03), and hands it to UDP.

### sock_deliver

UDP calls this for every datagram that arrives intact, from inside the interrupt
handler: this lesson adds that call at the end of `udp_rx` (08.03). It finds the
socket bound to the destination port, copies the datagram
onto its queue, and wakes the process that may be waiting.

### sockrecv

`recvfrom()` and `read()` on a socket call this. It takes the oldest datagram off
the queue and copies it out to the program, sleeping first if the queue is empty.

### udpecho.c

The first program to use the three calls, and the one Run it drives. Given a port,
`udpecho 2000` is a server: it binds the port and sends every datagram that
arrives straight back to its sender, for ever or, with a count, `udpecho 2000 2`,
for that many. Given an address, `udpecho 10.0.2.2 9000 hi` is a client: it sends
`hi` from a port the kernel picks and prints the reply. A reply may never come,
and no system call here has a timeout, so the client forks a child as its alarm
clock: the child sleeps five seconds (50 ticks, 03.02) and then kills its parent,
unless the parent got its answer first and killed the child.

## How it works

### Writing sockalloc, step by step

1. **Start with the easy case: a free port, a free slot.** Under the lock, take the
   first unused socket and give it the port. The lock is there from the first line
   because two processes asking for port 2000 at the same moment must not both get
   it.
   ```
   struct sock*
   sockalloc(int port)
   {
     ...
     acquire(&socks.lock);
     ...
     for(so = socks.sock; so < socks.sock + NSOCK; so++){
       if(!so->used){
         so->used = 1;
         so->port = port;
         ...
         release(&socks.lock);
         return so;
       }
     }
     release(&socks.lock);
     return 0;
   }
   ```
2. **Refuse a port that is taken,** by checking under the same lock, before any
   slot is touched.
   ```
   if(port == 0 || sock_find(port)){
     release(&socks.lock);
     return 0;
   }
   ```
3. **Pick a port when the caller asked for any.** Try the next port in turn, from
   49152 up and round again, and stop at the first one no socket holds. If the
   whole range is busy, `port` stays 0 and the check above refuses it.
   ```
   uint16 p = socks.nextport;
   socks.nextport = p == 65535 ? EPHEMERAL : p + 1;
   ```

### Writing sock_deliver, step by step

1. **Start with the easy case: someone is listening.** Find the socket, copy the
   datagram into a page, append it at the tail of the queue, and wake the reader.
   ```
   void
   sock_deliver(uint16 port, uint32 src, uint16 sport, char *data, int len)
   {
     ...
     acquire(&socks.lock);
     so = sock_find(port);
     ...
     memmove(d->data, data, len);
     if(so->tail)
       so->tail->next = d;
     else
       so->head = d;
     so->tail = d;
     ...
     wakeup(so);
     release(&socks.lock);
   }
   ```
   The copy cannot wait: the card's buffer is given back as soon as the interrupt
   handler moves on (08.01).
2. **Drop what cannot be kept.** No socket on the port, a queue already 16 long, or
   no page to copy into: three causes, one answer, because an interrupt handler has
   no way to wait for room.
   ```
   if(so == 0 || so->qlen >= SOCKQ || (d = kalloc()) == 0){
     release(&socks.lock);
     return;   // nobody listening, or too much waiting: dropped
   }
   ```
3. **Wake the reader while still holding the lock,** so that the wakeup cannot fall
   between a reader's look at the empty queue and its sleep (see below).

### Writing sockrecv, step by step

1. **Start with the easy case: a datagram is waiting.** Unlink the oldest under the
   lock, then copy it out to the program and free its page. The lock is released
   before the copy, because the datagram is off the queue and belongs to this
   process alone.
   ```
   int
   sockrecv(struct sock *so, uint64 addr, int n, uint64 ipaddr, uint64 portaddr)
   {
     ...
     acquire(&socks.lock);
     ...
     d = so->head;
     so->head = d->next;
     ...
     release(&socks.lock);

     int m = d->len < n ? d->len : n;
     ...
     kfree(d);
     return r;
   }
   ```
   Only `m` bytes go out; the rest of a longer datagram is lost.
2. **Sleep while the queue is empty, under the same lock.** A killed process
   returns -1 instead of sleeping again.
   ```
   while(so->head == 0){
     if(killed(p)){
       release(&socks.lock);
       return -1;
     }
     sleep(so, &socks.lock);
   }
   ```
3. **Copy out the sender and the port only if asked.** A program that passes 0 for
   either does not care, and `read` passes 0 for both.

### Why it is built this way

**One lock covers the check and the sleep.** The reader looks at the queue, finds
it empty, and goes to sleep. If a datagram arrived in between, its wakeup would
find no one asleep and be lost, and the reader would sleep with a datagram waiting.
Both sides take the same lock, and `sleep` lets go of it only once the reader is
asleep (04.03), so the interrupt side cannot slip in between. **Invariant:** a
datagram is on exactly one queue from the moment it is delivered until a reader
takes it, and after that only the reading process touches it.

**The interrupt side drops; the process side sleeps.** An interrupt handler cannot
sleep, so when a socket already holds 16 datagrams, or no socket has the port, the
new one is thrown away. UDP promises nothing more. The process side is the one that
can afford to wait, so it does. Sixteen waiting datagrams absorb a burst while the
reader is busy, and the bound keeps a socket nobody reads from eating memory: at
most 16 pages each, for at most 16 sockets in the whole system, more than the few
programs here ever open.

**A socket is a file descriptor.** The socket lives behind an ordinary open file
(05.07), so `close`, `dup`, `fork` and `exit` treat it like any other: a forked
child shares the socket, and when the last descriptor goes, the port is freed and
anything still queued is thrown away, which is how the killed server's port came
free. `read` on a socket takes one datagram; `write` fails, because a datagram
needs an address and a file write has none.

![From a file descriptor to a socket. fork shares the struct file, and with it the socket; the last close frees the port.](figures/08.04-fd.svg)

**Ports nobody asked for come from the top.** Port 0 is given a free port from
49152 to 65535, the range set aside for that, taken in turn.

**Datagrams keep their edges, one page each.** One `recvfrom` takes exactly one
datagram; if the program's buffer is too small, the rest of that datagram is lost.
Each waiting datagram sits in a page of its own, though it holds at most 1472
bytes of the page's 4096: `kalloc` is the only allocator the kernel has, and a
page per datagram is simpler than anything that packs them.

**Sending holds no lock.** Below `sendto`, IP may have to ask ARP for an address
and wait up to three seconds (08.02). The kernel panics with `sched locks` if a
process sleeps holding a spinlock, and even if it did not, holding the sockets'
lock across that wait would stall every arriving datagram on every socket.

**A killed process stops waiting.** A reader asleep on an empty queue checks
whether it has been killed each time it wakes. That lets `kill` end a process
blocked on a socket, as it ended the background server above, and it is what
`udpecho`'s alarm child relies on.

The rest of the lesson is plumbing: three system call numbers and their entries
in the user library, `sockinit` at boot, a socket case in `fileread` and
`fileclose`, and the call to `sock_deliver` at the end of `udp_rx`.

## Break it

In `sock_deliver` (in `build/at/xv6/08.04/kernel/sock.c`), delete the
`wakeup(so);` line. Boot with `make qemu UDPFWD=2000` and run a server:

<!-- verify: patch file=kernel/sock.c
-  wakeup(so);
-->
<!-- verify: session run="./learn run xv6 --at 08.04" -->
```
$ udpecho 2000 1
udpecho: listening on port 2000
```

Send it `hello` from the host as before. Nothing comes back:

<!-- verify: skip reason="the host's UDP client timing out, run from a second terminal: the verifier has one terminal and sends nothing from the host" -->
```
Traceback (most recent call last):
  File "<string>", line 1, in <module>
TimeoutError: timed out
```

and xv6 prints nothing. Press Control-P for the process list:

<!-- verify: session send=ctrl-p -->
```
1 sleep  init
2 sleep  sh
3 sleep  udpecho
```

The datagram arrived, passed every check, and sits in the socket's queue. The
server sleeps on that socket and nothing will ever wake it: the one call that was
supposed to is gone. A second datagram only joins the first. It is not the race
of 04.03, where a wakeup comes too early; here it never comes at all, and from
outside it looks exactly like a network that delivers nothing.

## Decide the boundary

xv6 has three calls, binds in `socket`, speaks only UDP, and has no options. BSD
sockets, which Linux, macOS and Windows all copied, split the same work into
`socket` (pick a protocol family and type), `bind`, `connect`, `sendto` and
`recvfrom`, add `setsockopt` for limits and timeouts (`SO_RCVBUF`,
`SO_RCVTIMEO`), and `poll` to wait on many sockets at once. Each split serves a
case xv6 cannot express: a socket that sends before choosing its port, one that
talks TCP, one server waiting on a socket and a pipe together. Plan 9 went the
other way and made the network a file system, where a connection is a directory
under `/net` that you read and write. Without timeouts, an xv6 program that
wants one builds it from processes, as `udpecho` does. What does a program need
from the kernel to use the network, and what is better built in user space on
top of a few calls?
