# 08.03 IPv4 and UDP

IPv4 and UDP carry a datagram from a port on one host to a port on another, with a
checksum at each layer to catch damage on the way.

## Where this fits

![Where 08.03 fits](figures/08.03-map.svg)

Ethernet gets a frame to the next card on the local network, and no further. A
datagram needs more: an address that names the final host, even one far beyond the
local network, and a number that names one program on that host. These two layers
sit on Ethernet and ARP, which they use to reach the next card, and under sockets,
which hand their datagrams to processes. After this lesson the kernel can address
a datagram to a port on any host, near or far, and check the ones that arrive.

## The idea

![A DNS query to 10.0.2.3 after its Ethernet header: 20 bytes of IPv4 header, 8 of UDP, then 29 bytes of data. Offsets count from the start of the IP header.](figures/08.03-headers.svg)

A DNS question has to reach port 53 on 10.0.2.3, and its answer has to come back
to the program that asked, not to another one running beside it. Two headers in
front of the data make that happen, one for each problem.

The **IP** header (RFC 791) gets the packet to the right host. It holds the two
addresses, the total length, what kind of packet is inside (17 for UDP), a TTL that
each router lowers by one so a packet caught in a loop eventually dies, and a
checksum of the header itself.

IP may also cut a packet that is too big for some network on the way into
**fragments**, each with its own IP header, for the receiver to put back together;
the header's id field says which packet a fragment belongs to. xv6 neither cuts
nor reassembles: it never sends more than fits in one frame, and drops any
fragment that arrives.

The **UDP** header (RFC 768) gets the data to the right program. It is only 8
bytes: a source **port**, a destination port, a length and a checksum. A port picks
out one socket on a host; a DNS question goes to port 53 because that is where DNS
servers listen.

The DNS question above is 29 bytes of data. UDP puts 8 bytes in front of it, IP
puts 20 in front of those, and the IP header's total length says 57. On the way in,
each layer reads one field to choose where the rest goes: Ethernet the type, IP the
protocol, UDP the destination port.

### in_cksum

Both headers carry a checksum so that a receiver can tell whether bytes changed on
the way. This is the one function both use: the Internet checksum (RFC 1071), a sum
over 16-bit words that comes out 0 when the receiver adds up bytes that arrived
intact.

### ip_send

Every IP packet xv6 sends goes through here. It writes the IP header, picks the
next card, asks ARP for that card's address (08.02), and hands the packet to
Ethernet. The next card depends on how far the packet is going. A destination
that shares the first 24 bits of xv6's own address, 10.0.2.x (that is what the
netmask 255.255.255.0 picks out), is on the local network, and the frame goes
straight to its card. Anything else, say 8.8.8.8, goes to the **gateway**,
10.0.2.2, with 8.8.8.8 still in the IP header, and the gateway passes it on.

### ip_rx

Every IP packet that arrives comes here from Ethernet: this lesson adds that
branch to `net_rx` (08.02). It drops anything whose header is broken, that is a
fragment of a bigger packet, that is not for xv6, or that is not UDP, and passes
the rest up.

### udp_send

Sockets call this to send a datagram (08.04). It adds the ports and the checksum
and passes the result to IP.

### udp_rx

This checks an arriving datagram's length and checksum and gives its data to the
socket bound to the destination port. Sockets come with 08.04, which adds that
last call; until then a datagram that passes the checks goes no further.

## How it works

### Writing in_cksum, step by step

1. **Start by adding the data up as big-endian 16-bit words.** The bytes are
   combined in network order whatever the CPU's order, and the checksum is the
   complement of the sum.
   ```
   uint16
   in_cksum(void *data, int len, uint32 sum)
   {
     uint8 *p = data;

     while(len > 1){
       sum += (p[0] << 8) | p[1];
       p += 2;
       len -= 2;
     }
     ...
     return ~sum & 0xffff;
   }
   ```
   Stored in a header, the complement makes the receiver's sum of everything come
   to 0xffff, so `in_cksum` over a good header returns 0.
2. **Fold the carries back in.** The top half of the 32-bit sum collects carries,
   and one's complement adds them back in at the bottom. One fold can carry again,
   hence the loop.
   ```
   while(sum >> 16)
     sum = (sum & 0xffff) + (sum >> 16);
   ```
3. **Pad an odd last byte.** It is the high half of a word whose low half is 0.
4. **Let the caller start the sum.** The `sum` argument is where adding starts, so
   UDP can begin with the pseudo-header's part and continue over its own bytes.

### Writing ip_send, step by step

1. **Start with the shape every layer has:** a header in front, then the layer
   below. Every caller leaves the 20 bytes before the payload free. Fill in the
   header there, find the next hop's card, and hand the packet to Ethernet.
   ```
   int
   ip_send(char *payload, int len, uint8 proto, uint32 dst)
   {
     struct ip *ip = (struct ip *)(payload - sizeof(struct ip));

     ip->vhl = IP_VHL;
     ...
     if(arp_resolve(hop, mac) < 0)
       return -1;
     return eth_send((char *)ip, sizeof(struct ip) + len, ETHTYPE_IP, mac);
   }
   ```
   `arp_resolve` may sleep for up to three seconds; if no one answers, the send
   fails with -1.
2. **Number packets atomically.** The id comes from one counter that senders on
   several harts may bump at the same moment.
   ```
   ip->id = htons(__sync_fetch_and_add(&ip_id, 1));
   ```
3. **Checksum last, over a zero checksum field.** The checksum covers the whole
   header, its own field included, so that field must be 0 while the sum is taken.
   ```
   ip->sum = 0;
   ...
   ip->sum = htons(in_cksum(ip, sizeof(struct ip), 0));
   ```
4. **Choose the next hop:** the destination itself if it is on the local network,
   the gateway if it is not.
   ```
   uint32 hop = (dst & NETMASK) == (MYIP & NETMASK) ? dst : GATEWAY;
   ```

### Writing ip_rx, step by step

1. **Start with a good UDP packet for xv6.** Hand UDP exactly its bytes, as many as
   the header's total length says, and the two addresses, which UDP's checksum
   needs.
   ```
   void
   ip_rx(char *pkt, int len)
   {
     if(len < sizeof(struct ip))
       return;
     struct ip *ip = (struct ip *)pkt;
     ...
     int total = ntohs(ip->len);
     ...
     udp_rx(pkt + sizeof(struct ip), total - sizeof(struct ip), ntohl(ip->src), ntohl(ip->dst));
   }
   ```
2. **Accept only plain, intact IPv4.** 0x45 means version 4 with no options;
   options would put the UDP header somewhere else. Then the header checksum:
   `in_cksum` over a good header is 0.
3. **Trust the total length, within reason.** Less than what arrived is normal,
   since short frames are padded; more means the packet is broken.
   ```
   if(total < sizeof(struct ip) || total > len)
     return;
   ```
4. **Drop fragments, and anything that is not UDP for xv6.** A packet with the
   more-fragments bit or an offset is a piece of something bigger, and xv6 does not
   reassemble.

### Why it is built this way

**Headers are written in front, in one page.** The socket layer copies the data 42
bytes into a page and leaves those 42 bytes empty. UDP writes its 8 in front of the
data, IP its 20 in front of those, Ethernet its 14, and the frame starts exactly at
the beginning of the page. Nothing is copied on the way down until the driver
copies the finished frame.

![One datagram down and up the stack. Going down, each layer writes its header in front of the one above, in the same page; going up, each strips its own and passes on what follows.](figures/08.03-path.svg)

**A checksum that can be built in pieces.** The Internet checksum adds 16-bit words
in **one's complement**: a carry out of the top bit is added back in at the bottom.
The result does not depend on the order of the words, so a sum can be started over
one piece of data and continued over another. It is cheap and needs no table. It
cannot see two words swapped, and it was never meant to stop anyone on purpose.

![The IP header checksum of the query, word by word. Adding the result back in gives 0xffff; its complement, what in_cksum returns, is 0.](figures/08.03-checksum.svg)

**UDP's checksum covers addresses it does not carry.** The UDP header has ports but
no addresses. Its checksum still covers them, through a **pseudo-header** that is
never sent: both IP addresses, the protocol and the length. `udp_send` and
`udp_rx` both start the sum on that, then continue it over the real header and
data, which is what the order-free sum allows. A datagram delivered to the wrong
host, or claimed by the wrong protocol, then fails its checksum.

**Zero means "no checksum".** IPv4 lets a sender leave the UDP checksum out by
sending 0. One's complement has two ways of writing zero, 0x0000 and 0xffff (all
bits clear, and all bits set), so a sum that really comes out as 0 is sent as
0xffff, and a receiver checks any checksum that is not 0.

**The other fields are the usual defaults.** A TTL of 64 is more hops than any
real path needs; a type of service of 0 asks for ordinary handling; and every
packet gets a new id even though xv6 never fragments, because a router on the way
may, and the receiver then needs the id to tell one packet's pieces from
another's.

**Believe the header, not the frame.** An Ethernet frame is at least 60 bytes, so a
small packet arrives padded: the 5-byte datagram in Run it is 47 bytes in a
60-byte frame. `ip_rx` trusts the total length in the IP header and ignores the
padding.

**Every number is big-endian on the wire.** A total length of 57 is the bytes 00
39, and RISC-V would store 57 as 39 00, so every field is written through `htons`
or `htonl` and read through `ntohs` or `ntohl`.

**Invariant:** a datagram reaches a socket only if its IP header and UDP checksums
hold and it was addressed to xv6 and to that socket's port. Fragments are dropped,
and nothing over 1472 bytes of data can be sent, since every datagram must fit in
one frame: at most 1500 bytes of IP packet after the 14-byte Ethernet header.

## Break it

Keep the `printf` from Run it, and in `pseudo()` leave the two addresses out of
the pseudo-header:


```
IP (tos 0x0, ttl 64, id 0, offset 0, flags [none], proto UDP (17), length 33)
    10.0.2.2.58289 > 10.0.2.15.2000: [udp sum ok] UDP, length 5
IP (tos 0x0, ttl 64, id 1, offset 0, flags [none], proto UDP (17), length 33)
    10.0.2.2.59889 > 10.0.2.15.2000: [udp sum ok] UDP, length 5
```

QEMU summed the addresses in; `udp_rx` did not, got a different number, and threw
each datagram away without a word. UDP has no way to say "your packet was bad":
the only symptom is silence. The bytes were perfect; the two ends just disagreed
about what the checksum covers. Since `udp_send` uses the same `pseudo()`, from
08.04 on every datagram xv6 sends would be dropped by QEMU the same way.

## Decide the boundary

xv6 computes every checksum on the CPU. A virtio card can do it instead
(`VIRTIO_NET_F_CSUM`), as real cards do. IPv6 dropped the header checksum
altogether: the Ethernet frame already has a 32-bit CRC, checked by every card it
crosses, and the layers above check their own data. Which checks are worth
repeating at each layer, and which only make sense at the two ends?
