# 08.01 The virtio network card

The network card driver moves Ethernet frames between the kernel and QEMU's
virtio network card, and it is the floor everything else in the network module
stands on.

## Where this fits

![Where 08.01 fits](figures/08.01-map.svg)

Until now every byte xv6 handled came from its own disk or its own keyboard. To
ask another computer anything, the kernel must put bytes on a wire and take bytes
off it, and bytes off a wire arrive whenever someone else decides to send them.
The card driver is the lowest layer of the network: below it is the card, a device
of the same family as the disk; above it, every layer this module adds hands it
frames to send and receives the frames that arrive. After this lesson the kernel
can send and receive raw frames, though nothing yet knows what to put in them.

## The idea

![The card's two queues. Receive buffers are handed over before any frame exists; a transmit buffer is handed over with its frame already in it.](figures/08.01-queues.svg)

This module builds a network stack from the bottom up. This lesson moves frames.
08.02 puts an address on each frame and finds out which card owns which IP
address. 08.03 adds IP and UDP, which carry a datagram from a port on one host to a
port on another. 08.04 hands datagrams to processes through sockets, and 08.05 uses
all of it to look a name up in DNS: the first answer in this course that comes from
outside the machine.

The card is a virtio device, like the disk (05.01): the driver and the device share
queues in ordinary memory, and the driver posts buffers on them. But the two
devices differ in one way that shapes the whole driver: who starts the traffic. A
disk only answers. The driver asks for a block and knows a reply is coming. A
network card **receives** whenever anyone on the network sends, and the driver
cannot know when that will be.

So the driver hands the card empty buffers before any frame exists: eight of
them at boot, `NUM`, the same queue size the disk uses. The card keeps them,
writes each arriving frame into one, and raises an interrupt. Sending is the
familiar direction: fill a buffer with a frame, post it, tell the card.

Eight is plenty here. Frames arrive one or two at a time, and the interrupt handler
gives each buffer back as soon as it has dealt with the frame in it. A burst of
more than eight before the handler runs would find no buffer: a real card drops
such frames, and QEMU holds them until a buffer comes back.

### virtio_net_send

Every frame any layer of the stack sends ends up here. It copies the frame into one
of the card's transmit buffers, posts it, and returns at once. Processes call it to
send their packets, and so does the interrupt handler. Before QEMU delivers
anything to xv6 it broadcasts a question, "which card has 10.0.2.15?" (ARP,
08.02), and xv6 answers from inside the handler that received the question. A
handler cannot sleep, so this function must never wait.

### virtio_net_intr

This runs when the card raises its interrupt to say frames have arrived. It hands
each frame up to the Ethernet layer, then gives the buffer back to the card so it
can be filled again. At this lesson there is no Ethernet layer yet, so it only
gives the buffers back, and every frame that arrives is dropped; the line that
hands a frame up comes with 08.02.

`hello` never comes.

## How it works

### Writing virtio_net_init, step by step

1. **Start from the disk's setup (05.01).** Make sure a network card is in the
   slot, do the same handshake as the disk, set up two queues where the disk had
   one, and say the network is up. QEMU's machine has a row of virtio slots, one
   page apart: the disk is in the first, the card in the second, `VIRTIO1`. An
   empty slot is not an error: the kernel returns quietly, `net_up` stays 0, and
   every send fails.
   ```
   void
   virtio_net_init(void)
   {
     ...
     if(*R(VIRTIO_MMIO_MAGIC_VALUE) != 0x74726976 ||
        *R(VIRTIO_MMIO_VERSION) != 2 ||
        *R(VIRTIO_MMIO_DEVICE_ID) != 1 ||
        *R(VIRTIO_MMIO_VENDOR_ID) != 0x554d4551)
       return;
     ...
     vq_init(&net.rx, RXQ);
     vq_init(&net.tx, TXQ);
     ...
     net_up = 1;
   }
   ```
2. **Accept two features and nothing else.** Feature bits come in two banks of 32.
   `VIRTIO_NET_F_MAC`, in the first, says the card will tell us its Ethernet
   address. `VIRTIO_F_VERSION_1`, in the second, says the driver speaks the current
   virtio standard rather than the legacy one, which among other things fixes the
   header in front of each frame at 12 bytes. Leaving the offloads off is what keeps
   every frame in one buffer, exactly as the stack built it.
   ```
   *R(VIRTIO_MMIO_DRIVER_FEATURES) = features & (1 << VIRTIO_NET_F_MAC);
   ...
   *R(VIRTIO_MMIO_DRIVER_FEATURES) = features & (1 << (VIRTIO_F_VERSION_1 - 32));
   ```
3. **Give the card every receive buffer before going live.** A frame may arrive the
   moment the driver says it is ready, so all eight buffers are marked writable by
   the card and posted first.
   ```
   for(int i = 0; i < NUM; i++){
     net.rx.desc[i].flags = VRING_DESC_F_WRITE;
     net.rx.avail->ring[i] = i;
   }
   ```
4. **Turn off transmit interrupts, and read the card's address.** Finished sends are
   collected by the next send, so the card need not interrupt for them. The six
   bytes of the Ethernet address come from the card's config space: a few
   registers after the common virtio ones whose meaning depends on the kind of
   device. The address is QEMU's choice, not xv6's; the monitor's `info network`
   shows the same 52:54:00:12:34:56.

### Writing virtio_net_send, step by step

1. **Start with the easy case: buffer `i` is free.** Refuse a frame that cannot fit
   one buffer, copy it in behind a zeroed header, and post the buffer as the disk
   driver posts a request. The copy is what lets the caller reuse its own memory as
   soon as this returns.
   ```
   int
   virtio_net_send(void *frame, int len)
   {
     if(!net_up || len < 0 || len > sizeof(struct eth) + ETH_MTU)
       return -1;
     ...
     char *buf = net.tx.buf[i];
     memset(buf, 0, sizeof(struct virtio_net_hdr));
     memmove(buf + sizeof(struct virtio_net_hdr), frame, len);
     ...
     *R(VIRTIO_MMIO_QUEUE_NOTIFY) = TXQ;
     return 0;
   }
   ```
2. **Find a free buffer, or drop the frame.** If all eight are still the card's,
   return -1. Waiting is not an option, because the caller may be an interrupt
   handler answering ARP.
3. **Take back what the card has finished.** No interrupt says a frame has left, so
   without this loop every buffer stays busy and the ninth send is dropped. Each
   send looks first:
   ```
   while(net.tx.used_idx != net.tx.used->idx){
     __sync_synchronize();
     net.txbusy[net.tx.used->ring[net.tx.used_idx % NUM].id] = 0;
     net.tx.used_idx += 1;
   }
   ```
4. **Post with two fences.** The card must see the ring entry before the index that
   announces it, and both before the notify that makes it look.
   ```
   net.tx.avail->ring[net.tx.avail->idx % NUM] = i;
   __sync_synchronize();
   net.tx.avail->idx += 1;
   __sync_synchronize();
   ```
5. **Hold the transmit lock across all of it.** Processes on any hart and interrupt
   handlers may send at the same moment, and they share the queue and the busy
   flags.

### Writing virtio_net_intr, step by step

1. **Start with the loop that gives buffers back.** Acknowledge the interrupt, or
   the card keeps it raised and the handler runs again and again; the two status
   bits are "used ring changed" and "configuration changed", and both are cleared.
   Then each new entry in the used ring names a buffer the card has filled, and it
   goes straight back on the available ring. From 08.02 on, the frame is handed up
   just before that; for now it is dropped.
   ```
   void
   virtio_net_intr(void)
   {
     *R(VIRTIO_MMIO_INTERRUPT_ACK) = *R(VIRTIO_MMIO_INTERRUPT_STATUS) & 0x3;
     ...
     while(net.rx.used_idx != net.rx.used->idx){
       ...
       int id = e->id;
       net.rx.used_idx += 1;
       ...
       net.rx.avail->ring[net.rx.avail->idx % NUM] = id;
       ...
     }
     ...
   }
   ```
2. **Fence before reading each entry,** so that it is not read before the index
   that announced it, and between the entry and the index when giving the buffer
   back, as in a send.
3. **Notify once, at the end.** One write covers every buffer given back in this
   pass, and none is needed if the loop found nothing.
   ```
   if(given){
     __sync_synchronize();
     *R(VIRTIO_MMIO_QUEUE_NOTIFY) = RXQ;
   }
   ```

### Why it is built this way

**Every buffer starts with a header the driver ignores.** virtio puts a 12-byte
header in front of each frame, for offload requests like "compute the checksum for
me". The driver accepts none of those features, so it sends the header as zeroes
and skips it on receive. Each buffer is 2048 bytes, half a page. The longest frame
is 1514 bytes, a 14-byte Ethernet header and 1500 bytes of payload, so with the
header 1526 bytes fit in any buffer and no frame is ever split.

![One 2048-byte buffer: the virtio header, then the Ethernet frame. Offsets in bytes.](figures/08.01-buffer.svg)

**Buffers never move.** Descriptor 0 always points at buffer 0, descriptor 1 at
buffer 1, and so on, for the life of the system. The disk driver chains three
descriptors per request and so needs a free list to allocate them from; here one
descriptor is one frame, so an index names both, and a busy flag per transmit
buffer is all the bookkeeping there is. `vq_init` panics if the queue is already
live or holds fewer than eight entries, because every line after it assumes it
owns exactly eight.

**Sending never waits for the card.** No one is told when a frame has left; the
transmit queue does not even raise an interrupt. Instead, each send first looks at
which buffers the card has finished with since last time, and takes a free one. If
all eight are still in flight, the frame is dropped, which a network is allowed to
do. Waiting is not allowed, because an interrupt handler may be the one sending.

**Receiving takes no lock.** Sending takes a lock, since processes and interrupt
handlers on any hart may send at once. The receive side needs none: after boot only
the interrupt handler touches it, and the interrupt controller never gives the
same interrupt to two harts at once (03.03). That matters, because a frame handed
up may cause a reply to be sent from inside the handler; one lock for both
directions would deadlock against itself.

**Who owns a buffer** is the invariant. A receive buffer belongs to the card from
the moment it is posted until it comes back in the used ring, then to the driver
until the handler posts it again. A transmit buffer belongs to the card while it
is marked busy. Everything above the driver must copy what it keeps before the
handler gives the buffer back.

The rest of the lesson is the wiring the disk needed in 05.01: the kernel maps the
card's register page, the interrupt controller lets its interrupt 2 through, and
`devintr` calls `virtio_net_intr` for it.

## Decide the boundary

xv6 copies every frame: into a card buffer on the way out, out of one (08.04) on
the way in, and it takes an interrupt for each burst of arrivals. Linux's
virtio-net driver hands the card the pages a packet already sits in, so nothing
is copied, and under heavy load it turns the interrupt off and polls the used
ring instead (NAPI), because at a million packets a second the interrupts alone
would fill the CPU. Each of these removes work per packet and adds code that must
track who owns which page, and for how long. At the rate this kernel sees packets,
a copy costs less than reading the code that avoids it. At what packet rate does
that stop being true, and which would you add first?
