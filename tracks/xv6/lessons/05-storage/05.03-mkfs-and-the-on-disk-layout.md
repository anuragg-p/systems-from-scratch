# 05.03 mkfs and the on-disk layout

This lesson covers how the disk is laid out, as the host program `mkfs`
writes it, and the bitmap allocator the kernel uses to hand out disk
blocks and take them back.

## Where this fits

![Where 05.03 fits](figures/05.03-map.svg)

The layout is a contract between the build and the kernel: a program on
the host writes the disk image, and the kernel reads the same layout when
it boots. The block allocator sits on the buffer cache and keeps its
record of free blocks in a block of its own. Above it, files will ask for
a new block whenever they grow and give blocks back when they shrink or
are deleted. After this lesson the kernel knows where everything is on
the disk and can find a block that nobody is using.

## The idea

![On the finished system's disk `mkfs` used blocks 0 to 788, so byte 98 of the bitmap is 0x1f and the first clear bit is block 789.](figures/05.03-bitmap.svg)

**The need.** `echo hi > a` creates a file and puts three bytes in it.
Those bytes need a disk block that no other file is using, and the
choice has to be remembered: after a reboot the kernel must still know
which blocks are taken. Before any of that, the kernel must know where on
the disk the files, the free-space record and the rest even are.

**The idea.** The disk is cut into regions, always in the same order: a
boot block, a superblock, the log, the inodes, the free-block bitmap, and
then the data blocks. The **superblock** says where each region starts,
so the kernel reads it once at boot and knows the map.

Two of those regions belong to later lessons, but their shapes are fixed
here, because `mkfs` must write them. An **inode** is a 64-byte record per
file: its type, its size, and the numbers of the blocks that hold its
bytes (05.05). A directory is a file whose bytes are a list of (name,
inode number) entries (05.06). The **log** is a staging area where a
change that spans several blocks is written in full before any of it
touches its real place, so a crash cannot leave it half done (05.04).

The **free bitmap** has one bit per block on the disk: 1 for in use, 0 for
free. To allocate, find a 0 bit, set it, and the block is yours; to free,
clear it. Because the bitmap is itself a disk block, the record survives a
reboot.

Worked example, on the finished system's disk: when the kernel boots,
`mkfs` has already used blocks 0 to 788 for the metadata, the root
directory and the programs it copied in. So bits 0 to 788 are set, byte 98
of the bitmap is 0x1f (its low five bits, blocks 784 to 788), and the first
free block is 789. That is the block `echo hi > a` will get.

### `mkfs.c`

Someone has to write the first version of all this. `mkfs` is not kernel
code: it runs on the host at build time, includes the kernel's own
`kernel/fs.h` so it uses the same structures, and writes `build/fs.img`
with the superblock, an empty log, the root directory and a copy of
`README`; from lesson 07.01 on, one file per user program too. It hands
out blocks simply in order, and writes the bitmap once at the end. It
takes the file types from `kernel/stat.h`, new here too, which also
holds `struct stat`, what a program gets back when it asks about a file
(05.05).

### Writing `mkfs.c`, step by step

1. **Lay out the regions and hand out blocks in order.** The size of each
   region is fixed when `mkfs` is compiled; the superblock records where
   each one starts and goes in block 1. Files get blocks counting up from
   the first one after the metadata, and at the very end the bitmap is
   written once, with a bit set for every block used so far.
   ```
     nmeta = 2 + nlog + ninodeblocks + nbitmap;
     nblocks = FSSIZE - nmeta;

     sb.magic = FSMAGIC;
     sb.size = xint(FSSIZE);
     ...
     freeblock = nmeta;     // the first free block that we can allocate
     ...
     memmove(buf, &sb, sizeof(sb));
     wsect(1, buf);
     ...
     balloc(freeblock);
   ```
2. **Every number in the kernel's byte order.** The kernel that reads the
   image runs on RISC-V, which stores the low byte of a number first, and
   the host running `mkfs` need not. `xint` and `xshort` lay the bytes out
   the RISC-V way whatever the host does.
3. **Zero the whole image first,** so that every inode reads as free, the
   log header as empty, and reading back a block never runs past the end
   of the file.
   ```
     for(i = 0; i < FSSIZE; i++)
       wsect(i, zeroes);
   ```
4. **The root directory comes first,** so that it gets inode 1, the number
   the kernel looks it up by before it has read any directory. Inode 0 is
   never used: a directory entry with inode number 0 is an empty slot.
   The root's first two entries, `.` and `..`, both point at itself.
   ```
     rootino = ialloc(T_DIR);
     assert(rootino == ROOTINO);
   ```
5. **One file per argument:** a new inode, an entry for it in the root
   directory, and the host file's bytes appended with `iappend`, which
   takes every new block from `freeblock++`. At the end the root
   directory's size is rounded up to the whole block it fills.
   ```
       inum = ialloc(T_FILE);
       ...
       iappend(rootino, &de, sizeof(de));

       while((cc = read(fd, buf, sizeof(buf))) > 0)
         iappend(inum, buf, cc);
   ```

### `balloc`

Files (05.05) will call it whenever one needs another block. It searches
the bitmap for the first 0 bit, sets it, zeroes the new block and returns
its number, or returns 0 if the disk is full. Like everything in the file
system it takes a device number, `dev`; there is one disk, device 1.

### `bfree`

Called when a file is truncated or deleted. `bfree` clears the block's
bit, and stops the kernel if the bit was already clear.

### `fsinit`

Also new in `fs.c`: it reads the superblock and checks its magic
number. Reading means sleeping until the disk is done, so it needs a
process: the first process calls it, in 07.02.

## How it works

### Writing `balloc`, step by step

1. **Find a 0 bit in the bitmap block and set it.** Block `b + bi` is bit
   `bi % 8` of byte `bi / 8`. Mark it before letting the buffer go, so no
   one else can find the same bit.
   ```
       bp = bread(dev, BBLOCK(b, sb));
       for(bi = 0; bi < BPB && b + bi < sb.size; bi++){
         m = 1 << (bi % 8);
         if((bp->data[bi/8] & m) == 0){  // Is block free?
           bp->data[bi/8] |= m;  // Mark block in use.
           brelse(bp);
           ...
           return b + bi;
         }
       }
   ```
2. **One bitmap block at a time.** One block of bits covers 8192 blocks,
   so an outer loop steps through the disk that far at a time. This disk
   needs only one; the loop is there for bigger disks. The inner loop
   stops at the disk's size, because the last bitmap block may describe
   blocks the disk does not have.
   ```
     for(b = 0; b < sb.size; b += BPB){
   ```
3. **Zero the new block** before returning its number, with
   `bzero(dev, b + bi)`; why is below.
4. **Nothing free:** print a message and return 0, which callers take to
   mean "disk full".

### Why it is built this way

**Every bitmap change will be part of an operation.** `balloc` and
`bfree` do not write the bitmap block to the disk; at this lesson their
change stays in the buffer cache. Lesson 05.04 adds one line to each, and
to `bzero`: a call to `log_write`, which means "this block changed, write
it as part of the current operation". A file growing by one block changes
two things, the bitmap and the file's list of blocks, and they must reach
the disk together or not at all. A crash between the two would leave a
block marked used that no file owns, or a file pointing at a block marked
free.

**Find and mark under one lock.** `balloc` reads a bitmap block with
`bread`, which hands it over locked, and both finds the 0 bit and sets it
before giving the block back:

```
      if((bp->data[bi/8] & m) == 0){  // Is block free?
        bp->data[bi/8] |= m;  // Mark block in use.
```

Two processes allocating at once therefore cannot both see the same bit as
free; the second one finds it already set.

**A new block is zeroed.** Before returning, `balloc` clears the new
block. A freed block still holds whatever the last file wrote there, and
without the clear a new file could start out showing a deleted file's
data.

**Block 0 is never a data block.** It is the boot block, kept for a boot
loader as on a PC's disk; QEMU loads the kernel directly, so here it is
simply unused. That lets `balloc` return 0 to mean "the disk is full"
without any confusion. `bfree` treats a bit that is already clear as a
sign that two owners each thought they had the block, and panics rather
than let the bitmap go wrong silently.

`mkfs` has a `balloc` too, with the same name and a different job. It never
searches, because at build time nothing has been freed: it counts upward.
The kernel's `balloc` searches because files come and go for as long as it
runs.

The **invariant**: a block's bit is set if and only if something owns it,
a file, a directory, the log or the metadata. A set bit nobody owns leaks a
block; a clear bit on a block that a file uses lets a second file take it.

The layout of this 2000-block disk, in one table:

| blocks | what |
|---|---|
| 0 | boot block, unused |
| 1 | superblock |
| 2 to 32 | log: a header and 30 blocks |
| 33 to 45 | inodes, 16 per block, 200 in all |
| 46 | free bitmap |
| 47 to 1999 | data |

## Break it

In `build/at/xv6/05.03/mkfs/mkfs.c`, write the bitmap at the start
instead of the end: move `balloc(freeblock);`, near the end of `main`, up
to just after the superblock is written:

-->

+  balloc(freeblock);

```
  wsect(1, buf);
  balloc(freeblock);
```

When the bitmap was written, `freeblock` still pointed just past the
metadata. The root directory then took block 47 and `README` block 48,
and neither is marked. Nothing complains: no check reads the bitmap
against the files. The first time the kernel's `balloc` runs it will find
bit 47 clear, zero the block and hand it to a new file, wiping the root
directory.

## Decide the boundary

xv6 stores free space as a bitmap and scans it from the start for the first
free bit. It is easy to check by eye, and one bitmap block covers 8192
blocks. It pays with a linear scan on every allocation, and it gives no help
with placement: a file's blocks can scatter across the disk. Another file
system could keep free extents in a tree, as ext4 and XFS do, find a run
of blocks near the previous one, and allocate a whole extent at once.
It pays with a more complicated structure to keep consistent on disk.

For a 2 MB disk the scan is nothing. At what size of disk does the cost of
looking for a free block, or the scatter of the blocks you find, start to
matter?
