# 05.02 The buffer cache

This lesson covers the buffer cache, which keeps one copy of each disk
block in memory and lets one process at a time use it.

## Where this fits

![Where 05.02 fits](figures/05.02-map.svg)

The buffer cache sits right on top of the disk driver and is the only
thing that calls it. Everything above, the block allocator, the log,
files and directories, asks the cache for a block instead of going to
the disk. Below, it uses the driver from the last lesson, and the sleep
and wakeup from module 04 to make processes take turns on a block. After
this lesson the file system has a safe, shared place to read and change
disk blocks.

## The idea

![`brelse` moves a buffer whose count reaches 0 to the front; `bget` looks for a victim from the back.](figures/05.02-lru.svg)

**The need.** Suppose two processes create files in the same directory at
the same time. Both must change the directory's data block. If each read
the block from the disk into a private copy, each would add its entry to
its own copy and write it back, and the second write would erase the
first entry. On top of that, every read would cost a trip to the disk,
even for a block read a moment ago.

**The idea.** Keep a fixed set of in-memory buffers, 30 of them, each
able to hold one block. A process that wants block 47 asks the cache. If a
buffer already holds 47, it gets that buffer; if not, the cache takes a
buffer nobody is using, labels it 47, and the block is read into it. Either
way the process gets the buffer locked, uses it, and gives it back. Since
there is only ever one buffer for block 47, both directory writers above
work on the same copy, one after the other.

When a buffer has to be reused for another block, the cache takes the one
used least recently. Buffers just given back go to the front of a list;
the search for a victim starts at the back. The list is a circle through
a head, a `struct buf` that holds no block: the front is `head.next`, the
back is `head.prev`, and an empty list is the head pointing at itself both
ways. So adding and removing a buffer never meets a null pointer, and a
scan stops when it comes back round to the head. At boot, `main` now calls
`binit`, which starts that empty circle and links the 30 buffers into it.

Thirty is three times `MAXOPBLOCKS`, the most blocks one file system
operation (creating a file, writing a piece of one) may change. The log
of 05.04 keeps every block an operation changed in the cache until it is
safely on disk, and lets up to three operations do that at once, so the
cache is sized to hold them.

### `acquiresleep` and `releasesleep`

The lock on each buffer, and from 05.05 on each inode. A process holds a
buffer for as long as it uses it, including while the disk reads into it,
which takes milliseconds. A spinlock would be the wrong tool twice over:
every hart waiting for it would spin for the whole transfer, and the
holder could not sleep, since the scheduler refuses to switch away from a
process holding a spinlock. A sleep lock puts its waiters to sleep
instead. `acquiresleep` sleeps until the lock is free and then takes it,
`releasesleep` frees it and wakes the waiters; both are built from
04.03's sleep and wakeup. The price is that a sleep lock needs a process
to put to sleep, so it can never be taken in an interrupt handler.

### `bget`

Every block read starts here. `bget(dev, blockno)` finds the buffer that
holds the block, or recycles the least recently used free one for it,
and returns it locked. A block is named by its device number and its
number on that device; xv6 has one disk, but the cache would keep two
apart. `bread` is `bget` plus a disk read when the buffer does not hold
valid data yet; `bwrite` writes a buffer the caller holds to the disk and
waits. Nothing calls `bwrite` until the log of 05.04, the only code that
writes blocks back.

### `brelse`

Every user of a buffer ends with it. `brelse(b)` unlocks the buffer and
drops the caller's reference; when nobody holds it any more, it moves it
to the most-recently-used end of the list. The data stays, so the next
request for the same block may find it there. `bpin` and `bunpin` raise
and lower the same count without holding the buffer; the log uses them to
keep a changed block from being recycled before it reaches the disk.

## How it works

### Writing `bget`, step by step

1. **Look for the block, under `bcache.lock`.** The list, and every
   buffer's label (which block it holds) and count, are shared by all
   harts. If a buffer already holds the block, raise its count, drop the
   spinlock, take the buffer's sleep lock and return it.
   ```
     acquire(&bcache.lock);

     for(b = bcache.head.next; b != &bcache.head; b = b->next){
       if(b->dev == dev && b->blockno == blockno){
         b->refcnt++;
         release(&bcache.lock);
         acquiresleep(&b->lock);
         return b;
       }
     }
   ```
   The search starts at the most recently used end, where a block just
   used is most likely to be.
2. **Otherwise recycle one,** searching from the least recently used end
   for a buffer whose count is 0. Relabel it for this block, mark it not
   `valid` so that `bread` reads the disk, set the count to 1, and lock it
   the same way.
   ```
     for(b = bcache.head.prev; b != &bcache.head; b = b->prev){
       if(b->refcnt == 0) {
         b->dev = dev;
         b->blockno = blockno;
         b->valid = 0;
   ```
3. **Nothing to recycle** means every buffer is in use at once, more than
   the cache was sized for. `bget` panics rather than wait: the holders
   may themselves be waiting for a buffer, and then nobody would ever give
   one back.

### Writing `brelse`, step by step

1. **Unlock the buffer and drop the count.** The sleep lock goes first, so
   a process waiting for this block can go ahead; the count changes under
   `bcache.lock`, like everything else `bget` reads.
   ```
     releasesleep(&b->lock);

     acquire(&bcache.lock);
     b->refcnt--;
     if (b->refcnt == 0) {
       ...
     }
   ```
2. **At 0, move it to the most recently used end** of the list, so it is
   the last to be recycled. Its data stays, and the next request for the
   block may find it there.
3. **Check the caller holds the buffer** with `holdingsleep`, and panic if
   not: releasing a lock someone else holds would let two processes into
   the same buffer.

### Why it is built this way

**Two locks with two jobs.** One spinlock, `bcache.lock`, protects the
list and the labels: which block each buffer holds and how many
processes hold it. Each buffer's own sleep lock protects its contents.
The spinlock is held for a few instructions at a time; the sleep lock from
the moment a process gets the buffer until it gives it back.

![The spinlock covers the list and which block a buffer holds; the sleep lock covers what is in it.](figures/05.02-buf-locks.svg)

**Find and claim in one step.** `bget` searches the list and, on a miss,
relabels a buffer for the block, all under one hold of `bcache.lock`. If
it let go between the search and the claim, two processes missing on the
same block could each relabel a different buffer, and there would be two
copies of block 47. That is the **invariant**: at most one buffer holds a
given block.

**Count before you wait.** `bget` must drop the spinlock before it takes
the buffer's sleep lock, because a process may not sleep while holding a
spinlock. What protects the buffer in that gap is its reference count,
raised while the spinlock was still held:

```
      b->refcnt++;
      release(&bcache.lock);
      acquiresleep(&b->lock);
```

Only buffers with a count of 0 are ever recycled, so the buffer cannot be
relabelled for another block while the process waits for it.

## Break it

`binit` is the one piece of this lesson that runs at boot. In
`build/at/xv6/05.02/kernel/bio.c`, delete the two lines that make the
empty circle:

<!-- verify: patch file=kernel/bio.c
-  bcache.head.prev = &bcache.head;
-  bcache.head.next = &bcache.head;
-->
```
  bcache.head.prev = &bcache.head;   <- delete
  bcache.head.next = &bcache.head;   <- delete
```

Run it again:

<!-- verify: session run="./learn run xv6 --at 05.02" panics=kerneltrap -->
```
xv6 kernel is booting

scause=0xf sepc=0x80000084 stval=0x48
panic: kerneltrap
```

A store page fault at address 0x48. Look `sepc` up in
`build/kernel/kernel.asm`: it is `bcache.head.next->prev = b` on the first
time round the loop. `bcache` starts zeroed, so `head.next` is a null
pointer, and `prev` sits 0x48 bytes into a `struct buf`.

## Decide the boundary

xv6 has one lock for the whole cache and a linear scan of at most 30
buffers. That is correct and short, and every `bget` on every hart queues
on `bcache.lock`. Another kernel could hash blocks into buckets, one lock
each, as the xv6 buffer cache lab does, or keep a radix tree per file as
Linux's page cache does. That removes contention and pays with a harder
invariant: finding a victim now means taking locks across buckets.

It also decides what the cache is for. xv6 caches blocks of a disk; Linux
caches pages of files. Is a block cache enough, or does your kernel need to
know which file a cached page belongs to?
