# 05.04 The write-ahead log

This lesson covers the write-ahead log, which makes a group of disk writes
happen all together or not at all, even when the machine stops in the
middle.

## Where this fits

![Where 05.04 fits](figures/05.04-map.svg)

The log sits between the buffer cache and everything that changes the file
system. Above it, every operation that writes, such as creating a file,
writing to one or deleting one, will wrap its changes in a log operation
instead of writing blocks straight to the disk. Below, it keeps changed
blocks in the buffer cache and uses the disk driver to write them, first
into a log area and then into place. After this lesson a crash in the
middle of any change leaves the disk as it was before the change or as it
is after it, never halfway.

## The idea

![The transaction that creates `a`, on disk after each step of `commit`. One header write decides which way a crash goes.](figures/05.04-commit.svg)

**The need.** Creating a file changes at least two blocks: one to mark an
inode as in use, one to add the name to the directory. The disk writes one
block at a time, and power can fail between any two. If only the inode
write reaches the disk, there is an inode in use that no name points to,
lost for good. If only the directory write does, a name points at an inode
marked free, which the next file created will take over.

**The idea.** Do not write the changed blocks in place. Write them first to
a separate area of the disk, the **log**. Then write one block, the log's
**header**, that lists them. Only after that, copy each block to its real
home, and finally clear the header.

The header write is the moment that decides. If the machine stops before
it, the header still lists nothing, and at the next boot the half-written
log is ignored: the change never happened. If it stops after, the header
lists every block, and the next boot copies them all into place again: the
change happened completely. A group of writes treated this way is a
**transaction**, and the single header write is its **commit point**.

All of this rests on one fact about the disk: a single block write
either happens or does not, it never leaves a block half new. That is why
the header has to fit in one block, and why `initlog` refuses to start
if it does not.

Every operation that changes the file system, creating a file, writing a
piece of one, deleting one, is bracketed by `begin_op` and `end_op`, and
everything it changes in between joins the current transaction.

### `log_write`

File system code that changes a block calls this instead of writing the
block itself. This lesson adds the first calls, to 05.03's block code:
`balloc` and `bfree` hand it the bitmap block, and `bzero` the block it
cleared. `log_write` writes nothing to disk. It adds the block's number to
the list of blocks in the current transaction and keeps the buffer in the
cache until the commit.

### `commit`

Called when the last operation in a transaction ends (`end_op`). It
writes the listed blocks into the log, writes the header, copies the
blocks home, and clears the header, in that order.

### `recover_from_log`

Runs once, before anything else touches the file system: this lesson has
`fsinit` (05.03) call `initlog`, which finds the log on the disk and
recovers from it. `recover_from_log` reads the header and, if it lists
blocks, copies them home again, then clears it. This is what turns "the
machine stopped after the commit point" into "the change happened".

## How it works

### Writing `begin_op` and `end_op` (in `log.c`), step by step

Every caller of the log uses these two, and `log_write` refuses to run
outside them.

1. **Count the operations in progress; the last one out commits.**
   `begin_op` adds one to `log.outstanding` under `log.lock`, and `end_op`
   takes it away again:
   ```
     acquire(&log.lock);
     log.outstanding -= 1;
     ...
     if(log.outstanding == 0){
       do_commit = 1;
       ...
     }
     release(&log.lock);

     if(do_commit){
       commit();
   ```
   `commit` runs after the lock is released, because it waits for the disk
   and a process may not sleep holding a spinlock.
2. **Keep new operations out of a commit.** An operation that started
   while `commit` was writing would add blocks to a transaction already
   half on disk. So `end_op` sets `log.committing`, `begin_op` sleeps while
   it is set, and `end_op` clears it and wakes them when the commit is
   done.
3. **Reserve room before starting.** `begin_op` also waits when the
   operations already open, each counted at its worst case, might not
   leave room in the log for one more:
   ```
       } else if(log.lh.n + (log.outstanding+1)*MAXOPBLOCKS > LOGBLOCKS){
         // this op might exhaust log space; wait for commit.
         sleep(&log, &log.lock);
   ```
4. **Wake the waiters when an operation ends without committing,** with
   `wakeup(&log)`: its reserved room is free again.

### Writing `log_write`, step by step

1. **Remember the block, write nothing.** Add the block's number to the
   in-memory header and pin the buffer, so it stays in the cache until the
   commit copies it.
   ```
     acquire(&log.lock);
     ...
     log.lh.block[i] = b->blockno;
     if (i == log.lh.n) {  // Add new block to log?
       bpin(b);
       log.lh.n++;
     }
   ```
2. **Look for the block in the list first.** If it is there already, `i`
   stops at it and nothing is added: absorption.
3. **Panic on a full log, or on a write outside `begin_op` and `end_op`;**
   either would be a change that is never committed.

### Writing `commit`, step by step

1. **Without a crash, two copies are enough:** the changed blocks from the
   cache into the log area, then from there to their homes. A crash in
   the second copy, though, leaves the disk half changed, and nothing at
   the next boot knows.
   ```
     if (log.lh.n > 0) {
       write_log();     // Write modified blocks from cache to log
       ...
       install_trans(0); // Now install writes to home locations
       log.lh.n = 0;
       ...
     }
   ```
2. **Write the header between the two copies.** It lists the blocks, and
   writing it is the commit point: after it, a crash means the change
   happens at the next boot.
3. **Clear the header afterwards,** so that a crash while the next
   transaction fills the log area does not replay half-new data under the
   old block numbers.

### Writing `recover_from_log`, step by step

1. **Copy home whatever the header lists, then clear it.** After a crash
   past a commit point the header lists blocks; otherwise `n` is 0 and
   this does nothing.
   ```
     read_head();
     ...
     install_trans(1); // if committed, copy from log to disk
     log.lh.n = 0;
     write_head(); // clear the log
   ```
   The 1 tells `install_trans` that this boot never pinned these buffers,
   so it must not unpin them.
2. **Copying twice is fine,** so this is right whether or not the crashed
   boot got as far as copying the blocks itself.
3. **The clear is not optional.** Leave the header listing blocks and
   every later boot copies them home again, over whatever has been written
   since.

### Why it is built this way

**The order of the four writes is the whole design.** `commit` does:

```
    write_log();     // Write modified blocks from cache to log
    write_head();    // Write header to disk -- the real commit
    install_trans(0); // Now install writes to home locations
    log.lh.n = 0;
    write_head();    // Erase the transaction from the log
```

The **invariant**: the header on disk lists blocks only when all of them
are already in the log, and no block is copied home until the header lists
it. Swap the first two lines and a crash could leave a header pointing at
log blocks that were never written; recovery would copy garbage home.
Copying a block home twice does no harm, so a crash during recovery is
safe too: the next boot just does it again.

**Changed blocks stay in the cache until commit.** Between `log_write` and
the commit, the only up-to-date copy of a changed block is its buffer. If
the cache recycled that buffer for another block, a later read would fetch
the old contents from the disk and the change would be gone. So
`log_write` **pins** the buffer, raising its reference count so the cache
cannot reuse it, and the copy-home step unpins it.

**A block changed twice is logged once.** `log_write` first looks for the
block in the current list. Creating one file writes the new inode's block
twice, once to claim the inode and once to fill it in, and the log holds
it once. This is **absorption**.

**Several system calls share one commit.** `commit` runs only when the
last open operation ends, so system calls running at the same moment ride
the same transaction: **group commit**, and a block they both change is
absorbed across them too. The log has room for 30 blocks, and each open
operation is assumed to need up to 10, so `begin_op` makes a caller wait
when another operation might not fit. That is also why a large `write`
(05.07) is split into several operations, each its own transaction, and
is not atomic as a whole.

## Break it

Nothing runs a transaction until a process creates a file, and seeing
what survived takes `ls` and `cat`, so this experiment runs on the 07.03
build. It also needs a disk that keeps its writes: `./learn run` boots a
throwaway copy of the image, while the project's own `make qemu` writes
to `build/fs.img`. Write the 07.03 project with
`./learn files xv6 --at 07.03`, and in `build/at/xv6/07.03/` run
`make qemu` once, to the `$` prompt, then quit with Control-a x. That
first boot lets `init` create the console file, a transaction of its
own. Keep the disk as it is now with `cp build/fs.img spare.img`.

Now add a crash just after the commit point, in `commit()` in
`kernel/log.c`:

$ cp build/fs.img spare.img
-->
<!-- verify: patch file=kernel/log.c at=07.03

```

    panic("crash after commit");

Run `make qemu` and type `echo hi > a`:

<!-- verify: session at=07.03 cwd=project run="make qemu" panics="crash after commit" -->
```

Quit, delete the `panic` line, and run `make qemu` again on the same
disk:

<!-- verify: revert file=kernel/log.c at=07.03 -->
<!-- verify: session at=07.03 cwd=project run="make qemu" -->
```
$ cat a
$ ls a
a              2 16 0
```

`a` exists and is empty. The create had reached its commit point, so
`recover_from_log` replayed it at boot; writing `hi` was a later
transaction that never began. Now `cp spare.img build/fs.img`, put the
crash just before `write_head()` instead, as
`panic("crash before commit");`, and do the same two steps:

<!-- verify: setup at=07.03 cwd=project
$ cp spare.img build/fs.img
-->
<!-- verify: patch file=kernel/log.c at=07.03
+    panic("crash before commit");
     write_head();    // Write header to disk -- the real commit
-->
<!-- verify: session at=07.03 cwd=project run="make qemu" panics="crash before commit" -->
```
$ echo hi > a
panic: crash before commit
```

and after the boot without it:

<!-- verify: revert file=kernel/log.c at=07.03 -->
<!-- verify: session at=07.03 cwd=project run="make qemu" -->
```

ls: cannot open a
$ cat a
cat: cannot open a
```

The file is not half created; it never existed. Which side of one disk
write the crash fell on decided it.

## Decide the boundary

xv6 logs whole blocks, data included, commits synchronously when the last call
ends, and writes everything twice. Another system could journal only metadata:
ext4's default mode logs inode and directory blocks but not file contents, and
commits in the background every few seconds. It writes much less, but a call
returns before it is durable, and file data can be lost or stale after a crash.
A copy-on-write file system such as ZFS never overwrites in place, so it has no
log to replay and pays in allocation work. A file system with no protection
(FAT) is fastest and pays with a full scan after every crash.

What must be true the moment `write()` returns, and what are you willing to
write twice to get it?
