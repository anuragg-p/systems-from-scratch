# 05.05 Inodes

This lesson covers inodes, the record that maps a file's bytes onto disk
blocks, and the four functions that read a file, write it and empty it.

## Where this fits

![Where 05.05 fits](figures/05.05-map.svg)

Files sit on top of the log and the block allocator. Above them,
directories are files with a fixed format, and everything a program does
with a file, reading it, writing it, running it, comes down to the
functions here. Below, they take blocks from the allocator, read and
change them through the buffer cache, and make each change part of a log
transaction. After this lesson the kernel can read and write the contents
of any file once it knows which file; finding a file by its name comes
next.

## The idea

![`cat` on the finished system's disk: twelve blocks straight from the inode, the next 24 through block 61.](figures/05.05-inode-blocks.svg)

**The need.** A program asks for bytes 5000 to 5099 of `cat`, which on
the finished system's disk is 36176 bytes long. On the disk it is 36
separate blocks wherever the allocator found room, not necessarily next
to each other. Something has to say which disk block holds which part of
the file, how long the file is, and how many names it has.

**The idea.** Each file has an **inode**: a small fixed-size record on the
disk with the file's type, its size, its number of names, and the list of
its blocks in order. Byte 5000 is in the file's block 4 (5000 / 1024), at
offset 904 inside it, so the kernel looks up entry 4 of the list, reads
that disk block, and copies from offset 904.

The record is 64 bytes, so that exactly 16 fit in a block: four 2-byte
fields, the 4-byte size, and 13 block numbers of 4 bytes each. The first
12 are the file's first 12 blocks, the **direct** blocks. The 13th names
an **indirect** block, a whole disk block used to hold 256 more block
numbers. So a small file needs nothing beyond its inode, and the largest
file is 12 + 256 = 268 blocks. `cat`, at 36 blocks, uses all 12 direct
entries and 24 of the indirect block's.

### The in-memory inode, `file.h`

Every function in this lesson works on an in-memory inode, a
`struct inode`: a copy of the disk record plus what the kernel needs to
share it, a reference count, a sleep lock and a flag saying whether the
copy has been read yet. The kernel keeps them in a table of 50, one copy
per inode, for the same reason the buffer cache keeps one copy per
block: two processes using the same file must see the same size and the
same list of blocks. (`major` and `minor` matter only for device files, 05.07.)

Five functions in `fs.c` manage the table. `iget` finds the inode's
entry, or claims a free one, and raises its count; it neither reads the
disk nor locks. `ilock` takes the inode's sleep lock and, the first time,
reads the record from the disk. They are separate because holding an
inode and using it are different things: an open file or a process's
current directory holds a reference for a long time and locks the inode
only for the moment it reads or writes, and a path lookup (05.06) holds
several inodes but locks one at a time. `iupdate` writes the in-memory
copy back through the log. `ialloc` claims a free record on the disk, one
whose type is 0.

`iput` drops a reference. When it was the last one and no directory
entry names the inode any more, its `nlink` is 0, `iput` frees the inode:
it empties it with `itrunc` and writes it back with type 0. That writes
the disk, so every `iput` has to be inside a transaction. The count and
the number of names are different things: a deleted file is emptied only
when the last process holding it lets go, which is why a program can keep
reading a file that has just been removed. At boot, `main` now calls
`iinit` to set up the table's locks.

### `bmap`

Every read and write of a file asks it the same question: which disk
block holds block `n` of this file? `bmap(ip, bn)` answers from the
direct list or the indirect block, and when a write reaches a block that
does not exist yet, it gets one from the allocator on the spot.

### `readi`

Everything that reads a file comes here: the `read` system call, `exec`
loading a program, a directory search. `readi` copies a range of bytes
out of the file, block by block, into user or kernel memory, and stops at
the end of the file.

### `writei`

The mirror image, for the `write` system call and for adding names to
directories. `writei` copies bytes into the file block by block, logging
each block it changes, and grows the file's size when it writes past the
end.

### `itrunc`

Called when a file is deleted and the last user lets go of it, and when a
file is opened for rewriting from scratch. `itrunc` gives every block
back to the allocator and sets the size to 0.

## How it works

### Writing `bmap`, step by step

1. **Direct blocks first.** For `bn` below 12 the answer is in the inode.
   If the entry is 0, the block does not exist yet: get one from `balloc`
   and remember it there. If `balloc` returns 0, the disk is full; return
   0 and let the caller stop.
   ```
     if(bn < NDIRECT){
       if((addr = ip->addrs[bn]) == 0){
         addr = balloc(ip->dev);
         if(addr == 0)
           return 0;
         ip->addrs[bn] = addr;
       }
       return addr;
     }
   ```
2. **Past 12, go through the indirect block.** Subtract 12 to get an index
   into it, and allocate the indirect block itself the first time the file
   grows past 12 blocks, the same way as a direct one.
3. **Read the entry from the indirect block,** allocating the data block
   if the entry is 0, and log the indirect block, because it is a disk
   block that has just changed:
   ```
       if((addr = a[bn]) == 0){
         addr = balloc(ip->dev);
         if(addr){
           a[bn] = addr;
           log_write(bp);
         }
       }
   ```
4. **Past block 267:** panic. `writei` refuses such writes before they get
   here, so reaching this line is a bug.

### Writing `readi`, step by step

1. **Copy one piece per block.** Find the disk block with `bmap`, read it,
   copy the part of it that falls inside the request, release it, and
   move on by the size of the piece.
   ```
     for(tot=0; tot<n; tot+=m, off+=m, dst+=m){
       uint addr = bmap(ip, off/BSIZE);
       ...
       bp = bread(ip->dev, addr);
       m = min(n - tot, BSIZE - off%BSIZE);
       if(either_copyout(user_dst, dst, bp->data + (off % BSIZE), m) == -1) {
         ...
       }
       brelse(bp);
     }
     return tot;
   ```
   `either_copyout` copies to a user address or a kernel one, as
   `user_dst` says. The user half, `copyout` in `vm.c`, copies through a
   process's page table; nothing passes a user address before module 06.
2. **Refuse or trim the request** before the loop. Starting past the end
   reads nothing, and an `off + n` so large that it wraps around is
   refused the same way; running past the end is cut at the file's size,
   as shown below.
   ```
     if(off > ip->size || off + n < off)
       return 0;
   ```
3. **Fail cleanly:** if the destination address is bad, the copy fails and
   `readi` returns -1.

### Writing `writei`, step by step

1. **Run `readi`'s loop the other way round:** `bmap`, which allocates as
   needed, read the block, copy the caller's bytes in, and log the block
   instead of writing it.
   ```
     for(tot=0; tot<n; tot+=m, off+=m, src+=m){
       uint addr = bmap(ip, off/BSIZE);
       ...
       bp = bread(ip->dev, addr);
       m = min(n - tot, BSIZE - off%BSIZE);
       if(either_copyin(bp->data + (off % BSIZE), user_src, src, m) == -1) {
         ...
       }
       log_write(bp);
       brelse(bp);
     }
   ```
2. **Refuse a write that starts past the end,** which would leave a hole,
   or one that would make the file bigger than 268 blocks.
   ```
     if(off > ip->size || off + n < off)
       return -1;
     if(off + n > MAXFILE*BSIZE)
       return -1;
   ```
3. **Stop early** if the disk is full or the source address is bad, and
   report how much was written. A bad address can stop the copy part way
   through a block, so log that block anyway: the bytes already in it would
   otherwise be lost when the cache lets it go.
   ```
       if(either_copyin(bp->data + (off % BSIZE), user_src, src, m) == -1) {
         log_write(bp);   // the copy may have changed part of the block
         brelse(bp);
         break;
       }
   ```
4. **Grow the size and write the inode back.** The size grows if the
   write went past the old end; the inode is written back every time, and
   why is below.
   ```
     if(off > ip->size)
       ip->size = off;
     ...
     iupdate(ip);
   ```

### Writing `itrunc`, step by step

1. **Free the direct blocks** and zero their entries, then set the size to
   0 and write the inode back, so the disk agrees.
   ```
     for(i = 0; i < NDIRECT; i++){
       if(ip->addrs[i]){
         bfree(ip->dev, ip->addrs[i]);
         ip->addrs[i] = 0;
       }
     }
     ...
     ip->size = 0;
     iupdate(ip);
   ```
2. **Free every block the indirect block lists,** then the indirect block
   itself, in that order; why is below.
3. **Zero the inode's entries as their blocks are freed.** Without it, the
   next truncation of this inode would free the same blocks again, and by
   then one of them may belong to another file.

### Why it is built this way

**The size says where a file ends, not the blocks.** The last block of a
file is usually only partly used, and the rest of it holds zeros. So
`readi` cuts every request at the file's size before it reads anything:

```
  if(off + n > ip->size)
    n = ip->size - off;
```

Then it copies in pieces: from the starting offset to the end of that
block, then whole blocks, then the part of the last block that is wanted.
Each piece is the smaller of "what is left of the request" and "what is
left of this block".

![`readi` clamps the request to the file's size, then copies it one block at a time.](figures/05.05-readi-pieces.svg)

**No holes.** `writei` refuses to start past the end of the file, so
every block below the file's size exists. Together with the clamp, that
means `readi` only ever asks `bmap` for blocks that are there, and a read
never allocates. One that did would change the bitmap and the inode from
inside a read, outside any transaction.

**The inode goes back to disk after every write.** When `bmap` allocates a
direct block, it changes only the in-memory copy of the inode. So
`writei` always ends by writing the inode back through the log, even when
the size did not change; otherwise the file's new block would be
forgotten at the next boot. A new entry in the indirect block is
different: that block is a disk block in its own right, and `bmap` logs it
when it changes.

**Free the entries before the indirect block.** `itrunc` frees each block
listed in the indirect block, and only then the indirect block itself.
Freed first, the indirect block could be handed to another file, and the
list of blocks still to free would be overwritten.

## Break it

Give the inode one more direct block. In
`build/at/xv6/05.05/kernel/fs.h`:

<!-- verify: patch file=kernel/fs.h

@block
-->
```
#define NDIRECT 13
```

Run it again. It does not get as far as booting; the build stops in
`mkfs`:

<!-- verify: session run="./learn run xv6 --at 05.05" build-fails="Assertion failed" more -->
```
Assertion failed: ((BSIZE % sizeof(struct dinode)) == 0), function main, file mkfs.c, line 95.
```

<!-- verify: mention names="build/at/xv6/05.05/build/mkfs.log" outside reason="a file the build writes, not one of the project's sources" -->
The record is now 68 bytes, and 1024 is not a multiple of 68: fifteen
records would fit in a block with 4 bytes left over. Nothing in the
kernel's arithmetic would break, since it finds inode `n` with the same
count of inodes per block that `mkfs` uses, but `mkfs` insists that
records fill a block exactly and stops on any size that does not. Make
it 28 instead: the record is 128 bytes, the build goes through, and
`build/at/xv6/05.05/build/mkfs.log` shows what the bigger record costs:

<!-- verify: patch file=kernel/fs.h
-#define NDIRECT 13
+#define NDIRECT 28
-->
<!-- verify: file path=build/mkfs.log -->
```
nmeta 60 (boot, super, log blocks 31, inode blocks 26, bitmap blocks 1) blocks 1940 total 2000
```

Eight inodes to a block, so the 200 inodes take 26 blocks instead of 13,
and every region after them moves. The size of one record is part of the
disk's format, which is why `mkfs` and the kernel take it from the same
`fs.h`.

## Decide the boundary

xv6 finds a block with a fixed array: 12 direct pointers, one indirect block. Small
files cost one disk read for the inode and nothing more; the maximum is 268 KB.
Unix kept going: a double-indirect block multiplies the limit by 256 and costs one
more disk read per far-away block. ext4 stores extents, "N blocks starting at
block B", which describe a contiguous 1 GB file in a few bytes and need no
per-block lookup, and pays in complexity when a file is fragmented. FAT chains
blocks in a table and pays in seeking, since reaching byte N means walking N/BSIZE
links.
