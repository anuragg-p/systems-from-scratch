# 05.07 Open files

This lesson covers open files: the shared record that stands between a
process's file descriptor and the file, pipe or device underneath.

## Where this fits

![Where 05.07 fits](figures/05.07-map.svg)

Open files are the top of the storage stack and the bottom of what a user
program sees. Above them, each process's file descriptors point at open
files, and the read, write and close system calls of module 06 go through
them. Below, an open file refers to a file from the last lessons, to a
device such as the console, or to a pipe. After this lesson the kernel can
hand a process something to read and write without the process needing
to know what is underneath.

## The idea

![`dup` and `fork` share one `struct file` and its offset; a second `open` gets its own, over the same inode.](figures/05.07-fd-file-inode.svg)

**The need.** Type `(echo a; echo b) > out` at the shell. The shell opens
`out` once and two processes write to it, one after the other, through
the same descriptor. The second must write after the first, not over it,
so the two processes must share one position in the file. A program
reading descriptor 0 also should not need to care whether it is the
console, a file or a pipe.

**The idea.** Keep one system-wide table of **open files**. Each entry
records what kind of thing is underneath and points at it, whether it may
be read or written, and, for a file, the **offset**: where the next read
or write happens. A process's descriptor is just a small number that
indexes the process's own array of pointers into this table.

Opening a file makes a new entry. Duplicating a descriptor, with `dup` or
by `fork` copying all of them, does not; it makes one more pointer to the
same entry, so both share its offset. Two separate `open` calls of the same
file make two entries, each with its own offset, over one inode. Each
entry counts how many descriptors point at it, and it is freed, and the
thing underneath let go, when the count reaches zero.

### `filealloc`

The `open` and `pipe` system calls of module 06 will call it when they
need a fresh open file. `filealloc` finds an unused entry in the table,
gives it a count of 1 and returns it, or returns 0 if all 100 are in use.
At boot, `main` now calls `fileinit` to set up the table's lock.

### `filedup`

Called by `dup` (06.07), and by `fork` (06.04) for every descriptor the
child inherits. `filedup` adds one to the entry's count.

### `fileclose`

Called by `close` and, for every descriptor still open, by `exit`.
`fileclose` takes one from the count; when it reaches zero, it frees the
entry and lets go of what is underneath: it releases the inode inside a
log operation, and from lesson 06.06 on it closes its end of a pipe.

### `devsw`

A device has no blocks; reading it means asking its driver. Each device
has a **major number**, its index in `devsw`, a table of each driver's
read and write functions. A device file is an inode of type device that
records the major number (05.05's `major`); `mknod` (06.07) makes one,
`open` copies the number into the open file, and `fileread` and
`filewrite` call through `devsw[f->major]`. The console is major 1,
`CONSOLE`, and `consoleinit` now fills in its entry at boot.

### `consolewrite`

The console's write, for every `printf` a user program will make. It
sends each byte with `uartputc`, new in `uart.c`: it puts the byte in the
UART's output buffer and, when the buffer is full, sleeps until the UART
interrupt has sent some (`uartstart` now wakes it). The kernel's own
`printf` keeps `uartputc_sync`, which spins until the byte is out and
works even with interrupts off; a process writing a lot of output should
give the hart away instead.

### `consoleread`

The other half of the console input path of 03.03 and 04.03: the
interrupt handler collects a line, and this is where a process waits for
it. It sleeps on the input buffer's read index until a whole line has
arrived, then copies bytes up to and including the newline. A Control-D
ends the read; if some bytes came before it, it is kept for the next
read, which then returns 0, the way a program sees end of input. Before
each sleep it checks `killed`, a flag set when the process is to be
killed (06.01), so a process waiting for a line it will never get can
still be ended.

## How it works

### Writing `fileclose`, step by step

1. **Drop one reference under `ftable.lock`.** Panic if there were none,
   which means a double close; return if others remain.
   ```
     acquire(&ftable.lock);
     if(f->ref < 1)
       panic("fileclose");
     if(--f->ref > 0){
       release(&ftable.lock);
       return;
     }
     ...
     release(&ftable.lock);
   ```
2. **For the last reference, copy the entry and free the slot,**
   `ref = 0` and `FD_NONE`, while the lock is still held.
3. **Release the lock, then close what is underneath,** from the copy:
   the inode inside `begin_op` and `end_op`, since letting go of an inode
   can free a deleted file's blocks, which is a change to the disk. A
   device file is an inode too, so it goes the same way.
   ```
     if(ff.type == FD_INODE || ff.type == FD_DEVICE){
       begin_op();
       iput(ff.ip);
       end_op();
     }
   ```
   Lesson 06.06 adds the other case here, closing a pipe's end.

### Writing `filewrite` (in `file.c`), step by step

`fileread` is the same dispatch in the other direction, and needs no
transaction, since a read changes nothing on the disk. `filewrite` is
longer, because a write does change it. (`filestat`, for the `fstat` call, copies an
inode's `struct stat` out to the program. It zeroes the struct first, so the
padding between its fields carries no old bytes of the kernel's stack out
with it.)

1. **Check the open file allows writing, then go by its type.** A
   negative count is refused here too, as in `fileread`, before code below
   (`readi`, `writei`) takes it for a huge unsigned one. A device is
   reached through `devsw` by its major number; the `1` says `addr` is a
   user address.
   ```
     if(f->writable == 0 || n < 0)
       return -1;

     if(f->type == FD_DEVICE){
       ...
       ret = devsw[f->major].write(1, addr, n);
     } else if(f->type == FD_INODE){
       ...
     } else {
       panic("filewrite");
     }
   ```
2. **A file is written at the open file's offset,** which then moves on,
   all under the inode's lock, so two processes sharing the open file
   cannot both write at the same offset.
   ```
         ilock(f->ip);
         if ((r = writei(f->ip, 1, addr + i, f->off, n1)) > 0)
           f->off += r;
         iunlock(f->ip);
   ```
3. **In pieces that fit in one transaction.** One operation may log at
   most 10 blocks (05.04). Take away the inode, the indirect block and two
   blocks for unaligned ends, and halve the rest, since each new data
   block may also change a bitmap block: 3072 bytes. Each piece gets its
   own `begin_op` and `end_op`.
   ```
       int max = ((MAXOPBLOCKS-1-1-2) / 2) * BSIZE;
   ```
4. **Stop at the first short piece,** a full disk or a bad address, and
   return -1 unless every byte was written.

### Why it is built this way

**The offset belongs to the open file, not the descriptor.** This is the
choice the whole table exists for. Since `dup` and `fork` share the entry,
a parent and child that inherited the shell's output write one after the
other into the same file instead of over each other, and a shell can
redirect a command's output just by putting a different open file in
slot 1 before running it.

**Close the thing underneath after letting go of the table.** When the
count reaches zero, `fileclose` copies the entry, marks the slot free, and
releases the table's spinlock before it does the real closing:

```
  ff = *f;
  f->ref = 0;
  f->type = FD_NONE;
  release(&ftable.lock);
```

Releasing an inode can mean freeing a deleted file's blocks, which waits
for the disk, and a process must not sleep while holding a spinlock. The
copy is needed because, once the lock is released, another process may
take the slot for a new file at once.

**One kind of record, three kinds of thing.** The reading and writing code
looks at the entry's type. A file goes to the inode functions at the
entry's offset, then moves the offset on. A device goes to its driver
through `devsw`, and has no offset at all. The third kind, a pipe, comes
with 06.06, which adds a branch for it to `fileread`, `filewrite` and
`fileclose` that goes to the pipe's own functions. A program reading
descriptor 0 never learns which of the three it has.

The **invariant**: an open file stays valid while any descriptor points
at it. Its count is changed only under the table's lock, raised by
`filealloc` and `filedup` and lowered by `fileclose`.

## Break it

Nothing shares or closes an open file until there is a shell, so this
experiment runs on the 07.02 build: make the change in
`build/at/xv6/07.02/kernel/file.c` and run `./learn run xv6 --at 07.02`.
In `filedup`, delete the `f->ref++;` line. The shell starts; type
`echo hi`:

<!-- verify: patch file=kernel/file.c at=07.02
-  f->ref++;
-->
<!-- verify: session run="./learn run xv6 --at 07.02" panics=fileclose -->
```
$ echo hi
hi
panic: fileclose
```

`init` opens the console once and hands it to descriptors 0, 1 and 2
with `dup`, and every `fork` copies them, all through `filedup`. None of
that was counted, so the console's open file still said 1 while
descriptors in `init`, the shell and the `echo` child pointed at it.
When `echo` exited, its first `fileclose` took the count to 0 and freed
the slot, and the next one found a count below 1.

## Decide the boundary

xv6 has two tables: per-process descriptors, and a global open-file table with
shared offsets. That split is how Unix gets `dup` and `fork` to share a position,
and how a shell redirects output by swapping a slot. Another kernel could keep the
offset in the descriptor and make `dup` copy it. That is simpler and needs no
global lock, and pays by breaking the rule that `fork` leaves parent and child
writing to one file in order. Windows
hands out opaque handles to kernel objects, a third answer.

Should two descriptors that came from one `open` share a position, or each have their own?
