# 05.06 Directories and path names

This lesson covers directories and path names: how the kernel turns a name
like `/d/../README` into the file it names.

## Where this fits

![Where 05.06 fits](figures/05.06-map.svg)

Directories sit on top of files: a directory is a file whose contents are
a list of names. Above them, every system call that takes a name, opening
a file, creating one, deleting one, changing directory, running a
program, will ask the path walker here for the file. Below, they read and
write directory contents with the file functions from the last lesson.
After this lesson the kernel can find any file by its path, starting from
the root or from a process's current directory.

## The idea

![A `struct dirent` is 16 bytes. A 14-character name fills its field with no NUL after it.](figures/05.06-dirent.svg)

**The need.** Programs name files with paths: `cat /d/notes`. The file
system knows files only by inode number. Something has to turn the one
into the other, and also record new names when files are created.

**The idea.** A **directory** is an ordinary file, marked as a directory,
whose contents are a list of fixed 16-byte entries: an inode number and a
name of up to 14 characters. Finding a name in a directory means reading
its entries until one matches. An entry with inode number 0 is an empty
slot.

A path is a chain of such lookups, one per element. `/d/notes` starts at
the root directory, which is always inode 1, looks up `d` there, then
looks up `notes` inside `d`. A path without a leading slash starts at the
process's current directory instead.

There is nothing special about `.` and `..`. Every directory is created
with two real entries: `.` holds its own inode number, `..` its parent's.
So `/d/../README` is three ordinary lookups: `d` in the root, `..` in `d`,
which leads back to the root, and `README` there.

![`/d/../README` after `mkdir d` on the 07.03 disk: three directory scans, with `..` found like any other name.](figures/05.06-path-walk.svg)

### `dirlookup`

One lookup in one directory, used by the path walker for every element
and by system calls that check whether a name exists.
`dirlookup(dp, name, &off)` reads the entries with `readi`, and on a
match returns the named inode, referenced but not locked, and the entry's
position in the directory.

### `dirlink`

The other direction: creating a file, a directory or a link adds a name.
A **link** is a second entry for an inode that already has one; the
inode's `nlink` counts its names. `dirlink(dp, name, inum)` refuses a name
that is already there, then writes the new entry into the first empty
slot or at the end, with `writei`.

### `skipelem`

The string work of a path walk. `skipelem(path, name)` copies the first
element of a path into `name` and returns the rest, so the walker can
take one element per step: `"a/bb/c"` gives `"a"` and leaves `"bb/c"`.

### `namex`

The path walker itself, behind `namei` ("the file this path names") and
`nameiparent` ("the directory that holds this path's last name"). It
starts at the root or the current directory and calls `dirlookup` once
per element. Each step lets go of the directory it leaves with `iput`,
and that can be the last reference to a directory someone removed in the
meantime, which frees it and writes the disk (05.05). So a path walk
runs inside a transaction; the system calls of module 06 open it.


Each line is one entry: a 2-byte inode number, then 14 bytes of name
padded with zeros. `.` and `..` both hold inode 1, so the root is its own
parent and `/..` leads back to `/` with no special case anywhere.
`README` is inode 2. The rest of the block is zeros, empty slots: `mkfs`
rounded the root's size up to the whole block, so a lookup in it reads
all 64 slots, while a directory the kernel makes grows one entry at a
time.

## How it works

### Writing `dirlookup`, step by step

1. **Read the directory one entry at a time** with `readi`, from offset 0
   to its size, and compare names. A directory is a file of 16-byte
   entries, so this is all a lookup is.
   ```
     for(off = 0; off < dp->size; off += sizeof(de)){
       if(readi(dp, 0, (uint64)&de, off, sizeof(de)) != sizeof(de))
         panic("dirlookup read");
       ...
       if(namecmp(name, de.name) == 0){
         ...
         inum = de.inum;
         return iget(dp->dev, inum);
       }
     }
     return 0;
   ```
   `namecmp` compares at most 14 characters, and `iget` returns the inode
   referenced but not locked, which `namex` relies on below. A directory's
   size is always a whole number of entries, so a short read means the
   directory is damaged, and the kernel stops.
2. **Skip empty slots,** the entries whose inode number is 0. Removing a
   name leaves one behind.
3. **Report where the entry is** through `poff` when the caller asks:
   removing a name (06.07) needs the offset to clear the entry.
4. **Insist on a directory;** anything else is a bug in the caller.

### Writing `dirlink`, step by step

1. **Write the new entry at offset `off`.** `strncpy` pads the name with
   zeros and leaves a 14-character name unterminated; `writei` appends
   when `off` is the end of the directory.
   ```
     strncpy(de.name, name, DIRSIZ);
     de.inum = inum;
     if(writei(dp, 0, (uint64)&de, off, sizeof(de)) != sizeof(de))
       return -1;

     return 0;
   ```
2. **Find the slot:** the first entry whose inode number is 0, so the room
   a removed name left is used again. When there is none, the loop runs off
   the end and `off` is just past the last entry.
3. **Refuse a duplicate:** look the name up first, and give back the
   reference if it is found.

### Writing `skipelem`, step by step

1. **Skip leading slashes, then measure the element** up to the next slash
   or the end. If nothing is left after the slashes, return 0: the path is
   used up.
   ```
     while(*path == '/')
       path++;
     if(*path == 0)
       return 0;
     s = path;
     while(*path != '/' && *path != 0)
       path++;
     len = path - s;
     ...
     return path;
   ```
2. **Copy it into `name`:** whole, with a terminating zero, if it is
   shorter than 14 characters; otherwise exactly 14 bytes, which cuts a
   longer name.
3. **Skip the slashes after it** before returning the rest, so the caller
   can tell by an empty rest that this was the last element.

### Writing `namex`, step by step

1. **Start somewhere and take one element per pass.** The start is the
   root inode for a path beginning with `/`, otherwise the current
   directory, with `idup`, which takes one more reference to it, so the
   walk owns a reference of its own. Each pass locks the current
   directory, looks the next element up in it, and moves on to what it
   found.
   ```
     if(*path == '/')
       ip = iget(ROOTDEV, ROOTINO);
     else
       ip = idup(myproc()->cwd);

     while((path = skipelem(path, name)) != 0){
       ilock(ip);
       ...
       ip = next;
     }
     ...
     return ip;
   ```
   How the lookup lets go of one directory before taking the next is below.
2. **Fail if the current inode is not a directory,** as in
   `/README/x`, or is a directory that has been removed: a process can
   still stand in one, and its `..` may name a directory already freed.
   ```
       if(ip->nlink == 0){   // removed: its ".." may be gone too
         iunlockput(ip);
         return 0;
       }
   ```
3. **For `nameiparent`, stop one step early:** when the element just
   taken is the last one, return the directory, unlocked.
   ```
       if(nameiparent && *path == '\0'){
         // Stop one level early.
         iunlock(ip);
         return ip;
       }
   ```
4. **At the end with `nameiparent` set,** the path had no last element (it
   was `/`), so release the inode and fail.

### Why it is built this way

**One lock at a time.** To search a directory, the walker must lock it.
It would be natural to keep the parent locked while locking the child,
but that deadlocks. Looking up `.` returns the directory itself, so the
walker would wait for a lock it already holds. And `..` lets two walks
meet head on: one walking `a/..` holds `a` and wants its parent, while
another walking down holds the parent and wants `a`, and both wait
forever. So `namex` never holds two:

```
    if((next = dirlookup(ip, name, 0)) == 0){
      iunlockput(ip);
      return 0;
    }
    iunlockput(ip);
    ip = next;
```

This works because `dirlookup` returns the next inode with a reference
but without its lock. The reference keeps the inode in the kernel's table
while the walker unlocks and lets go of the current directory
(`iunlockput` is `iunlock` then `iput`); the lock is taken at the top of
the next step. That is the **invariant**: at most one inode lock held by
the walk at any moment.

**Stopping one step early.** Creating `/d/notes` needs the directory `d`,
to add a name to, and the last element, `notes`. Walking all the way would
fail, since `notes` does not exist yet. So with `nameiparent` set, the loop
stops when the element it just took was the last one, and returns the
directory with the name copied out. `skipelem` strips the slashes after
each element precisely so the walker can tell, by an empty rest, that it
has reached the last one.

**Names of exactly 14 characters.** A name field is 14 bytes with no room
for a terminating zero, so a 14-character name is stored without one.
Every comparison therefore uses `strncmp` limited to 14, and a longer name
in a path is cut to 14 by `skipelem`: `abcdefghijklmnopqrst` names the
same file as `abcdefghijklmn`.

**One name, one entry.** `dirlink` looks the name up before it adds it and
fails if it is there. It is the only place that checks: the system calls
that add names, such as `link`, rely on it.

## Break it

Nothing adds a name until there is a shell with `ln`, so this experiment
runs on the 07.03 build: make the change in
`build/at/xv6/07.03/kernel/fs.c` and run `./learn run xv6 --at 07.03`.
In `dirlink`, delete the duplicate check:

```
  if((ip = dirlookup(dp, name, 0)) != 0){
    iput(ip);
    return -1;
  }
```

Link the same name twice, then remove it:

<!-- verify: session run="./learn run xv6 --at 07.03" -->
```
$ ln README x
$ ln README x
$ rm x
$ ls x
x              2 2 480
$ rm x
$ ls x
ls: cannot open x
```

With the check, the second `ln` prints `link README x: failed`. Without
it the directory holds two entries named `x`. `rm` removes the one
`dirlookup` finds first, and the name is still there; it takes a second
`rm` to make it go.

## Decide the boundary

xv6 stores names in 16-byte slots and finds one by reading the whole directory.
The limit is 14 characters and a lookup costs one read per 64 entries. Linux
filesystems keep names up to 255 bytes and index big directories with hash trees
(ext4's htree) or B-trees (XFS), so a lookup in a directory of a million files
touches a handful of blocks; they pay in format complexity and in rebalancing on
every create and unlink. Another choice is a flat namespace with no directories at
all, where a name is a key and the cost moves into whoever lists or groups files.

How many entries will one directory hold, and how long does a name need to be?
