# 05.01 The virtio block device

Everything the file system keeps ends up on a disk, and this lesson covers
the driver that moves one block at a time between memory and that disk.

## Where this fits

![Where 05.01 fits](figures/05.01-map.svg)

The disk driver is the bottom of the storage stack and the only code that
talks to the disk. Above it, a cache of disk blocks will ask it for every
block it needs, and above that come the log, files, directories and open
files, each built on the layer below. Below it is the virtual disk that
QEMU provides, and the interrupt path from module 03 that tells the kernel
a request has finished. After this lesson the kernel knows how to read
and write any block of a disk; the disk image to read arrives in 05.03.

## The idea

![Reading block 1: the header says what to do, the second descriptor says where the data goes, and the device fills in the status byte.](figures/05.01-descriptor-chain.svg)

**Where this module goes.** Processes can run and wait (module 04), but
they have nothing to keep. Module 05 builds a file system from the bottom
up: a driver for the disk (this lesson), a cache of disk blocks (05.02),
the layout of the disk and a block allocator (05.03), a log that makes
multi-block updates survive a crash (05.04), files (05.05), names for them
in directories (05.06), and the open files a process holds (05.07). Each
layer uses only the ones below it. Module 06 then lets user programs reach
all of it through system calls.

**The need.** The file system thinks in 1024-byte blocks numbered from 0:
"give me block 47". The disk is a separate device that works in its own
time, and a request takes far longer than thousands of instructions. The
kernel needs a way to say "read block 47 into this buffer", let the
requesting process sleep while the device works, and wake it when the
data is there.

**The idea.** QEMU's disk is a **virtio** device: instead of imitating a
real disk controller, it shares a few tables in ordinary RAM with the
driver. To make a request, the driver writes three small records, a
**descriptor chain**: a header that says what to do ("read, starting at
sector 2"), a pointer to the buffer for the data, and one byte where the
device will write a status. It posts the chain in a ring the device
watches, pokes one register to say "look", and puts the process to sleep.

The device does the transfer by itself, straight into or out of the
buffer, then posts the finished chain in a second ring and raises an
interrupt. The interrupt handler finds the request, marks the buffer as
done and wakes the sleeping process. Nothing waits in a loop; the hart
runs other processes while the disk works.

### `buf.h`

The driver moves one `struct buf` at a time: a block's 1024 bytes in
`data`, the number of the block they belong to in `blockno`, and a flag
`disk` that is 1 while the device has the buffer. The driver never makes
one of these. From 05.02 the buffer cache owns them all and hands one to
the driver for each transfer.

### `virtio_disk_rw`

The buffer cache will call it whenever it needs a block read from the
disk or written back. It builds the three-descriptor request for
`b->blockno`, posts it, and sleeps until the interrupt says the device is
done. It is the only way data reaches or leaves the disk.

### `virtio_disk_intr`

The other half, called by the kernel's interrupt dispatch, `devintr`,
when the disk raises its interrupt. It goes through every request the
device has finished since last time and wakes the process waiting on
each. This lesson adds the disk's case to `devintr` and enables the
disk's interrupt line in the PLIC (03.03), so the interrupt reaches it.

## Run it

```
./learn run xv6 --at 05.01
```

The boot looks as it did in 04.04. Nothing calls the driver at this
lesson: `main` starts it from 05.03 on, and the first read waits for the
first process, in 07.02. What you can look at is the device slot the
driver talks to. Press Control-a c for the QEMU monitor and read its
first three registers:

<!-- verify: session run="./learn run xv6 --at 05.01" send="ctrl-a c" -->
```
(qemu) xp /3wx 0x10001000
0000000010001000: 0x74726976 0x00000002 0x00000000
```

The magic value is "virt" in ASCII, read lowest byte first; version 2 is
a modern virtio device; the device ID is 0, which means nothing is plugged
into this slot. A disk reads 2. Control-a x quits.

## How it works

### Writing `virtio_disk_init` (in `virtio_disk.c`), step by step

Before any request, the driver has to find the device, agree with it on
features, and hand it the addresses of the shared tables. It does that
once, at boot.

1. **Find the device and walk the status handshake.** Check the magic
   number and the device type, then set one status bit after another.
   Each bit tells the device how far the driver has got, and the device
   takes no requests before the last one, `DRIVER_OK`.
   ```
     if(*R(VIRTIO_MMIO_MAGIC_VALUE) != 0x74726976 ||
        ...
       panic("could not find virtio disk");
     }
     ...
     status |= VIRTIO_CONFIG_S_ACKNOWLEDGE;
     *R(VIRTIO_MMIO_STATUS) = status;
     ...
     status |= VIRTIO_CONFIG_S_DRIVER_OK;
     *R(VIRTIO_MMIO_STATUS) = status;
   ```
2. **Agree on features.** A feature is one bit: the device sets the ones
   it offers, the driver writes back the ones it will use. Clear
   everything this driver does not handle (a read-only disk, several
   queues, indirect descriptors and the like). The device may still
   refuse, so read the status again:
   ```
     status = *R(VIRTIO_MMIO_STATUS);
     if(!(status & VIRTIO_CONFIG_S_FEATURES_OK))
       panic("virtio disk FEATURES_OK unset");
   ```
3. **Give it queue 0.** Allocate a zeroed page each for the descriptor
   table and the two rings, and write their addresses into the device's
   registers. The device reads RAM directly, by physical address, so each
   table must sit in one physically contiguous piece; a page from `kalloc`
   is, and the kernel maps RAM at the same addresses (02.04), so its
   pointer is the physical address. Zeroed, because the device must not
   find stale entries in a ring.
   ```
     *R(VIRTIO_MMIO_QUEUE_DESC_LOW) = (uint64)disk.desc;
     *R(VIRTIO_MMIO_QUEUE_DESC_HIGH) = (uint64)disk.desc >> 32;
   ```
4. **Mark all eight descriptors free.** The driver's own record starts out
   zeroed, which means "in use"; without this the first request would wait
   for a descriptor forever.

### Writing `virtio_disk_rw`, step by step

1. **Post a request, then sleep until it is done.** The skeleton: turn the
   block into a sector (the device counts 512-byte sectors, a block is
   1024 bytes), mark the buffer as the device's, post the request, and
   sleep until the interrupt handler clears the mark. All of it under the
   driver's lock, which the handler takes too.
   ```
     uint64 sector = b->blockno * (BSIZE / 512);

     acquire(&disk.vdisk_lock);
     ...
     b->disk = 1;
     ...
     while(b->disk == 1) {
       sleep(b, &disk.vdisk_lock);
     }
     ...
     release(&disk.vdisk_lock);
   ```
2. **Get three descriptors, or wait for them.** A request needs three, and
   with eight in the table, two requests in flight leave only two. Then
   the process sleeps until a finished request gives some back;
   `free_desc` wakes that channel.
   ```
     while(1){
       if(alloc3_desc(idx) == 0) {
         break;
       }
       sleep(&disk.free[0], &disk.vdisk_lock);
     }
   ```
3. **Build the chain:** the header (read or write, and the sector), the
   data descriptor pointing at `b->data`, and the status byte. The data's
   `WRITE` flag is from the device's point of view, so it is set for a
   read:
   ```
     if(write)
       disk.desc[idx[1]].flags = 0; // device reads b->data
     else
       disk.desc[idx[1]].flags = VRING_DESC_F_WRITE; // device writes b->data
   ```
   The status byte starts at 0xff, so that the device's 0 for success is
   something it really wrote.
4. **Publish it:** record the buffer in `disk.info[]` under the chain's
   first index so the interrupt handler can find it, put that index in
   the avail ring, count it, and write to `QUEUE_NOTIFY`. The fences
   between those writes are explained below.
5. **Clean up** after waking: forget the buffer and free the chain, which
   also wakes anyone waiting for descriptors.

### Writing `virtio_disk_intr`, step by step

1. **Wake the owner of every finished request.** Under the same lock as
   the requesters, walk the used ring from `disk.used_idx`, how far the
   driver has read, to `disk.used->idx`, how far the device has written.
   One interrupt can stand for several finished requests.
   ```
     acquire(&disk.vdisk_lock);
     ...
     while(disk.used_idx != disk.used->idx){
       ...
       int id = disk.used->ring[disk.used_idx % NUM].id;
       ...
       struct buf *b = disk.info[id].b;
       b->disk = 0;   // disk is done with buf
       wakeup(b);
       disk.used_idx += 1;
     }
   ```
2. **Acknowledge before the loop.** The device raises no new interrupt
   until this one is acknowledged, by writing back the bits of its
   interrupt status. There are two: bit 0 says the used ring changed,
   bit 1 that the device's configuration did; `& 0x3` acknowledges
   exactly those. A request that finishes while the loop runs is picked
   up now or by the next interrupt, never missed.
   ```
     *R(VIRTIO_MMIO_INTERRUPT_ACK) = *R(VIRTIO_MMIO_INTERRUPT_STATUS) & 0x3;
   ```
3. **Check the status byte** of each request before waking its owner, and
   panic if it is not 0: a failed transfer would otherwise hand the file
   system a buffer of garbage as if it were the block.

### Why it is built this way

**Blocks are not sectors.** A disk sector is 512 bytes and a file system
block is 1024, so the request asks for sector `blockno * 2`:

```
  uint64 sector = b->blockno * (BSIZE / 512);
```

Get this wrong and every transfer still succeeds; it just reads the wrong
place.

**Publish the request before the count.** The driver tells the device
about a new request in two stores: the chain's first index into the next
slot of the avail ring, then one more in the ring's count, `avail->idx`.
The device is running at the same time and reads the count first, so the
order matters:

```
  disk.avail->ring[disk.avail->idx % NUM] = idx[0];
  __sync_synchronize();
  disk.avail->idx += 1; // not % NUM ...
```

The fence stops the compiler and the CPU from making the new count
visible before the entry it counts. Without it, the device could fetch a
stale slot and run someone else's old request. The second fence, before
the write to `QUEUE_NOTIFY`, does the same for the count itself: once
notified, the device looks at once. The interrupt handler mirrors this
with a fence inside its loop, so it reads a used-ring entry only after
the count that says the entry is there.

The count is never taken `% NUM`: it runs freely and wraps at 65536, and
only the slot number is reduced. That is why `NUM` must be a power of
two, as the spec requires: 65536 divides evenly by it, so the slot
sequence stays unbroken when the count wraps.

**Sleep and wake under the same lock.** The process sleeps until a flag on
the buffer, `b->disk`, goes back to 0, holding `vdisk_lock` while it
checks; the interrupt handler takes the same lock to clear the flag and
call `wakeup`. This is 04.03's rule, and it means the disk can finish at
any moment, even before the process has gone to sleep, and the wakeup is
not lost.

The **invariant**: `b->disk` is 1 exactly while the device owns the
buffer, and nobody touches the buffer's data between posting and the
wakeup. A descriptor is in use from the moment it is allocated until the
waiting process frees the chain.

## Decide the boundary

xv6 sends one block per request and the caller sleeps for it. Eight
descriptors allow two requests in flight, and nothing reorders them or reads
ahead. A real kernel would sort requests to cut seek time and
batch them, as Linux's block layer does with its I/O schedulers and
multi-queue (`blk-mq`) path. That pays for itself on a spinning disk or a
fast NVMe. It costs a lot of machinery in front of a disk that here is a
file on the host.

With the disk already the slowest thing in the machine, is it worth adding
a request queue to hide that, or is one request at a time clear enough for
a kernel meant to be read?
