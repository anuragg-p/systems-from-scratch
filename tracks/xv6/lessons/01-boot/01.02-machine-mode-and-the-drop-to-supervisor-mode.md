# 01.02 Machine mode and the drop to supervisor mode

`start()` moves each hart from machine mode, where it wakes up, to supervisor
mode, where the rest of the kernel runs, and on the way does the few jobs
that only machine mode can do.

## Where this fits

![Where 01.02 fits](figures/01.02-map.svg)

This is the second half of boot. The lesson before gave every hart a
stack; this one makes the call into C, and takes each hart down from the
most powerful privilege level to the one the kernel lives in. Everything above it, from
page tables to traps to user programs, assumes that level. After this lesson
the kernel's main code runs on every hart, in the right mode, with all of
memory open to it.

## The idea

![`start` puts S in `mstatus.MPP` and the address of `main` in `mepc`. `mret` takes the mode from one and the pc from the other.](figures/01.02-mret.svg)

A RISC-V hart has three privilege levels. **Machine mode** (M-mode) can do
anything and no memory protection applies to it; every hart wakes up there.
**Supervisor mode** (S-mode) is where an operating system kernel belongs:
paging works there, and traps from user programs arrive there. **User mode**
is for the programs.

So the kernel has to get from M-mode to S-mode, and there is no instruction
that says "switch to supervisor mode". There is only `mret`, "return from a
machine-mode trap". It goes back to whatever mode the trap came from, which
the hardware recorded in a field of `mstatus` called `MPP`, and to whatever
address it recorded in `mepc`.

The trick is to fake that record. Write "supervisor" into `MPP`, write the
address of `main` into `mepc`, and execute `mret`. The hart "returns" from a
trap that never happened, lands at the first instruction of `main`, and is
in S-mode.

There is a catch: some settings can only be written from M-mode, and once
the kernel leaves it never comes back. So everything machine mode must
arrange happens first, in the same function: hand every trap down to
S-mode, open memory to S-mode, and note the hart number somewhere S-mode
can read it. Asking for timer interrupts is one more such job; lesson 03.02
adds it here.

### `start`

`kernel/start.c:start` is the first C function, called from `_entry` on the
hart's new stack: this lesson adds that `call start` at the end of
`_entry`. It runs once on every hart and never returns: its last
instruction is the `mret` into `main`.

### `early_puts`

`kernel/start.c:early_puts` prints a string by storing each byte straight
into the serial port's transmit register. No lock, no formatting, no setup.
It works before anything else does, which makes it the way to find out how
far a silent boot got.

### `main`, in `main.c`

`main` is where every hart lands after `mret`. For now it only parks the
hart: `wfi` ("wait for interrupt") sleeps until an interrupt arrives, and
none can yet, since no device or timer has been told to raise one. Turning
interrupts on first (`intr_on`) is what the loop will need once there are
traps to take (03.01).

### `riscv.h`

C has no way to name a CSR, so `riscv.h` wraps each read or write of one in
a one-line function, `r_mstatus`, `w_mepc` and so on, each a single
`csrr` or `csrw` instruction. `start` uses a handful; the rest wait for
later lessons.

### `defs.h`

`defs.h` declares every function one kernel file calls in another.

### `memlayout.h`

`memlayout.h` says where things are in physical memory. This lesson needs
one address from it, `UART0`, the serial port's registers, for
`early_puts`; lesson 02.01 fills in the rest.

## How it works

### Writing `start`, step by step

1. **The bare switch.** The least that reaches S-mode is three moves: set
   `mstatus.MPP` to S, put `main` in `mepc`, execute `mret`.
   ```
   void
   start(void)
   {
     unsigned long x = r_mstatus();
     x &= ~MSTATUS_MPP_MASK;
     x |= MSTATUS_MPP_S;
     w_mstatus(x);
     w_mepc((uint64)main);
     asm volatile("mret");
   }
   ```
   Clear the field before setting it: `MPP` is two bits, M is `11` and S is
   `01`, so OR-ing S into a field that holds M would still say M.
2. **Open memory, or the first fetch faults.** S-mode may touch no memory
   until machine mode allows it, through **physical memory protection**
   (PMP) entries, so fetching `main`'s first instruction would fail. One
   entry that covers every address:
   ```
   w_pmpaddr0(0x3fffffffffffffull);
   w_pmpcfg0(0xf);
   ```
3. **Hand every trap to S-mode.** The kernel never returns to M-mode, so a
   trap that went there would find no handler. `medeleg` hands down the
   exceptions (faults the running code causes) and `mideleg` the
   interrupts (from devices and timers). `sie`, which picks the interrupts
   S-mode will take, is an S-mode register that `main` could set as well;
   it is set here only to keep the trap settings together.
4. **Paging off, and the hart number kept.** `satp` points the hardware at a
   page table (02.04); `w_satp(0)` turns paging off, so `main` begins on
   physical addresses whatever state the hart was in. And S-mode cannot
   read `mhartid`, so this is the last chance to learn it: copy it into
   `tp`, which the kernel treats as "this hart's number" from now on.

Only the position of `mret` matters. Steps 2 to 4 just have to happen
before it, in any order.

### What the protection entry says

`pmpcfg0 = 0xf` is read, write and execute (the low three bits) plus a
matching mode called "top of range": the entry covers every address from 0
up to, but not including, the one in `pmpaddr0` shifted left by 2.
`0x3fffffffffffff` makes that top 0xfffffffffffffc, four bytes short of
2^56, the end of the 56-bit physical address space, so the one entry covers
all of it that any device uses.

![`pmpcfg0 = 0xf` sets read, write and execute with top-of-range matching, and `pmpaddr0` puts the top at the end of the physical address space.](figures/01.02-pmp-entry-0.svg)

### `tp` is not an ordinary register

From here on, nothing in the kernel may use `tp` for anything else; any code
that saves and restores registers has to treat it with care. The trap
handlers of 03.01 and 06.01 are where that matters.

Note what is not here: no trap vector for S-mode and no new stack. The hart
keeps its `stack0` slice, and the trap vector arrives in lesson 03.01.

## Break it

In `build/at/xv6/01.02/kernel/start.c`, comment out `w_pmpcfg0(0xf);` and
leave the rest. The console was empty anyway, so mark the way: call
`early_puts("A\n")` just before the `mret`, and `early_puts("B\n")` as the
first line of `main`. What will it print?

Three `A`s, one per hart, and their three newlines, mixed differently each
run because the harts print at the same moment (here the `A`s came first),
and never a `B`. Every hart got as far
as `mret` and not one instruction past it: S-mode has no memory permission,
so fetching the first instruction of `main` faults, and no trap handler
exists yet to report it. Put the line back and three `B`s follow the `A`s.
When the machine is silent, `early_puts` is how you bisect.

## Decide the boundary

xv6 boots with `-bios none` and enters S-mode itself. Real RISC-V systems put
**firmware** in M-mode permanently: OpenSBI (the Supervisor Binary
Interface) runs in M-mode, handles the timer, inter-hart interrupts and
console, and the kernel calls it with `ecall` while staying in S-mode. Linux
on RISC-V works that way. That keeps the kernel portable across boards and
keeps machine-specific code out of it, and costs you a second program to
trust, build and version.

xv6 skips it because there is nothing to hide the board from: the board is
QEMU `virt`. Is the kernel meant to run on one machine, or on many?
