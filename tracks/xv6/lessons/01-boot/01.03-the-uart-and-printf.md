# 01.03 The UART and printf

The kernel's `printf` is how it says anything at all: it turns a format
string and its arguments into characters and pushes them, one at a time, out
of the serial port.

## Where this fits

![Where 01.03 fits](figures/01.03-map.svg)

This lesson builds the output half of the console, the kernel's first
driver. Below it is the serial port on QEMU's machine, wired to your
terminal. Above it, every layer from here on reports what it is doing
through it, and every crash is announced through it. After this lesson the
kernel can print text and numbers, which is how every later lesson is
debugged.

## The idea

![`printint(1024, 10, 0)`: division stores the digits lowest first, and the print loop reads `buf` from the top down.](figures/01.03-printint-reverse.svg)

There is no C library in the kernel, so the kernel carries a `printf` of its
own. And the hard part of `printf` is not the text. It is the numbers.

A number in a register is binary. To show 1024 on a terminal, the kernel has
to send four characters: `1`, `0`, `2`, `4`. The way to get digits out of a
number is to divide by ten again and again, and each remainder is a digit:
1024 gives 4, then 2, then 0, then 1. Division hands out the digits
backwards.

So the idea is to collect them first and print them afterwards, in reverse:
the buffer fills with `4 2 0 1`, and reading it from the end gives `1024`.
Hex works the same way with 16 in place of 10.

Each character then travels down a short path: `printf` hands it to the
console layer, the console layer to the UART driver, and the driver stores
it into one byte-wide register of the serial chip, which sends it.

### `printint`

`kernel/printf.c:printint` turns one integer into its digits, in base 10 or
16, signed or not. `printf` calls it for `%d`, `%u`, `%x` and their `l`
forms.

### `printptr`

`kernel/printf.c:printptr` prints an address for `%p`: `0x`, then all 16 hex
digits, leading zeros kept, so every pointer prints the same width and two
of them line up.

### `console.c`

The console layer sits between `printf` and the UART. For output it passes
each character straight on; its `BACKSPACE` case is for echoing what you
type, once the keyboard works (03.03).

### `uartinit`, in `uart.c`

The chip needs setting up once before it sends anything. `uartinit` turns
its interrupts off while it works, sets the speed (38.4K baud: QEMU ignores
it, a real chip does not) and 8-bit characters, and resets the chip's
queues (FIFOs). Last it asks for interrupts on a received character or a
free transmitter; nothing listens for those until 03.03. One oddity matters
to `main`: the speed registers share addresses with others and are reached
only while a "baud latch" bit is set, so during those writes register 0 is
not the transmit register.

### `cpuid`, in `proc.c`

`main` needs to know which hart it is running on. S-mode cannot read
`mhartid`, but `start` left the number in `tp` (01.02), so `cpuid` is a
read of `tp`. `proc.c` and `proc.h` will hold processes (04.01); for now
they hold `cpus[]`, one `struct cpu` per hart, which `mycpu` finds by that
number and whose fields later lessons use. `spinlock.h` comes along
because `printf.c` and `uart.c` include it; its lock is lesson 02.03's.

### `main` waits for hart 0

All three harts arrive in `main` at once, and only one of them may set up
the console: while `uartinit` has the baud latch set, a character another
hart sent would land in a speed register instead. So hart 0 does the
setup and prints the banner, then sets `started`; the others spin until
they see it. Two details make the flag trustworthy. `started` is
`volatile`, so the waiting loop reads memory every time instead of a copy
in a register. And `__sync_synchronize()`, a fence, on both sides makes
every write hart 0 did before setting the flag visible to a hart that has
seen it, whatever order the hardware would otherwise let them arrive in.

## How it works

### Writing `printint`, step by step

1. **Peel off digits, then print them backwards.** Each remainder of a
   division is a digit, lowest first, so store them, then print the buffer
   from the end.
   ```
   printint(long long xx, int base, int sign)
   {
     char buf[24];
     ...
     do {
       buf[i++] = digits[x % base];
     } while((x /= base) != 0);
     ...
     while(--i >= 0)
       consputc(buf[i]);
   }
   ```
2. **Any base, and zero.** Looking each remainder up in `digits`,
   `"0123456789abcdef"`, lets the same loop print hex. The `do ... while`
   always produces at least one digit; a plain `while` would print nothing
   for 0.
3. **Negative numbers.** In C, `-7 % 10` is `-7`, so take the sign off
   first and keep the magnitude in an unsigned `x` (2^63, the magnitude of
   the most negative number, does not fit in a signed one). A `'-'` then
   goes on the end of the buffer, which is the front of the number.
   ```
   if(sign && (sign = (xx < 0)))
     x = -xx;
   else
     x = xx;
   ```

### Writing `printf` in `printf.c`, step by step

`printf` is the function the rest of the kernel calls. It walks the format
string, sends ordinary characters straight to the console, and hands each
`%` conversion to `printint`, `printptr` or a loop over a string.

1. **Copy text, convert `%d`.** Every character that is not `%` goes out as
   it is. After a `%`, look at the next letter and take the next argument,
   of the type that letter promises, from the variable argument list.
   ```
   va_start(ap, fmt);
   for(i = 0; (cx = fmt[i] & 0xff) != 0; i++){
     if(cx != '%'){
       consputc(cx);
       continue;
     }
     i++;
     c0 = fmt[i+0] & 0xff;
     if(c0 == 'd'){
       printint(va_arg(ap, int), 10, 1);
     }
     ...
   }
   ```
   The type in `va_arg` must match what the caller passed: `%d` with a
   64-bit argument reads only half of it.
2. **Two-letter conversions.** `%ld`, `%lu` and `%lx` need a look one
   character further, and a skip past it. That second look happens only if
   the first found a character, so a format ending in `%` is not read past
   its terminating zero.
   ```
   if(c0) c1 = fmt[i+1] & 0xff;
   ...
   } else if(c0 == 'l' && c1 == 'd'){
     printint(va_arg(ap, uint64), 10, 1);
     i += 1;
   ```
3. **Strings, and a null one.** `%s` sends characters up to the string's
   zero. A null pointer passed by mistake would fault inside `printf`, just
   as the kernel tried to say something, so it prints `(null)` instead.
4. **The odd cases.** `%%` prints one `%`. A `%` at the very end stops the
   loop, or its `i++` would step past the zero. Anything unknown is printed
   as written, `%` and letter, so a typo in a format shows up on the screen
   instead of vanishing.

### Pointers need no buffer

`printptr` is too short to need a walkthrough, and it works the other way
round. It takes the top four bits first and shifts the next four up each
time, so the most significant digit comes out first and nothing needs
reversing. It never skips a zero, which is what keeps the leading zeros.

### Output waits for the hardware, on purpose

At the bottom, `uartputc_sync` spins until the chip says it can take a
byte, then writes it. Waiting like this is slow, and it is why the kernel
can print anywhere: before interrupts exist, with interrupts off, and in the
middle of a crash. (`early_puts` from 01.02 skips the wait; QEMU's chip
never falls behind, but a real one drops bytes sent faster than it can
transmit them.)

The chip's registers are not memory. A load or store to `UART0 + n` is a
message to the device, so the driver reaches them through a `volatile`
pointer: without it the compiler could merge, reorder or drop the accesses,
as it would for ordinary memory.

![The UART's eight registers, one byte each from `UART0`, and the two that `uartputc_sync` uses.](figures/01.03-uart-registers.svg)

### A lock to come, with an exception

Lesson 02.03 gives `printf` a lock for the whole call. A panic will be the
exception: a dying hart prints even if another hart holds the lock, because
its message matters more than a tidy screen; the `panicking` flag `panic`
sets here is what will let it.

## Break it

Forget the reverse. In `build/at/xv6/01.03/kernel/printf.c`, replace the
print loop in `printint` with `for(int j = 0; j < i; j++) consputc(buf[j]);`,
so digits come out in the order they were produced. Single digits are
unaffected, so the boot still looks right. Add this to `main` after the
banner, and say what it will print before you run it:

<!-- verify: patch file=kernel/printf.c
-  while(--i >= 0)
-    consputc(buf[i]);
+  for(int j = 0; j < i; j++) consputc(buf[j]);
-->
<!-- verify: patch file=kernel/main.c
     printf("xv6 kernel is booting\n");
@block
-->
```
printf("%d %x %d\n", 1024, 0x1f2, -42);
```

<!-- verify: session run="./learn run xv6 --at 01.03" more -->
```
xv6 kernel is booting
4201 2f1 24-
```

Every number came out backwards, the minus sign last. The failure is
silent: the kernel does not know the number is wrong, and the same bug in a
pid or an address in a panic would send you looking in the wrong place.
Remove the extra line and put the `while(--i >= 0)` loop back.

## Decide the boundary

xv6 prints by polling: `uartputc_sync` busy-waits on the device for each
character. Another kernel could queue output in a buffer and let the UART
interrupt when it is ready for more, as `uartputc` does for `write()` from
lesson 05.07 on, so the CPU never waits on a 38.4K serial line. Linux
printk does something like that, writing into a ring buffer and draining it
from a console driver. The cost is more state, a lock and an interrupt
path that must itself never print, and a crash that can lose the last lines
still in the buffer.

xv6 chooses the loss-free path for the kernel's own messages. When the kernel
is dying, which would you rather have: all of its last words, or a CPU that
never waited?
