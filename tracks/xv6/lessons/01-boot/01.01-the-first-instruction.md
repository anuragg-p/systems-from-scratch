# 01.01 The first instruction

The first instructions the kernel runs give each hart its own stack, because
not one line of C can run without one.

## Where this fits

![Where 01.01 fits](figures/01.01-map.svg)

This lesson starts boot, the row just above the machine. Below it there is
only QEMU, which jumps to the kernel's first byte on every hart at the same
moment, with nothing set up. Everything above it is written in C, and C
needs a stack before it can make a single call. After this lesson every hart
has a stack of its own, ready for the first C call, which the next lesson
makes.

## The idea

![Each hart's `sp` starts at the top of its own slice of `stack0`, and its stack grows down from there.](figures/01.01-stack0-slices.svg)

Module 01 takes the machine from that first jump to a kernel that can talk:
a stack for each hart (this lesson), the move from machine mode, where a
hart wakes up, down to the less powerful supervisor mode the kernel runs in
(01.02), and printing to the serial port (01.03).

Here is the problem. Three harts arrive at 0x80000000 at once, and the stack
pointer of each holds nothing useful. The very first thing a C function does
is save its return address on the stack. With `sp` at zero, that store goes
to an address with no memory behind it, and since nothing is set up to
report a fault yet, the machine simply stops. Before any C, each hart needs
a stack, and no two harts may share one.

The idea is to carve one array into equal slices, one per hart, and let each
hart pick its slice by its own hart number. There is one twist: a stack
grows toward lower addresses, so a hart must start at the top of its slice,
not the bottom.

In this lesson's kernel the array starts at 0x80001000, so with 4096 bytes
per slice hart 0 starts at 0x80002000, hart 1 at 0x80003000 and hart 2 at
0x80004000. Each grows down toward the start of its own slice.

### `_entry`, in `entry.S`

`kernel/entry.S:_entry` is the code at the kernel's very first byte, the
place QEMU jumps to. It is six instructions of assembly, because C cannot
run yet, and all they do is work out this hart's stack pointer. The call
into C comes with lesson 01.02, together with `start`, the first C function
it calls. Until then each hart falls into `spin`, a jump to itself, and
waits there with its stack ready.

### `kernel.ld`

The linker script says where each part of the image goes, and it answers
00.01's second question: the image starts at 0x80000000. Code comes first,
so `_entry`, linked first, is the first byte; then read-only data, data, and
`.bss`, the zero-filled variables such as `stack0` (the `.s` sections are
small-data variants gcc may emit). Two symbols mark boundaries later lessons
need: `etext`, the end of the code rounded up to a page, so that page tables
(02.04) can make code executable and data writable without one page needing
both; and `end`, the first byte after the image, above which memory is free
(02.02). `ENTRY(_entry)` records the start in the ELF header for tools such
as `readelf`; QEMU's boot ROM does not read it.

Next to the Makefile from 00.01, this lesson adds five files, all in
`kernel/`:

`build/` is not one of them: `make` writes it and `make clean` deletes it.
And `entry.S` ends in a capital S, which matters twice. The Makefile builds
the kernel from `kernel/*.c` and `kernel/*.S`, nothing else. And gcc runs
the C preprocessor on a `.S` file but not on a `.s` one; a later assembly
file, `trampoline.S`, needs it for its `#include` lines. With a lower-case
`kernel/entry.s`, `make` stops at once:

## How it works

### Writing `_entry` in `entry.S`, step by step

1. **One hart, one stack.** If only one hart ran, three instructions would
   do: point `sp` at the top of a 4096-byte array, then wait. Lesson 01.02
   puts `call start` just before `spin`, and that call is the reason for all
   of it: `start` begins by storing its return address through `sp`, and
   with `sp` at zero that store has nowhere to go.
   ```
   _entry:
           la sp, stack0
           li a0, 1024*4
           add sp, sp, a0
   spin:
           j spin
   ```
2. **One slice per hart, from the top.** Three harts run this code at once,
   and two on one stack overwrite each other's return addresses. So hart N
   takes slice N. It learns N with `csrr`, which reads a control and status
   register (CSR), one of the hart's special registers: `mhartid` holds the
   hart's number. It starts at the end of its slice, `(N + 1) * 4096` bytes
   in, because a stack grows down; leave out the `+ 1` and each hart grows
   into the slice below (more below).
   ```
           csrr a1, mhartid
           addi a1, a1, 1
           mul a0, a0, a1
   ```
3. **Only registers until then.** All of this builds the answer directly in
   `sp`, keeping nothing in memory, because there is no stack yet to keep
   anything on.

### Plus one, for the top

Slice N runs from `stack0 + N * 4096` up to `stack0 + (N + 1) * 4096`. A push
moves `sp` down first and stores after, so the starting `sp` must be the top
of the slice. Started at the bottom instead, hart N's stack would grow into
slice N - 1, and hart 0's out of the array altogether.

![Without the + 1, hart N starts at the bottom of slice N, and hart 0 grows down out of `stack0`.](figures/01.01-stack0-without-plus-one.svg)

### A static array, because there is nothing else

Why an array in the kernel image and not memory handed out at run time?
Because nothing can hand memory out yet. The page allocator (lesson 02.02)
is C code, and C code needs a stack. The only memory the kernel can name
this early is memory the linker laid out, so `stack0` is a global array in
`kernel/start.c`. Its size is fixed when the kernel is built, so it is sized
for `NCPU` = 8 harts, the most the kernel allows: QEMU starts three, and
`make qemu CPUS=8` would start eight.

### Aligned, and without a guard

The RISC-V calling convention requires `sp` to be a multiple of 16.
`stack0` is declared 16-byte aligned and 4096 is a multiple of 16, so the
top of every slice is aligned too.

4096 bytes is enough for boot and for the kernel's deepest call chains in
this course, but nothing checks it. A hart that went deeper would overwrite
its neighbour's stack without any fault. Later, every process gets a kernel
stack with an unmapped guard page under it (lesson 02.01), so an overflow
there faults at once; `stack0` has no such guard.

## Break it

Point the stacks the wrong way. In `build/at/xv6/01.01/kernel/entry.S`,
change `add sp, sp, a0` to `sub sp, sp, a0` and run it again. Where does
each hart's stack start now? The console is as empty as before, since
nothing has used a stack yet, but the monitor shows the damage waiting:

<!-- verify: patch file=kernel/entry.S
-        add sp, sp, a0
+        sub sp, sp, a0
-->
<!-- verify: session run="./learn run xv6 --at 01.01" send="ctrl-a c" wait=8 more -->
```
(qemu) info registers -a

CPU#0
...
 x0/zero  0000000000000000 x1/ra    0000000000000000 x2/sp    0000000080000000 x3/gp    0000000000000000
...
CPU#1
...
 x0/zero  0000000000000000 x1/ra    0000000000000000 x2/sp    000000007ffff000 x3/gp    0000000000000000
...
CPU#2
...
 x0/zero  0000000000000000 x1/ra    0000000000000000 x2/sp    000000007fffe000 x3/gp    0000000000000000
```

Hart N now starts at `stack0 - (N + 1) * 4096`. For hart 0 that is the
kernel's own first byte, and its first push would go just below it, below
the start of RAM; harts 1 and 2 start lower still. Ask the monitor what is
there:

<!-- verify: session -->
```
(qemu) xp /2gx 0x7ffffff0
000000007ffffff0: 0xffffffffffffffff 0xffffffffffffffff
```

That is not RAM, and the monitor reads back all ones. The first call, in
01.02, would save its return address there. To see what that does, make the
same change in the 01.03 build, the first that prints, and run
`./learn run xv6 --at 01.03`: the console stays empty, not even the banner,
and every hart's pc is 0. A wrong stack does not fail where it is set up; it
fails later, wherever it is first used. Put `add` back.

## Decide the boundary

xv6 carves per-hart stacks from one static array indexed by hart id. Another
kernel could have the boot hart (the first one) set up the machine alone and
release the others later, so only one stack is needed at first, as Linux
does with a boot CPU and secondary CPUs brought up one at a time. That
avoids three harts running at once with no lock, and pays with a handshake
(a flag the others spin on - `started` in `kernel/main.c`, lesson 01.03, is
one) and more code before anything runs.

xv6 starts all harts together because it is the least code. Does a kernel
need the others awake at 0x80000000, or only after main?
