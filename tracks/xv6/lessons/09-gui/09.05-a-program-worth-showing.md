# 09.05 A program worth showing

`paint` is a program for drawing with the mouse, and it shows how an interactive
program is built: wait for input, change the program's state, draw a whole new
frame.

## Where this fits

![Where 09.05 fits](figures/09.05-map.svg)

The screen, the input events and the drawing library are all in place, but nothing
yet ties them into something a person would want to use. `paint` is that program:
an ordinary process at the top of the stack that reads the input device, draws
with the library into its back buffer, and shows each frame on the mapped screen.
Nothing new is added below it. After this lesson the module ends in a program worth
showing someone.

## The idea

![paint's screen, drawn here at half size: the title bar, the canvas, the colour bar with the chosen swatch in a white frame, and the pointer.](figures/09.05-layout.svg)

An interactive program spends nearly all its time waiting for a person. When
nothing happens it should do nothing at all; when the mouse moves it should answer
with the right picture, at once. That is an **event loop**: wait for events, let
each one change what the program knows, then draw a frame from what it knows.
`paint` sleeps in `read` on the input device, so waiting costs nothing.

![One turn of paint's loop: wait for events, handle each, then build and show one frame.](figures/09.05-loop.svg)

What `paint` knows is a handful of facts: where the pointer is, which colour is
chosen, how wide the pen is, whether the button is down, and the **canvas**, the
picture drawn so far. The canvas is the only thing that keeps pixels from one frame
to the next. Everything else on the screen, the bars, the swatches, the pointer,
is drawn fresh every frame on top of a copy of the canvas.

Follow one drag. The mouse moves while the button is down: an x arrives, then a y,
then a sync. At the sync the pointer moves to its new place, and because the button
is down, a stroke goes onto the canvas from the old place to the new one. Then the
frame is built: the canvas, then the bars, then the pointer on top, and the finished
frame goes to the screen.

### handle

This takes one event and changes what `paint` knows: a new pointer position, a
button pressed or let go, a key that picks the pen, clears the canvas or quits. It
is the only place strokes are added to the canvas. It returns 0 when it is time to
quit.

### redraw

This builds one whole frame in the back buffer from what `paint` knows, back to
front so that each layer covers the ones before it, and then shows it with
`present` (09.04).

shell in your terminal stays yours.

(The shell prints its next prompt before `paint` prints its line.) QEMU's window
shows the frame in the figure above: the title bar with its help text, a white
canvas, and ten swatches with black chosen and "pen 2" at the right. There is no
pointer until the mouse moves. Move it into the window: a small black cross
follows it, open in the middle so you can see the pixel it points at. Hold the
left button and draw: black strokes, three pixels wide. Click red: the white frame
jumps to it, and the next stroke is red. Press 3 and the pen is five pixels wide,
and the bar says so; press c and the canvas is white again. However much you draw
over or under the pointer, it never leaves a mark: move it away and the drawing
underneath is intact. Esc ends `paint` and leaves the screen black. To end it from
the terminal instead, find it with Control-P and kill it:

<!-- verify: session send=ctrl-p

-->
```
1 sleep  init
2 sleep  sh
4 sleep  paint
kill 4
$
```

(It is 4, not 3: for `&` the shell forks a child that starts `paint` and exits at
once.) `kill` wakes `paint` from its sleep in `read`, the read sees the killed flag
and fails, and the kernel ends the process on its way back to user mode (06.04),
before `paint` runs another line. Nobody clears the screen, so the window keeps
the last frame it drew.

## How it works

### Writing paint's `main` loop, step by step

`main` is not one of the two pieces above, but it is the loop they live in.

1. **Start with the event loop.** Read a batch of events, handle each one, then draw
   one frame for the whole batch. One `read` returns every event waiting, up to 32,
   about ten pointer moves; any more wait for the next turn. A result of 0 or
   less means the read failed, and ends the loop.
   ```
   for(;;){
     int n = read(fd, ev, sizeof(ev));
     if(n <= 0)
       break;
     for(int i = 0; i < n / sizeof(ev[0]); i++){
       if(handle(&ev[i]) == 0){
         ...
       }
     }
     redraw();
   }
   ```
2. **Set up before the loop.** `screen_open` maps the screen and gives the back
   buffer, the canvas is a second surface the height of the screen minus the two
   bars, and `input_open` makes `/input` the first time it is needed.
   ```
   canvas.w = FB_WIDTH;
   canvas.h = CANVAS_H;
   canvas.px = malloc(FB_WIDTH * CANVAS_H * sizeof(uint));
   ```
3. **Start white and show a first frame.** The canvas is filled white and one frame
   is drawn before any event arrives, so the window shows `paint` at once.
4. **Leave a black screen on the way out.** When `handle` says quit, the window
   would otherwise go on showing a program that is gone.

### Writing `handle`, step by step

1. **Start with the pointer.** An x or a y is only written down; the sync, which
   closes the group, moves the pointer to the new place.
   ```
   static int
   handle(struct inputevent *e)
   {
     if(e->type == EV_ABS){
       if(e->code == ABS_X)
         nx = e->value;
       else if(e->code == ABS_Y)
         ny = e->value;
     } else if(e->type == EV_SYN){
       ...
     }
     return 1;
   }
   ```
2. **Draw at the sync if the button is down.** The stroke runs from the old place to
   the new one. Until both coordinates have arrived once, there is nowhere to move
   to.
   ```
   if(nx >= 0 && ny >= 0){
     if(drawing)
       stroke(px, py, nx, ny);
     px = nx;
     py = ny;
   }
   ```
3. **The left button chooses a colour or starts drawing.** Going down over a swatch,
   it chooses that colour; in the canvas, it starts drawing with a stroke from the
   pointer to itself, so a click without a move still leaves a dot. Going up, it
   stops drawing.
4. **Other keys act when they go down or repeat, never when they go up.** Otherwise
   every key press would act twice. `keychar` (09.03) turns the key code into the
   character it types. Esc returns 0 to quit; c clears the canvas; 1, 2 and 3
   choose the pen: they set `pen`, the stroke's radius, to 0, 1 or 2, a stroke 1,
   3 or 5 pixels wide, and the bar shows the key, "pen 1" to "pen 3".
   ```
   } else if(e->type == EV_KEY && e->value != 0){
   ```

### Writing `redraw`, step by step

1. **Start back to front: the canvas first, the pointer last, then show it.** Each
   layer covers the ones before it.
   ```
   static void
   redraw(void)
   {
     ...
     blit(&back, 0, TOP, &canvas);
     ...
     if(px >= 0)
       pointer(px, py);
     present(&back);
   }
   ```
2. **The title bar in between.** A dark rectangle, "paint" at the left, and the help
   text right-aligned: its x is the screen width, minus 8, minus 8 pixels per
   character.
3. **Then the colour bar.** A dark rectangle, then each swatch. The chosen one gets
   a white rectangle 2 pixels larger on every side drawn first, so the swatch on top
   leaves a white frame showing.
   ```
   if(i == choice)
     fillrect(&back, x - 2, SW_Y - 2, SW_W + 4, SW_H + 4, WHITE);
   fillrect(&back, x, SW_Y, SW_W, SW_H, swatches[i]);
   ```
4. **The pen label last of the bars,** right-aligned like the help text.

### Why it is built this way

**One frame per batch, not per event.** Each `read` asks for up to 32 events and
gets all that are waiting. `paint` handles them all, then draws once. A fast mouse
can send dozens of events between two frames; drawing after each would fall
further and further behind the hand. This way the frames follow the events, and the
program is never more than one batch late.

**The pointer moves at the sync, not at each coordinate.** A move arrives as x,
then y, then a sync. Moving the pointer at the x would put it, for a moment, at the
new x and the old y, and a stroke drawn then would have a corner the hand never
made. So a coordinate is only noted, and the sync moves the pointer.

**The canvas holds strokes and nothing else.** **Invariant:** the canvas holds
exactly the strokes, and everything else on the screen is drawn fresh each frame.
That is why the pointer can sit on a stroke and leave it undamaged: it was only
ever drawn on the frame. It is also why `redraw` starts by copying the canvas,
which covers whatever the last frame left in the back buffer.

**The canvas has its own coordinates.** It is 640 by 428 pixels, shown from row 20,
below the title bar. A stroke is drawn on the canvas 20 rows higher than the screen
position, and the canvas's own clipping keeps a stroke that runs off it from
spilling onto the bars.

**A thick stroke is a thin line drawn many times.** `stroke` draws the one-pixel
line again at every offset up to the pen's radius: 9 lines for the middle pen, 25
for the widest. A real thick-line routine would draw each pixel once, but it would
be the hardest code in the program, and a stroke between two pointer positions is
usually a few pixels long, so 25 short lines per event cost nothing a person can
see.

**Two consoles that do not meet.** `paint` never reads the terminal, and keys in
the window go to the virtio keyboard, not to the serial line, so the shell and
`paint` each get their own input and never steal each other's. Running `paint` in
the foreground works as well; the shell then waits for it, and keeps what you type
in the terminal until it is back.

## Break it

In `redraw`, in `build/at/xv6/09.05/user/paint.c`, delete the first line, the one
that copies the canvas into the frame:

```
  blit(&back, 0, TOP, &canvas);
```

<!-- verify: patch file=user/paint.c
-  blit(&back, 0, TOP, &canvas);
-->

Run the lesson again, run `paint`, move the pointer around the window and draw a
stroke. The canvas area is black, not white, and every place the pointer has been
leaves a cross behind, a trail of them along its path. The stroke you drew does
not appear anywhere. The back buffer starts out as zeroes, and nothing clears it
any more: each frame only adds the bars and the pointer to whatever the last frame
left. The strokes are all there in the canvas, which nothing shows. A frame that
is not rebuilt from scratch is a frame that remembers what it should have
forgotten.

## Decide the boundary

`paint` redraws the whole screen for every batch of events: 1.2 MB composed and
1.2 MB copied, even when the pointer only moved one pixel. A window system
would track **damage** instead, the rectangles that changed (the cross where it
was, and where it is now), and redraw only those, at the cost of keeping that
list right as everything else changes. Real displays go further for the pointer
itself: a **cursor plane** is a tiny second image the display lays over the
screen, so moving the pointer is one register write and no pixels at all;
virtio-gpu has a queue of its own for it. In a 640 by 480 window at a few dozen
batches a second, the whole-frame redraw is cheap enough not to matter. When is
it cheaper to compute everything again than to remember what changed?
