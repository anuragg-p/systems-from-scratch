# 09.03 Keyboard and mouse

The input driver turns a key pressed or a mouse moved in QEMU's window into small
events that a user program can read.

## Where this fits

![Where 09.03 fits](figures/09.03-map.svg)

A program can now draw, but it cannot hear the person in front of the window. Keys
typed in the window do not reach the serial console; they go to a virtio keyboard,
and the mouse is a second virtio device. This lesson is the driver for both, built
on the same kind of device queues as the disk, and a device file that programs
read. Below it are the two devices and the interrupt
controller; above it, the drawing library's input helpers and `paint`. After this
lesson a program can wait for a key or a click and act on it.

## The idea

![A key press, from QEMU's window to the program that reads it. The device side and the process side meet at input.q, and the interrupt handler's wakeup joins them.](figures/09.03-keypath.svg)

A key pressed in the window has to reach `paint`, which may be busy drawing a
frame or asleep waiting for something to happen. The press arrives as an
interrupt, at a moment the person chose, and has to wait somewhere until `paint`
asks for it.

Both devices speak in **events** of 8 bytes: a type, a code and a value. The
format is Linux's evdev, which the virtio input devices copy on purpose. Pressing
`a` sends "key 30 went down" and then a sync event that closes the group; letting
go sends "key 30 went up" and another sync. Moving the mouse sends where the
pointer now is, x then y, then a sync: this mouse reports positions, not
movements. A program acts at the sync, when the group is whole.

![What the devices send: 8-byte events in groups, each group closed by EV_SYN. A key press is two events, a pointer move three.](figures/09.03-groups.svg)

The driver talks to the devices through virtio queues, as the disk driver does
(05.01), but the traffic starts at the other end. The disk only answers what the
driver asked; a keyboard speaks whenever someone presses a key. So the driver
gives each device eight empty buffers ahead of time; the device writes one event
into each and raises an interrupt. The interrupt handler copies the events into
one queue that both devices share, and hands the buffers straight back. A program
reads the queue through a device file, `/input`, and sleeps while it is empty.

### virtio_input_intr

This runs when the keyboard or the mouse raises its interrupt. It moves each new
event from the device's buffer into the shared queue, turning mouse positions into
screen pixels on the way, gives the buffer back to the device, and wakes any
program waiting to read.

### inputread

This is what `read` on `/input` does. It hands the program as many whole events as
are waiting and fit in its buffer, oldest first, and sleeps when there are none.

### input_open

The user side lives in `user/gui.c`, a small library that `events` links.
`input_open` opens `/input`, and the first time it finds no such file it makes one
with `mknod`, the way init makes `console` (07.02). Nothing else in the system
then needs to know about the input device: not mkfs, and not init, which belongs to
the core. Beside it, `keychar` turns a key code into the character it types, and
`keyname` into a name to print.

## How it works

### Writing indev_init, step by step

1. **Start from the disk's setup (05.01).** Make sure an input device, device
   18, is in the slot, do the same handshake, set up one queue, and mark the
   device up. An empty slot is not an error: a machine without a keyboard or a
   mouse simply has no events.
   ```
   static void
   indev_init(struct indev *d)
   {
     ...
     if(*R(d, VIRTIO_MMIO_MAGIC_VALUE) != 0x74726976 ||
        *R(d, VIRTIO_MMIO_VERSION) != 2 ||
        *R(d, VIRTIO_MMIO_DEVICE_ID) != 18 ||
        *R(d, VIRTIO_MMIO_VENDOR_ID) != 0x554d4551)
       return;
     ...
     d->up = 1;
   }
   ```
   The same function serves both devices; `devs[]` gives each its registers and its
   interrupt.
2. **Ask the device where the pointer can be.** The interrupt handler needs each
   axis's range to turn positions into pixels. An input device answers questions
   in its config space, the bytes after its registers: the driver writes what it
   wants to know into `select` and `subsel` (the range of an axis, and which
   axis), then reads the answer from the bytes that follow. The tablet says 0 to
   32767; a keyboard has no axes and answers with a size of 0.
   ```
   d->absmax[ABS_X] = absmax(d, ABS_X);
   d->absmax[ABS_Y] = absmax(d, ABS_Y);
   ```
3. **One page of 8-byte buffers, all handed over before going live.** An event is
   8 bytes, so one page holds every buffer, and each descriptor points at its own
   slot in it.
   ```
   d->desc[i].addr = (uint64)&d->ev[i];
   d->desc[i].len = sizeof(struct virtio_input_event);
   d->desc[i].flags = VRING_DESC_F_WRITE;
   ```

### Writing virtio_input_intr, step by step

1. **Start with the loop that moves events.** Under the queue's lock, walk the
   device's used ring, copy each event into the shared queue, and wake readers at
   the end. The lock is held across the whole walk, because readers on other harts
   take events off the same queue.
   ```
   void
   virtio_input_intr(int irq)
   {
     ...
     acquire(&input.lock);
     while(d->used_idx != d->used->idx){
       ...
       int id = d->used->ring[d->used_idx % NUM].id;
       struct virtio_input_event *ve = &d->ev[id];
       ...
       input.q[input.w++ % NEVQ] = e;
       d->used_idx += 1;
       ...
     }
     wakeup(&input.r);
     release(&input.lock);
     ...
   }
   ```
2. **Find which device it was, and acknowledge it.** The keyboard and the tablet
   share this handler, and the interrupt number picks the device; without the
   acknowledge it keeps its interrupt raised.
3. **Scale positions on the way.** A position becomes a screen pixel here, once, so
   no program ever sees the tablet's units.
   ```
   if(e.type == EV_ABS && e.code <= ABS_Y && d->absmax[e.code] > 0){
     int size = e.code == ABS_X ? FB_WIDTH : FB_HEIGHT;
     e.value = (uint64)ve->value * size / ((uint64)d->absmax[e.code] + 1);
   }
   ```
4. **Drop an event when the queue is full.** With 64 events waiting, a new one is
   thrown away; an interrupt handler cannot wait for room.
   ```
   if(input.w - input.r < NEVQ)
     input.q[input.w++ % NEVQ] = e;
   ```
5. **Give each buffer back, and notify the device once at the end.** Ring entry,
   fence, index, the way the disk driver posts a request.

### Writing inputread, step by step

1. **Start with events waiting.** Under the queue's lock, copy whole events out,
   oldest first, while there are events and room for another; return the bytes
   copied.
   ```
   static int
   inputread(int user_dst, uint64 dst, int n)
   {
     ...
     acquire(&input.lock);
     ...
     while(input.r != input.w && n - got >= sizeof(struct inputevent)){
       struct inputevent e = input.q[input.r % NEVQ];
       if(either_copyout(user_dst, dst + got, &e, sizeof(e)) < 0)
         break;
       input.r++;
       got += sizeof(e);
     }
     release(&input.lock);
     return got > 0 ? got : -1;
   }
   ```
   It never copies part of an event, so a program can always treat what it read
   as an array of events. An event leaves the queue only once it has been copied; if a copy
   fails, the loop stops there.
2. **Sleep while the queue is empty, unless killed.** As the console's `read`
   does, the check and the sleep happen under the queue's lock (04.03), so an
   event cannot arrive in between.
3. **Refuse a buffer too small for one event.** Such a read could never return
   anything.

### Why it is built this way

**A tablet, not a mouse.** QEMU offers a mouse that reports how far it moved and a
tablet that reports where the pointer is, like a pen on a tablet. In a window the
tablet is what you want: the pointer in xv6 is wherever your pointer is over the
window, and QEMU never has to capture your mouse. The tablet reports positions from
0 to 32767 on each axis, and the handler scales them to the screen, so 5145 becomes
5145 * 640 / 32768 = 100. It divides by 32768, one more than the largest
position, so that 32767 lands on the last pixel, 639, never one past it. Programs
never see the device's units.

**One queue, one lock, and no lost wakeups.** Both devices feed one queue, because
a program wants keys and clicks in the order they happened, from one `read`; with
a queue each it would have to wait on two files at once, which an xv6 program
cannot do. The queue has the shape of the console's input buffer (03.03): the
interrupt handler adds, never sleeps, and drops an event when the queue is full; a
process takes, and sleeps while it is empty. 64 events, about twenty pointer
moves, is plenty for a program that reads between frames. The handler wakes
readers while holding the queue's lock, and a reader checks for an empty queue and
goes to sleep under that same lock, so an event cannot arrive in the gap between
the two (04.03). A killed reader stops waiting and its `read` returns -1, so
`kill` can end a program asleep here.

**A device file, not a new system call.** `/input` is an inode of type
`T_DEVICE` with major number 2. Every `read` on it is sent to the input driver
through the kernel's table of device functions, exactly as reads of the console go
to the console driver (05.07). Input needed one slot in that table, and no new
system call.

**Buffers go back at once.** A buffer belongs to the device from the moment it is
handed over until the device returns it full; the handler copies the event out and
hands the buffer back in the same step. That matters more than it seems, because
QEMU holds the events of a group until the sync and delivers the group only if
there is a free buffer for every event in it. Short of buffers, it drops the whole
group.

Nothing crashed; the devices simply have nowhere to put anything.

## Decide the boundary

xv6 has one queue for everyone. An event goes to whichever process reads first,
and events wait there until someone does, so a program started later gets
keys pressed before it started. Linux's evdev gives each open file of
`/dev/input/eventN` its own buffer, so every reader sees every event from the
moment it opened the device, and a reader that falls behind gets a
`SYN_DROPPED` instead of silent loss. Above that, a display server owns the
devices and decides which window a key belongs to: the one with focus. And
`poll` lets one program wait on input, a timer and a socket at once, which an
xv6 program cannot do. Which program should see a key press: every reader, the
first one to read, or the one whose window has focus, and who decides?
