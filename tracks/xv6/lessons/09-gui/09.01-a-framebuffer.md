# 09.01 A framebuffer

A framebuffer is memory whose contents are the picture on the screen; this lesson
finds QEMU's ramfb display, tells it where the kernel's framebuffer is, and draws
the first pixels.

## Where this fits

![Where 09.01 fits](figures/09.01-map.svg)

Everything xv6 has shown so far is text on a serial line. To show a picture the
kernel needs a screen, and the simplest kind of screen is a block of ordinary memory
that the display reads over and over. This lesson sits right on the hardware, below
everything else in the module: the kernel sets the screen up once at boot and can
draw on it from then on. Above it, the next lessons hand the screen to programs and
add a keyboard and a mouse. After this lesson xv6 boots with a window that shows a
picture. The module stands on the core alone: if you built the network module, its
lines are left out of this module's code views.

## The idea

![The two conversations with fw_cfg on this machine: read the file directory to find etc/ramfb, then write its 28-byte record by DMA. Numbers are from a real boot.](figures/09.01-fwcfg.svg)

This module gives xv6 a screen, a keyboard and a mouse, and a program that uses all
three. This lesson draws from the kernel. 09.02 puts the screen into user
programs, 09.03 reads the keyboard and the mouse, 09.04 is a small drawing library
in user space, and 09.05 is `paint`, a program to draw with the mouse.

A **framebuffer** is memory that holds the picture: one 32-bit word per pixel, row
after row from the top left. Nothing ever sends a picture anywhere. The kernel
stores into memory, and the display reads that memory and paints it, every time it
refreshes. To make pixel (100, 50) red, the kernel stores 0x00ff0000 into the word
50 rows and 100 columns in. That is the whole drawing interface.

![The pixel format and the address of pixel (x, y). One pixel is a 32-bit word, 0x00RRGGBB, so its bytes in memory run blue, green, red, unused.](figures/09.01-pixel.svg)

The display only has to be told once where that memory is and how to read it. QEMU's
ramfb display takes that as a 28-byte record: the address of the first pixel, the
pixel format, the width, the height, and the **stride**, the number of bytes from
one row to the next. xv6 asks for 640 by 480, small enough that the whole picture
is 1.2 MB, and for the format the figure shows, which makes a pixel one aligned
32-bit store. Formats are named by a four-letter code, a fourcc, from the list
Linux's display layer (DRM) keeps; this one is XRGB8888, "XR24".

The record is delivered through **fw_cfg**, the device QEMU uses to hand
configuration to firmware. fw_cfg holds numbered items, and some of them are named
files; ramfb adds one called `etc/ramfb`. Writing the record into that file is what
turns the window on.

So the boot goes: find the file `etc/ramfb`, draw a first picture into the memory,
then write the record. From that moment QEMU shows whatever the memory holds.

### fw_cfg_find

The item number of `etc/ramfb` depends on which devices QEMU was started with, so
the kernel looks it up by name. This reads fw_cfg's directory of files and returns
the number of the one asked for.

### fw_cfg_write

This delivers the 28-byte record into that item. Reading fw_cfg is easy: select an
item, then read its bytes one at a time from a data register. Writing is not, because
QEMU stopped accepting writes to that register in version 2.4; the only way in is
DMA, where the kernel leaves a small request in memory, gives fw_cfg its address,
and QEMU carries it out.

### fb_rect

The kernel's one drawing operation: fill a rectangle with a colour. It draws the
boot screen, and it is the model for every drawing routine later in the module.

## Run it

Boot with `./learn run xv6 --at 09.01`. The console shows the same boot as before
the module existed, and QEMU also opens its own window, 640 by 480 pixels, with the
kernel's boot screen: dark blue-grey, a white border one pixel wide around the very
edge, and three squares of 80 by 80 pixels in a row across the middle, red, green
and blue. The serial console stays in your terminal; the window only shows pixels.
Until the kernel has written its record, the window shows QEMU's own words instead:
"Guest has not initialized the display (yet)."

## How it works

### Writing fbinit, step by step

`fbinit`, at the end of the file, is the routine at boot that uses all three
pieces, in this order.

1. **Start with the machine that has a screen.** Find `etc/ramfb`, fill in the
   28-byte record, big-endian, and write it. The record is `static`, because QEMU
   reads it at its physical address.
   ```
   void
   fbinit(void)
   {
     static struct ramfb_cfg cfg;
     ...
     if((sel = fw_cfg_find("etc/ramfb")) < 0)
       return;
     ...
     cfg.addr = be64((uint64)fb);
     cfg.fourcc = be32(DRM_FORMAT_XRGB8888);
     ...
     if(fw_cfg_write(sel, &cfg, sizeof(cfg)) < 0){
       ...
     }
     fb_up = 1;
   }
   ```
   Without `-device ramfb` there is no such file, and the kernel carries on quietly
   without a screen.
2. **Check that fw_cfg is there at all.** Item 0 reads "QEMU"; on a machine without
   fw_cfg that address is something else, and nothing more may be asked of it.
3. **Draw before showing.** The boot screen goes into the framebuffer before the
   record is written, so the very first picture QEMU shows is a finished one.
4. **Say the screen is up only once QEMU accepts.** If it refuses, the kernel says
   so and goes on without a screen. `fb_up` is what every later lesson checks
   before using the screen.

### Writing fw_cfg_write, step by step

1. **Start with the request.** Build it in memory, the item number in the top 16
   bits of the control word with the select and write bits, then the length and the
   address of the data, all big-endian; then start the transfer by writing the
   request's address to the DMA register.
   ```
   static int
   fw_cfg_write(int sel, void *buf, int len)
   {
     static struct fw_cfg_dma req;
     volatile struct fw_cfg_dma *d = &req;

     d->control = be32((uint32)sel << 16 | FW_CFG_DMA_SELECT | FW_CFG_DMA_WRITE);
     ...
     *(volatile uint64 *)FW_CFG_DMA = be64((uint64)d);
     ...
   }
   ```
2. **Fence before the start.** The request must be in memory before QEMU is told
   where it is.
3. **Wait for the control word to come back.** QEMU clears every bit except, on
   failure, the error bit, which decides between 0 and -1.
   ```
   while(be32(d->control) & ~FW_CFG_DMA_ERROR)
     ;
   ```

### Writing fb_rect, step by step

1. **Start with a rectangle that is wholly on the screen.** Fill it row by row,
   finding each row by the stride.
   ```
   void
   fb_rect(int x, int y, int w, int h, uint32 color)
   {
     ...
     for(int j = 0; j < h; j++){
       uint32 *row = (uint32 *)(fb + (y + j) * FB_STRIDE + x * FB_BPP);
       for(int i = 0; i < w; i++)
         row[i] = color;
     }
   }
   ```
2. **Clip the left and top edges.** A rectangle that starts left of the screen is
   shortened by the part that is off and starts at 0; the same for the top.
   ```
   if(x < 0){
     w += x;
     x = 0;
   }
   ```
3. **Clip the right and bottom edges** at the edge. A rectangle entirely off the
   screen is left with no width or no height, and the loops do nothing.

### Why it is built this way

**The pixels live inside the kernel's own image.** The display needs one block of
memory that is contiguous in physical memory, 1,228,800 bytes. The page allocator
cannot promise that; it hands out single pages from wherever they happen to be. So
the framebuffer is a page-aligned array in the kernel's bss: 300 pages below the
end of the kernel, which the allocator never sees. The kernel maps memory at its
own address (02.04), so the array's address is also the physical address the
display needs. **Invariant:** once the record is written, those pages belong to the
screen for as long as the machine runs; nothing else may ever use them.

**Every number is turned around by hand.** fw_cfg is big-endian and RISC-V is
little-endian, so every number crossing between them has its bytes swapped, with
shifts. GCC's `__builtin_bswap32` would have been shorter, but on a RISC-V without
the bit-manipulation extension it becomes a call into libgcc, which the kernel does
not link.

**The DMA request must sit at a physical address.** QEMU reads the request and the
record straight from physical memory. A local variable lives on the kernel stack of
whichever process is running, and that stack's virtual address is not its physical
one (04.01). So the request and the record are `static`, in the kernel's data,
where the two addresses agree. The specification says to wait until QEMU writes the
control word back, and `fw_cfg_write` does, though QEMU finishes before the store
that started it returns.

**Rows are found by stride, not by width.** Here a row is exactly 640 pixels, 2560
bytes. Real hardware is free to pad rows for alignment, so `fb_rect` steps from row
to row by the stride and would still be right if stride and width came apart. It
also clips first: a rectangle that hangs off an edge draws only the part on the
screen, and never writes outside the array.

## Break it

In `fw_cfg_find`, in `build/at/xv6/09.01/kernel/fb.c`, return the item number as
it came off the device:

```
      return f.select;
```

instead of `return be16(f.select);`, and run the lesson again:

-->
```
xv6 kernel is booting

fbinit: ramfb refused the configuration
hart 1 starting
hart 2 starting

```

and the window never leaves "Guest has not initialized the display (yet)." The
directory said 00 25 (the figure). Read as a little-endian 16-bit number that is
0x2500, an item that does not exist, so the DMA request selected nothing, QEMU set
the error bit, and `fbinit` gave up. The shell works; there is just no screen. A
byte-order mistake rarely crashes anything. Everything runs, on the wrong number.

## Decide the boundary

ramfb is about the simplest display there can be: one record to set it up, then
plain memory, and no way to say what changed, so QEMU repaints the whole window
from guest memory on every refresh. The virt machine also offers
`virtio-gpu-device`. Its driver creates a resource, attaches pages to it (they
need not be contiguous), points a scanout at it, and then sends "transfer" and
"flush" commands on a virtqueue for each rectangle that changed. That is a
command queue and a dozen message types instead of one record, and in return
the host does no work while nothing changes, the guest can change resolution,
and a second screen is just another scanout. On real machines Linux hides all
of these behind DRM, which separates making framebuffers from showing them. xv6
took ramfb because a framebuffer that is just memory lets this lesson be about
pixels and not about a protocol. When a large screen hardly ever changes, what
does "repaint everything" cost, and who pays it: the guest, or the host?
