# 09.02 Pixels from user space

`fbmap` is a system call that maps the screen into the memory of the process that
asks for it, so that a program draws by storing to an array.

## Where this fits

![Where 09.02 fits](figures/09.02-map.svg)

The kernel can draw, but programs cannot: the screen is kernel memory, and a
program that wanted a picture would have to ask the kernel for every pixel. This
lesson connects the screen of the previous lesson to user programs, through the
page tables every process already has. Below it are the framebuffer and the paging
code of the memory module; above it, the drawing library and `paint`. After this
lesson any program can put a pixel on the screen at the cost of one memory store.

## The idea

![colors and its child each map the screen at 0x40000000, and both page tables lead to the same 300 pages of fb. Their own memory, from 0 to sz, is separate: the child's is a copy.](figures/09.02-mapping.svg)

A painting program redraws its window every time the mouse moves: 640 by 480 is
307,200 pixels. A system call per pixel is out of the question. Even one system
call per frame, copying the picture into the kernel (a **blit**), moves 1.2 MB
through the kernel each time.

The other way is to let the program reach the screen itself. The screen is 300
pages of memory; the kernel can enter those same pages into the program's page
table, readable and writable from user mode, at a fixed address, 1 GB. Then
drawing is ordinary storing: `fb[y * 640 + x] = color` puts one pixel up, with no
system call and no copy. The kernel's work is done once, when the program asks.

`colors` shows it. The parent maps the screen and draws eight colour bars. Then it
forks, and the child maps the screen too and draws a grey ramp below the bars. The
two page tables lead to the same physical pages, so when the child has exited, the
parent reads the last pixel through its own mapping and finds the child's white
there.

### fbmap

This is the system call a program makes to get the screen. It enters the screen's
300 pages into the caller's page table and returns the address, or -1 when there is
no screen. Asking twice is harmless: the second call returns the same address.

### fbunmap

Whenever a process's page table is freed, on exit and on exec, the kernel first
calls this to take the screen's entries back out, for every process, whether it
mapped the screen or not. It clears the entries and frees nothing, because the
pages belong to the screen, not to the process.

The window shows a test card: the top 360 rows are eight colour bars, 80 pixels

## How it works

### Writing `fbmap`, step by step

1. **Start with the mapping itself.** Enter all 300 pages of the screen into the
   caller's page table at one fixed address, readable and writable from user mode,
   and return that address. The user bit is what lets the program touch them at
   all; the kernel's own mapping of the same pages lacks it.
   ```
   uint64
   sys_fbmap(void)
   {
     struct proc *p = myproc();
     ...
     if(mappages(p->pagetable, FBVA, FB_SIZE, (uint64)fb, PTE_R | PTE_W | PTE_U) < 0){
       ...
       return -1;
     }
     return FBVA;
   }
   ```
2. **No screen, no mapping.** If the kernel found no ramfb at boot, return -1.
3. **Already mapped: return the address again.** If the first page is in the page
   table, the whole screen is.
4. **Undo a half-made mapping.** `mappages` can fail part way, when it cannot get a
   page for a page table, leaving some of the screen mapped. `fbunmap` clears what
   is there, so the process is left exactly as it was.

`fbmap` is system call number 25. The numbers 22 to 24 belong to the network
module's socket calls, so the two modules can be added in either order without
their numbers colliding.

### Why it is built this way

**The screen lives outside the process's memory.** Everything from address 0 up
to the process's size is the process's own: it was allocated for it, fork copies
it, and exit frees it. The screen must take part in none of that, so it is mapped
far above, at 1 GB, and the process's size does not grow. A 128 MB machine can
never grow a heap that high, and fork's copy and exit's free never look there.

**Take the screen out before freeing a page table.** One routine does look at the
whole page table: `freewalk`, which `uvmfree` calls last to free the page-table
pages themselves. It panics on any mapping it still finds, because a page left
mapped is a page nobody accounted for. So before that runs, the screen's entries
are cleared, exactly as the trampoline and trapframe are: unmap, never free. Most
processes never mapped the screen, so `fbunmap` must quietly skip entries that are
not there. That costs every exit and exec 300 calls to `walk`, mapped or not. A
flag in the process would skip them, but it would be one more thing for fork and
exec to keep right, and for a process without the screen each walk stops at the
top level, where the entry for 1 GB is empty.
**Invariant:** every page-table entry that points into the screen is cleared before
the page table is freed, and no page of the screen is ever handed to the page
allocator.

![proc_freepagetable, step by step. Only the process's own pages are freed; fbunmap clears the screen's PTEs so that freewalk finds no leaf.](figures/09.02-teardown.svg)

**Fork does not pass the screen on.** A child gets a copy of its parent's own
memory and nothing else, so it starts without the screen and asks for it, as the
`colors` child does. Two processes can then draw at the same moment, and the kernel
would not notice: the last store to a pixel wins, as with any shared memory.

**Asking twice is checked.** If the screen is already mapped, `fbmap` returns the
address without mapping again. Without that check, mapping the same pages a second
time would panic with `mappages: remap`.

**What it costs.** The 300 pages fit in one last-level page table of 512 entries,
so the first `fbmap` allocates two page-table pages and exit frees them again. The
screen's own pages never move, and from then on a store goes from the program to
the pixel with nothing in between.

## Break it

In `fbunmap`, in `build/at/xv6/09.02/kernel/fb.c`, delete the two lines that clear
the PTE, and keep the loop:

```
    if(pte != 0 && (*pte & PTE_V))
      *pte = 0;
```

<!-- verify: patch file=kernel/fb.c
-    if(pte != 0 && (*pte & PTE_V))
-      *pte = 0;
-->

Run the lesson again. `echo hi` still works: it never mapped the screen. Then:

<!-- verify: session run="./learn run xv6 --at 09.02" panics="freewalk: leaf" -->
```
$ colors
colors: the screen is at 0x0000000040000000
panic: freewalk: leaf
```

The child drew the ramp and exited, and when the parent's `wait` freed it, its
page table still held 300 valid PTEs at 1 GB; `freewalk`, finding them, stopped
the machine. The panic is the kernel's own bookkeeping catching a page whose owner
it cannot name. The other mistake, freeing them, is just as loud: `kfree` panics
on any page below `end`, and every page of `fb` is.

## Decide the boundary

xv6 gives any process that asks the whole screen, at a fixed address. Linux's
older framebuffer device, `/dev/fb0`, is the same deal through `mmap`. Modern
desktops do the opposite. Under Wayland a program never touches the screen: it
draws into a buffer of its own, shares that buffer with the compositor, and the
compositor decides what is on the screen and where, so two programs cannot
scribble on each other. The price is a compositor process and one more copy or
one more trip through the GPU for every frame. Fork is a second choice. Linux
keeps a shared mapping in the child (mmap(2): mappings are preserved across
fork), and offers `MADV_DONTFORK` to leave one out. xv6 leaves the screen out
by construction and lets the child ask. Who should own the screen: every
program that maps it, one server that all programs talk to, or the kernel?
