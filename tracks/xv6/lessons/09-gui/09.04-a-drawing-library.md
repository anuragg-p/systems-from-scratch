# 09.04 A drawing library

The drawing library is the small piece of user code that turns "a rectangle here,
a line there, the word paint at the top" into pixels.

## Where this fits

![Where 09.04 fits](figures/09.04-map.svg)

A program now has the screen as an array and a stream of input events, but drawing
anything more than a filled box by hand gets old fast. The drawing library lives in
user space, linked only into the programs that draw. Below it are the screen
mapping and the ordinary heap; above it is `paint`. It turns three requests, a
rectangle, a line and a character, into pixels, and makes a finished picture appear
all at once instead of piece by piece. After this lesson a program can draw shapes
and text without thinking about individual pixels.

## The idea

![The letter a in user/font.c: eight bytes, one per row. A 1 bit is a pixel to draw, and bit 7 is the leftmost.](figures/09.04-glyph.svg)

`paint` needs a dark title bar with its name in it, ten colour swatches, strokes
that follow the mouse in any direction, and a pointer that may hang half off the
edge of the screen. Three operations cover all of it: fill a rectangle, draw a
line, draw a character.

They all draw into a **surface**: a block of pixels with a width and a height, the
screen or any other picture in memory. And they all **clip**: whatever falls
outside the surface is simply not drawn. A caller can ask for a rectangle at
x = -3, or a pointer centred on the last column, and nothing outside the surface
is touched.

A line is the interesting one. Between (0, 0) and (8, 3) there is no row of pixels
that is exactly the line; there are only pixels near it. The way to choose them,
worked out by Jack Bresenham for a pen plotter in 1962, steps one pixel at a time
along the longer direction and keeps a running error that says when to step
sideways as well, using only integer additions.

![The line from (0, 0) to (8, 3). Each column gets one pixel; the error term, kept in integers, decides when y steps too.](figures/09.04-line.svg)

Text is pictures too. Each character in the font is 8 by 8 pixels stored as 8
bytes, one per row, with a 1 bit for every pixel to draw, as the letter a shows
above. Drawing a character is drawing its 1 bits.

Finally, the library keeps the screen from showing a picture half drawn. Programs
draw into a **back buffer**, a surface in ordinary memory the size of the screen,
and one call, `present`, copies the finished frame to the screen.

### fillrect

The most used of the three: every bar, swatch and cleared canvas in `paint` is a
filled rectangle. It clips the rectangle to the surface once, then fills row by
row.

### line

The strokes `paint` draws as the mouse moves, and the arms of its pointer. It
draws a line one pixel wide between two points, both ends included, in any
direction.

### drawchar

Every word on the screen. It draws one character from the 8 by 8 font with its top
left corner at a given point, and draws nothing where the font has a 0, so what is
behind the text shows through.

## How it works

### Writing fillrect, step by step

1. **Start with a rectangle wholly inside the surface.** Fill it row by row; each
   row starts `y + j` rows of `s->w` pixels into the surface.
   ```
   void
   fillrect(struct surface *s, int x, int y, int w, int h, uint color)
   {
     ...
     for(int j = 0; j < h; j++){
       uint *row = s->px + (y + j) * s->w + x;
       for(int i = 0; i < w; i++)
         row[i] = color;
     }
   }
   ```
2. **Clip to the left and top.** A rectangle starting at x = -3 loses 3 pixels of
   width and starts at 0; the same for y.
3. **Clip to the right and bottom.** A rectangle wholly off the surface has no width
   or height left, and fills nothing. These are the same three steps as the
   kernel's `fb_rect` in 09.01, on a surface instead of the screen.

### Writing `line`, step by step

1. **Start with the loop: plot, stop at the end, step.** `putpixel`, a small
   helper, stores the pixel only if it falls inside the surface. Plotting before
   the test draws both ends, and a line from a point to itself draws exactly one
   pixel. Everything else decides which way the next step goes.
   ```
   void
   line(struct surface *s, int x0, int y0, int x1, int y1, uint color)
   {
     ...
     for(;;){
       putpixel(s, x0, y0, color);
       if(x0 == x1 && y0 == y1)
         break;
       ...
     }
   }
   ```
2. **Keep an error: how far the diagonal step would land from the line.** Take
   the width as a positive number and the height as a negative one. Then a step
   in x changes the error by `dy` and a step in y by `dx`, and it starts at
   `dx + dy`: on (0, 0) to (8, 3), 5, because the diagonal pixel (1, 1) is 5/8 of
   a pixel off the true line, counted in eighths.
   ```
   int dx = x1 > x0 ? x1 - x0 : x0 - x1;
   int dy = y1 > y0 ? y0 - y1 : y1 - y0;   // minus the height
   ...
   int err = dx + dy;
   ```
3. **Pick the closest of the next pixels.** At (1, 0) in the figure err is 2: the
   diagonal pixel (2, 1) is 2 eighths off the line, the next one in the row,
   (2, 0), is err - dx = -6, and the one in the next row, (1, 1), is
   err - dy = 5. Stepping in x is right when err is at least as near zero as
   err - dy, which works out to 2 * err >= dy; stepping in y, when it is at least
   as near zero as err - dx, that is 2 * err <= dx. Doubling keeps it in integers.
   ```
   int e2 = 2 * err;
   if(e2 >= dy){
     err += dy;
     x0 += sx;
   }
   ```
   Here 4 >= -3 and 4 <= 8, so both steps happen: the diagonal.
4. **Step in y the same way.** For a steep line the y test passes every time and
   the x test only now and then.

### Why it is built this way

**Clipping is the invariant.** A surface is just memory, and a pixel at x = -3 is a
store into the row above, or before the start of the array. So
**no drawing call writes outside the surface, whatever coordinates it is given**.
`fillrect` keeps that by cutting the rectangle down before it fills anything, so a
rectangle entirely off the surface fills nothing; `line` and `drawchar` check each
pixel as they plot it, through `putpixel`. Programs rely on this: `paint` draws
its pointer at the very edge of the screen without a second thought.

**Clip a rectangle once, not per pixel.** Checking every pixel would also be
correct, and would do the same four comparisons 307,200 times to fill the screen.
Clipping the rectangle first leaves a loop that only stores.

**The rest of `gui.c`.** `drawtext` draws a string one character every 8
pixels. `blit` copies one surface into another at a position, clipping as it
goes; 09.05 uses it to put its drawing on the frame. `screen_open` maps the
screen with `fbmap` and allocates a back buffer the size of it, all zeroes, which
is black; `present` copies that buffer to the screen.

**Integers only, in one loop for every direction.** The steps are +1 or -1 in x
and y, so a single loop draws lines going left, right, up, down, steep or shallow.
Integers matter here for more than speed: this kernel never saves floating-point
registers when it switches processes, so integer arithmetic is the only kind a
user program can count on.

**Bit 7 is the leftmost pixel.** A font is only an agreement about which bit is
which pixel, and the drawing code and the font must make the same one. In
`user/font.c` each byte has its row drawn beside it in a comment, so the font can
be read and changed by hand. Real text rendering scales outlines and smooths their
edges; at 8 by 8 pixels there is nothing to smooth.

**Why a back buffer.** QEMU reads the screen whenever it repaints the window, and
it cannot know whether a program is halfway through a frame. A program drawing
straight onto the screen would show its work in progress, for an instant a canvas
without a pointer or a cleared screen before the shapes return: that is flicker.
The back buffer is 1.2 MB from `malloc` (07.01), and `present` copies it to the
screen 8 bytes at a time, two pixels per store, half the stores of copying pixel by
pixel. The window then moves from one whole frame to the next.
Not quite atomically: if QEMU repaints during the copy, it shows the top of the new
frame over the bottom of the old one for one refresh, a **tear**. Hardware avoids
that by keeping two framebuffers and switching which one the display reads between
refreshes.

![Double buffering. The program draws into back, which nobody shows; present copies the finished frame to the screen in one pass.](figures/09.04-buffers.svg)

## Break it

Keep the lines in `events.c`, and in `drawchar`, in
`build/at/xv6/09.04/user/gui.c`, test the bits from the other end:

<!-- verify: patch file=user/gui.c
-      if(glyph[row] & (0x80 >> col))
@block
-->
```
      if(glyph[row] & (0x01 << col))
```

Run the lesson again and run `events`. The word at the top left is mirrored
letter by letter, in place: its p has turned into a q, its a and t face
backwards, while i and n, nearly symmetric, hardly change. Each letter also sits
one pixel further right than before. The glyphs use columns 1 to 5 of their 8;
mirrored, they use 2 to 6. Nothing complained, because a font is only an
agreement about which bit is which pixel, and this broke the agreement on one
side.

## Decide the boundary

xv6 turns lines into pixels in the program, with a library linked into each
program that draws. The kernel only maps memory. Elsewhere that work happens in
other places. In Plan 9 the kernel's draw device takes drawing commands written
to a file and does the drawing itself. An X11 program sends "draw a line from
here to there" over a socket to the X server, which owns the screen and draws for
everyone. A Wayland program draws into its own buffer, as xv6 does, and a
compositor puts the buffers together. Drawing in the program is the fastest
path and the least protected one; drawing in a server costs a message per
request and lets windows overlap safely. Where should a line become pixels: in
the program, in a server, or in the kernel?
