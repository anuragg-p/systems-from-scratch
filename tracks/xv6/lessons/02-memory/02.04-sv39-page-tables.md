# 02.04 Sv39 page tables

Page tables let the kernel decide what every address means: each access goes
through a table the kernel builds, which says where in RAM it lands and what
may be done there.

## Where this fits

![Where 02.04 fits](figures/02.04-map.svg)

This lesson finishes the memory layer. Below it, the page allocator supplies
the pages the tables are made of, and the memory map says what must be
mapped. Above it, every process will get a table of its own, so the same
address can mean different memory in different programs, and the kernel's
table keeps its own code from being overwritten. After this lesson paging is
on, and every address the kernel uses goes through a table.

## The idea

![The kernel's table at this lesson: devices and RAM at their own addresses, with the code one page below `etext`. The two mappings at the top that are not at their own addresses, the kernel stacks (04.01) and the trampoline (06.01), come later.](figures/02.04-kernel-address-space.svg)

Until now every address is physical: the number in a pointer is the place in
RAM. That cannot last. Two user programs are both built to start at address
0, and each must get its own memory there. A program must not be able to
read the kernel's memory, or another program's. And the kernel's own code
should not be writable, so that a stray pointer cannot overwrite it.

All three need the same thing: a layer between the address code uses and the
place in RAM it reaches. With **paging** the hardware looks every address up
in a table that the kernel owns. The table maps memory in pages of 4096
bytes, and each entry says which physical page an address lands on and
whether it may be read, written or executed.

One flat table for all addresses would be enormous, so RISC-V's **Sv39**
scheme uses a tree three levels deep. An address splits into three 9-bit
indices and a 12-bit offset. Take 0x80001234: the top index is 2, the middle
index is 0, the bottom index is 1, and the offset is 0x234. The hardware
reads entry 2 of the root table, which points at a second table; entry 0 of
that points at a third; entry 1 of the third gives the physical page; the
offset says where in it. Each table is exactly one page (512 entries of 8
bytes), so the allocator from the last lesson can supply them.

An entry holds a physical page number in bits 53..10 and flags below it:
V (valid), R, W and X (read, write, execute), U (user programs may use
it), and A and D, which the hardware sets once the page has been used and
written. An entry that is valid but has none of R, W, X points to the next
table, not to a page. The hardware finds the root through the `satp`
register, which holds mode 8 (Sv39) and the root's page number.

![`PA2PTE` moves the physical page number of `pa` into bits 53..10 of a PTE; the flags take the low bits.](figures/02.04-pte-bits.svg)

The kernel's own table is the simplest possible one: it maps every address
to the same physical address, a **direct map**, but with only the
permissions each region needs.

### `walk`

`kernel/vm.c:walk` does in software what the hardware does on every access:
it follows an address down the three levels and returns the bottom-level
entry for it. When asked to, it creates the missing tables on the way down.
Everything that reads or changes a mapping goes through it. `walkaddr`,
beside it, uses it to look up a user address; nothing calls that until
later lessons copy data in and out of a program's memory.

### `mappages`

`kernel/vm.c:mappages` maps a run of addresses to a run of physical memory,
one page at a time, using `walk` to find each entry and filling it in. It is
how every mapping, kernel or user, gets made.

### `kvmmake`

`kernel/vm.c:kvmmake` builds the kernel's table once at boot: the devices,
the kernel's code and the rest of RAM. When it is done, each hart switches
the hardware to that table and paging is on. Two more mappings join it
later, at the top of the address space, once there is something to put
there: the kernel stacks in lesson 04.01 and the trampoline in 06.01.

### `sfence_vma`

The hardware keeps recent translations in a small cache, the **TLB**
(translation lookaside buffer), so that it need not walk the tree on every
access. `sfence.vma` orders and flushes it. `kvminithart` issues one before
writing `satp`, so the table entries just written are what the hardware
walks, and one after, so no translation cached from before survives.

## How it works

### Writing `walk`, step by step

1. **Follow the tree.** Start at the root. At level 2, then level 1, take the
   entry for this level's index; a valid one holds the physical address of
   the next table, so go there. At level 0, return the entry's address, and
   let the caller read it or fill it in.
   ```
   for(int level = 2; level > 0; level--) {
     pte_t *pte = &pagetable[PX(level, va)];
     if(*pte & PTE_V) {
       pagetable = (pagetable_t)PTE2PA(*pte);
     } else {
       ...
     }
   }
   return &pagetable[PX(0, va)];
   ```
   `PX` picks one level's 9-bit index out of an address, and `PTE2PA` and
   `PA2PTE` convert between an entry and a physical address. Using a
   physical address as a pointer works because of the direct map, below.
2. **Build missing tables.** A new tree is empty, so the first mapping finds
   no table at level 1. When the caller allows it, link in a page from
   `kalloc` with `PTE_V` alone, which marks "points to a table"; when it is
   only looking, return 0.
   ```
   if(!alloc || (pagetable = (pde_t*)kalloc()) == 0)
     return 0;
   memset(pagetable, 0, PGSIZE);
   *pte = PA2PTE(pagetable) | PTE_V;
   ```
   The `memset` is not tidiness: a page from `kalloc` is full of 5s, and an
   unzeroed table would claim 512 valid mappings to nonsense.
3. **Out of range.** An address at or above `MAXVA` would have its high bits
   silently ignored and land on some other entry, so `walk` panics instead.

### Writing `mappages`, step by step

1. **A run of pages.** Walk to each page's entry, creating tables as needed,
   and fill it in: the physical page, the permissions, and the valid bit.
   `a` and `pa` move forward together, one page at a time, up to the last
   page of the range.
   ```
   a = va;
   last = va + size - PGSIZE;
   for(;;){
     if((pte = walk(pagetable, a, 1)) == 0)
       return -1;
     *pte = PA2PTE(pa) | perm | PTE_V;
     if(a == last)
       break;
     a += PGSIZE;
     pa += PGSIZE;
   }
   ```
2. **Out of memory.** The -1 is for a `walk` that could not get a page for a
   table: the caller decides. At boot nothing can recover, so `kvmmap` turns
   it into a panic; later callers undo what they mapped.
3. **Overlaps.** If the entry is already valid, two mappings claim one
   address. Replacing one silently would hide that bug, so panic at the
   moment it happens:
   ```
   if(*pte & PTE_V)
     panic("mappages: remap");
   ```
4. **Bad arguments.** Panic on an unaligned address or size, or a size of 0.
   Any of them would map pages the caller did not mean.

### Writing `kvmmake`, step by step

1. **A root, and the kernel's own memory.** One page from `kalloc`, zeroed
   for the same reason as in `walk`, then the kernel's code and the rest of
   RAM, each address mapped to itself.
   ```
   kpgtbl = (pagetable_t) kalloc();
   memset(kpgtbl, 0, PGSIZE);
   ...
   kvmmap(kpgtbl, KERNBASE, KERNBASE, (uint64)etext-KERNBASE, PTE_R | PTE_X);
   kvmmap(kpgtbl, (uint64)etext, (uint64)etext, PHYSTOP-(uint64)etext, PTE_R | PTE_W);

   return kpgtbl;
   ```
2. **Split at `etext`.** Two mappings, not one, so code can be run but not
   written, and data written but not run: a stray store into the kernel's
   code faults instead of quietly changing it.
3. **The devices.** The UART, the virtio disk and the PLIC, at their own
   addresses, read and write: once paging is on, the drivers still reach
   their registers by the addresses in `memlayout.h`. The PLIC gets 64 MB,
   all the register space its specification lays out, though QEMU's chip
   uses only the first 6 MB.
   ```
   kvmmap(kpgtbl, UART0, UART0, PGSIZE, PTE_R | PTE_W);
   ```

### Why the direct map is safe to switch on

Mapping every address to itself sounds pointless, and it is what makes the
kernel easy: a physical address from `kalloc` can be used as a pointer as it
is, which step 1 of `walk` relies on.

It also makes the moment paging turns on safe. **The invariant:** the page
the program counter is in must stay mapped and executable across the switch.
The instruction after the one that turns paging on is fetched at the same
address before and after, and with a direct map that address still leads to
the same code.

## Break it

In `build/at/xv6/02.04/kernel/vm.c`, drop the execute permission on kernel
text: in `kvmmake`, change the line that maps `KERNBASE` to `etext` from
`PTE_R | PTE_X` to just `PTE_R`. Run it, and the boot prints the banner and
then stops, with no panic and no hart lines:

The table is built, but when paging is turned on, the next instruction fetch
is from a page without execute permission: an instruction page fault. There
is no trap handler yet (it arrives in 03.01, after this point in `main`), so
the fault has nowhere useful to go: the monitor shows hart 0 at pc 0 with
`scause` 0xc, faulting on every fetch, and harts 1 and 2 still waiting for
`started`. You get silence, which is why 03.01 matters.

## Decide the boundary

xv6 uses a direct map and 4 KiB pages everywhere, three levels of tables, one
page per table. It is easy to reason about and costs a lot of table pages and
TLB entries for 128 MiB of RAM.

Another kernel could use 2 MiB or 1 GiB **superpages** (a leaf at level 1 or 2)
for the direct map, which saves tables and TLB entries. Linux does that for
its direct map. It pays with granularity: one permission and one fate for the
whole superpage. Or the kernel can map less, only what it needs, and use
temporary mappings to reach other physical memory.

Direct mapping all of RAM is simple and works while RAM fits in the address
space. The question that decides it is how much physical memory the kernel
needs to reach by plain pointer at once.
