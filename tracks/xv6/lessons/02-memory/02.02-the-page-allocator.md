# 02.02 The page allocator

`kalloc` and `kfree` hand out physical memory one 4096-byte page at a time,
and take it back.

## Where this fits

![Where 02.02 fits](figures/02.02-map.svg)

The memory map says free RAM runs from the end of the kernel to the end of
the machine's RAM; this lesson is what hands it out. Below it there is only
that RAM. Above it, nearly everything asks it for memory: page tables,
process stacks, pipe buffers, every page a user program owns. After this
lesson the kernel can get a page of memory when it needs one, and give it
back.

## The idea

![Each free page holds the address of the next free page in its first 8 bytes. `kalloc` takes the head and fills it with 5s.](figures/02.02-free-list.svg)

At run time the kernel keeps needing memory it could not plan for: a new
process needs a stack, a new page table needs a page, a pipe needs a buffer.
Each request must get memory nobody else is using, and each page given back
must become available again. Something has to keep track of some 32,750
pages.

The catch is that the bookkeeping itself needs memory, and there is no
allocator yet to get it from. The way out: a free page is, by definition,
not being used, so it can hold the bookkeeping itself. Each free page stores
the address of the next free page in its first 8 bytes. The free pages
**are** the list. Giving a page back pushes it on the front; handing one out
takes the front one off. Both are a handful of instructions, whatever the
size of memory.

All pages are the same size, 4096 bytes, the unit the page tables of 02.04
work in. Nothing smaller is ever handed out, so there is never a gap too
small to use.

### `kinit`

`kernel/kalloc.c:kinit` runs once, early in boot on hart 0. It gives every
whole page between the end of the kernel image and the end of RAM to
`kfree`, one at a time, so that the list starts out holding all of free
memory.

### `kfree`

`kernel/kalloc.c:kfree` takes a page back. It is called by everyone who is
done with a page, and by `kinit` to fill the list in the first place. It
checks the address, fills the page with junk, and pushes it on the list.

### `kalloc`

`kernel/kalloc.c:kalloc` hands a page out. It pops the front of the list,
fills the page with different junk, and returns it, or returns 0 when memory
has run out, so every caller must be ready for that.

### `string.c`

The junk goes in with `memset`, and with no C library there is no `memset`
to call, so `string.c` brings the kernel's own: `memset`, and the other
byte and string routines (`memmove`, `strlen`, `safestrcpy` and the rest)
that later lessons use.

## How it works

### Writing `kfree` and `kalloc`, step by step

1. **A list in the free pages.** The simplest allocator that works on one
   hart: treat a free page as a `struct run`, which is nothing but a next
   pointer, push it on the list to free it, and pop the head to hand one
   out.
   ```
   kfree(void *pa)
   {
     r = (struct run*)pa;
     r->next = kmem.freelist;
     kmem.freelist = r;
   }

   kalloc(void)
   {
     r = kmem.freelist;
     if(r)
       kmem.freelist = r->next;
     return (void*)r;
   }
   ```
   The page must point at the old head before it becomes the head: that
   pointer is the only link to the rest of the list. An empty list makes
   `kalloc` return 0, and every caller has to check for it.
2. **Refuse bad pages.** `kfree` panics on an address that is not page
   aligned, or not between the end of the kernel and the end of RAM. Pushed
   on the list, such a "page" would be handed to someone much later, far
   from the bug that freed it.
3. **Junk.** Fill a page with 1s as it comes back and with 5s as it goes out.
   Code that keeps using a freed page then reads 0x0101010101010101, and code
   that assumes a fresh page is zeroed reads 0x0505050505050505; either fails
   early, near the mistake. Callers that need zeroes, such as page tables,
   clear the page themselves.
4. **Three harts, later.** Two harts popping at the same moment can take
   the same page: one page, two owners. For now only hart 0 allocates;
   lesson 02.03 puts the push and the pop under `kmem.lock`, the field
   already waiting in `kmem`, and leaves the fills outside it, since they
   touch only a page one caller owns.

### One owner per page

**The invariant:** every page is either on the free list or owned by exactly
one caller, never both. The classic way to break it is to free a page twice:
it then sits on the list twice, and two callers will get it. The range check
in step 2 keeps garbage off the list, and the junk in step 3 makes a breach
show up quickly, near the caller that broke it. Between harts it needs the
lock of step 4, which 02.03 adds.

`kinit` builds the starting list with nothing but `kfree`: it rounds `end`
up to the next page boundary (`PGROUNDUP`), since the image rarely ends on
one, and frees every whole page from there to `PHYSTOP`, lowest first.

## Break it

In `build/at/xv6/02.02/kernel/kalloc.c`, make the push in `kfree` forget
the rest of the list: replace `r->next = kmem.freelist;` with
`r->next = 0;`. In `main`, in place of Run it's three lines, ask for two
pages:

<!-- verify: patch file=kernel/kalloc.c
-  r->next = kmem.freelist;
+  r->next = 0;
-->
<!-- verify: patch file=kernel/main.c
     kinit();         // physical page allocator
@block
-->
```
printf("first page %p\n", kalloc());
printf("second page %p\n", kalloc());
```

What will they be?

<!-- verify: session run="./learn run xv6 --at 02.02" more -->
```
xv6 kernel is booting

first page 0x0000000087fff000
second page 0x0000000000000000
```

Every `kfree` now throws away every page freed before it. After `kinit`, the
list holds exactly one page, the last one freed; the second `kalloc` finds
the list empty and returns 0. The first build with a real caller is
02.04's, where the kernel's page table needs many pages: make the same
change in `build/at/xv6/02.04/kernel/kalloc.c`, run
`./learn run xv6 --at 02.04`, and the boot stops right after the banner with
`panic: kvmmap`.

<!-- verify: patch file=kernel/kalloc.c at=02.04
-  r->next = kmem.freelist;
+  r->next = 0;
-->

![With `r->next = 0`, every `kfree` drops the list it was handed, and only the last page freed is left on it.](figures/02.02-lost-list.svg)

The point: the next pointers are the only record of which pages are free. Lose
them and the memory is still there, 128 MiB of it, but nothing can ever be
allocated from it again.

## Decide the boundary

xv6 keeps one free list for the whole machine, one lock, one page size. It is
about as small as an allocator can be.

Another kernel could give each hart its own free list, so a hart allocates
without touching a shared lock, and steals from a neighbour only when its own
list runs dry. It pays in code: stealing, and keeping the lists balanced.
Linux goes much further. Its buddy allocator hands out runs of 2^n contiguous
pages, which devices that do DMA need, and it pays with splitting and merging
logic and a separate path for small objects (the slab allocator).

With three harts and a page grabbed only now and then, one lock is not the
bottleneck. How many harts, and how often, before the lock is what you wait on?
