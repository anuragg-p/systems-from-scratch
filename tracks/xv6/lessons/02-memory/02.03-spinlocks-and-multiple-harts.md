# 02.03 Spinlocks and multiple harts

`acquire` and `release` let three harts share one piece of data without
losing each other's changes.

## Where this fits

![Where 02.03 fits](figures/02.03-map.svg)

Locks do not sit above or below the other layers; they sit beside all of
them. Below them is the machine itself: three harts reading and writing one
shared memory. Above them, every shared structure in the kernel is guarded
by one, starting with the page allocator's free list from the last lesson,
and later the process table, the disk cache and the console. After this
lesson the kernel can let three harts touch the same data safely.

## The idea

![Two harts adding 1 to `x`, which holds 5. Without a lock both load 5. With one, hart 1 spins until hart 0 has stored.](figures/02.03-race-and-lock.svg)

Take the simplest shared update there is, `x = x + 1`, with `x` holding 5.
On a hart it is three steps: load `x`, add one, store it back. If two harts
do it at the same moment, both can load 5 before either stores, and both
store 6. One of the two increments is simply gone.

The page allocator has exactly this problem. If two harts read the front of
the free list at the same time, both take the same page, and one page now
has two owners who will overwrite each other's data.

The fix is to make the code that touches shared data a **critical section**:
only one hart may be inside it at a time. A **spinlock** guards it with one
word: 0 when free, 1 when held. To take the lock, a hart sets the word to 1;
if it was already 1, someone else has it, so the hart tries again, in a
loop, until it wins.

### `acquire`

`kernel/spinlock.c:acquire` takes a lock before a critical section, and
waits as long as it has to. Every shared structure in the kernel is reached
through a call to it.

### `release`

`kernel/spinlock.c:release` gives the lock back at the end of the critical
section, so one of the harts spinning in `acquire` can get in.

### The first two locks

This lesson also puts the first locks to use, in the two places that
already share data between harts. The allocator of 02.02 gets its push and
its pop under `kmem.lock`. And `printf` takes a lock of its own for each
whole call, which is what finally keeps the hart lines of 01.03 in one
piece; a panic still prints without waiting for it.

### `uartputc_sync`

The UART's `uartputc_sync` now turns interrupts off around its wait and
its write, although it takes no lock. The pair must not be split: an
interrupt whose handler prints (the keyboard echo of 03.03 will) could fill
the transmitter after this hart saw it empty, and the byte written next
would be lost. It uses the same `push_off` and `pop_off` the locks use, so
that when `printf` already holds its lock, interrupts stay off afterwards.

## How it works

### Writing `acquire` and `release`, step by step

1. **One indivisible swap.** The obvious lock, wait until `locked` is 0 and
   then set it to 1, lets two harts both see 0 before either writes 1, and
   both walk in. Instead, swap 1 into the word and look at what came out, as
   one atomic step. Only the hart that gets 0 back has the lock; everyone
   else tries again. Freeing it is a store of 0.
   ```
   acquire(struct spinlock *lk)
   {
     while(__sync_lock_test_and_set(&lk->locked, 1) != 0)
       ;
   }

   release(struct spinlock *lk)
   {
     __sync_lock_release(&lk->locked);
   }
   ```
2. **Fences.** The processor and the compiler may move loads and stores
   across the swap, so work meant for inside the critical section could
   happen before the lock is held or after it is freed. A
   `__sync_synchronize()` after taking the lock and one before freeing it
   pin that work inside.
3. **Interrupts off while a lock is held.** If a hart holding the lock on
   the tick counter takes a timer interrupt whose handler wants the same
   lock, the handler spins forever: the holder cannot release anything
   until the handler returns. So `acquire` begins with `push_off()` and
   `release` ends with `pop_off()`.
4. **Know the owner.** `acquire` ends by recording `lk->cpu = mycpu()`, this
   hart's `struct cpu` from 01.03, found through `tp`. Then taking a lock
   twice on one hart, which would spin forever, panics at once, and so does
   releasing a lock this hart never took.
   ```
   if(holding(lk))
     panic("acquire");
   ```
5. **Release in the right order.** `release` clears the owner before it
   frees the word. The moment `locked` is 0, another hart may take the lock
   and write its own name, and a clear after that would wipe it out.
   ```
   lk->cpu = 0;
   __sync_synchronize();
   __sync_lock_release(&lk->locked);
   ```

### The swap, in the machine code

<!-- verify: fact cmd='sed -n "/<acquire>:/,/^$/p" build/kernel/kernel.asm | grep -o "amoswap.*" | tr "\t" " "' expect="amoswap.w.aq a5,a5,(s1)" -->
The loop in Run it is step 1 as the hardware sees it.
`amoswap.w.aq a5,a5,(s1)` writes a5, which holds 1, into the lock word at
`(s1)` and puts the old value in a5, as one step the memory system will not
split. Of any number of harts swapping on the same word, exactly one gets 0
back; the `bnez` sends the rest round again. The `.aq` suffix (acquire)
also stops later loads and stores from moving above the swap.

![Both harts swap 1 into `lk->locked`. The memory does one swap at a time, so only the first gets back 0.](figures/02.03-amoswap.svg)

Releasing needs no swap. The compiler turns it into `fence rw,w` and a
plain `sw zero,0(s1)`: an aligned 32-bit store is atomic on RISC-V, and the
fence supplies the ordering.

### Interrupts come back only at the last release

Locks nest: a hart can hold two at once. So `push_off` and `pop_off` keep a
count, and they remember whether interrupts were on before the first one.
Two locks held means two `push_off`s, and interrupts come back only when the
last `pop_off` takes the count to zero, and only if they were on to begin
with.

![Two locks held, two `push_off`s. Interrupts come back only when the last `pop_off` takes `noff` to 0.](figures/02.03-push-pop-nesting.svg)

**The invariant:** a lock's word is 1 exactly while one hart is inside its
critical section, and that hart cannot be interrupted.

## Break it

replace the swap loop in `acquire` with

```
  while(lk->locked != 0)
```

On most boots one hart line is missing, and nothing else ever prints. (Now
and then both harts do walk in at once: their lines mix, and a `release`
panics, because the lock no longer names that hart as its holder.) The
monitor finds the missing hart in `acquire`, at 0x8000074e, which
`kernel.asm` shows is a loop of two instructions:

<!-- verify: file path=build/kernel/kernel.asm -->
```
    8000074c:	409c                	lw	a5,0(s1)
    8000074e:	e381                	bnez	a5,8000074e <acquire+0x22>
```

The hart found `printf`'s lock held by the other one, and the compiler,
seeing nothing in the loop that could change `locked`, loaded it once: the
hart now waits on a copy in a register (the reason `started` in 01.03 is
`volatile`). Even read every time, two harts could both see 0. The swap is
one instruction that reads and writes memory, so neither can happen. Put it
back.

## Decide the boundary

xv6 uses only spinlocks: a waiting hart burns cycles in a loop and never
sleeps. That is right when the critical section is a few instructions, like
the list update in `kalloc`. It is wrong for a long wait, such as a disk read,
where spinning wastes a whole hart for milliseconds; for those the kernel uses
`sleep` and `wakeup` (04.03), and sleep locks later.

Another kernel could use a ticket lock, which hands the lock out in arrival
order so no hart starves, at the cost of a second word and more traffic. Linux
does this and more: queued locks, so each waiter spins on its own cache line.

With three harts, plain spinning is cheap. The question that decides it is
how many harts contend for one lock.
