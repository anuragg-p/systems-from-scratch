# 02.01 The physical memory map

Before the kernel can manage memory it has to know where memory is: which
addresses are RAM, which are devices, and which fixed places at the top of
every address space are spoken for.

## Where this fits

![Where 02.01 fits](figures/02.01-map.svg)

This lesson opens the memory layer, which sits on top of boot and under
almost everything else. Below it, the machine has RAM at one address and
device registers at others, and nothing at run time tells the kernel which
is which. Above it, the page allocator, the page tables, every process and
every driver use these numbers. After this lesson the kernel has one place
that says where everything is.

## The idea

![Physical addresses on QEMU `virt` as this kernel uses them: device registers low, RAM from `KERNBASE` to `PHYSTOP`.](figures/02.01-physical-map.svg)

Module 02 makes memory something the kernel can manage: this map, a page
allocator that hands out free RAM (02.02), locks so three harts can share it
safely (02.03), and page tables that switch on virtual memory (02.04).

To the hardware, an address is just a number, and what happens when you use
it depends entirely on where it points. A store to 0x10000000 prints a
character on the terminal. A store to 0x80000000 overwrites the kernel's own
first instruction. A store to 0x88000000 faults, because the machine has no
RAM there. Nothing stops the kernel from getting any of these wrong.

So the kernel writes the facts down once, in one header,
`kernel/memlayout.h`, and everything else uses the names. It holds two kinds
of address. A **physical address** names a real byte in the machine: RAM or
a device register. A **virtual address** is what running code uses once
paging is on (lesson 02.04), translated by the hardware into a physical one.
The first half of the header is physical: where QEMU's board puts each
device, and where RAM starts and ends. The second half is virtual: the
fixed pages at the top of every address space.

## Run it

```
./learn run xv6 --at 02.01
```

The boot looks just as it did in 01.03: this lesson adds names, not code.
What the names describe can be checked against the machine itself. Press
Control-a, then c, and ask QEMU for its memory map:

<!-- verify: session run="./learn run xv6 --at 02.01" send="ctrl-a c" -->
```
(qemu) info mtree
...
    000000000c000000-000000000c5fffff (prio 0, i/o): riscv.sifive.plic
    0000000010000000-0000000010000007 (prio 0, i/o): serial
    0000000010001000-00000000100011ff (prio 0, i/o): virtio-mmio
...
    0000000080000000-0000000087ffffff (prio 0, ram): riscv_virt_board.ram
...
```

Each line is one of the header's constants: `PLIC` at 0x0c000000, `UART0`
at 0x10000000 (8 bytes of registers), `VIRTIO0` at 0x10001000, and RAM from
`KERNBASE` up to, not including, `PHYSTOP`, 0x88000000. The rest of the
list is the board's other devices, which this kernel never touches.

## How it works

### The addresses are written in, not discovered

QEMU's `virt` is a fixed board, so the kernel simply knows where its devices
are; the header has a constant for each. A real machine would describe its
devices in a **device tree** passed in at boot, and a kernel for real
hardware would read it. This one does not. The price is that the kernel runs
on exactly this board, and on nothing else.

### RAM is assumed to be exactly 128 MB

RAM starts at `KERNBASE`, 0x80000000, where the linker put the kernel, and
the kernel assumes it ends at `PHYSTOP` = `KERNBASE + 128*1024*1024` =
0x88000000. That number is a promise about the `-m 128M` in the Makefile.
The memory from `end` up to `PHYSTOP`, nearly all of 128 MB's 32,768 pages
of 4096 bytes, is what the page allocator in 02.02 will hand out.

**The invariant:** every address in the header must be true of the
machine. `PHYSTOP` must match `-m 128M`, and each device must be where the
board puts it. Nothing checks any of it.

### Interrupt numbers, for later

Devices get a hart's attention with interrupts, each with a number: the
UART raises interrupt 10 and the disk interrupt 1 (`UART0_IRQ`,
`VIRTIO0_IRQ`; the disk speaks virtio, the standard interface of QEMU's
virtual devices, lesson 05.01). The **PLIC**, the platform-level interrupt
controller, collects them and passes each to a hart. The `PLIC_*` macros
are the addresses of its registers: a priority per interrupt, and per hart
the interrupts it wants, the lowest priority it takes, and where it claims
the one that arrived. Lesson 03.03 uses them; they are here so that the
whole map is in one place.

### The top of the address space is spoken for

`MAXVA` is 2^38, not 2^39. Sv39 paging (02.04) has 39 address bits, but
the hardware insists the top bit be copied into every bit above it, and xv6
sidesteps that by using only the lower half. Counting down from there: the
**trampoline** page, mapped at the same address in every address space
(lesson 06.01); below it each process's **trapframe**, where its registers
are saved; and below that one kernel stack per process slot.

None of these pages exists yet. The names are written down now so that the
whole map is in one place: `MAXVA` itself is defined with the page tables
of lesson 02.04, the kernel stacks are mapped in 04.01, and the trampoline
and the trapframes in 06.01.

The kernel stacks are two pages apart, and only one of each pair is mapped.
The empty page under each stack is a **guard page**: a stack that overflows
runs into it and faults at once, instead of quietly overwriting the next
process's stack. That is the protection `stack0` in lesson 01.01 does not
have, and the reason the stacks live up here and not in RAM's own
addresses, where every page will be mapped (02.04) and none can be left
empty.

![The top pages of virtual memory. One address can mean different pages in the kernel's table and in a process's.](figures/02.01-virtual-top.svg)

User programs fill the address space from the other end: their code and
data start at 0, then a stack page with a guard below it, then a heap that
grows upward until it would reach the trapframe.

## Break it

Tell the kernel its serial port is somewhere else. In
`build/at/xv6/02.01/kernel/memlayout.h`, change `UART0` from `0x10000000L`
to `0x88000000L`, just past the end of RAM, and run it again. What will the
console show?

<!-- verify: patch file=kernel/memlayout.h
-#define UART0 0x10000000L
+#define UART0 0x88000000L
-->

Nothing at all. The monitor tells why:

<!-- verify: session run="./learn run xv6 --at 02.01" wait=3 send="ctrl-a c" -->
```
(qemu) info registers -a

CPU#0
...
 pc       0000000000000000
...
 scause   0000000000000001
...
CPU#1
...
 pc       0000000080000094
...
CPU#2
...
 pc       0000000080000094
...
```

(trimmed). Hart 0's first store to the "UART", in `uartinit`, went to an
address with nothing behind it and faulted. With no trap handler yet
(03.01), the fault sent it to address 0, where there is nothing either, and
it faults there over and over (`scause` 1: an instruction fetch failed).
Harts 1 and 2 sit at 0x80000094, in `main`'s loop waiting for `started`,
which hart 0 never set. The header made a claim, and nothing checked it.

<!-- verify: revert file=kernel/memlayout.h -->
<!-- verify: patch file=kernel/memlayout.h at=02.02
-#define PHYSTOP (KERNBASE + 128*1024*1024)
+#define PHYSTOP (KERNBASE + 256*1024*1024)
-->
<!-- verify: revert file=kernel/memlayout.h at=02.02 -->

`PHYSTOP` makes the same kind of claim, but nothing reads it until the page
allocator of 02.02. Put `UART0` back, and in the 02.02 build
(`build/at/xv6/02.02/kernel/memlayout.h`) change `PHYSTOP` to
`(KERNBASE + 256*1024*1024)`, leaving QEMU at 128 MB. With
`./learn run xv6 --at 02.02`, the banner prints and then nothing does: the
allocator writes to every page it is told is RAM, and the first one past
0x88000000 is not there.

## Decide the boundary

xv6 hard-codes the machine: constants in a header, one board, 128 MB. Linux
asks the firmware for a device tree, finds the RAM size at boot, and loads
a driver for what it finds. xv6 gets simplicity (no parsing, no probing,
no drivers loaded) and gives up running anywhere but `virt` with this much
memory.

Neither is wrong; they answer different questions. Is the kernel for
one known machine, or for whatever it happens to wake up on?
