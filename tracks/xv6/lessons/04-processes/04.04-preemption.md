# 04.04 Preemption

This lesson adds the two lines that let the timer interrupt take a hart
away from a process that is running kernel code.

## Where this fits

![Where 04.04 fits](figures/04.04-map.svg)

Preemption joins two pieces built earlier: the timer interrupt, which
arrives on every hart about ten times a second, and the scheduler, which
can set a running process aside. Until now a process left its hart only
when it chose to. This lesson lets the tick choose for it when the tick
lands while the process is in the kernel; the same choice for user code
comes with the user trap handler in module 06. Once both are in, no
process can keep a hart forever.

## The idea

![What sits on A's kernel stack while the tick has it switched out, and the steps that bring it back.](figures/04.04-preempted-stack.svg)

**The need.** Picture a system call that loops for a long time without
sleeping, or a kernel bug that loops forever. Nothing in it calls `yield`
or `sleep`, so with only the code so far, that hart is gone: the processes
waiting for it never run on it again. Scheduling that relies on every
thread to give up the hart by itself is **cooperative**, and it is only as
good as the least cooperative thread.

**The idea.** Something outside the running code has to make the choice,
and the kernel already has it: the timer interrupt from 03.02, which
arrives on every hart about ten times a second. When a tick finds a
process running on the hart, the interrupt handler yields on that
process's behalf. The interrupted code never knows; when the scheduler
comes back to it, the trap returns and the code carries on at the
instruction where it was stopped. Taking the hart from a thread that did
not ask to give it up is **preemption**.

A tick can find the hart in one of two places. If the process was running
user code, the trap goes to the user trap handler, which 06.01 builds with
the same check. If it was running kernel code, in a system call say, the
trap goes to `kerneltrap`, and that is the half this lesson adds.

### The two lines in `kerneltrap`

`kernel/trap.c:kerneltrap` handles every trap taken while the hart is in
the kernel, and by this point it has asked `devintr()` what the trap was.
The two lines say: if it was the timer, and a process is running on this
hart, call `yield()` from 04.02.

## Run it

`./learn run xv6 --at 04.04` boots to the same lines as before. There is
no process yet, so every tick lands in a scheduler and the new lines do
nothing. To see them work, give the harts more than they can hold: four
processes that never give the hart up. Add this at the end of
`build/at/xv6/04.04/kernel/proc.c`:

<!-- verify: patch file=kernel/proc.c append
@block
-->
```
static void
spin(void)
{
  release(&myproc()->lock);   // the scheduler took it, as for forkret
  intr_on();
  for(;;)
    ;
}

void
spawn(void)
{
  for(int i = 0; i < 4; i++){
    struct proc *p = allocproc();
    p->name[0] = 'A' + i;
    p->context.ra = (uint64)spin;
    p->state = RUNNABLE;
    release(&p->lock);
  }
}
```

The `intr_on` matters: the scheduler hands over with interrupts off, and a
loop with interrupts off cannot be interrupted by anything. In
`kernel/main.c`, declare `void spawn(void);` above `main` and call
`spawn();` right after `procinit();`. Boot, and press Control-P a few
times; two of the listings:

## How it works

**Yielding from inside a trap.** When the tick arrives, the hart is
halfway through some kernel function. `kernelvec` has pushed the
registers on the process's own kernel stack and called `kerneltrap`; the
two lines then switch away. The process is parked in the middle of a
trap, with the frames of `kernelvec`, `kerneltrap`, `yield` and `sched`
on its stack, as the figure shows. That is fine, because the stack goes
with the process. When a scheduler, on any hart, picks it again, the calls
unwind and the trap returns as if nothing had happened.

**Putting the trap registers back.** One thing does not travel with the
process: the hart's trap registers. While it was switched out, other code
took traps and overwrote `sepc` and `sstatus`, and the process may even be
resumed on another hart. So `kerneltrap` reads both into local variables
at its start and writes them back after the two lines:

```
  w_sepc(sepc);
  w_sstatus(sstatus);
```

Without that, `kernelvec`'s `sret` would return to wherever the last trap
on this hart came from.

**Only the timer.** A key or a finished disk read does not mean the
running process has had its turn, so device interrupts do not yield;
yielding on every one would only add switches.

**Only when there is a process.** The scheduler loop itself runs with no
process (`myproc()` is 0) and opens a window for interrupts on every pass,
and an idle hart wakes from `wfi` with an interrupt pending, often the
tick. A tick taken there has nothing to yield. Hence the second check,
`myproc() != 0`.

A trap in the kernel can arrive only when no spinlock is held, because
holding one turns interrupts off. So when `yield` takes the process lock,
it is the only lock held, and `sched`'s rule of exactly one lock is met.

The **invariant**: every hart takes a timer interrupt about ten times a
second, and a tick that finds a process running on that hart, in user
space or in the kernel, ends with `yield()`.

Within the first second the boot dies, on more than one hart at once, so
everything after the first line comes out mixed. `scause=0xd` is a load
page fault and `stval=0x0` the address. Look the `sepc` up in
`build/at/xv6/04.04/build/kernel/kernel.asm` and it is the first
instruction of `holding`, reading `lk->locked`: a tick landed in a
scheduler, where `c->proc` is 0, and `yield` went to lock `&p->lock` with
`p` = 0. It takes no bug in the scheduler to get there, only a tick in the
window the scheduler opens on every pass.

## Decide the boundary

<!-- verify: mention names="preempt_disable()" outside reason="Linux's, not this kernel's" -->
xv6 preempts in both modes, on a fixed 100 ms tick. Another kernel could
preempt user code only. Linux did exactly that until the 2.6 series added
optional kernel preemption, and it still lets code switch it off with
`preempt_disable()`. A non-preemptible kernel is easier to write: no other
thread runs in the middle of kernel code unless it sleeps. It pays in latency:
a long system call holds the hart, and a loop in the kernel hangs that hart
for good.

Would you rather reason about kernel code that can be interrupted
anywhere, or live with a hart that a runaway system call can keep?
