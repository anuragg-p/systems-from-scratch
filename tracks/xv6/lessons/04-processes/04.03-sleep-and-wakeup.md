# 04.03 Sleep and wakeup

Most of the time a process is waiting for something, and this lesson
covers the pair of calls that lets it wait without holding a hart.

## Where this fits

![Where 04.03 fits](figures/04.03-map.svg)

Sleep and wakeup sit on top of the context switch: a process that waits
is switched out and not picked again until the event it waits for
happens. Above them, nearly every part of the kernel that waits will use
them: console input, the disk, pipes, a parent waiting for its child, the
clock. Below, they use the process table and the scheduler from the last
two lessons. After this lesson a process can wait for an event without
spinning, and whoever causes the event can wake it.

## The idea

![If `sleep` let go of the condition lock first, the wakeup could land in the gap and find no one asleep.](figures/04.03-lost-wakeup.svg)

**The need.** The shell asks for a line of input and none has been typed.
It could loop, checking the console buffer over and over, but that burns a
whole hart doing nothing, and with three harts and a few such waiters the
machine would be full of busy loops. What the shell wants is to be set
aside until the line arrives, and then be made runnable again by whoever
put it there.

**The idea.** A waiter marks itself `SLEEPING` on a **channel**, which is
just an address both sides agree on, and switches to the scheduler, which
will not pick it while it sleeps. When the event happens, the code that
caused it calls `wakeup` on the same address, which turns every sleeper on
that channel back into `RUNNABLE`. The console will sleep and wake on the
address of its read index, the `wait` system call (06.04) on the parent's
own process slot, and the disk driver of 05.01 on the buffer it is
filling.

The hard part is timing. The waiter checks a condition ("is there a
line?"), finds it false, and goes to sleep. If the line arrives in the gap
between the check and the moment the waiter is marked asleep, `wakeup`
finds nobody sleeping and does nothing. The waiter then sleeps on a
condition that is already true, and nothing will ever wake it. This is the
**lost wakeup**, and it shapes everything below.

The fix uses the lock that already protects the condition, the
**condition lock**. The waiter checks the condition while holding it, and
the waker takes it to change the condition and call `wakeup`. `sleep` is
handed that lock, and must let go of it while asleep, or the waker could
never get in, but it must let go in a way that leaves no gap.

### `sleep`

Called by anything that waits: the disk driver (05.01), sleep locks
(05.02), the console's reader (05.07), `wait` (06.04) and pipes (06.06).
`kernel/proc.c:sleep(chan, lk)` puts the calling process to sleep on
`chan`, releasing the condition lock `lk` while it sleeps, and returns
holding `lk` again, ready to recheck the condition.

### `wakeup`

Called by whatever makes the condition true: an interrupt handler, a
pipe writer, an exiting child, the timer. `kernel/proc.c:wakeup(chan)`
makes every process sleeping on `chan` runnable. It does not run them; the
scheduler will.

This lesson adds the first two calls to it, in code that already runs on
every interrupt. The console's input handler (03.03) now wakes the
console's reader when it finishes a line, `wakeup(&cons.r)`, and the clock
(03.02) wakes whoever sleeps on `ticks`, `wakeup(&ticks)`, on every tick of
hart 0. Both follow the rule above: each is called with its condition lock
held, `cons.lock` and `tickslock`.

## Run it

`./learn run xv6 --at 04.03` boots to the same lines as before: nothing
sleeps yet, because there is no process to do it. Make one that sleeps on
the clock. Add this at the end of `build/at/xv6/04.03/kernel/proc.c`:

<!-- verify: patch file=kernel/proc.c append
@block
-->
```
static void
nap(void)
{
  release(&myproc()->lock);   // the scheduler took it, as for forkret
  acquire(&tickslock);
  for(;;){
    uint t0 = ticks;
    while(ticks - t0 < 10)
      sleep(&ticks, &tickslock);
    printf("nap: tick %d, hart %d\n", ticks, cpuid());
  }
}

void
spawn(void)
{
  struct proc *p = allocproc();
  safestrcpy(p->name, "nap", sizeof(p->name));
  p->context.ra = (uint64)nap;
  p->state = RUNNABLE;
  release(&p->lock);
}
```

It is a process that lives only in the kernel, with its context's `ra`
pointed at `nap` instead of `forkret`. In `kernel/main.c`, declare
`void spawn(void);` above `main` and call `spawn();` right after
`procinit();`. Boot, and press Control-P between two lines:

## How it works

### Writing `sleep`, step by step

1. **The obvious version first:** record the channel, set the state to
   `SLEEPING`, give up the hart. That is all that sleeping is, but as it
   stands it does not work yet: `sched` refuses a caller that does not hold
   its own `p->lock`.
   ```
     struct proc *p = myproc();
     ...
     p->chan = chan;
     p->state = SLEEPING;

     sched();
   ```
2. **Take `p->lock`, then release the condition lock, in that order.**
   `sleep` has to give up `lk`, or nobody could ever make the condition
   true; taking `p->lock` first is what leaves no gap, as explained below.
   ```
     acquire(&p->lock);
     release(lk);
   ```
3. **After waking, put things back:** clear the channel, release
   `p->lock`, take `lk` again, so the caller can recheck its condition.

### Writing `wakeup`, step by step

1. **Scan every slot** and make each one `SLEEPING` on this channel
   `RUNNABLE`; the scheduler does the rest.
   ```
     for(p = proc; p < &proc[NPROC]; p++) {
       ...
         if(p->state == SLEEPING && p->chan == chan) {
           p->state = RUNNABLE;
         }
       ...
     }
   ```
2. **Lock each slot while looking at it.** That is what makes a waker wait
   for a sleeper that is halfway into `sleep`.
3. **Skip the caller.** It is running, so it cannot be asleep on the
   channel, and taking its lock would panic (02.03) if it happened to hold
   it already.

### Why it is built this way

**Take the process lock before releasing the condition lock.** `wakeup`
must take a sleeper's `p->lock` to look at its state. Once `sleep` holds
`p->lock`, a waker that gets `lk` either finished before this point, in
which case the waiter's check already saw the new condition, or it blocks
on `p->lock` until the waiter has switched away with its state set to
`SLEEPING`. Either the waiter saw the event, or `wakeup` sees a sleeping
waiter. There is no third case. The scheduler releases `p->lock` after the
switch (04.02), and only then can the waker get in.

![Taking `p->lock` before releasing `lk` closes the gap: the waker waits until the sleeper is really asleep.](figures/04.03-sleep-order.svg)

**Wake everyone, and let each recheck.** `wakeup` scans the whole table
and makes every sleeper on the channel runnable. It does not know which
one the event was meant for, and it does not need to: each caller sleeps
in a loop that rechecks its condition, as `nap` does, and as the console's
`consoleread` will in lesson 05.07.

<!-- verify: quote at=05.07 -->
```
    while(cons.r == cons.w){
      ...
      sleep(&cons.r, &cons.lock);
    }
```

A return from `sleep` is a hint, not a promise. Another process may have
taken the event first; the loop sends this one back to sleep.

The **invariant**: a process in state `SLEEPING` has its channel set and is
parked inside the scheduler switch, holding no lock but its own
`p->lock`, which the scheduler drops. Nothing sleeps while holding any
other spinlock; `sched` panics if it tries.

## Break it

Keep `nap`, and in `sleep` delete the line that changes the state:

<!-- verify: patch file=kernel/proc.c
   p->chan = chan;
-  p->state = SLEEPING;
-->
```
  p->chan = chan;
  p->state = SLEEPING;     <- delete this line
  sched();
```

Boot:

<!-- verify: session run="./learn run xv6 --at 04.03" panics="sched RUNNING"
lines 3-4 anywhere
lines 3-4 optional
line 5 ~ (hart [12] ?[a-z]*)?panic: sched RUNNING
-->
```
xv6 kernel is booting

hart 2 starting
hart 1 starting
panic: sched RUNNING
```

`nap`'s first sleep reached `sched` still marked `RUNNING`. Let through, it
would be lost without a sound: no scheduler picks a `RUNNING` process and
no `wakeup` touches one. `sched` panics instead, so the mistake shows where
it was made.

Put the line back and swap the first pair instead, so `sleep` lets go of
`lk` before it takes `p->lock`. Here nothing changes that you can see: a
wakeup that lands in the gap is lost, but the clock calls `wakeup` again a
tenth of a second later. A lost wakeup hangs a process for good when the
event comes once, like a disk read finishing, and the first build with
such reads is 07.02, where the first process reads the disk before it can
run `init`. The gap is only a few instructions wide, so give it room. In
`build/at/xv6/07.02/kernel/proc.c`, make the swap with a delay between the
two lines:

<!-- verify: patch at=07.02 file=kernel/proc.c
-  acquire(&p->lock);
-  release(lk);
@block
-->
```
  release(lk);
  for(volatile int i = 0; i < 1000000; i++)
    ;
  acquire(&p->lock);
```

Run `./learn run xv6 --at 07.02`. The boot stops after the hart lines, with
no `init: starting sh`, and Control-P shows the only process asleep (it has
no name yet):

<!-- verify: session run="./learn run xv6 --at 07.02" send=ctrl-p more
line 1 ~ 1 sleep(  init)?
-->
```
1 sleep  
```

The disk finished during the delay, its `wakeup` found the process still
`RUNNING`, and now nothing will ever wake it. Four boots out of four hung
like this, one of them a little later, in the first command. Without the
delay the bug is still there but rarely bites, and a hang that comes
rarely, with no message, is what makes it dangerous; that is why the order
is a rule and not a taste.

## Decide the boundary

xv6 sleeps on a bare address and wakes everything on it. `wakeup` scans all
64 slots and wakes every waiter, and each rechecks its own condition. That
is simple, and it works because the number of sleepers is small. Another
kernel could use a wait queue per object, as Linux does (`wait_queue_head_t`
and `wake_up`), or condition variables with `signal` for one waiter. That
avoids scanning and the thundering herd of a hundred processes woken
for one event, and pays for a queue to link and unlink on every wait.

Is the thing you are waiting on rare enough that a scan is cheap, or does
one event wake so many waiters that you must name the one you want?
