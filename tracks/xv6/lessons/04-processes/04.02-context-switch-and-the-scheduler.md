# 04.02 Context switch and the scheduler

A hart has to move between processes, stopping one wherever it is and
carrying on with another; this lesson covers the context switch that does
the moving and the scheduler loop that picks where to move to.

## Where this fits

![Where 04.02 fits](figures/04.02-map.svg)

The context switch sits just above the process table: it takes a process
out of its slot and runs it on a hart, and later puts it back. Below it
are the harts and the kernel stacks from the last lesson. Above it,
everything that stops a running process will use it: waiting for an
event, being interrupted by the timer, exiting. After this lesson
processes can share the harts and take turns on them, as soon as there are
processes to run.

## The idea

![`swtch` stores fourteen registers into `*old`, loads fourteen from `*new`, and `ret` follows the new `ra`.](figures/04.02-swtch-registers.svg)

**The need.** Three harts and a shell, `init`, and every command you type:
there are more processes than harts. Without a way to set one process
aside and pick up another, a hart that starts running `sh` would belong to
`sh` until it exits, and `echo hi | wc` could never have both halves alive.

**The idea.** Everything a hart is doing at a given moment is in its
registers: where it is in the code, which stack it is on, the values it is
working with. So to set a process aside, save its registers; to pick
another one up, load the registers that one saved last time. The hart
carries on exactly where the other process left off, on that process's
stack, as if it had never stopped.

xv6 makes this an ordinary function call. A process that wants to give up
the hart calls a function that saves its registers and loads someone
else's; much later, some hart loads its registers back, and from the
process's point of view the call simply returns.

What gets switched between are **kernel threads**: a stack plus the
registers saved for it. Each process has one, its kernel stack and its
context from 04.01. Each hart has one more, its **scheduler**, which runs
on the hart's boot stack and so belongs to no process. A process always
switches to its hart's scheduler; the scheduler picks the next runnable
process and switches to that.

### `swtch`

The switch itself, in assembly, because C cannot name `sp` and `ra` as
variables. Everything else in this lesson calls it.
`kernel/swtch.S:swtch(old, new)` stores the current registers into `*old`
and loads `*new`, then returns, into whoever saved `*new`.

### `scheduler`

What a hart does when it is not running a process. Each hart enters it at
the end of boot and never leaves. `kernel/proc.c:scheduler` loops over the
process table, and for each `RUNNABLE` process it marks it `RUNNING` and
switches to it. When that process gives the hart back, the loop goes on to
the next. If a whole pass finds nothing to run, the hart waits for an
interrupt with `wfi` instead of spinning.

### `sched` and `yield`

The way back. `kernel/proc.c:sched` is the one door from a process into its
hart's scheduler: it checks that the process is in a fit state to be set
aside, then switches. Everything that stops running a process goes through
it: `yield` here, and later `sleep` (04.03) and `exit` (06.04).
`kernel/proc.c:yield` is the simplest caller: mark myself `RUNNABLE`, so
the scheduler will come back to me, and switch.

## How it works

### Writing `swtch`, step by step

1. **Save, load, return.** Store the caller's registers into `*old`
   (`a0`), each at its offset in `struct context`, 8 bytes apart; load the
   other thread's from `*new` (`a1`) at the same offsets; `ret`.
   ```
   swtch:
           sd ra, 0(a0)
           sd sp, 8(a0)
           sd s0, 16(a0)
           ...
           ld ra, 0(a1)
           ld sp, 8(a1)
           ld s0, 16(a1)
           ...
           ret
   ```
2. **Only fourteen registers:** `ra`, `sp` and `s0` to `s11`. Because
   `swtch` is called like any C function, the calling convention has done
   the rest: a callee may clobber `t0`-`t6` and `a0`-`a7`, so the caller
   has already saved whatever it needed from those on its own stack.
3. **The `ret` is the switch.** The program counter is not saved: `ret`
   jumps to the `ra` just loaded, right after the other thread's own call
   to `swtch`, or into `forkret` for a process that has never run.

### Writing `scheduler`, step by step

1. **Loop forever, running whatever is `RUNNABLE`.** A hart with nothing
   else to do never returns from here.
   ```
     for(;;){
       ...
       for(p = proc; p < &proc[NPROC]; p++) {
         acquire(&p->lock);
         if(p->state == RUNNABLE) {
           p->state = RUNNING;
           c->proc = p;
           swtch(&c->context, &p->context);
           c->proc = 0;
           ...
         }
         release(&p->lock);
   ```
   The `swtch` comes back only when the process gives the hart up through
   `sched`, having already changed its own state. `c->proc` is what
   `myproc()` reads, and setting it back to 0 is how the rest of the
   kernel can tell that this hart is in its scheduler, running no process
   (04.04 depends on that).
2. **Hold the slot's lock while looking,** and across the switch. It
   stops another hart's scheduler from picking the same process, and the
   process releases it once it is running, as `forkret` does.
3. **Let interrupts in for a moment** at the top of every pass. If every
   process is asleep waiting for a device, the device's interrupt has to
   be able to arrive, or nothing would ever wake up.
   ```
       intr_on();
       intr_off();
   ```
   They are off again for the scan and the `wfi`, and that loses nothing:
   `wfi` wakes on a pending interrupt even with interrupts off, and the
   next pass takes it. Were they on, an interrupt could wake a process the
   scan had already passed, and the hart would doze in `wfi` with work
   waiting.
4. **Idle cheaply.** If a whole pass found nothing, `wfi` stops the hart
   until the next interrupt instead of spinning on the table.

### Writing `sched`, step by step

1. **The switch itself,** from the process into the hart's scheduler,
   with `intena` carried across it.
   ```
     struct proc *p = myproc();
     ...
     intena = mycpu()->intena;
     swtch(&p->context, &mycpu()->context);
     mycpu()->intena = intena;
   ```
2. **Why `intena` rides along.** The kernel remembers, per hart, whether
   interrupts were on before the first lock was taken. That value belongs
   to the hart, and the process may come back on a different one, so it
   travels in a local variable on the process's own stack.
3. **Check the four rules first,** and panic if one is broken: holding
   `p->lock`, holding nothing else, state already changed from `RUNNING`,
   interrupts off. A process that left still marked `RUNNING` would be
   lost: the scheduler only picks `RUNNABLE` ones. A second lock carried
   across the switch would stay held while other threads ran, and the next
   one to want it would spin forever.

### Why it is built this way

**Switching through the scheduler, not process to process.** A process
could hand the hart straight to the next one, saving a switch. xv6 always
goes through the hart's scheduler, two switches per hand-off, because it
keeps the locking simple: there is one place that chooses, and every
process gives up the hart the same way. The scheduler needs a stack that
belongs to no process for this, so that a process can end and give up its
own stack while the scheduler carries on; the boot stack each hart already
has is that stack.

**The process lock crosses the switch.** The scheduler takes the chosen
process's lock and then switches to it; the process releases that lock
once it is running. Going the other way, the process takes its own lock,
changes its state and switches; the scheduler releases the lock on the
other side. For the whole time a process's state and saved registers are
in flux, its lock is held, so no other hart's scheduler can pick it up half
saved. That is the **invariant**: a process is never `RUNNING` on two
harts, and its context is never loaded before it has been completely
saved.

Every run gives the same address. `ret` jumps to whatever `ra` held, which
is the scheduler's own return address, so the hart carries on in the
scheduler right after its call to `swtch`, but with A's `sp` and
`s0`-`s11`. Look the `sepc` up in `build/at/xv6/04.02/build/kernel/kernel.asm`:
it is the very next line, `c->proc = 0`, which the compiler wrote as a
store 48 bytes past the address in `s4`. That `s4` now comes from A's
context, which `allocproc` zeroed, so the store goes to 0 + 48 = 0x30, the
`stval` (`scause` 0xf is a store page fault). A context is a consistent
set: `sp`, `ra` and the `s` registers must all come from the same thread.

## Decide the boundary

xv6 has one policy: scan the table in order and run the first `RUNNABLE`
process, round-robin, with every hart locking and scanning the same table.
It does not know about priorities, and an idle hart wakes on every
interrupt to scan 64 slots. Another kernel could keep per-hart run queues,
as Linux does, and balance them. That scales to many cores and allows
priorities, and it pays in complexity: queues to lock, migration rules, and
a policy to tune.

Switching through a per-hart scheduler thread costs two `swtch` calls per
switch where a direct hand-off would cost one. xv6 takes the extra call for
a simple lock story. Does the kernel have enough harts and processes that a
linear scan and a shared table are the bottleneck, or is the rule
"anything RUNNABLE goes" good enough?
