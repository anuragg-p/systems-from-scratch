# 04.01 The process table and kernel stacks

A process is one slot in a fixed table, with a kernel stack of its own,
and this lesson covers how a slot is made ready to run and how it is given
back.

## Where this fits

![Where 04.01 fits](figures/04.01-map.svg)

Processes sit between the programs above and the machine below.
Everything above them - the shell, the programs it starts, the system
calls those programs make - runs as some process. Below, a process uses
what the earlier modules built: pages of memory, page tables, and traps
into the kernel. This lesson is the foundation of the module, the table
where every process lives. After it the kernel knows how to make a
process ready to run and how to tear one down, though nothing runs one
until the next lesson, and the first one is made only once there is a
program for it to run (07.02).

## The idea

![The states a slot moves through, and the function that makes each move.](figures/04.01-states.svg)

**Where this module goes.** The kernel can boot on three harts, hand out
pages, build page tables and take traps (modules 01 to 03). What it cannot
do is run more than one thing. Module 04 adds processes in four steps: a
table of process slots (this lesson), moving a hart from one process to
another (04.02), letting a process wait without holding a hart (04.03),
and letting the timer take a hart back from a process that never lets go
(04.04). Module 05 then gives processes a disk and files, and module 06
gives them a user half: programs of their own.

**The need.** Picture `echo hi | wc`. Two programs run at once, and either
one may be stopped in the middle of a system call while the other runs.
Each needs its own record: who it is, what state it is in, what memory it
has. Each also needs its own kernel stack, because a process stopped
halfway through kernel code leaves its call frames on that stack, and they
must still be there when it resumes.

**The idea.** xv6 keeps a fixed table of 64 slots. A process is one slot.
Making a process means finding a free slot and filling it in; ending one
means emptying it. Every slot is given its kernel stack once, at boot, at
a fixed address high in the kernel's address space.

The interesting part of "filling in" is that a new process must look as
if it had already run and stopped. The switch in 04.02 knows only how to
resume: it loads a few saved registers, the process's **context** (`ra`,
`sp` and the twelve `s` registers), and returns to wherever `ra` points.
So a fresh slot gets a context that, when resumed, starts it in `forkret`
at the top of its own kernel stack. For now `forkret` only lets go of the
slot's lock, which the scheduler (04.02) takes before switching in; lesson
06.01 makes it carry the process out to user space.

A slot has room for more than this lesson fills in: the channel it sleeps
on (04.03), its parent, exit status and kill flag (06.04), its open files
and current directory (module 05). Two globals wait for later too:
`wait_lock`, for `wait` and `exit` (06.04), and `initproc`, the first
process (07.02).

### `allocproc`

Every new process will start here: `fork` (06.04) makes them, and
`userinit` (07.02) makes the very first one at boot; nothing calls it yet.
`kernel/proc.c:allocproc` finds an `UNUSED` slot and makes it ready to
run: a pid, a trapframe page, an empty page table and a starting context.
It hands the slot back locked, so the caller can finish filling it in
before anyone else looks at it.

### `proc_pagetable`

A process needs a user page table before it has any user memory, because
the trap path (06.01), which crosses between user space and the kernel,
needs pages at the very top of it before the process ever runs.
`kernel/proc.c:proc_pagetable` builds that table, with the process's
**trapframe**, the page where 06.01 saves its user registers on every
trap, at the top, invisible to user code. Lesson 06.01 adds the second
page, the trampoline, above it.

### `freeproc`

The other end. When a parent's `wait` collects a child that has exited,
or when `allocproc` fails halfway, the slot must go back to `UNUSED` and
give up what it owned. `kernel/proc.c:freeproc` frees the trapframe and
the page table and clears the slot.

## Run it

`./learn run xv6 --at 04.01` boots as before, and Control-P now prints the
process table: an empty line, since no slot is in use. To fill some, add
this at the end of `build/at/xv6/04.01/kernel/proc.c`. It makes three
processes, gives the middle one back, and makes a fourth:

<!-- verify: patch file=kernel/proc.c append
@block
-->
```
void
tryslots(void)
{
  struct proc *p;

  for(int i = 0; i < 3; i++){
    p = allocproc();
    p->name[0] = 'a' + i;
    release(&p->lock);
  }
  p = &proc[1];
  acquire(&p->lock);
  freeproc(p);
  release(&p->lock);
  p = allocproc();
  p->name[0] = 'd';
  release(&p->lock);
}
```

In `kernel/main.c`, declare it above `main` with `void tryslots(void);`
and call `tryslots();` right after `procinit();`. Boot and press
Control-P:

<!-- verify: patch file=kernel/main.c
 volatile static int started = 0;
+void tryslots(void);
-->
<!-- verify: patch file=kernel/main.c
     procinit();      // process table
+    tryslots();
-->
<!-- verify: session run="./learn run xv6 --at 04.01" send=ctrl-p -->
```
1 used a
4 used d
3 used c
```

`d` went into the slot `b` gave back, the first free one, but got a new
pid: the counter never goes back, so a pid names one process for good, and
a parent asking after an old child can never get a newcomer in its slot.
All four are `USED`: built, never run, because nothing can run a process
until 04.02. Keep `tryslots` for Break it.

The kernel stacks show up in the monitor: `info mem` lists the kernel's
mappings, and the last lines are the stacks of slots 3 down to 0:

## How it works

### Writing `allocproc`, step by step

1. **Find a free slot and claim it.** Walk the table, taking each slot's
   lock before looking at it, and keep the lock on the first `UNUSED`
   one. Without the lock, two harts creating processes at the same moment
   could both claim slot 5. If all 64 are taken, return 0, and the `fork`
   that asked fails with -1.
   ```
     for(p = proc; p < &proc[NPROC]; p++) {
       acquire(&p->lock);
       if(p->state == UNUSED) {
         goto found;
       ...
     }
     return 0;

   found:
     p->pid = allocpid();
     p->state = USED;
     ...
     return p;
   ```
   The state is `USED`, not `RUNNABLE`: nothing in the slot is ready yet,
   and the scheduler only looks for `RUNNABLE`.
2. **Give it a trapframe page and a page table.** Either allocation can
   fail; then `freeproc` undoes the claim and the lock is released, so a
   failed `fork` leaves no half-used slot behind.
   ```
     if((p->trapframe = (struct trapframe *)kalloc()) == 0){
       freeproc(p);
       release(&p->lock);
       return 0;
     }
   ```
3. **Forge the starting context.** Point `ra` at `forkret` and `sp` one
   past the top of the slot's kernel stack page (a stack grows down), so
   the first switch into it "returns" into `forkret` on its own stack.
   There is no separate "start a process" path anywhere; every process,
   new or old, is entered by resuming a context.
   ```
     p->context.ra = (uint64)forkret;
     p->context.sp = p->kstack + PGSIZE;
   ```
4. **Return it locked,** because the caller still has to copy memory or
   set a parent before anyone else may look at it.

### Writing `proc_pagetable`, step by step

1. **An empty table with the trapframe in it,** mapped at `TRAPFRAME`
   without the user bit, so the trap code can use it and user code cannot
   see it.
   ```
     pagetable = uvmcreate();
     if(pagetable == 0)
       return 0;

     if(mappages(pagetable, TRAPFRAME, PGSIZE,
                 (uint64)(p->trapframe), PTE_R | PTE_W) < 0){
       ...
     }
   ```
2. **Undo if the mapping fails.** `mappages` may need a page for a lower
   level of the table and not get one; then the table is freed again with
   `uvmfree`, so `allocproc` fails without leaking it. (Lesson 06.01 adds
   the trampoline mapping before this one.)

The helpers it uses arrive in `vm.c` with this lesson: `uvmcreate` makes an
empty table, `uvmunmap` removes mappings, and `uvmfree` frees a table and
the memory under it. Module 06 uses them in earnest.

### Writing `freeproc`, step by step

1. **Free what the slot owns, then mark it free.** Free only what exists
   and zero each pointer as it goes; set `UNUSED` last. That way the same
   function cleans up a process that ran for an hour and a slot whose
   second allocation just failed, and calling it twice does no harm.
   ```
     if(p->trapframe)
       kfree((void*)p->trapframe);
     p->trapframe = 0;
     if(p->pagetable)
       proc_freepagetable(p->pagetable, p->sz);
     p->pagetable = 0;
     ...
     p->state = UNUSED;
   ```
2. **Forget the old process:** zero the pid, parent, name and the rest, so
   nothing stale reaches the next process to get this slot. The page table
   goes through `proc_freepagetable`, which unmaps the trapframe without
   freeing it twice, then frees the user memory and the table itself.

### An overflow faults instead of corrupting a neighbour

The kernel stacks are laid out at boot by `proc_mapstacks`, which this
lesson adds to the kernel's table in `kvmmake` (02.04), one page each, two
pages apart:

```
#define KSTACK(p) (TRAMPOLINE - ((p)+1)* 2*PGSIZE)
```

The page between two stacks, the gap `info mem` showed, is never mapped: a
**guard page**. A process that overflows its 4096 bytes runs into it and
faults on the spot. Without
it, the overflow would quietly overwrite the next process's stack, and the
crash would come later, in someone else's code. That is why the stacks get
addresses of their own up here: through the direct map, pages from
`kalloc` sit side by side with no gap to fault in.

![One stack page per slot, with an unmapped page below each, so an overflow faults instead of overwriting a neighbour.](figures/04.01-kernel-stacks.svg)

One more small thing: `myproc` turns interrupts off while it reads the
hart's current process. From 04.04 a timer interrupt can move a process to
another hart, and one landing between "which hart am I" and "what runs on
it" would answer for the wrong hart.

The **invariant**: a slot's state and the fields behind it change only
while `p->lock` is held, and an `UNUSED` slot owns nothing.

## Break it

Keep `tryslots`, and in `freeproc` delete the last line,
`p->state = UNUSED;`. Boot and press Control-P:

<!-- verify: patch file=kernel/proc.c
   p->xstate = 0;
-  p->state = UNUSED;
-->
<!-- verify: session run="./learn run xv6 --at 04.01" send=ctrl-p -->
```
1 used a
0 used
3 used c
4 used d
```

`b`'s pages were freed and its pid and name cleared, but its slot was never
given back. It stays `USED` with nothing in it, `allocproc` passes over it,
and `d` lands one slot further on. Every process that ended this way would
cost a slot for good; after 64, `allocproc` would find nothing and every
`fork` would fail.

The forged context matters only once a process first runs, which happens
in the 07.02 build. In `build/at/xv6/07.02/kernel/proc.c`, delete `p->context.sp = p->kstack + PGSIZE;` from `allocproc` and run
`./learn run xv6 --at 07.02`. The boot prints the hart lines and stops:
no panic, no `init: starting sh`. In the monitor, `info registers -a`
finds one hart in `kernelvec`, at its first store, `sd ra, 0(sp)`
(trimmed):

<!-- verify: patch at=07.02 file=kernel/proc.c
-  p->context.sp = p->kstack + PGSIZE;
-->
<!-- verify: session run="./learn run xv6 --at 07.02" send="ctrl-a c" type="info registers -a" trimmed
line 1 ~ CPU#[012]
vary fffffffe6c6e5dd0 hex
-->
```
CPU#1
 pc       0000000080001e92
 scause   000000000000000f
 x0/zero  0000000000000000 x1/ra    0000000080002ea2 x2/sp    fffffffe6c6e5dd0 x3/gp    0000000000000000
```

The first switch into process 1 loaded `sp` = 0, left there by the
`memset` in `allocproc`. `forkret`'s first push went below 0, to the top
of the address space, which is not mapped. The fault arrived on that same
`sp` (03.01: a trap in the kernel keeps its stack), so `kernelvec`'s own
push faulted too, and again, each time 256 bytes lower. No trap gets far
enough to print anything.

## Decide the boundary

xv6 keeps a fixed array of 64 processes with one page of kernel stack each.
That is simple: no allocator, no failure path beyond "table full", and a
process is found by pointer arithmetic. Another kernel could allocate a
process structure and a larger kernel stack on demand, as Linux does with
its 16 KiB (x86-64) task stacks plus a separate slab-allocated `task_struct`.
The cost is an allocator in the hottest path and a failure case at every
`fork`.

The fixed stack is the sharper limit. Four KiB means kernel code cannot use
deep recursion or big local arrays, and the guard page only reports an
overflow; it does not grow the stack. Does the kernel need more than 64
processes or deeper call chains, or is a hard ceiling that panics
predictably better than a table that can grow without bound?
