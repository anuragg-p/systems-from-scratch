# 00.02 Running and debugging the kernel

This lesson is the loop the rest of the course runs on: change the kernel,
boot it, read what it says, and when it dies, find the line that killed it.

## Where this fits

![Where 00.02 fits](figures/00.02-map.svg)

This lesson is still about the bottom row of the map: the machine, and how
to watch the kernel on it. Nothing in the kernel is built here. Every later
lesson ends by booting the kernel this way, and every failure in them is
chased down this way. After this lesson a crash is a line number, not a
mystery.

## The idea

![The loop: edit, build and boot with `make qemu`, read the console, quit with Control-a x. When the kernel dies, `sepc` in the panic names the instruction, and `kernel.asm` names its source line.](figures/00.02-run-loop.svg)

A kernel has nobody underneath to catch it. There is no debugger inside it,
no core dump and no stack trace. When it dies, the most it can do is print
three numbers and a word, as in the figure. `scause` says what kind of trap
stopped it: 0xf is a store to an address with nothing mapped there, 0xd the
same for a load. `sepc` is the address of the instruction that did it, and
`stval` the address it tried to touch. `kerneltrap` is the kernel's handler
for a trap taken inside the kernel itself (lesson 03.01), which panics
because there is nothing better to do.

That is enough, because the tools that matter live outside the kernel. QEMU
can see the whole machine, even when the kernel cannot see itself. And the
kernel file on the host still carries every line number the compiler knew.

So the loop has two halves. The everyday half: edit, `make qemu`, read the
console, Control-a x to quit. The half for when it dies: take the address in
the panic, look it up in `build/kernel/kernel.asm`, and read the source line
printed right above it. And when the machine goes silent instead of
panicking, ask QEMU where each hart is.

## Run it

Every lesson's Run it starts from one command, given from the repository
root:

```
./learn run xv6 --at 01.01
```

It writes the project as it stands at that lesson into
`build/at/xv6/01.01/`, builds it, and boots it in QEMU with the same options
as `make qemu`. Those files are yours to read and change: the next run
builds your edits, and `--fresh` writes the originals back.
`./learn files xv6 --at 01.01 <dir>` writes the same files to a folder of
your choice and builds nothing.

There is no kernel at this lesson yet, and the tools are best seen on one
that runs programs, so the rest of this lesson uses the 07.03 build, the
first with the shell and `kill`: `./learn run xv6 --at 07.03`. Paths below
are inside its folder, `build/at/xv6/07.03/`. The boot ends at the shell:

## How it works

### The console belongs to QEMU first

`make qemu` passes `-nographic`, which puts the machine's serial port on
your terminal. QEMU keeps Control-a for itself: Control-a x quits, Control-a
c toggles the monitor, Control-a h lists the rest. Everything else goes to
the kernel.

`./learn run xv6` adds one thing: it attaches the disk with `snapshot=on`,
so files you create in the shell vanish when QEMU exits and every run starts
from the same disk. `make qemu` writes to `build/fs.img` for real.

### Control-P is the kernel's, not the shell's

Control-P never reaches the shell. The kernel's keyboard interrupt handler
(lesson 03.03) spots it and prints the process table itself (lesson 04.01).
That is the point of putting it there: it still works when the shell is
stuck, or when a process is wedged inside the kernel.

### A panic has the last word

When the kernel panics, it prints its message even if another hart holds
the printing lock, then stops every other hart from printing, and spins
forever. Without that, three harts' output would interleave and the one
message that matters could scroll away. It is why a panic is always the
last thing on the screen.

### Line numbers stay on the host

The kernel carries no symbol table; it would cost memory and code. The
Makefile builds with `-ggdb`, so the ELF file on the host keeps the line
numbers instead, and three tools read them: `kernel.asm` puts each source
line above its instructions, `addr2line -e build/kernel/kernel ADDRESS`
prints a file and line directly, and `kernel.sym` maps a name to its address
when you need to go the other way.

### gdb, when reading is not enough

`make qemu-gdb` starts QEMU frozen before the first instruction, with a
debug server on port 26000. In a second terminal, from the same folder, run
a RISC-V gdb (`riscv64-elf-gdb`, `riscv64-unknown-elf-gdb` or `gdb-multiarch`):

<!-- verify: skip reason="needs a RISC-V gdb (riscv64-elf-gdb or gdb-multiarch), which is not one of the track's tools and is not installed where lessons are verified; and the block shows only the commands typed, nothing gdb prints back" -->
```
(gdb) file build/kernel/kernel
(gdb) target remote localhost:26000
(gdb) break _entry
(gdb) continue
```

You are then at 0x80000000. `stepi` runs one instruction, `info registers`
shows the registers and `x/8i $pc` disassembles; the three harts appear as
threads (`info threads`, `thread 2`).

## Break it

Plant a bug and find it. `sys_kill` in
`build/at/xv6/07.03/kernel/sysproc.c` is the kernel's side of the `kill`
command (lesson 06.04): it fetches the pid the program passed and kills
that process. Make it load the pid from address 0x10 instead:

<!-- verify: patch file=kernel/sysproc.c at=07.03
-  argint(0, &pid);
-  return kkill(pid);
@block
-->
```
  argint(0, &pid);
  pid = *(volatile int *)0x10;
  return kkill(pid);
```

(`volatile` makes the compiler emit the load exactly as written.) Before you
run it and type `kill 5`, say what the three numbers will be. The kernel
runs with paging on, and nothing is mapped at 0x10.

<!-- verify: session run="./learn run xv6 --at 07.03" panics=kerneltrap -->
```
$ kill 5
scause=0xd sepc=0x800050bc stval=0x10
panic: kerneltrap
```

A load page fault, at 0x10. Search `build/kernel/kernel.asm` for `sepc`:

<!-- verify: file path=build/kernel/kernel.asm at=07.03 -->
```
  pid = *(volatile int *)0x10;
    800050bc:	01002503          	lw	a0,16(zero) # 10 <_entry-0x7ffffff0>
```

<!-- verify: fact at=07.03 cmd="grep -B1 '^ *800050bc:' build/kernel/kernel.asm | grep -A1 -F 'pid = *(volatile int *)0x10;' | awk 'NR==2 {print $3}'" expect=lw -->
The source line comes right above the instruction: a `lw` from address 16.
The same lookup without the listing:

<!-- verify: session cwd=project at=07.03
line 1 typed
line 2 ~ .+/kernel/sysproc\.c:82
-->
```
riscv64-elf-addr2line -e build/kernel/kernel 0x800050bc
.../kernel/sysproc.c:82
```

Three numbers on the console were enough to name the line. Take the load
out again.

## Decide the boundary

xv6 gives you a printf, a panic and a disassembly, and no debugger inside
the kernel. Another kernel could carry a symbolic stack trace in its panic
handler, or a built-in debugger like Linux's kdb, and pay for it in kernel
code and a symbol table kept in memory. Here the debugger is outside: QEMU
and gdb see everything for free.

The question that decides it: how much of the kernel's own memory do you
want spent on helping you find its bugs?
