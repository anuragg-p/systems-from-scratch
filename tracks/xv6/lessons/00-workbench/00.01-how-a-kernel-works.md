# 00.01 How a kernel works

A kernel stands between every program and the machine. This lesson follows
one `ls` through the whole kernel before any part of it is built, then turns
to the tools and the machine underneath it: what turns C into a kernel
image, and where that image has to sit for the machine to run it.

The kernel is xv6, the small Unix that MIT wrote to teach its
operating-systems course, in its version for RISC-V. The code in these
lessons is xv6's, arranged to be put together one piece at a time (the
network and the screen of modules 08 and 09 are this course's own), so what
you learn is a kernel that is really taught and studied, and you can open
[the upstream code](https://github.com/mit-pdos/xv6-riscv) beside any
lesson and compare.

## Where this fits

![Where 00.01 fits](figures/00.01-map.svg)

Everything in this course runs on a RISC-V computer that QEMU pretends to
be, the bottom row of the map. This lesson is about that machine and about
the tools that turn C into something it can start. Every row above it is
the kernel, and none of it exists yet. After this lesson you know what the
build has to get right before there is anything to build; the first file it
builds arrives in the next module.

## The idea

![One `ls`: the request goes down from the program to the disk, the answer comes back up, and then the names go out to the console.](figures/00.01-ls-trip.svg)

### The whole kernel, in one `ls`

The fastest way to see what a kernel is made of is to follow one command
through it. Type `ls` at the shell and press Enter.

The shell is an ordinary program. It reads your line, starts another
program, `ls`, and waits for it to finish. Both run in **user space**: they
cannot touch the disk, the screen or each other's memory.

`ls` wants the names in the current directory, so it asks the kernel. A
**system call** is that question. The program runs one special instruction,
and the hardware **traps**: it stops the program and jumps into the kernel,
which runs the request on the program's behalf and returns.

The **file system** turns "the directory `.`" into a list of numbered disk
blocks. It keeps recently used blocks in memory, and it writes changes
through a log, so a crash can never leave the disk half-changed.

The **disk driver** hands the request for those blocks to the disk. The disk
is slow, so the driver puts the process to sleep, and the **scheduler** gives
the **hart** (a hardware thread: one of the machine's processors; this
machine has three) to someone else in the meantime.

When the disk is done it raises an **interrupt**. That pulls a hart into the
kernel, the driver wakes the sleeping request, and the answer climbs back up:
blocks into directory entries, entries copied out to `ls`.

Then `ls` prints the names. That is one more system call, which goes down to
the **console driver** and out of the serial port to your terminal.

Three layers sit under all of this. **Memory** gives every process its own
address space and the kernel its pages. **Locks** let three harts share the
kernel's structures without corrupting them. And **boot** gets the machine
from power-on to a kernel that can do any of it.

### The order we build in

We build from the bottom up, because each layer can only be run and looked
at with the ones beneath it.

Boot comes first: nothing runs without it. Then printing, because a kernel
that cannot say what it is doing cannot be debugged. Then memory and locks,
because every later piece asks for pages and shares them between harts.
Then traps, so the hardware can interrupt the kernel and a fault in it is
reported instead of silent. Then processes, so more than one thing can run.
Then the disk and the file system, because programs live in files. Then
system calls and user space, where programs ask the kernel for all of the
above. Last come the shell and its utilities, and with them the `ls` above.
The network and the screen are optional extensions on the finished core.

### Before the first instruction

All of that is still to come. This lesson stops at the bottom row, because
three things are decided before the kernel runs a single instruction.

A normal C program leans on an operating system it never sees: a C library,
a loader that puts it somewhere in memory, start-up code that calls `main`.
A kernel has none of that. Nobody loads it but QEMU, nobody calls `main`,
and there is no `printf` to link against.

So the build has to answer three questions the usual defaults get wrong.
Which compiler? The host is usually not RISC-V, so it needs a cross compiler.
Where in memory? QEMU's `virt` board has RAM at 0x80000000 and jumps there,
so the kernel must be linked to run at exactly that address. Which byte
first? Whatever sits at 0x80000000 runs first, so the entry code must be
the image's first byte.

`tracks/xv6/Makefile` answers the first and third. `kernel/kernel.ld`, the
linker script, answers the second; it comes with lesson 01.01, beside the
first instruction it puts in place.

### Where the files go

The Makefile sits at the top of the project, and everything else hangs off
it. The kernel's own sources go in `kernel/`, starting with
`kernel/entry.S` in 01.01. Everything `make` produces goes in `build/`:
object files, the kernel, its listings. `build/` is output only, and
`make clean` deletes it, so never put a file of your own there.

## How it works

### Three rules

<!-- verify: mention names="kernel.ld" at=01.01 -->

The Makefile is three rules and the flags they share. Compile each
`kernel/*.c` and `kernel/*.S` into `build/kernel/*.o`. Link the objects into
`build/kernel/kernel` with `kernel.ld`, `entry.o` first. Then disassemble the
result into `kernel.asm`, every instruction under its source line, and
`kernel.sym`, a plain "address name" list: the two files lesson 00.02 uses
to turn a crash address into a line.

### The compiler flags

Two flags carry a real decision.

`-mcmodel=medany` is there because of where the kernel lives. The default
model, `medlow`, builds addresses as absolute numbers that reach only 2 GB
either side of zero, and 0x80000000 is just past that. `medany` builds them
relative to the program counter instead, so compiled C works anywhere.

![`medlow` reaches 2 GB either side of address 0, and the kernel starts just past that; `medany` reaches 2 GB either side of the pc.](figures/00.01-mcmodel-reach.svg)

<!-- verify: mention names='printf("x\n") kernel/string.c' at=02.02 -->

`-ffreestanding`, `-nostdlib` and `-fno-builtin` tell the compiler there is
no C library. The last one matters most: without it, gcc may quietly turn a
copy loop into a call to `memcpy`, or `printf("x\n")` into `puts`, and the
link fails or calls something that does not exist. The kernel supplies its
own `memset` and friends in `kernel/string.c`.

The rest are hooks for later. `-ggdb` keeps line numbers in the kernel file,
for `kernel.asm` and the debugger; `-fno-omit-frame-pointer` keeps a chain
of stack frames a backtrace can follow. `-MD` has gcc write a `.d` file of
the headers each object includes, and the `-include` line reads them, so
changing a header rebuilds every file that uses it. `-Wall -Werror` turns
every warning into a stopped build.

### The linker script

`kernel.ld` (01.01) starts the image at 0x80000000, and because `entry.o` is
linked first, `.text` starts with `_entry`. The figure shows the finished
kernel laid out that way.

![The kernel image as the finished `kernel.ld` lays it out: `_entry` at the first byte, the trampoline (06.01) on a page of its own, and `end` after `.bss`.](figures/00.01-kernel-image.svg)

### The machine

The Makefile boots QEMU with `-machine virt -bios none -m 128M -smp 3`.
`virt` is a board QEMU invents for exactly this: RAM at 0x80000000 and a
handful of devices at fixed addresses (lesson 02.01). `-smp 3` gives it
three harts, so the kernel has to cope with several processors at once from
its first instruction (01.01, 02.03); one would hide those problems.
`-bios none` is the decision: no firmware runs first. A tiny boot ROM at
0x1000 jumps straight to 0x80000000 on every hart, in machine mode, the
most privileged mode (01.02). With `-d in_asm`, QEMU logs it:

<!-- verify: setup at=finished cwd=project
$ qemu-system-riscv64 -machine virt -bios none -kernel build/kernel/kernel -m 128M -smp 3 -nographic -global virtio-mmio.force-legacy=false -drive file=build/fs.img,if=none,format=raw,id=x0,snapshot=on -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0 -d in_asm -D in_asm.log
keys ctrl-a x
-->
<!-- verify: file path=in_asm.log at=finished -->
```
----------------
IN:
0x00001000:  00000297          auipc                   t0,0                    # 0x1000
0x00001004:  02828613          addi                    a2,t0,40
0x00001008:  f1402573          csrrs                   a0,mhartid,zero
...
----------------
IN:
0x0000100c:  0202b583          ld                      a1,32(t0)
0x00001010:  0182b283          ld                      t0,24(t0)
0x00001014:  00028067          jr                      t0
...
----------------
IN:
0x80000000:  0014a117          auipc                   sp,330                  # 0x8014a000
...
```

The ROM puts the hart id in `a0`, loads the address to jump to, and jumps.
All three harts do this at once, so all three arrive at `_entry` together.
Lesson 01.01 starts there.

## Break it

This lesson has no kernel of its own to break, so move the first one that
prints, the 01.03 build: `./learn run xv6 --at 01.03` shows its banner. In
`build/at/xv6/01.03/kernel/kernel.ld`, change `. = 0x80000000;` to
`. = 0x80100000;` and run it again. What happens?

<!-- verify: patch file=kernel/kernel.ld at=01.03
-  . = 0x80000000;
+  . = 0x80100000;
-->
<!-- verify: fact at=01.03 cmd="riscv64-elf-readelf -h build/kernel/kernel | awk '/Entry point/ {print $4}'" expect=0x80100000 -->

The console stays silent: no banner at all. QEMU loaded the image at the
new address, but the boot ROM still jumps to 0x80000000, where there is
nothing. Run QEMU with `-d in_asm` and the log shows the boot ROM's
`jr t0` and then "0x80000000: illegal". `readelf -h` shows the ELF entry
point is 0x80100000, but the boot ROM does not use it. The linker script
and the machine must agree on one number. Put the line back.

<!-- verify: revert file=kernel/kernel.ld at=01.03 -->

## Decide the boundary

xv6 runs with `-bios none`: the kernel is the first and only software, and
it does the machine-mode setup itself (lesson 01.02). Another system could
boot through firmware - OpenSBI is what Linux on RISC-V uses - and start the
kernel already in supervisor mode, where kernels normally run, with a
**device tree**, a description of the hardware, passed in. That is more
portable and much less code in the kernel, and you pay for it with a
dependency you did not write and cannot read in the same tree.

This course is "from scratch", so the first instruction is ours. Which
parts of the boot would you rather not own?
