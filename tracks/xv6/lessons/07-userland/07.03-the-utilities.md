# 07.03 The utilities

The utilities are the small programs typed at the shell, `cat`, `ls`, `wc` and the
rest, each a few system calls wrapped around one shared agreement about input and
output.

## Where this fits

![Where 07.03 fits](figures/07.03-map.svg)

The shell can start any program on the disk, but a shell with nothing to run is not
much use. The utilities are those programs. They sit on the user library and reach
the file system through ordinary system calls; above them is the person at the
shell, who joins them together with pipes and redirection. None of them knows about
the others: they cooperate only because each reads and writes the same way. After
this lesson the system has the everyday tools to show files, list directories and
count what is in them.

## The idea

Every utility keeps one promise: it reads from descriptor 0, or from the files it
is named, and writes its results to descriptor 1. Errors go to descriptor 2, so a
redirection never swallows them. That is all the shell needs (07.02). It can point
descriptor 0 at a file or at a pipe, and the program cannot tell the difference.

Here is the promise at work. `cat README | grep xv6 | wc` runs three programs that
have never heard of each other: `cat` copies the file, `grep` keeps the one line
that mentions xv6, and `wc` counts it, `1 3 17`. Each program is small, and the
combinations are endless.

### cat

`cat` is the simplest filter there is: copy everything from one descriptor to
descriptor 1. Given file names, it copies each file in turn; given none, it copies
descriptor 0, which is what lets it stand at the end of a pipe or show what was
typed.

### ls

`ls` is how a person sees what a directory holds. It can be an ordinary program
because a directory is an ordinary file (05.06): an array of 16-byte entries, each
an inode number and a name of up to 14 characters. `ls` opens the directory, reads
it one entry at a time, and asks `stat` about each name to print its type, inode
and size. There is no "list this directory" system call, and none is needed.

![`ls` with no arguments: it reads `.` one 16-byte entry at a time, skips empty slots, and `stat`s each name to print its line.](figures/07.03-ls-loop.svg)

### wc

`wc` counts lines, words and bytes, and is the usual last stage of a pipe: the
question "how many?" asked of whatever came before. A word is a run of bytes that
are not spaces, tabs or newlines.

### `grep.c`

`grep` prints the lines that match a pattern. Its matcher is Rob Pike's, small
enough to read in a minute: `.` for any character, `^` and `$` for the start and
end of the line, and `*` for any number of the character before it.

### `mkdir.c`

`mkdir` calls `mkdir` on each name it is given and stops at the first one that
fails, as `rm` does.

### `rm.c`

`rm` calls `unlink` on each name. It removes a name, not necessarily the file:
after `ln f g; rm f`, `cat g` still works, since a file lives until its last name
is gone.

### `ln.c`

`ln old new` is one `link`: a second name for the same inode.

### `kill.c`

`kill` calls `kill` on each process number. The victim does not stop at once: the
kernel only marks it, and it exits the next time it passes through `usertrap`
(06.01), at the latest on the next timer tick.

## Run it

`./learn run xv6 --at 07.03` boots to the shell, and the disk now holds the
utilities:

```
$ wc README
11 87 480 README
$ mkdir d
$ ls d
.              1 16 32
..             1 1 1024
$ echo hi | wc
1 1 3 
$ cat README | grep xv6 | wc
1 3 17 
```

In `ls`, the type is 1 for a directory, 2 for a file, 3 for a device
(`kernel/stat.h`); the next number is the inode, which depends on what was created
before, and the last is the size in bytes. Run `ls` with no arguments to see every
program on the disk.

## How it works

### Writing `ls`, step by step

1. **Open the path, ask what it is, print one line.** For a file or a
   device that is all `ls` does:
   ```
   if((fd = open(path, O_RDONLY)) < 0){
   ...
   if(fstat(fd, &st) < 0){
   ...
   switch(st.type){
   case T_DEVICE:
   case T_FILE:
     printf("%s %d %d %d\n", fmtname(path), st.type, st.ino, (int) st.size);
     break;
   ...
   close(fd);
   ```
   If `open` or `fstat` fails, `ls` says so and returns, so that `ls a b c`
   still lists the names that exist.
2. **A directory is read like a file,** one `struct dirent` at a time until
   a read comes back short, skipping slots whose inode number is 0:
   ```
   while(read(fd, &de, sizeof(de)) == sizeof(de)){
     if(de.inum == 0)
       continue;
   ```
3. **Build each entry's full path.** The directory's path and a slash go
   into a buffer once, after checking that a name will still fit; each name
   then goes in after the slash.
   ```
   strcpy(buf, path);
   p = buf+strlen(buf);
   *p++ = '/';
   ```
4. **Ask about each entry, not the directory.** `stat`, the library's
   open-and-`fstat` by name (07.01), on the full path gives the entry's own
   type, inode and size, which is the line `ls` prints.
5. **Pad the names.** `fmtname` pads each name to 14 characters so the
   columns line up.

### Writing `wc`, step by step

1. **Read in chunks, counting bytes and newlines:**
   ```
   l = w = c = 0;
   while((n = read(fd, buf, sizeof(buf))) > 0){
     for(i=0; i<n; i++){
       c++;
       if(buf[i] == '\n')
         l++;
       ...
     }
   }
   printf("%d %d %d %s\n", l, w, c, name);
   ```
2. **Count a word where it starts.** A word is counted at its first byte: a
   byte that is not whitespace, arriving when the previous one was.
   ```
   if(strchr(" \r\t\n\v", buf[i]))
     inword = 0;
   else if(!inword){
     w++;
     inword = 1;
   }
   ```
3. **Keep the flag across reads.** `inword` is set to 0 once, before the
   reading loop. If it were reset for each chunk, a word split by a read,
   `hel` in one chunk and `lo` in the next, would count twice.
4. **Report a failed read.** A negative count from `read` after the loop is
   an error, not an end of file.

### Writing `grep` in `grep.c`, step by step

1. **Read a chunk, cut it into lines, print the ones that match.** Each
   newline is turned into a 0 so the line is a string for `match`, and put
   back before the line is written:
   ```
   while((n = read(fd, buf+m, sizeof(buf)-m-1)) > 0){
     m += n;
     buf[m] = '\0';
     p = buf;
     while((q = strchr(p, '\n')) != 0){
       *q = 0;
       if(match(pattern, p)){
         *q = '\n';
         write(1, p, q+1 - p);
       }
       p = q+1;
     }
   ```
2. **Keep the unfinished line.** A read can end in the middle of a line.
   The tail after the last newline moves to the front of the buffer, and
   the next read appends to it, which is what `buf+m` is for:
   ```
   if(m > 0){
     m -= p - buf;
     memmove(buf, p, m);
   }
   ```
   A line longer than the 1024-byte buffer never finds its newline: the
   buffer stays full, the next read asks for 0 bytes, and `grep` stops
   there.
3. **The matcher works one pattern character at a time.** `match` tries
   the pattern at every position of the line, or only at the start for
   `^`. `matchhere` takes one character of the pattern against one of the
   text and calls itself on the rest. `matchstar` is a loop that first
   tries the rest of the pattern right where it stands, which is zero
   copies of `c`; only if that fails, and the next character is a `c`,
   does it step past it and try again:
   ```
   do{  // a * matches zero or more instances
     if(matchhere(re, text))
       return 1;
   }while(*text!='\0' && (*text++==c || c=='.'));
   ```

### Why it is built this way

**cat treats a short write as an error.** `write` may take fewer bytes than it
was given, say when the disk fills up. `cat` stops with `cat: write error` rather
than pretend the copy worked, so a full disk is reported, not silently truncated.

**ls skips empty entries.** A directory's file only grows. When a file is removed,
its entry is not taken out; its inode number is set to 0 and the slot stays, ready
for the next name. An inode number of 0 is how the disk says "no file here".

**ls makes each name a string.** A name that uses all 14 characters has no zero
byte after it on the disk. `ls` copies the name into its own buffer, after the
directory's path and a slash, and puts the zero there itself before calling
`stat`.

```
$ ls
.              1 1 1024
..             1 1 1024
README         2 2 480
...
console        3 15 0
               1 1 1024
               1 1 1024
               1 1 1024
...
```

After the 16 real entries come 48 lines with no name. The root directory's file is
a whole 1024-byte block (`mkfs` rounds it up), 64 slots of 16 bytes, and only 16 of
them hold a name; the rest have inode number 0 and a name of all zero bytes. Without
the check, `ls` builds the path `./` plus an empty name, and `stat("./")` describes
the root directory itself: type 1, inode 1, size 1024.

## Decide the boundary

xv6 keeps `ls`, `cat` and `wc` as separate tiny programs and the shell just runs
them. Another system could put them in the shell (busybox's ash does, to save the
`fork` and `exec`) or in one multi-call binary, trading a smaller disk image and
faster startup for a shell that is no longer small and a build that no longer has
one file per command. A third could make `ls` ask the kernel for a list of names
instead of parsing raw directory blocks, which hides the on-disk format from user
code at the cost of a new system call per kind of query. Which of those belongs to
the system, and which to programs?
