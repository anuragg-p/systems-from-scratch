# 07.01 The user library

The user library is the small C library every xv6 program links: it is how a C
program reaches the kernel, and it holds the one piece of user code that needs
real thought, the memory allocator.

## Where this fits

![Where 07.01 fits](figures/07.01-map.svg)

The kernel is complete: it can load a program from the disk, run it, and answer
its system calls. But it speaks only in system calls, and a C program wants more
than that: formatted output, strings, and memory in any size, freed in any order.
The user library sits just above the system-call line, linked into every program,
and turns the kernel's few calls into what a C programmer expects. Below it is the
kernel; above it is every program in this module. After this lesson a C program can
be built for xv6 and placed on its disk, which is what the shell and the utilities
need.

## The idea

This module crosses to the other side of the system-call line, to everything a
person at the console sees. This lesson is the library. 07.02 adds `init` and a
shell, the first programs to run, and 07.03 the utilities typed at that shell:
`cat`, `ls`, `wc` and the rest. By the end of the module the system boots to a
prompt and is usable.

The gap the library fills is easy to see. The kernel offers `write(1, buf, n)`; a
program wants `printf("%d files\n", n)`. The kernel offers `sbrk`, which can only
move the top of the heap; a program wants `malloc(100)` now, `malloc(30)` next,
and to free the first while it keeps the second.

Most of the library is thin. A program starts in `_main`, which calls `main` and
hands its return value to `exit`, so a `main` that simply returns still ends
cleanly. A system call from C is three generated instructions: put the call's
number in a register, trap, return. `printf` turns a format into characters and
writes them. The string functions are what they always are. One piece needs real
thought, and it is the allocator.

### malloc

Every program that builds something whose size it cannot know in advance calls
`malloc`: the shell, for instance, for each piece of each command it parses
(07.02). It turns the heap that `sbrk` grows (06.05) into blocks of any size, and
`free` takes them back.

This has to live in the program, not the kernel. `sbrk` can grow the heap, but it
cannot leave a hole in the middle of it. If a program allocates 100 bytes, then
30, then frees the 100, those 100 bytes are free, and only the program knows it.
So the library keeps track of the holes and hands them out again.

The idea, from Kernighan and Ritchie's book on C, is a **free list**. Every block
of the heap starts with a small header that says how big the block is. The free
blocks are chained into a ring, in address order. To allocate, walk the ring and
take the first block that is big enough; if it is bigger than needed, cut off the
part you need from its end. To free, put the block back in its place in the ring,
and if it touches its neighbours, glue them into one bigger block. When nothing on
the ring is big enough, ask the kernel for a large piece and add it to the ring.

Here is `malloc(100)` on a fresh heap. Memory is counted in units of 16 bytes, the
size of a header (a pointer and a size; the header is a union with a `long`, K&R's
way of making every header, and so every block after it, aligned for any value a
program stores). 100 bytes is 7 units, plus 1 for the header: 8 units, 128
bytes. The ring is empty, so the library asks `sbrk` for 64 KiB, 4096 units, and
puts that on the ring as one free block. It cuts 8 units off the end, writes a
header there, and returns the address just after it.

![`malloc(100)` on a fresh heap: 8 units are cut from the tail of the block `morecore` added, so the header the free list holds stays where it was.](figures/07.01-free-list.svg)

`free`, and `morecore`, which asks the kernel for more, sit beside `malloc` in
the same file.

### `echo.c`

The first program the build puts on the disk, and the simplest one: it writes its
arguments with `write`, a space between them and a newline after the last. It
needs nothing from the library but the system call wrappers and `strlen`.

## How it works

### Writing `malloc`, step by step

1. **Walk the ring and take the first block that fits.** Count the request
   in 16-byte header units, plus one unit for the block's own header; take
   a block of exactly that size off the ring and return the byte after its
   header:
   ```
   nunits = (nbytes + sizeof(Header) - 1)/sizeof(Header) + 1;
   ...
   for(p = prevp->s.ptr; ; prevp = p, p = p->s.ptr){
     if(p->s.size >= nunits){
       if(p->s.size == nunits)
         prevp->s.ptr = p->s.ptr;
       ...
       freep = prevp;
       return (void*)(p + 1);
     }
   ```
   The `+ 1` is the unit for the block's own header. `freep = prevp`
   starts the next search where this one stopped, so allocations spread
   around the ring.
2. **Make a ring on the very first call.** There is nothing to walk yet,
   so the first call makes `base`, a header of size 0 that points at
   itself. Size 0 never fits, so `base` is never handed out, but every walk
   has a place to start and stop.
   ```
   if((prevp = freep) == 0){
     base.s.ptr = freep = prevp = &base;
     base.s.size = 0;
   }
   ```
3. **Cut a bigger block from its end,** and give the part cut off a
   header of its own:
   ```
   p->s.size -= nunits;
   p += p->s.size;
   p->s.size = nunits;
   ```
4. **Grow the heap when the walk comes back round.** Arriving at `freep`
   again means nothing fits. `morecore` asks `sbrk` for more, hands the new
   block to `free`, which links it into the ring, and returns the point to
   keep walking from. If the kernel has no memory left, `malloc` returns 0.

### Writing `free` in `umalloc.c`, step by step

`free` is the other half of the ring.

1. **Find the header and put the block back in address order.** The
   caller holds the address just after the header, so the header is one
   unit back; walk until the block lies between a free block and the next
   one, and link it in there:
   ```
   bp = (Header*)ap - 1;
   for(p = freep; !(bp > p && bp < p->s.ptr); p = p->s.ptr)
     if(p >= p->s.ptr && (bp > p || bp < p->s.ptr))
       break;
   ...
     bp->s.ptr = p->s.ptr;
   ...
     p->s.ptr = bp;
   freep = p;
   ```
2. **Mind the wrap.** The ring has one place where "between" cannot work,
   where it wraps from the highest address back to the lowest; there, a
   block above the highest or below the lowest belongs too. That is the
   second check in the loop.
3. **Merge with the free block after it.** If `bp` ends exactly where the
   next free block starts, swallow that block instead of pointing at it:
   ```
   if(bp + bp->s.size == p->s.ptr){
     bp->s.size += p->s.ptr->s.size;
     bp->s.ptr = p->s.ptr->s.ptr;
   ```
4. **Merge with the free block before it,** the same way: if it ends
   exactly where `bp` starts, it swallows `bp`.

### Writing `vprintf` in `printf.c`, step by step

`printf` and `fprintf` both come down to `vprintf` in `user/printf.c`. Its
`va_list` comes from `<stdarg.h>`, a header the compiler supplies itself, so it
works with no C library underneath. Each character goes out through `putc`, one
`write` per byte: a trap for every character, and two programs printing at once
interleave theirs. xv6 accepts both for code this short.

1. **Copy characters until a `%`, then let the next one choose.** Two
   states are enough: ordinary text, and just after a `%`:
   ```
   for(i = 0; fmt[i]; i++){
     c0 = fmt[i] & 0xff;
     if(state == 0){
       if(c0 == '%'){
         state = '%';
       } else {
         putc(fd, c0);
       }
     } else if(state == '%'){
       if(c0 == 'd'){
         printint(fd, va_arg(ap, int), 10, 1);
       ...
       state = 0;
   ```
2. **One routine for every number.** `printint` takes the base and whether
   the value is signed, so `%d`, `%u` and `%x` share it. Division yields
   the lowest digit first, so the digits go into a buffer and are printed
   backwards:
   ```
   do{
     buf[i++] = digits[x % base];
   }while((x /= base) != 0);
   ```
3. **Two-letter conversions look one ahead.** `%ld` checks the next
   character and skips it. The point of the `l` is the `va_arg` type: a
   64-bit argument read as `int` would lose its upper half.
   ```
   } else if(c0 == 'l' && c1 == 'd'){
     printint(fd, va_arg(ap, uint64), 10, 1);
     i += 1;
   ```
4. **Strings and mistakes.** `%s` of a null pointer prints `(null)` instead
   of faulting, and an unknown sequence is printed as it is, so a typo in a
   format shows in the output.

### Why it is built this way

**Hand out the tail.** When a free block is bigger than the request, `malloc`
gives away its end, not its start. The free block keeps its header where it was,
only smaller, so the ring that points at it is still right and nothing else on the
ring has to change. Giving away the front would mean writing a new header further
on and fixing the pointer in the block before it.

**Keep the ring in address order.** `free` could put a block anywhere on the ring,
and allocation would still work for a while. But then two free blocks that sit side
by side in memory could not find each other, and the heap would crumble into ever
smaller pieces until no large request fits. In address order, a block's neighbours
on the ring are its neighbours in memory, and `free` merges with both in two
comparisons. **Invariant:** the ring is sorted by address, circular, and `freep`
always points at a block on it.

**Ask for a lot at once.** `morecore` never asks the kernel for less than 64 KiB.
Each `sbrk` is a trap into the kernel and a change to the page table, so a program
that makes a thousand small allocations should pay for a few of those, not a
thousand. The memory never goes back: `sbrk` with a negative count could shrink the
heap, but this allocator never calls it.

**How a program gets onto the disk.** The library is linked into every program,
and the Makefile is what puts each program on the disk. Every `user/*.c` file that
is not a library is a program: it is linked with the library into `_name`, and
`mkfs` copies it into the root directory of `fs.img` without the underscore, where
`exec("echo", ...)` finds `/echo` by name. The underscore marks the linked program
among the files the build leaves beside it (`echo.o`, `echo.asm`) and gives the
Makefile one pattern for "a program". A new program is one new `.c` file, with no
list to edit. This lesson adds those rules, and `echo` is the first program they
put on the disk; `cat` and the rest follow in 07.03.

![The path for `echo`: `user/echo.c` is linked with the user library into `_echo`, `mkfs` stores it as `/echo`, and `exec` finds it by name in the root directory.](figures/07.01-to-disk.svg)

## Break it

No process runs until there is a shell, so this experiment uses the 07.02 build:
`./learn run xv6 --at 07.02`. In `build/at/xv6/07.02/user/umalloc.c`, drop the
`+ 1` from the first line of `malloc`:

<!-- verify: patch file=user/umalloc.c at=07.02
-  nunits = (nbytes + sizeof(Header) - 1)/sizeof(Header) + 1;
@block
-->
```
  nunits = (nbytes + sizeof(Header) - 1)/sizeof(Header);
```

Run it and type a command or two:

<!-- verify: session run="./learn run xv6 --at 07.02" -->
```
$ echo hi
usertrap(): unexpected scause 0xf pid=3
            sepc=0xc50 stval=0x15000
$ echo a b c
usertrap(): unexpected scause 0xf pid=4
            sepc=0xc50 stval=0x15000
$ 
```

Every command's child dies with a store page fault at 0x15000, the first byte past
the 64 KiB that `malloc` got from `sbrk`. Look up `sepc` in `build/user/sh.asm`:
0xc50 is inside `memset`. The child's first allocation is the 168-byte node for the
command. Without the `+ 1` it gets 11 units, header included, where it needed 12,
so only 160 bytes are left after the header, and the block was cut from the very
end of the heap. Zeroing the node runs 8 bytes past that end. In the middle of the
heap the same bug would not fault; it would quietly overwrite the next block's
header. The shell itself survives and prompts again, because only the child was
killed: the allocator is user code, and a bug in it hurts only the program that
links it.

## Decide the boundary

xv6 puts `malloc` in user space and gives the kernel only `sbrk`. Another system
could put the policy in the kernel, so that every `malloc` is a system call;
allocation would be uniform and checkable, but each small request would cost a
trap. Real C libraries split it the other way: glibc's allocator keeps its own bins
and arenas, takes memory from the kernel in large chunks with `brk` and `mmap`, and
gives pages back only rarely. Here, a program that frees a block never returns it
to the kernel: `sbrk` could shrink the heap, but this allocator never asks. What
belongs in the library, and what only the kernel can do?
