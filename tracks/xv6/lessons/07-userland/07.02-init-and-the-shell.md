# 07.02 init and the shell

The shell is the program that turns a typed line into running programs, and
`init`, the first process, is what keeps a shell on the console.

## Where this fits

![Where 07.02 fits](figures/07.02-map.svg)

After boot there is one process and a person at the console who wants to type
`cat README | wc` and see the answer. The kernel will run `cat` and `wc`, but only
when a program asks it to, and nothing in the kernel reads a line of text, starts
two programs, or joins the output of one to the input of the other. The shell does,
as an ordinary program built on the user library, using only process and file
system calls the kernel already has. Above it is the person at the keyboard. After
this lesson the system can be typed at.

## The idea

![One command: the shell forks, the child parses the line and becomes `echo` at `exec`, and the shell sleeps in `wait` until it exits.](figures/07.02-fork-exec-wait.svg)

The shell's trick is that it never runs a command itself. For each line it forks a
child, and the child becomes the command with `exec` while the shell waits.
Between the fork and the exec, the child is still running the shell's code, and
that is where redirection and pipes happen: the child rearranges its own
descriptors 0 and 1, then execs the program, which inherits them without knowing.

Take `echo hi > f`. The child closes descriptor 1 and opens `f`. `open` always
returns the lowest free descriptor, and 1 was just freed, so `f` becomes
descriptor 1. Then the child execs `echo`, which writes "hi" to descriptor 1 as it
always does, and the words land in `f`. `echo` never heard of `f`.

A pipe works the same way with two children: one whose descriptor 1 is the write
end of a pipe, one whose descriptor 0 is the read end. Each runs its program, and
neither knows the other exists.

To know which of these to do, the shell first parses the line into a small tree of
commands. `echo a | wc > f` becomes a pipe whose left side is `echo a` and whose
right side is a redirection to `f` wrapped around `wc`. Each node is a small struct
whose first field says which kind it is, so the code that runs the tree can read
any node's kind before it knows which struct it holds.

`init` comes before all of this. It opens the console as descriptors 0, 1 and 2,
which every process after it inherits, starts the shell, and starts another if the
shell ever exits.

With `init` on the disk, the kernel can at last make its first process, and this
lesson adds the code that does it: `userinit` in `kernel/proc.c`, which takes a
slot with `allocproc` (04.01), gives it the root as its current directory and
marks it runnable, and a call to it at the end of `main`. The process has no program yet.
Its first trip through `forkret` starts the file system and loads `/init` (06.03),
and from there everything else in this module runs.

### The main loop

This is the shell's `main`, the code a person is talking to. It prints a prompt,
reads a line and runs it in a child, then waits. The one line it handles itself is
`cd`, for a reason How it works explains. Two small helpers sit beside it: `fork1`
is `fork` that gives up on failure, and the shell's own `panic` prints a message
and exits the shell, nothing like the kernel's.

### `runcmd`: run a program, redirection, pipes

`runcmd` takes one node of the command tree and makes it happen, inside the child
the main loop forked. Running a program is an `exec`; a redirection rearranges a
descriptor and then runs the command inside it; a pipe forks the two sides with the
pipe's ends in place. Every path ends in `exec` or `exit`, so `runcmd` never
returns.

### `init.c`

The first program. Its opening lines are there because a fresh disk has no
console file: `open("console")` fails, so `init` makes it with `mknod`, a device
file whose major number, `CONSOLE`, sends reads and writes to the console driver
(06.07). That number is defined in a kernel header, which is why `init` includes
`kernel/file.h` and the headers it depends on. The console opens as descriptor 0,
and two `dup(0)` make 1 and 2.

## Run it

From this lesson on, the system boots to a prompt: `./learn run xv6 --at 07.02`.
The disk holds three programs, `init`, `sh` and `echo`, so `echo` and the shell
itself are all there is to run:

```

$ echo hello > f

$ echo echo hi | sh
$ hi
$ $ 
```

`echo hello > f` created `f` through the redirection, and the pipe ran both sides,
though the right one never reads; `cat` comes with 07.03. The last line pipes a
command into a second shell, an ordinary program reading descriptor 0: it prompted,
ran `echo hi`, prompted again, read end of file and exited, and then the first
shell prompted. Its prompts reach the screen because the shell writes them to
descriptor 2, which no redirection touched; `sh < script > out` keeps them out of
`out`.

## How it works

### Writing `main`, step by step

1. **Read a line, run it in a child, wait.** This is the whole shell, and
   everything else in `main` handles a case it gets wrong:
   ```
   while(getcmd(buf, sizeof(buf)) >= 0){
     char *cmd = buf;
     ...
       if(fork1() == 0)
         runcmd(parsecmd(cmd));
       wait(0);
     ...
   }
   exit(0);
   ```
2. **Stop at end of file.** `getcmd` returns -1 when it reads nothing at
   all, not even a newline: the input is gone. The loop ends, the shell
   exits, and `init` starts another.
3. **Skip blank lines,** so pressing Enter costs no fork.
4. **Run `cd` in the shell itself.** A line starting with `cd ` is caught
   before the fork. Its newline is cut off first, or `chdir` would look for
   a directory whose name ends in a newline.
5. **Make sure descriptors 0, 1 and 2 are open.** Before the loop the shell
   opens the console until it gets a descriptor of 3 or more. A shell
   started with one of them closed would let the next `open` land there,
   and a command would print into whatever file that was.

### Writing `runcmd`, step by step

1. **Switch on the node's type; run a program; end in `exit`.** Every node
   starts with `int type`, so `runcmd` reads it and casts to the right
   struct. The simplest node is a program, which is an `exec`:
   ```
   switch(cmd->type){
   ...
   case EXEC:
     ecmd = (struct execcmd*)cmd;
     if(ecmd->argv[0] == 0)
       exit(1);
     exec(ecmd->argv[0], ecmd->argv);
     fprintf(2, "exec %s failed\n", ecmd->argv[0]);
     break;
   ...
   }
   exit(0);
   ```
   If `exec` comes back at all, it failed. Nothing returns from `runcmd`.
2. **Redirect, then run what is inside.** Close the descriptor, open the
   file, and call `runcmd` on the inner node. It recurses because the inner
   node may be another redirection: `cat < in > out` is two of them around
   one program.
   ```
   close(rcmd->fd);
   if(open(rcmd->file, rcmd->mode) < 0){
   ...
   runcmd(rcmd->cmd);
   ```
3. **Run a list in order.** For `a ; b`, fork the left side and wait for
   it, then run the right side in this same process.
4. **Make the pipe and fork both sides.** In the first child, close
   descriptor 1 and `dup` the write end, which lands on 1, then close both
   original pipe descriptors; the second child does the same with 0 and
   the read end.
   ```
   if(fork1() == 0){
     close(1);
     dup(p[1]);
     close(p[0]);
     close(p[1]);
     runcmd(pcmd->left);
   }
   ```
5. **Close both ends in the parent and wait for both.** A reader sees end
   of file only once every copy of the write end is closed. Waiting for
   both means the pipeline is finished before the shell prints its next
   prompt.
6. **Run a background job.** Fork and do not wait. The process running
   `runcmd` exits at once, so the shell's own `wait` returns immediately,
   and the command carries on as an orphan that `init` will collect.

### Writing the parser in `sh.c`, step by step

The parser turns a line into the tree `runcmd` walks. Each kind of node has
a function that parses it, calling the one for the tighter-binding kind.

1. **A simple command, from tokens.** `gettoken` skips spaces and returns
   one token, a symbol or `'a'` for a word, with two pointers marking where
   the word starts and ends in the line; `peek` looks ahead without taking
   anything. `parseexec` collects words until it sees `|`, `)`, `&`, `;` or
   the end of the line:
   ```
   while(!peek(ps, es, "|)&;")){
     if((tok=gettoken(ps, es, &q, &eq)) == 0)
       break;
     ...
     cmd->argv[argc] = q;
     cmd->eargv[argc] = eq;
     argc++;
     ...
   }
   ```
   It records pointers into the line itself rather than copying the words.
2. **Redirections wrap the command.** `parseredirs` runs before and after
   each word, and wraps the node in a redirection node for each `<`, `>` or
   `>>` it finds.
3. **Pipes call themselves.** `parsepipe` parses one command, and if `|`
   follows, builds a pipe whose right side is the rest of the pipeline:
   `a | b | c` is `a | (b | c)`.
   ```
   cmd = parseexec(ps, es);
   if(peek(ps, es, "|")){
     gettoken(ps, es, 0, 0);
     cmd = pipecmd(cmd, parsepipe(ps, es));
   }
   ```
4. **Lists, background jobs and parentheses** follow the same pattern.
   `parseline` wraps what came before in a background node for each `&`
   and builds a list for `;`; `parseblock` handles `( ... )` by calling
   `parseline` inside them, so a whole list can be piped or redirected.
5. **Terminate the words last.** `nulterminate` walks the finished tree
   and writes a 0 at every word's end. It cannot be done earlier: in
   `echo|wc`, the end of `echo` is the `|`, and writing a 0 there before
   the parser had read it would erase the pipe.

### Why it is built this way

**Fork first, then parse and run.** The main loop forks before it even parses the
line, and the child calls `runcmd`, which never comes back. That is deliberate: a
command ends either by becoming another program or by exiting, and the shell must
outlive both. Running the tree in a child it can afford to lose is what keeps the
shell alive.

**Redirection leans on "lowest free descriptor".** The redirection case is a
`close` followed by an `open`. There is no call that says "open this file as
descriptor 1"; the rule that `open` takes the lowest free slot (06.07) does that
job, provided nothing runs in between.

**Pipes close everything they do not use.** After `pipe` and two forks, three
processes hold both ends of the pipe. A reader sees end of file only when every
write end is closed (06.06), so each child closes both pipe descriptors once it has
copied the one it needs onto 0 or 1, and the parent closes both before it waits.

![`echo hi | wc` just before the children exec: each end of the pipe is open in exactly one process.](figures/07.02-pipe-fds.svg)

**cd is built in.** `chdir` changes the current directory of the process that
calls it. Run as a program, `cd` would change its own directory and exit, and the
shell would be where it was. So the main loop catches `cd` and calls `chdir`
itself: it is the one command that has to happen in the shell's own process.

**init never stops waiting.** Any process whose parent exits becomes a child of
`init` (06.04), so `init`'s `wait` loop also collects those orphans, not just the
shell. If `init` itself ever exited, nothing would be left to do that, and the
kernel panics rather than carry on.

## Break it

In `build/at/xv6/07.02/user/sh.c`, in the `PIPE` case, delete the parent's
`close(p[0]);` and `close(p[1]);`, the two lines just before the two `wait(0)`
calls. Run `./learn run xv6 --at 07.02` and pipe a command into a shell again:

<!-- verify: patch file=user/sh.c
-    close(p[0]);
-    close(p[1]);
     wait(0);
     wait(0);
-->
<!-- verify: session run="./learn run xv6 --at 07.02" hangs=2 -->
```
$ echo echo hi | sh
$ hi
$ 
```

The second shell ran `echo hi` and prompted, and then nothing: the first shell's
prompt never comes back, and typing does nothing. Press Control-P for the process
list:

<!-- verify: session send=ctrl-p -->
```
1 sleep  init
2 sleep  sh
3 sleep  sh
5 sleep  sh
```

`echo` (4) wrote its line and exited. Process 5, the second shell, read the line,
ran it and reads again. Process 3, the shell's child that ran the pipe, still holds
`p[1]`, so the pipe is empty but not at end of file, and 5 sleeps. Process 3 is
blocked in `wait` for 5, and 5 waits for 3 to close a descriptor: two processes
that each need the other. The shell itself, 2, waits behind them, and the `$ ` on
the screen is the second shell's prompt, which reads from the pipe, not from you.

## Decide the boundary

xv6 keeps the shell as an ordinary program that composes five system calls.
Another system could build job control into the kernel: a process-group call, a
terminal that knows which process owns it. Unix adds exactly that (setpgid,
tcsetpgrp, SIGINT to the foreground group), which is what gives you Control-C and
`fg`, and pays with signals, sessions and a controlling terminal. A different shell
could skip `fork`: Windows creates a process directly, with the redirections as
arguments. Where should the knowledge that "this command is in the foreground"
live - in a program, or in the kernel?
