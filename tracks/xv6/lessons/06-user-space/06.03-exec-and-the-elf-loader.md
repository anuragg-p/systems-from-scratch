# 06.03 exec and the ELF loader

This lesson covers `exec`, which replaces a process's memory with a
program read from a file and starts it running.

## Where this fits

![Where 06.03 fits](figures/06.03-map.svg)

Loading a program draws on almost everything built so far. It finds and
reads the program through the file system, builds a fresh address space
from pages and page tables, and leaves the process ready to drop into user
mode through the trap path. Above it, the shell runs every command by
making a copy of itself and having the copy load the command, and the
kernel uses it to start the very first program. After this lesson the
kernel can turn a program file into a process's memory; the first process
to use it arrives with 07.02.

## The idea

![The two LOAD headers of `_echo` become its first two pages; `kexec` then adds a guard page and a stack page above them.](figures/06.03-elf-load.svg)

**The need.** A program on the disk is a file of bytes. To run it, its code
and data must sit at the addresses it was linked for, with the right
permissions: code executable, data writable. It needs a stack, and on that
stack its arguments, so that `main(argc, argv)` finds them. And if
anything goes wrong halfway, say a corrupt file or no memory left, the
process that asked must carry on as before, with `exec` returning -1.

**The idea.** The file says what to load where. A program here is an
**ELF** file, and its header lists **program headers**, each one saying
"take these bytes of the file and put them at this address, this big,
with these permissions". In the header's own names: `filesz` bytes from
offset `off` in the file go to address `vaddr`, in a region `memsz` bytes
long, with the permissions in `flags`. Take `echo`, one of the first
programs 07.01 puts on the disk (the build calls the file `_echo`; the
underscore is dropped on the disk). It has two headers that matter: its
code, at address 0, readable and executable; and its data, on the next
page, writable.

So `exec` builds a complete new address space off to the side: a new page
table, memory for each segment with the bytes copied in from the file,
then a stack page, a guard page below it that the program may not touch,
and the argument strings pushed onto the stack. The process keeps running
on its old memory the whole time. Only when every step has worked does
`exec` swap in the new page table and free the old one. The process
returns from the system call into the new program, at its entry point.

### `kexec`

The kernel half of the `exec` system call. `sys_exec` copies the path and
arguments in from user space and calls it. `forkret` (04.01) calls it too,
once, for the very first process: this lesson has it start the file
system with `fsinit` (05.03), which must run inside a process because it
sleeps on the disk, and then load `/init`. Both `/init` and that first
process come with 07.02. `kexec` returns the argument count, or -1 with
the caller untouched.

## Run it

Nothing runs in user space yet: there is no process to call `exec` until
07.02, and no program on the disk until 07.01, so
`./learn run xv6 --at 06.03` boots to the hart lines and waits. One ELF
file is here already, though: the kernel itself. In `build/at/xv6/06.03/`,
the cross toolchain's `readelf` shows its program headers, the same kind
`kexec` reads:

Only `LOAD` headers are loaded. This one says: copy 0x67d0 bytes from
offset 0x1000 of the file to 0x80000000, in a region 0x1fb40 bytes long;
the part past the file's bytes is the kernel's zeroed variables. Its flags
are `RWE`, everything at once, because the kernel's linker script packs
code and data together (the kernel sets its own page permissions in
`kvmmake`, 02.04). A user program must not look like this, which is why
it gets a linker script of its own, below.

## How it works

### Writing `kexec`, step by step

1. **A new page table, the segments copied in, then switch.** For a
   well-formed file with nothing going wrong, `kexec` is a loop over the
   program headers and a swap at the end:
   ```
     if((pagetable = proc_pagetable(p)) == 0)
       goto bad;
     for(i=0, off=elf.phoff; i<elf.phnum; i++, off+=sizeof(ph)){
       ...
       if((sz1 = uvmalloc(pagetable, sz, ph.vaddr + ph.memsz, flags2perm(ph.flags))) == 0)
         goto bad;
       sz = sz1;
       if(loadseg(pagetable, ph.vaddr, ip, ph.off, ph.filesz) < 0)
         goto bad;
     }
     ...
     p->pagetable = pagetable;
   ```
2. **Open the file and check it is ELF** first, with the inode locked while
   it is read, all inside a log operation. That is because the path lookup
   puts back the inodes it passes, and putting back the last hold on a
   deleted file frees its blocks: a disk write, which must belong to a
   transaction (05.04).
3. **Distrust every program header.** The file is just bytes anyone could
   have written, so a segment whose memory size is smaller than its file
   size, whose end overflows, or whose start is not page aligned fails the
   whole `exec`.
4. **Add the stack, with a guard page under it:** two more pages, and the
   user bit taken off the lower one.
   ```
     if((sz1 = uvmalloc(pagetable, sz, sz + (USERSTACK+1)*PGSIZE, PTE_W)) == 0)
       goto bad;
     sz = sz1;
     uvmclear(pagetable, sz-(USERSTACK+1)*PGSIZE);
   ```
5. **Push the arguments,** strings first, then the array of pointers to
   them, failing if they do not fit in the stack page; the array's address
   goes in `a1`.
6. **Undo on any failure.** Every `goto bad` lands on one piece of code
   that frees the new page table and the inode, and returns -1 to a caller
   whose old memory was never touched. It frees only what exists:
   `pagetable` starts at 0, and `ip` is set to 0 once the file is put
   back, so a failure before either is built leaves it alone.

### Writing `sys_exec`, step by step

1. **Copy the path and every argument into the kernel, then call `kexec`.**
   ```
     if(argstr(0, path, MAXPATH) < 0) {
     ...
     for(i=0;; i++){
       ...
       if(fetchaddr(uargv+sizeof(uint64)*i, (uint64*)&uarg) < 0){
       ...
       argv[i] = kalloc();
       ...
       if(fetchstr(uarg, argv[i], PGSIZE) < 0)
         goto bad;
     }
     int ret = kexec(path, argv);
   ```
   The copies are needed because the strings live in the old address
   space, which `kexec` frees. Each gets a whole page because a page is
   the only size the kernel's allocator hands out, and it gives the string
   a limit, `PGSIZE`, for free.
2. **Find the end of the list.** The program's `argv` is an array of
   pointers ending in 0, fetched one pointer at a time with `fetchaddr`
   (06.02); more than `MAXARG` fails.
3. **Free the pages on both ways out,** after `kexec` and at `bad`. The
   array is zeroed at the start, so both loops stop at the first slot never
   filled:
   ```
     memset(argv, 0, sizeof(argv));
   ```

### Why it is built this way

**Commit at the very end.** Until the last few lines, everything `kexec`
builds lives in a page table the process is not using. Then:

```
  oldpagetable = p->pagetable;
  p->pagetable = pagetable;
  p->sz = sz;
  p->trapframe->epc = elf.entry;  // initial program counter = the ELF entry point
  p->trapframe->sp = sp; // initial stack pointer
  proc_freepagetable(oldpagetable, oldsz);
```

That is the **invariant**: until this point the old address space is
untouched, so any failure can still return -1. `elf.entry` is where the
program starts; for our programs that is `_main` in the user library
(07.01), which calls `main` and passes its result to `exit`.

**Filling the pages.** `uvmalloc` grows the new address space a page at a
time with zeroed pages, always readable and user-accessible, plus the
execute or write permission `flags2perm` turned the ELF flags into.
`loadseg` then copies the file's bytes in. It cannot write through the new
page table, which is not installed, so for each page it asks `walkaddr`
for the physical address and has `readi` write straight there: the kernel
reaches all of physical memory at the same addresses (02.04).

**Segments start on page boundaries.** Permissions belong to whole pages,
so code and data cannot share one. The linker script `user/user.ld` starts
the data on a fresh page, so a program gets two `LOAD` headers, one `R E`
and one `RW`, instead of the kernel's single `RWE`; and `kexec` rejects a
segment whose address is not page aligned. A segment's memory size can be
larger than its file size; the difference, the **bss**, needs no copying,
because every new page is already zeroed.

**A guard page under the stack.** The upper of the two stack pages is the
stack, which grows down. The lower one stays mapped but without the user
bit, so a program that recurses too deep runs off the bottom of its stack
and faults at once, instead of writing over its own data.

**The arguments are laid out like a C call.** The strings go at the top of
the stack, each start rounded down to a multiple of 16 as the RISC-V
calling convention requires, then an array of pointers to them ending in
0. `sp` and `a1` point at that array, so it is `argv`; `kexec`'s return
value becomes the system call's result in `a0`, so it is `argc`.

![The top of the stack page after `exec` of `echo a bb ccc`: the strings, then the `argv` array, with `sp` and `a1` both at 0x3F90.](figures/06.03-argv-stack.svg)

## Break it

No process runs until 07.02, so this experiment uses the 07.02 build,
where `forkret` loads `/init` as the first process; `init` is the one
process the kernel never lets exit. In
`build/at/xv6/07.02/kernel/exec.c`, load every segment with no extra
permissions: change `flags2perm(ph.flags)` in the `uvmalloc` call to `0`,
and run `./learn run xv6 --at 07.02`:

```
xv6 kernel is booting

hart 2 starting
hart 1 starting
usertrap(): unexpected scause 0xc pid=1
            sepc=0xf8 stval=0xf8
panic: init exiting
```

`exec` succeeded and `/init` was loaded. But `uvmalloc` gave its text
pages only the read and user bits, not execute, so the first instruction
fetch at 0xf8 raises an instruction page fault (`scause` 0xc). `usertrap`
kills the process, and the kernel panics because `init` may not exit. The
ELF flags are a request for permissions; `kexec` is the code that makes
the page table say so.

## Decide the boundary

xv6 loads a statically linked ELF at fixed addresses, in whole, and starts it. It has
no dynamic linker, no randomisation, and no `PT_INTERP`. Linux's `execve` does all of
those: it maps the program lazily, loads a shared-library interpreter, and
randomises the stack and heap, so a program is smaller and harder to attack, and
the loader is thousands of lines. Windows has no `fork`; `CreateProcess` builds a
new process directly from an image, so a failed start never touches the caller, but
every setting the child needs must be a parameter.

Should starting a program be one step that builds a new process, or two, fork then
exec, with the child free to rearrange itself between them?
