# 06.04 fork, exit and wait

This lesson covers how processes are made and ended: `fork` copies the
caller into a new process, `exit` ends a process, and `wait` lets the
parent collect it.

## Where this fits

![Where 06.04 fits](figures/06.04-map.svg)

Fork, exit and wait sit on the process table from module 04 and hand
control of it to user programs. Above them, the shell starts every command
by forking and then waiting, and the first process uses them to keep a
shell running and to collect processes nobody else will. Below, fork uses
the process table, the page allocator to copy memory, and open files to
share descriptors; exit and wait use sleep and wakeup. After this lesson the
kernel has the calls a program needs to start another process and find out
when, and how, it ended; the first program to use them comes with 07.02.

## The idea

![`init` forks its first child: every page is copied, the trapframe too except `a0`, and descriptors 0 to 2 still point at the same `struct file`.](figures/06.04-fork-copy.svg)

**The need.** You type `echo hi`. The shell has to run `echo` and still be
there afterwards, waiting for the next command, and it must know when
`echo` has finished before it prints the prompt. Meanwhile the slot
`echo` used must not stay taken forever, or after 64 commands the table
would be full.

**The idea.** `fork` makes a new process that is an exact copy of the
caller: the same memory (copied, not shared), the same registers, the same
open files and current directory (shared). The two differ in one thing
only, what `fork` returns: 0 in the child, the child's pid in the parent.
That one difference is enough. The child sees 0 and calls `exec` to become
`echo`; the parent sees a pid and calls `wait`.

A process cannot free itself when it ends: it is still running on its own
kernel stack, under its own page table. So `exit` gives up everything it
can, its open files and its directory, records an exit status, and turns
into a **zombie**: a slot that holds nothing but a pid and a status. The
parent's `wait` finds the zombie child, takes its status, and frees the
slot. A process whose parent exits first is handed to `init`, which waits
for anything that comes its way.

### `kfork`

The kernel half of `fork()`; `sys_fork` just returns what it returns: the
child's pid, or -1 if there is no free slot or no memory left.

### `kexit` and `kwait`

Part of the same story. `kexit` has been in `kernel/proc.c` since 06.01,
because `usertrap` ends a killed process with it; this lesson puts the
`exit` system call in front of it. `kwait` comes with this lesson, behind
the `wait` system call: it frees a zombie child's slot and returns its pid,
and sleeps while the children are all still running.

### `sysproc.c` and `kkill`

`sysproc.c` is the thin layer behind the process system calls: each one
fetches its arguments and calls into `proc.c`. Next to `fork`, `exit` and
`wait`, this lesson adds the small calls a program needs around them.
`getpid` returns the caller's pid. `uptime` returns `ticks`, the count the
timer interrupt keeps (03.02). `sleep(n)` waits for `n` ticks: it sleeps
on `&ticks`, which the timer wakes on every tick, with `tickslock` as the
condition lock (04.03).

`kill(pid)`, through `kkill`, does not end the victim. It only sets the
victim's `killed` flag, and wakes it if it is asleep. `kill(0)` fails at
once: every unused slot in the table has pid 0, and a killed flag left on
one would kill the next process to take it. The victim may be
in the middle of a system call, holding locks or halfway through a file
update, and ending it there would leave all that behind. So it ends
itself with `kexit` the next time it passes through `usertrap` (06.01),
where it holds nothing. The wake-up matters because the kernel's waiting
loops, `sleep`'s and `kwait`'s among them, check the flag each time they
wake and give up.

## Run it

Nothing runs in user space yet, so nothing calls `fork`: the first
process, the one every other is forked from, comes with 07.02.
`./learn run xv6 --at 06.04` boots to the hart lines and waits. Press
Control-P, which lists the process table, and it prints only an empty
line: the table is empty.

## How it works

### Writing `kfork`, step by step

1. **A slot, a copy, a 0.** Take a slot with `allocproc` (04.01), copy the
   memory and the saved registers into it, make `fork` return 0 in the
   child, and let it run:
   ```
     if((np = allocproc()) == 0){
       return -1;
     }
     if(uvmcopy(p->pagetable, np->pagetable, p->sz) < 0){
     ...
     np->sz = p->sz;
     *(np->trapframe) = *(p->trapframe);
     np->trapframe->a0 = 0;
     ...
     np->state = RUNNABLE;
     ...
     return pid;
   ```
2. **Out of memory halfway:** if `uvmcopy` fails, give the slot back with
   `freeproc` and return -1.
3. **Share the open files and the current directory:** `filedup` each
   descriptor, `idup` the directory.
4. **Set the parent under `wait_lock`,** with the child's own lock dropped
   first, for the lock order explained below:
   ```
     acquire(&wait_lock);
     np->parent = p;
     release(&wait_lock);
   ```
5. **Runnable last,** under the child's lock, once everything is in place.

### Writing `kexit`, step by step

1. **Become a zombie and switch away for good.** The status is kept for
   the parent, and `sched()` never comes back here:
   ```
     acquire(&p->lock);

     p->xstate = status;
     p->state = ZOMBIE;
     ...
     sched();
     panic("zombie exit");
   ```
2. **Give back what can be given back first:** close every open file, and
   drop the current directory inside a log operation.
3. **Hand the children to `init` and wake the parent,** which may be
   asleep in `wait`, both under `wait_lock`:
   ```
     acquire(&wait_lock);
     reparent(p);
     wakeup(p->parent);
   ```
4. **Refuse to let `init` exit,** with a panic: orphans would have nobody
   left to collect them.

### Writing `kwait`, step by step

1. **Scan for a zombie child; sleep if there is none yet.**
   ```
     for(;;){
       for(pp = proc; pp < &proc[NPROC]; pp++){
         if(pp->parent == p){
           ...
           if(pp->state == ZOMBIE){
             ...
             freeproc(pp);
             ...
             return pid;
           ...
       sleep(p, &wait_lock);
     }
   ```
   It sleeps on its own address, which is what `kexit` wakes, with
   `wait_lock` as the condition lock (04.03). `kexit` takes `wait_lock`
   before its `wakeup`, so a child cannot exit between the scan and the
   sleep and leave its parent asleep for ever.
2. **Copy the status out** to the address the caller gave, if any, before
   the slot is freed.
3. **No children at all, or killed:** return -1 instead of sleeping for
   ever.

### Why it is built this way

**`fork` returns twice.** A system call's result travels back in the saved
`a0` of the trapframe (06.02). `kfork` copies the parent's whole
trapframe into the child, so the child's saved pc is the instruction after
the parent's `ecall` and every register matches. Then:

```
  // Cause fork to return 0 in the child.
  np->trapframe->a0 = 0;
```

When the child first runs, it leaves the kernel through `forkret` and
returns to user mode as if from the same `fork()` call, with 0. The
parent gets the pid, which `syscall` stores in its own `a0`.

**Copy memory, share files.** `uvmcopy` copies every page of the parent
into a fresh page and maps it with the parent's flags, so after `fork` a
write in one process is invisible to the other, while the child's code
stays executable and its guard page stays out of reach. Open files are
the opposite: the child gets new references to the same open files
(05.07), so the two share each file's offset. That is what lets a shell's
children write to the same output one after another. The current
directory is shared the same way: `idup` counts one more user of its
inode, which keeps it in the inode table while either process uses it.

**Not runnable until complete.** The child is created `USED`, which the
scheduler ignores, and becomes `RUNNABLE` only as the very last step.
Another hart that picked it up with a half-copied trapframe would run
garbage. The parent pointer is set under `wait_lock`, the lock that exit
and wait use to read it; the code drops the child's own lock first and
takes it again after, because the kernel's lock order is always
`wait_lock` before any process lock.

**Zombies and orphans.** `kexit` marks itself `ZOMBIE` and switches away
for the last time; only its parent's `wait` can free the slot. A parent
that never waits leaks one slot per child. If the parent exits first, its
children are given to `init`, whose loop of `wait` calls collects them.

![B exits with status 3: it stays a zombie until A's `wait` collects it, and its child C is handed to `init`.](figures/06.04-exit-wait.svg)

The **invariant**: every process except `init` has a living parent that
will eventually wait for it, so every slot that is used is eventually
freed.

## Break it

No process runs until 07.02, so this experiment uses the 07.02 build:
in `build/at/xv6/07.02/kernel/proc.c`, delete the line
`np->trapframe->a0 = 0;` from `kfork`, and run
`./learn run xv6 --at 07.02`. On that build the first process, `init`,
loops: it prints `init: starting sh` and forks; the child execs the
shell, and the parent waits, starts a new shell when that one exits, and
gives up with an error if `wait` fails. The shell never appears; the
console fills with:

<!-- verify: patch file=kernel/proc.c at=07.02
-  np->trapframe->a0 = 0;
-->
<!-- verify: session run="./learn run xv6 --at 07.02" more -->
```
...
init: starting sh
init: wait returned an error
init: starting sh
init: wait returned an error
```

and repeats forever. The child's `a0` is now a copy of the parent's, which
is not 0, so in `init` both processes believe they are the parent. The
child calls `wait`, has no children, gets -1, prints the error and exits.
The real parent collects it, sees the pid of the child it forked, and
starts another shell. Nothing is wrong with the kernel's copying; the only
difference between the two processes was that one zero.

## Decide the boundary

xv6 copies all of the parent's memory in `fork`, eagerly, even though the shell's
child will usually call `exec` a microsecond later and throw the copy away. Another
kernel could use **copy-on-write**: share the pages read-only, copy one only when
somebody writes it. Linux does this, and `fork` of a large process costs almost
nothing. The price is a page-fault handler that tracks per-page reference counts and
makes every write to a shared page a possible trap. Or it could drop `fork` and offer
a single "spawn this program" call, as Windows does, and pay with a clumsier way to
set up the child's descriptors (the shell in 07.02 does it with plain `close` and
`dup` between `fork` and `exec`). Which cost do you want: a trap handler that is
harder to get right, or a process-creation call that is harder to use?
