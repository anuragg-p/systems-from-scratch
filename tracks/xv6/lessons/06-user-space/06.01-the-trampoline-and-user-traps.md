# 06.01 The trampoline and user traps

This lesson covers the crossing between a user program and the kernel in
both directions: the small piece of assembly that runs on the way in and
out, and the C code that decides what a trap from user space was.

## Where this fits

![Where 06.01 fits](figures/06.01-map.svg)

The trap path from user space is the one door every program uses to reach
the kernel. Above it sit system calls, and through them everything a
program can ask for: files, processes, memory. Below, it builds on the
kernel's own trap handling from module 03, the page tables of module 02,
and the processes and scheduler of module 04. After this lesson the kernel
has the path a process takes to run in user mode, under its own page
table, and to come back on a system call, an interrupt or a fault. The
first process to take it arrives with 07.02.

## The idea

![`struct trapframe` at `TRAPFRAME`: the five values `uservec` needs to enter the kernel, then the 31 user registers, each at an offset the assembly hard-codes.](figures/06.01-trapframe.svg)

**Where this module goes.** Up to now everything has run inside the
kernel. Module 06 gives processes a user half. This lesson is the
crossing itself. Then come system calls, the numbered requests a program
makes through it (06.02); `exec`, which loads a program from a file into
a process (06.03); `fork`, `exit` and `wait`, which make and end processes
(06.04); a heap that grows on request (06.05); pipes between processes
(06.06); and the file system calls (06.07). Module 07 then supplies the
programs themselves: `init`, the shell and the utilities.

**The need.** A user program runs with its own page table, and the kernel
is not mapped in it at all: the program must not be able to read or
change kernel memory. When the program makes a system call, or the timer
fires, or it touches a bad address, the hardware switches to supervisor
mode and jumps to one fixed address. That is all it does. The program's
page table is still installed, and every register, including the stack
pointer, still holds the program's values. The kernel's code, stack and
data are not even visible.

**The idea.** Put one page of code, the **trampoline**, at the same address
at the very top of every user page table and of the kernel's page table.
Next to it, in each user page table, put a page of the process's own, the
**trapframe**, as a place to keep registers. It cannot be the kernel
stack: at the moment of the trap only what the user page table maps can
be touched, so the save area has to be a page of that table, mapped
without the user bit. On a trap the trampoline saves every user register
into the trapframe, loads the kernel's stack pointer and page table that
were left there for it, switches to the kernel page table and calls into
C. Because the trampoline sits at the same address in both tables, the
instruction after the switch is still there.

The way back is the same in reverse: switch to the user page table,
reload every user register from the trapframe, and return to user mode.
The trampoline is mapped without the user bit, so a program can neither
read it nor jump into it; the only way in is a trap.

### Putting the trampoline in place

This lesson gives the trampoline's code a page of its own in the linker
script (01.01), which refuses to link if the code outgrows it: nothing
above the last page of the address space could be mapped. That page, at
`TRAMPOLINE`, is mapped in the kernel's table and in every process's
table, with the trapframe just below it. And `forkret` (04.01), where a new process's
first switch lands, now goes on to user space through `prepare_return`
and `userret`. Whoever makes the process fills its trapframe first: a
forked child gets a copy of its parent's (06.04), and the very first
process gets its pc and stack pointer from `exec` (06.03).

### `uservec`

Where every trap from user space lands; the kernel points the trap vector
at it before returning to a program. `kernel/trampoline.S:uservec` saves
the 31 user registers into the trapframe, picks up the kernel's stack,
hart number, page table and handler address from it, switches page
tables, and jumps to `usertrap`.

### `usertrap`

The C side of the way in, running on the process's kernel stack.
`kernel/trap.c:usertrap` works out what the trap was: a system call; a
device or timer interrupt, which it hands to `devintr()`; or a fault,
which marks the process to be killed (`setkilled` sets a flag in the
process, `killed` reads it). For a system call it only gets ready here: the
call to `syscall()`, the dispatcher, is the one line lesson 06.02 adds.
A killed process is ended with `kexit`, which closes its files, hands its
children to the first process and leaves it a zombie for its parent to
collect; it comes into `kernel/proc.c` with this lesson because
`usertrap` is its first caller, and 06.04 shows how it works. On a timer
tick `usertrap` yields the hart, as `kerneltrap` does since 04.04.

### `prepare_return`

Every return to user space goes through it: at the end of `usertrap`, and
for a brand-new process, at the end of `forkret`.
`kernel/trap.c:prepare_return` points the trap vector back at `uservec`,
leaves in the trapframe what `uservec` will need next time, and sets the
privilege and pc registers so the next `sret` lands in user mode at the
right instruction.

### `userret`

The last step out. `kernel/trampoline.S:userret` switches to the user page
table, reloads every user register from the trapframe, and executes
`sret`.

## Run it

Nothing crosses this path yet: there is no process until 07.02. What you
can see is the page this lesson put in place. Boot this lesson's kernel
with `./learn run xv6 --at 06.01`; after the hart lines, press Control-a c
for the QEMU monitor and type `info mem`, which lists the mappings of the
page table the hart is using, the kernel's. The last line is the
trampoline:

## How it works

### Writing `uservec`, step by step

1. **The shape: free a register, save, switch, jump.** On arrival every
   register still holds a value of the program's, and storing anything
   needs an address in a register. So the first move is to park `a0` in
   `sscratch`, a spare supervisor register that user code can neither read
   nor write, and point `a0` at the trapframe, which is at the same
   address, `TRAPFRAME`, in every process's table. After that the path is
   straight: store the registers, load what the kernel left, install its
   page table, call into C.
   ```
   uservec:
           csrw sscratch, a0
           li a0, TRAPFRAME
           sd ra, 40(a0)
           ...
           ld t0, 16(a0)
           ld t1, 0(a0)
           sfence.vma zero, zero
           csrw satp, t1
           sfence.vma zero, zero
           jalr t0
   ```
2. **Save all 31, the parked `a0` last.** Each register goes to the offset
   `struct trapframe` fixes for it; the assembly and the struct must change
   together. `a0` comes back out of `sscratch` once `t0` is free to hold it:
   ```
           csrr t0, sscratch
           sd t0, 112(a0)
   ```
3. **Pick up the kernel's stack and hart number** before calling C.
   Without the stack pointer, `usertrap` would push its frame onto the
   program's stack; without `tp`, `cpuid()` would read the program's value.
   ```
           ld sp, 8(a0)
           ld tp, 32(a0)
   ```
4. **Fence on each side of the switch,** so that no stale translation from
   one table is used under the other.
5. **Jump through a register, not with `call`.** This code runs at
   `TRAMPOLINE`, not at the address it was linked at, so a pc-relative
   `call usertrap` would land in the wrong place; the real address comes
   from the trapframe instead. `jalr` returns, with the user page table in
   `a0`, to the next instruction, which is `userret`.

### Writing `usertrap`, step by step

1. **The easy case, a system call, and the way back.** A program makes a
   system call with the `ecall` instruction, which traps with `scause` 8
   and leaves `sepc` pointing at the `ecall` itself. Save the user pc,
   step past the `ecall`, and hand `userret` the user page table:
   ```
     struct proc *p = myproc();
     p->trapframe->epc = r_sepc();
     if(r_scause() == 8){
       ...
       p->trapframe->epc += 4;
       intr_on();
     } else if((which_dev = devintr()) != 0){
     ...
     prepare_return();
     uint64 satp = MAKE_SATP(p->pagetable);
     return satp;
   ```
2. **Send further traps to the kernel's handler,** first thing, after
   checking the trap really came from user mode. `stvec` still names
   `uservec`; a device interrupt taken in the kernel would land there and
   save kernel registers as if they were the program's.
   ```
     w_stvec((uint64)kernelvec);
   ```
3. **Anything that is neither a system call nor a device is a fault:** a
   bad address, an illegal instruction. The kernel cannot repair the
   program, so it prints the cause and marks the process killed.
4. **Exit if killed, yield if it was the timer.** Without the yield, a
   program looping without system calls would keep its hart for ever.

### Writing `prepare_return`, step by step

1. **What `sret` reads.** `sstatus` decides the mode and interrupt state
   after the jump, `sepc` where it lands:
   ```
     struct proc *p = myproc();
     ...
     unsigned long x = r_sstatus();
     x &= ~SSTATUS_SPP; // clear SPP to 0 for user mode
     x |= SSTATUS_SPIE; // enable interrupts in user mode
     w_sstatus(x);
     w_sepc(p->trapframe->epc);
   ```
2. **Point traps back at `uservec`,** at its address inside the
   trampoline page. The code is linked into the kernel image but runs from
   the trampoline's address:
   ```
     uint64 trampoline_uservec = TRAMPOLINE + (uservec - trampoline);
     w_stvec(trampoline_uservec);
   ```
3. **Interrupts off before that,** for the reason below.
4. **Leave the notes for the next entry** in the trapframe: the kernel page
   table, the top of this process's kernel stack, the address of
   `usertrap`, the hart number. `uservec` cannot look anything up, so they
   must be there before the trap comes. They are written on every return,
   not once, because the process may have moved to another hart while it
   was in the kernel.

### Writing `userret`, step by step

1. **`uservec` backwards.** Install the user page table passed in `a0`,
   reload every register from the trapframe, and `sret`:
   ```
   userret:
           sfence.vma zero, zero
           csrw satp, a0
           sfence.vma zero, zero
           li a0, TRAPFRAME
           ld ra, 40(a0)
           ...
           ld a0, 112(a0)
           sret
   ```
2. **`a0` last,** since it holds the trapframe's address until every other
   register is back.
3. **`sret` goes where the C side left `sstatus` and `sepc`:** user mode,
   interrupts on, at the saved pc.

### Why it is built this way

**Save the trap registers before anything can trap again.** The hardware
records the program's pc in `sepc` and the reason in `scause`, one copy
per hart. The first thing `usertrap` does with them is copy the pc into
the trapframe, and it turns interrupts on only after it is done with them,
because a timer interrupt or a switch to another process would overwrite
both. For a system call it also adds 4 to the saved pc, so the program
resumes after its `ecall` instead of running it again.

Why turn interrupts on during a system call at all? A call can run for a
long time, copying a large file, say. With interrupts off for all of it,
the hart would not hear its devices or the timer until the call ended:
keystrokes and disk completions would wait, and no other process could
have the hart (04.04).

**Interrupts off before the vector changes.** While the kernel runs, traps
must go to the kernel's handler; while a program runs, to `uservec`.
`prepare_return` changes the vector to `uservec` while still in the
kernel, so it turns interrupts off first:

```
  intr_off();
```

An interrupt between the change and the `sret` would enter `uservec` from
kernel mode, save kernel registers as if they were the program's, and
wreck the process. That is the **invariant**: the trap vector names the
kernel's handler whenever kernel code runs with interrupts on, and
`uservec` only from just before the return to user space until the next
trap.

![One trip from `ecall` and back: the kernel page table is installed only between the two `csrw satp`, and `stvec` names `kernelvec` from the start of `usertrap` until `prepare_return`.](figures/06.01-round-trip.svg)

## Break it

No process runs until 07.02, so this experiment uses the 07.02 build,
whose first process, `init`, starts with a system call. In
`build/at/xv6/07.02/kernel/trap.c`, in `usertrap`, comment out the line
that steps past the `ecall`:

<!-- verify: patch file=kernel/trap.c at=07.02
-    p->trapframe->epc += 4;
-->
```
    p->trapframe->epc += 4;
```

and run `./learn run xv6 --at 07.02`. The kernel boots and then stops:

<!-- verify: session run="./learn run xv6 --at 07.02" hangs=3
lines 3-4 unordered
-->
```
xv6 kernel is booting

hart 2 starting
hart 1 starting
```

`init: starting sh` never prints, and Control-P, which lists the
processes, shows `init` running, not waiting:

<!-- verify: session send=ctrl-p -->
```
1 run    init
```

`sepc` points at the `ecall` itself, so without the `+ 4` the `sret`
returns to the same instruction and `init` executes its first system call
again, forever. Nothing crashes: every trap succeeds, and nothing moves.
Put the line back.

## Decide the boundary

xv6 keeps the kernel out of user page tables, mapping only the trampoline and
trapframe, and pays for it on every trap with two page-table switches and a full
`sfence.vma`. Another kernel could map itself into every address space, protected
by the supervisor-only bit, so a trap needs no switch at all. Linux did exactly
that on x86 until the Meltdown attack made kernel mappings in user tables readable
through speculation; it then moved to xv6's design, a small entry trampoline in
each user table, and took the slowdown.

How much of the kernel should a user page table be able to see, and what are you
willing to pay on every system call to hide the rest?
