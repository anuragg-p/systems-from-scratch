# 06.06 Pipes

This lesson covers pipes: a buffer in the kernel that one process writes
into and another reads from, so the output of one program can become the
input of the next.

## Where this fits

![Where 06.06 fits](figures/06.06-map.svg)

A pipe is an open file with no disk behind it. Above it, programs read and
write a pipe exactly as they read and write a file or the console, and the
shell will build every pipeline from one pipe, two forks and a little
rearranging of descriptors (07.02). Below, it uses an open file for each
end (05.07), one page from the page allocator for the buffer, and sleep
and wakeup (04.03) so that each side can wait for the other. After this
lesson two processes can stream data to each other while both run.

## The idea

![The 512 bytes of `data` as a ring: 300 bytes are waiting, and they wrap past the end of the array.](figures/06.06-ring.svg)

**The need.** In `cat README | grep xv6`, `cat` produces bytes and `grep`
consumes them, and neither knows how fast the other is. If `cat` runs
ahead, its output must be held somewhere; if the holding space fills up,
`cat` must wait; if `grep` runs ahead, it must wait for more; and when
`cat` is finished, `grep` must be told there is no more coming, or it will
wait forever.

**The idea.** A pipe is a small ring buffer of 512 bytes in the kernel,
with a read end and a write end that are ordinary open files. A writer
copies bytes in until the buffer is full, then sleeps until a reader makes
room. A reader takes whatever bytes are there; if there are none, it
sleeps until a writer adds some. Each side, after changing the buffer,
wakes the other.

The end of the stream is not a position, as it is in a file; it is an
event: the last write end being closed. A reader that finds the buffer
empty and no writer left returns 0, which every program treats as end of
file. Likewise, a writer whose readers are all gone gets an error instead
of filling a buffer nobody will drain.

### `pipealloc`, first in `pipe.c`

Where a pipe comes from. `kernel/pipe.c:pipealloc` takes two open files
from the file table (05.07) and one page from the page allocator for the
ring, its lock and its two counts. Both files point at that page; the
first can only be read, the second only written. These are the two
descriptors the `pipe` call will hand back. If any of the three
allocations fails, it gives back the ones that succeeded.

### `pipewrite`

What `write` on a pipe's write end comes down to.
`kernel/pipe.c:pipewrite(pi, addr, n)` copies `n` bytes from the user's
buffer into the ring, sleeping whenever it is full, and returns -1 if the
read end is closed or the process is killed.

### `piperead`

What `read` on the read end comes down to.
`kernel/pipe.c:piperead(pi, addr, n)` sleeps while the pipe is empty and a
writer still exists, then copies out whatever is there, up to `n` bytes,
and wakes any writer waiting for room. An empty pipe with no writer left
gives 0.

### Pipes as open files

A pipe's two ends are open files (05.07), so this lesson also adds the
pipe case to the open-file code: `fileread`, `filewrite` and `fileclose`
now send a pipe's end to `piperead`, `pipewrite` and `pipeclose`. The
system call that makes a pipe, `pipe`, comes with 06.07, beside the other
calls that hand out file descriptors.

## Run it

Nothing runs in user space yet, and nothing could make a pipe if it did:
the `pipe` call comes with 06.07 and the first process with 07.02. So
`./learn run xv6 --at 06.06` boots to the hart lines and waits, and the
pipe code sits in the kernel unreached.

## How it works

### Writing `pipewrite`, step by step

1. **When there is room and a reader, it is a copy loop.** Under the
   pipe's lock, copy byte by byte into the ring, then wake the readers:
   ```
     acquire(&pi->lock);
     while(i < n){
       ...
         char ch;
         if(copyin(pr->pagetable, &ch, addr + i, 1) == -1){
           ...
         }
         pi->data[pi->nwrite++ % PIPESIZE] = ch;
         i++;
     ...
     wakeup(&pi->nread);
     release(&pi->lock);
   ```
2. **A full buffer: wake the readers and sleep** on the write count until
   there is room. Without the wakeup, a reader asleep on an empty pipe
   would never come to drain it:
   ```
       if(pi->nwrite == pi->nread + PIPESIZE){
         wakeup(&pi->nread);
         sleep(&pi->nwrite, &pi->lock);
   ```
3. **Give up if nobody can read,** checked on every pass: the read end is
   closed, or this process has been killed. Return -1 rather than fill a
   buffer nobody will drain.
4. **A bad source address** fails the write with -1 if nothing was copied
   yet, so the caller sees an error rather than a write of nothing, and
   otherwise returns the bytes that made it.

### Writing `piperead`, step by step

1. **Copy out what is there.** Under the lock, take bytes until `n` are
   done or the pipe runs dry, then wake the writers:
   ```
     acquire(&pi->lock);
     ...
     for(i = 0; i < n; i++){
       if(pi->nread == pi->nwrite)
         break;
       ch = pi->data[pi->nread % PIPESIZE];
       if(copyout(pr->pagetable, addr + i, &ch, 1) == -1) {
       ...
       pi->nread++;
     }
     wakeup(&pi->nwrite);
   ```
2. **Wait while the pipe is empty and a writer exists.** Copying from an
   empty pipe would return 0, which the caller takes as end of file; so
   sleep first, and return 0 only once no writer is left. A killed process
   gets -1 instead of sleeping on. A read of 0 bytes never sleeps: there is
   nothing it could be waiting for, so it returns 0 at once.
3. **A bad destination address** fails the read with -1 if nothing was
   copied yet, and otherwise returns the bytes that made it.

### Why it is built this way

**Counters that only grow.** The pipe keeps two counts, bytes ever written
and bytes ever read, and finds the position in the array by taking each
count modulo 512. The pipe is empty when the counts are equal and full
when they differ by 512. Two wrapped indexes could not tell "empty" from
"full" without wasting a slot. The counts are 32-bit and do wrap after
4 GiB, but 2^32 is a multiple of 512, so the position and both checks
still come out right.

**Two channels, one lock.** Readers sleep on the address of the read count
and writers on the address of the write count, all under the pipe's lock,
and each side wakes the other's channel after it changes the buffer. Both
sleeps sit in `while` loops, so a process that wakes rechecks the buffer
under the lock before it acts (04.03).

**End of file is decided in the reader's loop.** The reader sleeps only
while it wants bytes, the pipe is empty *and* the write end is open:

```
  while(n > 0 && pi->nread == pi->nwrite && pi->writeopen){
```

When the last writer closes its end, `pipeclose` clears `writeopen` and
wakes the reader, the loop ends, nothing is copied, and `piperead` returns
0. That is the **invariant**: a reader sleeps only while some process could
still write.

![One reader and one writer: each sleeps on its own counter and wakes the other's, and closing the write end is what turns an empty pipe into end of file.](figures/06.06-sleep-wake.svg)

**"Closed" means every copy closed.** `fork` duplicates descriptors, so
after a shell makes a pipe and forks twice, three processes hold both ends.
The write end counts as closed only when every holder has closed it or
exited. A shell, or a reader, that forgets to close its own copy of the
write end keeps `writeopen` at 1, and the reader never sees end of file.
It is the most common bug in a first shell, and the kernel cannot fix it.

Bytes move one at a time, each through `copyin` or `copyout`. That is
slow, and it keeps the code short: the lock is held across the whole copy,
and no page is ever shared between processes.

## Break it

No process can make a pipe until there is a shell, so this experiment uses
the 07.02 build, whose only programs are `sh` and `echo`. In
`build/at/xv6/07.02/kernel/pipe.c`, delete `&& pi->writeopen` from the
`while` condition in `piperead`, so the loop is
`while(n > 0 && pi->nread == pi->nwrite)`.
Run `./learn run xv6 --at 07.02` and hand a second shell a command through
a pipe:

<!-- verify: patch file=kernel/pipe.c at=07.02
-  while(n > 0 && pi->nread == pi->nwrite && pi->writeopen){
+  while(n > 0 && pi->nread == pi->nwrite){
-->
<!-- verify: session run="./learn run xv6 --at 07.02" hangs=2 -->
```
$ echo echo hi | sh
$ hi
$
```

The `$` lines are the second shell's prompts, and the first shell's prompt
never comes back. Control-P shows who is waiting:

<!-- verify: session send=ctrl-p -->
```
1 sleep  init
2 sleep  sh
3 sleep  sh
5 sleep  sh
```

`echo` (pid 4) wrote `echo hi` into the pipe and exited, closing the write
end. The second shell (pid 5) read the line, ran it, and asked for the next
one. It found the pipe empty, and the loop now sleeps on an empty pipe no
matter who could still write. Nothing will ever wake it, so it never sees
end of file and never exits, and the first shell's child (pid 3) waits for
it forever. Unchanged, the second shell gets 0 from that read, exits, and
the first shell's prompt comes back.

## Decide the boundary

xv6 makes a pipe a 512-byte buffer inside the kernel, with blocking on both sides.
Linux uses a larger buffer (64 KiB by default, in pages) and can move data between
pipes and files without copying. Another system could skip the buffer and make writer
and reader meet directly, handing bytes over only when both are present - tiny, but
each side now waits for the other on every call. Or it could drop pipes and have the
shell write a temporary file, which is how early MS-DOS did `a | b`, and pay with
disk space and no overlap between the two programs. How much should the kernel hold on
behalf of a writer that runs faster than its reader?
