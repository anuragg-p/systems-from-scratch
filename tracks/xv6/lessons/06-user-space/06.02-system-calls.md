# 06.02 System calls

This lesson covers system calls: how a program says which service it
wants and passes its arguments, and how the kernel picks the right
function and hands the result back.

## Where this fits

![Where 06.02 fits](figures/06.02-map.svg)

System calls sit right on top of the trap path from the last lesson: a
call is a trap with a request attached. Above them is every user program,
through a small library of tiny wrappers, one per call. Below them are
the services the kernel offers: files, processes, memory. After this
lesson the kernel can take a request by number and hand back an answer;
the first program to make one runs with 07.02.

## The idea

![`write(1, buf, 3)` as a system call: the wrapper puts 16 in `a7`, `syscall` uses it to pick `sys_write` from the table, and the result goes back through the trapframe's `a0`.](figures/06.02-syscall-path.svg)

**The need.** A program calls `write(1, buf, 3)`. The trap from the last
lesson brings it into the kernel, but all the kernel learns from the
hardware is "this was an `ecall`". It still needs to know which of two
dozen services is wanted, what the arguments are, and where to put the
answer so that `write` returns 3 in the program.

**The idea.** Agree on registers, the way a C function call does. The
program puts a call number in `a7` and up to six arguments in `a0` to
`a5`, runs `ecall`, and finds the result in `a0` when it resumes. The
trampoline has already saved all of those registers in the process's
trapframe. So the kernel reads the number from the saved `a7`, looks it up
in a table of functions, calls the one it finds, and writes the return
value into the saved `a0`. The return to user space reloads `a0` from the
trapframe, and the program sees it as the value of `write`.

On the user side, each call is a wrapper of three instructions, generated
from one list of names by `user/usys.pl` at build time:

<!-- verify: session cwd=project run="perl user/usys.pl" before more -->
```
.global write
write:
 li a7, SYS_write
 ecall
 ret
```

The compiler has already put `fd`, `buf` and `n` in `a0` to `a2`, as for
any function call; the wrapper only adds the number.

### `argraw`

Every system call function needs its arguments, and reads them through
`argint`, `argaddr` or `argstr`, which all come down to this.
`kernel/syscall.c:argraw(n)` returns argument `n`, 0 to 5, from the copy
of register `a0 + n` in the trapframe. A string argument is copied in by
`fetchstr`. Its neighbour `fetchaddr` reads one 64-bit word from the
program's memory, after checking that the word lies below the process's
size (in two comparisons, because `addr + 8` can wrap around); its first
user is `exec` in 06.03, which reads the program's argument pointers
with it.

### `syscall`

Called by `usertrap` for every `ecall`: this lesson adds that call, in
the place 06.01 left for it. `kernel/syscall.c:syscall` reads the call
number, and if it names a function in the `syscalls[]` table,
calls it and stores its return value as the program's `a0`. An unknown
number prints a message and returns -1.

### `sysfile.c`

The table starts with four calls from this file, `read`, `write`,
`close` and `fstat`. They work on a descriptor the process already
holds, so they need nothing beyond the open files of 05.07: `read` and
`write` pass on to `fileread` and `filewrite`, `close` empties the slot,
and `fstat` copies a `struct stat` (type, size, inode number, link
count) out to the program through `filestat`. The calls that make
descriptors and change the file tree come with 06.07. All four begin
with `argfd`, which turns the descriptor argument into the process's
`struct file`, refusing a number outside 0 to `NOFILE`-1 or an empty
slot: a descriptor is a number from user space like any other.

## How it works

### Writing `syscall`, step by step

1. **Read the number, call, store the result.** The number comes from the
   saved `a7`; the result goes into the saved `a0`, which is what the
   program will see as the return value:
   ```
     int num;
     struct proc *p = myproc();

     num = p->trapframe->a7;
     p->trapframe->a0 = syscalls[num]();
   ```
   Leave the store out and every call "returns" whatever the program had
   in `a0`: its own first argument.
2. **Check the number** before using it as an index. A program can put
   anything in `a7`, and the table has holes; without the check, a bad
   number would make the kernel call through whatever pointer lay in a
   hole or past the end of the table.
   ```
     if(num > 0 && num < NELEM(syscalls) && syscalls[num]) {
   ```
3. **An unknown number** prints the pid, the program's name and the number,
   and returns -1.

### Writing `copyinstr`, step by step

`argstr` comes down to `copyinstr`, which copies a string out of the
program's memory without trusting anything about it.

1. **One page at a time.** Find the page holding the next byte through the
   process's page table, and copy from its physical address, which the
   kernel can use as a pointer since it maps all of memory at the same
   address:
   ```
     while(got_null == 0 && max > 0){
       va0 = PGROUNDDOWN(srcva);
       pa0 = walkaddr(pagetable, va0);
       if(pa0 == 0)
         return -1;
       ...
       char *p = (char *) (pa0 + (srcva - va0));
       ...
       srcva = va0 + PGSIZE;
     }
   ```
   It has to be page by page: two neighbouring pages of the program can be
   anywhere in physical memory. `walkaddr` (02.04) returns 0 for a page
   that is not mapped or lacks the user bit, so a kernel address fails
   here.
2. **Copy up to the zero byte.** Inside a page, bytes are copied until the
   string's end; finding it sets `got_null` and ends both loops.
3. **Stop at `max`.** A string with no zero byte within `max` bytes fails
   with -1 instead of running past the end of the kernel's buffer.

### Why it is built this way

**Arguments come from the trapframe, not the registers.** By the time a
system call function runs, the kernel has been running C code for a
while, and the real `a0` to `a5` hold the kernel's own values. The
program's arguments survive only in the copies `uservec` made, so that is
where `argraw` reads them, and where `syscall` writes the result.

**Never trust a pointer from user space.** `argaddr` hands back the
raw number the program passed. It might be a kernel address, an unmapped
address, or a string that runs off the end of a page, and in any case it
is an address in the program's page table, not the kernel's. So the
kernel never dereferences it. It copies, with `copyin`, `copyout` and
`copyinstr`, which look the address up in the process's page table and
refuse any page that is not mapped for user access. A bad pointer makes
the call return -1; it cannot make the kernel read or write its own
memory on the program's behalf. That is why `argaddr` and `argint` check
nothing and cannot fail: an address is checked when it is used, in the
copy, and a number by the call that knows its range, as `argfd` does.
`argstr` can fail because it copies at once.

**One list of calls.** The call numbers live in `kernel/syscall.h`, and both
the kernel's table and the user wrappers are built from them; `usys.pl`
exists so that the two sides cannot drift apart.

The **invariant**: the program's view of a system call is exactly a
function call. Its arguments are read from the trapframe, its result is
written there, and nothing else in the program's registers changes.

## Break it

The table is written with each function's number in brackets,
`[SYS_read] sys_read,`. Write it as a plain list instead: in
`build/at/xv6/06.02/kernel/syscall.c`, take the four `[SYS_...]` labels
off, leaving

<!-- verify: patch file=kernel/syscall.c
-[SYS_read]    sys_read,
-[SYS_fstat]   sys_fstat,
-[SYS_write]   sys_write,
-[SYS_close]   sys_close,
@block
-->
```
sys_read,
sys_fstat,
sys_write,
sys_close,
```

Run `./learn run xv6 --at 06.02` again. It builds, with no word about the
table, and boots as before. Dump the start of the table as in Run it (it
has not moved):

<!-- verify: session run="./learn run xv6 --at 06.02" send="ctrl-a c" -->
```
(qemu) x/4gx 0x800066d0
00000000800066d0: 0x00000000800035ca 0x00000000800036ca
00000000800066e0: 0x0000000080003622 0x000000008000367a
```

The four functions sit in slots 0 to 3, in the order they were listed,
and the table ends there; what follows in memory is other data. But a
program asks by number, and none of the numbers, 5, 8,
16 and 21, is below 4 any more: the bounds check in `syscall` would
refuse every call with "unknown sys call". Without that check it would be
worse, a jump through whatever lies past the table. The numbers in
`syscall.h` are positions, and the brackets are what put each function
in its position. Put them back.

## Decide the boundary

xv6 has 21 calls in its core (the network and screen modules add four),
found by a number in a register and a table lookup, with every pointer
copied and checked. Linux has several hundred, and also uses `ecall`
(`syscall` on x86), but has faster paths for hot calls such as `gettimeofday`, which
the kernel maps into the process as a **vDSO** and answers without any trap at all.
Another design has no system calls: a unikernel links the application with the
kernel in one address space and calls it as a function. That costs nothing per call
and protects nothing; one bad pointer takes down everything.
