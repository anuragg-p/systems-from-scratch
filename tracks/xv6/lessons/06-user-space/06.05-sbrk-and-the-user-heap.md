# 06.05 sbrk and the user heap

This lesson covers `sbrk`, the system call a process uses to ask for more
memory while it runs, and `growproc`, which grows or shrinks the process.

## Where this fits

![Where 06.05 fits](figures/06.05-map.svg)

Growing a process sits between a program's memory allocator and the
kernel's page tables. Above it, the allocator in the user library (07.01)
will ask for memory in large pieces and hand it out in small ones; the
shell uses it for every command it parses. Below, it uses the page
allocator and the page-table calls of module 02 to add pages to the
process or take them away. After this lesson a process is no longer stuck
with the memory it was started with.

## The idea

![`sbrk(8192)` in a process laid out like `echo`: two zeroed pages appear at the old `p->sz`, which is what the call returns.](figures/06.05-sbrk-heap.svg)

**The need.** When `exec` starts a program, the program gets exactly its
code, its data and one page of stack. But the shell cannot know in
advance how many commands it will parse or how long they will be; it needs
memory on demand, and the right to give it back.

**The idea.** A process's memory is one range starting at address 0 and
ending at its size, the **break**. Everything below the break is mapped.
Above it, all the way up to the trapframe near the top of the address
space, nothing is: that empty stretch is where the heap can grow. So
asking for more memory means moving the break up: map fresh pages just
above it and move it past them. `sbrk(n)` does that and returns the old
break, which is exactly where the new bytes begin. A negative `n` moves
the break down and frees the pages.

A worked example with a program from 07.02, the shell. Its code and data
fill the first three pages and the guard and stack pages follow, so its
break starts at 0x5000. Its first `malloc` (the user library's, 07.01)
asks for 64 KiB, `sbrk(65536)`. The kernel maps sixteen zeroed pages from
0x5000 to 0x14fff, moves the break to 0x15000, and returns 0x5000, where
`malloc` puts its first block.

### `sys_sbrk`

The system call. `kernel/sysproc.c:sys_sbrk` reads `n`, remembers the
current break, asks `growproc` to move it, and returns the old break, or
-1 if there was not enough memory. Like every call since 06.02 it also
gets a number, a line in the dispatch table and a wrapper in `usys.pl`.

### `growproc`

The one place that changes a process's size. `kernel/proc.c:growproc(n)`
maps new writable pages for a positive `n` and unmaps and frees pages for a
negative one, then records the new size.

## Run it

Nothing runs in user space yet, so nothing calls `sbrk`: its caller,
`malloc`, comes with 07.01, and the first process with 07.02.
`./learn run xv6 --at 06.05` boots to the hart lines and waits. What you
can look at is the program's side of the call. In `build/at/xv6/06.05/`,
`perl user/usys.pl` prints the wrappers, and the new one is

## How it works

### Writing `growproc`, step by step

1. **Growing:** map the new range writable from the current size up, and
   record the new size:
   ```
     sz = p->sz;
     if(n > 0){
       if((sz = uvmalloc(p->pagetable, sz, sz + n, PTE_W)) == 0) {
         return -1;
       }
     ...
     p->sz = sz;
     return 0;
   ```
   If memory runs out, `uvmalloc` gives back what it added, so a failed
   call leaves the process as it was.
2. **Refuse to reach the trap pages,** before mapping anything:
   ```
       if(sz + n > TRAPFRAME)
         return -1;
   ```
   The top two pages of every user address space are the trapframe and
   the trampoline (06.01), and they are already mapped. Without the check,
   a heap that reached them would make `mappages` find a page in use and
   panic (02.04): one program's request would stop the whole kernel. A
   request the kernel cannot grant must come back as -1. With 128 MB of
   memory the pages would run out long before 0x3fffffe000, but the rule
   should not depend on how much memory the machine has.
3. **Shrinking:** `uvmdealloc` unmaps and frees the whole pages above the
   new size.

### Why it is built this way

**Return the old break.** It is the start of the new memory, so the caller
can use the answer as a pointer straight away; `sbrk(0)` then means "where
is the break now?". Returning the new break instead would hand the caller
an address just past the memory it asked for.

**Pages now, not later.** `growproc` allocates and zeroes every new page at
once, whether or not the program ever touches it. It is the simplest rule
that keeps the **invariant**: every address below the break is mapped and
backed by a page of its own, all of it user-accessible except the stack's
guard page; every address at or above the break, up to the trapframe, is
not mapped. Zeroing matters too: a page fresh from the allocator holds
whatever its last owner left there.

The break is also what `fork` copies: the child gets a copy of every page
below it. A bigger heap makes a slower `fork`.

Put together, a process's address space from the bottom up:

| address | what |
|---|---|
| 0 | code, then data on its own page |
| next page | guard page, mapped without the user bit |
| next page | stack, one page |
| above it, up to the break | heap, grown by `sbrk` |
| 0x3fffffe000 | trapframe |
| 0x3ffffff000 | trampoline |

## Break it

No process runs until there is a shell, so this experiment uses the 07.02
build. In `build/at/xv6/07.02/kernel/sysproc.c`, make `sys_sbrk` return the
**new** end instead of the old one: change `return addr;` to
`return myproc()->sz;`. Run `./learn run xv6 --at 07.02` and type `echo hi`:

<!-- verify: patch file=kernel/sysproc.c at=07.02
-  return addr;
+  return myproc()->sz;
-->
<!-- verify: session run="./learn run xv6 --at 07.02" -->
```
$ echo hi
usertrap(): unexpected scause 0xf pid=3
            sepc=0x1372 stval=0x15008
$
```

The shell's child parses the line with `malloc`, and the first `malloc`
called `sbrk(65536)` with the break at 0x5000 and got back 0x15000, the new
end. It wrote its block header there, just past the end of the heap, and
took a store page fault (`scause` 0xf) at 0x15008, the header's size field;
`sepc` is inside `malloc` in `build/user/sh.asm`. The kernel killed that
process (pid 3, the shell's child), and the shell itself survived to print
the next prompt.

## Decide the boundary

xv6 grows the heap with one call that maps real pages at once. Another kernel could
make the allocation **lazy**: `sbrk` only bumps `p->sz`, and a page fault on an
unmapped address allocates the page then. Programs that ask for much more than they use
then cost nothing, and Linux works this way. The price is a real page-fault handler in
`usertrap`, and a third outcome for every kernel read of user memory (the page may
simply not exist yet). A different design drops `sbrk` altogether for `mmap`, which can
also map files and release pieces from the middle of the heap, at the cost of
per-region bookkeeping. Is the kernel's job to hand over memory when asked, or when
first used?
