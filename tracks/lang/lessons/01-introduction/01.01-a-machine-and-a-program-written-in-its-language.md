# 01.01 A machine, and a program written in its language

A processor runs **instructions**, and the first programs were written as
nothing else. This lesson builds a small machine, a C program that runs
RISC-V instructions written as text, and one program for it written by
hand: the greatest common divisor of two numbers. Every way of running a
program that this chapter builds ends in a machine, so the track starts
with one.
**Read first:** chapter 1 from its first page to the start of section 1.1 (pages 5 to 7), in Programming Language Pragmatics, 4th edition.

The chapter opens with one program, the greatest common divisor by
Euclid's method, shown twice: as the bytes a processor runs (Example 1.1)
and as assembly (Example 1.2). This lesson makes Example 1.2 for a machine
of your own. Lesson 01.02 shows you the bytes of the same program, as your
own computer's C compiler makes them; this machine gets bytes in chapter 5.
The book's examples are in C and x86 assembly. This track's are in a
language of your own and in RISC-V assembly.

## Where this fits

![Where 01.01 fits](figures/01.01-map.svg)

This is all of chapter 1 in one picture, as it stands when the module is
done. Follow one program through it: the greatest common divisor of 1071
and 462. While the two numbers differ, the larger loses the smaller; when
they are equal, that is the answer, 21. The chapter runs this program five
ways, in the book's order, and every way prints 21:

1. **By hand, on a machine** (this lesson). The program is written as the
   machine's own instructions. The machine is given that text and the two
   numbers, and gives back what the program prints.
2. **By an interpreter** (01.03). The program is written once, in your
   language (lesson 01.02 writes it). The first interpreter is given its
   text and the numbers and gives back the output, reading the text as it
   goes.
3. **By a translator** (01.04). The translator is given the program and
   gives back a C program. Your computer's C compiler, assembler and linker
   are given that, and give back a program for your computer, which is
   given the numbers.
4. **Through a compiler's front end, then a walk of its tree** (01.06 to
   01.09). A **scanner** is given the characters and gives back tokens, the
   words of the program; a **parser** is given the tokens and gives back a
   tree; **semantic analysis** is given that tree and gives back a smaller
   one, with a table of the program's names. An interpreter walks that
   tree and gives back the output.
5. **Through the compiler's back end, to the machine again** (01.10,
   01.11). A **code generator** is given the same tree and gives back
   assembly for this lesson's machine. An **improver**, before it, decides
   which variables can stay in registers, so that the code is shorter.

Lesson 01.02 writes down what every way must print, and lesson 01.05 builds
the bar across the bottom of the map: one command that runs every program
every way and compares what each printed, byte for byte. That check is the
habit of the whole track.

The order is the book's. Section 1.4 sets the interpreter against the
translator; section 1.6 takes a compiler apart, phase by phase, on this
same program. The machine comes first because the chapter's first pages
are about it, and because two of the five roads end at it. Read each
section of the book first, then its lesson: the lesson builds what the
section describes, and runs it.

## The idea

![The machine: a few registers, a program, and the rule for which instruction runs next.](figures/01.01-machine.svg)

Before a program in any language can run, something has to run
instructions. Your computer's processor does, but its instructions are
those of its own kind of processor, and its programs are numbers. So this
track builds a machine of its own: `machine`, a C program that behaves as a
RISC-V processor would, and runs a program written as assembly text.

A machine is three things. **Registers**: a few named places, each holding
one number; this machine has RISC-V's 32, each 64 bits, named `zero`,
`ra`, `sp`, `a0`, `s1` and so on. A list of **instructions**, each a small
step: `sub s1, s1, s2` subtracts `s2` from `s1` and leaves the result in
`s1`. And a rule for which instruction runs next: the next one in the list,
unless the one that just ran was a **jump**, or a **branch** (a jump taken
only when a comparison holds), which names another. **Assembly** is that
list as text, one instruction a line. A **label** such as `loop:` names the
place of the instruction after it, so that a jump can say where it goes.

Here is the program, `programs/gcd.s`, written by hand:

```
# gcd.s: the greatest common divisor of two numbers, written by hand
# for the machine. i is kept in s1 and j in s2.
main:
    call getint           # a0 = the next number of the input
    mv   s1, a0           # i
    call getint
    mv   s2, a0           # j
loop:
    beq  s1, s2, done     # until i == j:
    ble  s1, s2, smaller  #   the larger one loses the smaller
    sub  s1, s1, s2       #   i = i - j
    j    loop
smaller:
    sub  s2, s2, s1       #   j = j - i
    j    loop
done:
    mv   a0, s1
    call putint           # print i
    li   a0, 0
    call exit             # status 0
```

Lines 4 to 7 read the two numbers. `call getint` puts the next number of
the input in `a0`, and `mv s1, a0` copies it into `s1`: the first number,
`i`, lives in `s1`, and `j` in `s2`. Lines 8 to 15 are the loop. `beq s1,
s2, done` leaves it when the two are equal. `ble s1, s2, smaller` goes to
the other arm when `s1` is the smaller (branch if less or equal).
Otherwise `s1` loses `s2` and `j loop` goes round again; at `smaller`, `s2`
loses `s1`. At `done` the answer goes to `a0`, `call putint` prints it, and
`call exit` ends the program with the status in `a0`, 0.

<!-- verify: fact cmd="grep -cE '^ +[a-z]' programs/gcd.s" expect=14 -->
Writing it by hand made you decide everything, in 14 instructions: that
`i` is `s1` and `j` is `s2`, every label, and where every jump goes (`ble`
to `smaller` and not to `loop`, or the program is wrong without a word).
The algorithm's `if` and `else` are two branches and two jumps, and nothing
in the text says so. And it runs on this machine only: a processor of
another kind has other registers and other instructions, and the program
would be written again. That is the book's case for languages above the
machine, and the subject of the rest of the chapter.

The text is real RISC-V: the GNU assembler for RISC-V takes this file as
it is. Some of its instructions are **pseudo-instructions**, shorthands
that a real assembler turns into one or more real instructions: `mv s1,
a0` is `addi s1, a0, 0`, `j loop` is a jump-and-link (`jal`) that keeps no
return address, and `call` is two instructions. This machine runs each as
written and counts each as one. It also runs the text itself, where a real
processor runs instructions as numbers; chapter 5 gives this machine its
numbers.

### a register by its name

`reg` reads a word and looks for it among the 32 names in `regs[]`. Where
it is found is the register's number, so `regs[]` is in RISC-V's own
order: `zero` is x0, `ra` x1, `sp` x2, and `s1` is x9 and `s2` x18, since
the names follow what each register is for, not its number. A name that
is not there stops the machine, with its line.

### the first pass: the labels

`find_labels` splits the file into lines and cuts each where its comment
starts. A line may hold a label, an instruction, or both. A label is
recorded with the address the next instruction will have; what is left of
the line, if anything, is kept as the text of an instruction, with its
line number, for the second pass.

### the second pass: each instruction

`read_instructions` finds each instruction's name in `ops[]`. Beside every
name a short string says what follows it: `rrr` is three registers
(`sub`), `rrl` two registers and a label (`beq`), `rn` a register and a
number (`li`), `l` a label (`j`, `call`). One loop reads every
instruction's operands from that string. A label becomes the address the
first pass gave it, and a `call` may name one of the machine's routines
instead of a label.

### getint: a number from the input

`getint` skips white space, takes an optional sign and the digits, and
leaves the character after them to be read next. The digits are added up
in an `unsigned long`, so a number too large for 64 bits wraps around
instead of being undefined in C. At the end of the input the program stops
with `machine: getint: no more input` and status 1.

### the routines of the machine

`routine` does in C what `getint`, `putint` and `exit` stand for: the next
number into `a0`; `a0` printed, with a line end; the program ended, with
status `a0`. They change `a0` and nothing else.

### --trace: each instruction and what it changed

Before each instruction the run loop copies the registers into `before[]`.
`trace` prints the instruction's line and text, then every register that no
longer holds what it held, as `name = value`.

### the run loop

`run` starts at `main`, with `pc`, the **program counter**: the address of
the next instruction. Each time round it checks that `pc` is the address of
an instruction, counts it, takes its operands' values, and does what the
`switch` says. A jump, or a branch whose comparison holds, sets the next
`pc`; anything else goes on to the instruction after. Sums are done on
unsigned numbers, which wrap around as RISC-V's registers do, so none is
undefined in C; `div` by zero gives -1, as RISC-V's `div` does.

The loop goes round twice, once on each arm, and the third `beq` finds the

is line 5's instruction, the one after the first `call`.

## How it works

### A jump forward needs a second pass

Line 9, `beq s1, s2, done`, names a label seven lines further down. Read in
one pass from the top, the machine would meet `done` before it knew where
`done` was. So it reads the text twice. The first pass only counts. A
RISC-V instruction is 4 bytes, so instruction `i` is at address `4 * i`,
and a label's address is 4 times the number of instructions above it:

```
      labels[nlabels++] = (Label){p, len, 4L * ninsns};
```

The second pass then turns every label into its address, wherever in the
file it is. In the trace, `ra = 56` after the last `call` is 14 times 4:
the address just past the last instruction.

### The way back is an address in a register

`call` is a jump that remembers where it came from. It puts the address of
the next instruction in `ra`, then goes to the label; `ret` goes to
whatever address `ra` holds.

```
    case CALL:
      set(RA, next);
```

At the start `ra` holds the address just past the last instruction, so a
`main` that calls nothing can end with `ret`, as a C `main` returns to
whoever called it, and the program stops. `gcd.s` calls `getint`, and that
call replaced `ra`. A `ret` on its last line would go back to line 19, the
instruction after the last call, and run lines 19 and 20 for ever. So it
ends with `call exit`.

### The library is part of the machine

`getint`, `putint` and `exit` are not labels in `gcd.s`. The second pass
finds them among the machine's routines instead, and the run loop hands
such a call to `routine`, which does the work in C. On a real computer
there are no such instructions: reading a number is code, which asks the
operating system for characters and turns digits into a value, and it is
kept in a library and joined to each program by the linker. Lesson 01.02
writes that code in C, in `rt.c`, and lesson 01.04 has the linker join it
to a program (the book's Example 1.11). Here it is part of the machine, so
that a program of this chapter reads and prints with one line, and the
machine needs no memory, characters or operating system to do it.

### One register is always 0

The **invariant** of the machine: `zero` always holds 0. A program may
name it as the register to write, and the write is dropped. Every
instruction writes its register through one function, and this is the
line that keeps it:

```
  if (r != ZERO)                 // what is written to zero is dropped
    x[r] = v;
```

With it, 0 is always to hand without an instruction to make it. The real
assembler's `beqz a0, done` is `beq a0, zero, done`, and its `j loop` is a
jump-and-link that writes its return address into `zero`: nowhere.

## Decide the boundary

This machine keeps the program as text, read into an array of C structs
where nothing the program does can reach it. A real RISC-V computer keeps
the program as numbers, 4 bytes an instruction, in the same memory as the
program's data, and fetches each instruction from there by its address.
That buys a great deal. A program is only bytes, so another program can
write it, save it and load it, which is how every compiler's output comes
to run, and one memory serves both. It costs an encoding for every
instruction, a decoder, and a memory with addresses and limits, none of
which says anything about languages. Chapter 1 is about languages, so this
machine runs the text. Chapter 5, on how machines are built, gives the
instructions their numbers and puts them in memory. Does your machine need
to run a program that another program has just made, as bytes?

## Break it

Make the machine read the file once. In `build/at/lang/01.01/machine.c`, in
`read_instructions`, let an instruction see only the labels that a single
pass from the top would have met by then: after the line that finds the
label, add

<!-- verify: patch file=machine.c
         Label *l = find(p, n);
@block
-->
```
        if (l && l->address > 4L * i)
          l = NULL;
```

A label further down has an address greater than the instruction's own,
and is now treated as missing. Build it again and run:

<!-- verify: session -->
```
$ make -s
$ ./machine programs/gcd.s < programs/gcd.in; echo $?
machine: programs/gcd.s:9: no label 'done'
1
```

Line 9 is the first jump forward, and `done` is in the file, seven lines
down. The jumps back would have been fine: `loop` is above both `j loop`.
An assembler that reads once must forbid jumps forward, or remember each
one it cannot finish and fill it in when the label turns up; reading twice
is the simplest of the three. Take the two lines out again.
