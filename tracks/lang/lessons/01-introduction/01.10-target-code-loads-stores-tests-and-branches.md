# 01.10 Target code: loads, stores, tests and branches

The compiler's last phase: a code generator that walks the syntax tree once
and writes assembly for the machine of lesson 01.01. Every use of a variable
becomes a load from memory, every assignment a store, and every loop a test
and two jumps.

**Read first:** section 1.6.3 (pages 34 to 36), in Programming Language Pragmatics, 4th edition.

Example 1.26 and Figure 1.7 are the naive code a simple compiler writes for
the book's GCD program, for an x86; here the same kind of code comes out of
`./mote -S` for `gcd.mote`, and the RISC-V machine of lesson 01.01 runs it.

## Where this fits

![Where 01.10 fits](figures/01.10-map.svg)

This lesson is the code generator, the box on the right road's right-hand
fork that writes `assembly` for the machine of lesson 01.01 below it. Above
it is the front end the tree walk of lesson 01.09 uses; the improver between
them is lesson 01.11's. After this lesson `mote` is a compiler: what it
writes runs without `mote`, on a machine that now has a memory for variables.

## The idea

![Where the variables of gcd.mote live: a slot each in the machine's memory, found from sp.](figures/01.10-slots.svg)

The tree walk of lesson 01.09 decides at every node what kind of node it is,
and keeps each variable's value inside the interpreter. A program for the
machine, which has only registers, instructions and now a memory, can do
neither; so the code generator decides once, as it writes.

First, a place for each variable. The machine gets 1 MiB of memory, and
`sp`, the **stack pointer**, starts at its top. The first instruction moves
`sp` down to make the program's **frame**, the piece of the stack a routine
takes for its variables, and each variable gets an 8-byte **slot** in it,
in symbol table order: `i`, entry 1, at `0(sp)`, the address in `sp` plus
0; `j`, entry 2, at `8(sp)`. `ld t0, 0(sp)` **loads** the 8 bytes there
into `t0`, and `sd t0, 0(sp)` **stores** `t0` there.

Then code for each node. A number is an `li`, a use of a variable a load, an
operator one instruction on registers, an assignment a value stored. A
condition is a branch, a loop a label, the branch out, the body and a jump
back. Nothing is remembered from one statement to the next: each loads what
it uses, even what was just stored. That keeps it simple, and right whatever
order the statements come in.

![`i := i - j` as the code generator writes it, an instruction a step: two loads, a subtraction, a store.](figures/01.10-statement.svg)

### `check`

The machine's memory: an address must have its 8 bytes in it, or the run stops.

### `load`

What `ld` does: 8 bytes put together into one value, lowest byte first.

### `store`

What `sd` does: a value taken apart into 8 bytes. Also new in `machine.c`:
`addi`, `ld`, `sd`, `sp` set to the top of memory, and `divzero`.

### `operand` and `into`

`into` writes the code that puts a node's value into a given register;
`operand` puts it in the register of its depth, `t0` to `t6`, and says which.

### `check_divisor`

Before every `div`: if the divisor is not zero, jump past; if it is, put the
line of the `/` in `a0` and call `divzero`, which stops the program.

### `branch_unless`

A condition: both sides into registers, one branch taken when it is false.

### `stmt`

`read` calls `getint` and stores `a0`; `write` puts the value in `a0` and
calls `putint`; `if` and `while` are labels, branches and jumps.

### `generate`

The slots, `main:`, the frame, the statements, then `li a0, 0` and
`call exit`. `./mote -S` runs it after analysis; `agree` gains a fourth way.

```
    li   a0, 0

```

`.L1` is the top of the `while`, and `beq` leaves the loop for `.L2` when
`i == j`, the opposite of `i != j`. The `if` branches to its `else` part,
`.L3`, when `i <= j`. `i := i - j` is the four lines from `ld` to `sd`; `j .L4`
jumps past the `else` part to where `j .L1` goes back to the top. Below,
first `programs/gcd.s` of lesson 01.01: not a way of running your program,
but the same computation written by hand for the machine, the measure for
compiled code. Then a division by zero, compiled, and the check before its

## How it works

### Slots, and a frame of 16

Entry k gets the slot `8 * (k - 1)` bytes above `sp`, and `sp` moves down by
the slots' size rounded up to a multiple of 16:

```
    s->offset = 8 * n++;
  ...
    emit(NULL, "addi", "sp, sp, -%d", (8 * n + 15) / 16 * 16);
```

The machine would not mind 8 or 24, but RISC-V's **calling convention**,
the agreement about which registers mean what across a call, asks that `sp`
be a multiple of 16 whenever a routine is entered, and `main` calls
`getint`: the code keeps the rule a real RISC-V computer would hold it to.
Three variables get a frame of 32 bytes, 8 of them unused.

### One branch, on the opposite

![A while loop as a test and two jumps: the condition becomes one branch on its opposite, past the loop.](figures/01.10-while.svg)

A branch jumps when its comparison holds, and the code must leave the loop,
or skip the `then` part, when the condition does not: so the generator
branches on the opposite, past the code the condition guards:

```
  static const char *opposite[] = {[N_EQ] = "bne", [N_NE] = "beq", [N_LT] = "bge",
                                   [N_GE] = "blt", [N_GT] = "ble", [N_LE] = "bgt"};
```

### Registers as a stack, seven deep

An expression's values wait in `t0` to `t6`, used as a stack: a node's value
and its left operand in the register of its depth, its right operand a
register deeper. [The cc track's lesson 02.03](/t/cc/02.03) is this scheme at
length. An eighth waiting value is `expression too deep`, as in
`1 - (2 - (3 - (4 - (5 - (6 - (7 - 8))))))`; [its lesson 02.06](/t/cc/02.06)
goes on, keeping some of the waiting values in memory.

### Code nobody wrote

On RISC-V a division by zero does not stop the program: the manual defines
the quotient as -1, every bit set, raises no exception, and notes that a
language that wants an error can add one branch before the division.
`check_divisor` is that branch, and the **invariant** it keeps is the
language's: a program that divides by zero stops there and names the line,
compiled or walked. Section 1.6.2 says a compiler may generate a dynamic
check, or the language may leave it unchecked; the check `maybe.mote` needed,
a flag and a test on every load, was left out.

## Decide the boundary

This generator keeps every variable in memory: simple, and never wrong,
since whatever happens between two statements the slot holds the value.

<!-- verify: fact cmd="./mote -S programs/gcd.mote > build/f.s && ./machine --trace build/f.s < programs/gcd.in 2>&1 | grep -cE '^ +[0-9]+  (ld|sd) '" expect=82 -->
It costs a load on every use and a store on every assignment: on 1071 and
462, 82 of the 142 instructions are loads and stores.

gcc without optimisation makes the same choice. Here is the loop of
`programs/gcd.c`, lesson 01.02's, from a RISC-V gcc 15.2.0 at `-O0` on an
Apple M4 Pro Mac (yours may differ):

<!-- verify: skip reason="needs a RISC-V gcc, not one of this track's tools; its output depends on its version (15.2.0 here, Homebrew's riscv64-elf-gcc on macOS)" -->
```
$ riscv64-elf-gcc -O0 -march=rv64im -mabi=lp64 -I. -S -o - programs/gcd.c
...
	sd	a0,-32(s0)
	j	.L2
.L4:
	ld	a4,-24(s0)
	ld	a5,-32(s0)
	ble	a4,a5,.L3
	ld	a4,-24(s0)
	ld	a5,-32(s0)
	sub	a5,a4,a5
	sd	a5,-24(s0)
	j	.L2
...
```

`i` and `j` live at `-24(s0)` and `-32(s0)`; every use loads them and every
assignment stores them. The other choice keeps variables in registers, and
costs deciding which ones and knowing it is safe; lesson 01.11 makes it. Is
a load on every use a fair price for never having to ask where a variable is?

## Break it

Branch on the condition itself instead of its opposite, for `!=`. In
`build/at/lang/01.10/gen.c`, in `branch_unless`'s table, change
`[N_NE] = "beq"` to `[N_NE] = "bne"`, and build again:

<!-- verify: patch file=gen.c old='[N_NE] = "beq"' new='[N_NE] = "bne"' -->
<!-- verify: session -->
```
$ make -s
$ ./mote -S programs/gcd.mote > build/gcd.s && ./machine --count build/gcd.s < programs/gcd.in
1071
13 instructions
$ ./agree
gcd     mote0 ok  motec ok  mote ok  machine DIFFERS
primes  mote0 ok  motec ok  mote ok  machine ok
sum     mote0 ok  motec ok  mote ok  machine ok
3 programs, 4 ways each: 1 differs
```

`while i != j` now leaves the loop exactly when it should stay: 1071 and 462
differ, so the first branch jumps to the end and `i` is printed untouched.
`sum` and `primes` use no `!=`. The tree walker shares the front end and is
right, so `agree` points at the code generator. Put the entry back.
