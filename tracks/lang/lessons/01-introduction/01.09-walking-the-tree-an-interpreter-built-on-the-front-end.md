# 01.09 Walking the tree: an interpreter built on the front end

The front end of lessons 01.06 to 01.08 turns a program into a syntax tree
whose names point into a symbol table. This lesson runs the program from that
tree: a second interpreter, which reads no text and looks up no name while the
program runs.
**Read first:** Example 1.25 in section 1.6.2 (page 33), with Figure 1.4 (page 27) beside it, in Programming Language Pragmatics, 4th edition.

Figure 1.4 draws an interpreter as a compiler's front end with a walk of the
tree after it, and Example 1.25 walks the syntax tree of the book's GCD
program the way that walk would. Here the last box of Figure 1.4 becomes a
file, `interp.c`, and Example 1.25 is what `./mote` does with `gcd.mote`.

## Where this fits

![Where 01.09 fits](figures/01.09-map.svg)

This lesson is the tree walk: the box that leaves the right-hand road to the
left, after semantic analysis, and ends in output. Everything above it is the
front end, the scanner, the parser and the analysis, which hands it a syntax
tree and a symbol table. Below it there is only the output. Until now `mote`
could show what each phase made but could not run a program; from this lesson
on it runs every program in `programs/`, a third way beside the first
interpreter and the translator to C.

## The idea

![The walker on gcd.mote with 6 and 4: the node it is at, and the values in the symbol table.](figures/01.09-walk.svg)

The first interpreter, of lesson 01.03, ran a line by reading its characters.
On every pass of gcd's loop it read the `while` line again, worked out
`i != j` from the text, and found `i` and `j` by comparing their names with
each name in its table. Lesson 01.08 did that reading once, before the run,
and left a tree in which `i := i - j` is four nodes and each name is a
pointer to its entry in the symbol table.

Running the program is now a walk over that tree, in program order. A
statement node says what to do; an expression node's value comes from its
children's values. A variable's value is kept in its symbol table entry:
using it is following a pointer, and giving it a value is writing through one.

With 6 and 4 as input, `read i#1` puts 6 in entry 1 and `read j#2` puts 4 in
entry 2. The `while` asks `(!= i#1 j#2)`: the walk goes down to the two
names, takes 6 and 4 from the entries, and compares them. They differ, so the
body runs: `(> i#1 j#2)` holds, and `:= i#1 (- i#1 j#2)` writes 6 - 4 into
entry 1. Back at the `while`, the condition is asked again, from the tree. On
the next pass `j` becomes 2, the condition fails, and `write i#1` prints 2.

This is the mixed arrangement section 1.4 says most systems use: a front end
that translates the program into a form made for running it, and a small
machine, here the walk, that runs that form.

### `input`

What `read` does: the next whole number of the input, read as the machine's
`getint` and `rt.c` read it, so that every way takes the same input the same
way. Its errors, `read: no more input` and `read: not a number`, are reported
at the `read`.

### `eval`

An expression's value. A number is its value; a variable is its entry's
value, if the entry has one; an operator works out its left operand, then its
right one, then itself. The arithmetic is done on unsigned longs, which wrap
around as the language says numbers do, where an overflowing C `long` would
be undefined. Division by zero is an error at the `/`, and the most negative
number divided by -1 is itself, which C would leave undefined too.

### `test`

A condition's truth: both sides worked out, then compared.

### `interpret`

A list of statements, run in order. A `read` or an assignment writes the
entry's value and marks it as having one; `write` prints; `if` runs one of
its two lists; `while` asks its condition before every pass. The entry gains
the two fields this needs, `value` and `has_value`; `main.c` calls
`interpret()` after analysis, so `./mote FILE` with no option runs the
program; and `agree` gains its third way.

cost the first interpreter more on every pass, and the walker nothing.

## How it works

### Values in the symbol table

![One pass of gcd's loop under each interpreter: the first reads lines and searches for names; the walker follows pointers.](figures/01.09-per-pass.svg)

The first interpreter found a name by comparing its characters with each
name in its table, every time it met the name. That search is section 1.4's
own example of what compiling saves: a variable's place known in advance,
against looked up in a table on every use. The walker does not search: the
analysis of lesson 01.08 searched once, when it made each name node point at
its entry. A use of a variable is three lines of `eval`:

```
    if (!e->sym->has_value)
      error_tok(e->tok, "%.*s has no value yet", e->sym->len, e->sym->name);
    return e->sym->value;
```

### The walk has the grammar's shape

`eval` calls itself for each operand, and `interpret` for the statements
inside an `if` or a `while`: every level of nesting in the program is one more
call, and where the walk has got to is kept on C's own call stack. The first
interpreter kept its own list of open blocks and, on a false condition, read
forward counting `while`s and `if`s against `end`s to find where to go. Here
a block's end is the end of a list, and the `else` part is a pointer; the
language's `while` is C's `while`, asking its condition before every pass:

```
    case N_IF:
      interpret(test(s->cond) ? s->body : s->els);
      break;
    default:
      while (test(s->cond))
        interpret(s->body);
```

### One flag, one test

That a variable must have a value when it is used cannot be checked from the
text, as lesson 01.08 found; section 1.6.2 calls such a rule dynamic. The
walker checks it as it goes. The **invariant** is that no entry's value is
read before something has written it, kept by the test in `eval` before each
read and by one line right after each write:

```
      s->sym->has_value = true;
```

The cost is a flag in every entry and a test on every use, on every pass.

### Still decided on every pass

`interpret`, `eval` and `test` each begin by asking what kind of node they
are at, and the answer never changes: on 1071 and 462 the `if` inside gcd's
loop is reached on each of the loop's eleven passes, and asked each time.
Lesson 01.10 asks once: its code generator walks the tree a single time and
writes instructions, and the program that runs no longer holds the question.

## Decide the boundary

This interpreter runs the tree itself. Another could translate the tree once
more, into instructions for a simple machine of its own, kept one after
another in an array, and run those: the next step is the next entry of the
array, not a pointer to a node somewhere else in memory. That is a
**bytecode** machine, and chapter 16 builds one.

Crafting Interpreters builds both for one language, Lox: jlox walks the
tree, clox compiles to bytecode. Its chapter "Chunks of Bytecode" gives the
tree's costs as memory and locality, every node an object of its own reached
through a pointer, and in "Calls and Functions" the author finds clox about
five times faster than jlox on a recursive Fibonacci program. jlox is written
in Java and clox in C, so not all of that gap is the tree's.

The walk is the easier one to build, read and change, and each step it takes
is a step of the program you wrote. The bytecode machine costs a second
translator and a second format to keep right. How much of your programs' time
goes into getting from one node to the next, and would you write a second
translator to save it?

## Break it

Make the loop ask its condition once instead of before every pass. Taken
literally, that never ends: once the condition holds, nothing asks it again,
and the body runs forever. The nearest change that ends asks once and runs
the body once, as an `if` does. In `build/at/lang/01.09/interp.c`, in
`interpret`, change `while (test(s->cond))` to `if (test(s->cond))`, and build
again:

<!-- verify: patch file=interp.c old="while (test(s->cond))" new="if (test(s->cond))" -->

<!-- verify: session -->
```
$ make -s
$ ./mote programs/gcd.mote < programs/gcd.in

$ ./agree
gcd     mote0 ok  motec ok  mote DIFFERS
primes  mote0 ok  motec ok  mote DIFFERS
sum     mote0 ok  motec ok  mote DIFFERS
3 programs, 3 ways each: 3 differ
```

609 is 1071 - 462: the body ran once and the program went on to the `write`.
Nothing stops with an error; only the answer is wrong, and `agree` catches
it by holding the walker to what the other two ways print. Put the line back.
