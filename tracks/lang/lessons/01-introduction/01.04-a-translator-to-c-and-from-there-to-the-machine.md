# 01.04 A translator: to C, and from there to the machine

The second way to run a program of your language: translate it once, before
the run, into a C program, and let your computer's C compiler, assembler and
linker make that into a program that runs by itself. The translator works a
line at a time and understands almost nothing; everything hard is borrowed.
**Read first:** the rest of section 1.4, from Example 1.11 (pages 19 to 24), in Programming Language Pragmatics, 4th edition.

This lesson makes real a translator that does its work and goes away (Example
1.7), the library and the linker (1.11), assembly on the way (1.12), the
preprocessor (1.13), and another high-level language as the target (1.14).

## Where this fits

![Where 01.04 fits](figures/01.04-map.svg)

This lesson is the middle road of the map. The translator takes the same text
as the interpreter of lesson 01.03 and gives back a C program. Your computer's
C compiler, assembler and linker, drawn hollow because they are not this
track's, make that into a program for your computer, with the routines of
lesson 01.02 joined in by the linker. After this lesson every program of your
language can be made into a program of your computer.

## The idea

![From gcd.mote to a program your computer runs: the stages, and the file each one leaves.](figures/01.04-stages.svg)

`mote0` reads every line each time it runs it. A translator reads each line
once, before the run, and writes something that runs without it. Writing
machine code is the work of the compiler that lessons 01.06 to 01.10 build,
but there is a shorter road: your language's statements are close to C's, its
operators are C's, and your computer has a C compiler. So `mote2c` writes a
line of C for each line of the program: `read i` becomes `i = getint();`,
`write e` becomes `putint(e);`, `x := e` becomes `x = e;`, `while c do` and
`if c then` open a C block, `else` is `} else {` and `end` is `}`. The C
compiler does the rest, and the program it makes needs nothing of this track
but `rt.o`.

![The translator works a line at a time: each line of gcd.mote and the line of C it becomes.](figures/01.04-line-for-line.svg)

### `find_names` and `translate`

The first pass keeps every name that `read` or `:=` gives a value, once, so
that the C can declare them all at the top. The second makes each line into
its line of C by its first word; a condition, the text between `while` and
`do` or `if` and `then`, is copied into parentheses. Only the line's form is
checked: `do` or `then` at its end, `:=` after a name, nothing after `read x`,
`else` or `end`.

### the C program

`#include "rt.h"`, `int main(void) {`, a `long` for each name, set to 0, then
the program's lines, indented as they were, and `return 0;`. A line that is
only a comment is dropped; a blank line stays.

### `motec`

<!-- verify: mention names="build/NAME.c" outside reason="the file motec writes, named after the program; not part of the project" -->
The road as a script: `mote2c` into `build/NAME.c`, the C compiler into an
object file, the linker with `rt.o` into `build/NAME`. A step that fails stops
it, with that step's status.

## Run it

<!-- verify: session wait=10 -->
```
$ ./learn run lang --at 01.04
Running lang as it stands at 01.04 (A translator: to C, and from there to the machine). Its files are in build/at/lang/01.04/
21
```

That is `./motec programs/gcd.mote && build/gcd < programs/gcd.in`. Now the
same road a stage at a time. First the translator:

<!-- verify: session -->
```
$ cd build/at/lang/01.04
$ ./mote2c programs/gcd.mote > build/gcd.c
$ cat build/gcd.c
#include "rt.h"

int main(void) {
    long i = 0;
    long j = 0;
    i = getint();
    j = getint();
    while (i != j) {
        if (i > j) {
            i = i - j;
        } else {
            j = j - i;
        }
    }
    putint(i);
    return 0;
}
```

Then the C compiler's own stages, which `cc` runs one after another unless
told to stop. These are from an Apple M4 Pro Mac with Apple clang 21; yours
will differ in the details. `-E` stops after the **preprocessor**, which
carries out the lines that start with `#` (Example 1.13):

<!-- verify: skip reason="this computer's C preprocessor (Apple clang 21.0.0, macOS 26.6): the reader's output differs" -->
```
$ cc -E -I. build/gcd.c
...
# 1 "./rt.h" 1




long getint(void);
void putint(long n);
# 2 "build/gcd.c" 2
...
```

`rt.h` is pasted in place of the `#include`, its comments blanked; the `#`
lines tell the compiler which file each piece came from. `-S` stops after the
compiler, with assembly (Example 1.12):

<!-- verify: skip reason="this computer's C compiler (Apple clang 21.0.0, arm64): the reader's assembly differs" -->
```
$ cc -O1 -fwrapv -I. -S -o build/gcd.s build/gcd.c
$ grep -E 'getint|putint' build/gcd.s
	bl	_getint
	bl	_getint
	bl	_putint
```

The calls name `getint` and `putint` (with a `_` in front, on this Mac), which
nothing here defines. `-c` goes on through the assembler, to an **object
file**:

<!-- verify: session -->
```
$ cc -O1 -fwrapv -I. -c -o build/gcd.o build/gcd.c
```

<!-- verify: skip reason="this computer's nm (Apple LLVM 21, Mach-O): the reader's symbols differ in form" -->
```
$ nm build/gcd.o
                 U _getint
0000000000000000 T _main
                 U _putint
0000000000000000 t ltmp0
0000000000000058 s ltmp1
```

`nm` lists an object file's names: `T` for code defined here, `U` for a name
used here and defined elsewhere. The file is incomplete until the **linker**
joins it with `rt.o`, which defines the two (Example 1.11):

<!-- verify: session -->
```
$ cc -o build/gcd build/gcd.o rt.o
$ build/gcd < programs/gcd.in
21
```

`./motec` does those stages in one. Now the two ways side by side: a long run,
gcd on 1 and 10000000, timed on the same Mac (best of three):

<!-- verify: skip reason="timings, on one computer (Apple M4 Pro, macOS 26.6, zsh's time)" -->
```
$ echo '1 10000000' > big.in
$ time ./mote0 --count programs/gcd.mote < big.in
1
70000004 lines read
./mote0 --count programs/gcd.mote < big.in  1.21s user 0.00s system 99% cpu 1.220 total
$ time build/gcd < big.in
1
build/gcd < big.in  0.01s user 0.00s system 93% cpu 0.010 total
```

<!-- verify: fact cmd="echo 1 10000000 | ./mote0 --count programs/gcd.mote 2>&1 > /dev/null | cut -d' ' -f1" expect=70000004 -->
Over a hundred times faster, here; yours will differ. `mote0` read 70000004
lines and searched its table for `i` and `j` on every use; the compiled
program runs a handful of instructions a pass. (Not `sum.mote`: at `-O1` this
C compiler replaces its loop with a formula, and leaves no loop to time.)

![What is decided when. The interpreter decides everything while the program runs, on every pass of the loop; the translator and the C compiler decide it once, before.](figures/01.04-when.svg)

Then a mistake. `mote0` names the line of your program:

<!-- verify: session -->
```
$ printf 'x := 1 +\nwrite x\n' > oops.mote
$ ./mote0 oops.mote
oops.mote:1: expected a number, a name or '('
```

`motec` passes the line through, and the C compiler complains, in C's terms,
about line 5 of a file you never wrote:

<!-- verify: skip reason="the C compiler's message (Apple clang 21.0.0): the reader's differs" -->
```
$ ./motec oops.mote; echo $?
build/oops.c:5:12: error: expected expression
    5 |     x = 1 +;
      |            ^
1 error generated.
1
```

By the book's own test in Example 1.14, a compiler understands its input, and
a preprocessor need not and may pass on text that fails further on. By that
test `mote2c` is a preprocessor, and the compiler on this road is the C
compiler. Lessons 01.06 to 01.10 build one that understands your language.

## How it works

### Two passes, because C declares first

C wants a variable declared before its first use, and your language makes a
name when the text first gives it a value, perhaps deep inside a loop. So the
first pass collects the names and the second writes the C, with every
declaration at the top:

```
    printf("    long %.*s = 0;\n", lens[k], names[k]);
```

The `= 0` also removes a check: under `mote0`, `write x` before `x := 1` stops
with `x has no value yet`; translated, it prints 0.

### Expressions go through untouched

The operators are C's, by the decision of lesson 01.02, so an expression is
copied character for character. That keeps `mote2c` short, and leaves every
expression unchecked until the C compiler sees it. Copying is not
understanding, either: C gives a number written without a suffix the first
type it fits in, and a number that fits in 32 bits is an `int`, so C works out
`18 * 1000000007` in 32 bits.

<!-- verify: session -->
```
$ printf 'write 18 * 1000000007\nx := 18\nwrite x * 1000000007\n' > wide.mote
$ ./mote0 wide.mote
18000000126
18000000126
```

<!-- verify: fact cmd="./motec wide.mote 2> /dev/null && build/wide | head -1" expect=820130942 -->
The program `./motec wide.mote` makes prints 820130942 on its first line,
where every other way prints 18000000126 (clang warns of the overflow on this
Mac); the second line, with `x`, is worked out as a `long`, and is right.
Other gaps of the kind, met by no program in `programs/`: a number written
with a leading 0, which C reads as octal; a name that is a C keyword; and a
division by zero, which `mote0` reports at its line and C leaves undefined.

### `-fwrapv`

Your language says `+`, `-` and `*` wrap around. C says a signed overflow is
undefined: it may wrap, trap, or be optimized away. `-fwrapv`, which GCC
documents and clang accepts, tells the compiler to wrap around:

```
cc -O1 -fwrapv -I"$here" -c -o "build/$name.o" "build/$name.c" || exit
```

## Decide the boundary

Translating to C borrows a compiler: a back end, an assembler and a linker
that someone else wrote and keeps right, on every computer that has a C
compiler, and the speed above. The price is that errors arrive in C's terms,
about a file the programmer never wrote, and the language can say only what C
can, in C's way, as `wide.mote` showed. Writing your own compiler pays the
other price, every instruction yours to get right; lesson 01.10 pays it.
Examples 1.15 to 1.18 are for reading: this track writes your language in C,
as the book suggests for a first compiler (1.15); bytecode and compiling at
the last moment (1.16, 1.17) come back in chapter 16; microcode (1.18) is
below anything the track builds. Is the language yours if another language's
compiler decides what its programs mean?

## Break it

Make the first pass miss the names that `read` gives a value. In
`build/at/lang/01.04/mote2c.c`, in `find_names`, change the line after the
test for `"read"` so that it reads `n = 0;`:

<!-- verify: patch file=mote2c.c old="n = word(s = skip(s + n));" new="n = 0;" -->

Build it, and look at what it writes for `sum.mote`:

<!-- verify: session -->
```
$ make -s
$ ./mote2c programs/sum.mote | sed -n 3,6p
int main(void) {
    long sum = 0;
    long i = 0;
    n = getint();
```

`n` is used and never declared. The C compiler finds it, on a file you never
wrote:

<!-- verify: skip reason="the C compiler's messages (Apple clang 21.0.0): the reader's differ" -->
```
$ ./motec programs/sum.mote; echo $?
build/sum.c:6:5: error: use of undeclared identifier 'n'
    6 |     n = getint();
      |     ^
build/sum.c:9:17: error: use of undeclared identifier 'n'
    9 |     while (i <= n) {
      |                 ^
2 errors generated.
1
```

<!-- verify: fact cmd="./motec programs/sum.mote > /dev/null 2>&1; echo $?" expect=1 -->
`motec` stops with status 1, and nothing says the mistake was in the
translator.

<!-- verify: fact cmd="./motec programs/gcd.mote > /dev/null 2>&1 && build/gcd < programs/gcd.in" expect=21 -->
`gcd.mote` still compiles and prints 21, because `:=` gives its `i` and `j`
values too. Put the line back.
