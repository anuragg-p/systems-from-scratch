# 01.11 Code improvement: variables kept in registers

Most of what lesson 01.10's code does is move values between memory and
registers. This lesson keeps the variables in registers instead, and gcd's
compiled loop comes out as the one written by hand in lesson 01.01.

**Read first:** section 1.6.4, then the chapter's summary, section 1.7 (pages 36 to 38), in Programming Language Pragmatics, 4th edition.

Example 1.27 improves Figure 1.7's naive code until it is Example 1.2, the
program the chapter opened with; here `./mote -S -O` does that to lesson
01.10's code for `gcd.mote`, and what comes out is `programs/gcd.s` but for
one jump.

## Where this fits

![Where 01.11 fits](figures/01.11-map.svg)

This lesson is the improver, between semantic analysis and the code generator
on the right road's right-hand fork. It takes the syntax tree and the symbol
table, writes its decisions into the table, and the code generator of lesson
01.10 reads them; it runs when `mote -S` is given `-O`. With it the map is
whole: five ways to run one program, and `agree` holding them to one answer.

## The idea

![gcd.mote compiled twice: on the left every use is a load and every assignment a store; on the right `i` and `j` live in `s1` and `s2`.](figures/01.11-before-after.svg)

<!-- verify: fact cmd="./mote -S programs/gcd.mote > build/f.s && ./machine --trace build/f.s < programs/gcd.in 2>&1 | grep -cE '^ +[0-9]+  (ld|sd) '" expect=82 -->
Of the 142 instructions lesson 01.10's gcd runs on 1071 and 462, 82 are loads
and stores, there because each variable lives in memory. If a variable can
stay in a register for the whole program, they go: a use is the register
itself, and an assignment writes the register.

It can stay there only while nothing but the program's own assignments
changes it. That is section 1.6.4's warning, and in chapter 1's language it
always holds: a variable is reached only through its name, and the routines
a program calls, `getint` and `putint`, change only `a0` on this machine.

So the **improver** chooses which variables get one. It counts how often each
appears in the tree and gives `s1` to the most used, `s2` to the next, and so
on to `s11`; any others stay in memory. The code generator then uses the
register wherever the variable appears, as an operand and as the destination
of an assignment: `i := i - j` is `sub s1, s1, s2`, one instruction where
lesson 01.10 wrote four.

### `count`

Every appearance of every variable under a node, as a target or an operand,
added up in its entry's new field `uses`.

### `improve`

Eleven rounds: in each, the entry with the most uses and no register yet gets
the next of `s1` to `s11`, in its new field `reg`. In `gen.c` a variable with
a register has no slot, and `operand`, `into`, `store` and the assignment use
the register; `main.c` calls `improve()` before `generate()` when given `-O`.

The improved listing has no `ld`, no `sd`, and no `addi sp`: with no
variable left in memory there is no frame. Set it against the loop of
`programs/gcd.s`:

```
loop:
    beq  s1, s2, done     # until i == j:
    ble  s1, s2, smaller  #   the larger one loses the smaller
    sub  s1, s1, s2       #   i = i - j
    j    loop
smaller:
    sub  s2, s2, s1       #   j = j - i
    j    loop
done:
```

<!-- verify: fact cmd="grep -v '^#' programs/gcd.mote | grep -ow i | wc -l" expect=7 -->
<!-- verify: fact cmd="grep -v '^#' programs/gcd.mote | grep -ow j | wc -l" expect=6 -->
Both are 14 instructions. Both keep `i` in `s1` and `j` in `s2`: in gcd.s
because its author chose to, here because `i` appears 7 times and `j` 6.
Both leave the loop with `beq` and pick the arm with `ble`. The labels
differ, numbers against names. And the first arm differs: by hand it jumps
back to `loop`; compiled, it jumps to `.L4`, the end of the `if`, where the
`while`'s `j .L1` waits: a jump to a jump.

<!-- verify: fact cmd="./mote -S -O programs/gcd.mote > build/f.s && ./machine --trace build/f.s < programs/gcd.in 2>&1 | grep -c '  j    .L4'" expect=8 -->
It runs once on each of the 8 passes where `i` is the larger, which is the

only a jump and send `j .L4` straight to `.L1`; chapter 17 builds the

## How it works

### Safe here, and why it stops being safe

A register holds a copy of the variable that nothing else knows about, right
only while every change goes through it. Here that is so, for the two
reasons above. On a real RISC-V computer `getint` and `putint` would be code
linked in, as `rt.o` was in lesson 01.04, and the calling convention says a
routine must give back `s0` to `s11` as it found them, while it may change
`t0` to `t6` and `a0` to `a7`: hence the `s` registers.

Later chapters take the safety away. Chapter 3 brings functions and with them
a variable another function can change; chapter 8 brings arrays, where `a[i]`
and `a[j]` may be the same place. An improver then has to know that nothing
else can reach a variable before it keeps one in a register.

### Which variables, and why eleven

![Which variables get a register: counted by use, the most used first, eleven at most.](figures/01.11-who-gets-a-register.svg)

The `s` registers are `s0` to `s11`, and by the calling convention `s0` is
the frame pointer when a routine has one, so the improver leaves it alone:
eleven. In each round the best so far is replaced only by a count larger than
its own, so a tie goes to the lower index:

```
      if (!v->reg && (!best || v->uses > best->uses))
        best = v;
```

<!-- verify: fact cmd="grep -v '^#' programs/primes.mote | grep -ow p | wc -l" expect=8 -->
In `primes.mote`, `p` appears 8 times, `d` 7, `prime` 3 and `n` twice, so
`n` gets `s4` and `p` gets `s1`:

<!-- verify: session -->
```
$ ./mote -S -O programs/primes.mote | head -4
main:
    call getint
    mv   s4, a0
    li   s1, 2
```

### Marks, not a new tree

The improver changes no node; it marks entries of the symbol table, and the
code generator reads the marks. Whether a variable may live in a register
depends on the language, on what else can reach it; which register depends
on the machine, here one of eleven. `improve()` makes both decisions in one
loop; as the language grows, the first becomes the hard one.

The **invariant** is that the improved program prints what the unimproved
one prints, and `agree` holds it: its `machine` and `machine -O` columns run
the same generator's code without and with the improver.

### The chapter, whole

Chapter 1 has run one program, gcd on 1071 and 462, once by hand, and five
ways from its text, and each says 21. By hand, `programs/gcd.s` is the
computation written straight for the machine of lesson 01.01: the measure
the compiled code is set against. From the text: the first interpreter,
`mote0`, reading every line every time (lesson 01.03); the translator to C
and the computer's own compiler, `motec` (01.04); the tree walk, `mote`,
behind a front end of scanner, parser and analysis (01.06 to 01.09);
compiled for the machine, by the same front end and a code generator
(01.10); and compiled and improved, the same road with `-O` (01.11). Those
five are the five columns of `agree`, which holds every program in
`programs/` to the output written down for it.

Every piece is the smallest that works. Chapter 2 goes back to the first two
phases, the scanner and the parser, and builds them properly: the language's
tokens and grammar written down, and each half of the front end made a second
way from that description, printing the same tokens and tree as the first.

## Decide the boundary

This improver counts appearances in the text. Another would weigh each use
by how often it runs, a use inside a loop counting for more, and would let
two variables never needed at the same time share a register. In
`many.mote`, `b` is needed only until `c` is made, `c` only until `d`: two
registers would do for all twelve, `a` in one and `b` to `l` in the other,
each value replacing the one it was made from. Chapter 17 builds that; it
costs knowing, at every point of the program, which variables still have a
use ahead. Is counting in the text close enough for your programs, or do
your loops need the measured answer?

## Break it

Give two variables the same register. In `build/at/lang/01.11/improve.c`, in
`improve`, change `best->reg = s[r];` to `best->reg = s[r / 2];`, so each
register goes to two variables, and build again:

<!-- verify: patch file=improve.c old="best->reg = s[r];" new="best->reg = s[r / 2];" -->
<!-- verify: session -->
```
$ make -s
$ ./mote -S -O programs/gcd.mote | head -5
main:
    call getint
    mv   s1, a0
    call getint
    mv   s1, a0
$ ./agree
gcd     mote0 ok  motec ok  mote ok  machine ok  machine -O DIFFERS
primes  mote0 ok  motec ok  mote ok  machine ok  machine -O DIFFERS
sum     mote0 ok  motec ok  mote ok  machine ok  machine -O DIFFERS
3 programs, 5 ways each: 3 differ
```

The second `read` overwrites the first: `i` and `j` are both `s1`, always
equal, so the loop never runs and gcd prints 462. Only the improver's
decision is wrong, and the unimproved program, the `machine` column, still
agrees: it is what catches an improver's mistake. Put the line back.
