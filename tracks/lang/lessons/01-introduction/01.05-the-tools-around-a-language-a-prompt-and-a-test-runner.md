# 01.05 The tools around a language: a prompt and a test runner

A language is more than the program that runs it. This lesson adds two
tools around Mote: a prompt, where the first interpreter runs each line as
you type it, and `agree`, which runs every program every way there is and
holds each to the output it must print.
**Read first:** section 1.5 (pages 24 to 25), in Programming Language Pragmatics, 4th edition.

Section 1.5 is a list of the tools a programmer uses around a compiler.
This lesson builds the two your language needs first, and says where the
track builds the others.

## Where this fits

![Where 01.05 fits](figures/01.05-map.svg)

The prompt is the small cell inside the first interpreter on the map. It is
the same interpreter, given its lines one at a time by a person instead of
all at once from a file. The bar across the bottom is `agree`. It sits
under every road that ends in output, because its job is to collect what
each road printed for the same program and compare it with the one answer
written down in lesson 01.02. Above it are the two ways of running a
program that exist so far, the interpreter and the translator; the road
still dashed on the right brings three more ways to it by the end of the
chapter, each joining as it is built. After this lesson you
can try a line of the language without writing a file, and one command
says whether every way agrees on every program.

## The idea

![A session at the prompt: what is typed, what is held until the block ends, and the names after each line.](figures/01.05-prompt.svg)

To try `write 6 * 7` with `mote0` as lesson 01.03 left it, you write a
file and run it. But an interpreter stays while the program runs, as
section 1.4 described it, and one that stays does not need a
whole program before it starts: it can run a line, keep its table of
names, and wait for the next. That is a **prompt**.

Two questions decide how it behaves. When is a line run? `x := 6` can run
at once, but `while x > 4 do` cannot: what it repeats has not been typed
yet. So a line that opens a block is held, and so is every line after it,
until the `end` that closes the block. Then the held lines run together.
And what happens to a mistake? A program from a file stops at its first
error. At the prompt the error is reported, the names keep their values,
and the prompt comes back.

The second tool is about the five ways of running a program that chapter 1
builds. Lesson 01.02 wrote down, for each program in `programs/`, its input
and the output it must print. That is the language's standard. A standard
nobody checks drifts, so **agree** checks it: every program, every way,
the output compared with the expected one byte for byte. A way is a road
on the map; at this lesson there are two, `mote0` and `motec`.

![agree: the programs down the side, the ways across, and one expected output for each row.](figures/01.05-agree.svg)

The editor, the pretty printer and the style checker are yours to choose.
And the track adds one tool of its own, which a language with more than
one implementation needs from the start: `agree`.

### `prompt`

The loop that reads a line, adds it to the program's lines, and decides
whether it can run yet. `main()` calls it when `mote0` is given no file. It
asks for a line with `> `, or with `. ` while a block is open. The lines go
into the same array a file is split into, and run through the same `run()`
that runs a file's lines, so there is one interpreter, not two. The end of
the input (Control-D at a terminal) ends the session.

Around it, `error()` learns to come back here instead of ending the
program, and a `read` typed at the prompt takes its number from the next
line.

### `agree`

A shell script. For each program in `programs/` that has a `.in` and a
`.out` beside it, it runs every way with the `.in` on standard input,
keeps what each printed in `build/`, compares it with the `.out`, and
prints a row: `ok` or `DIFFERS` under each way. The last line counts, and
the exit status is 1 if anything differs. Which ways there are is one line
at the top, and how each way runs a program is a `case` below it.

## Run it

At this lesson the sample is `agree` itself:

<!-- verify: session wait=10 -->
```
$ ./learn run lang --at 01.05
Running lang as it stands at 01.05 (The tools around a language: a prompt and a test runner). Its files are in build/at/lang/01.05/
gcd     mote0 ok  motec ok
primes  mote0 ok  motec ok
sum     mote0 ok  motec ok
3 programs, 2 ways each: all agree
```

Six runs, and every one printed exactly its `.out`. Now the prompt: in
`build/at/lang/01.05`, start `mote0` with no file and type the lines after
each `>` and `.`. This is the session on an Apple M4 Pro Mac:

<!-- verify: skip reason="typed at mote0's own prompt: its '> ' and '. ' are not prompts the verifier knows for this track (track.py has no VERIFY_PROMPTS), so a typed line races the prompt; the next block replays the same lines from a file" -->
```
$ ./mote0
> x := 6
> while x > 4 do
. x := x - 1
. end
> write x
4
> write y
line 6: y has no value yet
> write x * 7
28
> ^D
```

The `while` line and the one after it were held: the prompt changed to
`. ` and nothing ran. The `end` closed the block, and the three lines ran
as one, twice round the loop. `y` has never had a value, so `write y` is
an error, reported with its line in the session (the sixth typed), and the
prompt came back with `x` still 4. At the last `>`, Control-D ends the
input and the session; some terminals show it as `^D`, some show nothing.

The prompt reads its lines from standard input, so the same lines can come
from a file:

<!-- verify: session -->
```
$ cd build/at/lang/01.05
$ printf 'x := 6\nwhile x > 4 do\nx := x - 1\nend\nwrite x\nwrite y\nwrite x * 7\n' > session.in
$ ./mote0 < session.in
> > . . > 4
> line 6: y has no value yet
> 28
>
```

Nobody types now, so only what `mote0` prints shows: a prompt each time it
waits for a line, and what the lines print. Two `> ` for `x := 6` and the
`while`, two `. ` while the block is open, a `> ` for `write x`, and 4.

## How it works

### Held until the block is whole

The prompt counts blocks the way `skip()` of lesson 01.03 does, by the
first word of each line: a `while` or an `if` opens one, an `end` closes
one.

```
    depth += is(w, len, "while") || is(w, len, "if") ? 1 : is(w, len, "end") ? -1 : 0;
```

While the count is above zero the line is only kept. When it comes back to
zero, everything typed since the last run goes to `run()`, from `first`,
the first line not yet run. This keeps an **invariant** that `run()` was
written for: the lines it is given hold every block whole, from its
`while` or `if` to its `end`, exactly as a file does. `run()` never meets
a block whose end has not arrived, so it needed no change at all.

The lines are never thrown away, which is why the error above says line 6:
the session is one program that grows, and a line's number is its place.

### Back to the prompt after a mistake

An error can happen anywhere: deep in `factor()`, in the middle of an
expression, in a loop. Run from a file, `error()` prints and calls
`exit(1)`. At the prompt it must instead abandon every call between it and
the prompt, and C has one tool for that: `setjmp` marks a place, and
`longjmp`, from anywhere below it, returns there.

```
    if (!setjmp(again))
      run(first);
```

`setjmp` returns 0 when it marks the place, so `run()` is called. If an
error happens, `error()` does this, after printing the message:

```
  if (!file)
    longjmp(again, 1);
```

and `setjmp` returns a second time, now with 1, so the prompt skips the
call and carries on. The table of names is not on the stack that
`longjmp` throws away, so every name keeps the value it had. A statement
that failed leaves its name as it was, because an assignment or a `read`
changes a name only after its value is worked out; in a block that failed
halfway, the statements before the error have done their work.

### A read at the prompt

At the prompt the program and its input come from the same keyboard. A
`read` takes the next number typed, on a line of its own, and no prompt
asks for it. Here the three lines are `read n`, `12` and `write n * 2`:

<!-- verify: session -->
```
$ printf 'read n\n12\nwrite n * 2\n' | ./mote0
> > 24
>
```

Two prompts before the 24: one for `read n`, one for `write n * 2`. The
12 was the read's. Its line end must not be taken for the next line of
the program, or an empty line would join the program, the prompt would
ask once more for nothing, and every line number after it would be one
too high. So `input()`, at the prompt only, drops the rest of the line
after the number.

### Bytes, not looks

`agree` compares with `cmp`, byte for byte, and only standard output: what
a way writes to standard error is kept in `build/` and not compared. Two
outputs that look the same can differ by a space at the end of a line or a
missing line end, and a check that forgives that lets two implementations
drift apart unnoticed. Break it, below, shows how little it takes.

Which ways there are is one line near the top of the script:

```
ways="mote0 motec"
```

That line is the second **invariant**, a rule about the track rather than
the code: a way is added in the lesson that builds it, and from then on
every program must pass it, every time `agree` runs. Lessons 01.09, 01.10
and 01.11 each add one. A program joins by putting its `.mote`, `.in` and
`.out` in `programs/`: from then on every way must run it.

## Break it

Lesson 01.02 broke the standard by hand. Break it again, and let `agree`
find it. In `build/at/lang/01.05/rt.c`, in `putint()`, change
`printf("%ld\n", n);` to

<!-- verify: patch file=rt.c
-  printf("%ld\n", n);
+  printf("%ld", n);
-->
<!-- verify: skip reason="the line as the reader changes it; the patch above makes the change" -->
```
  printf("%ld", n);
```

and build again, then run `agree`:

<!-- verify: session exit=1 -->
```
$ make -s
$ ./agree
gcd     mote0 ok  motec DIFFERS
primes  mote0 ok  motec DIFFERS
sum     mote0 ok  motec DIFFERS
3 programs, 2 ways each: 3 differ
```

Every program compiled by `motec` now prints its numbers with nothing
between them; `mote0` does not use `rt.c` and still prints what it should.
The exit status is 1, so a script or a `make` rule that runs `agree` stops
here. What the broken way printed is in `build/`:

<!-- verify: session -->
```
$ cat build/primes.motec.out; echo
2357111317192329
```

Ten primes, one number to the eye. The program is still right; only the
agreement about what a line of output looks like is broken, and that is
enough to fail. Put the line back.
